# 专家团协作规范

jiuwenswarm 专家团（agent_group）的实际调度由 swarm 装配层完成，不是靠 persona 里的"模拟发言"。本规范说明哪些是**包规范强制的硬约束**，哪些是**persona / AGENT.md 里建议的协作约定**。

---

## 一、包规范硬约束（校验器强制，违反则 expert.load 失败）

1. 顶层 `agents` 必须含 `"leader"`（固定主理人位）
2. leader 子包必须有 `AGENT.md`；非 leader 成员**禁止** `AGENT.md`
3. 成员 `agentCard.id` 须等于成员目录名
4. 成员级禁止 `rails` / `subagents`
5. `persona.dir` 指向的目录必须有 `*.md`
6. 所有路径包内相对、禁止逃逸

---

## 二、装配层语义（agent_group.py:load_agent_group_package）

- 顶层 `instruction` → 注入每个成员的 `agent_group_instruction` section（priority 20）
- 顶层 `skills` 共享技能 → 合并进每个成员的 skills（去重保序）
- leader 的 `AGENT.md` → 注入 `agent_group_leader_rules` section（priority 15）
- 成员模板经 agent-core loader 二次解析（双保险）

## 三、成员命名规范

专家团每位成员对外暴露三样信息：`agentCard.name`（展示名）、`agentCard.description`（职业定位）、所在目录名（id）。三者各司其职，不应出现重复。

### name：带职能彩蛋的人名

| 规则 | 说明 |
|------|------|
| 建议三字 | 按真实姓名的节奏起，两字亦可 |
| 像个真人名 | 不加任何解释，别人也认为它是名字 |
| 藏一点巧思 | 谐音、拆字、化用成语皆可，自然一点 |
| 与 description 分工 | name 回答"这是谁"，description 回答"做什么" |

**示例（数据分析团队）：**

| description | name | 巧思 |
|------|------|------|
| 数据分析 | 甄能算 | 真能算（算得准） |
| 可视化设计 | 贺出彩 | 何出彩 → 贺出彩（出彩） |
| 增长策略 | 涂破局 | 图破局（破局） |
| 用户研究 | 辛知微 | 心知微（见微知著） |
| 质量保障 | 杜纰漏 | 杜绝纰漏 |

**禁止：**

- 目录名（id）用中文名
- 单字 name，或拿职能词直接当 name
- name 与 description 语义重复
- 随手起的无信息名（小明、Tom）
- 叠音收尾的取名（"数灵灵""稿妥妥"式）
- 读起来像口号、短语，而非人名

### 主理人 description 规范

leader 的 `description` 不能落在泛化头衔上（团长、主理人、Team Lead 之类），要写出这支团队的打法和业务落点。

**示例：**

| 专家团 | 主理人 name | description |
|--------|-----------|---------------|
| 财务经营团队 | 计深远 | 财务统筹官 |
| 法务合规团队 | 程守正 | 合规把关人 |
| 市场增长团队 | 常开疆 | 增长开拓者 |

## 四、协作铁律（写入 leader AGENT.md）

### 4 条正则

1. **建团**：任务启动时由主理人划定协作边界、明确分工；建团动作只能由主理人完成，不得下放给任何成员。
2. **派活**：按 SOP 各阶段点名成员入团、分配独立任务；成员是独立产出方，主理人不越俎代庖。
3. **中转**：成员产出一律先交回主理人，由主理人汇总后流向下一棒；成员之间不建立直达通道。
4. **采信成员**：专业结论以对应成员的输出为准，主理人只做编排与汇编，不改写结论。

### 5 条红线

-  跳过建团，自己一人分饰多角、并行虚构成员发言
-  替成员代笔任何专业产出
-  前序阶段尚未收口就抢跑后续阶段
-  成员私聊直连、绕开主理人
-  主理人把编排、汇总、决策再外包给派生出的调度者

### 协作规则

1. 调度一律走"建团 → 点名派活 → 成员回传"的固定链路
2. 阶段交接传递完整产出原文，不做摘写删减
3. 点名成员用其 **id**（`agents/` 下的目录名），不写中文名或临场造名
4. 结论型角色（评审、风控之类）必须落到明确结论，不允许含糊收场
5. 每阶段收尾向用户同步一次进度
6. 输出语言跟随用户的提问语言

> 注：jiuwenswarm 的实际多角色调度由 swarm runtime（`assembly.py` 七步装配 + `TEAM_MEMBER_IDENTITY` rail）完成，不是靠 leader "自己模拟成员发言"。AGENT.md 里的铁律描述**期望的调度形态**，swarm 会遵循——不需要在 persona 里写"我来 spawn 某成员"的实现细节。

## 五、SOP 工作流编排

### 并行 vs 串行

- **并行阶段**：一轮消息里同时派出多个成员，适合彼此没有输入依赖的任务
- **串行阶段**：等上一阶段全部交卷，把结论喂给下一阶段成员

### 示例 SOP

```
阶段 1（并行）：
  market-scanner → 行业与竞品动态
  voice-listener → 用户口碑与舆情
  price-watcher  → 竞品定价与促销

阶段 2（串行，汇入阶段 1 结论）：
  strategy-maker → 输出打法建议

主理人汇编 → 交付
```

### 预设 Workflow 设计原则

每个 Workflow 固定写清三件事：
- **命中场景**：哪些问法会触发它
- **阶段编排**：成员怎样串并行接力
- **数据流向**：每阶段吃什么、交什么

数量贴合用户真实的高频场景来定，宁精勿滥。

## 六、与 swarm 装配的关系

> 专家团被 `expert.load` 加载后，由 `agents/swarm/assembly.py` 的专家团组装七步
> 装配为 TeamAgentSpec：基础 spec enrich → 团覆写（leader/teammate + 共享 skills）→
> 身份文本渲染。persona 的协作约定会进入 leader/teammate 的系统提示词，但**实际
> 的多进程/多通道调度由 swarm runtime 完成**，不是靠 leader "自己模拟成员发言"。

因此 persona / AGENT.md 里的协作铁律应描述**期望的调度形态**，而非"我来 spawn 某成员"的实现细节（实现由 swarm 接管）。
