# 意图驱动家居控制技能

## 🚨 核心设计思想（你必须理解并遵循）

**本技能不是"场景模板匹配"——不是把"我要睡觉了"映射到"睡眠场景"再映射到"关灯、空调睡眠模式"。**

正确的流程是：

```
用户输入(如"我要睡觉了")
    → 理解意图：用户想睡觉
    → 推理需求：睡觉需要 "暗、安静、凉爽、安全、舒适、放松"
    → 查询设备：家里有什么设备能满足这些需求？
        - 暗？→ 有灯 → 关掉或调暗
        - 凉爽？→ 有空调 → 睡眠模式或调温
        - 舒适？→ 有智能床 → 调平躺模式
        - 安静？→ 有音箱 → 音箱停止播放
        - 安全？→ 有门锁 → 检查
    → 覆盖度审计：检查是否有设备被漏评（新增）
    → 执行控制：逐个执行
    → 汇报结果
```

**绝对禁止的做法：**
- ❌ 查表匹配场景模板（"这是睡眠场景，第1步关灯，第2步空调..."）
- ❌ 写死某个场景的设备操作步骤
- ❌ 用户说一样的话就走一模一样的流程

---

## 功能说明

1. **理解用户意图** — 用户说人话，你就听懂他想要什么样的环境
2. **推理需求** — 这个意图需要什么样的环境条件（光照、温度、气流、噪音、安全、舒适、放松）
3. **查询设备** — 家里有什么设备能满足这些条件
4. **动态发现** — 对未知设备类型做服务能力动态发现，不遗漏任何设备（新增）
5. **覆盖度审计** — 对比已评估设备与全部设备，确保无遗漏（新增）
6. **动态控制** — 只有存在且相关的设备才去控制
7. **异常提醒** — 参考异常场景处理规范

## 核心原则

- **意图→需求→设备→控制**：四步走，不跳过
- **先查后控**：先获取设备列表和状态，确认用户家里有什么设备
- **动态适配**：家里有什么就控制什么，没有就跳过。**不要提家里不存在的设备**
- **在线优先**：先查在线状态，离线设备标注⏳，不重复发送
- **房间边界**：睡眠/起床/降温/勿扰 → 只动用户所在房间+公共区域；离家/回家 → 可动全屋
- **设备覆盖度校验**：**必须**对比"全量设备"和"已评估设备"的差异，对遗漏设备做能力发现（新增）
- **控制失败≠推荐购买**：绝对禁止在场景控制失败后推荐用户买新设备

## 🚨 异常场景处理规范

### 异常场景1：设备离线或不可用（状态兜底）

**触发条件**：调用设备时返回 `Offline` 或 `Unreachable` 错误码

**处理流程**：
1. 设备离线时，发送一次控制命令，标注 ⏳
2. **必须生成弥补策略**：
   - 查找同类替代设备（如空调离线→开风扇）
   - 如无替代设备，使用安抚话术
3. 向用户提供解决方案或建议

**话术示例**：
```
接收到您的降温需求，但客厅空调当前不在线，已为您打开客厅风扇，需要帮您检查空调网络吗？
```

---

### 异常场景2：意图指代不明或多目标冲突（澄清反问）

**触发条件**：多个设备符合条件，无法通过空间感知确定唯一目标

**处理流程**：
1. 当存在多个符合条件的设备时，**挂起当前 Action**
2. 向用户发起澄清反问，**不直接执行任何设备**
3. 等待用户明确目标后，再执行控制

**话术示例**：
```
好的，请问是调暗客厅的主灯还是卧室的台灯？
```

**空间感知优先级**：
- 用户明确说了房间名 → 使用该房间设备
- 能通过上下文推断用户位置 → 按位置匹配
- 无法推断 → 必须澄清

---

### 异常场景3：安全限制与敏感操作拦截（高危熔断）

**触发条件**：用户指令涉及安防设备（门锁、摄像头）或大功率电器

**安全设备列表**：
- 智能门锁（lock）
- 摄像头（camera）
- 烤箱、取暖器等大功率电器

**处理流程**：
1. 识别到敏感操作意图，**直接拦截**
2. 返回安全提示，要求显性确认
3. **绝不通过模糊指令自动触发**

**话术示例**：
```
安全起见，开锁需要您提供明确的语音指令或进行身份验证。
```

---

### 异常场景4：指令超出设备物理能力边界（合法性校验）

**触发条件**：用户指定的参数值超出设备注册的 Value_Range

**处理流程**：
1. MCP 层进行边界拦截
2. 获取设备支持的合法参数范围
3. 自动调整到边界值并向用户说明

**话术示例**：
```
空调最低只能设到16度，已为您调整到16度
```

---

## 🧠 场景记忆优先（用户教的习惯）

> 用户主动设定过习惯的场景，直接按用户记忆执行。没记忆的场景，走标准动态推理。

### 检查逻辑

执行任何意图控制前，**先检查用户场景记忆**：

```bash
cat default-spec-skill/intent-scene-skill/user-scene-memory.json
```

**双路径流程：**

```
用户说"睡觉了"
  → 匹配 user-scene-memory.json 中的 triggers
  → 有记忆？ → 路径A：直接用记忆中的设备操作
  → 没有？   → 路径B：标准动态推理（意图→需求→设备→控制）
```

**路径A（有记忆）：**
- 按 `user-scene-memory.json` 中该场景记录的设备和操作执行
- 查询家中实际设备是否在线，在线则执行，离线则标记 ⏳
- 设备验证、汇总回复与路径B相同

**路径B（无记忆）：**
- 走下方标准四步流程（步骤1→2→3→4）

**关键区别：**
- 记忆只存"用户教我的"（用户主动设定或对话中明确要求的）
- 记忆不等于场景模板。**来源不一样**：模板是开发者预设的（❌），记忆是用户教的（✅）
- 用户的场景记忆可以随时修改/新增/删除

### 📝 用户场景记忆记录 -（两种来源）

**来源1：模糊指令 + 3分钟内调整**
- 模糊指令执行后，3分钟内用户对指令做出调整，将最终调整参数写入`user-scene-memory.json`

**示例：**
```
用户说"客厅太暗了"
→ 解析：场景=dark, 触发词=暗/太暗了/有点暗, 房间=客厅
→ 标准动态推理控制设备（吸顶灯和筒灯亮度调到最大）
→ 3min内用户调整控制的设备（吸顶灯亮度调到80）
→ 将用户修改指令后的场景写入 user-scene-memory.json
→ 回复："好的，以后您说太暗了，我会按照您的习惯进行亮度调节"
```

**来源2：用户主动触发**
当用户说"帮我记住"、"记下来"、"以后记得"、"每次xxx"、"你记住"、"你记一下"等习惯记录类指令时：

**流程：**
1. 解析用户的习惯描述，提炼出：{触发词, 房间, 设备, 操作}
2. 精确记录参数值：不只是记录“调亮”，要记录具体值如“亮度调到255”
3. 读取当前 `user-scene-memory.json`
4. 新增或修改对应场景的 `triggers`、`room`、`devices`、`timestamp`
5. 写回 `user-scene-memory.json`
6. 回复用户确认

**示例：**
```
用户说"帮我记住，睡觉时空调开除湿，留射灯1做夜灯"
→ 解析：场景=sleep, 触发词=睡觉/睡觉了/晚安, 房间=儿童房
→ devices = {空调: "除湿模式", 灯光: "保留射灯1做夜灯（最低亮度+暖色温），其余关闭"}
→ 写入 user-scene-memory.json
→ 回复："记住了，以后您说睡觉，我会开除湿、留射灯1当夜灯"
```

**注意：** 写文件使用 `write` 工具，确保 JSON 格式正确，不要破坏已有数据。

❌ **禁止写入记忆的场景**
- 标准推理执行完毕 -> 禁止写入记忆
- 用户没说“记住”类关键词 或 用户没在3分钟内做指令调整 -> 禁止写入记忆

## 执行步骤

### 步骤 0：场景记忆检查（优先于一切）

**先于步骤1执行：**

```bash
cat default-spec-skill/intent-scene-skill/user-scene-memory.json
```

**匹配逻辑：**
1. 遍历 `user-scene-memory.json` 中的场景
2. 对每个场景，检查 `triggers` 列表是否有字段匹配用户输入
3. 匹配上 → 执行路径A（记忆直接执行）
4. 没匹配上 → 走路径B（下方步骤1→4）

**路径A详细流程：**
- 从记忆场景中获取 `room`、`devices` 描述
- 查询该房间的设备列表，确认设备是否存在且在线
- 按记忆对每个设备执行操作 + 验证
- 汇总回复

### 步骤 1：理解意图 → 推理环境需求（路径B）

拿到用户的话，不要想着"这是什么场景"，而是想"用户想要什么样的环境"。

**意图示例与需求推理（仅供参考，不要死记硬背）：**

| 用户说... | 用户想要的是... | 所以需要...                                    |
|-----------|----------------|--------------------------------------------|
| 我要睡觉了/晚安/准备睡了 | 安静、暗、**舒适**、凉爽、安全的环境 | 关灯或调暗、空调睡眠模式、智能床调平躺/睡眠模式、检查安全、**音箱必须停止播放** |
| 出门了/离家/去上班 | 省电、安全 | 关灯、关空调、检查门窗                                |
| 回家了/到家了/回来了 | 明亮、舒适的环境 | 开灯、开空调                                     |
| 太热了/有点热/热死了 | 凉爽 | 空调制冷、风扇                                    |
| 天有点闷/空气不好 | 空气流通、干爽 | 开窗、除湿、通风                                   |
| 太冷了/有点凉 | 温暖 | 空调制热                                       |
| 太刺眼了 | 柔和光线 | 关灯、调暗、暖色温                                  |
| 看电影 | 暗、安静、沉浸的氛围 | 关灯、降低噪音、开大屏、**音箱暂停或音量调小**                  |
| 吃饭了/开饭了 | 温馨、放松 | 暖色灯光、背景音乐                                  |
| 起床了/早上好 | 明亮、提神、**舒适** | 开灯、开窗帘、恢复空调、智能床调起身姿态                       |
| 勿扰/不要打扰 | 安静、隐私 | 降低音响音量、关公共区域灯                              |

> ⚠️ **【强制】起床场景标准操作定义**
> 
> **"起床"场景包含 3 个必选维度：明亮 + 提神 + 舒适。**
> 
> | 维度 | 对应设备 | 标准操作 | 说明 |
> |------|---------|---------|------|
> | 明亮 | 灯类设备 | 恢复100%亮度+正常色温（约5000K） | 驱散睡意，营造清醒氛围 |
> | 提神 | 空调/空气设备 | 退出睡眠模式，恢复正常制冷/通风 | 避免闷热感 |
> | **舒适** | **智能床/按摩椅** | **调至起身姿态（头部抬起）** | **🆕 必选操作：只要目标房间有智能床/按摩椅且支持 headControl/modeSelect，必须执行调起身操作。不是"如果有就做"，而是"有就必须做"** |
> 
> **执行规则：**
> - 智能床调起身 **优先级等同于开灯**，两者同属"起床"的标准操作
> - 不要问用户"要不要调智能床"——直接执行
> - 如果智能床离线，标记 ⏳ 并告知用户

**🆕 新增/扩充的环境需求维度：**

| 维度 | 用户关键词 | 能匹配的设备服务                                      |
|------|-----------|-----------------------------------------------|
| 光照 | 暗、亮、柔和 | 灯类（light, switch, brightness, cct）、窗帘（opener） |
| 温度 | 凉爽、温暖 | 空调（mode, airKey）、风扇（switch, fan）              |
| 空气 | 干爽、清新 | 除湿机、净化器、空调除湿模式                                |
| 安静 | 安静、勿扰 | 音箱（volume, playControl）、大屏（power）                        |
| 安全 | 安全、离家 | 门锁（check only）、摄像头                            |
| **舒适/放松/助眠** 🆕 | 睡觉调平躺、起床调起身 | 智能床/按摩椅（modeSelect, headControl, legControl）  |
| 沉浸 | 看电影、氛围 | 大屏、音箱、灯光调暗                                    |

**关键规则：**
- **不要映射到场景名**，直接映射到"环境需求"
- **环境需求→设备操作** 是动态的，不同家庭有不同设备
- 例如"暗"这个需求，有窗帘家庭可以拉窗帘，有灯家庭可以关灯，有调光灯家庭可以调暗。**根据设备能力灵活操作**
- **🆕 舒适维度必须纳入睡觉/起床推理**——睡觉时智能床可调平躺，起床时可调起身

### 步骤 2：查询设备，匹配需求（路径B）

#### 2a：获取全量设备列表

```bash
# 获取目标家庭所有设备
node common-skill/bin/smarthome-claw.js get_devices_info
```

从中提取每个设备的：`deviceId`、`prodId`、`roomName`、`productName`、`deviceType`、`homeName`

**🆕 记录全量设备清单，为步骤2.5的覆盖度审计做准备。**

#### 2b：已知类型 → 标准映射（查表匹配）

以下为已知设备类型的标准映射表。如果设备 `deviceType` 在此表中，按标准规则匹配：

| `deviceType` | 品名(`productName`) | 能满足的环境需求 | 关键服务ID（sid）                                              | 操作说明                                                                                      |
|-------------|-----------------|----------------|----------------------------------------------------------|-------------------------------------------------------------------------------------------|
| A1A / A0E / 01B / A13 | 吊灯/筒射灯/射灯/台灯/开关 | 暗、亮、柔和 | `light/switch`(根据设备快照查询服务sid)、`brightness`(亮度)、`cct`(色温) | 关灯→on=0；调暗→brightness降低；暖光→cct色温降低                                                        |
| 012 / 1FA | 挂机空调/空调伴侣       | 凉爽、温暖、干爽 | `airKey`(空调码)、`switch`(开关)、`mode`(模式)、`sleepCurve`(睡眠曲线) | 制冷、制热、除湿需要依赖profile判断mode的枚举值、睡眠曲线，空调伴侣开/关判断以airKey.power(1开 0关) 为准，switch仅代表伴侣自身，不作为空调状态依据 |
| 01C | 开合帘/电机          | 暗、亮、柔和 | `opener`(开合)、`current`(当前位置)                             | 关闭→action=0、开启→action=1                                                                   |
| A0B | 智能门锁            | 安全 | —                                                        | 只读不控，安全熔断                                                                                 |
| 00A | 智能音箱            | 安静、沉浸 | `volume`(音量)    `playControl`(控制)                        | 降低音量->smartspeaker(sid) + volume调低; 停止播放-> smartspeaker + playControl(0:停止播放, 1:启动播放)     |
| 029 | 风扇              | 凉爽 | `switch`(开关)、`fan`(风速)、`mode`(模式)                        | 开启→on=1、关→on=0、调风速                                                                        |
| 013 | 空气净化器           | 清新、干爽 | `switch`(开关)、`mode`(模式)、`fan`(档位)                        | 开启自动模式或睡眠模式                                                                               |
| 02E / 09C | 大屏/智慧屏          | 沉浸、氛围 | `power`(电源)                                              | 开关                                                                                        |
| 025 | 体重秤             | 健康 | —                                                        | 不参与场景控制，跳过                                                                                |
| 008 | 网络摄像头           | 安全 | —                                                        | 只读不控，安全熔断                                                                                 |

#### 2c：🆕 未知设备类型 → 服务能力动态发现

**对于不在上表中的 `deviceType`，禁止静默跳过！必须执行以下发现流程：**

```bash
# 对该设备调用服务快照查询
node common-skill/bin/smarthome-claw.js get_device_service_snapshot_celia_claw --device-ids "<deviceId>"
```

解析返回的 `services[]` 数组，通过**服务名关键词匹配**来判断该设备能参与哪些场景：

| 服务名关键词（sid包含）                                                  | 能匹配的环境需求 | 说明 |
|----------------------------------------------------------------|----------------|------|
| `switch`（排除childLock/keytone/screen/light/UV/anion等子开关）        | 暗、亮 | 有关闭能力的设备可参与关灯场景 |
| `brightness` / `cct` / `colourMode`                            | 暗、亮、柔和 | 可调光的照明设备 |
| `modeSelect` / `headControl` / `legControl` / `headLegControl` | **舒适、放松、助眠** 🆕 | 智能床/按摩椅等身体姿态设备 |
| `mode`                                                         | 凉爽、温暖 | 多模式设备（需结合设备类型判断） |
| `fan` / `speed`                                                | 凉爽、清新 | 有风扇/风速能力的设备 |
| `volume` / 'playControl'                                       | 安静、沉浸 | 有音量调节的设备 |
| `opener` / `current`                                           | 暗、亮 | 开合类设备（窗帘/窗） |
| `sleepCurve` / `sleepMode`                                     | 凉爽、助眠 | 专门睡眠模式的设备 |

**匹配规则**：设备的 `services[]` 中只要有一个 sid 匹配到上表中的关键词，就纳入该环境需求的控制候选。

**🆕 动态发现示例：智能床**

假设设备返回以下服务快照：
```
services: [
  { serviceId: "modeSelect", data: { action: 6 } },
  { serviceId: "headControl", data: { action: 1 } },
  { serviceId: "legControl", data: { action: 0 } },
  { serviceId: "headLegControl", data: { action: 0 } }
]
```
- `modeSelect` → 匹配"舒适、放松、助眠"需求 → 可调睡眠/平躺模式
- `headControl` / `legControl` → 匹配"舒适、放松、助眠"需求 → 可调头/腿角度
- 结论：智能床有姿态调节能力，睡觉时可调平躺/睡眠模式，起床时可调起身

**兜底规则**：
- 服务名关键词**有匹配** → 纳入控制计划，控制参数从 `data` 中解析
- 服务名关键词**无匹配** → 跳过该设备，在步骤2.5审计日志中记录"已评估但无匹配服务"

### 🆕 步骤 2.5：覆盖度审计（校验是否有设备漏评）

**这是新增步骤。在步骤2完成、步骤3开始之前，必须执行。**

```
全量设备集 = 步骤2a中 get_devices_info 返回的所有设备ID（目标房间内的）
已评估设备集 = 步骤2b已知类型匹配到的 + 步骤2c动态发现匹配到的 + 明确标记跳过的
未评估设备集 = 全量设备集 - 已评估设备集
```

如果 `未评估设备集` 不为空：
1. 对每个未评估设备，调用 `get_device_service_snapshot_celia_claw` 做能力发现
2. 如果发现新能力，纳入控制候选
3. 如果确实无匹配能力，记录审计日志（不报错），继续执行
4. 覆盖度审计逐台核对 - 同品类设备（如多台音箱），必须每一台单独查在线状态，禁止使用一台代表整组

**审计日志格式（内部记录，不展示给用户）：**
```
[覆盖度审计] 目标房间：某房间
  全量设备：N台
  已评估设备：M台（映射表匹配A台 + 动态发现B台 + 标记跳过C台）
  未评估设备：K台 → 已做服务能力发现 → X台有匹配，Y台确认跳过
  覆盖率：100% ✓
```

**如果覆盖率 < 100% 且缺少审计说明，禁止跳过步骤3。必须完成审计才能构建控制计划。**

### 步骤 3：动态构建控制计划

**这是最关键的一步。不要用固定模板，而是根据步骤1的需求 + 步骤2的设备匹配 + 步骤2.5的确认，动态构建操作列表。**

**通用推理模式（每次动态构建，不查表）：**

```
步骤1产出的环境需求列表 → 逐条匹配：
  需求A（如"暗"） → 目标房间内有哪些设备能实现"暗"？
    - 有灯 → 可关灯或调暗
    - 有窗帘 → 可拉窗帘
    - 两者都有 → 都控制
    - 都没有 → 跳过此需求
  
  需求B（如"凉爽"） → 目标房间内有哪些设备能实现"凉爽"？
    - 有空调 → 设制冷/睡眠模式
    - 有风扇 → 开风扇
    - 两者都有 → 都控制
    - 都没有 → 跳过此需求

  需求C（如"舒适"） → 目标房间内有哪些设备能实现"舒适"？
    - 有智能床 → 调平躺/睡眠模式
    - 没有 → 跳过此需求
```

**示例：用户说"我要睡觉了"（纯示例，实际按设备清单动态构建）**

```
1. 需求分析：暗 + 凉爽 + 舒适 + 安静 + 安全
2. 设备匹配（动态）：
   - 暗 → 目标房间有灯类设备 → 关灯（⚠️ 【强制】必须是目标房间所有灯，包括台灯）或保留小夜灯
   - 凉爽 → 目标房间有空调 → 开睡眠模式或调温
   - 舒适 → 目标房间有智能床（通过2c动态发现）→ 调平躺模式
   - 安静 → 目标房间有音箱 → 音箱停止播放 （⚠️ 【强制】目标房间有音箱在播放时必须停止播放）
   - 安全 → 目标房间有门锁 → 只读检查
3. 控制计划：①关灯(留小夜灯，没有小夜灯时，禁止将台灯当小夜灯) → ②智能床调平躺 → ③空调开睡眠模式 → ④音箱停止播放
```

**示例：用户说"起床了/早上好"（纯示例，实际按设备清单动态构建）**

```
1. 需求分析：明亮 + 提神 + 舒适
2. 设备匹配（动态）：
   - 明亮 → 目标房间有灯类设备 → 恢复100%亮度+白光
   - 舒适 → 目标房间有智能床 → 调起身姿态（抬起头部）
3. 控制计划：①灯光恢复照明 → ②智能床抬起头部
```

**示例：用户说"太热了"**

```
1. 需求分析：凉爽
2. 设备匹配：
   - 凉爽 → 目标房间有空调 → 设制冷模式
   - 凉爽 → 目标房间有风扇 → 开风扇
3. 控制计划：①空调设制冷 → ②风扇开启（如有）
```

**示例：用户说"看电影"**

```
1. 需求分析：暗 + 安静 + 沉浸
2. 设备匹配：
   - 暗 → 有灯 → 关灯
   - 沉浸 → 有大屏 → 开屏
   - 安静 → 有音箱 → 调低音量/音箱停止播放（⚠️ 【强制】有音箱必须调低音箱音量或音箱停止播放）
3. 控制计划：①关灯 → ②开大屏 → ③音箱降音量
```

### 步骤 4：按序执行 + 强制验证结果

**串行执行规则：**
1. 每次控制一个设备
2. 控制顺序：按设备的房间位置（先公共区域，后目标房间），同房间的按自然顺序
3. 同一房间内：先处理环境类设备（温度/空气），再处理照明类设备，最后处理舒适类设备（智能床等）
4. 离线设备：发一次命令，标注⏳
5. 失败降级：跳过，不重复
6. 执行control_device_celia_claw接口，返回响应的数据中`failedList`中如果有报错信息，根据报错信息判断是否控制失败，禁止根据`allFailed`字段判断控制结果
7. 增加空调验证：
   对空调伴侣/码库/联动型设备，判定是否开启必须看反映真实运行的字段（power/运行模式），禁止用switch推断
   示例：
   ```
      关空调 -> POST sid='airKey' data={"power":0} -> 验证 services 中 sid='airKey' 的 data.power=0 ✅
   ```
```bash
node common-skill/bin/smarthome-claw.js control_device_celia_claw --dev-id "<deviceId>" --prod-id "<prodId>" --device-type "<deviceType>" --operation "POST" --sid "<服务ID>" --data '{"键":"值"}'
```

**【强制】验证操作结果（每条指令都必须执行）：**
发送控制指令后，必须按以下步骤验证控制是否真的生效：
1. 等待 **5~10秒** 让设备执行并上报状态
2. 调用 `get_device_detail_celia_claw` 主动查询该设备对应服务的实时状态
   ```bash
   node common-skill/bin/smarthome-claw.js get_device_detail_celia_claw --dev-id "<deviceId>"
   ```
3. 检查返回的 `data.services` 字段中`sid` = `控制的sid` 的data值是否与操作目标一致
   - 返回数据格式示例：
   `{
    "errorCode": "0",
    "errorMsg": "success",
    "data": {
        "services": [{
                "st": "binarySwitch",
                "ts": "20260805T092748Z",
                "sid": "switch",
                "data": {
                    "on": 1
                }
            }, {
                "st": "brightness",
                "ts": "20260805T030234Z",
                "sid": "brightness",
                "data": {
                    "brightness": 182
                }
            }
        ]
    }}`
   - 例如关闭灯光（sid=switch）应检查 data.services 中 `sid` = `switch`时`data`字段里面 `on` 值是否为 0
   - 例如关闭窗帘（sid=opener）应检查 data.services 中 `sid` = `opener`时`data`字段里面 `current` 值是否为 0 
   - 例如智能床调模式（sid=modeSelect）应检查 data.services 中 `sid` = `modeSelect`时`data`字段里面 `action` 值
4. 只向用户汇报 **确认后的实际状态**，而不是"指令已下发"
5. 后置检查 **强制执行** 在控制指令执行并验证完毕后，必须检查当前的指令是否为`参数调整操作`
- **回溯检查**：过去3分钟内，用户是否发出过模糊环境描述指令（如"有点暗"、"太热了"、"有点闷"、"睡觉"等描述环境状态的笼统表达, 但未指定具体参数值）?
- **关联判断**：如果当前指令是对模糊指令控制设备的属性（如调亮度、调温度、 调色温等），且发生时间在模糊指令的**3分钟内**，立即触发记忆**来源1**，按流程自动写入记忆user-scene-memory.json

**验证示例：**
```
【操作】关闭灯光 → POST sid='switch', data={"on":0}
【等待5秒】
【验证】get_device_detail_celia_claw → data.services, sid='switch'里面的'data': {"on":0} ✓ 确认已关闭
【后置检查】根据上下文判断这条控制指令是否是对模糊指令的调整，是 && 三分钟内 -> 触发记忆`来源1`，按流程自动写入记忆文件user-scene-memory.json； 否 -> 不做处理
【汇报】灯光已关闭
```

## 注意事项

1. **不要预设场景模板** — 每次都是动态构建控制计划
2. **不要写死设备操作** — 控制参数从服务快照中读取
3. **家里没有的设备不要提** — 没有窗帘就不说窗帘
4. **🆕 覆盖度审计必须执行** — 步骤2和步骤3之间必须对比设备清单
5. **🆕 未知设备类型必须做动态发现** — 禁止静默跳过，否则会漏掉智能床、按摩椅等新品类
6. **不要重复控制** — 同一个设备在一次交互中只发一次命令
7. **控制失败≠推荐购买** — 绝对禁止在场景控制失败后推荐用户买新设备
8. **房间边界** — 睡眠/起床/降温→只动用户房间+公共区域；离家/回家→可动全屋
9. **结合四季** — 选择设备可以结合当前季节使用频率高的设备操作
10. **profile备选** — 遇到未知设备类型但服务名关键词匹配成功，控制参数从该服务的data字段解析
