## 1. 工作流概述

### 两阶段探索式流程（v2.0 重构，v3.0保留）

```
输入 → P1验证 → P2归一化+路由+case_context → P3初步分类(L3)
                                                    ↓
                                          ┌── 交互点I1 ──┐
                                          │  输出：第一轮概览 │
                                          │  · 数据快照      │
                                          │  · TOP5异常信号  │
                                          │  · 建议深入方向  │
                                          │                │
                                          │  用户选择方向：  │
                                          └────────────────┘
                                                    ↓
                              P4深度异常(L2) → P5深度流向(L2) → P6 10区块HTML组装 → 输出
                                            ↓
                                    SOFT_DEGRADED判定
```

**v2.0-v3.0 核心变更**：
- P2 新增 `case_context` 加载——案件参考数据同步归一化，P3/P4/P5按需使用
- 新增 **交互点 I1**——第一轮概览→用户选择深化方向→P4/P5按选定方向深度分析
- P6 输出从"6段+附加块"重构为**10区块HTML完整结构**（v3.0），核心发现从四要素升级为六要素（+对方可能抗辩+策略影响评分）
- v3.0 移除所有Markdown输出通道，统一为HTML

### Phase风险标注

| Phase | 风险等级 | 原因 |
|-------|----------|------|
| P1 | L1 | 输入验证，无法律判断 |
| P2 | L1 | 数据归一化+case_context加载，无法律判断 |
| P3 | **L3** | 交易分类涉及法律定性（如"工资"vs"劳务费"），case_context提升精度 |
| **I1** | **L2** | 交互概览含异常信号初步判断，影响深化方向 |
| P4 | L2 | 异常检测涉及行为识别，case_context提升敏感度 |
| P5 | L2 | 资金流向分析涉及关联推断，case_context控制追踪深度 |
| P6 | L1 | 报告组装与质量检查，10区块HTML完整结构 |

## 2. Phase 1 输入验证与渠道识别

### 输入

- 用户原始输入（三种形态之一）

### 步骤

1. **输入形态判定**：识别IM1/IM2/IM3
2. **渠道识别**：从数据特征或用户标注识别渠道类型（bank/wechat/alipay/混合）
3. **案件类型检查**：确认case_type是否在CT1-CT6范围内
4. **硬拒绝检查**：H1-H3（见input-spec.md §7）
5. **软警告检查**：W1-W3，发出警告但继续

### 输出

- 输入形态：IM1/IM2/IM3
- 渠道清单：[bank, wechat, alipay] 子集
- 验证结果：通过/警告/拒绝
- 案件类型：CT1-CT6
- 附加信息：案件类型条件必需参数（分居日期/工资标准等）

### 检查点

- [ ] 至少识别出1个渠道
- [ ] 案件类型在CT1-CT6范围内
- [ ] CT5（刑事辩护）需有律师确认标记

## 3. Phase 2 数据归一化与案件类型路由

### 输入

- Phase 1验证通过的原始数据
- 案件类型CT1-CT6
- 用户输入的参考信息（将在本Phase结构化为case_context）

### 步骤

1. **数据归一化**：按渠道字段映射表（input-spec.md §3）转化为NormalizedTransaction
   - IM1结构化：直接映射，confidence=high
   - IM2半结构化：容错解析，confidence=medium
   - IM3自然语言：LLM逐条提取，confidence=low
2. **日期标准化**：统一为YYYY-MM-DD格式
3. **金额标准化**：统一为decimal类型，单位元
4. **方向标准化**：统一为"收入"/"支出"
5. **case_context 构建**（v2.0新增）：
   - 从用户输入中提取案型相关的参考数据，按 input-spec.md §4.1 定义的字段模型结构化
   - 区分 required / recommended / optional 三级必填性
   - 若有P1识别到的条件必需参数（如分居日期/工资标准等），直接填充到case_context对应字段
   - 若用户输入中未提供某些字段，标记为缺失，按降级规则处理
6. **案件类型路由**：加载对应CaseTypeSpec配置文件
7. **多渠道合并去重**：
   - 去重规则：同一天+同一金额+同一对方 → 可能重复
   - 处理方式：保留银行记录（优先级最高），标记其他渠道记录为"可能重复"

### 输出

- NormalizedTransaction集合
- **case_context 结构化对象**（v2.0新增）
- case_context 完整性评估（required字段缺失清单）
- 已加载的CaseTypeSpec配置
- 去重报告（若多渠道）
- 数据置信度评估

### 检查点

- [ ] 所有交易记录已归一化
- [ ] 方向标注与用户视角一致（非银行记账方向）
- [ ] case_context 已按案型构建，required字段缺失已标注（v2.0新增）
- [ ] CaseTypeSpec配置已加载
- [ ] 多渠道数据已尝试去重

### case_context 对后续Phase的影响（v2.0新增）

| case_context 完整性 | P3分类 | P4异常 | P5流向 | 输出 |
|---------------------|--------|--------|--------|------|
| required全部有 | 完整精度 | 完整敏感度 | 完整深度 | 10区块HTML完整报告 |
| required缺失1-2个 | 相关分类步骤跳过 | 相关异常规则跳过 | 深度降级 | 含"初步推断"标注 |
| recommended缺失 | 分类置信度降级 | 异常置信度降级 | 追踪范围缩减 | 含"建议补充信息"标注 |
| case_context完全缺失 | 按v1.0行为运行 | 按v1.0行为运行 | 按v1.0行为运行 | 10区块HTML+通用补充 |

## 4. Phase 3 按案件类型交易分类

### 风险等级：L3

本Phase涉及法律定性判断，如"备注劳务费"在劳动案中可能是工资争议焦点。必须按CaseTypeSpec配置的分类标签体系进行，每个标签附带法律要件说明。

### 输入

- NormalizedTransaction集合
- CaseTypeSpec配置
- **case_context**（v2.0新增——提升分类精度）

### 步骤

1. **加载分类标签体系**：从CaseTypeSpec读取该案件类型的分类标签
2. **加载 case_context 分类增强规则**（v2.0新增）：根据case_context中的参考数据，激活对应的分类精度提升规则
   - CT1：若有 separation_date，按分居日期前后分别标注分类倾向
   - CT2：若有 employer_name + agreed_salary，主动识别工资发放规律（即使用户未明确标注）
   - CT3：若有 principal_amount，将还款与本金进行金额级比对，精确区分本息
   - CT4：若有 payment_schedule，将付款与约定节点逐条匹配
   - CT5：若有 crime_period，按涉案期间过滤交易，精确区分涉案/非涉案
   - CT6：若有 execution_amount，将消费水平与执行金额对比，识别异常消费
3. **逐笔分类**：对每笔交易按标签体系进行分类
   - 优先匹配规则：备注关键词 > 交易模式 > 对手方特征 > case_context辅助判定
   - 分类不确定时标注置信度
   - case_context 加载后，部分原来标注"待定"的交易可获得更高置信度的分类
4. **法律要件映射**：每个分类标签附带法律要件说明
5. **法条检索**（§17.15强制契约）：涉及法律定性的分类结论，必须联网验证引用法条
6. **分类冲突处理**：同一笔交易匹配多个分类标签时，选择最具体的一个，标注其他可能分类

### 各案件类型核心分类维度

| 案件类型 | 核心分类维度 | 典型分类标签 | case_context 增强效果 |
|----------|-------------|-------------|----------------------|
| CT1婚姻家事 | 财产归属 | 共同财产支出/个人消费/疑似转移/待定 | 分居日期锚点使"疑似转移"识别精度提升 |
| CT2劳动争议 | 收入性质 | 工资/加班费/报销/奖金/其他 | 用人单位名称使工资识别无需依赖备注 |
| CT3民间借贷 | 本息区分 | 本金/利息/还款/其他 | 本金金额使还款的本息拆分可精确计算 |
| CT4合同纠纷 | 履约进度 | 合同约定付款/违约金/其他 | 付款节点表使履约验证从推断变为比对 |
| CT5刑事辩护 | 涉案关联 | 涉案资金/关联资金/待定 | 涉案期间+涉案人员使涉案交易筛选精确 |
| CT6执行追索 | 财产线索 | 生活消费/可执行财产/财产转移 | 执行金额使消费水平与还款能力可对比 |

### 输出

- 分类标注结果：每笔交易附带分类标签+法律要件说明+置信度
- 分类冲突记录
- 法条验证结果
- **case_context辅助分类日志**（v2.0新增）：记录case_context哪些字段参与了哪些交易的分类判定

### 检查点

- [ ] 每笔交易有且仅有一个主分类标签
- [ ] 分类不确定的交易已标注置信度
- [ ] 所有分类标签附有法律要件说明
- [ ] 涉及法律定性的分类已联网验证法条
- [ ] 无推断性结论被呈现为确定性事实
- [ ] case_context 加载后分类精度是否明显提升（v2.0新增：对比有无参考数据时的分类差异）

## 5. 交互点 I1 第一轮概览与方向确认

### 风险等级：L2

### 设计理念（v2.0新增）

I1替代了v1.0的"一次性提交→一次性出报告"线性模式。真实律师分析流水的模式是：**先快速扫描 → 发现疑点 → 定向深挖 → 建构叙事**。I1正是这个流程中的"发现疑点、选定深挖方向"环节。

### I1不适用场景

以下情况跳过I1，直接进入P4→P5→P6：
- **FAST_TRACK模式**（交易≤10笔+单渠道+快速概览）——数据量过小，无深挖必要
- **用户明确要求"直接出完整报告"**——尊重用户选择
- **S1降级模式**（<3笔有效交易）——数据不足以做方向选择

### I1输出：第一轮概览

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  交易流水第一轮概览（I1）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

|------|-------|-------|-------|

## 6. Phase 4 异常模式检测

### 风险等级：L2

### 输入

- 分类标注结果
- CaseTypeSpec异常规则
- **case_context**（v2.0新增——提升异常检测敏感度）
- **I1用户选择**（v2.0新增——若指定方向，仅对选定方向深度检测）

### 步骤

1. **加载异常检测规则**：从CaseTypeSpec读取该案件类型的异常定义
2. **加载 case_context 异常敏感度规则**（v2.0新增）：
   - CT1：若有 separation_date+filing_date，激活"起诉前N天内"精确计算；若有 known_relations，激活"向特定关系人转出"精确匹配
   - CT2：若有 hire_date+leave_date，精确识别"入职后/离职前"时间窗口；若有 agreed_salary，激活"低于约定工资"检测
   - CT3：若有 principal_amount+loan_date，激活砍头息检测（借款日1-2天内回款）+超出本金还款识别
   - CT4：若有 payment_schedule，逐节点比对逾期天数（而非模糊判断）
   - CT5：若有 crime_period_start/end，按涉案期间精确过滤后再做异常检测；若有 alleged_amount，激活"推算金额vs指控金额差异"检测
   - CT6：若有 execution_date，激活"执行后财产减少"时间窗口检测；若有 execution_amount，激活"消费vs执行金额比例"检测
3. **通用异常检测**：
   - 大额整数转账：金额为整数且≥阈值（默认5万元或月收入3倍）
   - 起诉前密集转出：起诉前N天内支出频率显著高于平均
   - 与收入不匹配的消费：单笔支出>月均收入
   - 备注矛盾：备注内容与交易模式不符
4. **案件类型特有异常检测**（按CaseTypeSpec，case_context增强后置信度提升）
5. **对手方异常**：与未知对手方的大额或频繁交易
6. **I1方向过滤**（v2.0新增）：若用户选择了指定方向，仅对该方向相关的异常进行深度检测

### 输出

- 异常信号清单：每条含异常类型+涉及交易+严重程度+法律含义+建议核实方向
- 异常统计概览
- **case_context 对异常检测的影响日志**（v2.0新增）

### 检查点

- [ ] 异常检测规则已量化（非模糊描述）
- [ ] 每条异常信号关联到具体交易
- [ ] 严重程度使用L1/L2/L3标准
- [ ] case_context 加载后异常检测敏感度是否明显提升（v2.0新增）

## 7. Phase 5 对手方与资金流向分析

### 风险等级：L2

### 输入

- 分类标注结果
- 异常信号清单
- **case_context**（v2.0新增——控制追踪深度）
- **I1用户选择**（v2.0新增——若指定方向，仅对选定方向深度追踪）

### 步骤

1. **对手方聚类**：按counterparty字段汇总
2. **对手方分类**：
   - 已知关联方：case_context 中的 known_relations/involved_parties/employer_name 等自动标记
   - 疑似关联方：交易频率/金额模式暗示关联
   - 未知方：无足够信息判断
3. **追踪深度控制**（v2.0新增——按案型调节）：
   | 案型 | 默认追踪层数 | case_context 加载后 |
   |------|-------------|---------------------|
   | CT1 | 1层 | 若有 known_relations，追踪关联方资金去向 |
   | CT2 | 1层 | — |
   | CT3 | 2层 | 若有 principal_amount，追踪还款来源和最终去向 |
   | CT4 | 2层 | 若有 payment_schedule，追踪每笔付款的资金来源 |
   | CT5 | 3层 | 若有 involved_parties，追踪至第三层+检测回流 |
   | CT6 | 2层 | 若有 property_declaration，追踪至财产线索指向的资产 |
4. **资金流向构建**：
   - 节点：当事人+各对手方
   - 边：交易方向+累计金额
   - 生成Mermaid graph LR代码
5. **资金流向分析**：
   - 主要流入来源
   - 主要流出方向

## 8. Phase 6 报告组装与质量检查

### 风险等级：L1

### 输入

- 全部分析结果（P1-P5+I1）
- 降级判定结果

### 步骤

1. **降级判定**：根据数据完整度、case_context完整性、分类置信度判定是否降级
2. **报告组装**（v3.0重构——10区块HTML完整结构）：
   - 完整报告（全部深入）：**S1报告头→S2金字塔结论摘要→S3数据快照→S4六要素核心发现→S5资金流向拓扑→S6对手方分析→S7异常信号登记→S8证据附件(交叉引用)→S9分析限制与敏感度→S10页脚与治理**

   - 简化报告（只看概览）：仅S2+S3+S8(仅附1)+S9+S10

   - 每个发现配备影响标签（CRITICAL/SIGNIFICANT/NOTEWORTHY）
   - 证据锚点引用证据附件具体行号范围
   - 详见 output-spec.md v3.0 §4
4. **质量自检**（见下方清单）
5. **HTML报告输出**：按output-spec.md v3.0 §2完整HTML模板生成
