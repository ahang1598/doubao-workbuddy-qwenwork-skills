## 1. 输入模型概述

本技能采用**宽容摄取**模型——优先接受自然语言输入，支持多种输入形态，通过交互补全最多3轮完善必要信息。

### 必需参数

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| case_type | enum | 是 | 案件类型：CT1-CT6 |
| transaction_data | mixed | 是 | 交易记录数据（三种形态均可） |

### 条件必需参数

| 参数 | 类型 | 条件 | 说明 |
|------|------|------|------|
| channel | enum | IM1结构化输入时必填 | 来源渠道：bank/wechat/alipay |
| date_range | object | 建议提供 | 分析时间范围 |

## 2. 三种输入形态

### IM1 结构化输入（已导出CSV/Excel）

**触发条件**：用户提供已导出的文件内容或标准格式数据

**格式要求**：

```csv
交易日期,方向,金额,对方,备注
2024-01-15,支出,50000.00,张三,借款
2024-03-20,收入,30000.00,李四,还款
```

**渠道标注**：必须标注文件来源渠道（bank/wechat/alipay），不同渠道的字段映射不同。

**置信度**：high

### IM2 半结构化输入（手动整理的交易列表）

**触发条件**：用户从截图中手动整理的关键交易

**格式要求**：以下格式均可接受（容错处理）：

```
格式1：2024-01-15 微信转账 张三 50000 支出 备注：借款
格式2：1月15日 给张三转了5万 借款
格式3：24.1.15 支出 50000 对方：张三 备注：借款
```

**容错规则**：
- 日期格式：支持YYYY-MM-DD / YYYY/MM/DD / M月D日 / YY.MM.DD
- 金额格式：支持50000 / 50,000 / 5万 / 50000.00
- 方向推断：无明确标注时根据上下文推断（"转给""付出"→支出，"收到""进账"→收入）

**置信度**：medium

### IM3 自然语言输入（口头描述）

**触发条件**：当事人只有口述信息，无结构化数据

**格式要求**：无格式要求，自然语言描述即可

```
对方在2024年3月15日通过微信转了8000块给我，说是还之前的借款。
4月份又转了一笔2万，说是利息加部分本金。
```

**LLM逐条提取**：从自然语言中提取transaction_date、direction、amount、counterparty、remark等字段

**置信度**：low

## 4.1 case_context 参考数据模型

`case_context` 是案件相关的结构化参考数据，在 **P2 归一化阶段**与流水数据同步加载。P3/P4/P5 加载 case_context 后，分析的准确度、异常敏感度、追踪深度自动提升。

### 设计原则

1. **不是可选参数**——是分析精度提升的前提输入。缺失不拒绝处理，但对应分析步骤降级运行
2. **按案型定义不同字段**——6个案型的参考数据完全不同，各取所需
3. **影响置信度**——缺少 `required` 字段时，相关分析结论的置信度降一级
4. **不影响流水归一化**——NormalizedTransaction 结构不变，case_context 仅作为 P3/P4/P5 的辅助分析依据

### 通用字段

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| case_type | enum[CT1-CT6] | 是 | 案件类型 |
| user_role | string | 是 | 用户在本案中的角色（如"原告/被告/申请人/被执行人"） |

### 降级规则

| 情况 | 降级行为 |
|------|----------|
| `required` 字段缺失 | P3/P4/P5 中依赖该字段的分析步骤跳过，输出标注"因缺少{field}，以下为初步推断" |
| `recommended` 字段缺失 | 相关分析结论置信度降一级（🟢→🟡，🟡→🔴） |
| case_context 完全缺失 | 按当前 v1.0 行为运行（无参考数据增强），输出标注"建议补充案件信息以获得更精确分析" |

## 6. 降级路径

```
IM1结构化(high) → IM2半结构化(medium) → IM3自然语言(low)
                    ↓                        ↓
              容错解析失败时               提取不完整时
                    ↓                        ↓
              SOFT_DEGRADED              SOFT_DEGRADED
              (C+D+G最小骨架)           (C+D+G最小骨架)
```

### 降级触发条件

| 降级级别 | 触发条件 | 输出策略 |
|----------|----------|----------|
| S3 | 部分交易无法分类或金额有歧义 | 接近完整但关键金额标注"待核实" |
| S2 | 大量交易缺乏备注或渠道信息不明 | +数据概览与渠道分布，分类标注粗粒度 |
| S1 | 输入极度不完整（<3条有效交易记录） | 仅C+D+G，强烈建议补充数据 |

## 7. 输入验证规则

### 硬拒绝条件

以下情况直接拒绝处理，不进入SOFT_DEGRADED：

| 编号 | 条件 | 理由 |
|------|------|------|
| H1 | 无法识别任何有效交易记录 | 无分析对象 |
| H2 | 案件类型不在CT1-CT6范围内 | 超出技能能力边界 |
| H3 | 刑事辩护案件(CT5)但无律师确认标记 | C类高风险案件需律师主导 |

### 软警告条件

以下情况发出警告但仍继续处理：

| 编号 | 条件 | 处理方式 |
|------|------|----------|
| W1 | 交易记录时间跨度>5年 | 提示可能需要分段分析 |
| W2 | 单笔金额与当事人收入严重不符 | 标注需核实 |
| W3 | 同一对手方出现3种以上不同名称 | 可能需要对手方归并 |
