# 目标 SKILL.md 生成模板

把访谈纪要按本模板填空生成最终的 SKILL.md。模板的 `<...>` 占位符必须替换为业务内容，不允许保留。

---

## frontmatter

```yaml
---
name: <skill-name>            # 与目录名一致；只能用小写字母、数字和连字符 '-'（^[a-z0-9-]+$）
description: <一段中英短语齐备的触发说明>
---
```

`description` 写作要点：

- 第一句中文，说明 skill 是做什么的（流程型，跑完产出什么）。
- 接 5–10 个**中文同义改写短语**：覆盖业务场景的不同问法。
- 再接 5–10 个**英文同义改写短语**：覆盖跨语言团队的搜索习惯。
- 最后一句**触发条件**：明确"何种意图触发"，并显式声明**不适用**的范围（例如"一次性分析不触发"）。
- 单段、单句、不分行——遵循 LinkFox 官方 skill 的 description 风格。

**刻意"推一把"，对抗欠触发**：agent 在面对相关请求时**普遍倾向于不调用 skill**（典型表现：用户已经说出业务场景，agent 却选择直接回答而不进入流程）。为对抗这一倾向，description 收尾要主动加一句**反向补漏**，例如：

> "...即使用户没有明确说'流程'/'每周'/'sop'/'workflow' 等字眼，只要意图涉及多步、可重复执行的电商业务（如选品、广告复盘、补货、监控），也应触发。"

这一句不是装饰——它直接提升触发率。**不允许省略**。同样不允许把 description 写成"防御式":"仅当用户明确请求 X 时触发"——这种写法会进一步压低触发率。

参考反例与正例：

❌ "周度选品流程。当用户请求'每周选品流程'时触发。"  
✅ "周度选品流程……即使用户只说'我想做个每周从种子词找候选 ASIN 的事'，没有明说 SOP 或 workflow，也应触发本 skill。"

## 主体结构（7 段固定章节）

### 1. 适用场景与不适用场景

```markdown
## 适用场景

<一句话总述业务目标和节奏>

| 场景 | 说明 |
|------|------|
| <子场景 1> | <什么时候跑、谁跑、产出什么> |
| <子场景 2> | <...> |

## 不适用

- <一次性分析的反例>
- <已有对应数据 skill 的单点查询反例>
- <人工判断为主、不依赖数据的任务>
```

### 2. 一次性参数

```markdown
## 输入参数

| 参数 | 类型 | 默认 | 说明 |
|------|------|------|------|
| country | string | US | 站点代码 |
| time_window | string | last7d | last7d / last4w / yyyy-MM-dd~yyyy-MM-dd |
| <业务参数> | <类型> | <默认> | <说明> |
```

参数表只列**运行时入参**。硬编码到 skill 内部的常量（如阈值默认值）写在对应步骤里，不进参数表。

### 2.5 已挂载能力约束

产物的可执行步骤只能引用当前 agent 已挂载的公共 skill。`linkfoxagent-v2/` 全集可以作为设计参考，但未挂载能力不能写成当前可执行步骤。

```markdown
## 已挂载能力约束

| skill | 用途 | 调用位置 | 状态 |
|-------|------|----------|------|
| linkfox-amazon-product-detail | <为什么需要它> | S<N> | 已挂载 |
| linkfox-report-generator | 报告样式、排版、md/html 导出 | 收尾 | 已挂载 / 未挂载则提示先安装 |
```

若某个关键能力未挂载，必须二选一：改用已挂载能力重做流程；或把该能力写入「局限性 / 安装提示」，并明确当前版本暂不可完整执行。安装提示指向“技能广场”或 `https://skill.linkfox.com/`，说明安装后可从用户自己的 `skills/` 路径访问。不得承诺运行时自动加载、自动修改 `dependencies.json` 或让用户处理 git。

### 3. 流水线步骤（大纲 + 按步加载）

流程型 skill 又长又复杂，**把全部步骤细节一次性写进 SKILL.md 会让 agent 注意力失焦**——执行到后面的步骤时，被前面大量细节干扰、丢失当前焦点。因此采用两层结构：

- **SKILL.md 只写大纲**：一段「执行编排」+ 一张「流水线」总览表（每步一行：标题 / 一句话做什么 / `依赖` / `用途` / 指向 `references/steps/S<N>.md`）。让 agent 始终看得到完整流程图与并行计划。
- **`references/steps/S<N>.md` 写血肉**：单步的完整 输入 / 操作 / 输出 / 落盘 / 参数。**agent 执行到该步时才 Read**，只把当前步的细节加载进上下文，跑完即可丢弃。

**何时拆 steps/**（满足任一即拆，否则可内联进 SKILL.md）：

- 步骤数 ≥ 4；或
- 任一步的操作含具体命令 / 多参数 / 落盘段落 / 字段清单等 ≥ 8 行细节；或
- 预计 SKILL.md 主体（不含 frontmatter）会超过 ~200 行。

简单短流程（≤ 3 步且每步几行）允许直接把详情内联在 SKILL.md，不必强拆——大纲化是为长流程治失焦，别为拆而拆。

#### SKILL.md 里的步骤大纲（每步一行）

```markdown
### 执行编排

<见下方「并发执行」小节，列出并行层>

### 流水线

| 步骤 | 做什么（一句话） | 依赖 | 用途 | 详情 |
|------|----------------|------|------|------|
| S1 <动词短语> | <一句话> | 无 | <被谁消费> | `references/steps/S1.md` |
| S2 <动词短语> | <一句话> | 无 | <...> | `references/steps/S2.md` |
| S3 <动词短语> | <一句话> | S1, S2 | <...> | `references/steps/S3.md` |
```

`依赖` 与 `用途` **必须留在大纲表里**——DAG 校验与并行编排都靠它们，要一眼可见；其余细节进 steps 文件。

#### references/steps/S<N>.md（单步详情，运行到该步才加载）

每个步骤一个文件，严格写齐 5 项（`依赖` / `用途` 与大纲表保持一致，便于离线核对）：

```markdown
# 步骤 N：<动词短语>

- **输入**：<字段名 1>、<字段名 2>，或 `<上游步骤 S(N-1)> 的输出`
- **依赖**：<本步开始前必须先完成的上游步骤，如 `S1`、`S2`；与所有前序步骤都没有数据依赖时写 `无`，表示它可以和同层步骤并行发起>
- **操作**：调用 `<linkfox-skill-name>`，传入 `<参数 1>=...`、`<参数 2>=...`；或运行 `scripts/step_N_<verb>.py`
- **输出**：`<字段 1>`、`<字段 2>`、...
- **用途**：被 <步骤 S(N+1) 的输入 / 报告章节 X / 决策 Y> 消费

<若该步需落盘，在此处嵌入 large-response-snippet.md 整块>
```

`依赖` 只写**真实的数据依赖**——「这一步的输入字段需要上游某步先产出」。不要因为"习惯上先做 A 再做 B"就写依赖：没有数据依赖的步骤应当并行，串行会让墙钟时间线性累加（流程型 skill 超时的头号原因）。

#### 写作格调：解释 why，不要堆 ALWAYS/NEVER

每条规则都尝试用一句话**解释为什么**这么写，而不是用全大写的 MUST / ALWAYS 强压。理由是：

- 给出理由后，agent 在边界情形下能做出合理判断；只给命令则在新情形下失灵。
- 用户阅读时也更容易理解、维护、修改——"为什么这么定"比"必须这么做"更耐住时间。
- 全大写命令式的过度使用会让 skill 显得僵化，且模型常常视而不见。

示例对比：

❌ 干命令式：

> 步骤 3 必须使用落盘脚本。

✅ 解释式：

> 步骤 3 返回数据量大（搜索词报告 50+ 字段、含数组分页），如果直接灌进上下文容易把后续步骤挤丢；因此通过 `response_io.py` 落盘后再投影需要的字段。

唯一例外：**`用途` 字段是硬约束**（DAG 校验依赖它），写作上不需要解释，但内容必须具体到"被哪个下游消费"。其余规则都能解释。

#### 用途字段的合规与不合规示例

✅ 合规：

- `用途：作为步骤 S3 的候选 ASIN 输入`
- `用途：进入报告"竞品对标表"章节`
- `用途：触发"加入否定词候选池"决策`

❌ 不合规（生成期会被自检拦下）：

- `用途：留作参考`
- `用途：可能在后续分析中有用`
- `用途：完整保存以备查阅`
- `用途：（留空）`

#### 落盘段落（条件嵌入）

若某步需要落盘，**就近嵌入** `references/large-response-snippet.md` 的整块内容（按目标 skill 的命令路径调整）：已拆 steps/ 的，嵌在该步的 `references/steps/S<N>.md` 末尾；未拆分的，嵌在 SKILL.md 该步末尾。**不要**只在文末整体提一次"大响应处理"——必须按步骤就近嵌入，否则 agent 执行该步时看不到。

#### 并发执行（默认优先）

流程型 skill 串行跑完，墙钟时间是各步耗时之和；这是用户反馈"任务跑太久 / 中途卡住"的头号原因。**没有数据依赖的步骤默认应并行**，不要无谓串行。

依据每步的 `依赖` 字段把流程切成若干**并行层**：同一层内的步骤彼此无依赖，应在**同一轮里一次性并行发起**（一条消息里同时调用多个工具），全部返回后再进入下一层。

> 说明：并行靠"主流程在一轮内批量发起多个互相独立的工具调用"实现，**不依赖 subagent**——本规范不使用 subagent。

在产出的 SKILL.md 流水线章节开头，用一小段「执行编排」说明并行计划，例如：

```markdown
### 执行编排

- 第 1 层（并行）：S1 拉竞品详情、S2 拉关键词流量 —— 两者输入相互独立，同一轮并行发起。
- 第 2 层：S3 合并打分 —— 依赖 S1 + S2 全部返回。
- 第 3 层：S4 出报告 —— 依赖 S3。
```

正反例：

✅ 推荐（独立步骤并行）：

> S1「按种子词拉关键词」与 S2「拉类目 BSR 榜单」都只依赖运行时入参、互不消费对方输出 → 同一轮并行发起，二者返回后再进 S3 汇总。

❌ 反模式（无依据的串行）：

> 先跑完 S1 拿到关键词，再"顺手"去跑和它毫无数据关系的 S2 榜单 —— 平白把两段耗时相加。

⚠ 不要为了并行而并行：**有真实数据依赖的步骤必须串行**（下游要用上游的输出），强行并行会拿到空数据或脏数据。`依赖` 字段就是用来区分这两种情况的唯一依据。

### 4. 报告产物（条件存在）

仅当用户在访谈阶段 3 报告诉求子环节选择需要报告时存在。

**硬规则——所有报告交给 `linkfox-report-generator`**：

> 报告排版 / 视觉 / md & html 导出 / 元信息块统一由团队 `linkfox-report-generator` skill 维护。
> 本 skill 只负责把业务数据准备好，**不要在本 skill 里复制报告样式或 html 模板**——视觉一致性 + 维护成本两件事都靠这个 handoff 兜底。

产出 SKILL.md 的「报告产物」章节按下面骨架写（**最后一段 handoff 不允许省略**）：

```markdown
## 报告产物

每次执行流程后，按访谈记录的章节生成报告，写入 `--out-dir` 指定的目录，命名 `report_<yyyymmdd_HHMMSS>__<run_label>.{md,html}`。

报告必备元信息：

- 生成时间（ISO 8601，本地时区）
- 参数快照（country / time_window / 业务阈值，原样附在文首）
- 数据来源清单（步骤 → skill / 参数）
- 局限性说明（数据延迟、覆盖空白、阈值假设）

业务章节（由本 skill 的访谈结果决定，例如「竞品对标表」「关键词漏斗」「补货建议」）：
- <章节 1>：<数据来自哪一步、关键字段>
- <章节 2>：<...>

> **⚠ 如果需要生成报告 / 精美报告，必须去阅读 SKILL `linkfox-report-generator`，根据它的规范来。**
> 本 skill 只准备业务数据；样式、排版、md/html 导出、元信息块统统由 `linkfox-report-generator` 负责。
> 不要在此处复制报告样式或 html 模板。
```

### 5. 自检 checklist（轻量版）

```markdown
## 执行自检

每次跑完流程，agent 在收尾时确认：

- [ ] 所有步骤都拿到了非空数据，否则在报告局限性章节注明
- [ ] 报告的每个章节都有数据来源（无来源章节标"暂无数据"）
- [ ] 决策动作都有触发条件证据，避免拍脑袋
- [ ] 参数快照已写入报告头
```

### 6. 局限性

```markdown
## 已知局限

- <数据延迟>
- <覆盖空白>
- <未消除的 TBD>（如有，列出并说明影响）
- <阈值假设>
```

## 报告样式规范

**已迁出本仓库**——团队报告规范统一由 `linkfox-report-generator` 维护：md / html 样式、元信息块、A4 排版、配色、打印兼容、html 骨架等都在那个 skill 里。

本模板**只**关心业务数据如何准备：把每个报告章节定义清楚（数据来自哪步、关键字段、口径），剩下的样式、文件名、导出格式让 `linkfox-report-generator` 接管。

> 如果 `linkfox-report-generator` 还没装/还没找到，把这一情况写进产物的「局限性」章节，让用户去拉那个 skill；**不要回退到自己造样式**。

## DAG 校验规则（生成前必跑）

把所有步骤、报告章节、决策动作建模为有向图：

- 节点类型：`step` / `report_section` / `decision`
- 边：`step.outputs[i] → step.inputs / report_section.fields / decision.preconditions`

判定：

1. 每个 `step` 至少一条出边到 `step / report_section / decision`，否则报错"孤岛步骤 S<N>"。
2. 每个 `交付字段`（来自访谈阶段 2 具象化字段 / 阶段 3 报告章节）至少一条入边反向追溯到某 `step.outputs`，否则报错"无来源交付字段 <field>"。
3. 没有循环依赖（`step` 之间不形成环）。
4. **并行分组**：按 `依赖` 字段对步骤做拓扑分层——同一层（彼此无依赖路径）的步骤归为一个**可并行组**。把分组结果写进 `.draft/dag.md`，并据此生成 SKILL.md 的「执行编排」说明。
5. **过度串行告警**：若存在两个步骤被排成前后串行、但彼此之间并无 `依赖` 关系（一个的输出不是另一个的输入），标记为"疑似无谓串行"，回访谈确认是否应并行。

把这张图写入 `<产物目录>/.draft/dag.md`，作为生成期产物的一部分（不分发到目标 skill 中——`.draft/` 是产物目录的临时子目录，跟随产物归档但不进打包）。`.draft/dag.md` 建议同时画出分层，便于核对并行计划：

```
[输入参数]
   ├─（第 1 层 · 并行）→ [S1] ┐
   └─（第 1 层 · 并行）→ [S2] ┘→ [S3]（第 2 层，依赖 S1+S2）→ [S4 报告]（第 3 层）
```
