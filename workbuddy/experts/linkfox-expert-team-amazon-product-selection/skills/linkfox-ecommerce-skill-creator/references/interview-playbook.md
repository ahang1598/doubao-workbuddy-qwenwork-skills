# 访谈剧本

本剧本指导 agent 与用户进行多轮结构化访谈，最终产出一份"每一步都有用途"的流程纪要。

## 核心原则

1. **用业务结果讲话，不要把技术决策甩给用户**（最高优先）。
   - 选项必须是"业务后果"维度，不是"agent 动作"维度。
   - 镜像用户用语：用户讲什么词跟着讲什么词，不主动夹技术词。
   - **scope**：只约束对话和**产物 SKILL.md 中用户可见部分**；`.draft/`、内部 references、自检 checklist 该精确就精确。

   反例对照：

   | ❌ 技术动作维度 | ✅ 业务结果维度 |
   |----|----|
   | "要重试 / 改 pageSize / 跳过这步吗？" | "S3 拉评论没成功——这步在你流程里是必须的吗？必须就再试两次，不关键我先跳过把其他结果给你。" |
   | "S3 没产出，是孤岛步骤要删吗？" | "S3 算出来的东西后面好像没人用——是我漏看了，还是这步可以并到 S2？" |
   | "ABA 数据延迟一周，要跳过还是接受？" | "这个数据源大概会比实际晚一周——周报的话够用，做日级监控就跟不上。你这次哪种节奏？" |
   | "回到步骤 1 重新审定边界" | "我对你流程的理解可能偏了——能再讲一下你最想拿到的是什么吗？" |

2. **用户讲业务，agent 选工具**。用户描述场景、字段、决策、阈值；agent 决定调哪个 skill、怎么组合。**假设用户不了解任何数据源**。
   - **不允许**：在两个 skill 名 / 数据源 / 技术方案之间让用户裸选（"用极目还是卖家精灵？""ABA 加不加？""推荐组合 A / 组合 B 你选哪个？"）。
   - **允许**：把方案（含用途与风险）讲给用户听并请其确认；当多个工具业务等价时，列 A/B/... 各自的用途与风险供用户选。
3. **用户先讲，agent 后问**。基础信息确认后，第一件事是让用户用自己的话讲一遍场景与流程（阶段 1），不是开始拷问。**没有可识别的步骤序列就不允许进阶段 2**——这是硬阻断。
4. **倒推补全，不是从零拆解**。拿到用户自述后，agent 用倒推法验证与补全这份草图，找漏洞、拼断点，不要把用户已经说过的再问一遍。
5. **每轮 1–4 题**：用结构化提问工具，避免一次性轰炸用户。
6. **TBD 软话术**：业务模糊处允许标 `TBD`，但要明确告知"最后一起回看，未消除的 TBD 会阻断生成"。
7. **复述确认**：每个阶段结束时复述要点，让用户确认或修正。
8. **拒绝硬塞**：当发现用户其实想要的是一次性分析，立即停下并建议改用 `skill-creator`。
9. **先抽取，后访谈**：动手提问前先扫一遍上文（阶段 0），用户已经说过的内容不要再问一遍。

## 阶段 0：上文扫描 + 产物目录就位

> 目的：用户在触发本 skill 前的对话里很可能已经说了大量信息——抓取的工具、纠正过的步骤、提到的字段、想要的产出。**先抽再问**，避免重复打扰。同时把产物目录定下来，后续所有草稿都写进它。

具体做法：

1. 回看本会话从开始到现在的所有用户消息（不只是最近一条）。
2. 提取**已知信息**：业务场景、已提到的步骤、已明确的字段、已表达的偏好（"每周跑"、"出一份 html"、"接到 ERP" 等）。
3. 列一份"已知 / 待确认 / 完全空白"清单。
4. 进阶段 1 时，**已知项不再问**，直接复述请用户确认；**待确认项**作为本轮访谈的第一批问题；**空白项**留给阶段 1 的自由叙述自然带出。
5. **取一个工作名**（业务动作 + 节奏，如 `selection-weekly`），按 `references/target-structure.md` 的"输出位置默认"决定 `<产物目录>`，向用户复述确认（"我会把它建在 `<路径>`，对吗？"），然后建好目录骨架（含空的 `.draft/` 子目录）。后续访谈纪要、选型表、DAG、试跑提示词全部写进 `<产物目录>/.draft/`；这些是暂存草稿，不提供链接，用户需要看时直接在当前会话中展示。

复述话术示例：

> 我从上文看到这些已经明确：(a) 每周跑一次；(b) 输入是 3 个种子关键词；(c) 想要 5 个候选 ASIN。我打算把这个 skill 建在 `/root/.linkfox/workspaces/.claude/skills/selection-weekly/`，对吗？如果都没问题我们继续往下定剩下的部分。

## 阶段 0.5：方法论萃取（条件分支）

> **仅当**用户带了外部资料 / 方法论文档 / 历史样本时进入；用户能直接口述流程则跳过，直接进阶段 1。

完整步骤见 `methodology-extraction.md`。一句话：把用户的资料萃取成结构化方法论（含"通用化处理"与"平台 × 步骤数据缺口盘点"），产出的方法论步骤序列**等价于阶段 1 的自述**。复述方法论框架请用户确认后，**直接进阶段 2**，不再要求自由叙述。

复述话术示例：

> 我把你给的资料萃取成了一套方法论：核心思想是 <…>，分 M1 → M2 → M3；其中 M2 依赖 ABA，我标了「仅适用 Amazon」；各平台数据支持我盘了一下，Walmart 的 M1 暂无数据源。这个框架对吗？确认后我接着把每步的字段、参数、工具定下来。

> 忠实性底线：方法论只能从资料来，资料没覆盖的标 `TBD` 留到访谈补，不臆造步骤或阈值。

## 阶段 1：用户自述业务流程（不可跳过的切入口）

> 目的：让用户用自己的话讲一遍要做的事——是什么场景、谁来做、跑完得到什么、中间大概有几步。这一阶段 agent **只听不问**。

### 硬阻断

**进入阶段 2 之前必须输出"初始流程草图"**，草图必须包含：

- 场景（什么场合下跑）
- 节奏（一次性 / 每周 / 每月 / 每天）
- 主角 / 消费者（谁跑、谁看产出）
- **可识别的步骤序列（≥ 2 步，每步有动词）**
- 最终产出（哪怕暂时是抽象描述也行——具象化交给阶段 2）

例外：阶段 0 已从上文抽到完整草图——复述请用户确认即可。**仅有片段意图（"做选品"、"分析竞品"、"搞个周报"）不算完整草图**，必须回到本阶段让用户再讲。

如果 agent 发现自己已经在问技术细节、数据源、字段名 → **立即停下回阶段 1**。

### 邀请话术

> 接下来请你用自己的话讲一下这个流程：你在什么场景下用它？多久跑一次？谁来跑、谁是消费者？打算每次跑完拿到什么？大概有几个步骤、每一步做什么？不需要严谨——平时怎么想就怎么说，越具体越好（关键词、ASIN、店铺 ID、阈值这些都可以直接说出来）。说完我再来补问。

不要给用户填空模板——模板会束缚叙述。但如果用户卡住了说不动，可以给三条提示：

- "如果一时说不全也没关系，先讲场景就行——比如周一早上、周会前、负责选品的同事跑这个。"
- "可以从最后想要拿到的东西开始讲——比如最后想要一份 5 个 ASIN 的对比表。"
- "也可以从你现在手工怎么做开始讲，让我帮你梳理成自动流程。"

### agent 的工作

用户讲完后：

1. **不打断、不抢话**——哪怕用户说得乱，先听完。
2. **不问数据源、不问字段名、不问 skill 选型**——这些归阶段 4。
3. 在草稿里同步整理出**初始流程草图**：

   ```
   [初始流程草图]
   - 场景: <用户描述>
   - 节奏: <每周/每月/...>
   - 主角 / 消费者: <谁跑、谁看>
   - 步骤草稿（按用户讲述的顺序）:
       S1: <用户说的第一步>
       S2: <第二步>
       ...
   - 提到的字段 / 输入 / 输出: <边听边记>
   - 提到的偏好（如有）: <用户主动提到的工具偏好，作为 hint，不替代 agent 选型>
   - 用户没讲清楚的地方: <空白项清单>
   ```

4. **复述给用户确认**：

   > 我把你刚才讲的捋成这样：场景是 <...>；流程大概是 S1 → S2 → S3 → S4；最后产出 <...>。我有几个地方还没听明白：(a) ...; (b) ...; (c) ...。我们一项项过？

   如果用户对捋出来的草图有大改，重做一遍这个阶段；改动小则进阶段 2。

### 注意

- 用户可能讲到一半冒出**抽象交付物**（"给我个选品建议"）—— 不要当场拷问，**记到空白项**，留到阶段 2 去具象化。
- 用户讲述的步骤**很可能不完整、顺序混乱、有冗余**——都正常。阶段 2、3 会处理。
- 用户讲到**情绪化或矛盾**信息（"我也不知道这步是不是必要"）—— 直接抄进"空白项"，作为后续 TBD 的种子。

## 阶段 2：缺漏分析与补全

> 目的：对阶段 1 自述做缺漏分析，把抽象产出具象化、把模糊步骤问清楚、把没出口的步骤合并或删除。

agent 自己先做一次"草图体检"，再带着具体问题去问用户：

### 体检清单

1. **抽象交付物 → 具象字段**
   - 自述里提到"选品建议 / 优化方向 / 风险评估"等抽象词 → 必须问出**可枚举的字段或结论项**：
     - 报告：列章节标题
     - 表格：列列名
     - 决策：列每条决策的输入条件和输出动作
   - 把用户阶段 1 已经提到的具体字段**先填进来**，让用户**补全或修正**——不是从零让用户列。

2. **没出口的步骤**
   - 草图里某步的输出**不被任何下游消费**？问："S<N> 的输出好像没有下游消费——是我漏了，还是这一步可以删/并到 S<M>？"

3. **没来源的字段**
   - 交付字段在草图里**找不到产出步骤**？问："这个字段从哪儿来？我们是不是漏了一步？"

4. **重复产出同一字段**
   - 多个步骤声称产出同一字段？问："S<i> 和 S<j> 都说会给我 `<字段>` —— 是同一件事说了两遍，还是真有两个来源？"

5. **跨步骤的隐含合并**
   - 跨平台 / 跨账号的数据需要 join？补一步"汇总/归一"。
   - 历史对比 / 同比环比？标注时间窗参数。
   - 人工评审或确认的卡点？写成"人工节点"步骤，输出仍要写清。

### 复述与确认

体检后输出**修订草图**给用户：

> 我对照体检了一下，有这些发现：
> - <抽象项> 我建议拆成 <字段 1> / <字段 2> / <字段 3>，对吗？
> - S<N> 的输出我没看到下游用——你倾向删掉还是并到 S<M>？
> - <某交付字段> 没看到从哪一步出，我们是不是要在 S<X> 之后加一步专门算它？
> ……
> 修订后流程是 S1 → S2' → S3 → S3.5（新增）→ S4，对吗？

确认后进阶段 3。

## 阶段 3：深入调研

> 目的：对阶段 2 修订草图里的每一步追问详细需求；同时锁定一次性参数与报告诉求。

分三块进行：

### 3.1 每一步的详细需求

对每一步追问：

- **输入**：来自上一步的哪些字段？还有哪些是运行时入参？
- **输出字段**：精确到字段名（先用业务语言，agent 后续翻译成 API 字段）。
- **字段精度**：销量是要精确数字还是分桶值就够？评分要不要 ±0.1 以内？
- **阈值/筛选条件**：毛利率下限、销量下限、评分下限、价格区间等。
- **时间窗**：本步骤需要的数据时间窗（最近 7 天 / 最近 4 周 / 同比对比等）。

### 3.2 一次性参数（运行时入参）

询问（多选）：

- 站点（US/UK/DE/JP/...）
- 时间窗（最近 7 天 / 最近 4 周 / 自定义起止）
- 输入主体（ASIN 列表 / 关键词列表 / 类目 / 店铺 ID / 其他）
- 阈值参数（毛利率下限、销量上限、评分下限等）

询问（单选）：

- "下一次跑这个流程，需要变更的参数主要是什么？" —— 帮助识别哪些是运行时入参、哪些可以硬编码到 skill 中。

阶段 1 用户已经说过的参数值直接填进来确认，不要再问一遍。

### 3.3 报告诉求

向用户提问：

1. **是否需要报告**（单选）：是 / 否 / 视情况由调用方决定
2. **格式**（多选，仅当 1 为是或视情况）：
   - md（GitHub flavored Markdown，适合直接贴到协作工具）
   - html（单文件、内联 CSS、A4 友好，适合打印或邮件发送）
3. **必备元信息**（默认全开，让用户挑选要去掉的）：
   - 生成时间
   - 参数快照（站点、时间窗、阈值）
   - 数据来源（哪些 skill / 哪些参数被调用）
   - 局限性说明
4. **章节诉求**：让用户列出希望出现的章节名（不强制、不限制）。模板**只规定外观**，章节内容由用户驱动。

把回答记到草稿的 `report:` 区块。

## 阶段 4：工具选型与确认

> 目的：agent 根据阶段 1–3 的需求，从 available-skills 里为**每一步**选好工具；按规范向用户呈现方案（含用途与风险），由用户确认。

**硬阻断：必须拿到用户显式决策才能进阶段 5。** 沉默、"都行"、"你定吧"不算决策。

### 选型规约

agent 自己挑、自己出方案，但**不藏方案**。每一步的工具决定按这个模板讲给用户听：

```
S<N> <动作>
- 业务目标：<得到什么字段/结论>
- 选用工具：<真实 skill slug，例如 linkfox-amazon-product-detail>
- 工具用途：<这个 skill 提供什么数据，怎么用在这一步>
- 调用参数（默认值 / 可配置）：
  - <参数名 1>: <默认值>  （运行时入参——每次跑可改，对应阶段 3.2 的 <某入参>）
  - <参数名 2>: <默认值>  （默认值——基本不改，可在生成产物中调整）
  - <参数名 3>: <默认值>  （默认值）
- 风险/局限：
  - <覆盖空白：例 仅 US 站点>
  - <数据延迟与刷新频率：例 ABA 周更>
  - <配额、批量上限、成本：例 单次最多 10 ASIN>
  - <精度限制：例 销量为分桶值，非真实数>
  - <鉴权依赖：例 需店铺授权>
- 未选用 <另一个真实候选 skill slug> 的原因：<取舍点>
```

#### 关于"调用参数"

每个工具调用都有一组参数（如 `country`、`pageSize`、`sortBy`、阈值等）。**默认值 + 可配置** 的呈现方式：

- agent 主动给出 **每个关键参数的默认值**，不要让用户从零想。
- 每条参数标注**性质**：
  - **运行时入参**——每次跑都可能变，进入产物的 `## 输入参数` 表（来自阶段 3.2 已枚举的运行时入参）
  - **默认值**——通常不改，硬编码到对应步骤；用户认为该让它可改时可升级为运行时入参
- **明显需要让用户决定的参数**（如 `pageSize` 1000 vs 500、`sortBy` 销量 vs 评分），主动征询；其余按 agent 默认走。
- 用户可以：（a）接受默认；（b）改默认值；（c）把"默认值"升级为"运行时入参"，或反之。

**多个工具在业务上等价时**，列 A/B/...，每项都带用途、参数默认值与风险，给一个默认推荐与理由：

```
S<N> 这一步两种方案，你倾向哪种？
A) linkfox-amazon-product-detail —— 用途..., 默认参数..., 优势..., 风险...
B) linkfox-sorftime-amazon-product-query —— 用途..., 默认参数..., 优势..., 风险...
（推荐 A，理由 ...）
```

**禁止形态**：

- ❌ "用极目还是卖家精灵？"（没给用途和风险）
- ❌ "推荐组合 A / 组合 B 你选哪个？"（用户不掌握组合背后的差别）
- ❌ "ABA 加不加？"（用户不知道 ABA 是什么）

**风险维度清单**（agent 不要瞎编，按这五类落实）：

1. 覆盖空白（站点、品类、时间窗）
2. 数据延迟与刷新频率
3. 配额、批量上限、调用成本
4. 精度限制（分桶值、估算值、抽样）
5. 鉴权依赖（需店铺授权 / API key 等）

### available-skills 不覆盖时

明确告诉用户："这一步在 LinkFox 内置 skill 里没有现成对接。我可以在产物的 `scripts/` 里写一个 thin wrapper 调 <第三方工具>，或者跳过这一步。你倾向哪种？"——不要硬塞一个不合适的 LinkFox skill。

### 并发设计确认（业务语言）

选型确认后，agent 按每步的数据依赖把流程切成并行层（无数据依赖的步骤归为同层、可并行），用**业务语言**讲给用户听并确认合理性——不要甩"要不要开多线程"这种技术问法。

话术示例：

> 这个流程我打算这么跑：第一拨同时去做「拉竞品详情」和「拉关键词流量」——这两件事互不依赖，一起做能省一半时间；等它俩都回来，再做「合并打分」，最后出报告。你看这个并行安排有没有问题？比如这两步在你的业务里是不是其实有先后讲究？

确认要点：

- 被判为"可并行"的步骤，业务上是否真的互不依赖（用户可能知道某种隐含先后）。
- 被判为"必须串行"的链路是否过长——有没有能拆出来提前并行的部分。
- 用户确认后，把分层结果记进 `.draft/dag.md`，并在生成期写入产物 SKILL.md 的「执行编排」段。

> 依据：串行让墙钟时间线性累加，是流程型 skill 超时的头号原因；但并行的前提是步骤间无数据依赖，依赖关系只有业务方最清楚，所以必须确认而非 agent 独断。

### 确认与落盘

拿到用户显式决策后，写 `<产物目录>/.draft/mapping.md`：

| 步骤 | 业务动作 | 选用 skill | 用途 | 风险/局限 | 未选用候选 + 原因 | 依赖（上游步骤 / 无） |

否决项的"原因"会进入产物的"取舍说明"或"局限性"章节。

---

## 阶段 5：收尾（纪要复述 + 试跑提示词合成）

> 目的：消除模糊点、确保进入生成期前没有空步骤；agent 自己合成试跑提示词用于后续技能试跑。

### 5.1 复述纪要 + TBD 清算

输出一份 markdown 草稿给用户过目，结构如下。该草稿是 `.draft/` 工作稿，不提供链接；用户在当前会话中能直接看到。

```markdown
# 访谈纪要：<skill 名>

## 业务目标
<...>

## 一次性输入参数
- 站点: ...
- 时间窗: ...
- ...

## 步骤
### S1 <动作>
- 输入: ...
- 操作: ...（具体调哪个 skill）
- 输出: ...
- 用途: ...
- 风险/局限: ...

### S2 ...

## 报告
- 是否需要: 是/否
- 格式: md / html
- 章节: ...

## TBD
- [ ] 步骤 S<N> 的某字段来源待定
- [ ] ...
```

向用户复述并询问：

- 每个步骤的 `用途` 是否都明确？
- 有没有看似可有可无的步骤可以删？
- TBD 列表能不能现在就消除？

**硬约束**：未消除的 TBD 在生成期会阻断 skill 输出。本阶段引导用户尽量清零；用户坚持留 TBD 时，记录原因，进入产物的"局限性"章节明示。

### 5.2 合成试跑提示词

agent 自己从访谈纪要里**合成** 2–3 条试跑提示词，写到 `<产物目录>/.draft/试跑提示词.md`。**不向用户索取**——阶段 1 已经听过用户怎么讲业务，那时的语言比让用户刻意写更自然；再问一遍既消耗用户耐心，输出也常被仪式感污染。

合成规则：

- **取阶段 1 用户自述里的用词风格**——别用 SKILL.md description 里的官话。
- **填入访谈中出现的具体值**：关键词、ASIN、profile id、阈值都用真实数据，不要 `<...>` 占位。
- **至少 1 条覆盖主路径**，1 条覆盖边界情形（参数缺失 / 输入异常 / 阈值极端）。
- **像用户日常会打的字**，可以小写、可以省略主语、可以有口语化助词。

示例（仅作风格参考）：

- "周一上午跑一下选品，3 个种子词 wireless earbuds, dog bed, kitchen scale，给我 5 个 us 站候选。"
- "ppc 复盘了，profile 是 1234，campaign 那 3 个核心的，acos 目标 0.3。"

合成完直接进入步骤 4（生成产物）；用户的审核留到步骤 5 试跑前的"念给用户确认"那一刻。

## 话术模板

**开场**（在阶段 0 抽取后一次性说）：

> 我会通过几轮对话把这个流程拆清楚。流程是这样的：先请你用自己的话讲一遍场景和大致步骤——这一段我只听不打断；听完我会指出我没听明白的地方逐项问回来；然后再深入到每一步的字段和参数；最后我从 LinkFox 内置 skill 里给每一步选好工具，连带用途和风险讲给你听让你确认。如果一时说不清也没关系，我们先标 TBD，最后一起回看。准备好了吗？

**鼓励叙述**（阶段 1 用户卡住时）：

> 别担心讲得不完整，先讲你最熟悉的那部分——剩下的我会一项项问回来。

**遇到模糊回答**：

> 这部分我先记 TBD。我们继续往下走，回头一起回看是否能补上具体的字段或来源。

**遇到看似冗余的步骤**：

> 我注意到 S<N> 的输出好像没有下游消费——是我漏了，还是这一步可以并到 S<M> 里？

**进入下一阶段前**：

> 我把刚才几轮访谈的要点重述一下：<复述>。如果这跟你的设想一致，我们进入下一阶段。

**呈现选型时（阶段 4）**：

> 我给每一步都选好了 LinkFox 里的工具，下面把方案讲给你听——每一步包括"业务目标 / 用什么工具 / 这工具能给什么数据 / 有哪些风险或局限 / 我没选哪些以及原因"。你过目，有不同意见随时打断。

## 输出物

访谈结束时，agent 把纪要写到 `<产物目录>/.draft/interview.md`，把选型表写到 `<产物目录>/.draft/mapping.md`，作为后续步骤映射定稿、生成、自检的依据。
