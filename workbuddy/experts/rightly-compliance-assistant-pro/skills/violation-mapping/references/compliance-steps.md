# App隐私合规达标步骤指南

## 概述

本文综合《个人信息安全规范》(GB/T 35273-2020)、《App违法违规收集使用个人信息行为认定方法》、TTAF 077.1-2020《最小必要评估规范》等法规标准，梳理App达到隐私合规要求的完整步骤。

## 步骤一：隐私政策完善

### 要求
- **完整披露**：逐一列出收集使用个人信息的目的、方式、范围
- **SDK披露**：完整列出所有第三方SDK的名称、收集信息类型、目的（含嵌套SDK）
- **格式规范**：简体中文、字号/颜色清晰可读、访问路径不超过4次点击
- **弹窗告知**：首次运行弹窗提示，非默认勾选，明确App类型和基本功能
- **效力说明**：明确"同意隐私政策仅代表知悉和授权基本功能的必要个人信息"

### 检查要点
- [ ] 隐私政策是否完整包含所有信息收集类型
- [ ] 第三方SDK目录是否完整（含嵌套SDK）
- [ ] 首次弹窗是否规范（非默认勾选、包含App类型/基本功能/必要信息范围）
- [ ] 隐私政策访问路径是否在4次点击以内
- [ ] 提供可跳转链接，支持跳转到个性化推荐开关

## 步骤二：告知同意机制

### 要求
- **同意前管控**：用户同意隐私政策前，不得调用任何敏感API
- **单独同意**：收集敏感个人信息需单独告知并获取同意
- **分场景同意**：按业务功能分项征得同意，不得一揽子同意
- **撤回机制**：提供便捷的撤回同意途径

### 技术实现
```
// PMonitor隐私同意前管控示例
PMonitor.getConfig()
  .updateRuleForAPI(模块名, API名)
  .rule(GeneralRule.BACK_NORMAL_AND_FRONT_NORMAL)
  .ruleBeforeStrategy(RuleConstant.STRATEGY_BAN) // 同意前禁用
  .submitRule();
```

### 检查要点
- [ ] 同意隐私政策前是否有敏感API调用
- [ ] 敏感信息（身份证、银行卡、人脸等）是否有单独同意弹窗
- [ ] 是否提供了撤回同意的便捷途径

## 步骤三：最小必要收集

### 要求
- **类型最小**：不收集与业务功能无关的信息
- **数量最小**：收集的信息量不超出实际需要
- **频率最小**：收集频率不超出业务需要
- **39类App对照**：参照必要个人信息范围规定

### 评估框架（TTAF 077.1-2020）
1. **告知同意评估**：按业务功能分项告知，时机和频率适当
2. **权限评估**：只申请业务相关权限，优先用系统替代方案
3. **收集评估**：类型/数量/频率最小化
4. **使用评估**：消除身份指向性，定向推送提供关闭选项
5. **传输评估**：类型/数量/频率最小化
6. **存储评估**：最短必要时间，超期删除或匿名化
7. **第三方共享评估**：类型/数量/频率最小化，征得同意
8. **删除评估**：超出存储期限后删除或匿名化

### 检查要点
- [ ] 是否对照39类App规定评估必要信息范围
- [ ] 是否存在无关场景的信息收集
- [ ] 收集频率是否合理（如定位API调用频次）
- [ ] 后台是否存在静默采集行为

## 步骤四：权限动态申请

### 要求
- **动态申请**：在对应业务功能启动时申请权限
- **非一揽子**：不要求一次性同意多个非必要权限
- **目的告知**：申请权限时同步告知使用目的
- **不强制**：用户拒绝非必要权限后不影响基本功能

### 检查要点
- [ ] 权限是否在使用时动态申请（而非启动时一次性申请）
- [ ] 每次权限申请是否附带使用目的说明
- [ ] 用户拒绝权限后基本功能是否正常
- [ ] 是否存在声明但未使用的权限（建议移除）

## 步骤五：分模块授权

### 要求
- 按业务场景拆分权限管理
- 不同模块独立管控API调用
- 提供模块管理界面

### 技术实现
```
// Rightly分模块授权方案
// 1. 划分模块，定义模块与权限的关系
// 2. 模块进入退出打点
// 3. 模块管理界面（授权/取消）
// 4. API执行时根据模块授权情况管控
```

### 检查要点
- [ ] 是否按功能场景拆分了权限管理
- [ ] 非授权场景下是否禁止了敏感API调用
- [ ] 是否提供了模块权限管理入口

## 步骤六：三方SDK治理

### 要求
- **评估**：使用SDK前进行个人信息保护能力评估
- **协议**：通过合同明确各方权利和义务
- **披露**：集中展示并及时更新嵌入的SDK信息
- **管控**：限制SDK超范围收集

### 排查手段
1. 静态扫描：分SDK查看敏感API调用情况
2. 动态监控：根据SDK包名进行堆栈搜索
3. 网络传输监控：检查SDK的数据上传行为

### 检查要点
- [ ] 是否完整梳理了所有第三方SDK
- [ ] SDK的信息收集是否超出必要范围
- [ ] 隐私政策中SDK披露信息是否完整
- [ ] 是否配置了SDK的API访问兜底规则

## 步骤七：用户权利保障

### 要求
- **查询**：提供个人信息查询功能
- **更正**：提供个人信息更正功能
- **删除**：提供个人信息删除功能
- **导出**：提供个人信息复制/导出功能
- **注销**：提供便捷的账号注销功能（不得捆绑注销）
- **投诉**：公布投诉举报渠道
- **时限**：15个工作日内完成处理

### 检查要点
- [ ] 是否提供了个人信息查询、更正、删除、导出功能
- [ ] 账号注销是否便捷（非捆绑注销）
- [ ] 是否公布了投诉举报渠道
- [ ] 响应时限是否在15个工作日以内

## 步骤八：安全管理机制

### 要求
- 建立个人信息安全管理制度
- 采取访问控制、加密、去标识化等技术措施
- 建立安全事件应急响应制度
- 定期进行安全审计

### 检查要点
- [ ] 是否建立了个人信息安全管理制度
- [ ] 是否采取了技术安全防护措施
- [ ] 是否有安全事件响应预案
- [ ] 是否定期进行安全审计

## 步骤九：持续合规监控

### 要求
- 定期自查（建议每月/每季度）
- 版本更新时重新评估
- 关注年度治理重点方向
- 使用合规监控工具持续跟踪

### 推荐工具
- **Rightly**：静态扫描 + 动态监控 + 网络传输分析
- **PMonitor**：运行时API调用监控 + 规则管控
- **合规金丝雀**(ComplianceCanary)：调试期敏感访问可视化

### 检查要点
- [ ] 是否建立了定期自查机制
- [ ] 版本更新时是否重新评估合规状态
- [ ] 是否持续跟踪监管动态
