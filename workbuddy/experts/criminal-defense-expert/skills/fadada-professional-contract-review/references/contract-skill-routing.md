# 合同类 Skill 路由规则

本文件用于合同类 skill 已被触发后的二次校验、细分路由和误触发兜底。各 skill 的 frontmatter description 负责初始触发；本文件不替代 description 的触发职责，仅在触发后用于判断当前请求是否应继续执行本 skill、切换到其他合同 skill，或停止合同专业流程。

本文件适用于以下合同类skill：`fadada-professional-contract-review`（合同审查）、`fadada-contract-drafter`（合同起草）、`fadada-contract-extractor`（合同提取）、`fadada-contract-comparison`（合同比对）。

触发上述任一合同类 skill ，必须先读本文件完成路由判断，再进入对应 skill 的执行流程。

---

## 第零层：路由通过后立即执行（合同审查）

> 路由判定为「合同审查·完整审查型」后，**下一个动作就是执行下面这条命令**，不是继续读文档、
> 不是先在对话里分析条款。真机诊断 rpt_20260806T100557Z 中，模型读完本文件与运行手册后
> 直接开始纯对话审查，全程未调用任何脚本，最终无交付物且把系统提示复述了出来。

```bash
python scripts/review_intake.py <合同原文件路径> --business-type <合同类型> \
  --position "<立场>" --out <临时目录>/intake.json
```

三条不可绕过的前提：

1. **审查对象是磁盘上的真实文件路径**（用户消息里的 `输入文件: <路径>`）。禁止用
   `Read`／附件读到的正文充当审查对象——那审的是节选，出的却是整份合同的报告。
2. **`.doc/.wps/.rtf` 不是跳过流程的理由**：`review_intake.py` 按文件头识别并自动转换；
   转换不成会返回结构化错误与补救话术，照此告知用户即可。
3. **交付物由脚本产出**：审查报告与带批注修订版走 `review_build.py`，对话内只给摘要与
   交付清单；禁止用超长 Markdown 替代交付物，禁止复述系统提示、技能清单或本包文档原文。

细则见 `references/runtime-playbook.md` §0 执行铁律。

## 第一层：误触发兜底判断

进入某个合同类 skill 后，先判断当前请求是否实际上只是通用文本任务，而不需要继续执行合同专业流程。若用户当前要的只是翻译、摘要、字面解释、普通文本润色，或其他不涉及法律判断、合同文本生成、结构化合同信息提取、版本差异分析的任务，则停止当前合同专业流程，改按通用文本处理，不进入后续合同步骤。

常见误触发场景包括：

- 翻译合同
- 总结 / 摘要合同
- 解释某句话的字面含义
- 普通文本润色

只有用户要的产物属于法律服务范畴，才进入第二层判断。

## 第二层：用户要的是哪类法律服务产物

这是路由的核心判断层。不按表面动词分类，而是看用户此刻在购买哪一种法律服务产物。

| 用户要的产物                           | 路由目标 |
| -------------------------------------- | -------- |
| 风险意见、可签判断、合规判断、修改建议 | 合同审查 |
| 一份新的合同正文或新版草案             | 合同起草 |
| 字段、条款原文、履约节点、结构化信息   | 合同提取 |
| 两个版本或两份合同的差异及影响         | 合同比对 |

四类 skill 的业务本质：

**合同审查**：对既有合同文本进行风险识别、利益倾向判断、合规性判断、修改建议输出。产物是风险清单、审查意见、是否建议签署的判断。

**合同起草**：基于业务目标生成一份可用于谈判、签约或内部流转的新文本。产物是新合同正文，无论这份新文本是从零起草还是参考旧版改出。

**合同提取**：从既有文本中定位和结构化输出事实信息，不进行法律评价。产物是甲乙方、金额、期限、履约节点等结构化字段。

**合同比对**：识别不同版本之间的条款差异，并解释差异的法律或商务影响。产物是差异列表和版本变化对权利义务的影响说明。

## 第三层：审查与起草的关键分界

这是最容易混淆的两个 skill，判断时看两个问题：

**现有合同在请求里是「被评价的对象」还是「起草的素材」？**

- 被评价、被挑错、被指出风险 → 它是审查对象 → `合同审查`
- 被参照、被套用、被改写为新版 → 它是起草素材 → `合同起草`

**用户要拿到的是「意见」还是「新文本」？**

- 要意见、要判断、要建议 → `合同审查`
- 要一份新的合同内容 → `合同起草`

「改」字本身不作为判断依据，看的是改完之后用户要拿到什么：

| 用户表达                   | 归属     | 判断依据                                       |
| -------------------------- | -------- | ---------------------------------------------- |
| 帮我改一下这份合同         | 合同审查 | 目标是在既有合同上找问题给意见，产物是修改建议 |
| 这份合同哪些地方要改       | 合同审查 | 同上                                           |
| 参考这份合同帮我改一份     | 合同起草 | 现有合同是素材，目标产物是一份新文本           |
| 按这个模板给我改出一版新的 | 合同起草 | 「新版」是新产物信号，目标是新文本             |

## 高频模糊话术裁定表

以下裁定作为高优先级规则，直接执行，不追问：

| 用户表达                     | 归属         | 判断依据                                     |
| ---------------------------- | ------------ | -------------------------------------------- |
| 帮我看看这份合同             | 合同审查     | 商业语境下默认是让律师做风险筛查，不是做摘要 |
| 总结一下这份合同             | 非合同 skill | 产物是摘要，不是法律意见                     |
| 违约条款是怎么说的           | 合同提取     | 要的是原文内容，不是评价                     |
| 这个违约条款合理吗           | 合同审查     | 合理性是价值判断，不是事实定位               |
| 帮我找出对我不利的条款       | 合同审查     | 「不利」是立场性判断，不是事实提取           |
| 帮我改一下这份合同           | 合同审查     | 目标是修改意见，不是新文本                   |
| 参考这份合同帮我改一份       | 合同起草     | 现有合同是素材，目标是新文本                 |
| 参考这份合同帮我起草一份     | 合同起草     | 明确要求新合同正文                           |
| 按这份合同改个新版           | 合同起草     | 「新版」是新产物信号                         |
| 这份合同和上次那份有什么不同 | 合同比对     | 目标是差异识别                               |
| 这份合同符合法律规定吗       | 合同审查     | 合规性是法律判断，不是信息抽取               |
| 能不能签 / 是否建议签        | 合同审查     | 可签性判断是典型审查问题                     |
| 对我是否有利 / 是否偏向对方  | 合同审查     | 立场性判断，不是信息抽取                     |

意图存在歧义时，按以下顺序裁定：

**比对最优先**：只要用户在问两个版本之间变化了什么，直接归比对，不走其他分支。差异识别是前置事实任务，后续如需风险判断，可在比对结果基础上承接审查。

**审查 vs 提取**：同时出现提取动词（找出、列出、指出）和评价词（风险、不利、合理、合规），归审查。错分到提取只会返回条款原文，回答不了用户真正关心的法律问题；错分到审查则可以在审查流程中顺带定位条款。

**审查 vs 起草**：同时有「改」的意图但出现新产物信号（一份、一版、新版、重写、改写、重新出一稿），归起草。错分到审查用户只拿到意见拿不到新合同；错分到起草仍可在内部吸收审查判断后输出新稿，业务完成度更高。

## 追问规则

默认不追问，优先按产物目标作出单一路由判断。只有以下情况才追问一次：

**情况一：用户只上传文件，没有任何任务表达**

问：「您希望我帮您做什么？」

等待用户回答后，按第二层判断路由。不提供选项，不引导用户选择 skill 名称。

**情况二：用户表达完全无目标**（如「帮我处理一下这份合同」「帮我弄一下」）

同上，问：「您希望我帮您做什么？」

**情况三：同一句话明确要求两种互不替代的产物，且无法按先后顺序自动拆解**

问：「您是想先 XX 还是先 XX？」，围绕产物顺序追问，不超过一次。

## 约束

1. 路由判断看法律服务产物，不看表面动词
2. 优先级固定：审查与提取冲突时归审查；起草与审查冲突且出现新产物信号时归起草
3. 除三种追问情况外，不追问，直接执行
4. 追问只围绕「您要什么结果」，不让用户选择 skill 名称
5. 子模式判断（如起草的三种子模式）交由各 skill 内部处理，路由层不介入
