# 系统性改写工作流（子流程C）

> 合并自：systematic-redraft

## 核心原则：人审关卡

**未经用户确认，不执行改写。** 改写前必须先出改写计划（plan.json，状态=草稿），等用户批准（状态=已确认）后才生成修订版。

## 改写流程

```
理解意图 → 影响分析 → 改写计划(人审关卡) → 生成修订版 → 一致性校验 → 差异对比
```

### 1. 影响分析
- 理解改写意图（改什么+怎么改）
- 检索受影响的所有条款（连锁影响）
- 评估改写范围和风险

### 2. 改写计划（人审关卡）
- 输出plan.json（状态=草稿）
- 含：修改项清单+每条的影响范围+原文vs改写对比
- [注意] **等用户确认后才进入下一步**

### 3. 生成修订版
- OOXML `<w:ins>`/`<w:del>` 修订标记（非内联文字标注）
- 每条修改附依据标签

### 4. 一致性校验
- 编号序列（无重复/子级前缀一致）
- 交叉引用（无悬空引用）
- 定义（无重复/引用有定义）
- 金额（定义值与正文引用值匹配）

### 5. 差异对比
- 输出原文vs改写版的差异报告

## 典型场景

"把违约条款中的'极端恶劣情况'分成'一般违约'和'重大违约'两档，并联动调整赔偿上限和回购触发条件。"

→ 影响分析：违约条款(第X条) + 赔偿条款(第Y条) + 回购条款(第Z条)
→ 改写计划：三处修改+连锁影响评估
→ 用户确认→生成修订版→一致性校验→完成

## 约束

- 不编造条款内容，所有修改基于原文
- 不删除其他方权利条款而不标注
- 输出使用OOXML修订标记，非内联文字标注
