# PGTree拆解与RRAG内循环方法论

> 来源：patent-writer项目的方法论设计，本文件为方法论文档，非可执行代码。
> 用法：作为交底书撰写时的可选方法论参考，使用者决定是否调用。

---

## 一、PGTree（Patent Goal Tree）递归拆解

### 1.1 核心思想

PGTree将专利交底书的撰写目标递归分解为树状结构，每个节点代表一个需要解决的技术子问题。

**白话解释**：把"写一份交底书"这个大任务，像剥洋葱一样一层层拆成小任务，直到每个小任务都明确到"写什么、怎么写"。

### 1.2 树结构定义

```
根节点：专利交底书
├── L1节点1：技术背景（第一章）
│   ├── L2节点1.1：现有技术分类
│   ├── L2节点1.2：现有技术缺点
│   └── L2节点1.3：查新结果嵌入
├── L1节点2：技术问题（第二章）
│   ├── L2节点2.1：要解决的核心问题
│   └── L2节点2.2：技术效果目标
├── L1节点3：技术方案（第三章）
│   ├── L2节点3.1：系统架构
│   ├── L2节点3.2：模块功能
│   ├── L2节点3.3：流程设计
│   ├── L2节点3.4：符号与公式
│   └── L2节点3.5：关键参数
├── L1节点4：技术优点（第四章）
├── L1节点5：保护关键点（第五章）
└── L1节点6：实施例（第六章）
    ├── L2节点6.1：C端实施例
    ├── L2节点6.2：B端实施例
    └── L2节点6.3：失败实验
```

### 1.3 拆解规则

| 规则 | 说明 |
|------|------|
| **完备性** | 每个父节点的子节点集合必须覆盖父节点的全部内涵 |
| **独立性** | 同层兄弟节点之间不应有内容重叠 |
| **可追溯** | 每个叶节点必须映射到至少一个源材料ID（P001/E001/F001/C001） |
| **可验证** | 每个叶节点完成后必须通过RRAG内循环校验 |

### 1.4 使用方式

1. 撰写前：根据架构蓝图构建PGTree，确认每个叶节点有源材料支撑
2. 撰写中：按叶节点逐个撰写，每完成一个叶节点即触发RRAG校验
3. 撰写后：检查PGTree是否所有节点都已完成（无空洞）

### 1.5 与source grounding的配合

PGTree的每个叶节点必须标注source grounding状态：
- `explicit`：源材料中直接出现
- `inherent`：源材料中隐含，可合理推导
- `needs-confirmation`：需要发明人确认
- `unsupported`：无源材料支撑（禁止出现在正式交底书中）

## 二、RRAG（Refined Retrieval-Augmented Generation）内循环

### 2.1 核心思想

RRAG是对每个PGTree叶节点生成内容的内循环校验机制：生成→检索→比对→修正→再生成。

**白话解释**：写完一段内容后，马上去查相关文献，看写的内容和已有技术有没有矛盾，有矛盾就改，改完再查，直到没问题为止。

### 2.2 内循环流程

```
┌──────────────────────────────────────────┐
│  RRAG内循环（对每个PGTree叶节点）          │
│                                          │
│  1. 生成：基于源材料撰写该叶节点内容        │
│     ↓                                    │
│  2. 检索：提取该叶节点关键技术词，         │
│     调用patent-prior-art-searcher检索     │
│     ↓                                    │
│  3. 比对：将生成内容与检索结果比对          │
│     - 新颖性比对：是否与现有技术雷同       │
│     - 一致性比对：技术参数是否矛盾         │
│     - 充分性比对：是否缺少必要技术细节     │
│     ↓                                    │
│  4. 修正：根据比对结果修正内容             │
│     - 标注与现有技术的区别                │
│     - 补充缺失的技术细节                  │
│     - 修正错误的参数表述                  │
│     ↓                                    │
│  5. 再生成：输出修正后的内容               │
│     ↓                                    │
│  6. 校验通过？ ──是──→ 进入下一叶节点      │
│       │                                  │
│       否                                 │
│       │                                  │
│       └──→ 回到步骤2（最多循环3次）       │
│                                          │
└──────────────────────────────────────────┘
```

### 2.3 校验维度

| 维度 | 检查内容 | 工具支持 |
|------|----------|----------|
| **新颖性** | 生成内容是否与已检索到的现有技术雷同 | patent-prior-art-searcher |
| **一致性** | 参数、符号、术语是否与全文其他部分一致 | 交叉引用检查 |
| **充分性** | 技术方案是否能让本领域技术人员实施 | disclosure_self_check.md |
| **溯源** | 事实性声明是否有来源支撑 | hallucination-guard |
| **逻辑** | 因果关系是否成立，推理链是否完整 | 人工判断 |

### 2.4 退出条件

- **正常退出**：5个维度全部通过 → 标记为 `VERIFIED_DONE`
- **降级退出**：循环3次仍有未解决项 → 标记为 `needs_author_input`，列出具体问题请发明人确认
- **禁止退出**：存在 `unsupported` 内容时，禁止以"降级退出"跳过

## 三、PGTree + RRAG联合工作流

```
Step 1: 构建PGTree
  ├── 输入：架构蓝图 + 源材料
  ├── 输出：完整树结构 + 每个叶节点的source grounding状态
  └── 门禁：PGTree必须通过完备性检查（无空洞节点）

Step 2: 逐叶节点撰写 + RRAG内循环
  ├── 按L1节点顺序，逐个L2叶节点撰写
  ├── 每个叶节点完成后触发RRAG内循环
  └── RRAG通过后才进入下一叶节点

Step 3: 全文一致性检查
  ├── 所有叶节点完成后，检查跨节点一致性
  ├── 符号表、参数表、术语表全局校验
  └── 输出：交底书初稿 + PGTree完成度报告
```

## 四、与其他工具的配合关系

| 工具 | 在PGTree+RRAG中的角色 |
|------|----------------------|
| `patent-prior-art-searcher` | RRAG步骤2的检索引擎 |
| `hallucination-guard` | RRAG步骤3的溯源校验 |
| `disclosure_self_check.md` | RRAG步骤3的充分性校验 |
| `johari-window-auditor` | Step 3后的认知盲区补充检查 |
| `patent-compliance-checker` | 全文完成后的合规校验 |
| `math_render.py` | 叶节点含公式时的渲染工具 |
| `mermaid_render.py` | 叶节点含图示时的渲染工具 |

## 五、适用场景与限制

### 适用场景
- 从学术论文/技术文档转化为专利交底书
- 技术方案复杂、需要系统性拆解的专利
- 需要确保每个技术点都有源材料支撑的场景

### 不适用场景
- 简单的专利修改/迭代（直接用merger.md/correction_handler.md）
- 已有完整交底书只需格式调整（直接用patent-packager）
- 纯idea阶段无任何技术文档（先用Phase 0采集素材）

### 限制说明
- PGTree拆解深度建议不超过3层（L1→L2→L3），过深会导致效率下降
- RRAG内循环最多3次，超过则降级为人工确认
- 本方法论为辅助工具，不替代人工技术判断
