# 三种工作模式参考指南

> 来源：patent-writer项目的三种输入模式设计。
> 用法：使用者根据输入材料类型选择对应模式，不需要的模式跳过。

---

## 模式A：论文改专利（Paper-to-Patent）

### 适用场景
用户已有一篇学术论文（已发表或未发表），希望将其转化为专利交底书/申请文件。

### 输入要求
- 学术论文全文（PDF/Word/Markdown）
- 可选：补充实验数据、代码仓库链接

### 工作流程

```
1. 源材料解析
   ├── 提取论文结构：标题/摘要/引言/方法/实验/结论
   ├── 建立source grounding IDs：
   │   ├── P001... 论文文本块
   │   ├── E001... 公式
   │   ├── F001... 图表
   │   └── C001... 代码/补充材料
   └── 标注每个技术特征的支撑状态

2. 专利点挖掘（参考 disclosure/patent_points_analyzer.md）
   ├── 从论文贡献中提取3-5个候选专利点
   ├── 区分"论文已披露"vs"论文未披露"的技术点
   └── 融合为1个主专利点（方法+系统）

3. 新颖性风险评估
   ├── 若论文已发表 → 检查是否在6个月宽限期内
   ├── 已发表内容 → 只能作为背景技术，不能作为权利要求
   └── 未发表内容 → 可作为核心权利要求

4. 交底书生成（参考 disclosure/disclosure_builder.md）
   ├── 第一章：论文已公开内容 → 现有技术
   ├── 第二章：论文指出的不足 → 技术问题
   ├── 第三章：论文方法 → 技术方案（上位概念化）
   ├── 第四章：论文效果 → 技术优点
   ├── 第五章：权利要求偏向点
   └── 第六章：论文实验 → 实施例

5. 公式与符号处理
   ├── 论文公式 → 用 math_render.py 渲染为Office Math
   ├── 论文符号 → 按专利符号体例规范化（§7.7）
   └── 参数表与符号表逐字同形校验
```

### 关键约束
- **已发表论文**：论文中公开的所有技术内容不能作为权利要求的保护范围
- **未发表论文**：可作为原始技术方案，但需注意后续发表时机
- **公式保留**：核心公式必须保留为可编辑Office Math，不用纯LaTeX字符串

## 模式B：技术文档改专利（Tech-Doc-to-Patent）

### 适用场景
用户有技术文档（设计文档/技术方案/会议记录/代码注释），但不是学术论文格式。

### 输入要求
- 技术文档（任意格式）
- 可选：相关代码、设计图、会议纪要

### 工作流程

```
1. 项目扫描（参考 disclosure/project_scan.md）
   ├── 扫描所有技术文档
   ├── .docx/.pptx 先用 docx_to_md.py / pptx_to_md.py 转换
   ├── PDF用 extract_pdf_text.py 提取文本
   └── 建立技术知识库

2. 专利点挖掘
   ├── 从技术方案中识别创新点
   ├── 区分"行业通用做法"vs"独特创新"
   └── 融合为专利点

3. 查新与差异化
   ├── 调用 patent-prior-art-searcher
   └── 明确与现有技术的区别

4. 交底书生成
   └── 同模式A的步骤4
```

## 模式C：Idea到专利（Idea-to-Patent）

### 适用场景
用户只有技术想法/创意，没有成文的技术文档或论文。

### 输入要求
- 发明人访谈（Phase 0的15项问题）
- 可选：手绘草图、口述记录、竞品链接

### 工作流程

```
1. 深度访谈（Phase 0）
   ├── 完成法律事实层5项确认
   ├── 完成技术方案层5项采集
   ├── 完成心理预判层5项评估
   └── 输出：需求摘要

2. 技术方案补全
   ├── 基于访谈内容，AI提出技术方案框架
   ├── 请发明人确认/修正/补充
   ├── 可能需要多轮对话补全技术细节
   └── 输出：技术方案文档（由AI整理，发明人确认）

3. 查新检索
   ├── 基于技术方案提取关键词
   ├── 调用 patent-prior-art-searcher
   └── 评估新颖性和创造性风险

4. 架构设计
   ├── 基于确认后的技术方案设计交底书架构
   └── 输出：交底书架构蓝图

5. 交底书生成
   └── 同模式A的步骤4

6. 认知盲区补充
   ├── 调用 johari-window-auditor
   ├── 重点挖掘"隐藏区"（发明人知道但没说的）
   └── 重点探索"未知区"（未来演进/上位概念）
```

### 关键约束
- **多轮确认**：每个技术细节都需要发明人明确确认
- **不杜撰**：AI可以提出技术方案框架，但不能编造发明人未提及的技术细节
- **标记待确认**：所有AI推断的内容标记为 `[TO CONFIRM: 具体问题]`

## 附加能力：双语摘要

### 适用场景
需要同时提供中文和英文摘要的专利申请（如PCT国际申请预准备）。

### 工作流程

```
1. 先撰写中文摘要（≤300字）
   ├── 包含：技术领域 + 技术问题 + 技术方案 + 技术效果
   └── 字数检查（中文≤300字）

2. 翻译为英文摘要
   ├── 基于中文摘要翻译，不是重新撰写
   ├── 术语参照 nature-shared/core/terminology-ledger.md
   └── 英文摘要无字数限制（但建议≤250词）

3. 双语对照校验
   ├── 中英文技术术语一致性
   ├── 中英文技术方案描述一致性
   └── 中英文技术效果表述一致性
```

## 附加能力：断点续写

### 适用场景
专利交底书撰写过程中中断（如token限制/会话中断），需要从断点继续。

### 工作流程

```
1. 断点检测
   ├── 读取已有交底书文件
   ├── 识别最后完成的章节
   └── 识别未完成的章节

2. 上下文恢复
   ├── 读取已完成章节内容
   ├── 读取PGTree状态（如使用了PGTree）
   ├── 读取source grounding映射
   └── 恢复撰写上下文

3. 续写
   ├── 从断点处的下一个章节开始
   ├── 保持术语/符号/格式与已完成部分一致
   └── 续写完成后进行全文一致性检查

4. 断点记录
   ├── 使用 iteration_dialog_log.py 记录中断和续写信息
   └── 在案件目录的对话记录中追加续写记录
```

### 断点续写的文件标记

在交底书Markdown中使用HTML注释标记断点：

```markdown
<!-- BREAKPOINT: chapter=3, section=3.4, status=incomplete, reason=session_limit -->
```

续写时读取此标记，从标记位置继续。

## 模式选择决策树

```
用户有学术论文？
├── 是 → 模式A：论文改专利
└── 否 → 用户有技术文档？
         ├── 是 → 模式B：技术文档改专利
         └── 否 → 模式C：Idea到专利

需要双语摘要？
├── 是 → 附加：双语摘要能力
└── 否 → 跳过

撰写中断需要继续？
├── 是 → 附加：断点续写能力
└── 否 → 跳过
```
