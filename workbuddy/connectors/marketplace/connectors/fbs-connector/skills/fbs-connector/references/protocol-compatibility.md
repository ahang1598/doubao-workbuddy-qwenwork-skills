# MCP 双版本兼容合同

本连接器的兼容目标固定为以下两个相邻稳定修订：

1. `2026-07-28`（当前目标修订）
2. `2025-11-25`（前一稳定修订）

## 协商责任

- `mcp.json` 不静态设置 `MCP-Protocol-Version`；协议探测、选择和每请求协议头由 WorkBuddy 宿主负责。
- 连接器不从包版本、专家版本或自定义业务头推断 MCP 修订。
- 服务端与宿主必须在上述两个修订之一完成协商；落到更早修订时只能标记兼容降级，不得把它写成双版本已验证。

## `2026-07-28` 路径

- 宿主先使用 `server/discover` 获取服务信息与能力。
- 请求按该修订携带自描述协议头；连接器不依赖 `initialize` 或 HTTP 会话才能调用业务工具。
- 响应中的未知能力、缓存和 `_meta` 字段按向前兼容原则忽略，不能覆盖业务成功/失败判断。

## `2025-11-25` 路径

- 宿主使用 `initialize` 完成版本与能力协商，再调用 `tools/list` / `tools/call`。
- 若服务端返回会话标识，由宿主管理；福帮手业务连续性仍以工具返回的绑定参数为准，Skill 不自行维护 HTTP 会话。

## 两个修订共用的业务合同

- JSON-RPC 2.0 包络与请求 ID 必须正确。
- `tools/list` 是工具与 input schema 真源。
- `tools/call` 的工具级错误、业务失败与缺失回执必须失败关闭。
- 主线语义保持为身份确认 → 场景读取 → 真实交付后的幂等进度记录。
- 不把协议协商成功等同于工具可用、自然业务或上架成功。
