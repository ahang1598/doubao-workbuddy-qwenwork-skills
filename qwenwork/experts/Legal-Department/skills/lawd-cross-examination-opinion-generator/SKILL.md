# 质证意见生成

针对对方提交的民商事诉讼证据，完成逐项分析并交付可提交的 DOCX 质证意见书。

## 强制原则

1. **逐项覆盖**：证据清单中的每一项都必须出现在速览表、逐项正文和总结论中，编号、名称、结论保持一致。
2. **四维分析**：分别处理真实性、合法性、关联性和证明力。四维均须有状态；确实不适用时写明“不适用”及理由。
3. **事实受限**：只依据用户材料和已核验的法律依据。不得编造瑕疵、取证经过、反证、案件事实、法条或程序期限。
4. **精确表态**：区分“对证据真实性无异议”和“认可其证明目的”。前者不当然意味着认可关联性、证明力或对方主张。
5. **中性处理不确定性**：材料不足时使用“待核验”，说明待核验事项和所需材料；不得直接断言伪造、违法或无效。
6. **允许无异议**：没有材料支持异议时如实写“无异议”，不得为形式完整机械制造质疑。
7. **DOCX 强制交付**：任务完成必须产生可打开且通过校验的 `.docx` 文件。Markdown 只可用于预览，不得替代最终交付。

## 工作流程

### 1. 明确任务边界

确认：

- 代理方及对方证据的提交方；
- 本次需要质证的证据范围；
- 用户要正式提交稿、庭审提纲，还是两者均需；
- 已知的法院、案号、案由、争议焦点和时间要求。

仅在缺失信息会实质影响分析或正式文书时提问。用户已明确的信息不得重复确认，也不得固定要求两轮确认。

### 2. 建立证据索引

按 [材料与评估清单](references/intake-and-assessment-checklists.md) 建立唯一证据索引。至少记录：

- 证据编号和名称；
- 提交方及证明目的；
- 页码或其他可复核定位；
- 材料形态、原件或原始载体状态；
- 用户已说明的形成、取得、保管和提交情况。

对方证据是直接质证对象，缺少具体内容时不能生成实质质证结论。起诉状、答辩状、己方证据等属于增强材料，不得机械要求全部上传；缺失时说明分析边界后继续处理可处理部分。

发现证据编号重复、缺项或清单与材料不一致时，先列出差异并处理。无法确认的项目标记“待核验”，不得补造。

### 3. 逐项完成四维分析

对每项证据分别填写：

| 维度 | 核心问题 |
|---|---|
| 真实性 | 内容和载体是否真实完整，复制件能否核对，电子数据形成和保存过程是否可靠 |
| 合法性 | 形式、来源及取得方式是否符合法律规定，是否存在需要程序处理的问题 |
| 关联性 | 与争议焦点、待证事实及对方证明目的是否存在实质联系 |
| 证明力 | 即使前三项无异议，是否足以单独或结合其他证据实现对方证明目的 |

每个维度只能使用以下状态：

- `无异议`：当前材料没有支持异议的事实基础；
- `有异议`：材料中存在具体、可说明的异议事实；
- `待核验`：缺少作出判断所必需的材料；
- `不适用`：该维度对特定问题确实不适用，并写明理由。

“有异议”必须写明材料依据和对证明目的的影响；“待核验”必须写明待核验事项、所需材料及核验后的可能影响。

#### 四维之间的关系

四个维度分别判断，不得互相替代：

- 真实性存在疑问，不当然意味着取证违法；
- 证据来源合法，不当然意味着内容真实；
- 与案件有关联，不当然意味着足以实现证明目的；
- 复制件或截图需要核验，不当然意味着证据应被排除；
- 单项证明力较弱，不等于该证据在全案中毫无作用。

对于对方证据的同一部分，可以在某一维度无异议、在另一维度有异议。正文必须明确异议针对的是证据本身、部分内容、证明范围还是证明目的。

#### 材料依据分级

区分以下信息来源，并在发生冲突时说明：

1. 证据材料中直接可见的内容；
2. 起诉状、答辩状等诉讼文书中的单方主张；
3. 用户补充说明但尚无材料印证的事实；
4. 基于材料作出的分析性判断——**须使用"基于材料分析"前缀与第一类直接可见事实区分**（如"基于材料分析，该宣传口号属愿景性表达"），不得写成材料直接可见的事实；
5. 仍需原件、原始载体或第三方记录核验的事项。

**基于扫描件/图片描述得出的判断**（如盖章清晰度、签名形态），须标注"基于扫描件描述，以原件核验为准"。

不得把第二至第五类信息改写成已经查明的客观事实。引用材料时尽量保留页码、条款、段落、文件名或时间戳；材料没有页码时使用其他真实定位，禁止补造页码。

#### 证据之间的综合关系

完成单项分析后，再检查证据之间是否：

- 来自同一信息源而只是不同呈现形式；
- 在主体、时间、金额或履行节点上相互印证；
- 存在无法解释的冲突；
- 共同补足或仍未补足对方证明目的的关键环节；
- 被己方材料直接反驳，或仅受到一般性质疑。

**工具化交叉验证（涉及多份证据时必须逐项执行）**：

| 工具 | 做法 |
|------|------|
| 金额交叉验证表 | 列出各凭证/收据/聊天记录中的金额，逐笔加总并与诉称/主张金额核对；差异必须标注差异额与可能原因，禁止静默取其一；退费、已还款是否扣减须检查 |
| 时间线对照表 | 将各证据的形成时间排成时间线，检查与合同履行节点、诉称事实时序是否吻合 |
| 主体一致性检查 | 收据客户名、收款方、签字人与当事人的关系是否查明；不一致时查明关系并分析影响 |

综合分析不能覆盖或改变单项表态。若总结论依赖多项证据组合，明确列出组合逻辑。

### 4. 形成单项策略

在四维分析后，为每项证据给出：

- 认可部分；
- 异议或待核验部分；
- 对其证明目的的评价；
- 单项结论；
- 必要的程序性申请；
- 有材料基础时的反证或补强建议。

单项结论使用清晰自然语言，例如“真实性无异议，但不足以证明全部货款已经到期”“对真实性待核验，现阶段不认可其证明目的”。不要使用“完全不认可”掩盖具体理由。

### 5. 处理法律依据和程序申请

需要引用法律时读取 [evidence-rules.md](references/evidence-rules.md)，并核对法规名称、版本、条号、施行状态和官方来源。**引用法释条号后，应调用法规检索能力（律师法规检索 skill 或法规检索 MCP 连接器）做交叉核验，确认现行有效；** 无法完成现行性核验时，写明"法律依据待核验"，不得凭记忆填入条号，也不得仅依赖参考文件中的历史核验日期。

鉴定、调查取证、提交原件或原始载体、证人出庭等申请仅在材料支持且与具体证据对应时提出。不得把可能性写成必然结论，不得承诺法院会准许。

### 5.1 控制交互节点

默认一次完成可完成的分析，不设置固定的“初步判断确认—Markdown 再确认”双重暂停。以下情形才需要在生成 DOCX 前请求用户补充或确认：

- 同一证据存在两个可能版本，选择不同版本会改变结论；
- 代理角色、质证范围或提交主体不明；
- 用户口述与材料记载存在实质冲突；
- 即将写入程序性申请，但申请对象或事实依据无法确定；
- 用户明确要求先审阅预览稿。

如不需要暂停，完成分析后直接生成和校验 DOCX。若用户要求预览，Markdown 预览与最终 DOCX 必须来自同一结构化数据，用户修改后同步更新数据再生成。

### 5.2 控制交付范围

正式质证意见书是必交付物。以下内容按需输出，不机械附加：

- 庭审口头质证提纲：用户要求或证据较多、需现场发言时；
- 反证建议：现有材料能够支持具体建议时；
- 程序性申请清单：确有对应申请事项时；
- 法律依据附录：正文引用较多或用户要求时；
- 钉钉在线文档：用户明确要求或工作流确有需要时。

附加内容不得改变正式文书中的证据编号、名称和单项结论。

### 6. 生成结构化数据

按照 [文书模板](references/cross-examination-template.md) 的 JSON 契约整理数据。执行前检查：

- `evidence_items` 非空且编号唯一；
- 每项均含四个维度及单项结论；
- 速览信息、逐项正文和总结论来自同一数据对象；
- 不含 `[待填写]`、`XXX`、`TODO` 等占位符；
- 不确定内容使用“未提供”或“待核验”，不伪造正式信息；
- `submission_date`：有用户指示用指示值；**无指示时使用案件审理期间内的合理日期，不得默认填系统当前日期**（案件时间线较早时，当前日期会与案情冲突）；确无法判断填"未提供"。

### 7. 生成并校验 DOCX

优先执行本技能自带的确定性脚本：

```bash
python3 scripts/generate_cross_examination_docx.py \
  --input /absolute/path/cross-examination.json \
  --output /absolute/path/质证意见书.docx

python3 scripts/validate_cross_examination_docx.py \
  --input /absolute/path/cross-examination.json \
  --docx /absolute/path/质证意见书.docx
```

生成脚本依赖 `python-docx`。若当前环境提供更强的 DOCX 能力，可以使用，但最终文件仍须满足本技能结构和校验门禁。不得假设某个兄弟 Skill 一定已安装。

如用户同时要求钉钉在线文档，可在 DOCX 成功后使用当前环境可用的 `dws doc create` 路径创建在线副本。在线文档是附加交付物，不等同于 `.docx`，也不能替代 DOCX。

若生成失败：

1. 尝试当前环境实际可用的其他 DOCX 能力；
2. 再次运行校验或进行等价的结构校验；
3. 仍未取得合格 `.docx` 时，明确报告“DOCX 交付未完成”及原因。可以提供 Markdown 供核对，但不得宣称任务已经完成。

## DOCX 质量门禁

交付前必须确认：

- 文件为有效 ZIP/OOXML，能够被 Word 解析，文件非空；
- 页面为 A4，标题样式固定为黑色，适合黑白打印；
- 证据编号在速览表、逐项正文和总结论中全部覆盖；
- 三处证据名称和单项结论一致；
- 四维分析无缺项；
- 文书中不存在占位符；
- 案号、法院、当事人、日期均来自输入或明确显示“未提供”；
- 未把“真实性无异议”改写为“认可证明目的”；
- 程序性申请和反证建议有对应证据及材料基础。

只有校验通过后，才能向用户报告 DOCX 已完成并提供绝对路径。

## 交付说明

最终说明保持简洁：

- DOCX 文件路径；
- 校验结果；
- 仍为“待核验”的关键事项；
- 如有在线文档，另列链接；
- 签署、盖章、提交份数和期限须由经办律师结合受理法院要求核实。

不得把 AI 生成稿描述为已经由律师审核，也不得保证证据会被法院采信或排除。

## 可选套件上下文（不影响独立使用）

1. 工作目录根存在 `套件运行规则.md` 时必须先读取并执行；不存在时以本技能硬规则为准，不影响独立使用。
2. 工作目录根存在 `办案画像.md` 时，只读取与当前任务有关的诉讼立场、风险偏好和文书风格；不存在时按本技能默认运行，不追问、不报错。
3. 仅当用户明确切换到某案或提供唯一案件路径时，读取 `cases/{案件简称}/案件画像.md`；不得猜测案件，不得跨案带入。
4. 画像只影响表达与偏好，不得覆盖事实、法律依据、必备结构、验证结果或本技能硬规则。
5. 已明确绑定唯一案件且案件管家可用时，成果完成后提交标准案件事件；无案件不建档、不回写，回写失败不得阻塞成果交付。
