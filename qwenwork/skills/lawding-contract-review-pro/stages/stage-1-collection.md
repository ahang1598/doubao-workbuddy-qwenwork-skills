# 阶段一：前置信息收集

> **你接收到的上游数据：** 无（本阶段是起点）。
> **你需要产出的下游数据：** 阶段一产物 JSON（格式见 SKILL.md）。

当技能被触发时，**立即中止一切审查动作**，进入信息收集环节。

---

## 步骤 1：确认合同文件

检查用户是否已提供合同文件。如果没有，请求用户上传。

若文件不存在、无读权限、0 字节或无法打开，按 SKILL.md「异常处理与降级」说明原因并暂停后续阶段，不得进入审查。

**文件格式识别：**
- 用户上传文件 → 从文件扩展名识别格式
- 用户提供文件路径 → 从路径扩展名识别格式

| 扩展名 | file_format 值 | 后续影响 |
|-------|---------------|---------|
| .docx | .docx | 支持模式 A（嵌入式批注） |
| .doc | .doc | 仅支持模式 B（独立批注文档） |
| .pdf | .pdf | 仅支持模式 B |
| 其他 | 其他 | 仅支持模式 B |

### 合同正文提取（关键：为阶段四逐字比对做准备）

审查全程依赖**完整、顺序正确**的合同正文。不同格式按以下优先级提取，**不得**在无正文的情况下硬闯审查：

| 格式 | 推荐提取方式（按优先级） | 备注 |
|------|------------------------|------|
| .docx | 命令行 `python-docx` 读取段落文本；或模式 A 脚本内部处理 | 禁止用 Read/cat 直接读二进制 docx 填入 JSON |
| .pdf（文本层） | ① 合合文件解析 MCP（`parse_pdf_to_markdown`，保留表格结构）；② `pymupdf`(fitz) `page.get_text()`；③ `pdftotext`（若已安装） | **环境常缺 poppler/pdftotext**，Read 工具读 PDF 会报错，须优先走 MCP 或 pymupdf |
| .pdf（扫描件/图片） | 合合文件解析 MCP（内置 OCR）；或其他 OCR 能力 | OCR 结果须人工校对，扫描件半页噪声常见 |
| .doc | 提示用户转存为 .docx 或 PDF 后重传 | 无内置 .doc 解析能力 |

> **⚠️ 多栏/多列 PDF 错序告警：** 相寓租赁合同这类**多栏排版** PDF，按坐标线性提取会把不同栏的条款文字交错拼接（如"第一条"内容混入"第四/五条"），直接破坏阶段四"逐字复制关键字定位原文"的字符串匹配。发现正文条款编号与内容明显错位时，**必须**：① 优先改用合合文件解析（按阅读顺序还原）；② 或按条款编号重新人工梳理正文顺序后再进入阶段四；③ 无法还原时在交付物中披露"原文提取顺序可能存在偏差，批注定位以条款编号为准"。

## 步骤 2：智能推测审查配置

根据合同内容或上下文，推测以下四项配置，给出推测选项让用户确认（不要抛出空白问题）：

### 配置项推测规则

| 配置项 | 推测依据 | 默认值 |
|-------|---------|-------|
| 我方立场 | 合同中是否有明确标识（如"甲方：XX公司"与用户所属公司匹配） | 合同中明确标注的一方，或询问用户 |
| 市场地位 | 合同条款是否明显偏向某一方 | 平等 |
| 审核深度 | 合同金额、复杂度、用户上下文 | 标准 |
| 查询相对方企业背景 | 相对方名称是否为有效企业名称 | 是（若相对方名称为占位符或自然人则为否） |

### 市场地位判定表

| 判定条件 | 推测值 |
|---------|-------|
| 我方义务明显多于权利，违约责任明显更重 | 相对弱势 |
| 我方权利明显多于义务，违约责任明显更轻 | 相对强势 |
| 权利义务基本对等，违约责任基本平衡 | 平等 |

### 相对方名称有效性判定

| 相对方名称 | 是否有效企业名称 | 推荐值 |
|-----------|-----------------|-------|
| 具体公司名称（如"XX有限公司"） | ✅ 有效 | 是 |
| 占位符（如"XX公司"、"___"、"甲方"） | ❌ 无效 | 否 |
| 自然人姓名（如"张三"） | ❌ 无效 | 否 |

## 步骤 3：配置确认话术

使用以下话术模板向用户确认配置：

**话术模板：**

"我已经收到合同。基于初步浏览，我推测以下审查配置：

| 配置项 | 推测值 |
|-------|-------|
| 我方立场 | 【甲方/乙方/买方/卖方等】 |
| 市场地位 | 【平等/相对强势/相对弱势】 |
| 审核深度 | 【快速/标准/深度】（推荐：标准） |
| 查询相对方企业背景 | 【是/否】（相对方：【XX有限公司】） |

请确认以上设置是否符合您的要求？如有需要调整，请告知。"

**特殊说明（如适用）：**
- 若相对方名称为占位符："相对方名称为占位符（【XX】），暂无法进行企业背景查询，建议选择'否'。"
- 若相对方为自然人："相对方为自然人（【张三】），无法进行企业背景查询，建议选择'否'。"
- 标准审核说明："标准审核会覆盖核心法律/商业风险、首尾附件问题以及错别字、语句不通、金额日期冲突、条款引用错误等影响合同可用性的文本质量问题。"

---

## 步骤 4：必问特殊关注点

无论用户是否主动提供，**必须**在确认话术末尾附带询问：

"**另外，请问针对这份合同，您有什么特殊的关注点或自定义的审查要求吗？（如没有可回复"无"）**"

---

## 步骤 5：处理用户回复

### 情况一：用户确认推测配置

直接进入步骤 6，整理阶段一产物。

### 情况二：用户调整配置

记录用户调整后的配置，进入步骤 6。

### 情况三：用户提出特殊关注点

**先评估合理性：**

| 检查项 | 判定 | 处理 |
|-------|------|------|
| 是否违反法律强制性规定？ | 是 → 不合理 | 礼貌解释法律风险并建议修改 |
| 是否违背公序良俗？ | 是 → 不合理 | 礼貌解释并建议调整 |
| 是否为合理关注点？ | 是 → 合理 | 设为本次审查的最高优先级检查点 |

**不合理关注点的回复模板：**

"您提出的【关注点】涉及【法律风险说明】。根据【相关法律规定】，该要求可能存在法律风险，建议调整为【替代方案】。请问是否按调整后的要求继续审查？"

## 步骤 6：阶段关卡 + 产出

### 确认完成话术

根据是否执行相对方背景查询，使用不同的结束话术：

**用户选择查询相对方背景（`skip_counterparty_check: false`）：**

"好的，收到。我先对相对方企业做一个快速背景核查，随后开始正式审查，完成后将为您输出三份 Word 文档：**合同解读报告**（方便快速了解合同核心内容）、**审核意见书**（专业风险分析和修改建议）、**原文批注版**（逐条批注，可直接用于谈判修改），请稍候。"

**用户选择不查询（`skip_counterparty_check: true`）：**

"好的，开始审查，完成后将为您输出三份 Word 文档：**合同解读报告**（方便快速了解合同核心内容）、**审核意见书**（专业风险分析和修改建议）、**原文批注版**（逐条批注，可直接用于谈判修改），请稍候。"
