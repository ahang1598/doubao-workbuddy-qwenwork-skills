# 阶段五：生成交付物

> **你接收到的上游数据：** 阶段一产物 + 阶段二产物（可选，可能为 null）+ 阶段三产物 + 阶段四产物。
> **你需要产出的下游数据：** 一份对话框 Markdown（合同解读报告）+ 两份 Word 文件（审核意见书 + 原文批注版）。

**本阶段的输出形式：**
- **合同解读报告** → 直接以 Markdown 格式输出到对话框，不生成 Word 文件。
- **审核意见书** → 生成 Word 文件（工具见下方"Word 生成工具链与兜底"）。
- **原文批注版** → 生成 Word 文件（模式 A 用 `mode_a_annotator.py`；模式 B 见下方工具链）。

### Word 生成工具链与兜底（重要）

生成 `.docx`（审核意见书、模式 B 批注版）按以下优先级选择工具，**任一可用即可，绝不能因工具缺失而不产出 Word 文件**：

| 优先级 | 工具 | 适用与说明 |
|-------|------|-----------|
| ① | `docx` skill（`Skill(skill:"docx")`） | 若该技能已安装则优先使用，样式最完整 |
| ② | **`python-docx`（兜底，环境常已预装）** | 当 `docx` skill 不存在/加载失败时，直接用命令行 `python` + `python-docx` 按模板生成 `.docx` |
| ③ | 其他可用的 Markdown→docx 能力（pandoc 等，若已安装） | 前两者均不可用时 |

> **⚠️ 关键：`docx` skill 在很多环境中并未安装（`~/.qoderwork/skills/docx` 不存在），调用会失败。** 此时**不得**中止、不得只输出 Markdown，必须改用 `python-docx` 兜底生成真实 `.docx` 文件。python-docx 生成要点：`Document()` 建文档 → 中文正文字体设 `宋体/Songti SC`（同时设 `w:eastAsia`）→ 标题用 `add_heading` 或 `RunProperties` 加粗着色 → 风险等级标签用 `RGBColor` 着色（致命/重要=红、一般=橙、轻微=灰）→ 表格用 `add_table(style='Table Grid')` → `doc.save(输出路径)`。生成后**必须**校验文件存在且大小 > 0。

### 模式 A：修订标记 + 批注（ZIP + XML 方案）

> **⚠️ 硬性约束：禁止阅读 `mode_a_annotator.py` 源码！**
> 该脚本是黑盒工具，你只需要：复制到工作目录 → 准备 JSON 输入文件 → 通过命令行调用。
> **绝对不要**用 Read/Cat 等方式查看脚本内容，这会浪费大量执行轮次。

> **技术说明：** 脚本通过 Python 标准库（zipfile + xml.etree.ElementTree）直接操作 .docx 的 XML 内容，
> 在同一次 ZIP 读写中原子化完成所有修改，无外部依赖。

使用 `templates/mode_a_annotator.py` 脚本执行。步骤：

1. **复制脚本到工作目录**：
   ```bash
   cp <技能目录>/templates/mode_a_annotator.py ./mode_a_annotator.py
   cp <技能目录>/templates/mode_a_verifier.py  ./mode_a_verifier.py
   ```
   （技能目录即本文件所在目录的上级，在 QoderWork 中通常为 `~/.qoderwork/skills/lawding-contract-review-pro/`）
2. 将阶段四产物中的 `findings` 和 `missing_clauses` 整理为 JSON 输入文件（格式见下方），保存为 `mode_a_input.json`。
   > **⚠️ 注意：** `mode_a_input.json` 是脚本执行的技术中间件，**不是最终交付物**。它仅在步骤 3-5 的脚本调用过程中使用，执行完成后应清理。
3. **命令行预检**：`python mode_a_annotator.py --precheck mode_a_input.json`
   - 退出码 0 = 匹配率 ≥ 80%，可以执行
   - 退出码 1 = 匹配率 < 80%，需修正关键字后重试
4. **命令行执行**：`python mode_a_annotator.py mode_a_input.json`
5. **二次校验（v4.0.0 新增）**：执行完毕后，立即运行校验脚本：
   ```bash
   python mode_a_verifier.py mode_a_input.json [合同名称]_原文批注版.docx
   ```
   - 退出码 0 = 全部通过，可继续交付
   - 退出码 1 = 存在缺失，查看报告中的"缺失详情"，修正 `mode_a_input.json` 后重新执行步骤 4-5（最多重试 1 轮）
   - 重试 1 轮后仍不通过 → 按降级规则切换模式 B，并向用户说明具体缺失了哪些批注/修订

> **⚠️ 关键字准确性约束：**
>
> 脚本通过字符串匹配在原文 XML 中定位段落。AI 在阶段四审核时倾向于"复述"合同内容而非"复制"，
> 导致关键字与原文不一致。脚本已内置三轮容错匹配（精确 → 去空格 → 去标点归一化），
> 但关键字本身严重偏离原文时，任何容错都无法挽救。
>
> **核心原则：短、准、单**
>
> 1. **短片段优先（10-20字）**：复制原文中**连续 10-20 个字**的片段，不要复制整句。
> 2. **单段落匹配（严禁跨段落）**：每条 `old_text` 只包含**单个段落**的内容，严禁包含换行符 `\n`。
> 3. **条款编号最可靠**：优先使用条款编号 + 前几个字，如 `"9.1由乙方原因"`。
>
> **操作方法：** 整理每条 finding 时，必须回到合同原文中定位对应段落，从中复制，而非凭审查时的记忆填写。

**预检与重试：**

```bash
# 步骤 3：预检（匹配率 >= 80% 才执行）
python mode_a_annotator.py --precheck mode_a_input.json
# 退出码 0 → 执行；退出码 1 → 修正关键字后重试，最多 2 轮

# 步骤 4：执行
python mode_a_annotator.py mode_a_input.json

# 步骤 5：二次校验（v4.0.0 新增）
python mode_a_verifier.py mode_a_input.json [合同名称]_原文批注版.docx
# 退出码 0 → 通过，继续交付
# 退出码 1 → 查看报告，修正后重试步骤 4-5（最多 1 轮），仍失败则降级模式 B
```

> **⚠️ 模式 A 降级为模式 B 的触发条件（任一满足即降级）：**
> 1. 预检匹配率 < 80%，修正 2 轮后仍不达标
> 2. 脚本执行报错（退出码非 0，且非预检失败）
> 3. 脚本执行成功但输出文件无法打开或内容为空
> 4. **二次校验未通过，修正重试 1 轮后仍存在批注或修订缺失（v4.0.0 新增）**
>
> 降级时无需排查错误原因，直接切换模式 B 并告知用户："原文嵌入批注遇到技术限制，已切换为独立批注文档模式，审查内容完全一致。"若二次校验报告中有具体缺失条目，可附带说明缺失项目。

**JSON 输入格式：**

```json
{
  "source_file": "合同文件路径（仅 .docx）",
  "output_file": "[合同名称]_原文批注版.docx",
  "author": "AI法律顾问",
  "tracked_changes": [
    {
      "old_text": "日0.5%",
      "new_text": "日万分之五",
      "comment": "【重要风险】违约金费率过高...\n【理由】依据《民法典》第585条..."
    }
  ],
  "comments_only": [
    {
      "keyword": "付款方式",
      "author_label": "重要风险",
      "comment": "【问题】付款时间起算不明确...\n【建议】建议修改为..."
    }
  ],
  "insert_paragraphs": [
    {
      "anchor_keyword": "第十四条",
      "new_text": "第十五条 不可抗力\n一、本合同所称不可抗力...",
      "comment": "【缺失条款】合同缺少不可抗力条款...\n【理由】依据《民法典》第590条..."
    }
  ]
}
```

**模式 A 规则：**

1. **三层策略**：`tc` → Tracked Change + Comment；`comment_only` → 仅 Comment；`tc_insert` → 插入新段落 + Comment。
2. **批注作者**：按风险等级设为 `致命风险`、`重要风险`、`一般风险`、`缺失条款`，便于在 Word 中按作者筛选。
3. **缺失条款双重标注**：在最后一个实质条款段落添加汇总 Comment + 逐条插入建议条款。
4. **链式插入**：多条缺失条款依次插入，每条以前一条的关键字作为锚点。
5. **文件另存**：输出文件不覆盖用户原文件。

## 调用顺序

> **原则：先难后易，快速失败。** 原文批注版技术复杂度最高（文本匹配 + XML 批注/修订），放在最前可以尽早暴露匹配失败等问题，避免前两份文档生成成功后第三份才报错。

1. **合同解读报告** → 在对话框中直接输出 Markdown（用户可即时阅读）
2. **原文批注版**（最先生成 Word）→
   - **模式 A**：先 `python mode_a_annotator.py --precheck input.json`，匹配率 ≥ 80% 后 `python mode_a_annotator.py input.json`，执行完毕后立即运行 `python mode_a_verifier.py input.json [合同名称]_原文批注版.docx` 进行二次校验。若校验未通过，修正后重试步骤（最多 1 轮），仍失败则降级为模式 B。**禁止阅读脚本源码。**
   - **模式 B**：按"Word 生成工具链与兜底"生成（优先 `docx` skill，不可用时 `python-docx`）
3. **审核意见书** → 按"Word 生成工具链与兜底"生成（优先 `docx` skill，不可用时 `python-docx`）
4. **最终交付校验** → 检查两份 Word 文件是否存在且非空；不通过则返回补救，禁止宣布完成
5. **清理临时文件**（可选但推荐）→ 删除工作目录中的 `mode_a_input.json`、`mode_a_annotator.py`、`mode_a_verifier.py`，避免干扰用户对交付物的识别

> **⚠️ 工具分工（硬性约束）：**
> - **创建新文档**（审核意见书、模式 B 批注版）→ 优先调用 `docx` skill；若其未安装/失败，用 `python-docx` 兜底生成，**严禁**因此跳过 Word 交付。
