# 材料评估与卡片采集协议（AskUserQuestion 原生 · v4 整合版）

本文件只在阶段 0–2 读取一次。采集主通道唯一：`AskUserQuestion` 选项/填空卡片组。
禁止逐轮对话提问、禁止展示型 Widget 冒充表单、禁止让用户下载或复制 JSON。
凡需要文字填写的选项一律标注"请在「其他」中填写，本项勿选"（平台的"其他"项固定追加在末尾、不可自定义，填写指引写入题干）。

全程表述要求：短句、尊重、有人情味；说"现在需要做什么"，不催问、不责备。

## 1. 先评估，再发卡

读取用户指令和全部上传材料后，对以下主题逐项标记 `sufficient / partial / missing / not_applicable`，形成 `coverage_assessment.topics`：

`audience_type`、`actor_authority`、`testator_basic_info`、`testator_capacity_and_intent`、`heirs_and_relationships`、`assets`、`real_estate_details`、`real_estate_distribution`、`liabilities`、`existing_arrangements`、`distribution_goals`、`executor_and_custody`、`will_form_and_witnesses`、`special_factors`、`deliverable_selection`、`final_confirmation`。

- `sufficient` 必须有可追溯的材料原文或明确指令支持；OCR 猜测、模型推断不得标 `sufficient`。
- **用户提示词与上传材料同等构成覆盖依据**：提示词中已明确陈述的事实（人物、财产、分配、形式等）将对应主题标 `sufficient`/`partial` 并预填，不得再经卡片重复询问；简易、完整、律师三种模式一律适用。
- `sufficient` / `not_applicable` 跳过对应卡片，但仍进入汇总核对；`partial` 只补未确认字段；`missing` 完整发卡。

评估后用简短友善的一句话反馈识别结果，随即发出采集方式选择卡（话术见 `assets/cards/opening-messages.json`，话术中含数据用途一句话告知）。四种去向：简易模式（`fast`，推荐）、完整模式（`complete`）、律师专业通道（`lawyer_sheet`，仅律师/法律工作者）、我先上传材料（收到后重新评估并再次发出选择卡）。

## 2. 简易模式（fast）——前两轮内联直发（提速关键）

**首组延迟治理**：前两轮按下述内联规格直接发出——不读取卡组 JSON、不运行编译脚本、不先写 `work-data.json`（回答收回后再写）。卡组与脚本只在定向补采时才加载。

### 第 1 轮（≤4 题）

办理人为**遗嘱人本人**时：① 办理人（选项：遗嘱人本人 / 经授权代办）② 理解与表达（"您目前是否能清楚理解本次安排的含义，并顺畅表达自己的想法？"选项：能，理解和表达都很清楚 / 有些吃力，需要辅助 / 存在明显困难或疑点 / 不确定）③ 真实自愿（"接下来的各项安排是否都出自您真实、自愿的意愿，没有受到干扰或压力？"选项：是，完全自愿 / 存在干扰或压力的疑虑 / 不确定）④ 人员清单填空。

办理人为**经授权代办**时：① 办理人 ② 人员清单填空 ③ 财产清单填空 ④ 遗嘱形式（分支题收尾）。

### 第 2 轮（≤4 题）

本人场景：① 财产清单填空 ② 遗嘱形式（分支题收尾）③ 分配意向清单填空 ④ 假设修正多选。
代办场景：① 分配意向清单填空 ② 假设修正多选 ③ 理解与表达（转述口吻"据您观察，遗嘱人是否……"）④ 真实自愿（转述口吻）。

### 三道枚举填空题规格（选项均为：请在「其他」中直接填写，本项勿选 / 暂未整理好，先以占位符生成框架稿）

- **人员清单**：请一次列出遗嘱人和重要关系人。填写格式：姓名（身份证号码，与立遗嘱的人的关系），换行或逗号分隔均可；号码暂不方便提供的可留空后补（留空时性别、出生日期留待后补，是否法定继承人由关系推导）。示例：王五（3301\*\*\*\*\*\*\*\*0012，本人）、张小明（3302\*\*\*\*\*\*\*\*0034，儿子）。
- **财产清单**：请一次列出需要处分的财产。填写格式：财产描述（权属情况），权属可省略。示例：浙江省杭州市西湖区XX路88号房产（单独所有）、XX银行XXXXXXXX账户内存款X万元（不确定）、XXX公司30%股权、XXXX游戏账号（ID：XXXX）（单独所有）。
- **分配意向清单**：请逐项写明每项财产由谁继承及份额。格式：财产 → 继承人［份额］。示例：西湖区房产 → 张小明单独继承；存款 → 张小明50%、张小红50%。替补安排可写备注。

### 第 3 轮起：签署要点 + 定向补采

按所选遗嘱形式发单张签署要点告知卡（我知道了 / 不太清楚 / 不确定能否做到）；仅补真正缺失的签署版必需字段（已确认信息不再发卡；遗嘱人基本信息含住址同组发出）。

### 收尾：统一确认

不设单独的人员确认、财产清单确认、财产分配确认卡。枚举解析结果（标记 `system_inference`）与全部卡片回答一起在 §7 汇总核对中一次性呈现、一次性确认；确认后解析结果升级为 `confirmed` 写入工作数据。

## 3. 完整模式（complete）——五类卡组

**首组内联直发（提速关键，与 §2 对称）**：收到模式选择答案后，不读卡组 JSON、不运行脚本、不先写 `work-data.json`，按下列内联规格直接发出第一组（与编译队列顺序一致，模型不得改题）：① 办理人（遗嘱人本人 / 经授权代办）② 立遗嘱的人姓名（请在「其他」中填写，本项勿选）③ 立遗嘱的人身份证号码（请在「其他」中填写，本项勿选；性别与出生日期自动推导，无需另填）④ 立遗嘱的人常住地址（请在「其他」中填写，本项勿选）。用户类型不再询问：律师专业通道→lawyer，简易/完整模式→general_public。

首组回答收回后的同一轮内：一次性读取卡组 + 运行一次 compile/reconcile + 写一次 `work-data.json`；第二组起按 `card_categories` 五类顺序从卡组发出，同类卡片尽量合并轮次（每组 ≤4 题）。多次脚本调用须用 `&&` 串联在单次 Bash 调用中完成，不得拆成多个往返。**通过回答可以得出结论的，不再单独提问**（推导规则见卡组 `removed_cards_v4.merger_note` 与运行时 `_derive_inheritance_review`）。

| 类别 | 卡片 | 要点 |
|---|---|---|
| 人员确认类 | `testator-basic-info`、`testator-capacity`、`family-map`（计数题问"分配给几位重要关系人"；每页含法定继承人认定说明；填完后尾题排查其他法定继承人/必留份/胎儿份额/丧失继承权）、`guardianship-special` | 基本信息含住址同组；能力卡按本人/转述口吻分流 |
| 财产确认类 | `asset-declaration`（先多选类型：存款或其他理财/房产/数字资产，股权、股票、保险、债权等经「其他」申报；逐项只填关键识别信息、权属、抵押，类型不再重复选择，由描述自动推导）、`liability-scope` | 共有与抵押为组内单独确认的易遗漏项 |
| 遗产分配类 | `existing-arrangements`、`distribution-goals`、`estate-distribution`（逐项：受益人/方式/附义务条件/替补） | 遗赠接受期限风险由系统在汇总时自动标记，不单独提问 |
| 遗嘱形式与订立类 | `will-form-and-witnesses`（形式 + 签署要点告知 + 见证/代书人一题） | 签署要件单卡告知，不逐项确认 |
| 遗嘱执行类 | `executor-custody`（执行人/意愿/保管/宣读通知）、`deliverable-selection` | 执行人意愿并入执行卡 |

律师用户（`audience=lawyer`）使用完整模式时保留法条号与专业术语表述；普通用户短句通俗，内容不缩水。

## 4. 律师专业通道（lawyer_sheet）

仅律师可选。流程：

1. `lawyer-privacy-consent` 隐私确认卡（首卡，两项同时勾选方可继续）；
2. 提取用户提示词与材料中已有事实生成预填 JSON，替换 `assets/templates/lawyer-intake-form.html` 中的 `__PREFILL_JSON__`，生成本次预填表单（写入输出目录）并用 `qwenwork_file_present_files` 呈现；同轮对话告知操作：打开表单 → 填写或补充 → 点击「保存」（浏览器下载已填写文件）→ 回到对话回复；
3. 发出操作确认卡（已保存请 retrieval / 遇到问题 / 切换完整模式）；用户确认已保存后，自动在下载目录（`~/Downloads`）读取最新的 `lawyer-intake-filled-*.html`，提取其中 `intake-data` 嵌入 JSON 写入工作数据（标记 `system_inference`）；
4. 缺失项定向补采（已有信息不再询问）；
5. §7 汇总核对。未经核对确认不得写入工作数据、不得生成草案。

找不到保存文件时说明原因，请律师直接将下载的文件作为附件发送（已披露的通道例外）。文本信息表 `lawyer-intake-sheet.md` 保留为无浏览器场景的降级路径。

## 5. 卡片发出规则

每次 `AskUserQuestion` 调用 1–4 题：

1. 贪心合组；可重复卡的每一"页"单独成组。
2. 分支题之后不得在同组追加依赖其答案的问题；互相独立的分支题可同组。
3. 填空选项生成：材料已有值 → `["确认使用：{value}", "需要更正，请在「其他」中填写，本项勿选"]`；无值 → `["请在「其他」中填写，本项勿选", "暂不填写，先以占位符生成框架稿"]`；敏感字段掩码显示。
4. 用户误选"本项勿选"选项且未提供文本时视为未作答，当场请其通过"其他"重填，不跳题。
5. 占位符路径：值记 `null`、`answer_status = "later"`，框架稿保留 `{{占位符}}` 并标注"非正式签署版"；签署版生成前必须补齐。
6. 每组发出前用一行说明进度，不复述已答内容。
7. 每题最多 4 个选项；受益人选项取已采集关系人姓名前 4 位，其余靠"其他"补充。
8. `work-data.json` 每阶段写入一次（简易模式：前两轮回答收回后首次写入），不在每组后写盘。
9. 原始回答与规范化中间件保留不删（轨迹价值），禁用 `rm`；需整理时 `mv` 入 `processed/`。

## 6. 回答映射与记录

阶段末写入 `intake_session.card_responses`：`card_id` / `base_card_id` / `selected_values` / `field_values` / `free_text`（备注或清单原文）/ `answer_status` / `answered_at` / `confirmed`。填空字段卡必须产出 `field_values`，禁止聊天文本替代；枚举卡原文记 `free_text`，解析结果经汇总核对确认后才写入分区。性别与出生日期一律由身份证号推导（`derive_from_id_number`），用户修改身份证号时联动更新，统一在汇总核对确认；是否法定继承人在完整模式逐人确认、快速模式按关系推导；财产类型由描述文字推导（`_asset_type`），填写后不再重复选择。用户类型由模式选择派生，`audience_profile.selected_via_card_id = "mode-selection"`。

## 7. 汇总核对（阶段 2 · 全程唯一一次）

`intake-confirmation`：正文分组呈现全部信息（遗嘱人、关系人、财产与分配含解析来源标注、债务与既有安排、形式与签署确认状态、成果选择、未知项与待补清单、系统自动标记项如遗赠接受期限风险），敏感值掩码。选项："确认无误，继续 / 需要修改（请在备注中说明）"。

- 确认 → 解析结果升级为 `confirmed` 写入分区；`intake_session.status = "confirmed"`，进入阶段 3。
- 需要修改 → 仅重发受影响卡片；更正答案即最终确认，不再二次汇总。

## 8. 用户类型与语气

`lawyer`：术语、法条号、规则编号全保留。`general_public`：短句通俗，采集、检查、风险披露一项不减。语气底线：称呼用"您"；每轮先承接再提问；"不确定/暂不填写"回应以路径而非质疑；敏感主题中立克制。
