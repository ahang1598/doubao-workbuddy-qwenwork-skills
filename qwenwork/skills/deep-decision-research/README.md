# Deep Decision Research Skill 使用指南

本文档面向集成、测试和维护人员。运行时约束以 `SKILL.md` 为准。

## 一句话说明

`deep-decision-research` 当前是一个“QoderWork 决策研究 + 本地 HTML 决策报告生成”skill。它会先按任务复杂度选择 `light` / `standard` / `deep` 深度，再决定是否搜索、报告长度和自检强度。

```text
用户提出复杂决策问题
-> QoderWork 确认报告目标
-> QoderWork 按深度整理材料，必要时搜索
-> QoderWork 提炼候选方案、证据、风险、假设和行动建议
-> QoderWork 读取内置 HTML 报告规范
-> QoderWork 一次性写出完整 HTML 文件，优先保证文件完整可打开
-> QoderWork 把 HTML 文件路径和简要结论交给用户
```

本版本不依赖外部后端服务、远程异步任务或对象存储。研究由 QoderWork 自己完成，最后报告严格按照内置 spec 输出，核心目标是保证报告格式正确、可打开、可汇报。

## 适用场景

适合：

- 方案推荐 / 选型建议。
- 可行性分析 / 风险评估。
- 行程 / 项目 / 排期规划。
- 多方案对比决策。
- 用户明确要求“出一份报告”或“完整分析”。

不适合：

- 简单事实问答。
- 一句话建议。
- 不需要报告文件的任务。

## 上架页面推荐文案

如果需要填写 QoderWork 技能上架页的默认提示词、示例提示词和使用说明，建议使用下面这组文案。它会明确告诉用户：本技能支持轻量、标准、深度三种使用方式，用户可以通过“深度研究 / 全面调研 / 竞品研究 / 行业研究”等表达主动触发 deep 模式。

默认提示词：

```text
请帮我围绕下面这个决策问题进行材料整理、结构化分析，并生成一份可在浏览器打开的 HTML 决策辅助报告。你可以根据问题复杂度选择轻量、标准或深度研究模式；如果我明确要求“深度研究、全面调研、竞品研究、行业研究”，请使用深度模式。
```

提示词 1：

```text
帮我比较几个方案的优劣、风险、适用条件和推荐选择，并生成 HTML 决策报告。如果只是小决策，请用轻量模式；如果我要求深度研究，请主动扩展证据和分析维度。
```

提示词 2：

```text
帮我对一个项目或业务想法做可行性分析，包括机会、风险、成本、执行路径和下一步行动，并输出 HTML 决策辅助报告。
```

提示词 3：

```text
请使用深度研究模式，围绕一个复杂决策问题做资料搜索、行业/竞品/风险分析和结构化研究，输出包含结论、证据、对比、风险、假设和行动建议的 HTML 报告。
```

使用说明：

```text
输入一个需要辅助判断的决策问题，也可以补充已有材料、候选方案、约束条件、目标用户、预算、时间、风险偏好或输出用途。技能会先判断任务深度：轻量模式适合快速判断，标准模式适合常规方案对比，深度模式适合行业研究、竞品研究或复杂高风险决策。若你希望主动触发深度模式，请明确写“深度研究、全面调研、竞品研究、行业研究、尽可能完整”。技能会整理证据、假设、风险和信息缺口，并生成本地 HTML 决策辅助报告。
```

你会得到什么：

```text
你会得到一份结构化 HTML 决策辅助报告，通常包含决策摘要、推荐方案、方案对比、关键证据、风险登记、假设清单、信息缺口和下一步行动。轻量模式会优先稳定、简洁、可读；深度模式会保留更完整的搜索研究、证据链和 7 模块报告结构。
```

输入要求：

```text
请尽量提供：1. 决策目标或问题；2. 候选方案；3. 已有材料或背景；4. 约束条件，例如预算、时间、资源、地域、合规、安全或风险偏好；5. 期望输出用途。若信息不足，技能会基于当前输入和可获得资料生成报告，并明确标注置信度和信息缺口。
```

输出形式：

```text
HTML 报告文件 + 简要结论摘要。HTML 报告可直接在浏览器打开查看；最终回复会给出本地文件路径。
```

## 记忆策略

本 skill 以无记忆模式运行。运行时只使用当前用户请求、用户明确提供的输入、本轮检查过的文件和稳定通用知识；不调用记忆工具，不读取或更新 `USER.md`、`AGENTS.md`、`SOUL.md`、`MEMORY.md`、`memory/*.md`，也不把本次执行信息写入记忆。

## 固定流程

```text
节点 A：确认目标
  -> 最多追问 2 个问题，整理报告目标

节点 B：准备材料
  -> 制定研究计划
  -> 选择 light / standard / deep 深度
  -> 按深度搜索或整理用户提供材料
  -> 抽取结构化证据、KPI、候选方案、风险、假设、行动和信息缺口
  -> 验收研究材料包

节点 C：生成 HTML 报告
  -> 读取 ~/.qwenworkcn/skills/deep-decision-research/references/decision-report-prompt-spec.md
  -> 提炼对应深度的内部合规清单
  -> 一次性写入完整 HTML 文件
  -> light 只做结构检查；standard/deep 必要时做一次修正

节点 D：交付结果
  -> 给用户 HTML 文件路径、核心建议、关键依据、风险缺口、下一步
```

## 报告规范

唯一规范文件：

```text
~/.qwenworkcn/skills/deep-decision-research/references/decision-report-prompt-spec.md
```

该规范要求：

- 输出完整自包含 HTML 文件。
- 生成 HTML 前必须先完成研究材料包。
- CSS 在 `<head>` 的单一 `<style>` 块中。
- 文件一次性写入，避免分段 append。
- spec 是执行合同，不是参考样式。
- 生成前必须形成对应深度的内部合规清单，生成后必须自检。
- light 模式允许简洁报告；standard/deep 模式不能交付薄报告。
- 报告必须具备信息层次：结论/判断 -> 证据/数据 -> 决策含义 -> 行动/边界。
- standard/deep 禁止薄报告：不能只有标题、少量卡片、简单表格和泛泛建议。
- 必须遵守渐进式披露：首屏只放结论、关键 KPI、最高风险和立即行动；细节后置。
- light 模式必选内容：
  1. 决策摘要 / 推荐结论
  2. 方案对比或判断理由
  3. 主要风险 / 信息缺口
  4. 下一步行动
  5. 谨慎性声明
- standard/deep 模式必须包含 7 个模块：
  1. 决策摘要
  2. 推荐方案
  3. 多维对比矩阵
  4. 证据支撑
  5. 风险登记册
  6. 假设清单
  7. 行动建议

light 视觉交付下限：

- 自包含 HTML，包含 `<!DOCTYPE html>`、`<style>` 和闭合 `</html>`。
- 有清晰标题、结论区、对比区、风险/缺口区和行动区。
- 可以使用简单卡片、表格和列表；重点是完整、稳定、可读。
- HTML 建议 120-260 行；超过 350 行应压缩。

standard/deep 视觉交付下限：

- 深色 hero/header，包含标题、副标题和 4 个 KPI 横条。
- 每个模块有带编号徽标的 section 视觉标题。
- 主体采用卡片化结构，并体现 header/body 层级。
- 对比矩阵高亮首选方案列，用绿/橙/红表达好/中/差。
- 风险项左侧有红/橙/绿竖条。
- Badge 按语义上色。
- 证据、风险、假设、行动数量满足 `decision-report-prompt-spec.md` 的下限。

light 信息密度下限：

- 2-3 个 KPI 或判断指标。
- 2-3 个候选方案或可行动选项。
- 2-4 条证据、依据或用户材料摘录。
- 2-4 条风险/信息缺口。
- 2-4 条关键假设。
- 3-5 条下一步行动。

standard/deep 信息密度下限：

- Header 需要 4 个 KPI，每个 KPI 有指标名、数值和解释短句。
- 证据优先 6-10 条，至少 4 条；每条必须有来源、类型和决策含义。
- 风险优先 4-6 条，至少 3 条；每条必须有发生机制、影响维度和应对动作。
- 假设 3-6 条；每条必须说明如果不成立会怎样。
- 行动建议 3-5 条；每条必须有时间节点和验收指标。
- 重要信息缺口必须说明缺什么、为什么影响结论、如何补齐。

研究材料包下限：

- light 先把用户目标拆成 2-4 个信息问题；standard 3-5 个；deep 4-8 个。
- light 默认不搜索；standard 0-3 次搜索/工具查询；deep 4-8 次搜索/工具查询。
- 用户明确说“不要搜索 / 基于给定材料 / 不要太 deep”时，必须优先选择 light，禁止为了凑证据数量而搜索。
- 无法搜索或无需搜索时，整理用户材料并降低置信度。
- 每条证据必须包含来源、时间、类型、具体事实/数字、支撑的判断、决策含义、置信度和限制。
- KPI、候选方案、证据、风险、假设、行动必须先在材料包里成型，再进入 HTML 生成。
- 无法验证的数据不得标为已验证；拿不到的数据写入信息缺口。

## 产物稳定性规则

- 完整性优先于视觉精致度，视觉精致度优先于信息密度。
- 一次性写入最终 HTML，不使用 append 拼接长文件。
- 禁止先写半成品再删除重写的循环。
- HTML 已包含 `<!DOCTYPE html>`、`<style>` 和 `</html>` 后，不再继续清理、删除、重写或二次生成。
- light 模式结构检查通过后立即交付，不继续优化视觉。
- 如果临时脚本已生成完整 HTML，不为了清理脚本而冒险破坏最终交付。

渐进式披露下限：

- 首屏不展示完整证据、完整风险或完整行动清单。
- 每个模块开头先给 1 句 takeaway。
- 重要信息先出现，补充细节后置。
- 长内容拆成卡片、表格、标签、短段落或 HTML 原生 `<details>`。
- 禁止连续大段文字信息墙。

## 数据 Map

| 材料类型 | 写入方式 |
| --- | --- |
| 公开搜索、新闻、网页、公开报告 | 标记为 `L1_public_search` |
| 购买、合作、授权、API、导出的第三方数据 | 标记为 `L2_third_party` |
| 用户上传、截图、后台导出、对话补充、浏览器插件采集 | 标记为 `L3_user_owned` |
| 当前拿不到的数据 | 写入 `known_gap` |
