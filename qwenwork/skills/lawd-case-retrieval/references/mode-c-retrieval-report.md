# 模式C：正式类案检索报告（完整工作流）

> 本文件为 SKILL.md「三、模式工作流」3.3 模式C 的完整工作流细则（自 SKILL.md 外移），执行模式C 时必须完整读取并严格遵循。

### 3.3 模式C：正式类案检索报告

将经过核验的案例数据编排为专业类案检索报告，并强制生成、验证实际 `.docx` 文件。

#### 模式C 不可违反的规则

1. 只使用用户材料、本会话模式A 检索结果或可靠检索连接器返回的数据。
2. 不补造案号、法院、日期、审判人员、裁判理由、案例全文或来源。
3. 法院名称只使用来源数据中的正式名称；缺失时写"检索结果未提供"，不得拼接推断。
4. 仅校验并执行用户明确提出的时间、地域、法院层级、数量等约束。
5. 用户未提出时间或地域限制时，不增加"近三年""近五年"或任何默认过滤。
6. 分析结论必须注明基于本次样本，不得把有限案例表述为全部司法实践。
7. 用户要求报告时，只有 `.docx` 已生成且通过校验，才可宣告任务完成。
8. Markdown 只能用于大纲预览或失败诊断，不能替代 Word 最终交付物。

#### 模式C 数据来源原则

- **已有可核验案例材料（含本会话模式A 的交接产物）**：直接整理数据并生成报告，**不重复检索**。
- **没有案例材料**：先执行**模式A**取数（含模式A 的连接器三段式探测与全部门禁），再进入模式C。
- **检索连接器不可用且没有案例数据**：向用户说明需要安装案例检索连接器或提供案例数据；不得硬跑，不得生成虚构报告。
- **本技能自带确定性 DOCX 生成器**（`scripts/generate_report_docx.py`），优先使用；当前环境另有更完善的 DOCX 能力时可用其排版，但最终仍须通过本 Skill 的数据与 DOCX 校验脚本。
- 钉钉/在线文档可额外生成协作副本，但**在线文档不等同于 `.docx`**，不得替代强制交付。

#### Step 1：确认输入与目标

识别：

- 待研究的法律问题；
- 现有案例数据及其来源；
- 用户明确指定的案例范围；
- 报告署名、检索平台、检索方法和制作日期；
- 是否需要附案例全文。

缺失信息只有在会实质影响检索、筛选或署名时才询问。普通元数据缺失可在报告中如实写"未提供"。

需要附**案例全文**且案例有案号时，可在本技能内切换**模式B** 逐案取回逐字全文；未取得的案例 `full_text` 留空，附件部分如实注明。

#### Step 2：确定案例集合

1. 单轮且案例范围明确：使用该集合。
2. 多轮检索且集合可能重叠：按 `case_id → case_no → raw_record_locator` 依次取首个非空字段作为身份键并去重。
3. 用户明确指定案例：只保留指定案例。
4. 用户明确指定时间或地域：按原始字段核验，不满足或无法核验的案例不得擅自纳入。
5. 用户未指定约束：保留所有已选且相关的案例，不自动限时、限地域或凑足固定数量。

多个候选集合会实质改变报告时，展示简短清单请用户选择；用户已明确"全选"或授权自主处理时直接继续。

#### Step 3：建立结构化输入

按 `references/report-case-input-contract.md` 创建 UTF-8 JSON。至少包含：

- `schema_version`；
- `report` 元数据；
- `retrieval_targets`；
- `conclusions`；
- `explicit_constraints`；
- `cases`。

案例数据来自模式A 的交接 JSON（`schemaVersion: case-retrieval-handoff/v1`）时，按 `report-case-input-contract.md` 的「上游类案检索交接对接」映射转换：以 `delivery` 集合确定纳入报告的案例，以 `full` 集合回读正文。

保持原始字段原意：

- 缺失值使用空字符串、空数组或 `null`；
- 不为缺失的 `case_id` 虚构业务标识；每个案例至少保留案号或原始记录定位作为身份键；
- 不用推断结果填充缺失字段；
- "本院认为"仅放来源数据中的原文摘录；
- 每个案例保留 `raw_record_locator` 或其他可追溯来源。

#### Step 4：校验案例数据

运行：

```bash
python3 "<本技能目录>/scripts/validate_report_cases.py" /absolute/path/report-data.json
```

校验失败时修正数据映射或向用户补充取证。不得通过删除用户约束、伪造字段或修改脚本规则来强行通过。

#### Step 5：编制大纲与结论

按五部分结构组织：

1. 检索说明；
2. 检索目标；
3. 检索结果；
4. 检索内容；
5. 附件。

大纲会实质影响报告范围时先确认；用户已明确范围或授权连续执行时，不设置机械确认点。

结论只概括当前案例集合能支持的内容，并使用"基于本次纳入的 N 个案例"等限定表达。

#### Step 6：生成 DOCX

优先使用本 Skill 的确定性生成器：

```bash
python3 "<本技能目录>/scripts/generate_report_docx.py" \
  /absolute/path/report-data.json \
  /absolute/path/类案检索报告.docx
```

生成器负责 A4 页面、中文字体、标题层级、行距、表格、分页和案例附件编排。不得把 Markdown 文件改扩展名冒充 Word。

如当前环境提供更完善的 DOCX 能力，可以用其生成或进一步排版，但仍须保持输入数据一致，并执行 Step 7。

#### Step 7：强制验证 DOCX

运行：

```bash
python3 "<本技能目录>/scripts/validate_report_docx.py" \
  /absolute/path/report-data.json \
  /absolute/path/类案检索报告.docx
```

验证器至少检查：

- 文件存在、非空且为可打开的 DOCX ZIP；
- 页面为 A4，标题样式固定为黑色；
- 五个关键章节齐全；
- 文档内案例集合与输入 JSON 一致；
- 案件名称、案号和法院等关键字段未丢失；
- 不含模板占位符。

验证失败即未交付完成。修复后重新生成并验证。

#### Step 8：交付

向用户提供实际 `.docx` 文件路径或附件，并简要说明：

- 纳入案例数量；
- 执行了哪些用户明确约束；
- 哪些来源信息缺失；
- DOCX 校验已通过。

如同时创建在线文档，可另附链接并说明其为协作副本，不是 `.docx` 替代品。

#### 模式C 案例内容规则

**基本信息**

- 案件名称、案号、法院、裁判日期逐字使用来源数据。
- 缺失字段统一显示"检索结果未提供"。
- 不纠正疑似错误案号，不把地域和法院层级拼成法院名称。

**基本案情与裁判要旨**

- 可压缩无关内容，但不能改变原始事实关系和裁判结论。
- 无充分材料时写"检索结果未提供"，不得依常识补全。

**裁判观点**

- `court_reasoning_quote` 仅存放来源中的"本院认为"原文摘录。
- 不得把模型概括伪装为法院原文。
- 若只有摘要，明确标注为"检索摘要"，不要标为原文。

**附件**

- 有案例全文（模式B 取得的逐字全文）时按正文顺序附后。
- 无全文时列出案号、来源链接或原始记录定位信息，并注明"本次检索数据未包含案例全文"。
- 不得声称已附全文而实际只有摘要。

#### 模式C 异常与降级

**检索为空**：说明未找到结果，建议调整关键词或用户明确约束。没有案例时不生成看似完整的正式报告。

**数据矛盾**：列明冲突字段和各自来源，请用户确认；确认前不得选择一个版本写入正式报告。

**Python 或 python-docx 不可用**：先尝试当前环境已有 DOCX 能力。仍无法生成或校验时：

1. 明确说明 DOCX 交付失败；
2. 保留结构化 JSON 和错误诊断；
3. 可提供 Markdown 预览或创建在线文档供校对；
4. 不得宣称正式报告已经完成。

**DOCX 与在线文档双重失败**：返回失败原因和可恢复的输入数据，等待环境恢复后重试。不要用纯文本替代完成状态。

#### 模式C 完成检查

- [ ] 案例数据可追溯，未补造缺失信息
- [ ] 只执行用户明确约束，无默认时间或地域过滤
- [ ] 案例集合与模式A 交付集一致（数量、案号、顺序），未重复检索
- [ ] 结构化 JSON 已通过 `validate_report_cases.py`
- [ ] 五部分报告完整
- [ ] 实际 `.docx` 已生成
- [ ] `.docx` 已通过 `validate_report_docx.py`
- [ ] 最终交付未用 Markdown 或在线文档冒充 DOCX
