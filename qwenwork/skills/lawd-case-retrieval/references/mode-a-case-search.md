# 模式A：类案检索（完整工作流）

> 本文件为 SKILL.md「三、模式工作流」3.1 模式A 的完整工作流细则（自 SKILL.md 外移），执行模式A 时必须完整读取并严格遵循。

### 3.1 模式A：类案检索

将用户问题转化为可执行的类案检索，保留原始数据，并只基于实际返回结果生成分析。

#### 模式A 核心原则

1. 先取得案例检索连接器实际调用返回的 JSON，再陈述任何案例事实、裁判趋势或法规使用情况。
2. 不编造、补全、修正或猜测案号、法院、日期、裁判理由和法律依据。
3. 案号有值时逐字引用 `caseDomain.caseNo`；为空、`null` 或缺失时统一显示 `案号：无`。
4. 用户明确要求优先于默认行为；未指定的时间、地域、法院、分类和文件格式不得自行添加。
5. 用户未指定数量时，只检索首页并展示首页返回的全部去重结果。
6. 用户指定数量 N 时，按相同 Query 翻页，最终最多交付 N 条；不足时如实说明实际数量。
7. 仅在用户指定分类时分类；无法可靠分类的案例单列"无法判断"，不得强行归类。
8. AI 洞察必须注明"基于当前检索样本"，不能把有限样本表述为全部司法实践。
9. 默认只在对话中展示，不自动生成 Markdown、Word 或其他文件。
10. 保留完整结果文件；只将裁剪后的交付集送入模型上下文，以减少 Token 消耗。

#### 模式A 前置判断

确认用户至少提供以下一项：

- 案情或争议事实；
- 法律问题或裁判观点；
- 案由、罪名、主体名称或检索关键词。

信息不足以形成 Query 时，只追问会实质影响检索的一至三个关键问题。不要要求用户先完成完整案件分析。

**扫描件材料处理优先级**：用户提供的起诉状/证据清单等为扫描件 PDF 时，先做文字提取；**提取结果极少（<50 字符）即为扫描件，用 pymupdf 渲染 2x 图片后 Read 视觉读取**。材料信息已足以形成 Query 时，可不强制逐页全读，但须在检索说明中标注实际读取覆盖率；材料理解直接影响 Query 质量时，应全页读取。

#### 第一步：提取用户约束

分别记录：

- `original_intent`：用户真正要解决的问题；
- `requested_count`：仅在用户明确指定数量时记录正整数；
- 时间、地域、法院、案例级别和分类方式：仅记录明确要求；
- `need_court_think`：用户是否要求法院观点、裁判理由、本院认为或认定标准；
- `output_request`：对话、Markdown、Word 或其他明确格式。

"近年典型案例""多找一些"等无法机械确定数量或范围的表达，不得擅自转换成固定数字；必要时简短确认。

#### 第二步：改写 Query

按照 Query 引用文件判断处理模式，不再按输入字数机械分流：

- 输入已是可检索的主体、案由、罪名或法律问题：`direct`；
- 只需删除指令词、口语和重复内容：`cleanup`；
- 长案情需要提炼争议事实或法律术语：`full`。

保留用户明确约束。案情中偶然出现的地点或年份，不等于用户要求按地域或时间过滤。

#### 第三步：执行检索

本技能需要「案例/裁判文书检索」能力：输入自然语言案情描述或结构化条件，返回真实案例列表（案号、法院、裁判日期、案由、裁判要旨等）。调用方式只写能力语义，不写死任何供应商工具名；按 [references/connector-search.md](connector-search.md) 完成三段式探测：

- **探测**：用 `qwenwork_mcp_tool_list` 依次检索关键词 `案例 / 判例 / case / ptal / qwal / pkulaw / fabao / yuandian / 裁判文书`，汇总候选连接器；
- **匹配**：按工具名或描述含案例语义检索、案例条件检索、权威案例（指导性/公报/典型）、案例详情等语义判定；不确定时用 `qwenwork_mcp_tool_get` 查看 schema，schema 不符的切换下一家；
- **调用**：用 `qwenwork_mcp_tool_call` 执行；多家可用时按能力匹配度选择，首选出错切下一家。

Query 改写结果与用户明确约束按 connector-search.md 的入参语义映射传入（案情描述、案由、法院、地域、日期范围、文书类型、返回条数）；具体参数名以连接器运行时 schema 为准。

**执行门禁（必须遵守）**：在向用户输出任何案号、案例名称、法院、裁判日期或裁判内容之前，必须在本次任务中实际调用案例检索连接器并取得通过 `scripts/process_case_results.py` 校验的结果 JSON。**未实际检索不得罗列判例，禁止虚构案号**，禁止凭记忆、常识或网页搜索补案例事实。全部连接器不可用时按 A 档拒绝降级：

> 停止执行，并告知用户："本技能需要「案例/裁判文书检索」连接器。请前往 设置 → 连接器，搜索「案例」或「法律检索」安装法律案例检索类连接器后重试。"

不硬跑，不用网页搜索或模型记忆编造案例与案号。

检索执行步骤：

1. 创建本次任务独立的临时目录，避免覆盖并发检索。
2. 用最终 Query 和用户明确约束请求第 1 页（单页不超过 10 条），将归一化后的分页 JSON 原样保存为 `page_1.json`；命令行输出场景可用 `scripts/save_stdout.py` 管道保存。
3. 用户未指定数量时停止翻页。
4. 用户指定 N 且去重后不足 N 时，保持 Query 和过滤条件不变，按连接器支持的分页或偏移语义依次请求下一页，最多 5 页。
5. 服务端已无更多结果或达到 5 页后停止，不得为凑数混入无关案例。

若用户指定数量超过当前 5 页上限，先完成最多 50 条检索并明确技术上限；不要声称已满足超过实际交付量的要求。

#### 第四步：确定性处理结果

对已保存的分页 JSON 运行：

```bash
python3 "<本技能目录>/scripts/process_case_results.py" \
  --input "<第1页JSON>" \
  --input "<第2页JSON，如有>" \
  --full-output "<完整结果JSON>" \
  --trimmed-output "<交付集精简JSON>" \
  --stats-output "<统计JSON>" \
  --requested-count <用户明确数量>
```

- 用户未指定数量时省略 `--requested-count`。
- 用户需要法院认定或裁判理由时增加 `--include-court-think`。
- 每增加一页，重新处理现有全部分页文件；统计中的 `deliveryCount` 达到 N 后停止翻页。
- 脚本校验响应结构、合并分页、稳定去重、形成交付集、裁剪重字段并输出统计。
- 完整结果用于详情回读和报告交接；精简结果用于常规分析，不得用精简结果假装包含已裁剪正文。

处理脚本报错时停止分析，说明数据无法验证。不得绕过校验直接从异常响应中摘取案例。

#### 第五步：核验数量、案号与出处字段

读取统计文件并检查：

- `rawCaseCount`：分页原始案例总数；
- `uniqueCaseCount`：去重后的案例数；
- `deliveryCount`：本次应展示的案例数；
- `shortfall`：相对用户明确数量的缺口；
- `missingCaseNoCount`：交付集中缺失案号的数量。

**接着必须运行字段映射门禁**（新增，验收口径"判例带案号/法院/出处"的落地检查）：

```bash
python3 "<本技能目录>/scripts/validate_case_fields.py" "<交付集精简JSON>"
```

- 该脚本对**案号（`caseNo`）、法院（`trialCourt.name`）、出处/数据来源（`dataFrom`）**三项分别统计非空条数与缺失条数：
  - 任一字段缺失比例超过阈值（默认 30%，可用 `--max-missing-ratio` 调整）→ **拦截，禁止交付**；
  - `caseNo` 出现非字符串类型（连接器返回 int / list / dict 等）→ 逐条定位并拦截，不再像 `process_case_results.py` 那样整页崩溃且无法定位；
  - 未超阈值的零星缺失只提示不拦截，但交付时必须逐条注明"未提供"，**禁止推断补全**。
- 脚本退出码非 0 时**不得**向用户罗列案例，先向用户说明是字段映射问题（连接器返回字段与 `references/data-structure.md` 映射不一致）还是数据源本身缺字段。

若 `shortfall > 0`，明确说明"符合当前 Query 且已检索到的去重案例为 X 条，少于要求的 N 条"。需要放宽约束时，先说明拟放宽的具体条件并取得用户同意，不能静默改变 Query。

#### 第六步：生成样本内洞察

只依据精简交付集生成：

1. 裁判观点：概括样本中可直接支持的判断，不生成无依据的胜诉率。
2. 争议焦点：归纳样本反复出现的问题，同时保留少数分歧。
3. 法律适用：仅列出案例字段中实际出现的法律法规和条文。
4. 关联说明：结合用户意图与案例的争议焦点、案由、裁判结果，解释相关性。

无法从字段可靠判断时写"当前返回字段不足以判断"，不要用常识补全裁判内容。

#### 第七步：交付

**交付前必须实际 Read [references/output-format.md](output-format.md) 确认输出顺序与格式，未读取禁止交付**（在任务清单中标记 completed 不能替代实际读取）。按照输出引用文件交付，顺序为：

1. 检索说明：Query、明确约束、检索页数、去重及交付数量；
2. AI 洞察，并标注样本边界；
3. 核心法规关注清单；
4. 类案列表；
5. 数量不足、字段缺失或数据限制说明。

文件策略：

- 用户未要求文件：只在对话中展示，不写入任何文件。
- 用户明确要求 Markdown：生成 `.md`，并同时在对话中提供摘要和文件路径。
- 用户明确要求 Word/DOCX：**直接进入本技能模式C**（[references/mode-c-retrieval-report.md](mode-c-retrieval-report.md)），用模式A 的交接产物生成经校验的 `.docx`；无需探测外部 DOCX 能力，也不得把 Markdown 改扩展名冒充 Word。模式C 的 DOCX 生成或校验失败时，提供经核验的报告素材并明确"本次未生成 DOCX"，不得冒充 Word 交付成功。

#### 模式A → 模式C 内部衔接（原「下游报告交接」）

用户在模式A 之后要正式报告时，**在本技能内部切换到模式C**，传递本次任务的结构化产物，不要复制一份经过模型改写的案例清单作为事实源：

- 用户原始问题和最终 Query；
- 用户明确指定的时间、地域、法院、数量、分类和输出格式；
- 完整结果 JSON（`cases_full.json`）；
- 精简交付集 JSON（`cases_delivery.json`）；
- 统计 JSON（`stats.json`）；
- 已生成洞察中哪些结论存在字段不足。

模式C 必须以 `delivery` 集合确定纳入报告的案例，以 `full` 集合回读正文。不得因为报告模板有自己的结构而增加、替换或重新排序案例。若模式C 生成的报告案例数量、案号或顺序与交付集不一致，应停止交付并重新生成。**衔接过程中不重复调用检索连接器。**

#### 模式A → 模式B 内部衔接（原「查看案例详情」）

用户指定"第 X 条"时，按交付集顺序在完整结果的 `cases` 数组中读取对应案例。仅输出存在的字段；长字段缺失时说明检索结果未提供。

详情可包含：案件名称、案号、案由、法院、日期、审级、当事人、争议焦点、法院查明、法院认为、裁判结果、法律依据和数据来源。

不得再次通过标题、法院或日期推断案号。不得把列表阶段生成的关联说明当成裁判文书原文。

用户要求查看**完整裁判文书**时，只能输出 `sourceContent` 的实际内容。注意：案例检索连接器均无裁判文书逐字全文抓取能力，`sourceContent` 为连接器返回的整理后案例内容或片段，**不等同于原始文书逐字全文**。字段缺失时说明本次检索未提供全文。

用户仍需要逐字全文时：

1. 从 `cases_full.json` 取该案 `caseNo`；**案号非空**→**在本技能内部切换到模式B**（[references/mode-b-fetch-judgment.md](mode-b-fetch-judgment.md)），以该案号为输入执行 B1～B10；
2. `caseNo` 为空 → 告知用户"该条检索结果未提供案号，无法按案号取回逐字全文"，**不得**由标题、法院或日期反推案号；
3. 模式B 的浏览器能力不可用或抓取失败 → 按 SKILL.md 第 4.2 节 A 档降级停止全文获取，降级为**仅提供检索摘要 + 出处**，明确注明"未取得逐字全文"，并建议改用模式A 的裁判要旨。

任何情况下不能根据摘要扩写成全文。

#### 模式A 异常与重试

**检索服务失败**：保留错误信息并告知用户服务不可用。可用相同参数重试一次；仍失败时切换探测到的另一家可用连接器；全部不可用时按执行门禁的 A 档降级停止，不列举案例。

**返回空结果**：先确认 Query 是否包含无意加入的限制。可进行一次不改变用户明确约束的术语清理重试；仍为空时说明未检索到结果，并建议用户选择是否放宽范围。

**数据文件异常**：若 JSON 无法解析、响应失败、字段结构错误或脚本校验失败，重新获取对应页一次。仍失败则终止当前检索，不猜测数据。

**结果不足**：按原 Query 完成允许的翻页后仍不足时，如实交付现有结果。任何时间、地域、法院或法律问题的放宽都需要用户确认。

用户同意放宽后，将放宽后的检索视为新的检索轮次：保存新的 Query 和独立结果文件，并在最终输出中区分"原始条件结果"和"放宽条件结果"。不得把两轮数据混合后仍声称全部符合原始条件。

#### 模式A 交付前检查

- 已成功取得并保存连接器检索返回的 JSON，而不是把技能说明或搜索摘要当作案例数据。
- Query 只包含用户明确约束和必要法律概念。
- 默认未翻页、未分类、未生成文件；除非用户明确要求。
- 展示数量等于 `deliveryCount`，没有因分析偏好再次筛选。
- 每个案号逐字来自原始字段；缺失时仅显示"案号：无"。
- 法院、日期、法律依据和裁判内容没有推断或补全。
- 洞察明确限定为当前检索样本，不作无依据的全局趋势判断。
- `scripts/process_case_results.py` 与 `scripts/validate_case_fields.py` **均已运行且退出码为 0**。
- Word 请求已通过模式C 完成，或已明确说明未生成 DOCX，没有被虚假标记为成功。
- 所有临时文件路径仅用于当前任务，不覆盖其他并发检索。
