# 聊天消息转待办

从指定钉钉群聊消息中识别与我相关的任务类内容，经待办适合度判断后，创建为钉钉待办。

## 禁止事项

- 禁止通过 curl、HTTP API 等非 `dws` 方式操作钉钉产品
- 禁止凭空构造 openconversation_id、userId、taskId 等标识符，所有 ID 必须从实际命令返回值中获取
- 禁止 `dws` 命令不加 `--format json`
- 禁止在用户未提供群名称时自行猜测或搜索——必须明确要求用户输入群名称
- 禁止脱离上下文孤立分析单条消息——必须结合前后消息理解完整语境后再判断任务内容
- 禁止将即时性事务（如"来开会"、"快速聊一下"）识别为待办
- 禁止在 `chat message list` 中使用 `--user`——该命令仅支持 `--group`（群聊），单聊请用 `chat message list-direct --user`
- 禁止 `--time` 使用相对时间（如 `"7d"`）——必须使用 `yyyy-MM-dd HH:mm:ss` 格式的绝对时间
- 禁止 `hasMore=true` 时只用第一页消息——必须循环翻页直到 `hasMore=false`

## 强制要求

- 每条 `dws` 命令均须携带 `--format json` 参数
- 用户必须指定群名称；未指定时主动要求用户提供，不得自行搜索全部会话
- 默认拉取最近 24 小时消息，用户指定了时间范围时按用户给的时间查询
- `--time` 参数必须用当前时间减去对应时长计算为绝对时间（如 `"2026-03-24 14:00:00"`）
- 必须检查返回结果的 `hasMore` 字段，为 `true` 时用最后一条消息的 `createTime` 继续翻页，直到 `hasMore=false`
- 拉取完整消息后，从中定位两类"锚点消息"：① @当前用户 的消息 ② 消息文本中包含当前用户姓名的消息
- 对每条锚点消息，必须结合其前后上下文（同一话题的连续对话）来准确理解任务内容，不得孤立分析单条消息
- 对筛选出的每条消息必须进行待办适合度判断，区分"建议创建待办"和"不建议创建待办"
- 创建待办前必须向用户展示分析结果（含适合度判断和理由）并确认
- 每个待办必须包含标题；优先级和截止时间根据消息内容推断，无法推断时使用默认值（优先级 20 普通）

## 能力清单

| 动作 | 安全等级 | 说明 |
|------|---------|------|
| 搜索群聊 | 只读 | 根据用户提供的群名搜索目标群聊 |
| 会话智能排序 | 只读 | 搜索结果有多个时，拉取最近消息按相关度排序展示 |
| 获取聊天消息 | 只读 | 拉取指定群聊的消息内容 |
| 与我相关消息定位 | 只读 | 从全部消息中定位 @我 和提到我名字的"锚点消息" |
| 上下文语境分析 | 只读 | 结合锚点消息前后的对话上下文，准确理解任务内容 |
| 待办适合度判断 | 只读 | 判断消息是否适合创建为待办（过滤即时性事务） |
| 获取当前用户信息 | 只读 | 获取当前登录用户的 userId 和姓名 |
| 创建待办 | 写入 | 将适合创建的任务创建为钉钉待办，需用户确认 |

## 涉及工具

| 工具 | 用途 |
|------|------|
| `dws chat search` | 根据群名搜索会话，获取 openconversation_id |
| `dws chat message list` | 拉取群聊的消息内容 |
| `dws contact user get-self` | 获取当前用户 userId 和姓名（用于消息筛选和待办 executors） |
| `dws contact user search` | 按关键词搜索用户，获取 userId |
| `dws todo task create` | 创建钉钉待办任务 |

## 总体工作流

```
用户: "把项目冲刺群里的任务记下来"
      |
      v
Module A: 定位群聊
  → 用户提供群名 → chat search 搜索 → 多结果时智能排序 → 获取 ID
      |
      v
Module B: 获取消息并定位与我相关内容
  → 拉取全部消息（翻页至完整） → 定位 @我 + 提到我名字的"锚点消息"
      |
      v
Module C: 上下文语境分析 + 待办适合度判断
  → 结合锚点消息前后上下文理解任务 → 判断适合度 → 分类为"建议创建"/"不建议创建"
      |
      v
Module D: 创建待办
  → 展示分析结果（含适合度判断） → 用户确认 → 逐条 todo task create → 返回结果
```

详细命令示例见 [references/workflow-detail.md](./references/workflow-detail.md)

## 上下文传递表

| 阶段 | 从返回中提取 | 用于 |
|------|-------------|------|
| A1: `contact user get-self` | 当前用户 userId、姓名 | B 定位锚点消息（@我 + 姓名匹配）、D 创建待办的 executors |
| A2: `chat search` | openconversation_id、会话名称 | A3 智能排序（多结果时）、B 拉取消息 |
| A3: 智能排序（多结果时） | 排序后的会话列表 | 用户选择目标群聊 |
| B: `chat message list` | 全部消息内容（完整上下文） | B 定位锚点消息 + C 上下文语境分析 |
| B: 锚点定位 | @我的消息 + 提到我名字的消息 | C 结合上下文分析任务内容 |
| C: 上下文分析 + 适合度判断 | 建议创建的任务列表（标题、优先级、截止时间、判断理由） | D `todo task create` |

## 待办适合度判断规则

对每条锚点消息，AI 必须结合其前后上下文理解完整语境，再判断是否适合创建为待办。

### 上下文分析要求

锚点消息往往不包含完整信息，必须结合上下文才能准确理解：

| 场景 | 锚点消息 | 上下文 | 正确理解 |
|------|---------|--------|---------|
| 任务背景在前文 | "@张三 你来跟进一下" | 前文: "供应商报价还没回复" | 待办标题应为"跟进供应商报价回复"，而非"跟进一下" |
| 截止时间在前文 | "@张三 这个你处理下" | 前文: "周五之前需要把方案定下来" | 截止时间应为周五 |
| 多轮讨论后分配 | "@张三 行，你来吧" | 前文是关于竞品分析的讨论 | 待办标题应为"完成竞品分析"，而非"你来吧" |
| 回复确认非任务 | "好的张三，收到" | 前文: 张三分享了一个文件 | 不应创建待办——这是对他人消息的回复确认 |

### 建议创建待办（高匹配度）

包含需要持续跟进、有明确交付物或有截止时间的任务信号：

| 信号类型 | 典型表达 | 说明 |
|----------|---------|------|
| 跟进类动词 | 跟进一下、处理一下、确认一下、落实一下、推进一下 | 需要后续行动，适合作为待办跟踪 |
| 交付类动词 | 整理一份、输出一个、提交、发一下、准备好 | 有明确交付物 |
| 时间类线索 | 明天、后天、本周、下周、周五前、月底前、几号之前 | 有截止时间，适合待办提醒 |
| 分配类表达 | 你来负责、交给你、你这边处理、麻烦你 | 明确分配给我的任务 |
| 审批/反馈类 | 帮忙审一下、看一下这个方案、给个反馈、评审一下 | 需要我花时间完成 |

### 不建议创建待办（低匹配度）

即时性、一次性、无需后续跟踪的事务：

| 信号类型 | 典型表达 | 说明 |
|----------|---------|------|
| 即时行动 | 来会议室、过来一下、快速聊一下、马上开会 | 马上就要去做的事，做完即结束，不需要待办跟踪 |
| 信息知会 | 知道了、收到、好的、已处理、FYI | 仅通知，无需行动 |
| 简单回复请求 | 在吗、方便吗、你看到了吗 | 回复即完成，无跟踪价值 |
| 已完成事项 | 已提交、搞定了、我处理好了 | 已完成的事不需要再建待办 |
| 社交性 @ | @所有人 周末愉快、@某人 生日快乐 | 非任务性质 |

### 展示格式

分析结果必须分两区展示给用户：

```
✅ 建议创建待办（N 条）:
1. [标题] — 优先级: 普通 — 截止: 周五前
   原始消息: "@张三 帮忙把Q2报告整理一下，周五前给我"
   判断理由: 包含交付物（Q2报告）+ 截止时间（周五前）

⚠️ 不建议创建待办（M 条）:
1. 原始消息: "@张三 来会议室快速过一下"
   判断理由: 即时行动，无后续跟踪需要
```

用户可以对不建议的条目手动选择"仍然创建"。

## 会话智能排序规则

搜索结果有多个匹配时，对候选会话拉取最近 24 小时消息，按相关度打分排序：

| 维度 | 得分 | 说明 |
|------|------|------|
| @我的消息 | +10 分/条 | 群里 @当前用户 的消息越多，相关度越高 |
| 提到我名字的消息 | +8 分/条 | 消息文本包含当前用户姓名 |
| 我的活跃度 | +3 分/条 | 当前用户在该群发送消息的数量 |

展示规则：按总分从高到低排序展示给用户选择，总分 < 10 分的会话不展示。过滤后无剩余则展示全部并提示。

## 使用示例

### 示例 1: 从指定群聊提取任务
**用户说**: "把项目冲刺群里说的任务记下来"
**执行步骤**:
1. `contact user get-self --format json` 获取当前用户 userId 和姓名
2. `chat search --query "项目冲刺" --format json` 搜索群聊，获取 openconversation_id
3. `chat message list --group <id> --time "<24小时前绝对时间>" --format json` 拉取全部消息，翻页至完整
4. 从全部消息中定位 @当前用户 和包含当前用户姓名的锚点消息
5. 对每条锚点消息结合前后上下文理解任务内容，进行待办适合度判断，分类展示结果
6. 用户确认后逐条 `todo task create` 创建待办
**期望输出**:
```
从《项目冲刺群》最近 24 小时消息中，找到 8 条与你相关的消息：

✅ 建议创建待办（3 条）:
1. 整理Q2数据报告 — 优先级: 普通 — 截止: 2026-03-28
2. 跟进供应商报价 — 优先级: 较高 — 截止: 明天
3. 提交设计评审材料 — 优先级: 普通 — 截止: 本周五

⚠️ 不建议创建待办（5 条）:
1. "来会议室过一下方案" — 即时行动
2. "收到，我知道了" — 信息知会
...

是否创建以上 3 条待办？你也可以从不建议列表中选择需要创建的。
```

### 示例 2: 搜索结果多个匹配
**用户说**: "把产品群里的任务整理一下"
**执行步骤**:
1. `contact user get-self --format json` 获取当前用户信息
2. `chat search --query "产品" --format json` 搜索，返回多个匹配（产品需求群、产品设计群、产品运营群）
3. 对各群拉取最近消息，按 @我消息数 + 提到我名字的消息数 + 活跃度排序
4. 展示排序结果："搜索到 3 个匹配的群：1. 产品需求群 [3条@你] 2. 产品设计群 [1条@你] ..."
5. 用户选择后执行完整筛选→判断→创建流程
**期望输出**: 展示排序后的群列表供用户选择

### 示例 3: 用户未指定群名
**用户说**: "聊天记录转任务"
**执行步骤**:
1. 要求用户提供群名称："请告诉我要从哪个群聊中提取任务？请提供群名称或关键词。"
2. 用户回复群名后执行完整流程
**期望输出**: 引导用户提供群名

## 错误处理

| 错误 | 原因 | AI 应该怎么做 |
|------|------|--------------|
| 用户未提供群名 | 触发词不含群名信息 | 主动要求用户提供群名称或关键词 |
| 搜索群聊无结果 | 关键词过窄或群名不匹配 | 换用更宽泛的关键词重试，或请用户提供更准确的群名 |
| 403 权限错误 | 无权访问该群聊 | 提示用户确认是否有对应群聊的访问权限 |
| 无与我相关的消息 | 最近 24 小时没有 @我 或提到我名字的消息 | 告知用户未发现与你相关的消息，建议扩大时间范围（如指定最近 3 天或 7 天） |
| 有相关消息但无适合创建待办的 | 相关消息全部为即时性事务 | 展示不建议列表，告知均为即时性事务，用户可手动选择仍然创建 |
| 待办创建失败 | executors 参数错误 | 检查 userId 是否从 `contact user get-self` 正确获取 |
| 翻页拉取超时 | 消息量过大 | 使用已拉取的部分消息继续识别，标注"数据可能不完整" |
