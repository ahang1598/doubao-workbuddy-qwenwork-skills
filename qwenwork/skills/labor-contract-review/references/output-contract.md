# 劳动合同审查输出契约

本文件承接 `SKILL.md` 中的详细输出规则。正式报告、结构化 `issues` 和 Word 批注均应遵守本文件。

## 最终回复格式

对用户只给正式结果。报告必须从 `# 劳动合同审查报告` 开始；如是补充更正，可先写一句简短更正说明，再立即给完整报告。

正式报告必须包含：

1. `## 一、核心结论`
2. `## 二、关键风险（精简版）`
3. `## 三、针对行业的特别说明（自动生成）`
4. `## 四、完整审查明细`
5. `## 五、其他合规提示`
6. `## 六、附件下载`

并且 `## 四、完整审查明细` 下必须保留：

- `### 7. 整体修改建议`
- `### 8. 谈判与签署建议`

其中 `### 8. 谈判与签署建议` 至少输出 2 条实际建议。
不得在报告前输出任何过程性铺垫，不得输出逐规则检查记录，不得输出 “LCR001/LCR002…通过、命中、未命中” 这类中间过程。
`### 8. 谈判与签署建议` 应明显偏向当前审查立场：默认偏甲方；如用户指定乙方，则偏乙方；如用户要求均势审查，再给平衡型建议。

## 输出要求分级

### 硬约束

- 报告必须从指定标题开始。
- 最终报告必须保留六个章节。
- 实际命中的每个风险点必须用 Markdown 两列表格展示。
- 两列表格表头必须符合语义：事实信息、风险卡片、修改建议和附件结果使用 `项目 / 内容`；需用户确认或文本无法确定事项使用 `审查项 / 注意事项`。
- `注意事项` 列只能写签署前需补齐、核对或留痕的概括提醒，例如“主体信息待签署时补齐”“工资金额和发薪日期待填写”“规章制度附件签收状态待确认”，不得写成已经发现的风险问题。
- `## 四、完整审查明细` 中的风险卡片必须按合同原文条款顺序排列；不得按高风险、中风险、低风险分组。
- 仅展示命中的风险点，不展示未命中的规则。
- 不得把打印空白模板中的待填写留白直接包装成高风险、中风险或低风险。
- 不得把主体信息、工资金额、试用期、发薪日期等空白待填栏位写入 `issues` 或 Word 批注；这类事项只作为签署前注意事项。
- 空白主体信息栏位包括姓名、身份证号、住址、通讯地址、联系电话、电子邮箱、紧急联系人等；只要合同模板已经设置这些栏位但尚未手填，均不得输出为 `LCR001` 高风险卡片。
- 报告正文不得包含 `<br>`、`<br/>`、`<br />` 或字面量 `\n`；表格单元内需要换行含义时改为空格或简短分号。
- 工作地点修改建议不得写成“通勤时间增加超过30分钟即必须提供交通补贴或班车”等无法律强制依据的义务；可写为“跨区域调整按合理性原则协商处理，相关支持安排按甲方依法制定并公示的制度执行，或由双方另行协商确定”。
- 加班工资条款不得机械建议在劳动合同中写死具体基数，例如“以月工资9500元为基数”；可写加班审批和依法支付原则，具体基数放入依法制定并公示的薪酬、考勤或加班审批制度。
- “加班需经书面审批”可以作为管理规则，但不得写成未经审批一律不构成加班；应保留甲方实际安排、确认或依法认定加班的例外。
- 修改后文本示例应优先使用“依法处理、按甲方依法制定并公示的制度执行、双方另行协商确定、甲方可根据实际情况采取”等甲方可执行表述；除非劳动法律已有明确强制规定，不得写成“甲方应无条件提供/支付/保留/安排”。
- 不得做过度推断：风险说明和批注正文必须直接对应 `original_excerpt` 中出现的条款内容；原文没有“工资扣除、罚款、打听薪资、未经审批不算加班、交通补贴/班车、固定补正期、最低工资待遇”等内容时，不得在该条批注中引入这些风险。
- 保密条款只审保密范围、期限、责任、个人信息/患者信息保护和与竞业限制混同问题；不得把一般保密条款扩展为薪资保密、打听薪资或工资扣除风险，除非原文明确出现这些内容。
- 保密条款原文已经写明离职后继续保密义务的，不得批注“离职后保密义务缺失”或“保密期限缺失”；只能就保密范围、信息分类、责任边界、个人信息或患者信息保护等原文实际问题审查。
- 仅写“标准工时制、每日不超过8小时、每周不超过40小时”的条款，不得批注“未经书面审批一律不算加班”；只有原文明确出现加班审批或排除加班认定表述时，才审加班审批例外。
- 社保条款写“入职后30日内办理参保手续”时，优先按中风险“起算口径表述歧义”处理，不得直接定性为未缴社保或高风险；只有试用期不缴、转正后缴、资格取得后缴、以补贴替代社保等才按高风险处理。
- “故意或重大过失造成损害，依法承担责任”等原则性责任条款，通常按中风险或优化项提示责任认定程序，不得推断为解除条件或工资扣款风险，除非原文明确写入解除、扣款、固定赔偿或罚款。
- 工时排班、轮班夜班和值班规则缺失，或培训考核不合格后的暂停上岗程序/待遇不明，默认按中风险处理；只有原文明确排除加班工资、剥夺休息权、停发工资、长期停岗、当然解除或违反特殊工时审批要求时，才可升为高风险。
- 原文引用“甲方规章制度、员工手册、考勤制度、培训考核制度、奖惩制度”等作为遵守、处分、解除、排班、培训、考核、降薪、停岗或扣款依据，但未写明依法制定、公示告知或签收确认的，必须直接输出 `HFR003` 风险卡片和 Word 批注，不得只写入确认事项。
- 持证上岗资格异常的修改建议不得写死“15个工作日查明、30日补正、按最低工资支付”等具体期限或待遇标准；应写为依法结合原因、期限、补正情况、岗位影响、制度程序处理。
- `### 7. 整体修改建议` 和 `### 8. 谈判与签署建议` 必须保留。
- `## 六、附件下载` 必须保留，并用表格展示结果。
- 附件表格不能把纯文本文件名伪装成可下载链接；生成批注版时，真实 Word 文件必须作为平台文件附件交付。确认文件已生成并可交付时，表格中可写 Markdown 文件链接，或写 `见下方附件卡片`；未生成时写 `未提供`。不得填写“尝试生成”“待生成”“正在生成”等占位文字。
- `### 8. 谈判与签署建议` 必须体现立场策略，不能只写通用合规建议。

### 软约束

- 除 `修改后文本示例` 外，内容尽量简洁。
- 每个表格单元、编号项或说明项尽量控制在 100 字左右。
- 法律依据只点关键规则，不展开长篇论证。
- 行业信息不足时，不强行细分行业。

## 风险项要求

每个实际命中的风险点都要写成独立卡片，并包含：

- 规则编号
- 风险等级
- 风险类型
- 原文位置及摘要（展示层合并原文位置与原文摘要）
- 风险说明（展示层合并风险提示与风险分析）
- 修改建议
- 修改后文本示例

结构化结果中仍可分别保留 `原文位置`、`原文摘要`、`风险提示` 与 `风险分析`，但最终报告展示时合并为“原文位置及摘要”和“风险说明”表格行。

所有风险都按上述格式展开，并按合同原文条款顺序排列。未命中的规则不展示。每个风险点必须使用 Markdown 两列表格展示，不得改成项目符号、普通段落、“风险项1/2/3”列表或按风险等级分组。

## 风险项原子化

- 一个风险项只能对应一个明确原文锚点；Word 批注会直接挂在该锚点上，因此批注正文必须只解释该锚点本身的问题。
- 不得把相邻但性质不同的条款合并为同一风险项。例如“工资扣除/赔偿扣款”和“泄露、刺探、打听薪资被列为严重违纪”应拆成两个风险项，分别给出原文摘要、风险说明和修改建议。
- 如同一条款中同时出现多个独立风险，也应按风险性质拆分；只有原文、风险原因和修改方向高度一致时，才允许合并。
- `original_excerpt` 必须尽量摘录合同原文，不得写成概括性结论；`risk_message`、`risk_analysis`、`revision_suggestion` 不得引入另一个未单独列项的原文风险。
- 报告正文中的每个风险卡片都必须在结构化 `issues` 中有一条对应记录；不得正文拆分、批注 JSON 合并。
- 容易误合并的场景包括：主体信息多字段缺失、岗位地点与调岗权、工时与加班/休假、工资金额与加班工资、试用期期限与试用期工资、解除条件多项并列、竞业范围与补偿、保密义务与竞业限制、附件缺失与签收缺失。
- 空白模板栏位不是风险项，不适用上述拆分要求；多个空白待填事项可以合并写入“需用户确认或文本无法确定事项”。

## 高频败诉风险规则

以下规则每次审查都必须主动核查，命中后与 `LCR` 风险一样输出正式风险卡片和结构化 `issues`：

- `HFR001` 特殊工时自动适用风险
- `HFR002` 绩效考核直接作为调岗、降薪、不胜任依据风险
- `HFR003` 规章制度未公示告知仍当然有效风险
- `HFR004` 内部申诉期限逾期视为确认风险
- `HFR005` 不胜任工作包装为严重违纪风险
- `HFR006` 严重损失标准过低或过宽风险
- `HFR007` 离职交接固定倍数赔偿风险
- `HFR008` 固定区间赔偿或变相违约金风险
- `HFR009` 违法解除赔偿金按协议约定风险
- `HFR010` 工资异议逾期视为认可风险
- `HFR011` 劳动争议解决机构或程序表述错误风险
- `HFR012` 持证上岗资格失效直接解除或处分风险
- `HFR013` 轮班夜班值班安排不明风险
- `HFR014` 社保缴纳起算或试用期不缴社保风险
- `HFR015` 暂停上岗资格期间待遇与程序不明风险

`HFR` 风险卡片按其对应原文条款位置插入完整审查明细，不集中放在高风险、中风险或单独 HFR 小节。

## 谈判策略要求

- `### 8. 谈判与签署建议` 要写成可直接用于谈判的策略，不只做复述式提醒。
- 默认按甲方立场输出：优先写“哪些条款必须保留、哪些条款可让步、让步条件是什么、签署前要补什么留痕”。
- 默认甲方模板审查时，还应覆盖：员工按岗位和用工形态分类适配模板、固定期限劳动合同续签和无固定期限触发节点台账、附件和制度签收、竞业限制启动/解除通知、离职交接和送达地址留痕。
- 如按乙方立场输出：优先写“哪些条款必须争取删除或收窄、哪些条款可接受、接受前要换取什么补偿或限制条件”。
- 如按均势输出：才使用相对平衡的双向建议。
- 谈判建议应尽量围绕已命中的高风险和中风险条款展开，避免空泛。

## 批注结果

如果生成了 Word 批注版，应把实际存在的 `docx` 作为平台文件附件交付，而不是只在“六、附件下载”表格中写一个纯文本文件名。默认命名规则为：`原文件名-批注版-年月日.docx`。只有后处理脚本返回成功并确认文件存在时，才允许在附件表格中写 Markdown 文件链接或 `见下方附件卡片`；不得根据预期命名、报告文字或计划结果虚构附件。批注失败或未生成时，仍保留附件表格，但只能写 `未提供`，不得写“尝试生成批注版Word文档”等占位文本。

## 异常处理与状态管理

- 本技能为无状态设计，所有中间结果通过报告 Markdown、临时文件和后处理脚本参数传递，不依赖长期记忆或会话状态。
- 参数缺失（未提供 `docx` 原件）：仅输出 Markdown 报告，附件表格写 `未提供`。
- 文件读取失败：停止生成批注版，不尝试修复或猜测原文；仍交付 Markdown 报告，附件表格写 `未提供`。
- 大文件或复杂文档处理超时：可分块提取文本或提示用户简化合同；不得虚构完整审查或附件。
- 批注脚本执行失败：记录失败原因，继续交付 Markdown 报告作为可用成果，附件表格写 `未提供`。

## 附件说明限制

- 只要上下文中存在 `docx` 附件、附件文件名、附件路径或附件引用，就先按“可生成批注版”处理，并优先尝试解析原始文件。
- 解析原始文件时，先用明确路径；没有明确路径时，再用附件文件名、上下文中的本地路径、当前目录、输出目录、临时目录等常见落点继续查找。
- 不得仅因默认兜底或环境猜测就判断“无法访问原始 docx”。
- 不要提“沙盒环境”“会话附件”“工作区”“重新上传”“自行使用脚本处理”等技术性原因或操作建议。
- 能生成批注版且已确认文件存在时，必须直接上传/附加 `docx` 文件，并在附件表格中写 Markdown 文件链接或 `见下方附件卡片`。
- 不能生成时，不要单独写说明段落；只在附件表格中写 `未提供`。
- 禁止在附件表格中输出任何占位值或不可下载的伪链接，如未确认文件存在的纯文本批注版文件名、`尝试生成批注版Word文档`、`直接附上的 docx 文件`、`report_path`、`下载地址待补充`。
