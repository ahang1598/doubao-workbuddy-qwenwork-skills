# 劳动合同审查报告模板

最终报告从下面的标题开始。占位符由实际审查结果替换。
标题前不得出现任何过程说明或逐规则检查记录；只允许直接进入正式报告。
只要上下文中存在 `docx` 附件、附件文件名、附件路径或附件引用，就默认按“报告输出后可生成批注版”处理。先输出正式报告；批注版 Word 由后处理脚本 `scripts/annotate_report_docx.py` 在报告输出后生成，不改变报告正文和风险排序。

完整报告必须包含 6 个章节。`## 四、完整审查明细` 中的风险卡片必须按合同原文条款顺序从前到后展示，不得按高风险、中风险、低风险分组排序；每个风险点都包含风险等级、原文位置及摘要、风险说明、修改建议和修改后文本示例。
其中 `## 四、完整审查明细` 下必须保留 `### 7. 整体修改建议` 和 `### 8. 谈判与签署建议` 两个小节，不得省略。
默认甲方审查必须采用“合法底线 + 企业保护”口径：先指出可能导致甲方败诉、条款无效或举证困难的问题，再给出有利于甲方执行、留痕、成本可控和管理弹性的修改方案。除非用户明确指定乙方或均势审查，不得为了保护乙方而扩大甲方义务，不得把法律没有强制要求的补贴、保留岗位、延长补正、照发待遇、交通住宿支持等写成甲方合同硬义务。
每个风险点必须使用 Markdown 两列表格卡片展示，不得改成项目符号、普通段落或“风险项1/2/3”列表。
两列表格按语义选表头：事实信息、风险卡片、修改建议和附件结果使用 `| 项目 | 内容 |`；需用户确认或文本无法确定事项使用 `| 审查项 | 注意事项 |`。`注意事项` 列只写签署前需补齐、核对或留痕的概括提醒，例如“主体信息待签署时补齐”“工资金额和发薪日期待填写”“规章制度附件签收状态待确认”，不得写成已经发现的风险问题。
若初稿不是表格卡片，应先重排为表格后再输出最终报告。
`HFR001-HFR015` 高频败诉风险属于常规审查范围，与 `LCR001-LCR017` 一样输出正式风险卡片和结构化 `issues`，不得作为扩展风险或规则库外风险处理。
“原文位置及摘要”为展示层字段，由“原文位置 + 原文摘要”合并而成；“风险说明”为展示层字段，由“风险提示 + 风险分析”合并而成。结构化结果可继续保留这些原始字段。
每个风险点只能对应一个明确原文锚点；不得把相邻但性质不同的条款合并为同一风险项。例如“工资扣除/赔偿扣款”和“泄露、刺探、打听薪资被列为严重违纪”必须拆成两个风险项分别展示和批注。
报告正文中的每个风险卡片都必须在结构化 `issues` 中有一条对应记录；不得正文拆分、批注 JSON 合并。
扩展风险仅在存在命中时显示，编号统一写为 `EXTENDED-01`、`EXTENDED-02`……，并按原文条款位置并入 `### 2. 按合同条款顺序的风险问题`，不得单独按风险等级或规则来源分组。
如合同明显为打印空白模板，`____`、空格线、留白栏、括号待填、空白表格单元等待手工填写内容，默认写入“需用户确认或文本无法确定事项”，不直接写入高风险、中风险或低风险，不写入结构化 `issues`，也不生成 Word 批注。主体信息、合同期限、岗位地点、工时制度、工资金额、试用期期限、试用期工资、发薪日期、签署日期等待填栏位，均按此处理，不进入“必须修改”。
主体信息空白模板栏位包括姓名、身份证号、住址、通讯地址、联系电话、电子邮箱、紧急联系人等；只要合同模板已经设置这些栏位但尚未手填，均不得输出为 `LCR001` 高风险卡片，只能写入签署注意事项。
只有合同成稿中完全没有设置必要栏位，或已填写内容本身违法、矛盾、过宽、过低、排除法定权利时，才按对应规则输出风险。
甲方模板完善建议默认写入“整体修改建议”“谈判与签署建议”或“其他合规提示”，包括员工分类适配模板、合同期限台账、工作地点弹性设计、制度公示签收、离职交接、竞业限制启动/解除和送达地址留痕。此类建议没有明确原文风险锚点时，不进入风险卡片、`issues` 或 Word 批注。
工作地点修改建议不得写成“通勤时间增加超过30分钟即必须提供交通补贴或班车”等无法律强制依据的义务；如需跨区域调整，可提示按合理性原则协商处理，相关支持安排按甲方依法制定并公示的制度执行，或由双方另行协商确定。
加班工资条款不得机械建议在劳动合同中写死具体基数，例如“以月工资9500元为基数”；可写加班审批和依法支付原则，具体基数放入依法制定并公示的薪酬、考勤或加班审批制度。“加班需经书面审批”可以作为管理规则，但不得写成未经审批一律不构成加班，应保留甲方实际安排、确认或依法认定加班的例外。
修改后文本示例应优先使用“依法处理、按甲方依法制定并公示的制度执行、双方另行协商确定、甲方可根据实际情况采取”等甲方可执行表述；除非劳动法律已有明确强制规定，不得写成“甲方应无条件提供/支付/保留/安排”。
特殊岗位合同应额外核查持证资格、轮班夜班值班、排班休息、暂停上岗/暂停排班和社保起算。适用岗位包括但不限于医护、司机、保安、特种作业、危化、财务出纳、销售外勤等；命中时按 `HFR012-HFR015` 或对应 `LCR` 规则输出风险卡片，未命中时只在行业说明或签署动作中提示留痕。
风险卡片和 Word 批注必须忠实于当前原文锚点，不得为了显得完整而引入原文没有的风险。保密条款不得扩展成薪资保密、打听薪资或工资扣除；标准工时条款不得扩展成加班审批例外；原则性依法赔偿条款不得扩展成解除或扣款风险；工作地点条款不得写入固定通勤阈值、交通补贴或班车义务；资格异常条款不得写死固定补正天数或最低工资待遇。
保密条款原文已经写明离职后继续保密义务的，不得批注“离职后保密义务缺失”或“保密期限缺失”。工时排班、轮班夜班和值班规则缺失，或培训考核不合格后的暂停上岗程序/待遇不明，默认按中风险处理；只有明确排除加班工资、剥夺休息权、停发工资、长期停岗、当然解除或违反特殊工时审批要求时，才可升为高风险。原文引用规章制度、员工手册、考勤制度、培训考核制度、奖惩制度作为管理或处分依据但未写明公示告知或签收确认的，必须直接输出 `HFR003` 风险卡片和 Word 批注。
报告正文不得包含 `<br>`、`<br/>`、`<br />` 或字面量 `\n`；表格单元内需要换行含义时改为空格或简短分号。

除“修改后文本示例”外，所有生成内容都要简化。每个表格单元、编号项或说明项尽量控制在 100 字左右，用简单语言说明问题、原因和改法。

## 稳定性要求

- 保留六个章节，以及“整体修改建议”“谈判与签署建议”。
- `### 8. 谈判与签署建议` 必须输出，且至少填写 2 条实际建议，不得留空或省略。
- `### 8. 谈判与签署建议` 默认偏向当前审查立场：默认偏甲方；如用户指定乙方，则偏乙方；仅均势审查时使用平衡表述。
- 默认甲方审查时，风险识别要充分覆盖漏项，但修改建议必须偏企业可执行和风险可控；不得主动新增法律没有要求的甲方福利、补偿、交通住宿、岗位保留或长期照发待遇义务。
- 谈判建议应体现策略性，优先围绕高风险和中风险条款写“坚持点、可让步点、交换条件、签署留痕”，不要只写泛泛合规提醒。
- 默认甲方模板审查时，“整体修改建议”和“谈判与签署建议”至少覆盖 2 类模板完善动作：员工分类/期限台账、附件与制度签收、竞业启动或解除、离职交接、送达地址留痕、工作地点弹性边界。仅当这些事项对应明确原文风险时，才另列风险卡片。
- 不新增项目管理式栏目，如修订优先级、完成时间等。
- 除“修改后文本示例”外，所有内容短句表达，单项约 100 字。
- 每个风险点独立成 Markdown 表格卡片；所有风险都使用同一结构，并按合同原文条款顺序排列。若输出成项目符号、段落，或按风险等级分组，视为格式错误。
- `HFR001-HFR015` 命中时按原文条款位置并入 `### 2. 按合同条款顺序的风险问题`，不单独开“高频败诉风险”章节，也不得按 HFR/LCR 来源分组。
- 每个风险点和 Word 批注都必须原子化：一个原文锚点对应一个风险说明和一个修改方向；不得在挂到 A 条款的批注中主要讨论 B 条款。
- 主体信息、工资金额、试用期、发薪日期等模板待填空白，只能进入“需用户确认或文本无法确定事项”和签署动作；不得在风险问题章节展示，也不得写入 `issues`。
- 报告不得包含 `<br>` 或字面量 `\n`。
- 工作地点修改建议不得把交通补贴、班车服务或“通勤超过30分钟”的阈值写成法定义务；如有需要，只能写为按依法制定并公示的制度执行，或由双方另行协商确定。
- 加班工资修改建议不得把具体月工资数额写死为合同基数；不得写“未经书面审批一律不算加班”，应保留实际安排、确认或依法认定加班的例外。
- 社保“入职后30日内办理参保手续”优先按表述歧义中风险处理；不得直接写成高风险未缴社保。原则性“故意或重大过失造成损害依法担责”优先按责任标准和程序不明的中风险或优化项处理。
- 批注正文不得讨论当前原文锚点以外的条款风险；若发现另一个条款风险，应另列独立风险卡片和独立 `issues`。
- 纯管理建议不得使用 `EXTENDED` 编号；不得为了生成批注而虚构原文锚点。
- 容易误合并的场景必须主动拆分：主体信息多字段缺失、岗位地点与调岗权、工时与加班/休假、工资金额与加班工资、试用期期限与试用期工资、解除条件多项并列、竞业范围与补偿、保密义务与竞业限制、附件缺失与签收缺失。
- 核心结论要直接列明必须修改项、建议优化项和一句话总结。
- 关键风险可按风险等级概括，不罗列未命中的规则；但完整审查明细必须按合同条款顺序排列。扩展风险按实际风险等级并入摘要，不单列单独摘要栏。
- 原件为 `docx` 时，报告输出后通过 `scripts/annotate_report_docx.py` 生成批注版 Word；只有脚本成功返回且确认文件存在时，才把实际文件作为平台附件交付，并在本节写 Markdown 文件链接或 `见下方附件卡片`。无法提供时，在附件表格中写 `未提供`，不要另起说明段落。
- 批注版 Word 默认命名规则为：`原文件名-批注版-年月日.docx`。
- 本技能为无状态设计，所有中间结果通过报告 Markdown、临时文件和后处理脚本参数传递，不依赖长期记忆或会话状态。
- 参数缺失、文件读取失败、批注脚本执行失败或未生成批注版时，继续交付 Markdown 报告，附件表格写 `未提供`。
- 大文件或复杂文档处理超时时，可分块提取文本或提示用户简化合同；不得虚构完整审查或附件。
- 不得仅因默认兜底或环境猜测就判断“无法访问原始 docx”；应先尝试用附件路径、附件文件名、本地路径和常见目录解析原始文件。
- 不写技术性原因或操作指引，如沙盒限制、上传附件、复制到工作区、使用脚本处理等。
- 不输出逐条规则检查过程、`LCR001...通过/命中` 列表或任何“让我检查每个规则”的过程文字。
- 附件表格中只能填写已确认可交付的 Markdown 文件链接、`见下方附件卡片` 或 `未提供`；不得输出未确认文件存在的纯文本批注版文件名、`尝试生成批注版Word文档`、`直接附上的 docx 文件`、`report_path` 等占位文本。
