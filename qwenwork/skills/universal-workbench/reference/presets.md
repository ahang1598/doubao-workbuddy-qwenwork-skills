# 预置方案库（universal-workbench）

首轮引导**先匹配预置方案**：命中则直接出示成套设计契约（省掉 4 问），仅确认 1 轮即可开工；未命中再走通用四问。
每条预置含：触发画像 / 一句话 pitch（引导时可原样说给用户听，激发想象）/ 角色矩阵 / 实体与视图 / 权限要点 / 种子建议。

---

## P1 · 班级共写工作台（老师 / 家长 / 学生）

**一句话 pitch**：当了三年班主任终于不用群里追作业了——搭一个老师、家长、孩子一起用的网页。

**触发画像**：班主任、任课老师、家委会、家长提到"班级群太乱 / 追作业 / 收回执"。

| 角色 | 权限 |
|------|------|
| 老师（admin） | 发布作业/通知、批改、看全班提交情况、管理家长账号 |
| 家长（member） | 看通知，只看/只交**自家孩子**的作业，留言 |
| 学生（受限 member，可选） | 只读作业要求、上传自己的作业 |

**实体映射**：assignments 作业（标题/科目/截止日/要求）· submissions 提交（assignment_id/学生/内容/状态 待交已交已批）· notices 通知（标题/正文/需回执）· comments 留言。

**视图**：作业大厅（全员）· 通知公告（全员）· 我家作业（家长，owner 隔离：submissions.parent = 本人）· 批改台（老师 only）。

**权限要点**：家长隔离必须服务端过滤 `parent_id = me`，前端隐藏不算数；回执用 notices 的 comments 实现，不另建表。

**种子建议**：1 老师 + 3 家长演示号，2 份作业 + 各家不同状态的提交（待交/已交/已批），1 条带回执通知——演示"不用群里追"的完整闭环。

## P2 · 团队项目管理工作台（项目经理 / 团队 Leader）

**一句话 pitch**：带团队的人终于不用开早会了——团队共用一个项目管理工具，流程进展清晰透明。

**触发画像**：项目经理、组长、创业者提到"早会/站会流于形式 / 进展不透明 / 任务靠嘴跟"。

| 角色 | 权限 |
|------|------|
| Leader（admin） | 全部项目+任务+成员管理+一键生成日报 |
| 成员（member） | 任务看板、更新自己任务状态、看团队进展 |

**实体映射**：projects 项目（名称/负责人/风险/起止）· tasks 任务（项目/标题/负责人/状态 todo-进行-评审-阻塞/优先级/截止）· standups 每日进展（成员/今日完成/明日计划/阻塞）· milestones 里程碑。

**视图**：项目时间线 · 任务看板（按状态列）· 团队进展（今日全员 standup 聚合，替代早会）· 里程碑。

**权限要点**：进展视图全员可见（透明是卖点）；任务改状态任何成员可做但只能改自己的（服务端校验 owner）。

**种子建议**：1 leader + 3 成员，2 个项目（1 高风险）、12 条不同状态任务、今日 3 条 standup——打开就能看到"早会替代品"的样子。

## P3 · 达人合作管理工作台（品牌方 / 广告投放）

**一句话 pitch**：对接三十个达人的人终于有救了——搭一个让每个合作方互相隔离、统一管理的工作台。

**触发画像**：品牌投放、媒介、MCN 提到"达人太多管不过来 / 报价要保密 / 交付靠微信催"。

| 角色 | 权限 |
|------|------|
| 品牌 admin | 全部达人、合作单、比价、排期、结算，管理账号 |
| 投放运营（member） | 合作单+达人管理（可授权） |
| 达人（外部 guest 账号） | **只看自己名下**的合作单/需求单，上传交付物 |

**实体映射**：partners 达人（昵称/平台/报价/档期）· campaigns 合作单（达人/内容形式/报价/状态 洽谈-签约-制作-发布-结算）· briefs 需求单（campaign_id/要点/素材）· deliverables 交付（campaign_id/链接/审核状态）。

**视图**：达人总表（内部）· 合作看板（内部）· 需求与交付（达人登录后只见 campaign.owner = 自己的行）· 结算台账（admin only）。

**权限要点**：**行级隔离是本方案核心**——达人账号读 campaigns/deliverables 必须服务端加 `partner_id = me`；报价字段对非 admin 的达人视图直接不返回（SELECT 白名单）。

**种子建议**：1 admin + 1 运营 + 3 达人演示号，5 张不同阶段合作单（每达人 1-2 张），交付物含待审/已过——演示"互相看不见、管理者全看见"。

## P4 · 甲方审稿工作台（设计师 / 文案 / 乙方）

**一句话 pitch**：做了一个甲方可以直接评论意见的页面，不用每次电话沟通细节——你问需求才能有的放矢。

**触发画像**：设计工作室、文案、律师、代理公司提到"改稿来回发微信 / 意见没有留痕 / 甲方口头需求"。

| 角色 | 权限 |
|------|------|
| 乙方 admin | 全部项目/版本/评论，确认管理，客户账号管理 |
| 乙方成员（member） | 本方项目协作 |
| 甲方（client 外部账号） | **只看自己项目**的最新稿、逐条评论、一键确认验收 |

**实体映射**：projects 项目（甲方名/类型/状态）· versions 版本（project_id/版本号/链接或图/说明）· comments 评论（version_id/甲方/逐条意见/位置标注文本）· confirmations 确认单（version_id/甲方/时间/签字名，留痕即证据）。

**视图**：项目列表（乙方）· 版本管理（乙方，含内部备注——甲方不可见）· 审稿页（甲方：最新版本+历史评论+确认按钮）· 确认台账（admin）。

**权限要点**：versions 的 `internal_note` 列对甲方请求直接从 SELECT 剔除；确认单只能由 client 角色本人创建（服务端校验角色），构成有效留痕。

**种子建议**：1 乙方 admin + 2 甲方演示号，2 个项目各 2-3 版，评论含"改标题/换配色"这类真实颗粒度，1 条已确认记录——演示"电话沟通被页面评论替代"。

## 预置匹配规则

1. 用户描述先与四条 pitch 的画像关键词比对（教育/作业→P1，团队/任务/站会→P2，达人/投放/合作方→P3，甲方/改稿/乙方→P4）
2. 命中：出示对应 pitch + 设计契约，AskUserQuestion 只确认 1 项（真实数据 or 演示数据），即开工
3. 部分命中：以最接近的预置为骨架，指出差异点（如 P3 加"比价统计视图"），走一轮标准四问补齐
4. 未命中：走通用四问；引导时可引用四条 pitch 的句式（"XX 的人终于不用 YY 了"）帮用户描述自己的场景
5. 新场景沉淀：做完非预置工作台后，若画像足够典型（出现第二次即沉淀为新预置条目）
