# Structured Longform Writing Workflow

此文件定义结构化长文创作的详细执行流程。它用于补充 `SKILL.md`，避免 Agent 直接进入一次性正文生成。

## 1. Overall workflow

执行顺序：

1. Classify task：判断文档类型和主要用途。
2. Infer audience：推断目标读者。
3. Infer document goal：判断文档要让读者理解、相信、决策还是行动。
4. Create writing brief：形成内部写作 brief。
5. Create outline：设计服务目标的大纲。
6. Gather evidence：整理用户材料、事实、数据、案例和待补充信息。
7. Draft section by section：逐节展开正文。
8. Review：按质量标准检查。
9. Revise：必要时重排结构或重写段落。
10. Deliver final：输出最终稿，必要时附关键假设和待补充材料。

## 2. Task classification rules

### Blog

用户意图通常是传播观点、解释概念、输出经验、形成技术或产品洞察。常见表达包括“写一篇博客”“写一篇文章”“技术博客”“公众号文章”“经验总结”“观点文章”。

默认目标：让读者读懂一个观点，并获得可迁移的理解或方法。

### Report

用户意图通常是分析现状、调研问题、比较对象、形成结论和建议。常见表达包括“报告”“分析报告”“调研报告”“竞品分析”“现状分析”“总结一下并给建议”。

默认目标：把事实和材料组织成判断，支持后续决策。

### Proposal or plan

用户意图通常是提出建设方案、落地计划、项目规划或执行路径。常见表达包括“方案”“建设方案”“规划”“落地计划”“实施方案”“改进方案”。

默认目标：让读者理解为什么做、做什么、怎么做、怎么验收。

### PRD

用户意图通常是产品需求定义。常见表达包括“PRD”“产品需求文档”“需求说明”“功能设计”。

默认目标：让产品、设计、研发、测试能围绕同一需求执行。

### Competitive analysis

如果用户强调竞品、对比、行业实践、借鉴经验，归类为 `competitive_analysis`。若最终希望输出建议，整体可按 report 结构执行，并增加横向对比维度。

### Technical design

如果用户强调技术架构、模块、接口、流程、系统实现、工程方案，归类为 `technical_design`。若最终要落地建设，整体可按 proposal 结构执行，并增加架构和风险章节。

### Internal briefing

如果用户强调“给老板看”“内部评审”“汇报材料”“管理层”，归类为 `internal_briefing`。根据目标再套用 report 或 proposal 的核心结构。

## 3. Audience inference

当用户没有明确说明受众时，按上下文推断。

### 老板或管理层

关注背景、问题、判断、取舍、风险、收益、资源需求和下一步。写法应结论前置，避免过多技术细节。

### 产品经理

关注用户问题、场景、目标、方案边界、优先级、指标、上线节奏和风险。

### 技术人员

关注约束、架构、实现路径、模块拆分、接口、性能、稳定性、安全和可维护性。

### 客户

关注价值、场景、效果、实施成本、风险控制和服务承诺。避免内部术语过多。

### 普通读者

关注可理解性、故事线、例子、类比和实用收获。避免组织内部黑话。

### 混合受众

优先采用分层结构：摘要给决策者，正文给执行者，附录给需要细节的人。

## 4. Writing brief schema

内部 brief 建议使用以下字段。除非用户要求，不需要把完整 brief 输出给用户。

```yaml
document_type: blog | report | proposal_or_plan | prd | competitive_analysis | technical_design | internal_briefing | other_longform
audience: 目标读者
purpose: 写作目的
reader_action: 希望读者读完后采取的行动
core_message: 中心观点或核心判断
source_materials: 用户提供的材料
assumptions: 合理假设
constraints: 篇幅、风格、语言、格式、禁止项
required_sections: 必须出现的章节
evidence_needs: 需要事实、数据、案例或引用支持的地方
risks: 内容风险、事实风险、落地风险
```

## 5. Outline rules

1. 大纲必须先服务目标，而不是机械套模板。
2. 每个一级标题必须承担一个明确功能，例如交代背景、定义问题、给出分析、提出方案、说明风险。
3. 不要把相同内容拆成多个重复章节。
4. 管理层文档应结论前置。
5. 技术文档应先讲约束和设计目标，再讲模块和实现。
6. 博客应有明确问题意识，不要从空泛定义开始。
7. 报告应包含分析框架和关键发现。
8. 方案应包含路径、里程碑、风险和验收标准。

## 6. Evidence handling

1. 用户提供材料优先于模型一般知识。
2. 未提供事实依据时，不得编造具体数据、引用、公司案例、用户反馈比例或实验结果。
3. 可以使用“待补充数据点”提示用户后续补充。
4. 必须区分事实、判断和推测。
5. 如果事实不足，使用谨慎表达，例如“基于当前材料可以判断”“从问题表现看，可能存在”。
6. 需要外部来源且工具可用时，应先检索或读取资料，再写结论。
7. 不确定的信息不要写成确定事实。

## 7. Drafting rules

1. 逐节展开，不要把全部内容堆成一个长段落。
2. 段落之间要有逻辑推进：背景引出问题，问题引出分析，分析引出方案，方案引出风险和验收。
3. 避免空话套话，尤其是没有对象和机制的价值词。
4. 报告要有分析和判断，不只是信息罗列。
5. 方案要有落地路径，不只是愿景。
6. 博客要有观点和可读性，不只是说明书。
7. 需要对比时使用表格，但表格不要替代关键判断。
8. 需要展示流程时可以使用步骤列表或 Mermaid 图，但不要过度使用。

## 8. Revision rules

审稿时优先检查高层问题，再检查语言问题。

高层问题：

- 是否回应了用户真正的问题。
- 是否有中心观点或核心结论。
- 是否存在结构缺口。
- 是否有事实风险。
- 是否对目标读者有用。

语言问题：

- 是否重复。
- 是否空泛。
- 是否标题过度对称。
- 是否段落太长。
- 是否出现过多“首先、其次、最后”。

必要时重排结构或重写章节，而不仅是替换词语。

## 9. Delivery modes

### 默认：最终稿模式

当用户直接要求“写一篇”“生成一份”“帮我写”时，默认输出最终稿。

### 大纲优先模式

当信息严重不足、文档复杂度高、用户强调“先规划”或“帮我设计结构”时，先输出大纲或写作方案。

### Brief 确认模式

当文档用于重要评审、对外发布、合同、法律、医疗、财务等高风险场景时，先输出 brief 并提示需要确认关键信息。

### 多版本模式

当用户要求多个风格或多个角度时，输出多个版本，每个版本必须说明适用场景和取舍。
