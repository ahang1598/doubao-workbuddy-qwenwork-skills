# Proposal and Plan Template

用于建设方案、实施方案、产品方案、技术方案、项目规划、改进方案、策略方案等文档。

## 适用场景

- 用户需要提出一套可执行方案。
- 用户需要内部评审材料。
- 用户需要说明背景、目标、范围、实施路径、风险和验收标准。
- 用户希望让团队围绕一个计划行动。

## 不适用场景

- 只需要问题分析，不需要行动方案。
- 只需要博客或观点文章。
- 没有明确目标且无法合理假设的场景。

## 默认结构

```text
1. 方案摘要：一句话说明要解决什么、怎么解决、预期结果
2. 背景：为什么现在要做
3. 现状与问题：当前有哪些痛点和约束
4. 建设目标：要达成什么，可衡量则给出衡量方式
5. 范围与边界：本期做什么，不做什么
6. 方案设计：核心思路、模块、流程
7. 实施路径：阶段、任务、责任或依赖
8. 里程碑：关键节点和交付物
9. 验收标准：如何判断方案成功
10. 风险与应对：风险、影响、缓解措施
11. 预期收益：用具体机制说明收益
12. 下一步：近期动作
```

## 可选结构

### 产品方案

```text
1. 用户问题
2. 目标用户和场景
3. 产品目标
4. 功能范围
5. 用户流程
6. 关键能力
7. 指标和验收
8. 迭代计划
```

### 技术建设方案

```text
1. 背景和技术目标
2. 当前架构或能力现状
3. 设计原则
4. 总体架构
5. 核心模块
6. 数据流或调用链路
7. 兼容性和安全
8. 实施计划
9. 风险和回滚
10. 验收标准
```

### 改进方案

```text
1. 问题现象
2. 影响
3. 根因判断
4. 改进目标
5. 改进动作
6. 优先级
7. 节奏安排
8. 验收方式
```

## 写作策略

1. 不要直接上方案，先定义问题和目标。
2. 目标应尽量可衡量；没有数据时说明可采用的衡量方式。
3. 范围和边界必须清楚，避免方案无限扩张。
4. 方案设计要包含机制，而不是只写价值词。
5. 实施路径应有阶段、动作和交付物。
6. 风险必须与方案相关，不能泛泛列“资源不足、时间紧”。
7. 验收标准要能被检查。
8. 预期收益要说明来源，例如“通过大纲和质量门减少返工”，而不是只写“提升效率”。

## 常见失败模式

- 只有愿景，没有执行路径。
- 目标不可衡量。
- 方案模块名称很多，但不知道如何落地。
- 风险和应对非常泛泛。
- 预期收益都是口号。
- 没有说明本期不做什么。
- 没有验收标准。

## 输出前检查清单

- 是否说明背景和当前问题。
- 是否有明确建设目标。
- 是否定义范围和边界。
- 是否有核心方案设计。
- 是否有实施路径和里程碑。
- 是否有风险与应对。
- 是否有可检查的验收标准。
- 是否避免编造数据。
- 是否能让团队据此行动。

## 简短示例大纲

主题：《QoderWork结构化长文创作 Skill 建设方案》

```text
1. 方案摘要
2. 建设背景：长文生成效果不稳定
3. 现状问题：一次性生成缺少规划、证据、审稿
4. 建设目标：提升结构完整性、可落地性、事实安全
5. MVP 范围：博客、报告、方案
6. Skill 设计：SKILL.md、workflow、模板、rubric、反 AI 味指南
7. Agent 流程：分类、brief、大纲、正文、review、最终稿
8. 落地计划：本地 Skill、样例验收、真实 bad case 回归
9. 验收标准：触发准确率、样例评分、事实安全
10. 风险与应对
11. 下一步
```
