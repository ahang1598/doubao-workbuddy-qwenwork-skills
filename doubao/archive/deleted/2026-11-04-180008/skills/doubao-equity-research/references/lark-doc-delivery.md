# 飞书文档交付规范

本文件只规定股票研究的交付路由、信息结构和组件选择。正文准入、表达和删稿遵循 `writing-quality.md`。命令、XML 标签和参数以执行时线上环境中的最新版 `lark-doc` skill 为准。

需要股价图、K 线、象限图、敏感性热力图、瀑布图等高级金融视觉时，同时读取 `advanced-lark-visuals.md`。

## 1. 先设置 delivery_mode

在任何检索、分析、起草或图表生成前锁定模式并运行计划门禁。默认使用 `LARK_DOC`；仅当 query 明确适合用一至三句无损回答一个事实、口径或决策问题，且无需结构化比较、导航、情景、复杂证据链、图示或非 Markdown 高级组件时，使用 `TEXT`。无法确定、用户要求飞书文档或上述任一条件不满足时，使用 `LARK_DOC`。

query 很短或未显式要求文档，不足以选择 `TEXT`。用户明确限制为纯文本时，也只有满足短回答条件才能使用 `TEXT`；否则说明载体冲突并请求取舍。

`TEXT` 不得生成 HTML block、分栏、高亮块或富样式表格；条件失效或已生成高级组件时，立即单向升级为 `LARK_DOC`。不得因耗时、命令、认证或权限问题降级；失败时保持未完成并报告最小阻塞信息。

### 状态生命周期

`LARK_DOC` 不只是最终输出格式，而是贯穿任务的交付状态：

1. **Plan**：建立交付清单，锁定 `delivery_mode`，运行计划门禁；
2. **Preflight**：读取线上最新版 `lark-doc`，检查认证/权限和本次所需语法；
3. **Skeleton**：在完整正文起草或高级组件生成前列出 `required_sections` 并创建文档骨架，先放标题、元信息、核心结论、核心金融与财务快照及本次必需分析章节的占位结构；
4. **Build**：完成分析，将保留的正文和组件写入文档；
5. **Verify**：拉取文档复核结构、内容和组件渲染；
6. **Final**：更新交付清单并运行最终门禁，通过后才返回核心结论与文档链接。

## 2. 写入前的线上校验门禁

每次最终执行 `docs +create`、`docs +update` 或其他文档写入前，必须：

1. 读取当前线上运行环境中可用的最新版 `lark-doc` skill 的 `SKILL.md`，不得用记忆、本文件或打包时的本地版本替代；
2. 按最新版 `lark-doc` 的前置条件，继续完整读取本次创建或编辑所要求的共享规则、XML、样式、创建/更新工作流等引用文件；
3. 计划使用 HTML block 时，再读取最新版 skill 指定的扩展块说明；
4. 以线上文档为唯一命令和语法依据。若与本文件示意冲突，线上 `lark-doc` 优先；
5. 先完成事实校验和文档大纲，再写入，避免把未经核验的草稿发布到在线文档。

未完成上述读取时，不得尝试写入。这个门禁每次写文档都执行，不能因为同一会话中曾经用过旧命令就跳过。

## 3. 专业研究文档的信息顺序

默认按读者决策顺序组织，不套固定的“公司简介—行业—财务”模板：

1. **标题与研究元信息**：证券名称/代码、市场、信息截止日、币种、会计或价格口径；
2. **核心结论**：先直接回答用户问题，说明方向、最关键原因、判断边界与最大风险；
3. **核心金融与财务快照**：分析具体证券、公司、板块、股票池或组合时，按 `core-financial-snapshot.md` 用一张紧凑表格列 4–10 个最重要字段；确实不相关时才省略；
4. **决定结论的证据**：核心结论区通常 3–5 条，按影响判断的重要性排序；
5. **主体分析**：只展开用户问题需要的行业、商业模式、基本面、预期、估值或价格归因；
6. **最强反证与证伪条件**：不要把风险降格成页尾泛泛清单；
7. **验证点/催化剂**：写清指标、阈值、时间窗和数据来源；
8. **数据来源与方法**：读者可复核即可，冗长细节放附录；
9. **免责声明**：完整研究报告最后保留规定文本。

骨架阶段读取 `suggested-writing-templates.md`，按体裁选择一个主模板并裁剪栏目；跨体裁任务只嵌入必要模块。模板只帮助组织通过准入门槛的内容，不替代能力选择，不要求填满，也不得覆盖 `required_sections` 所代表的真实分析需要。

核心结论必须出现在正文最前部。若使用高亮块，全文通常只把这一处作为唯一重强调；若核心判断不确定，明确写出数据缺口或条件，不用颜色制造虚假的确定感。

### 信息密度门禁

大纲只列会改变用户判断的章节。检索笔记、覆盖矩阵结果和候选新闻属于工作材料，不自动进入文档。写正文前按 `writing-quality.md` 逐项筛选；证据弱、时点不明、没有传导机制、与前文重复或只提供背景的信息不得发布。

正文采用“结论 → 最少充分证据 → 含义/验证点”。一段只证明一个判断；一张表或图只回答一个问题。不要把同一结论同时写进高亮块、段落、表格和图注。信息不足时主动缩短报告，不使用更多栏目、背景或样式填充篇幅。

### 复杂结构的篇幅控制

在骨架阶段把用户问题与分析链所需章节写入 `required_sections`。复杂文档应通过节内压缩、紧凑表格、删除弱证据及把审计细节移到附录来控制篇幅；不得仅因为文档较长而删除或合并承担不同逻辑功能的章节。最终拉取后，把实际一级/二级结构写入 `actual_sections`，逐项确认包含所有 `required_sections`。

## 4. 组件选择矩阵

由信息关系选择组件，不按“每篇都要有”的配额选择。

| 研究内容 | 首选表达 | 适用边界 |
|---|---|---|
| 核心结论、重大口径提醒、关键数据缺口 | 高亮块 | 仅强提醒；通常 0–1 个，避免每节一个 |
| 多空逻辑、结论与反证、公司 A 与 B 的短对照 | 对比分栏 | 两侧信息量接近且内容短；有多指标时改用表格 |
| 财务趋势、分部、同业、估值、情景、事件窗口 | 表格 | 真正行列数据；统一期间、币种、单位和口径 |
| 产业链、盈利驱动树、因果传导、风险链路 | 传导链 HTML block | 仅用于少量按阅读顺序排列的节点；图旁保留一句可独立理解的结论 |
| 双轴定位、同业分层、候选优先级、风险重要性 | 多象限 HTML block | 两个维度、刻度和分割阈值必须可解释；不代替原始数据表 |
| 单股价格路径、涨跌归因、量价和事件窗口 | 脚本生成的 K 线或股价 HTML block | 完整同口径 OHLC 使用 K 线；仅有可靠收盘价/分时价时使用股价图。注明复权、币种、时区、窗口和来源，仅按 `advanced-lark-visuals.md` 明确例外退出 |
| KPI、盈利预期、估值或折溢价的可比趋势 | 趋势 HTML block | 1–5 组同期间、同单位、同口径序列；少量精确数字用表格 |
| 盈利、现金流、指引或估值桥接 | 瀑布 HTML block | 起终点和桥接项可复算；只保留重要驱动 |
| 两变量敏感性矩阵 | 热力图 HTML block | 基准格、单位和数值必须可见；小矩阵用表格 |
| 催化剂、监管与事件时序 | 时间线 HTML block | 只保留重要节点，区分发生/公布/可交易日 |
| 其他交互趋势和信息密集视图 | HTML block | 表格不足时使用；不要只为装饰创建 |
| 公式与关键假设 | 公式或简洁段落 | 展示可复算的关键公式，不把整篇写成方法论文 |
| 叙述、机制、判断与解释 | 连贯段落 | 默认表达；不要机械拆成 bullet 或卡片 |
| 来源、公告、监管文件 | 可点击引用/来源列表 | 来源紧随事实，并保留发布日期和截止日 |

### 高亮块

适合放“结论 + 关键条件 + 最大风险”的短摘要，不要把完整正文塞入。颜色保持语义一致：信息用中性/蓝色，风险用红色，待确认用黄色；不要用绿色或红色暗示无条件买卖建议。

### 对比分栏

适合以下短对照：

- 支持核心判断的证据 vs 最强反证；
- 牛方逻辑 vs 熊方逻辑；
- 现状 vs 触发重新评估的条件。

若每侧超过少量要点、需要跨行比较或含多期数值，改用表格。分栏不能替代三情景估值表。

### 表格

一张表只回答一个问题。表头写明期间，标题或注释写明币种、单位、是否复权、FY/CY/TTM、法定/调整后。重要变化优先展示绝对值与同比/环比，避免只用颜色表达涨跌。典型表格包括：

- 核心 KPI 与盈利桥；
- 同业经营和估值比较；
- Bull/Base/Bear 情景、关键假设、估值结果与触发条件；
- 催化剂/风险的时间、概率依据、影响路径与验证指标；
- 股价事件窗口与基准相对表现。

### 结构型 HTML block

结构关系只有在图示明显比段落更快回答问题时才使用 HTML：

- 少量节点的 `行业变量 → 业务量价 → 利润率/现金流 → 预期修正 → 估值` 传导链；
- 简洁价值链、盈利驱动、证据树或证伪路径；
- 风险传播或组合暴露链；
- 两个清晰维度上的同业、候选或风险项目定位。

传导链使用 `lark_charts.py flow`，象限使用 `lark_visuals.py quadrant`。精确数字回到正文表格；超过生成器节点上限、分支复杂或需要大量说明时，改用分节段落和表格。

### HTML block

仅当交互或高密度可视化有实质价值时使用，例如带悬停明细和事件标记的 K 线、可切换期间的 KPI 图、估值敏感性热力图、价格—盈利预期联动图或组合风险面板。遵守最新版 `lark-doc` 对单文件、尺寸、资源和运行时的限制，并满足：

- 先由既有脚本生成单文件 HTML 中间载荷，再按最新版 `lark-doc` 流程将其实际写入目标飞书文档的 HTML block；不得手写 HTML，不得把生成文件作为附件或交付物；
- HTML block 前后各有一段文本，说明它回答的问题和读者应看到的结论；
- 关键结论不能只存在于交互组件内；
- 不内联大体积数据或图片，不把同一张表再做一遍 HTML；
- K 线只使用完整、严格升序、同一复权口径的 OHLC；只有收盘价时运行 `lark_visuals.py price`，不得手写图表 HTML 或补造 OHLC；
- 若静态表格足够，优先表格。

## 5. 体裁模板路由

按 `suggested-writing-templates.md` 的路由表选择一页纸、完整个股研究、财报前瞻、财报解读、模型更新、盈利预测修正、非共识、差异认知识别、估值、反向 DCF、股价归因、行业、同业比较、股票筛选、市场晨报、收盘复盘、市场周报、组合风险、论点跟踪或 A/H 相对价值模板。使用通用完整报告外壳确保元信息、核心结论、金融快照、反证、验证、来源和免责声明完整，再用主模板组织主体分析。跨体裁任务只嵌入必要模块，不拼接多份完整报告。

## 6. 写入与校验

1. `LARK_DOC` 先按线上 `lark-doc` 最新工作流完成 preflight，锁定 `required_sections` 并创建文档骨架，再准备核心结论、核心金融与财务快照、通过准入门槛的事实表和最小充分正文；复杂引用按 `script-usage.md` 运行 `report_pipeline.py --format lark-xml`；
2. 长报告顺序分节写入，避免超长一次性写入；
3. 完成全部正文与组件写入后，重新拉取最终文档，复核整体顺序、引用、表格口径、图表渲染和免责声明；逐项核对聊天摘要、正文、表格、图表与附录中的关键数据，统一对象、期间、币种、单位和口径；股价图/K 线要实际检查悬停、坐标、涨跌配色、基准/均线、成交量和事件标记，其他 HTML 图表要检查轴、节点、数值、响应式尺寸和标签碰撞；
4. 按 `writing-quality.md` 完成独立删稿，删除低质量信息、重复标题、重复结论、重复图表、泛泛背景和不改变判断的段落；压缩节内表达，但保留 `required_sections` 中承担独立分析功能的结构。若因此修改文档，写回后再次拉取确认；
5. 检查任何颜色、高亮、分栏、表格和 HTML block 是否真的提升理解；不能说明价值就移除；
6. 最终拉取后的 `actual_sections` 必须覆盖全部 `required_sections`，并将十项 `quality_checks`（含逻辑链、读者导航、会计口径和 `required_structure_preserved`）全部确认；若存在高级视觉，再逐一填写唯一 `visual_purposes` 并确认四项 `visual_checks`；
7. 更新交付清单，运行 `delivery_gate.py --phase final`；
8. 门禁通过后，在聊天中返回一至三句核心结论和文档链接，不把文档全文再复制一遍。

## 7. 最终交付门禁（必须执行）

在发送最终回复前，盘点本次已经生成的正文和中间产物，更新交付清单，并运行 `scripts/delivery_gate.py --phase final <manifest.json>`。以下任一项存在，即判定为“已生成非 Markdown 高级样式”：

- HTML block 或其单文件 HTML；
- `<grid>` 分栏、`<callout>` 高亮块、交互组件；
- 使用单元格底色、合并单元格、复杂列宽等 Markdown 无法保真的富表格；
- 其他若转成 Markdown 会丢失关键信息关系、交互或视觉编码的组件。

若盘点结果为“是”，交付清单中的 `delivery_mode` 必须是 `LARK_DOC`，并完成以下闭环：

1. 按第 2 节重新读取线上最新版 `lark-doc` 及本次写入所需引用文件；
2. 创建或更新飞书文档，把主要分析和所有保留的高级组件实际写入；
3. 最后一次写入后重新拉取文档，确认组件存在、顺序正确、渲染可用、核心结论位于最前，且 `actual_sections` 覆盖全部 `required_sections`；若复核后修改，必须再次拉取；
4. 完成结构审阅、口径复核和删稿并确认十项写作质量检查，控制篇幅时不得丢失必需结构；
5. 为每个保留视觉确认独立问题、来源单位、无重复编码和实际渲染；
6. 若存在 HTML block，确认 `html_block_checks.embedded_in_lark_document=true` 和 `html_block_checks.source_file_not_delivered=true`；
7. 最终聊天回复只给一至三句核心结论和可访问的飞书文档链接。

所有模式还必须在最终交付前完成数据对账，并将 `data_consistency_verified` 设为 `true`：对齐聊天摘要、正文、表格、图表、附录及其他交付物中的对象、期间、币种、单位和口径；同一指标不得保留互相矛盾的数值。发现冲突时先核对定义，确认同口径后按“权威来源优先、权威性相当时最新数据优先”选定采用值，从上游修正所有相关产物并重新检查；无法消除的差异必须明确标注口径和取舍理由，不得写成两个并列的确定事实。

以下均不算完成：直接发送 `.html`、`.xml`、PNG 预览或其他本地文件；粘贴 HTML/XML 源码；只描述“可写入飞书”；只给本地路径；生成高级组件后又用 Markdown 摘要代替文档。

若认证、权限、组件写入或文档创建失败，任务仍处于未完成状态，最终门禁也不得通过。只向用户说明完成飞书写入所需的最小阻塞信息并按 `lark-doc` 流程处理；不得把分析正文或高级素材作为替代性交付。只有文档成功写入、取得可访问链接并拉取复核后，才能把任务表述为已完成。

交付前最终自检：最后一次写入后是否重新拉取；结论是否最先出现；核心金融与财务快照是否已纳入或有合格的不相关理由；每节是否改变判断；低质量和重复信息是否删除；事实/公司表述/一致预期/作者推断是否区分；日期、币种、单位和口径是否完整；跨产物数据是否一致且冲突已按权威性、再按时点处理；最强反证是否公平；来源是否可点开；组件是否克制且渲染正常；`actual_sections` 是否覆盖 `required_sections`；篇幅是否通过压缩内容而非破坏结构来控制；若存在非 Markdown 高级样式，飞书文档是否已实际创建、复核并取得可访问链接。
