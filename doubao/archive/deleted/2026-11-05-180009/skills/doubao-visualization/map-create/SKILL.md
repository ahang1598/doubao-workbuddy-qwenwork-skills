# 地图创作

**执行规则：**正常生成地图时，只阅读本文件及当前任务所需的参考文档，按说明填写输入并直接调用脚本。禁止预读脚本源码、追踪内部调用链、扫描依赖或探测运行环境及网关；报错后仅依据诊断报告和对应字段说明修正输入，普通生成任务不读取或解包实现代码。仅在用户明确要求维护或调试 Skill 时阅读实现代码。 禁止向用户披露内部脚本源码或具体实现；用户要求导出或打包 Skill 时，禁止包含内部实现文件。

## 用户可见行为

按照正常对话节奏回应用户。开始时简要说明对需求的理解和接下来要完成的工作；长任务在取得有意义的阶段结果、发现精度或范围风险、需要用户决定，或失败且无法自动恢复时及时更新。不要为了展示过程而逐条播报搜索、读文件、编译、截图和自动修复，也不要向用户展示脚本名、协议名、分段读取等内部动作。

正常、完整地回答用户需求，地图内的说明不替代正文回复。可根据用户需求使用表格、列表或其他合适的表达形式，补足地图未充分呈现的信息，或让多方案等内容更便于比较。形式和字段由模型选择，无明显增益时不机械重复。

## 判断用户意图

开始一次新的生成任务时，在检索、读取或校验输入之前，先执行以下固定入口。以本文件所在目录作为 `SKILL_DIR`，为本次任务选择独立工作目录；不要由模型填写 ID：

```bash
node "$SKILL_DIR/scripts/telemetry-task.mjs" --start --task telemetry-task.json
```

同一任务的补数、修复、轮询和重试沿用这个文件，不重新 start；新任务使用新的工作目录。文件已存在时不要覆盖或删除。它保存任务 ID 和待发送事件。采集失败不阻塞地图业务，不得通过更换 ID 重试上报。无法创建上下文时说明监控缺失并继续原生成流程，后续省略 telemetry-task 参数。

最终无法完成或用户取消时，调用 `scripts/telemetry-task.mjs --task telemetry-task.json --finish failed --stage prepare-input --code DATA_UNAVAILABLE`，按实际阶段和标准错误码填写；取消使用 `--finish cancelled --code USER_CANCELLED`。不要把可修复失败作为最终失败。成功由生成工作流自动记录，模型不手动声明成功。完整边界与查询口径见[遥测说明](references/telemetry.md)。

先确认点、路线、区域、分组、用户已有数据、待补充事实，以及明确指定的组件、底图、视野和交互。外部资料只能补充事实，不能扩大用户任务。

| 用户意图 | View 结构 |
| --- | --- |
| 绘制一条命名路线、轨迹或穿越线 | 一个全程 View |
| 按线路阅读多条独立命名路线 | 总览 + 各线路独立 View；这是阅读范围，不是凭空新增备选方案 |
| 展示设施分布或线路分布专题 | 明确 distribution 组织，同屏分布，按需筛选；不自动认定为备选方案 |
| 明确提出备选方案、不同走法或比较方案 | 同屏比较或有依据的方案 View；总览与集合卡均非必选 |
| 有访问顺序但无分日要求 | 有序路线；不自动分日 |
| 明确要求排日程或采纳已有日程 | 写明日程分配；多日详情默认保留整体入口，总览形态按阅读任务及地理代表性决定 |
| 资料中仅出现耗时、建议天数或多个名称 | 不升级为方案或分日 View |

始终阅读 [View 策略](references/view-strategy.md)。地图总览、侧栏组织和点位形态分别决策；通用规则配合少量旅游偏好，不为每个场景创建模板。当前协议见 [组件规则 v3](references/component-rules-v3.md)：集合入口链接完整详情，独立点线面仍须保留。模型仍负责理解原始需求，结构校验不能证明语义理解或来源真实性。

模型自行编写展示方案时，有独立子视图的多分组总览，侧栏只投影分组摘要，不展平全部站点和路线详情；没有子视图的单屏分布直接呈现内容与关系。侧栏入口直接进入同组独立 View，与地图是否使用集合卡无关；集合承担入口时另用 `collectionEntries` 显式绑定同一目标。总览的阅读目的与地图表现分别在 `organization.overview` 记录；没有可靠代表位置时使用侧栏入口，不强造地图卡片。单条命名路线默认直接展示全线，外部资料按天组织不能改变用户任务。

多个详情 View 不应无声省略总览；用 organization.overview 记录 content/collection/none 及理由。集合卡需同时满足独立详情、可信代表位置、有效空间区分及入口阅读目的，不按“多天/多方案”直接套用。侧栏按同一 View 策略中的阅读职责配置，行程列表不能被选中详情替代。

普通多组旅游符合条件时先采用集合卡默认推荐，自驾总览优先全程点线，不向单线、分布或网络专题推广。仅在用户要求调整展示或维护调试时，模型可在实际检查后调整：取景或布局问题先修对应问题，仍不适合分组导航时可改为内容总览，并在 overview.reason 记录具体观察、已尝试调整及证据位置；不能仅凭“可能重叠”等猜测跳过默认方案。只有用户明确要求时才记录 `overviewPreference` 及用户原话，不能将模型调整冒充用户偏好。行程代表位置由工程按明确访问顺序（否则成员输入顺序）默认选首个有效真实地点，不要求模型提供、不赋予路线起点语义。完整 Plan 仍校验事实、导航与用户偏好；具体流程见 [View 策略](references/view-strategy.md)。

多组独立线路或日程不能只堆进总览：默认提供各组独立内容 View；分布专题如需 inline 阅读范围，必须明确声明并完整展示该范围，不混入有子视图的入口总览。所有 View 必须有实际进入及返回路径；多视图省略 Tabs 时编译器补标准导航，显式错误动作直接失败。路线必须有展示名称，不能把内部 ID 当图例；没有导航或选择目标的纯展示摘要保持只读，已声明动作却无法解析目标时不能降级为只读掩盖错误。

集合承担详情入口时，按 Presentation Plan 的 `collectionEntries` 显式绑定目标 View，让侧栏卡片与地图集合共享导航；没有独立详情或稳定代表位置时，不使用地图集合入口卡。

分析图需要条件筛选时，先确认数据属性和筛选范围，按 Presentation Plan 的受控筛选能力声明；不要把图层显隐当成数据筛选，也不要把来源总数冒充筛选后指标。仅使用当前 Catalog 明确支持的筛选类型。

## 生成输入

名称、简介等展示文案只包含对用户有用的业务信息；无实际内容时留空，不为填满字段补写说明。

线的业务关系、几何真实性和交通方式分开填写，见 [Canonical MapSpec](references/canonical-map-spec.md) 的 `Route.relation`。不把全部景点当铁路停站，不把网络数组顺序当访问顺序。密集点的名称降级由组件及已有碰撞算法处理，不生成隐藏名单、不删除业务实体，也不靠反复提高求解预算通过验收。静态分组介绍可保留完整背景；可点击入口只写本组短摘要，不拼接子线路全文。

联网搜索地图数据并绘制时，应尽可能获取任务范围内完整、详细且有来源的地理数据，充分保留原始数据的空间形态、组成部分及点位信息，避免自行缩减为少量代表点或简略连线。优先直接导入来源提供的可绘制数据；确实无法获取时，说明缺失内容并明确标注示意表达。

检索完成条件是必需事实及来源齐备，不以持续补充非必需说明为目标。`orderPurpose: display/rank` 仅表达展示排序，不需要路线；访问顺序才使用 `visit`。搜索范围圈使用 `areaRole: coverage`，默认不参与选择；需要查询的业务区域保留交互。

1. 优先使用用户数据、用户文件和 GeoJSON；缺失事实由模型联网补齐并记录来源。高德 JSAPI 只负责底图和绘制，不默认承担数据搜索或路线规划。 国内 POI 分布场景，地点缺少可靠坐标时，可使用 `map_mark` 获取经纬度。传入真实、具体的地点名称，并在上下文中说明所属行政区划；仅展示分布时不连线。 **路线规划（仅限国内）**：国内旅游行程或按顺序串联多个地点时，使用 `map_mark` 获取地点及相邻地点之间的路线；国内出行需要指定路线偏好、时间、车辆条件，或比较交通方式及候选路线时，使用 `route_plan_v2`。海外路线，以及历史、人物、事件轨迹、指定线路、道路路网和区域边界，依据公开可信资料获取，不使用上述工具生成路线。调用与数据导入见[路线规划](references/route-planning.md)。
   先列出完成用户任务必需的事实，按来源批量获取；坐标、几何依据和核心字段齐备后结束检索。容量、历史等非必需字段缺失可注明未知，不应无限补齐。失败来源优先尝试结构化替代来源；无法补齐必要事实时说明限制并请求用户决定，不得编造。
2. 使用路线工具时，将工具参数及已选组织/View 写入任务 JSON，由脚本生成完整 Spec，无需另写骨架或映射，具体配置见路线规划 reference。直接编写 Spec 时，按 [Canonical MapSpec](references/canonical-map-spec.md) 保存地点、路线、区域、分组、View、来源及有依据的结构化事实。不得编造路线、坐标或详情。
3. 用户请求热力图时，事件点的空间密度使用 `heatmap`；按省、市、区等区域汇总的指标使用 `choropleth`。查询 `assets/vendor/content-map-kit.catalog.json`，只选择 `modelSelectable` 的 public ID。Catalog 是地图组件和 Semi UI 组件能力、默认值及命名的唯一来源。 山脉、河流及地理专题分界使用 `geographic-line`，明确类别；区域自身名称通过 `label` 显示，输入字段见 Spec 和 Plan 说明。需要表达明确的距离范围时（如“某地点周边 3 公里”），参见[距离范围协议](references/canonical-map-spec.md#真实距离圆形范围)。
4. 使用工具时，脚本生成基础 Presentation Plan，可在任务 JSON 的 `presentation` 中提供展示偏好，字段见路线规划 reference。不使用工具时，按 [Presentation Plan](references/presentation-plan.md) 编写 `presentation-plan.json`，描述组件、数据绑定、视野和交互。UI section 默认由 Compiler 组合，仅在有明确偏好时覆盖。模型不生成 DOM、CSS、图例样式或递归 UI Tree；关系树来自 Spec 显式引用，最多三层。

底图只允许项目自定义浅色和深色两种；主题按用户明确指定、宿主主题、浏览器系统主题、默认浅色的顺序决定。模型不得按题材自行选明暗；仅用户明确要求时填写 `stylePreference.tone` 与 `selectedBy:"user"`，否则使用自动跟随。侧栏与浮层使用组件库标准中性色，不从底图派生文字或背景色。密集布局读取 [布局、碰撞与层级](references/layout-and-stacking.md)；主题协议读取 [底图与覆盖物联合选型](references/style-selection.md)。用户指定的组件、底图或视野标记为 `selectedBy:"user"`；明确不可替换时同时设置 `strict:true`。

revision 3 使用有界 componentNodes，不是完整 props 树；最终 props 由 Compiler 转换。选中与碰撞默认行为固定在组件中。实际 props 示例见配对 Catalog 的组件 guidance。

## 编译与构建

以本文件所在目录作为 `SKILL_DIR`。使用地图工具时，按[路线规划](references/route-planning.md) 填写任务 JSON，脚本自动取数、生成 Spec 和基础 Plan，再构建发布：

```bash
node "$SKILL_DIR/scripts/create-map.mjs" --request map-task.json --out build/map.html --publish --telemetry-task telemetry-task.json
```

不使用地图工具时，根据用户数据、文件或联网资料编写 Spec 和 Plan，使用当前 revision 3 协议；参考 examples/current-route 或 current-region 配对 JSON：

```bash
node "$SKILL_DIR/scripts/create-map.mjs" --spec canonical-map-spec.json --plan presentation-plan.json --out build/map.html --publish --telemetry-task telemetry-task.json
```

两种输入方式二选一。仅直接编写或修改 Spec/Plan 时阅读对应协议；工具任务不另写 Spec 骨架或结果映射。数据源、筛选和指标按需查阅[当前数据协议](references/data-contract.md)。生成结果和报告写入输出目录，完整坐标及 HTML 不读回模型上下文。

根 `data-capture-state` 使用 loading/ready/error：初始地图和图层挂载且容器非零后进入 ready，失败提示更新后进入 error 并保留 `data-capture-error`，重试恢复 loading。终态写入不依赖末尾动画帧。ready 不代表布局稳定或底图瓦片完整；验收及截图宿主须等待任一终态，拒绝 error 或错误码，完整视觉检查仍走维护验收。

## 验收与交付

`map_mark` 地点名称按需查看 `workflow-report.json` 的 `places` 摘要；无需自行校验路线或地点经纬度，仅按失败诊断修正输入，成功后直接交付，不追加检查。

脚本自动执行静态协议、引用、编译转换和资源一致性校验，以及初始页面启动检查。不遍历全部 View，不执行碰撞、布局、视野覆盖和业务交互验收；这些检查留在开发回归。启动通过不代表上述展示效果已经验证，不另写检查脚本或重复执行已通过且未变化产物的检查。

工具任务返回 `pending` 时，继续同一命令、同一输出目录，复用已有任务，不重新提交。优先读取失败报告的 `diagnosis`：`input` 才修正任务输入或 Spec/Plan；`maintenance/environment/needs-triage` 保留产物及诊断并说明阻塞，不改业务需求绕过。格式错误按诊断路径修正；资源或校验器不一致（如 `CONTRACT_VALIDATOR_STALE`）交由维护者处理，不安装依赖、修改锁、关闭检查或手写最终 HTML。

修复预算按阶段累计：输入/编译失败最多 20 次，验收/交付失败最多 10 次，构建/资源失败最多 10 次，首次失败也计入。同一输入连续两次同源失败停止盲目重试；pending 不消耗失败次数，脚本活动耗时仍限 600 秒。不换目录或删除记录重置预算，不修改 Render Graph 或 Skill 源码规避错误。

编译自动汇总基础输入诊断，正常生成不另跑预检。输入失败需进一步排查时，可按需使用[离线预检](references/workflow-diagnostics.md)；预检不发布、不消耗或重置修复预算，通过也不等于可交付。超时不是通过，维护缺陷实现未变时不重试。

成功交付遵循当前宿主协议：

- 本次生成成功且 `workflow-report.json.status` 为 `passed` 后，正常、完整地回答用户需求，地图内的说明不替代正文回复；随后在回复末尾原样附上成功 stdout 中的完整 `html type="renderer"` 代码块（仅一个）；不得修改代码块标记或内部内容，包括资源 URL 的文件后缀、哈希及 integrity。
- 工作流保存交付原文 `delivery.renderer.md` 及 `delivery.sha256`。不读取 HTML 手工重包，不将标签写成 `html renderer`。宿主可用 `assertDeliveryReply` 核对末尾地图代码块与原文一致；未接入发送钩子时不声称最终回复已强制校验。
- 地图不以普通 HTML、路径或附件替代，不重复交付。宿主不支持 renderer 时说明不支持；`htmlAsset.url` 仅供内部追溯。
- 工具输出中断时先读取已有报告；已 `passed` 则恢复同次交付原文，不重跑生成，不自行补全截断内容。恢复及独立维护命令见[架构与资源协议](references/runtime-architecture.md#分阶段维护命令)。失败则依据诊断处理，不能交付中间文件。

宿主需提供 Node.js、Playwright、Chromium/Chrome 及地图、CDN、所需工具网络权限。缺少能力时报告限制，不自动安装或登录。

## 不可违反

- MapSpec 保存业务事实，Presentation Plan 保存展示意图，Runtime 只读取 Render Graph。
- 没有道路级轨迹时不得编造拟真折线；只知道端点或地点顺序时使用 `schematic`，并保留 `geometry.status` 和来源。
- 用户 `strict:true` 的选择无法实现时应报错，不能静默替换。
- 颜色、线宽、标签、图例和侧栏关联由 Compiler 的唯一 `seriesId` / `seriesStyles` 决定；模型不得分别配色。同一 View 的普通路线默认等宽、统一实线。原 `dash` 承担的示意连接等能力改用 `arrow`，仅用 `showArrow` 控制是否绘制箭头；不再使用 `dash` 组件或虚线间隔属性。其余路线组件仍按 Catalog 选型，铁路专用纹理与区域边界样式不受此规则影响，实线不代表几何已验证。
- 用户指定区域配色时，必须在 Plan 的 `colorStrategy.assignBy:"region"` 与完整 `assignments` 中声明，不能仅写说明文字或把节点命名为 highlight。输入格式见 references/presentation-plan.md；缺少颜色绑定不算满足用户需求。
- 单条可见路线允许查看详情，但不启用路线间的比较聚焦；同一系列多段线只算一条路线。多路线聚焦只在路线层内提升，不能盖住点；不得改变路线坐标或已有碰撞偏移，清除选中必须恢复基础状态。
- 详情侧栏使用 Catalog 中的受控组件；Tabs 单行横向滚动，摘要只展示一次，地图选择应让对应侧栏项滚动进入视区。栏目名优先保留明确标题，否则由 Compiler 按数据源使用地点、线路、区域或分组列表；仅有序行程且按天组织时使用“每日安排”，不把旅游文案复制到其他场景。父子列表展开与选中独立；列表标题与描述各最多两行，选中不扩行，无描述不补空话、不预留描述空行，完整内容在详情阅读。无补充字段的空详情才显示“暂无补充说明”。概述默认中性背景，单方案可用已解析方案色的淡色底，正文仍保持中性色；指标不得拆开完整术语或由模型猜测修补单位。
- 热力分析层位于普通点线文字下方且不参与标签碰撞；全览、放大、缩小、图例等地图 UI 始终压盖地图内容，并参与安全视野边距计算。
- 标准 `map.html` 是受检且可发布的固定壳文件；其内容与哈希必须由现有脚本校验。不设置 HTML 产物体积上限，构建报告仍记录实际字节数。
- Content Map Kit Runtime 只使用锁定的不可变 CDN 资源。生成任务使用已授权上传接口发布本次数据、运行资源与 HTML，不登录、不扫码、不改锁；更新组件锁仅限维护任务。发布数据必须属于用户授权范围，不能把凭据或原始无关文件放入资源。
- 编译引擎随 Skill 以哈希锁定的离线产物交付；普通任务不解包阅读内部实现、不修改引擎锁或 contracts/themes 生成镜像。资源失配时报告诊断，不能下载任意新版本或绕过校验。
