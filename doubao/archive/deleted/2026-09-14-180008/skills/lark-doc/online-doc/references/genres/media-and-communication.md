## Adapter 路由与子类型

本 Adapter 负责特定平台的内容组织与成稿呈现，包括标题、开头、叙事节奏、信息层次、图文关系、行动收束和视觉版式；用于交付微信公众号推文、小红书图文笔记、邮件、短视频口播稿、短视频分镜脚本，以及这些渠道的标题、封面文案和多版本标题库。它不放宽内容 contract 的事实、证据、合规和读者任务边界，也不处理平台运营方案、平台数据分析、媒介投放、账号定位或实际发布操作；前者按内容 contract 路由，后者切换对应平台或操作 Skill。

已命中内容 contract 时，先保留其任务、事实、证据与合规要求，再用本文件的平台内容规则组织成稿；未命中明确内容 contract 时，本文件的“平台内容与成稿共性原则”和对应子类型作为默认内容框架，但不得编造事实、数据、案例或承诺。命中子类型时，以对应子类型的成稿、视觉和 Block 规则为准；未命中任何子类型时，不套用其他渠道的封面、作者、编号、标签、称呼、镜头表或 emoji 规则。每份成稿只选择一个子类型；多渠道需求分别生成，不混写成同一篇成稿。

| 子类型 | 命中信号 | 交付物与标题归属 |
| --- | --- | --- |
| 微信公众号推文 | 微信公众号、公众号文章、公众号推文、微信长文、品牌公众号、公众号风格、微信爆文 | 图文长文；其文章标题按公众号子类型规则处理 |
| 小红书图文笔记 | 小红书、XHS、红书感、小红书笔记、小红书写法 | 图文笔记；小红书标题、封面配字和 `#话题` 按小红书子类型处理 |
| 邮件 | 邮件、email、e-mail、邮件主题、EDM、邀约邮件、跟进邮件 | 可复制到邮件客户端的邮件；邮件标题即主题行，按邮件子类型处理 |
| 短视频口播稿 | 抖音/快手/视频号/B站口播、短视频文案、视频脚本、短视频标题、标题库、封面标题 | 可直接朗读的台词或平台标题；不要求镜头表 |
| 短视频分镜脚本 | 分镜、逐镜、镜号、镜头表、拍摄脚本、storyboard、分镜图 | 可拍摄的镜头级执行稿；使用镜头表和按需的关键镜头视觉参考 |

标题类请求必须先识别所属渠道，而不是把标题当作无渠道的短句任务：微信公众号标题走“微信公众号推文”，小红书标题走“小红书图文笔记”，邮件主题走“邮件”，抖音/快手/视频号/B站标题或封面标题走“短视频口播稿”。用户未指定渠道时，仅按共性原则输出能兑现内容承诺的标题，不擅自附加平台格式、话题标签或 emoji。

Presentation Decision 记录 `adapter: "media-and-communication"`；具体渠道由本文件命中的子类型和 `visual_plan.reason` 说明。

## 平台内容与成稿共性原则

以下原则用于平台内容组织与渠道呈现；已命中内容 contract 时，不替代其确定的内容任务、事实、证据、合规或读者边界。

### 叙事：让目标读者理解并记住一件事

媒体传播不是把素材写长，而是把一个明确的信息交付给明确的读者：发生了什么、它与读者有什么关系、凭什么相信、下一步该做什么。生成前先确认受众、传播任务、核心信息和可核实材料；一篇内容只解决一个传播任务，信息不足时收窄结论，不用泛化口号填补。

### 视觉：让素材承担信息职责

媒体传播中的视觉必须在建立场景、展示产品、还原事件、提供证据、帮助比较中承担至少一项职责。优先使用用户提供的品牌资产、产品界面、活动现场图、人物肖像和原始数据；同一内容只建立一个视觉焦点，封面、标题和第一张图表达同一主题。

### 内容焦点：按内容 contract 选择平台化表达

| 平台化表达重点 | 读者需要得到的结果 | 成稿应优先呈现 |
| --- | --- | --- |
| 品牌认知 | 知道品牌为何存在、做什么、相信什么 | 主张、差异、真实故事或案例 |
| 产品沟通 | 理解产品变化及其实际价值 | 用户问题、变化、使用方式、适用边界 |
| 活动传播 | 决定是否参与，或记住发生过什么 | 价值、时间地点、关键环节、参与方式或活动成果 |
| 案例背书 | 相信方案在具体情境中有效 | 背景、行动、结果、限制条件 |
| 内容沉淀 | 获得可复用的知识或行业判断 | 问题、解释、证据、方法、边界 |

已命中内容 contract 时，由其决定采用哪条内容链路和主张边界，本表只帮助将该任务转化为平台可读的内容组织；未命中明确内容 contract 时，从本表选择最符合用户材料与读者任务的一条，作为默认内容骨架。

## 信息来源：用户 query 信息及附件 > 联网搜索

- **阅读用户提供的 query 信息及附件（重要性与权威性都最高）**：用户上传或提供的一切材料都是本次任务的第一手事实来源，优先级高于联网搜索和先验知识；query 中的关键信息都应理解和利用。附件中的关键信息可能藏在图、表或公式里，只读取纯文本会造成遗漏；此前只取得文本或尚未读取附件时，必须重新解析。DOCX 按当前 Skill 的跨载体路由先进入 Office Word 模块，PDF 和其他附件调用对应文件能力；同时读取文字、结构和视觉信息。DOCX 至少覆盖段落、表格、页眉页脚、媒体、图表、嵌入对象和逐页视觉；PDF 提取全文并查看每页，含图表、表格、图片或扫描信息的页面必须查看清晰页面图。附件中的图片和表格插入云文档时必须保留全部信息，不得裁剪，可以等比缩放以适配排版；与其他来源冲突时以用户附件为准。创建飞书文档前，必须完整读取附件中的文字、图片、表格等相关信息。
- **联网搜索**：补齐主题相关的真实数据、事实、案例；不得编造，缺失就标注占位/假设/待补，并标注来源。用户给的是完整文档或逐页大纲、且没说能否扩写时，默认联网搜索扩充素材与案例，除非用户明确要求不扩写。


### 从传播主题出发：云文档承担创作与协作台

创作、评审、发布准备阶段，用飞书文档串联 **内容 contract 确定的受众与目标 → 渠道成稿 → 素材与事实 → 内容/排期 → 审核与发布清单**。多渠道排期进入 Sheet/Base；素材、来源和评审意见贴近对应段落；任务和待确认项属于工作台，不能混入对外成稿。

## 场景级 Block 规则

| 工作台中的信息关系 | 推荐能力 | 使用边界 |
| --- | --- | --- |
| 创意主张、受众、调性、禁区 | 标题、段落、`callout` | 只高亮需要评审确认的结论 |
| 素材板、产品或活动证据 | `img`、`source`、链接预览 | 图片附必要来源；视频/音频优先附件或外链 |
| 分镜、内容排期、审批清单 | 文档 `table`、嵌入 Sheet/Base | 持续维护的排期进入 Sheet/Base，不截图 |
| 制作协作 | `checkbox`、已有 `task`、`time`、`cite type="user"` | checkbox 不等于可分派任务 |
| 内容原文 | 标题层级、段落、图片 | 最终对外版式由对应子模板约束 |

## 禁止项

1. 不虚构数据、用户反馈、人物引语、活动结果、产品能力或传播效果。
2. 不把平台 adapter 等同于产品广告；活动记录、活动招募、案例、访谈、知识内容同样可叠加本 adapter。
3. 不用无关装饰图、素材拼贴或夸张标题代替信息价值。
4. 不把内部任务、批注、待确认项和素材来源混进对外正文。
5. 不在 `lark-doc` 不具备的能力上做虚假承诺；图表、任务、日程、既有画板分别路由到对应 skill。
6. 微信公众号对外成稿**绝不使用** `<table>` / 文档表格 Block；即使原始材料是字段比较、预算拆分、时间表或名单，也必须改写为正文、简单列表或一张图片信息图。通用候选表、`presentation_mode`、原始材料格式和“信息需结构化”的要求均不得构成例外。

## 子类型1：微信公众号推文

### 路由条件

用户明确要求“微信公众号文章、公众号推文、微信长文、品牌公众号、公众号风格、微信爆文”时使用。它适用于品牌内容、产品更新、活动预告、活动回顾、访谈故事、案例与知识解释，不限于“品牌价值传播”。

不适用于微信聊天、群公告、朋友圈、视频号口播、小程序页面、服务通知；仅将微信作为研究对象或渠道时也不触发。

### 核心特点

公众号成稿是一篇可独立转发、在手机上连续阅读的图文文章。模型可根据真实材料自由选择叙事方式，不套固定内容结构；但必须让读者在开头明确知道文章讲什么，并让每一节提供新的事实、解释、场景或体验。结尾只完成与本篇任务匹配的动作，例如报名、查看资料、了解产品或回到一个判断。

### 视觉风格选择

每篇文章只选用一种风格系统，并从头到尾保持一致。若用户提供品牌手册、历史推文或视觉素材，以其为准；没有时从下列三种通用系统中选一种。

| 风格系统 | 适合内容 | 原生 XML 强调色与章节处理 | 参考效果 |
| --- | --- | --- | --- |
| 编辑解读 | 行业观察、知识解释、案例复盘、人物访谈 | 按主题选择 `blue`、`green` 或 `red`；章节使用居中的 `01`、`02` 加小节名；图注使用 `gray` | 逻辑清晰、阅读节奏稳定 |
| 叙事传播 | 人物故事、品牌故事、旅游内容、营地/活动回顾、IP 预热 | 将品牌主色映射为最接近的 `red`、`orange`、`purple`、`green` 或 `blue`；章节号和少量重点词共用该命名色 | 品牌识别明确，以场景和人物带动阅读 |
| 机构资讯 | 医院/学校/协会/企业动态、招生招募、培训会议、行业方案与成果发布 | 将机构标准色映射为 `blue`、`green` 或 `red`；小节左对齐，以编号提示层级；图注和说明使用 `gray` | 正式、清楚、资料感强，方便读者查找关键信息 |

不得混用两套颜色系统。正文和背景保持默认样式，不显式设置 `black`、`white` 或十六进制颜色；辅助文字使用 `gray`。品牌精确色值只用于封面、正文图片和其他视觉资产，不写入飞书原生 XML 属性。机构资讯中的获奖名单、会议议程、培训要点或指标对比，如确需表格，应制作为一张 **1080px 宽的信息图**，并在图前或图后以正文概述关键结论；不能将飞书表格直接放进公众号成稿区。

选择规则只看读者的首要阅读任务：读者要理解一个问题或判断，选“编辑解读”；要跟随人物、场景或事件获得感受，选“叙事传播”；要快速查找时间、名单、成果、安排或规则，选“机构资讯”。同一篇文章只有一个主风格；无法判断时默认“编辑解读”，不新增风格类别。热点信息、医疗信息和机构动态须先区分已确认事实与评论/观点，不能把网友观点写成事实。

#### 原生颜色映射

每篇只选一种原生强调色。`text-color` 仅使用 `red`、`orange`、`yellow`、`green`、`blue`、`purple`、`gray`；正文大段不着色。精确品牌色只进入图片 Brief，不作为原生 XML 颜色值。

| 风格系统 | 原生 XML 可选强调色 | 适用感觉 |
| --- | --- | --- |
| 编辑解读 | `blue` / `green` / `red` | 理性、科技、行业观察；冷静的知识科普；深度评论、人物与文化议题 |
| 叙事传播 | `red` / `orange` / `purple` | 品牌故事、产品发布、城市旅行；亲子营地与温暖活动回顾；创意项目、IP 预热、青年文化 |
| 机构资讯 | `blue` / `green` / `red` | 学校、协会、行业方案与正式发布；医疗培训、公共服务与专业教育；纪念、表彰、成果展示与传统文化 |

用户提供品牌色时，在图片中保留精确色值，在原生文字中映射为最接近的合法命名色。不得新增第二种原生强调色，也不得以配色替代信息层级。

### 成稿版式

公众号成稿区只使用飞书 XML 已定义且便于复制的基础富文本：`title`、`h1`、`h2`、`p`、`b`、`em`、`u`、`del`、`br`、`span`、`img`、普通列表和 `hr`。颜色只通过 `span` 的 `text-color` 属性表达，并填入一种合法命名色，例如 `<span text-color="blue">重点</span>`；不使用十六进制颜色、字体、像素级字号或未定义的短色线。不得使用画板、引用块、callout、分栏、表格、文件附件、Sheet/Base、任务、复选框、按钮、链接预览、@提及、文档引用、公式或 HTML5 Block。

选择本 adapter 时，`presentation_mode` 必须使用 `rich`。`rich` 只在本文件明确允许的表达范围内生效；本文件的视觉系统、组件限制、编号、素材、来源与回读规则为硬约束，优先于通用候选表达，不得因 `rich` 放宽。

公众号对外成稿的允许 Block 仅为标题、正文、`img`、普通列表和分隔线；`<table>` 是硬禁止项，不得因数据对比、方案清单或排版便利而写入。需要呈现多字段信息时，优先提炼为“结论句 + 列表”；确有横向比较必要时，制作成图片信息图并按正文图片规则插入。

#### 正文与文字样式

飞书云文档 XML 不设置字体或像素级字号。正文统一使用 `<p>`，保持左对齐和短段落：每段 2–4 句，段与段之间空一行。

未明确字数时，正文默认 800–1,200 字，最多 1,500 字。明确要求深度分析、系统解读或长文时，正文一般为 3,000–5,000 字；用户明确字数时，以用户要求为准。优先删减背景铺垫和重复论述，而非压缩关键事实、案例、行动信息或必要的图片说明。

**重点强调必须有明确规则，不随机决定是否上色：**每篇文章从所选视觉系统中确定一种合法命名色；对真正影响读者理解、判断或行动的短词句，可选择加粗、`span text-color`，或两者结合。可强调的内容包括核心结论、关键数据、行动节点、专有概念或关键人物/机构名；每次限一个短语或一句短句，不能把整段、连续句子或普通修饰词染色。没有需要强调的信息时可以不用；一旦使用颜色，全文不得再使用第二种正文强调色。斜体、下划线、删除线仅在语义确有需要时使用，不与颜色凑成装饰；长引语、人物原话或数据结论仍以普通段落呈现，不改变为引用卡片或底纹块。

#### 标题与章节

文章标题通过加粗和显式对齐建立层次，例如 `<title align="center"><b>标题</b></title>`；需要左对齐时将值改为 `left`，不给 `<title>` 直接添加未定义的颜色属性。标题只表达一个判断、事件或读者收益。日期等必要元信息使用 `<p align="center"><span text-color="gray">元信息</span></p>`，并与主标题选择相同的合法 `align` 值；作者和编辑信息置于封面图之后。

正文小节使用两级即可：一级小节使用一个 `<h1>` 同时承载编号和标题，例如 `<h1 align="left"><span text-color="blue">01</span> 小节名</h1>`；二级小节使用 `<h2>`。不得把一个章节拆成相邻的两个同级标题，也不使用 XML 未定义的短色线。不得使用 `seq="auto"`，编号由正文显式写为连续的两位数 `01`、`02`；不要使用超过两级的小标题、居中大段正文或通篇彩色文字。

生成时通过 `<title>`、`<h1>`、`<h2>` 和 `<p>` 的层级，以及加粗、合法命名色与 `align` 落实层次；不要求或尝试设置字体、字号和行距。

#### 封面图

除非用户明确要求不使用图片，每篇公众号文章必须有一张封面图。完整顺序固定为：标题 → 正文最开始给出封面图 → `<p align="center"><span text-color="gray">推荐封面图</span></p>` → 作者信息（如“作者｜xxx”）→ 正文。封面图只建立一个主题：优先选用用户提供且授权可用的品牌主视觉、产品核心场景、人物/活动关键瞬间或能说明主判断的原始数据图；没有可用素材时，先搜索与文章主题直接相关、来源清楚且可使用的图片；仍不满足时，可生成与文章主题、风格系统和强调色一致的非侵权插图。不得用无关风景、抽象素材或多图拼贴替代封面。

封面计入 `visual_plan.blocks` 的 `img` 最低数量。除用户明确要求不使用图片外，每篇公众号文章必须有一张**实际 `<img>` 封面图**，因此 `img.min_count` 至少为 1；普通文本留位不满足封面要求。写正文前先列出封面及所有需要图片承接的正文节点，`img.min_count` 必须等于这些节点所需实际图片的总数，而非只计算封面。正文在图片能提供证据、还原场景、推进人物叙事、解释产品或降低理解成本时，必须在对应位置插入实际图片。先搜索来源清楚、与主题直接相关的资料图；没有合适资料图且不涉及真实现场证明时，再生成明确为示意/氛围的图片。仅重复文字、无法核验或会冒充真实现场时不硬加图。

用户提供图片或明确要求图片数量时，该数量和素材使用要求高于默认封面策略，必须写入 `visual_plan.blocks` 的 `img.min_count` 与 `purpose`。用户提供的图片默认全部使用：先为每张图判断最直接的内容关系，再放在对应段落之后——产品图放在功能或使用说明之后，活动/人物图放在所还原的环节或叙事转折之后，数据图放在所支撑的结论之后；封面图只使用最能建立全文主题的一张。不得把多张用户图片无解释地集中堆在开头或文末。用户明确要求 N 张时，成稿必须至少包含 N 张实际图片；用户已提供图片但数量不足以满足 N 张时，按本文件的素材策略补充可用搜索图或生成图。若剩余图片只能由用户提供且未获素材，不得伪造图片或以占位符宣称已满足 N 张要求，应在最终回复中说明缺口。

当正文理应使用用户独有的真实照片（活动现场、人物、旅途、客户案例、采访、第一人称故事等），而用户尚未提供时，不搜索或生成会被误认为真实记录的替代图；但不得因此省略封面和可由资料图/示意图承担的正文视觉。必须在对应段落后插入一张实际 `<img>`：优先使用来源清楚的资料图，或在不冒充真实记录的前提下生成示意图；图注写为“图N：……（资料图/示意图；建议替换为作者/主办方实拍的……）”。不得只写灰色文字“配图留位”。这类实际图片计入 `img.min_count`，待用户补入素材后再替换图片及图注。只有用户明确要求“不要搜索或生成任何图片、仅保留文字位置”时，才保留灰色文本占位并在最终回复说明未插入图片。

用户明确不要图片时，才不搜索、不生成、不插入封面或正文图片，且 `blocks` 不得包含 `img`；此时以标题、段落、列表和分隔线完成版式。

#### 图片：来源、顺序与内容关系

正文图片必须是论点的证据、场景或信息补充：产品图解释功能，活动图还原发生的事，人物图服务人物叙事，数据图支撑结论。封面已经完成主题建立、正文没有额外视觉信息需求时，只使用封面是合理的；但存在可由资料图或示意图承担的关键场景、产品、数据或叙事转折时，必须补入正文实际图片，不得以文字留位替代。用户独有实拍缺失时，插入可替换的资料图/示意图，并在图注写明建议替换的素材类型。图片按首次出现顺序连续编号；封面不计入正文图号。每张正文图片下方使用 `<p align="center"><span text-color="gray">图1：说明（来源：机构/活动/产品名称）</span></p>`；资料图或生成图须明确写为“资料图”或“示意图”，不得写成作者实拍。图片前先用一至两段文字交代读者为什么要看图，图片后再解释读者应从中看到什么。不能以无关图片打断论述，也不连续堆叠两张没有文字承接的图片。

使用用户提供或已明确可用的图片；未获授权的肖像、商标、新闻图片和第三方截图不能默认采用。需要注明时，在图片下使用灰色普通文本，格式统一为“图N：说明（来源：机构/活动/产品名称）”。来源不确定时标记“图片来源待确认”，不要编造。

#### 图片：尺寸与排版

源图片优先按 **1080px 宽**准备，以保证复制到公众号后清晰；写入飞书云文档时，使用 `<img>` 的 `width` 属性控制显示宽度并保留原始比例。默认文档宽度约 820px，因此封面、横向场景、产品主图和信息图的显示宽度不超过 `800`；竖版人物或海报使用 `520–680` 内的具体整数；品牌标识、二维码等小型素材按需使用 `240–360` 内的具体整数。只有已确认文档使用宽版模式时，才可提高到约 `1000`。不同时强设 `width` 与 `height`，以免拉伸变形。产品截图必须保留关键按钮、数据和上下文；数据图不得裁掉坐标、图例与来源。单张图片前后各保留一段文字或一个空行，图注紧贴图片下方。

活动回顾可连续使用 2–3 张同一事件的照片，但必须按时间、人物或环节顺序排列，并以一段普通文本完成承接。封面图只在能建立主题时使用一张，不使用多图拼贴封面。

#### 图片审美与禁止项

先为每篇文章确定一个统一的**影像目标**：每张图片在生成或搜索前，明确它服务于封面主题、场景还原、人物叙事、产品证据还是数据解释；没有明确作用的图不使用。

图片选择优先级为：用户提供且授权的真实素材 → 官方/权威主体发布且可使用的实景、产品或人物图片 → 与主题直接相关、来源清楚的搜索图片 → 缺少真实素材时生成插图或氛围主视觉。人物、真实地点、产品界面、活动现场、机构建筑和可核实事件优先搜索真实图片，不用生成图冒充事实；生成图片只用于不承载事实证明的封面氛围、概念解释或明确标注的示意。

搜索图片必须进入原始素材页或授权下载页取得干净原图，不能直接使用搜索结果缩略图、新闻网页截图或带发布平台标识的转存图。插入前必须预览图片并检查四项：可确认授权或使用边界、无可见水印/媒体台标/图库标识/二维码/文字覆盖、主体与实际地点或事件相符、清晰度和裁切满足版式。任一项不满足即弃用，继续寻找官方无水印原图、取得授权或改用明确的示意图；不得以“图注已标来源”代替图片使用许可。

生成的氛围图或示意图必须给出具体画面 brief：主体、场景、时间/氛围、镜头景别、视觉焦点、色温与构图留白，并明确“不生成伪文字、伪数字、假标志、假界面或水印”。封面图以一个清楚主体和干净构图建立主题，不把标题或口号交给生成模型；需要真实文字、品牌标识或界面时，使用用户提供或已获授权的真实素材。

图片禁止项：
- 禁止使用与正文无关的装饰图、重复图片、低清或过度滤镜图、主体被裁断的图、任何可见水印/媒体台标/图库标识/二维码/文字覆盖、生成的假品牌标识/假产品界面/假新闻现场、乱码或伪文字、蓝紫霓虹、发光线路、赛博网格、彩虹光晕、玻璃拟态等通用 AI 科技视觉
- 需要生成多图时，必须以一张主图建立焦点，其余图片按事件或叙事顺序补充。
- 生成的氛围图和示意图不含伪文字、伪数字、假标志、假界面或水印；真实产品截图、数据图、信息图和已授权品牌视觉可保留其必要文字、数字、标志与界面，并在写入前逐项核对准确性

回读时逐张确认：主体清晰可辨、与相邻段落直接相关、比例未变形、关键内容未被裁切、无可见水印/台标/二维码/文字覆盖、生成图没有文字或异常细节、图片之间的光线/色温不突兀。任一项不通过，替换图片或移除该图，不用无关装饰补位。

#### 收尾与行动信息

收尾使用普通正文段落。报名、资料获取、产品入口或下一场活动的信息用一段明确的文字列出；发布时再由微信后台配置链接、菜单或小程序卡片。二维码、关注引导图或品牌尾图按需使用一张，不能作为每篇文章的固定装饰。

#### 事实来源

正文用可读的归因表达事实来源，例如“据三水区公开发布的信息”或“据某机构 2026 年报告”；不在正文段落直接粘贴原始 URL、方括号链接或参考文献编号。生成前须在内部完成关键事实、时效性、适用政策/平台规则与图片使用边界的核验；交通、开放状态、价格、活动、政策、资质、效果等易变信息，以主管部门、发布主体或服务提供方的最新公开信息为准。核验不通过或关键事实无法确认时，不交付可直接发布版本，也不以待确认表述填充正文。只要生成过程中搜索了外部事实、数据或图片，文章最后必须追加“资料来源”区：使用 `<hr/>`，再用 `<p><span text-color="gray">来源机构｜页面名称｜核验日期</span></p>` 列出可读来源名称，不添加 XML 未定义的普通超链接。原始 URL、完整授权信息和待确认项保留在内部来源映射中。该区必须位于所有正文、行动信息和品牌尾图之后；没有使用任何外部搜索素材时不添加。

#### 最终回复专用说明（不写入飞书云文档）

创建并回读文档后，最终对话回复必须另行提供以下内容：

1. **封面图方案与配图建议**：先按素材策略输出，不能把不同情形混为一谈。
   - **留位策略**：用户明确会自行插图，或图片需要证明真实活动、人物、地点、产品、案例或用户反馈时，仍在正文插入一张可替换的资料图/示意图，并在图注说明应替换为哪类用户自有/已获授权真实素材；不把资料图或示意图虚构为现场记录。只有用户明确要求仅保留文字位置时，才不插入替代图。只列出精简的替换建议，不输出核验过程。夏令营、活动回顾、人物故事、客户案例和现场报道通常使用此策略。
   - **推荐策略**：用户未提供素材，且图片不承担现场事实证明时，说明均为推荐图片方案；仅推荐已经按本文件的来源、无水印、真实性与使用边界规则完成核验的具体图片或生成图。用户持有自有版权或已获授权的实拍素材时，可替换对应推荐图。
2. **备选标题**：除成稿标题外提供 3–5 个备选标题，并标记推荐标题。

不输出内容验真清单、图片版权核验提醒或内部核验过程。以上内容只出现在最终对话回复中，**不得写入飞书云文档**的标题、元信息、正文、图注或工作台区域；唯一例外是：使用外部搜索素材时，云文档最后必须保留由合法 `p`、`span text-color="gray"` 和 `hr` 组成的简短“资料来源”区。云文档其余部分只保留可复制到公众号后台的成稿。

## 子类型2：小红书图文笔记

### 路由条件

用户明确要“小红书笔记、小红书写法、小红书 style、红书感、XHS 风格”，或要求小红书标题、封面配字、图文笔记时使用。只把小红书作为研究对象、数据源或业务渠道时不触发；平台运营方案走对应方案 Profile，平台数据或竞品分析走分析 Profile。若同时需要小红书风格稿和正式体裁，分别生成，不混写。

### 内容与标题

一篇笔记只解决一个主要问题，并让标题、封面配字、首屏和正文围绕同一获得感，且在正文中真实兑现。首屏用 1–3 个短段落完成具体场景/冲突、核心判断和内容预告；正文以短段落推进，每节新增动作、观察、例子、判断或限制，不用长铺垫、空情绪或泛化种草话术代替信息。

成稿只输出一个标题；标题以具体场景、痛点、收益、反差或可验证的体验切入，必须与封面配字和首屏一致，不做多行标题、标题库拼接或无法兑现的夸张承诺。未给出平台字数限制时，优先简短、可扫读的单行标题；用户给出字符限制或平台当前限制时，以该限制为准。正文末尾可给 3–5 个相关 `#话题`，只保留内容、地点、品类或人群真正相关的话题，不用堆砌热词。

emoji 用于导航、语气和停顿，可适量使用但不连续堆叠；美妆、旅行、生活方式、亲子、活动等可更活泼，B2B、医疗、金融、公共事务及用户要求专业/客观时默认不用。emoji 不能替代标题、逻辑层级、事实或行动信息。

### 图片、封面与配字

小红书图文以图片为主要阅读入口。除非用户明确不要图片或只要纯文字，必须规划一张封面和与正文直接对应的内容图；优先使用用户提供且授权可用的实拍、产品、活动或截图素材。用户没有素材、图片不承担真实现场证明时，必须搜索或生成具有小红书图文质感的图片，而不只给抽象配图建议。

封面使用一个鲜明、可在手机首屏识别的主体；可在封面上加入简短配字，以用户实际使用的语言写出场景、收益或判断，避免把整段正文、虚构数字、绝对化承诺或无关口号压进图片。正文图片可用实拍、局部特写、步骤卡、清单卡或前后对比卡组成阅读节奏；每张图只承载一个信息重点。生成图片时明确主体、场景、景别、光线、构图、配字文案与版式留白；真实人物、真实地点、真实活动、产品界面和可核实事件仍须使用用户/官方真实素材，不得用 AI 图冒充现场记录。

用户提供图片或明确要求图片数量时，按其数量和内容关系决定封面与正文位置；用户独有照片缺失且它承担事实证明时，在对应段落留下具体配图留位，不用 AI 替代。用户明确不要图片时，不搜索、不生成、不插入图片，也不保留空泛的封面要求。

### 成稿版式与回读

对外笔记区只使用标题、短正文、`img`、简单列表、分隔线和图片下的简短说明；不使用 `<table>`、画板、分栏、callout、引用块、任务、复选框、链接预览、文件附件、Sheet/Base、HTML5 Block、公式、@提及或文档引用等飞书特有 Block。图片可带小红书风格配字，但图片下方不写公众号式“图1：来源”图注；需要说明素材时，以短句融入正文或在末尾单列“素材说明”。

`presentation_mode` 使用 `rich`；`visual_plan.reason` 写明“小红书图文笔记｜图片视觉方向与封面配字｜短段落、标题与话题”，未明确拒绝图片时，`blocks` 至少记录封面所需的一张 `img` 及用途。创建后回读：确认只有一个标题、首屏/封面/配字同题、图片具小红书阅读价值、段落适合手机扫读、话题与内容相关、emoji 未堆叠，且不存在飞书特有 Block。

## 子类型3：邮件

### 路由条件

用户明确要“写邮件、邮件成稿、邮件草稿、邮件措辞、email、e-mail、邮件主题、EDM”，或要求起草回复、跟进、通知、邀约、外联邮件时使用。查看、搜索、发送、回复或管理真实邮件属于 `lark-mail` 操作；若任务既要成稿又要实际发送，先生成并确认内容，再切换邮件操作能力。

### 内容、主题与版式

一封邮件只承担一个主要沟通任务。主题行是邮件标题：准确表达对象、事项或所需行动，避免标题党、emoji、空泛寒暄和无信息量的“重要通知”；用户指定主题长度或邮件系统限制时优先遵守。成稿顺序为主题 → 称呼 → 首段来意/结论 → 必要背景 → 明确请求、选项或下一步 → 合适收尾 → 已知身份的署名。关系、称呼、截止时间、附件、发件人身份或联系方式不明时使用清晰占位符，不得编造。

默认使用 `formal`，只使用短段落、列表、用户已提供的纯文本 URL 和分隔线；不自行发明普通链接标签。全文不用 emoji、封面、装饰图、表格、callout、画板、分栏、任务、复选框、附件 Block、Sheet/Base、HTML5 Block、公式、@提及或文档引用。营销邮件或活动邀请只有在用户确认目标邮件编辑器支持、且图片能承担品牌主视觉或活动信息时，才可使用一张图片；图片不替代主题、正文和行动信息。

`visual_plan.reason` 写明“邮件｜主题与行动信息｜收件人关系和语气”；`presentation_mode` 默认为 `formal`。创建后回读：主题和首段能说明收件人为什么收到、需要知道或做什么；行动项可直接回应；语气与关系相符；复制到邮件客户端仍清晰可读。

## 子类型4：短视频口播稿

### 路由条件

用户明确要“抖音/快手/视频号/B站口播、短视频文案、视频脚本、短视频标题、标题库、封面标题、20 条文案”等，但未要求逐镜、分镜、镜号、镜头表、拍摄脚本或 storyboard 时使用。它交付可直接朗读的台词和按需的标题/封面文案，不把口播稿强制扩展成镜头表。

### 内容、标题与格式

先确定平台、受众、时长、核心动作和能证明主张的素材；未给时长时不虚构时长。口播开头尽快进入具体痛点、反差、结果、疑问或场景，随后以可理解的理由、动作、例子或边界推进，结尾只完成一个与任务匹配的行动。台词短、顺、可自然说出口；不把屏幕文字、镜头说明或括号提示混进需要直接朗读的台词。

标题、封面标题与口播是三个可独立交付物：标题提供观看理由，封面标题提供一眼可见的核心承诺，口播在开头兑现它们。用户只要标题或标题库时，只输出标题及必要封面配字，不补写完整口播。抖音标题优先强场景、反差或即时收益，避免复述封面文字；快手标题直接、真实、有人情味，避免过度包装；视频号标题可更完整地交代人物、事件或观点；B站标题说明主题、对象或问题，避免用空泛悬念替代信息。用户给出平台字符限制、禁词或风格样例时优先遵守；未给时不虚构统一字数限制。高信任行业如暖通、医疗、金融、政企及用户要求专业客观时默认不用 emoji；其他场景也仅按语义少量使用，不把 emoji 写入口播台词。

### 成稿版式与回读

口播稿按“标题（如需）→ 封面配字（如需）→ 口播正文 → 结尾动作/素材留位（如需）”输出，以短段落或编号列表组织；不使用表格、画板、分栏、callout、任务、复选框、Sheet/Base、HTML5 Block、公式、@提及、文档引用或链接预览。实际活动、人物、产品或案例需要画面证明但用户未提供素材时，留下可拍摄/可补入的普通文本留位，不伪造现场。

`visual_plan.reason` 写明“短视频口播稿｜平台语感与标题/封面配字｜钩子、口播节奏与行动”；`presentation_mode` 使用 `rich`。创建后回读：标题/封面配字/首句承诺一致，台词可直接朗读，平台语感没有压倒事实，且未混入分镜表或飞书特有 Block。

## 子类型5：短视频分镜脚本

### 路由条件

用户明确要求“分镜、逐镜、镜号、镜头表、拍摄脚本、storyboard、分镜图”，或材料明确要求拍摄团队据此执行时使用。它与短视频口播稿不同：分镜脚本必须给出能拍摄的画面、镜头与声音安排；仅要求台词、标题或口播时回到“短视频口播稿”。

### 分镜内容

先确定平台、画幅、时长、受众、核心目标与可用素材；按时长选择镜头密度，并在开场尽快给出痛点、反差、动作、结果或悬念钩子。每个镜头只写可被拍到的客观画面；台词短且口语化；通过动作、视线、道具、声音、景别或光色完成镜头衔接。核心卖点必须由可见动作、产品展示、人物变化或结果证明，而非只由旁白声称。

成稿以分镜表为核心，固定包含“镜号、时长、景别、机位、画面内容、台词、音效/花字”七项；镜号从 `01` 连续编号，时长写为 `Ns`，无台词或音效时明确写“（无台词）”或“（无）”。表格仅用于此类内部拍摄执行稿，不得迁移到微信公众号、小红书、邮件或口播成稿。封面方案与关键镜头视觉参考按需提供：用户没有明确拒绝图片且图片工具可用时，优先规划封面及开场钩子、核心展示、收束镜头的视觉参考；真实人物、场地、活动和产品仍优先使用用户/官方真实素材，生成图只作为不冒充事实的视觉参考。

### 平台标题与视觉

标题和封面配字按“短视频口播稿”的平台差异处理；封面图不强制把标题写进图内，只有用户要求或平台视觉策略确有必要时才加入简短配字。抖音/快手/视频号优先竖版构图，B站优先横版构图；以用户指定平台、画幅和素材为准。短视频分镜可使用内部 `table` 与 `img`，但不使用无信息价值的飞书画板、callout、任务、复选框、Sheet/Base、HTML5 Block、公式、@提及或文档引用。

`visual_plan.reason` 写明“短视频分镜脚本｜平台、画幅与视觉方向｜钩子、关键镜头与执行信息”；分镜含封面或关键镜头视觉参考时，在 `blocks` 写入所需 `img` 最低数量和用途。创建后回读：七列齐全、镜号连续、画面可拍、台词可说、标题/封面/首镜承诺一致，且图片已置于对应镜头或封面方案旁，而不是文末孤立堆放。
