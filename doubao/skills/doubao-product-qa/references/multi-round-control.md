# 多轮变更控制

用于“继续补充、删掉几条、恢复上一版、用 A 替换 B、总数只保留 N 条”等多轮任务。目标是保持上下文、编号和数量可审计，避免越改越乱。

## 目录

1. 稳定对象与编号
2. 变更原子动作
3. 变更台账
4. 限额与替换会计
5. 冲突与双轨
6. 外部飞书产物更新
7. 交付检查

## 1. 稳定对象与编号

命名空间固定：

| 对象 | 格式 | 规则 |
|---|---|---|
| 需求 | `REQ-<模块>-NNN` | 发布后不改名 |
| 冲突 | `CONF-<模块>-NNN` | 两种口径各保留来源 |
| 风险机制 | `RM-<模块>-NNN` | 按失效机制，不按页面 |
| 用例 | `TC-<模块>-NNN` | 删除后编号不复用 |
| 执行 | `EXE-<模块>-NNN` | 每次运行新建；不得借用 TC 编号 |
| 证据 | `EVD-<模块>-NNN` | 首败与复测分开 |
| Bug | `BUG-<模块>-NNN` | 不用执行记录号代替 |
| 变更 | `CHG-NNN` | revision 内顺序唯一 |

删除对象保留 tombstone：

```json
{
  "id": "TC-REF-013",
  "status": "removed",
  "removed_in_revision": 3,
  "reason": "用户明确从本轮范围删除"
}
```

不得为了“编号连续”重新编号。编号空洞比引用失效更安全。

## 2. 变更原子动作

先把用户话语拆成以下动作：

| 动作 | 语义 | 数量影响 |
|---|---|---|
| `ADD` | 新增对象，不替代旧对象 | 正数 |
| `MODIFY` | 保留 ID，修改内容 | 0 |
| `REMOVE` | 从当前有效集合移除 | 负数 |
| `RESTORE` | 恢复 tombstone | 正数 |
| `REPLACE` | 明确用新对象替代旧对象 | 新增数−删除数 |
| `NARROW` | 收缩范围，批量移除 | 负数或 0 |

“补充接口用例”默认是 `ADD`；“把第 3 条改成边界 30%”是 `MODIFY`；“加回打印 >2000 行”是 `RESTORE`；“总数仍为 10，用 2 条 API 用例替换 2 条 UI 用例”是 `REPLACE`。

不能判断是新增还是替换时，该差异会改变最终数量，属于唯一需要澄清的问题；不要一边问一边同时做两套。

## 3. 变更台账

每轮先递增 `revision`，再写：

```json
{
  "id": "CHG-004",
  "revision": 3,
  "action": "REPLACE",
  "object_type": "case",
  "removed_ids": ["TC-UI-006", "TC-UI-007"],
  "added_ids": ["TC-API-021", "TC-API-022"],
  "modified_ids": [],
  "before_count": 10,
  "after_count": 10,
  "delta_count": 0,
  "source": "用户第 3 轮指令",
  "summary": "总数保持 10，用 2 条 API 校验替换 2 条 UI 检查"
}
```

硬规则：

- `after_count - before_count == delta_count`；
- 同一对象类型的下一条变更 `before_count` 必须等于上一条 `after_count`；
- 最后一条记录的 `after_count` 必须等于当前有效集合数量；
- `ADD/RESTORE` 的 delta 为正；
- `MODIFY` 的 delta 为 0；
- `REMOVE/NARROW` 的 delta 不大于 0；
- `REPLACE` 同时包含 removed 与 added；
- `run.revision` 等于台账最大 revision。

## 4. 限额与替换会计

遇到“总数不超过 N”“只保留 N 条”：

1. 先列当前有效集合与数量；
2. 将用户点名保留项锁定；
3. 执行删除或替换；
4. 再新增；
5. 计算最终集合；
6. 验证 `count <= N` 或 `count == N`；
7. 显示“保留/修改/删除/新增”的 ID 清单。

禁止：

- 先新增后凭感觉删几条；
- 把一条 `MODIFY` 同时算作删除和新增；
- 用户要求“加回”时创建新 ID；
- 在总数限制下既保留旧项又加入替代项；
- 只写“已按 10 条调整”，不提供集合证据。

## 5. 冲突与双轨

新口头要求与旧 PRD 冲突时：

1. 新建 `CONF-*`；
2. 保留旧来源与新来源；
3. 写两套可测试预期；
4. 指明默认基线：用户已给优先级则服从，否则沿用正式 PRD；
5. 只将非冲突部分写入稳定用例；
6. 冲突解决后用 `MODIFY` 更新，不重建全套。

禁止用最新一句话静默覆盖旧基线，也禁止同时把两套预期都写成“应当”。

## 6. 外部飞书产物更新

飞书文档、表格、Base 和 PPT 都是 `qa-run.json` 的投影：

- 更新前读取原对象并确认 `source_revision`；
- 只改受影响章节、行、记录或页面；
- 更新同一对象，不创建“最终版2/最新版3”；
- 用例行以 `case_id` 定位，不以行号定位；
- 删除用例时将协作台账状态改为 `removed`，不物理抹去执行历史；
- 更新后回读数量、ID 和 revision；
- 回读失败时不提升 `delivery_manifest.status` 为 `validated`。

## 7. 交付检查

交付前必须回答：

- 本轮 action 是什么？
- 哪些 ID 保留、修改、删除、恢复、新增？
- 变更前后数量是否对账？
- 是否出现 ID 复用或命名空间冲突？
- 需求、风险机制、用例、执行和结论是否一起重算？
- 飞书产物是否与 canonical revision 相同？

任何一项答不上来，继续修订，不使用“已按要求更新”作为替代。
