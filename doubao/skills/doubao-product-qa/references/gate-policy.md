# 门策略

本文件是包内所有校验的**唯一分档口径**。实现在 `scripts/gate_policy.py`；
renderer、artifact validator 和 publish 全部走同一张表，不再各自用 `level=="error"` 判阻断。

## 为什么要分档

阻断条件的**总量**本身就是一道门。实测：填满 schema 全部必填字段之后，
一次 `complete` 仍然返回 94 条 error（其中 52 条只是 ID 命名格式）。
执行者面对这个量级时，理性选择是放弃整条链——真实 trace 里出现过
手写 78KB 的构建脚本、反读校验器源码、以及门返回 OPEN 之后照样把产物发出去。

所以分三档：

| 档 | 含义 | 谁来处理 |
|---|---|---|
| `BLOCK` | 错了会让用户拿到**错东西**（错数字、错结论、错优先级、没产物） | 必须修，修完重跑 |
| `FIX` | 答案唯一，脚本直接改完 | 脚本，执行者不用管 |
| `REPORT` | 不影响正确性的完整度问题 | 不阻断；用户相关的进成品披露段 |

**未登记的发现默认 `REPORT`。** 这是刻意的：宁可漏一条非致命项，
也不要因为门太多而让整个门禁体系被绕过。

## BLOCK 全集（10 类）

新增一类必须移除一类。

| 类 | 拦什么 | 为什么必须阻断 |
|---|---|---|
| `canonical-nonempty` | 来源、材料清单、需求、风险机制、用例、执行为空 | 报告要引用的集合为空时，正文里的数字没有来源 |
| `count-identity` | coverage 与 canonical 不一致 | 统计不自洽直接毁掉可信度 |
| `verdict-discipline` | 零证据下 go/no_go、未通过 P0 仍 go、未关闭 S1/S2 仍上线 | 越过证据下终审是核心红线 |
| `p0-blocking-identity` | P0 集合 ≠ 发布阻塞项集合 | 金标准的真实规则是 P0 ⟺ 阻断发布；不等就是 P0 膨胀 |
| `unverified-consistency` | 有未执行/阻塞却写「未验证范围：无」 | 成品内部自相矛盾 |
| `severity-priority-enum` | 出现 S0、致命、High、Blocker | 读者无法与既有 SOP 对齐 |
| `precheck-not-formal` | 预跑/小样本升成正式 Bug | 制造不存在的缺陷 |
| `open-oracle` | 未决口径被写成唯一预期 | 驱动开发按错误规则验收 |
| `delivery-contract` | 用户指定的载体/文件名/章节顺序未满足 | 那是硬契约不是默认值 |
| `delivery-artifact` | 产物不存在或未回读就宣称交付 | 用户拿不到东西 |

## FIX 档

答案唯一才自动改；有第二种合理答案的一律不碰。

- ID 命名补齐模块段（`REQ-001` → `REQ-REFUND-001`），并同步全部引用；
- 风险机制 ↔ 用例双向引用（由用例侧单向推导）；
- `cases[].status` 移除（状态一律由执行派生）；
- 变更台账计数重建、coverage 重算。

**已发布的 ID 不改名。** 出现在 change_ledger 或 tombstone 里的 ID 一律冻结——
多轮任务里编号空洞比引用失效安全（见 [multi-round-control.md](multi-round-control.md) §1）。

## 改门纪律

1. 改判据前拿四份金标准跑一遍。**金标准不过门就是判据错了，不是金标准错了。**
2. 新增 BLOCK 必须同时移除一条，并更新本文件与 `SKILL.md` 的清单。
3. 任何"不达标就不交付"的门都要有保底路径。唯一允许的终态阻断是
   **盘上没有产物可发**；"产物不够好"由披露承担，不由阻断承担。
4. 门的输出必须人类可读。执行者不应该需要写代码解析门的结果。
