# 风险机制闭环

风险覆盖的单位是“可能如何失败”，不是页面、字段或测试类型。一个页面可以包含多个机制；同一机制也可能跨 UI、API、存储和第三方系统。

## 目录

1. 风险机制对象
2. 通用机制清单
3. 从机制到独立用例

5. P0/P1 闭环判定
6. 停止扩展条件

## 1. 风险机制对象

在 `qa-run.json.risk_mechanisms` 中记录：

```json
{
  "id": "RM-PAY-001",
  "title": "重复提交产生重复资金副作用",
  "failure_mode": "客户端重试与服务端处理重叠，创建两笔退款",
  "business_impact": "重复退款与账务不一致",
  "oracle": [
    "同一业务键只存在一笔有效退款",
    "第二次请求返回幂等结果或明确拒绝",
    "消息、库存、优惠券和审计副作用仅一次"
  ],
  "requirement_ids": ["REQ-PAY-003"],
  "case_ids": ["TC-PAY-011", "TC-PAY-012"],
  "priority": "P0",
  "status": "designed"
}
```

`status` 只使用：

- `identified`：已识别，尚无测试；
- `designed`：已有可执行用例；
- `verified`：有执行证据且 oracle 满足；
- `failed`：执行证实存在失败；
- `blocked`：无法完成验证；
- `accepted`：有明确责任人接受残余风险；
- `not_applicable`：已确认不适用并记录理由。

风险机制不得只有标题。`failure_mode`、`business_impact` 和 `oracle` 缺一项即不能进入用例设计。

## 2. 通用机制清单

按相关性选择，不机械全选。发现一个独立失效原因就建立一个机制对象。

| 机制族 | 必问问题 | 典型数据 |
|---|---|---|
| 主值择真 | 同页/同响应出现多个候选值时选谁 | 原价、优惠、实付、余额同时出现 |
| 干扰隔离 | 非目标数字/文本会否被误识别 | 订单号、手机号、页码、余额 |
| 方向与符号 | 逆向业务是否被当正向处理 | 退款、冲正、撤销、负数、退货 |
| 边界与精度 | 闭区间、舍入、币种、时区是否一致 | 0.01、上限、上限+0.01、跨日 |
| 身份与对象归属 | 角色、租户、本人/他人、旧会话 | 被撤权账号、跨租户 ID |
| 状态合法性 | 非法迁移、终态重入、超时事件 | 已退款再审核、已删除再编辑 |
| 重复与幂等 | 连点、超时重试、消息重投是否重复副作用 | 同 key 并发 2 次、回调重放 |
| 并发冲突 | 两个有效操作同时发生如何裁决 | 最后一件库存、双端编辑 |
| 跨层一致性 | UI、API、库、缓存、搜索、消息是否一致 | 页面成功但消息失败 |
| 部分失败与补偿 | 链路中途失败是否回滚或可恢复 | 扣券成功、订单写入失败 |
| 生命周期与迁移 | 升级、降级、脏数据、损坏时是否可恢复 | 老版本数据、字段缺失、断电 |
| 容量与资源释放 | 重复操作后内存、句柄、温升、队列是否累积 | 连续 50 次识别/上传/打开 |
| 权限与隐私 | 拒绝、撤回、最小权限、落盘/日志/上传 | 永久拒绝、截屏文件残留 |
| 失败恢复 | 断网、超时、取消、重启后状态是否确定 | 请求结果未知、前后台切换 |
| 兼容边界 | 最低版本、屏幕、字体、语言、时区差异 | 760px/最窄屏、200% 字号 |
| 可访问性 | 键盘、焦点、名称/角色、错误关联 | 无鼠标主旅程、读屏表单 |
| 可观察性 | 失败能否定位并关联 | request ID、业务码、审计日志 |
| 灰度与回滚 | 开关、分群、版本回滚后数据是否兼容 | 10% 分流、关闭开关、降级 |

行业特有风险应落到上述机制，而不是新建一张互不相通的行业清单。例如“优惠券重复返还”属于重复与幂等；“OCR 取到订单号”属于干扰隔离。

## 3. 从机制到独立用例

每个 P0/P1 机制至少满足：

1. 一个主验证用例；
2. 一个关键失败或恢复用例；
3. oracle 能被 UI、API、数据、日志或第三方回执观察；
4. 用例引用 `risk_mechanism_ids`；
5. 机制回指 `case_ids`，双向一致。

以下写法不合格：

- 一条“完整验证退款流程”同时承担金额、权限、幂等、回调和优惠券一致性；
- 在步骤中顺带看一眼，没有独立数据和预期；
- 只写“验证多金额场景”，不说明候选值和选择规则；
- 只验证前端按钮置灰，不直调服务端约束；
- 把“风险低”当作没有用例的理由，但没有接受人和依据。

可以合并的条件：

- 失效根因相同；
- 使用同一数据构造；
- 断言集合相同；
- 失败后归因和修复点相同。

任一条件不满足，拆成独立用例。

## 4. 测试数据与 oracle

P0/P1 `test_data` 使用以下三种形态之一：

### 固定值

```text
订单实付=120.00 元；建议退款=60.00 元；审核输入=60.01 元
```

### 构造式

```text
max=10000 分；依次构造 max-1、max、max+1
```

### Fixture

```text
fixture=refund_pending_same_order_v2；业务键=order_id；预置一条 PENDING 退款
```

oracle 必须回答：

- 返回或页面显示什么；
- 最终业务状态是什么；
- 数据条数与关键字段是什么；
- 消息、通知、库存、资金或第三方副作用发生几次；
- 失败时是否回滚、补偿或可重试；
- 哪个证据能证明这些结果。

禁止使用：

- “使用正常账号”
- “样例为准”
- “输入合理金额”
- “结果正确”
- “数据库无异常”

## 5. P0/P1 闭环判定

一个 P0/P1 机制只有在以下条件同时满足时才是 `verified`：

- 关联需求有明确来源；
- 至少一个用例已执行；
- 当前执行状态为通过；
- 业务 oracle 的每一层都有断言或证据；
- 没有被另一个失败或阻塞用例推翻；
- 测试数据和环境可复现；
- 相关副作用已清理或登记。

存在以下任一情况，不得标 `verified`：

- 只跑了前端，没有验证服务端硬约束；
- 只创建了会话，没有完成真实业务流；
- 重跑通过覆盖了首次失败；
- 只验证模拟器，却把相机、支付、推送或真实性能推广到真机；
- 使用 mock 验证了契约，却声称真实第三方联调通过；
- 仅有统计数字，没有用例级证据。

## 6. 停止扩展条件

同时满足后停止铺量：

- 每条原子需求至少映射一个用例；
- 每个 P0/P1 风险机制已 `verified/failed/blocked/accepted`，不存在空白；
- 新增用例只重复相同机制与 oracle；
- 代表性组合已覆盖高风险交互对；
- 未覆盖项有明确理由、责任人和下一动作；
- 发布结论能从当前机制状态和执行证据推导。

完整性以风险机制闭环衡量，不以“至少 50 条用例”衡量。
