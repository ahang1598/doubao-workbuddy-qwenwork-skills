## 工具选择

零基础用户先按 `SKILL.md` 指向的 `beginner-onboarding.md` 完成输入分类和环境检测。只有公开 URL 时也能做黑盒冒烟：一次性 UI 验证先复用能读取 DOM/可访问性语义的浏览器控制能力；可重复回归使用项目已有测试或 Playwright。两者都不可用时，需经用户许可后安装项目内 Playwright/浏览器，否则只能做 HTTP/静态部分验证。有代码目录时由 Agent 自动识别启动方式和现有框架。

1. 只有公开页面且做一次 UI 冒烟/快速确认：先使用能读取 DOM、角色或可访问性语义的浏览器控制工具，保留结构化执行记录，再用 HTTP、控制台或网络结果交叉验证；结论标记 `exploratory`。
2. 当前登录态、扩展或用户浏览器状态很重要：使用 Chrome/浏览器控制工具探索和取证，但不把当前桌面会话写成正式回归依赖。
3. 有代码仓库、发布门禁或结果需要重复执行：使用项目已有测试框架；Web E2E 优先 Playwright。
4. 结构化 GUI 只能用于勘察或复现时，根据发现生成/修复 Playwright 用例，并重跑 Playwright 后才能记为 `full_automation`。
5. 只有 API：优先项目已有 API 测试；否则使用 HTTP 客户端并保存脱敏后的请求/响应。
6. 只有图像或固定坐标 GUI：须获得用户许可并标记弱兜底；工具不可用时输出手工步骤和未验证项，不伪造执行结果。

若当前环境提供专门的浏览器 skill，先读取并遵守它。不要为了自动化测试随意替换项目框架。

## 执行模式

- `standard`：覆盖需求追踪、核心旅程、关键异常、回归和代表性浏览器/视口。
- `hotfix`：只覆盖修复点、直接上下游、P0 冒烟、回滚和上线监控；使用 `assets/hotfix-test-template.md` 记录推迟项。

不要固定单元/集成/E2E 百分比。把可稳定验证的业务逻辑尽量下沉到单元/集成层，把少量关键用户旅程留给 E2E。

## 执行前门禁

记录：

- 目标 URL、构建号、环境和时间；
- 测试账号、角色、租户与登录态；
- 功能开关、地域、语言和时区；
- 可创建/删除的数据范围与清理方案；
- 支付、消息、外部回调、删除等副作用；
- 已知环境问题和第三方依赖。
- 本地工程的启动命令、工作目录、URL/端口、依赖状态、环境文件、服务 PID/会话和 readiness 条件。

先检查页面可达、核心接口可达、账号权限正确。若首页都无法稳定打开，先报告环境阻塞，不继续制造大量级联失败。

登录态按以下顺序选择：

1. 用户要求复用当前登录状态：使用现有 Chrome/浏览器会话；
2. 验证登录流程本身：使用测试账号自动化，验证码/扫码/OAuth 由用户在有头浏览器完成；
3. 登录不是测试目标：优先 API 登录并保存短期 storage state；
4. 无 GUI：使用测试 cookie/token 或 API 登录，无法获得时标记阻塞。

不得把真实密码、token、cookie 或 storage state 提交进仓库。认证状态必须与角色、租户和环境绑定，过期后重新生成。

执行测试前若用户未指定截图方式，询问一次：

1. `失败与 P0 关键节点`（推荐）；
2. `仅失败`；
3. `每一步`；
4. `不截图`。

记录用户选择并贯穿本轮执行，不在每个步骤重复询问。选择不截图时仍保留文本日志、trace、console、network 和框架报告；可能含敏感信息的页面应同时确认脱敏或排除区域。

## 探索与测试生成

只有 URL 或没有 PRD 时，先在 `qa-run.json.observed_surfaces` 建立可观察界面清单：

```text
surface_id, page, control_or_claim, state,
functional_check, visual_check, evidence_expected, source
```

把用户可见功能、控件、状态和页面宣称分别映射到功能断言、视觉断言与所需证据。运行时新发现的界面项可以补充，但必须标明来源为探索，不能伪装成产品需求。

本地工程需要确定性生命周期编排时使用 `scripts/run_web_session.py`：配置 `project_dir`、`base_url/readiness_url`、参数数组形式的 `start_command` 和 `test_command`。它只关闭本次启动的进程，并把 stdout、stderr、readiness 和 cleanup 写入 session summary；可通过 `--qa-run` 和 `case_id` 回写 canonical execution。Agent 私有浏览器工具不能由该脚本伪装调用，仍按结构化 GUI 探索路径记录。

遵循 `计划 → 生成 → 执行 → 诊断 → 复测`：

1. 阅读 PRD/验收标准和已有测试，形成用户级场景与明确 expect。
2. 从全新或可重置状态进入页面，盘点交互面、关键旅程、空/加载/错误态。
3. 查看控制台和网络请求，识别前端静默失败、重复请求和错误映射。
4. 先手动/交互式走通一次，再把稳定路径固化为测试代码。
5. 每个场景独立准备状态；避免场景 A 的结果成为场景 B 的隐藏前置。
6. 对每个用户步骤添加可观察断言，动作本身不是验证。
7. 运行新测试至少一次，并保存结果；失败进入诊断流程。

## Playwright 编写约定

### 定位器优先级

优先使用用户可感知语义：

1. `getByRole(..., { name })`
2. `getByLabel()` / `getByPlaceholder()`
3. `getByText()`（内容稳定且唯一时）
4. `getByTestId()`
5. 稳定 CSS；避免依赖 DOM 层级、动态 class 和 `nth()`。

### 断言

- 对最终业务结果断言，而不只断言点击成功。
- 检查 URL、可见状态、文本、表单值、列表变化、错误提示和必要的 API 响应。
- 对异步结果等待业务条件，不使用固定 `sleep`。
- 不使用 `networkidle` 代替业务就绪信号；实时连接和埋点可能让它永不稳定。
- 不以扩大 timeout 掩盖竞态；先找到具体未满足的条件。
- 只对稳定内容做完整截图/快照断言，动态时间、随机 ID 和广告需屏蔽或局部断言。
- 页面截图遵循用户选择；推荐用于失败、P0 关键节点和视觉回归，不要擅自为了证明每次点击都发生而逐步截图。
- 录像用于长链路、偶现问题或用户明确要求，不默认录制全部成功用例。

### 隔离与数据

- 每个测试创建唯一数据或使用可重置 fixture。
- 使用 API/fixture 做数据准备时，仍通过 UI 验证用户关键旅程。
- 并行运行时避免共享账号、固定名称和同一库存/配额。
- 清理不是把失败证据删掉；先保留标识和日志，再清理测试数据。
- 凭证放在环境变量或项目既有 secret 机制，不写入测试代码和报告。

### 推荐结构

```ts
import { test, expect } from '@playwright/test';

test('TC-ORDER-001 用户可提交有效订单', async ({ page }) => {
  await page.goto('/orders/new');
  await page.getByLabel('商品数量').fill('1');
  await page.getByRole('button', { name: '提交订单' }).click();

  await expect(page.getByRole('heading', { name: '订单提交成功' })).toBeVisible();
  await expect(page.getByTestId('order-number')).toHaveText(/^[A-Z0-9-]+$/);
});
```

测试标题包含用例 ID，便于从报告回溯需求。复用项目已有 fixture、baseURL、认证和目录约定。

## 接口与跨层断言

页面成功不等于业务成功。按风险选择：

- 请求是否只发送一次，方法/路径/关键 payload 是否正确；
- 响应状态、schema、业务码和错误映射是否符合契约；
- 刷新或重新进入后数据是否仍存在；
- 列表、详情、搜索、统计是否最终一致；
- 消息/通知/第三方副作用是否触发一次；
- 超时后重试是否造成重复数据。

不要在 E2E 中过度断言内部实现。只有当跨层一致性是业务风险时才增加接口/数据证据。

## 失败诊断

一次处理一个失败：

1. 复跑单个测试，确认稳定性和复现概率。
2. 在失败前后保存页面快照、trace、控制台和失败请求；截图仅在用户选择的策略允许时保存。
3. 检查实际 DOM/可访问名称是否变化，区分定位器漂移和产品行为变化。
4. 检查数据是否泄漏、账号/开关是否错误、请求是否超时或乱序。
5. 比较需求预期与实际；意图不明时不要自动修改断言。
6. 若纯脚本问题，做最小修复并复跑单测；若产品问题，保留失败并生成 Bug。
7. 修复后运行相邻场景和最小回归集。

禁止用以下方式“修复”：删除关键断言、无理由 `skip`、任意增加 sleep、捕获并忽略错误、把错误结果改成新预期。

## 证据与清理

失败证据命名建议：

```text
evidence/<case-id>/<timestamp>/
├── screenshot.png
├── trace.zip
├── console.txt
├── network.txt
└── context.md
```

`context.md` 记录构建、环境、浏览器、账号角色、测试数据标识、步骤和证据关联。网络与控制台日志应删除 token、cookie、手机号、邮箱、身份证、地址等敏感值。

执行结束后：关闭浏览器/调试会话和后台服务；清理测试数据；保留失败所需的非敏感标识；记录未能清理的副作用。
