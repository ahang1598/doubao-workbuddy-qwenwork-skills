# QA 成品写法与正反例

本文件校准“最终内容应该长什么样”。示例只示范颗粒度、证据纪律和表达方式，不是可逐字套用的业务模板。

## 1. 总体写法

成品第一屏回答三件事：测的是什么、现有证据说明什么、下一步要做什么。背景、方法和内部状态放后面。

### 正例

> 本轮基于预发环境 21 条 P0 执行记录收口：18 条通过、3 条失败。3 个失败均有请求响应或业务记录证据，其中 2 个涉及退款金额约束，当前不满足准出条件。修复后需重跑金额上限、重复审核和相邻回归集。

为什么好：

- 第一段给出范围、证据、发现与动作；
- “不满足准出条件”由真实失败支撑；
- 没把未执行 P1/P2 写成通过；
- 没展示 profile、renderer 或内部脚本。

### 反例（禁止）

> 我先创建了 qa-run.json，然后用 renderer 生成报告。整体通过率较高，建议尽快修复问题后上线。

为什么错：

- 内部过程占据第一屏；
- “通过率较高”掩盖 P0；
- “尽快修复后上线”没有条件、责任人和复测口径；
- 读者无法直接做决定。

### 结构由体裁决定，不是固定一套

**不要套用一份万能骨架。** 章节形状由本次任务类型和材料特征决定，
每次 `qa_flow.py anchor` 的输出末尾会印一张体裁卡，直接照它写：

```text
报告体裁：release-gate（有执行记录，要给 go/no-go）
章节（按此顺序写，没有内容的段已经被去掉，不要补空段）：
  结论 → 需求口径与资料冲突 → 业务链路与范围 → 风险排序 → 执行结果复核
       → 已确认缺陷 → 待确认 → 回归安排 → 准出条件
标题请用本任务的业务词，例如：外链、撤销、水印、密级、CDN
```

五种体裁及其触发条件见 [report-shapes.md](report-shapes.md)。三条纪律：

1. **空章节不占位。** 体裁卡已经按材料删掉了不适用的段。不要再写"待确认：无""阻塞：无"。
2. **标题用业务词，不用通用 QA 名词。** 写「关键序列重算」而不是「数据分析」，
   写「最终需求口径」而不是「需求梳理」，写「外链撤销与 CDN 失效」而不是「功能测试结果」。
   体裁卡末尾给的高频业务词就是素材。
3. **`plan-only` 体裁结构性禁止出现**执行结果、通过率、发布结论、上线建议——
   没有执行证据时这些段落本身就是越权，不是措辞问题。

不论哪种体裁，第一屏都必须回答：测的是什么、现有证据说明什么、下一步要做什么。

### 未执行的用例也要写完整

未执行不等于可以只写一行摘要。金标准里未执行用例同样有完整的前置条件、
具体测试数据和逐层预期——因为它们是要交给别人去执行的。

反例（禁止）：

```text
| TC-12 | 并发取消 | 未执行 |
| TC-13 | 回调乱序 | 未执行 |
```

正例：未执行用例与已执行用例在同一张表里，字段完整度一致，只是 `status` 不同。

### 未决口径与已知未覆盖必须单独成条

不要把它们散在正文各处提一句。收口报告在「准出条件」里、方案在「已知未覆盖」里，
逐条列出：哪条规则还没定、谁来定、定不下来会影响哪些用例；
哪些能力本轮**明确没测**（例如平台券真实到账依赖未联调的下游接口）。

写成独立条目的目的是让读者能直接拿它去开会，而不是读完全文自己归纳。

### 编号

首轮生成时编号连续，不要无故跳号。
多轮删除产生的编号空洞**保留**，不重新编号——引用失效比空洞更危险
（见 [multi-round-control.md](multi-round-control.md) §1）。跨轮沿用同一前缀。

### 不要写超出本轮指令边界的内容

用户只要"测试范围 + 用例"时，不要附赠自动化改造方案、CI 接入建议或工具选型。
即使声明了"非本轮交付"，它仍然稀释了交付物。有价值的建议放到最后一行提一句即可。

## 2. 输入与需求基线写法

### 输入清点正例

```text
SRC-001 PRD.docx：read；已核对正文、表格和修订时间
SRC-002 退款规则.xlsx：read；4/4 个 Sheet 已核对
SRC-003 原型包.zip：read；12/12 个成员已分类，其中 8 张原型、3 张状态图、1 份接口说明
SRC-004 飞书评审记录：blocked；缺少访问权限；最小动作=由文档所有者开放阅读权限
```

### 输入清点反例（禁止）

> 已阅读用户提供的所有附件。

反例没有材料清单、版本、读取状态和完整性证据；如果实际只看了首个 Sheet 或压缩包文件名，后续覆盖结论全部失真。

需求要写成可测试规则，不抄整段 PRD。

### 正例

| ID | 原子规则 | 来源 | 验收 |
|---|---|---|---|
| REQ-REF-003 | 已消耗课时占比 ≥30% 时，退款进入人工审核 | PRD §3.2 | API 状态为 PENDING_AUDIT；不触发自动退款 |

P0/P1 canonical 还要保存：

```text
actor：购买用户
precondition：订单已支付且存在可退金额
trigger：提交退款申请
rule：已消耗课时占比 ≥30%
state_change：退款单 CREATED → PENDING_AUDIT
observable_result：查询接口返回 PENDING_AUDIT
failure_behavior：不触发自动退款；返回可理解的审核提示
impact_scope：退款审核后台、支付指令、账务对账
```

### 反例（禁止）

| ID | 需求 | 来源 | 验收 |
|---|---|---|---|
| 1 | 退款功能正常 | PRD | 正常即可 |

改写配方：

1. 找角色或业务对象；
2. 找触发条件；
3. 找阈值/规则；
4. 找状态变化；
5. 找可观察结果和副作用；
6. 找失败行为。

### 待确认正例

| ID | 最小确认问题 | 影响 | 下一动作 |
|---|---|---|---|
| Q-REF-004 | 30% 是否包含恰好 30.00%？ | 决定 AUTO 与人工审核边界 | 产品在提测前确认 `>=` 或 `>` |

### 待确认反例（禁止）

- 待确认退款边界。

反例没有最小问题、没有影响，也没有责任动作，无法推动关闭。

### 冲突写法

```text
CONF-REF-002
来源 A：PRD 写“≥30% 转人工”
来源 B：临时口头要求写“>30% 转人工”
默认基线：PRD（用户已给优先级）
双轨验收：30.00% 在 A 下转人工，在 B 下自动处理
阻塞范围：边界用例与上线阈值；其余用例继续
```

禁止把两种预期混写成“30% 左右应转人工”。

## 3. 风险机制写法

风险必须描述“怎么坏、坏了影响什么、如何证明没坏”。

### 正例

```text
RM-REF-002 重复审核触发重复退款
failure_mode：客服连点或超时重试导致相同 refundId 两次 APPROVE
impact：重复打款与账务不一致
oracle：
1. 首次请求进入退款处理；
2. 第二次返回幂等结果或终态错误；
3. 支付指令、退款单和审计日志各只有一次有效副作用。
```

### 反例（禁止）

```text
风险：注意接口幂等。
```

反例缺失效方式、业务影响、数据和 oracle，无法变成用例。

### 风险排序正例

> `TC-API-008` 为 P0，因为服务端金额上限被绕过会直接生成超额退款指令；失败即阻断本版本。`TC-API-001` 缺少 reason 参数属于 P1 契约校验，除非它能绕过关键写入，否则不因“接口必填”自动升为 P0。

### 风险排序反例（禁止）

> 接口相关都很重要，所以全部 P0。

## 4. 用例写法

### 完整用例示例

```text
case_id：TC-API-008
title：审核金额超过实付 50% 上限
priority：P0
release_blocking_reason：服务端可生成超额退款，存在直接资损
preconditions：
- 订单 ord_60217 实付 20000 分
- 退款单 rf_50022 为 PENDING_AUDIT
- 客服账号属于该订单客服组
test_data：
- auditAmount=10001 分（上限 10000 + 1）
steps：
1. POST /api/refund/audit，action=APPROVE，auditAmount=10001
2. 查询退款单详情
3. 查询支付指令与审计日志
expected_result：
1. 接口返回业务码 40013；
2. 退款单保持 PENDING_AUDIT，amount 未写为 10001；
3. 不创建支付指令；
4. 审计日志记录一次被拒绝的审核尝试，不含敏感 token。
requirement_ids：REQ-API-003
risk_mechanism_ids：RM-REF-003
```

这个示例的写法重点：

- 数据固定到分；
- 上限和上限+1 分开；
- UI/API/数据/副作用都有可观察结果；
- P0 有阻断理由；
- 一个用例只承担“金额上限”机制。

### 反例（禁止）

```text
标题：测试退款金额
数据：合理金额
步骤：提交退款
预期：退款功能正常
优先级：P0
```

### 边界用例配方

若规则为 `0 < amount <= 10000`，优先示例：

| 数据 | 目的 | 预期 |
|---|---|---|
| -1 | 非法方向 | 拒绝 |
| 0 | 最小边界 | 拒绝 |
| 1 | 最小有效 | 接受 |
| 9999 | 上限内 | 接受 |
| 10000 | 上限 | 接受 |
| 10001 | 上限外 | 拒绝 |

不是每次都机械测七个点；只保留会改变业务分支的点。

### 多值择真示例

页面同时显示：

```text
原价 35.00
优惠 5.00
实付 30.00
余额 128.00
订单号 202607250001
```

用例要分别覆盖：

- 取 `实付 30.00`；
- 不取原价、优惠、余额和订单号；
- 数据保存后金额仍为 30.00；
- 若规则未说明“实付”优先，先建立待确认，不臆断。

### 资源释放示例

“连续操作”不要只写一次循环：

```text
执行 50 次 OCR：
- 每次完成后关闭确认层；
- 每 10 次记录耗时、内存、温升和失败数；
- 第 50 次仍可完成；
- 截图临时文件、句柄和任务队列没有单调累积；
- 阈值没有来源时只报告 baseline，不写达标。
```

### 性能预跑与正式结论

预跑只回答“是否出现需要继续验证的信号”，不回答“产品是否存在正式性能 Bug”：

```text
validation_scope=precheck
样本=3 次
观察=P95 约 2.4s
结论=待确认；样本量、并发模型和稳定环境不足
下一步=在固定数据集、预热完成、30 分钟稳定窗口下执行正式场景
```

只有正式场景达到约定样本、并发、环境、阈值来源和可重复性后，才能把性能失败提升为 Bug。水印、截图噪声或单次结果同样先归入待确认。

### 业务状态与技术结果

状态型用例至少分开：

```text
中间业务状态：AUTO_APPROVED
最终业务状态：REFUND_ACCEPTED
技术执行结果：SUCCESS
外部副作用：退款任务只创建一次，审计记录包含规则版本
```

`AUTO_APPROVED` 描述业务决策，`SUCCESS` 描述技术调用结果；不能只断言其中一个就推导另一个。异步流程还要分别检查中间状态、终态、重试/幂等和审计。

## 5. Bug 写法

报告必须把三个数字分列：

- 失败记录数：最新执行状态为失败的用例数；
- 正式 Bug 数：完成证据分级和归因后建立的 Bug 数；
- 根因数：被证据支持的独立根因数。

一条失败可能不是 Bug，多条失败也可能归并为一个根因；三者不得互相替代。

### 标题正例

> `BUG-REF-002：审核金额 18000 分超过实付 50% 上限仍返回成功并写入退款单`

标题包含条件、动作和错误结果。

### 标题反例（禁止）

> `退款有问题`

### Bug 正例骨架

```text
严重程度：S1
优先级：P0
理由：已证实服务端写入超额退款金额；真实渠道打款尚未验证

复现步骤：
1. 使用订单 ord_60217（实付 20000 分）创建待审退款单；
2. 客服提交 auditAmount=18000；
3. 记录响应并查询退款单。

实际结果：
- 返回 200 APPROVE_SUCCESS；
- amount 写为 18000。

期望结果：
- 返回 40013；
- 状态与 amount 不变；
- 不触发支付。

影响：
- 资金约束被绕过；
- 预发未接真实渠道，因此“已经真实打款”仍是未验证。

初步分析：
- classification：接口/后端业务校验；
- trigger_hypothesis：仅在人工审核金额大于规则上限时触发；
- change_correlation：上周金额规则从固定值改为比例，怀疑相关；尚需核对该次 diff；
- blast_radius：若校验位于共用退款审核服务，App、客服后台和批处理入口均需回归；
- confidence：medium。
```

### Bug 反例（禁止）

```text
严重程度：Critical/High/P0
原因：后端肯定没校验
影响：一定会造成真实打款
```

错在：

- 三套枚举混写；
- 未验证根因写成事实；
- 把尚未联调的真实打款写成已发生。

### 偶现问题写法

保留第一次失败的时间、环境、输入和证据，再新增复测：

```text
reproducibility=intermittent
repro_attempts=5
首次失败=EXE-UPLOAD-003 / EVD-UPLOAD-004
复测：第 2、3 次通过，第 4 次失败，第 5 次通过
结论：仍为开放偶现，不因最近一次通过关闭
```

## 6. 验收清单写法

验收清单服务发布决策，不逐条复制用例。一个验收项可以聚合多个共同证明同一决策目标的用例。

### 正例

```text
AC-REF-001｜core_flow｜核心退款申请、审核与到账链路
关联：TC-REF-001; TC-REF-004; TC-REF-008
blocking：true
派生状态：未通过（TC-REF-004 失败）

AC-REF-002｜data_consistency｜退款单、支付指令与账务记录一致
关联：TC-REF-011; TC-REF-012
blocking：true
派生状态：待验证（两条均未执行）

汇总：总数 2；通过 0；未通过 1；阻塞 0；待验证 1；不适用 0。
复算：0+1+0+1+0=2。
```

### 反例（禁止）

```text
- [x] 退款功能正常
- [x] TC-REF-001
- [x] TC-REF-002
结论：大部分通过
```

错在人工勾选没有执行来源、直接复制用例、汇总不可复算，也没有说明哪项阻断发布。

## 7. 发布结论写法

### 有执行失败时的正例

> 结论：`no_go`。预发执行证实 `TC-API-008` 与 `TC-API-011` 失败，分别绕过退款金额上限和重复审核保护，均为开放 S1/P0。放行条件：修复两个缺陷；单点复测通过；执行金额边界、重复请求、回调幂等及账务一致性回归；确认测试数据已清理。

### 零执行证据时的正例

> 结论：`undetermined/无法判断`。现有 PRD 足以完成风险分析和用例设计，但没有安装包、环境或执行记录，不能判断产品可上线或不可上线。最小补齐：提供目标构建与测试账号，执行 P0 冒烟并回传请求/日志证据。

### 零执行证据时的反例（均禁止）

> 风险很多，不建议上线。

> 目前没有发现问题，建议上线。

第一句把风险假设当产品失败，第二句把未执行当通过；两边都越过证据。

### 条件上线正例

```text
conditional_go
条件：
1. BUG-A11Y-004 在发布前关闭，负责人李雷，截止周五 12:00；
2. 灰度仅 5%，监控支付失败率与重复订单数；
3. 指标超过基线 +20% 自动回滚；
4. P2 Safari 兼容在灰度 24 小时内补测。
```

“有条件”必须能被逐项核验，不写“尽快修复剩余问题”。

## 8. 多轮变更写法

### 替换正例

用户要求：“总数仍是 10，删掉 2 条 UI，用 2 条 API 替换。”

```text
before=10
REMOVE：TC-UI-006, TC-UI-007
ADD：TC-API-021, TC-API-022
after=10
delta=0
保留：其余 8 条 ID 不变
```

### 替换反例（禁止）

```text
新增 2 条 API，现有用例已优化为 10 条。
```

反例没有说明删了什么，很可能实际变成 12 条。

### 恢复正例

用户说“加回打印超过 2000 行”：

- 查 tombstone；
- 恢复原 `TC-COMPAT-014`；
- action=`RESTORE`；
- 不创建 `TC-COMPAT-031`。

### 增量交付正例

第二轮只增加接口：

```text
保留 Round1 的 REQ-REF-* 与 TC-REF-*；
新增 REQ-API-*、RM-API-*、TC-API-*；
用映射表说明哪些接口用例加强了第一轮业务用例；
不复制第一轮整张表。
```

## 9. 飞书文档与表格写法

### 文档第一屏骨架

```text
# 组合优惠订单部分取消 · 灰度测试报告
版本：2026.07.25-rc3
结论：no_go
依据：14 条执行记录中 3 个失败已被日志/响应证实，其中 2 个涉及库存和优惠券一致性
```

## 10. 交付前对照

逐项对照成品：

- 第一段是否直接给范围、证据、结论与动作？
- 需求是否是原子规则，而不是 PRD 摘抄？
- 输入材料是否逐项清点，表格/压缩包是否核对完整？
- 每个 P0/P1 是否有独立风险机制、具体数据和 oracle？
- 验收项是否从执行派生，状态合计是否等于总数？
- Bug 的实际与期望是否分开？
- Bug 是否区分近期改动关联与横向波及范围？
- 严重程度与优先级是否只用一套枚举？
- 未验证内容是否仍明确可见？
- 零证据时是否拒绝了正反两种终审？
- 多轮数量与 ID 是否能复算？
- 文档、表格、Base、PPT 是否各自承担合适的信息形态？
- 用户可见产物是否删除了内部脚本、profile 和过程旁白？

任一项为否，回到对应对象修订，不在末尾追加一段“注意事项”掩盖结构问题。
