## 证据优先流程

1. 读取完整错误、需求预期、执行步骤和环境信息。
2. 第一次发现失败时立即保存证据，再在可控数据上至少做一次复现尝试；重跑不得覆盖首次失败。
3. 比较工作场景与失败场景，列出所有差异。
4. 沿数据流定位第一个出现错误的层级。
5. 提出一个可证伪的原因假设，做最小验证。
6. 只把已验证的机制称为根因；否则给出置信度和下一步取证。
7. 评估影响、回归面、临时规避和复测范围。

在 `qa-run.json` 中记录 `category`、`reproducibility=always/intermittent/once/not_reproduced`、`repro_attempts`、`first_failure_preserved`、`evidence_grade` 和 `evidence_ids`。未再次复现不等于第一次失败不存在；保留为 `not_reproduced` 或风险继续取证。

同一个 `EXE-*` 默认只支持一个开放缺陷主张。若一次执行确实同时暴露多个独立失败，每个 Bug 都要填写不同的 `independent_failure_signature`（例如“权限判定错误”和“审计事件缺失”），且证据能分别定位；否则合并为一个 Bug，在影响范围中列出多个表象。禁止把同一失败按页面、文案或下游表现机械拆单。

证据类型匹配 Bug 类型：

| Bug 类型 | 首选证据 |
|---|---|
| 静态错字、遮挡、布局 | 一张能定位问题的截图 |
| 交互、状态、时序 | 步骤截图 + 视频/trace/日志中的适用项 |
| API | 脱敏请求摘要 + 响应 + request/trace ID |
| Crash | 操作步骤 + 日志 + crash 文件 |
| Flaky | 首次失败 + 重跑结果，至少两次尝试且不覆盖首败 |

## 复现设计

记录以下变量：

- 构建/提交、环境、平台、浏览器/设备；
- 账号、角色、租户、地域、语言、时区；
- 功能开关、缓存、网络、依赖服务；
- 数据创建方式、状态和唯一标识；
- 操作时序、重复次数、是否并发；
- 首次发生时间、复现次数/总次数。

最小化时每次只移除或改变一个变量。偶现问题至少检查竞态、异步时序、共享数据、缓存、资源限制和第三方抖动。

## 分层定位

沿边界收集输入与输出：

```text
用户动作
  → UI 状态/表单值
  → 浏览器请求
  → 网关/服务响应
  → 持久化/缓存
  → 异步消息/第三方
  → UI 最终状态
```

找到“上一层正确、下一层首次错误”的边界，再深入该组件。常见证据：

- UI：DOM/可访问树、截图、控制台、前端状态；
- 网络：请求时间、方法、payload、状态码、响应、request ID；
- 服务：结构化日志、trace ID、错误栈、配置；
- 数据：事务前后、版本号、缓存与索引；
- 变更：相关 diff、依赖升级、开关和部署差异。

不在报告中暴露凭证或完整个人数据。

## 原因假设

用统一格式：

```text
假设：<机制> 导致 <观察结果>
依据：<当前证据>
反证条件：若 <检查结果>，该假设不成立
最小验证：<单一检查或实验>
结论：已证实 / 已排除 / 证据不足（置信度）
```

测试脚本失败的常见原因包括：定位器漂移、等待条件错误、共享数据污染、执行顺序依赖、环境/开关不一致。只有确认脚本预期仍符合需求后才修脚本。

## 严重程度与优先级判定

这两个数是 Bug 单里最容易被写错的字段，**必须在写 Bug 的这一步就定下来**，不要留到发布阶段再补。

### 严重程度 S：只描述影响有多大

- `S1`：系统不可用、资金/安全/严重数据损坏等灾难影响；
- `S2`：核心功能不可用且无合理绕过；
- `S3`：非核心功能错误或存在可接受绕过；
- `S4`：轻微展示/体验问题，不影响主要任务。

只用 `S1–S4` 四个字面值。**不要写 `S0`**（不存在这一级），也不要混入
`致命/严重/一般/轻微`、`Critical/High/Major/Blocker` 形成第二套等级——
读者拿它和自己团队的 SOP 对不上，整张 Bug 表就失去了排序意义。

### 优先级 P：只回答"这次发不发"

> **P0 ⟺ 这个不修就不能发布。** 两个集合必须完全相等。

| 优先级 | 判据 |
|---|---|
| `P0` | 失败会造成资金损失、重复处理、跨系统数据不一致或安全越权，**且已被写进本次发布的阻塞项** |
| `P1` | 本期必须修，但有绕过或影响可控，不阻断本次发布 |
| `P2` | 可排期修复 |
| `P3` | 观察项 |

写完 Bug 后在 `release_decision.blocking_bug_ids` 里逐个列出阻断项。
门会检查这两个集合是否相等：标了 P0 却不敢写进阻塞项，或写进阻塞项却标 P1，都会被拦下。
这样做的目的不是增加字段，而是**让 P0 有成本**——只要 P0 必须同时出现在发布结论里，
"重要的都标 P0"就自然不成立了。

正例：履约已 LOCKED 仍受理退款、订单/库存/WMS 三方不一致 → `S1/P0`，写进阻塞项。
同一轮里幂等键未校验请求体（用户会拿到旧结果）→ `S2/P1`，本期修但不阻断灰度。

反例（禁止）：
- 「接口相关都很重要，所以全部 P0」；
- 契约校验类问题（缺参、字段超长）默认给 P0——除非它能绕过关键写入，否则是 P1；
- 严重程度写 `S0` 或 `致命`。

严重程度描述影响，优先级还要考虑修复成本、发布时间和业务决策。不要仅因"必现"就定最高严重程度。

## 影响分析

从以下方面决定严重程度与回归面：

- 受影响角色、租户、平台、版本和数据范围；
- 是否阻断核心任务，是否存在可接受绕过；
- 数据是否错误、丢失、重复、泄露或不可恢复；
- 是否涉及资金、权限、隐私、合规或外部通知；
- 发生概率、暴露频率、可检测性；
- 同一根因可能影响的共享组件和相邻流程。

严重程度与优先级的判定表见本文件上一节，不在这里重复。

初步分析必须把两种容易混淆的判断分开：

- `change_correlation`：回答“这个问题是否由近期哪次需求、代码、配置、依赖或部署变化引入”。优先核对时间线、diff、发布记录和开关变化；没有证据时写“未发现明确关联，需结合发布记录排查”。
- `blast_radius`：回答“同一个失败机制还可能波及哪些入口、角色、平台、数据或上下游”。优先从共享组件、共用接口、共用数据表和相邻状态迁移扩展回归面。

前者谈引入时间线，后者谈横向波及范围。禁止两项都只写“可能是公共方法导致”；也禁止把“可能由上周改动引入”写成已证实根因。

## Bug 写作检查

- 标题包含条件、动作和错误结果，而非“功能异常”；
- 步骤从可获得的初始状态开始，不依赖作者记忆；
- 测试数据具体且已脱敏；
- 实际结果是观察事实，期望结果有需求或一致性依据；
- 环境、复现率、证据路径、关联需求/用例完整；
- 同一执行关联多个开放 Bug 时，独立失败签名互不相同且证据可分别定位；
- 影响与严重程度一致；
- 初步分析包含问题分类、触发假设、近期改动关联和波及范围，并区分已证实、可能和未知；
- 复测建议覆盖修复点、相邻路径和回归面。
