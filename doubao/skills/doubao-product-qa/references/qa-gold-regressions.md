# 四类 QA 金标准回归样例

这些样例用于写终稿前的人脑校准；机器测试位于 `tests/test_skill_regressions.py`。重点不是复述案例名称，而是识别可迁移的判断边界。

## 样例 1：失败、待确认、Bug 与 Markdown 文件

### 正例

```text
总记录 15
通过 10
失败 3
待确认 2
正式 Bug 3

待确认：
- 水印截图：当前只能证明截图存在水印，尚不能证明产品错误或来源链路；
- 小样本性能预跑：样本、并发模型和稳定环境不足，先记录信号。

发布结论：暂不进入客户灰度。
准出条件：
- 权限：跨租户、撤权、匿名访问通过；
- 缓存：权限/内容变更后的失效与旧链接行为通过；
- 并发：正式模型下的竞态、幂等与资源上限通过；
- 审计：关键访问、撤权和失败均可追踪。
```

用户说“输出 Markdown，报告在前，用例和 Bug 单在后”时，最终必须存在：

```text
外链分享灰度测试收口报告.md
├── 测试报告
├── 详细用例
└── Bug 单
```

并且 `qa_deliver.py` 回执返回该文件的真实定位，最终回复里的链接逐字来自这份回执。

### 反例（禁止）

```text
通过 10，失败 5，Bug 5
```

错在：

- 把两个待确认直接并入失败；
- 把失败记录数当作 Bug 数；
- 把预跑当正式性能验证；
- 在聊天中用了 Markdown，却没有创建 `.md` 文件。

## 样例 2：枚举与统计口径

### 正例

```text
总记录 14 = 通过 9 + 失败 3 + 待确认 2
严重程度：S1/S2/S3/S4
优先级：P0/P1/P2/P3
```

报告中的三个口径分开：

| 口径 | 示例 | 来源 |
|---|---:|---|
| 失败记录 | 3 | 最新 executions |
| 正式 Bug | 经过证据与归因后的数量 | bugs |
| 根因 | 被证据支持的独立机制 | analysis |

### 反例（禁止）

```text
严重程度：S0
失败 3，所以 Bug 3，所以根因 3
```

错在：

- `S0` 不属于受控枚举；
- 一条根因可能造成多条失败；
- 失败也可能来自环境、数据、需求或证据不足；
- 三个数字不能互换。

## 样例 3：性能预跑和待确认

### 正例

```text
总记录 17 = 通过 11 + 失败 4 + 待确认 2
R16：待确认
R17：待确认

R17 validation_scope=precheck
样本=少量预跑
结论=发现性能信号，但不足以建立正式 Bug
下一步=固定数据、预热、并发模型、持续窗口和阈值来源后正式复测
```

性能 Bug 的最小证据配方：

1. 明确指标与阈值来源；
2. 固定环境、版本、数据量和预热条件；
3. 明确并发/吞吐模型与持续时间；
4. 保存原始结果、时间线、服务端资源和错误率；
5. 至少一次可复现正式失败；
6. 将预跑与正式执行使用不同 execution ID。

### 反例（禁止）

```text
三次请求偏慢 → R17 失败 → 创建性能 Bug
```

错在样本、环境、阈值、规模和复现均不足。正确写法是“待确认 + 最小补证动作”。

## 样例 4：轮次范围、业务状态和 Office 成品

### 正例

用户只要求第一轮测试方案时：

```text
scope.included_rounds=["round-1"]
scope.excluded_rounds=["round-2","round-3"]
```

后续轮次可以帮助理解背景，但不能进入第一轮用例、统计或结论。

状态 oracle 正例：

```text
中间业务状态=AUTO_APPROVED
最终业务状态=REFUND_ACCEPTED
技术执行结果=SUCCESS
外部副作用=退款任务仅创建一次，审计记录包含规则版本
```

Office 交付正例：

```text
delivery.format=multi
artifacts=[
  {format: docx, filename: 退款申请与审核功能测试方案.docx},
  {format: xlsx, filename: 退款申请与审核功能测试用例.xlsx}
]
```

回读配方：

- DOCX：标题层级、表格、长文本、版本、结论；
- XLSX：Sheet、行列数、字段类型、枚举、换行、公式和空值；
- 两个文件：逐项存在、非空、文件名一致、revision 一致；
- 数据抽样：检查是否出现整列无意义常量、截断、数字文本化或状态混列。

### 反例（禁止）

```text
第一轮方案引用第二轮执行结果；
AUTO_APPROVED = SUCCESS；
两个 Office 文件只检查“能打开”；
XLSX 某列出现 21 个无语义的 26，仍直接交付。
```

错在范围污染、业务/技术状态混淆和只做容器级检查。Office “可打开”只是结构检查，不等于内容与版式回读通过。

## 终稿自检话术

提交前用以下对照逐项问自己：

- 我写的是“观察到”，还是把推测写成事实？
- 每个待确认是否有影响和最小确认动作？
- 失败、Bug、根因是否分列？
- 预跑是否仍标为 precheck？
- 业务中间态、终态、技术结果和副作用是否分开？
- 是否只使用请求范围内的来源和轮次？
- 用户要求的每个文件是否真实存在且回读？
- 最终路径是否逐字来自 `qa_deliver.py` 回执？是否只调用了一次上屏工具？

任一答案为否，禁止发送终稿。

## 样例 5：未决边界、缺陷拆分与发布锁

### 正例

```text
Q-REF-001：30% 是否包含边界？status=open
TC-REF-030 expected_result=按两种口径分别验证：若含边界则进入人工审核，否则保持自动路径

EXE-REF-008 → BUG-REF-001
现象：状态错转且审计记录缺失
判断：当前证据只支持一个共同失败机制，合并为一个 Bug。

QA_FLOW_STATE=DELIVER_BLOCKED
DELIVERY_LOCK=OPEN
（唯一会走到这里的原因：盘上没有产物可发。产物存在但不够好时一律放行 + 披露。）
```

### 反例（禁止）

```text
Q-REF-001 仍待确认，但 TC-REF-030 写“30.00% 均转人工审核”；
同一 EXE-REF-008 无独立失败签名地拆成两个开放 Bug；
`qa_deliver.py` 报 DELIVER_BLOCKED 后绕开它自己调上屏工具；或对同一产物重复调用上屏工具造成重复卡片。
```

错在把未决口径当成确定事实、把表象数当缺陷数，以及绕开唯一交付口自行上屏。
