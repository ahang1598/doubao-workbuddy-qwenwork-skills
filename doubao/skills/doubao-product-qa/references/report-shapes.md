# 报告体裁

同一套骨架套所有任务，等于所有人拿到的产物长得一样。本文件定义五种体裁与它们的触发条件。
体裁由 `scripts/report_shape.py` 在每次 `qa_flow.py anchor` 时自动判定并印在输出末尾——
**执行者不需要自己选，照体裁卡写即可**。

有一件事要先讲清楚，否则容易做反：

> **同一类任务下结构相似是正确的。** 三份收口报告的骨架本来就该接近，
> 因为 go/no-go 会议需要的就是那几件事。差异应该来自命中的体裁、
> 按材料取舍的专节、以及用业务词命名的标题——不是为了不同而随机换顺序。

## 五种体裁

| 体裁 | 触发条件 | 章节骨架 |
|---|---|---|
| `release-gate` | 有执行记录，要给 go/no-go | 结论 → 需求口径与资料冲突 → 业务链路与范围 → 风险排序 → 执行结果复核 → 已确认缺陷 → 待确认 → 回归安排 → 准出条件 |
| `rule-model` | 规则引擎/状态机类，且材料里**事件时间 ≠ 到达时间**并存在乱序或补传 | 决策摘要 → 规则来源与处理模型 → 关键序列重算 → 逐条复核 → 风险排序 → 已确认缺陷 → 待补证 → 尚未执行的重点 → 修复回归 → 准出条件 |
| `plan-only` | 没有任何执行记录（只有 PRD/原型） | 测试范围 → 风险点 → 需求口径与存疑项 → 测试用例 → 开放问题 → 已知未覆盖 |
| `bug-review` | 用户只要 Bug 复核或归因 | 归因结论 → 证据链 → 分层定位 → 影响与波及范围 → 回归点 → 待确认 |
| `incremental` | 多轮增删改，本轮只处理增量 | 本轮变更 → 受影响集合 → 增删改对账 → 重验结论 → 未受影响范围 |

## 专节按材料取舍

体裁卡给出的章节列表**已经**按本次材料删掉了不适用的段：

| 段 | 只在什么时候出现 |
|---|---|
| 需求口径与资料冲突 | canonical 里有 conflicts，或材料里出现变更单/优先级声明 |
| 已确认缺陷、回归安排、修复回归 | 确实有正式 Bug |
| 待确认 / 待补证 | 有待确认执行或缺陷候选 |
| 尚未执行的重点 | 有未执行用例 |
| 需求口径与存疑项、开放问题 | 有开放问题，或 PRD 自带「待确认/存疑点」章节 |

**不要给被删掉的段补一个"无"。** 「待确认：无」「阻塞与后续动作：无」这类空壳
既占版面又暗示"已经查过了"，是成品噪声。

## 判据是标定过的，不要随手放宽

`rule-model` 的判据早期写成"材料里出现 HH:MM:SS 或 event_time"，
结果四道题里三道命中——因为任何 QA 材料都有日志时间戳。
按四份金标准反标定后改成 **双时间轴 + 乱序/补传** 才回到 4/4 正确。

改判据前先拿四份金标准跑一遍：金标准判错了就是判据错了，不是金标准错了。

## 标题用业务词

体裁卡末尾给出本次材料里的高频业务专名。用它们给章节起名：

| 通用名（不要） | 业务名（要） |
|---|---|
| 数据分析 | 关键序列重算 |
| 需求梳理 | 最终需求口径 |
| 功能测试结果 | 外链撤销与 CDN 失效复核 |
| 问题汇总 | 组合优惠分摊与退款一致性 |

读者扫一眼目录就该知道这份报告在讲哪个业务，而不是"又一份 QA 报告"。
