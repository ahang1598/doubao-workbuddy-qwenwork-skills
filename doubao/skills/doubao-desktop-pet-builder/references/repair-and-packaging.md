# 修复与打包工作流

## 修复模式

1. 运行只读审计：`python scripts/audit_project.py <工程目录> --json <报告>`。
2. 创建独立修复副本，排除 `node_modules`、`.webpack`、`out`、`release`、日志和缓存。原地修改必须由用户明确要求。
3. 分类为：阻断启动、安全边界、素材/功能脱节、动态不足、角色体验、UI、跨平台、测试缺失、构建执行。
4. 优先局部修复。旧工程若要采用 v2 的独立母版和语义抠图，创建独立 v5 脚手架并迁移业务配置，不在旧工程中手工刷新契约哈希。
5. 修复后先 `npm run dev` 让用户验证原问题，再跑完整自动检查和打包。

重点检查：

- 每个状态是否在代码中可达，条件功能关闭时是否仍有孤儿素材；
- 互动是否与角色匹配，是否同时产生动作、反馈和数据变化；
- 是否全部单帧、没有呼吸回弹，或用程序形变冒充真实动作；
- 面板/提醒是否带系统标题栏、宿主底色、系统滚动条、默认表单感、裁切或通用占位文案；
- 默认/最小桌宠尺寸是否仍偏大，托盘图标是否为空，菜单是否缺少角色化 emoji；
- `nodeIntegration`、context isolation、sandbox、CSP、IPC sender/payload；
- 多屏/DIP、提醒持久化、文件路径、键盘监听降级、异常日志；
- 构建是否有锁、同盘临时目录、完整日志、状态和单次超时。
- spec 的素材路径是否与实际大小写一致，Webpack 是否递归导入，开发启动是否拿到首帧 `naturalWidth > 0` 的就绪证据；
- `.build/activity.lock` 的 PID 是否仍存活，日志错误是否被错误地描述成“不影响主功能”；
- JSON、HTML、包名和界面文案是否出现 UTF-8/GBK 乱码。
- 旧 `locked-chroma`/`adaptive-flood` 工程是否出现白色实心块、渐变底色、地面/投影残留；迁移到 v5 时保留原素材备份，并让不透明输入重新经过语义分割。

每个“已修复”都要有复现、自动检查、截图或用户试玩证据。当前系统无法验证时写“待在目标系统确认”。

## 单独打包模式

1. 确认工程能启动、受控锁机制存在、名称/ID/版本/图标明确；过期锁应由脚本安全回收。
2. 先运行已有测试；没有测试时至少审计、类型检查、资产/体验覆盖和启动冒烟。
3. 让用户选择安装版还是便携版。只想本机先用时，优先 `package:win` 并启动应用目录中的 EXE 验收。
4. 按 [build-execution.md](build-execution.md) 启动唯一受控构建，等待最终状态，不轮询猜测或并行重启。
5. 核对 manifest、SHA-256，实际安装/解压后走真人短清单。

Squirrel 失败不等于 package 失败。可以报告“应用目录可运行、安装器失败”，但未经用户选择不得擅自改为 ZIP 并宣称完成。

## 报告最小字段

- 模式、源工程、修复副本或生成目录；
- 已验证平台/架构与未验证平台；
- 试玩反馈及处理结果；
- 自动测试命令、退出码、日志、截图路径；
- 素材/功能覆盖和多帧状态数量；
- 真人验收逐项结果；
- 产物、模式、大小、SHA-256；
- 未签名提示、剩余风险和待确认项。
