# 阶段一：怎么写 process（解题 + 规划，专注、零像素数学）

这一步只做一件事：**把题解对**，并把"最终采纳、导向最终答案"的关键视觉证据整理成一个 process（内嵌 JSON，只活在你的思考里、不直接输出给用户）。**不要在这一步碰图像宽高 / 像素 / 绝对坐标**——只用 0~999 的相对比例坐标（凭视觉判断"在画面约百分之几处"）。这能避免 grounding 被换算数学带偏。

process **不限步数**；它列出的证据最终会被你合并进**一张**可视化图（阶段三）。解题旁白不写进 process（讲解在回复正文里说），process 只承载"在图上标什么"。

## process 数据结构

```json
{
  "steps": [
    {
      "type": "标注类型",
      "coords": [
        {"kind": "point", "x": 123, "y": 456, "label": "短描述"},
        {"kind": "bbox",  "xyxy": [100, 200, 300, 400], "label": "短描述"}
      ]
    }
  ],
  "final_answer": "最终答案文本"
}
```

- `steps[]`：每条最终采纳的视觉证据一项。`type` = 标注类型（见"标注类型"节）；`coords` = 该步要在图上标的点 / 框。
- 只列**最终采纳**、导向 `final_answer` 的视觉步骤；试错 / 回溯、纯逻辑 / 算式 / 汇总都不进 process（并入 `final_answer` 与回复正文）。每条 step 都对应图上的真实标记。
- `final_answer`：像不限字数地直接回答用户——给结论 + 完整支撑依据 + 必要展开，分点 / 分段讲清（分析 / 解读 / 建议 / 开放类一般 ≥500 字），别因前面有 step 就压成一两句；唯一确定答案的题给出含必要单位的明确结论即可。

## 硬性要求

- **结构严格照上面这个 schema，不许改造**：顶层只有 `steps` + `final_answer`（多图任务可加 `images`）；每个 step 只有 `type` + `coords`（多图任务可加 `img`）；每个 coord 必带 `kind`（`point` 或 `bbox`，多图任务可加 `img`）。`type` 只能取下面"标注类型"里的名字。**除多图的 `images`/`img` 外，禁止出现自创字段 / 自创结构**（如 `action` / `groups` / `members` / `count` / `color` / `unpaired` / `image_url` 等一律不许）。
- **多图任务（题目给多张图）**：顶层 `images:[url…]` 按附件顺序列出全部图；每个 step / coord 用 `img`（图索引，默认 0）绑定到某张图，其 0~999 坐标相对**那张图**；跨图对应 / 对比用 `match_pair`，两端 coord 各带自己的 `img`。单图任务省略 `images`/`img`。
- 每个 coord 必须**真实指向**它 `label` 所描述的图像对象（图像忠实，禁"指 A 描述 B"）；只标图中**真实存在**的对象，禁在空白 / 不存在的物体上凭空打点画框（宁少勿假）。
- **标注必须有信息增量**：只标**能回答用户问题**的关键证据——coord 指向原图中需帮助才看清的真实对象 / 位置 / 关系（定位 / 追踪 / 配对 / 读细节）；**别把报错标题 / 现状文字 / 用户一眼可见或已知的内容再标一遍**（零增量）。每条 label 要写出**依据 / 为什么 / 差异 / 对应**，而非只复述物体名称或数字。遮住字幕后，点 / 线 / 框本身就要能说明这步为何成立。纯计算 / 汇总在图上无新东西可指 → 并入文字，**禁止把算式 / 结果当点画到图上**。
- **标注对准关键细节、别贪大**：`bbox` 紧贴目标本身，不要大到把整片背景 / 大半张图都圈进去（要点出某处细节，就把框缩到那处）；`point` 落在真正承载判断的关键位置，别无脑铺一堆密集点。
- **path_grow / 路径 / 追踪 / 迷宫 / 连线类**：沿真实曲线**密集采样**（拐点必采 + 长直段中间补点），短线 ≥6 点、长曲线（多弯 / 横跨大半张图）≥12 点；**整条 trace 完才下结论**（禁只看起点几跳就猜结论），point 沿曲线方向**单调推进、不得回跳**。
- **node_walk / A→B 方向指引**：**恰好 2 个有序 point**（A=起点 / 参照，B=目标 / 下一步位置），渲染必是一条 A→B **带箭头头**的有向线；点数≠2、方向含糊、或渲染成无箭头头的裸线 → 违规。

## 坐标约定（0~999 相对，强制）

- **你的 grounding 输出（`<point>` / 定位坐标）本身就已经是 0~999 相对坐标——直接照抄这些数字填进 process，不要再做任何处理。** 这是本步最容易出错、也最致命的地方：定位时你脑子里得到的就是 0~999 的相对值，原样写进 `coords` 即可。
- **绝对禁止以下任何一种操作（出现即错）**：① 估计 / 假设 / 读取图片的像素宽高（如"图片宽 670、高 1280"）；② 把坐标当像素再"换算成相对"；③ 给坐标乘任何系数（如 `×999/宽`、`×1.49`、`y_px×0.78`、`x_rel = x_px×…`）。CoT 里一旦冒出"宽…px / 高…px / x_px / 乘以某系数"这类念头，就是在把已经正确的相对坐标改坏——立刻停手，回到"直接照抄 grounding 数字"。
- 0~999 → 画面位置的换算**只在阶段三的 HTML 渲染时发生一次**（`x/999`），推理 / 规划阶段一律不碰像素、不碰宽高、不做换算。
- 一律 **0~999 整数相对坐标**：`(0,0)`=左上，`(999,999)`=右下。
- `point`：`{"kind":"point","x":…,"y":…,"label":…}`；`bbox`：`{"kind":"bbox","xyxy":[x1,y1,x2,y2],"label":…}`，要求 `x1<x2`、`y1<y2`。
- 用线 / 路径连接的（path_grow / node_walk / match_pair）：用有序 `point` 列表表达（node_walk 恰 2 点、A→B 有序）。

## coord.label（图上给用户看的字幕，必须非空）

- 必须写清该位置、区域或关系为什么支持结论；可按任务包含计算结果、标号位置、颜色 + 对象类别、验证标记或必要短算式，但纯计算与汇总仍留在正文，不得为了满足格式凭空在图上打点。
- 只写面向用户的话，禁 `x=` / `y=` / `image_idx=` / 归一化坐标 / `bbox` 等机器字段。
- 密度自适应：coords 密集时用简单标号（「①」「(2,4)」）；coords 少时写更具体语义（对象 + 属性 / 结论 / ✅❌）。
- 例外：path_grow / 连线 / 追踪类的**中间采样点**只为还原曲线，label 用轻量统一标记（「轨迹」「·」）即可，密集采样优先于 label 丰富度。

## 标注类型（每个 step 选 1 个，按 1→6 顺序首次匹配即停）

1. **path_grow**：沿单条连续曲线 / 折线**密集采样 ≥6 个有序 point**，使 polyline 能复原原曲线几何。coords 全为 point，按曲线方向严格排序（首=起点、末=终点），拐点必采 + 长直段中间补点。适用：「沿一条线 / 一段轨迹 / 一条边界 走或量」。反例：<6 点 / 含 bbox / 散点不成曲线 → 违规；**原图已清晰画好的现成曲线（股票 / 价格 / 成交量走势线、函数曲线、统计折线图）一律不要描摹**——沿已有线重画一遍零信息增量，直接用文字说趋势 / 结论。path_grow 只服务于需要你帮用户顺着走通 / 厘清的路径：迷宫、连线 / 配线、轨迹追踪、图遍历路线、需顺走的边界 / 管道。
2. **node_walk**：一个 A→B 箭头表示「一段有向移动」，两类都用它：(a) 离散图遍历——从当前节点沿 1 条边走到相邻节点（第 k 跳 / 按权重 / 编号选下一跳）；(b) 操作指引——把部件 / 对象朝某方向移动一段（推 / 拉 / 扳 / 抬 / 拧 / 转 / 移，须有明确方向位移）。coords 恰好 2 个 point（A=起点 / 被操作锚点，B=终点 / 目标位置）。适用：「到 / 沿 / 走向 / 下一跳」或带方向操作动词。反例：两对象只是同时出现无移动 / 仅定位 / 纯点击按键 / 单纯注视 → bbox_zoom；连续曲线 → path_grow。
3. **match_pair**：表达**一对**元素之间的对应 / 关联 / 匹配 / 属于 / 同源关系。**一个 match_pair step 恰好 2 个 coord（就是这一对）**；要表达多对，就拆成**多个 match_pair step**（每对一个 step），别把多对塞进同一个 step。反例：只是同类 / 并列无两两映射 → count_pop；一个 step 里塞 >2 个 coord → 违规。
4. **count_pop**：N 个独立、并列、互不依赖（无配对 / 邻接 / 路径关系）对象的逐个标定 / 计数。coords 为 N 个对象各 1 个 coord（多为 point，也可全 bbox）。适用：「数总数 N」/「列出所有 X」/「逐一检查 N 个候选」/「N 个候选里逐个验证 ✅❌ 选 1」。反例：存在两两映射 → match_pair；构成连续轨迹 → path_grow。
5. **bbox_zoom**：聚焦读取 1 块 ROI（1 个连续区域）的细节，动作对象是 1 个连续区域而非 N 个并列对象。coords 主体是 1 个 bbox，可附少量 point / bbox 在 ROI 内做锚点。反例：动作对象是 N 个并列对象 → count_pop；两两映射 → match_pair。
6. **default**：兜底——仅需 1~2 个参考锚点的简单定位 / 强调。硬约束：coords 总数 ≤2 且不允许是 bbox（要框 ROI 改 bbox_zoom）。

## 写作

- 是否拆分 step 取决于「一个标注能否完整清晰地表达这一步」——要素过多 / 混乱 / 互相遮挡就拆，否则合并。
- 边解题边在脑中规划，最终把**采纳的关键步骤**用面向用户的讲解口吻写进 JSON（每条 text 直接陈述结论与依据，不写「观察 / 框选 / 下一步」这类自述）。
- 图片题或几何题只有在用户明确要求原图标注，或图中视觉证据确实能显著降低理解成本时使用本模式；普通做题、改题、代码分析和软件 UI 操作说明不因附带图片自动触发。
