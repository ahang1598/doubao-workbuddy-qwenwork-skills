# 通用组织与 View 规则

只使用 revision 3。决策顺序：事实关系 → 阅读任务 → View 组织 → 组件。不从组件、标题或分组数反推业务关系。

## 组织不是拆屏

| 原始事实/任务 | 组织维度 | 不得推导 |
| --- | --- | --- |
| 独立设施、兴趣点 | distribution | 清单编号不是访问顺序 |
| 一条完整线路/命名轨迹 | route | 路段、营地不是日期或备选方案 |
| 一条线的连续片段 | segments | 片段不是互斥选择 |
| 多条线路组成网络 | route/thematic | 多线路不自动成为 alternatives |
| 同一目标的可选方式/走法 | alternatives | 需明确比较关系，不只按数量判断 |
| 明确访问顺序 | itinerary | 有序不等于分日 |
| 用户要求排日程或采纳日程 | days | 来源建议耗时不构成日程 |
| 区域/分析数据 | thematic | 不从行业/地名猜统计口径 |

task.evidence 引用原始请求/数据并声明适用对象。alternatives/schedule 必须来自用户意图或已采纳关系。资料有多条路线时可拆阅读 View，不必虚构“备选方案”才能拆屏。

## 何时拆 View

分天与展示范围是独立决策，不覆盖显式 `views`。有独立详情时，总览侧栏使用同组摘要入口；地图由 `organization.overview` 与组件声明决定保留点线内容还是集合入口。详情按当前访问范围编号，保留同一地点的多次访问；全程总览可合并已明确身份的共享地点，不删除访问记录。

逐项检查：路线能否清楚区分？共享节点是否有多种局部角色？交叉和标签密度是否遮住主要信息？内容是否需要不同尺度？用户是看整体关系还是选一种走法？

过载时，用同一批事实组织不同阅读范围并记录 view-split 依据。例如网络关系总览、单条线路详情、独立设施分布。不要固定“超过 N 条就拆”，不要虚构新方案或日期。没有过载且任务单一时一个 View 足够。

多个独立日程或线路分组同屏时，必须为各组提供可阅读去向：默认建立同组独立内容 View；确实适合同屏完整阅读时，在 `organization.readingScopes[groupId]` 声明 `{mode:"inline",viewId,reason}`。inline 不是逃生开关：该 View 必须实际包含分组摘要、每条路线的名称与已有描述、全部成员地点。只有色条、图例或选中高亮不算详情；不能为了通过校验把真实航线虚构成备选行程。连续路段仍使用 segments，不强拆为独立方案。

每个 View 都要从初始 View 经实际控件可达，并能返回。Compiler 在多 View 缺少 Tabs 时补标准切换入口并记录诊断，不自行创造业务 View。显式 Tabs 若截断目标、动作无效或引用不存在的 View 则拒绝；不能仅以 `views` 数组非空判断可用。

方案/分日简介独立于地点详情：保留 group.summary 与 view.summary（后者同字段优先），已有简介必须显示，即使当天只有一个地点。时长、交通等已有字段同样展示；缺少独立地点坐标时不凭空补点。


一条命名线路默认保留全线。确有不同出口/走法才是备选；连续路段是 segments。建议天数不是分天依据。网络节点在总览和单线详情中都不自动产生行程起终点或访问顺序；交通路线的显式角色另按当前范围验证。

## 是否需要总览、何时用卡片

本节是唯一的阅读决策规则，不把场景案例转成页面模板。分别判断地图表达（聚合或空间内容）、侧栏组织（导航、比较、顺序、真实层级）和点位角色（访问、端点、换乘、独立地点）。优先级：事实与内容完整性约束 → 用户明确要求 → 业务偏好 → 通用默认。

少量业务偏好：普通旅游优先集合入口，自驾或全程包车优先完整路线；有明确游览顺序的点使用编号，包含首尾。单组或无详情不强行添加集合层级，无序地点不编造编号。`travel_route` 默认保留全程路线，`travel_plan` 沿用通用推荐，包括已有的驾驶路线推断；仅某段为 driving 不代表整个旅游任务是自驾。

引擎 `recommendOverview` 负责基础推荐，不强制最终组件选择，也不静默重写完整 Plan。`task.purpose:itinerary` 表达已采纳的有序游览；普通多组旅游具备唯一详情、可信且互异的代表位置时默认 collection，自驾优先全程点线，其他场景仍按自身任务选择表现。独立详情、成员身份、代表位置及同点情况由程序检查，模型填写的 reason/spatialReason 不能代替事实条件。用户明确偏好继续作为约束，模型实测调整不能覆盖它。

只有用户明确要求不同表现时，才在 Spec 的 `task.overviewPreference` 记录 `{mode:"content"|"collection",origin:"user-request",reference:"用户原始要求"}`；工具任务在根层填写同名字段，由程序复制到 Spec。没有明确要求就省略，不能把模型的设计理由改写为用户要求。`task.travelScene` 保留工具声明的 travel_plan/travel_route，使生成和编译校验采用一致场景。用户选择 collection 也必须满足真实代表位置和独立详情条件；完整 Plan 仍需提供合法组件与入口链接。此来源声明不等于自动证明用户确实说过该要求。

行程的代表位置不要求模型填写。工具导入、直接 Spec 和完整 Spec＋Plan 编译统一使用工程默认值：分组成员均有明确 `orderPurpose:visit` 与有效 order 时，按访问顺序取首个有效地点；否则按成员输入顺序取首个有效地点。坐标必须来自已有真实成员，程序用 adopted-data 记录派生依据，不新增访问顺序、区域中心或路线起点事实。已有显式 representative 保留兼容并继续校验，不用默认值掩盖错误。非行程任务不自动派生。不能以“均值落在水面”“可能碰撞”等假设推翻集合推荐；实际布局交由组件和验收处理。

这不要求用户前置提供数据文件。用户可仅提出自然语言地图需求，现有流程准备行程与解析地点坐标后，再执行默认选点。已有真实成员是落图时的数据条件，不是新增的用户输入字段；无有效坐标不能凭空造代表位置，也不能以默认选点掩盖缺失地点。

普通旅游按天进入详情，满足可信代表位置和空间区分时，默认生成集合入口；正常生成通过启动验收后直接交付，不额外检查展示。仅在用户要求调整展示或维护调试时检查实际效果。取景或布局问题先修相机、留白和布局；实际仍不适合分组导航时，模型可改用内容总览，并在 overview.reason 写明具体 View、观察到的问题、已尝试调整及对应报告或浏览器记录位置。“先看全程再进入某天”“可能重叠”“连线更直观”等泛泛理由不能替代实际检查。调整后保留完整事实、独立详情和侧栏入口，开发维护执行受影响检查及完整回归，正式生成执行最终启动验收，不以改表现掩盖维护缺陷或绕过修复预算。编译器只验证结构与事实，不声称从文字理由证明实测发生或视觉效果更好。没有可用于派生的有效成员时保留侧栏入口与地图内容。交通方式同起终点比较优先内容总览与紧凑方案列表，不使用关系树重复列出相同路线和地点。

先确定用户要完成的动作，再选表现：用户明确要求优先，其次实际任务与已采纳事实关系，最后才是默认策略；搜索资料的篇章、日程标题和路线数量不能改变用户任务。

在 `organization.overview` 记录决策：`{mode:"content"|"collection",purpose:"navigate"|"spatial",viewId,reason}`。集合另写 `spatialReason`；省略总览写 `{mode:"none",reason}`。purpose 表示阅读目的，mode 表示地图表现：navigate 可以使用点线地图搭配侧栏入口；spatial 保留点线面，不能替换为集合卡。Compiler 按实际分组范围确定侧栏层级，不猜测或改造地图组件；多个详情没有总览时必须声明 none 及理由。

| 用户要完成的动作 | 默认阅读目的与呈现 |
| --- | --- |
| 从明确的天、方案或主题范围中选择一个继续阅读 | navigate；总体简介、分组摘要入口；地图集合卡另看可信且可区分的代表位置 |
| 观察连接、覆盖、分布、路径差异 | spatial；点线面总览；已有独立子视图时侧栏仍提供摘要入口 |
| 绘制一条命名线路，来源却按几天记录 | 单一完整线路，不把检索来源组织升级为 days，不额外套唯一方案入口 |
| 区域指标或热力分布 | spatial；指标、图例、受控筛选和选中查询，不强造日程或地点清单 |

资料中的来源分组和展示分组必须分开：只有 user-request 或 adopted-data 的 schedule/alternatives 依据可支持分日或备选。不同游记的建议天数不是多方案证据；冲突的节点顺序和走向须核实，不能拼接成确定路线。

总览应回答不同于详情的问题：整体空间关系、完整行程或入口选择。先判断其独立价值与阅读目的，再选组件。完整任务拆成多个日程/范围详情时，默认提供整体入口；单一范围、与详情重复或用户只需指定局部时可以省略。多个 View 不机械强制总览，但不能无声遗漏：省略须用 `organization.overview:{mode:"none",reason:"具体理由"}` 明确记录。

- 内容总览：任务要求完整路线、网络或分布，画真实点线面；过载用分范围/详情/筛选，不自动替换成卡片。
- 入口总览：首先浏览各单元摘要、再进入独立详情，且每组有可信地理代表位置、卡片之间形成有意义的空间区分时，优先集合卡。不要求用户先说出组件名称。只聚合所属分组的路线与成员，独立地点、区域、其他分组及分析层可以共存；每卡显式绑定详情。地图卡片与侧栏入口必须指向同一 View。卡可代表某一天、主题区域或方案，不把这些都改称为备选方案。

未填代表位置不是退回内容总览的理由：先执行上述工程默认选点。确实没有有效成员、缺少独立详情或默认代表点同址时，记录具体原因并保留侧栏入口与内容；不挪坐标、不尝试虚构互异位置。内容总览直接覆盖主要内容；入口总览经合法链接覆盖详情内容，由独立 checker 检查。

## UI 阅读层级与动作

先定视图角色、范围与操作，再按 Catalog 能力选择组件。不得因为 routes/stops 存在就把两份完整列表都追加进总览。

- 有独立子视图的多组总览：整体简介与 `view.groups` 摘要入口；不同时输出所有 `view.routes`、`view.stops` 或完整关系树。地图仍按目的展示网络、分布或集合。没有子视图的单屏分布是直接内容阅读，默认平铺列表；只有真实父子包含关系才使用树，不强造导航目标。
- 子视图：当前组简介、已有指标、当前组成员；有访问顺序才用时间线。仅一个地点也保留当天简介。
- 单一完整范围：直接展示内容与地点/路线列表，不制造总览到唯一方案的冗余层级。
- 选中详情：只展示当前实体；关闭不删除范围简介和浏览列表。网络总览中的共享地点读取地点事实，不混入某一次访问的局部事实；进入单线后才使用成员上下文。

侧栏分组入口使用 `activate-view`，Compiler 按相同 groupId 的唯一独立子视图解析 `viewId`；无地图集合元素也能导航。集合入口已有显式映射时沿用同一目标。有多个候选则诊断歧义，不按标题猜测。摘要名称与说明投影自目标 View，来源唯一，不另外编写一套文案。不得用 `select-element` 冒充入口，也不能截断必要入口。

地图普通线/点点击仍是原地选择，侧栏入口是进入范围；两种控件不能使用相同的开关选中语义。切换后导航、地图、简介和成员列表由 activeViewId 同步更新，清除旧实体选择；Tabs 提供返回总览。

| 阅读任务与空间结构 | 默认选择 |
| --- | --- |
| 独立日程/主题范围，重点看摘要再进入，代表位置可信且可区分 | 集合入口总览 |
| 完整路线的连续片段，重点看全程走向 | 点线内容总览 |
| 网络的连接、共享节点、覆盖关系 | 点线内容总览 |
| 同起终点的多种交通方式，重点比路径、耗时和价格 | 点线对比总览＋侧栏方案摘要，不把卡片都堆在出发地 |
| 用户明确要求完整轨迹或同屏比较全部路线 | 点线内容总览 |

这些是关系与阅读任务的规则，不是地名、行业或天数特判。多日不必然用卡，多交通方式也不必然禁止卡：仍检查代表位置、空间区分和比较目的。工程按实际代表位置检查同址，不按模型猜测的覆盖范围、重叠或密度撤销集合推荐。不要通过挪坐标制造区分，也不引入固定距离阈值。

使用总览时在 `organization.overview` 声明 `mode:"content"|"collection"`、`viewId` 与 `reason`；集合另写 `spatialReason`，解释代表位置及空间区分，不只是“有多个分组”。编译器检查总览声明、节点一致性、代表位置依据、同点冲突、完整详情链接及用户明确偏好，不再以偏离默认推荐为由拒绝合法 Plan。文字理由解释实测后的决策，不代替客观条件或用户偏好来源。自动验收不宣称证明用户原话或实测说明的真实性。

## 侧栏的阅读职责

可见路线必须提供非空 `name`，不能以内部 ID 代替。路线说明使用 `properties.description`，也支持明确的 `properties.note`；不凭类型枚举补造说明。列表的 `select-element` 必须有当前可选元素；分组摘要有对应子视图时使用 activate-view；没有导航目标或可选地图元素时才只读。

多线路网络中的同一 `placeId` 默认只绘制一次，并保留所有 member 身份供关联及校验；共同起点或共同终点保留一致角色，混合角色使用普通共享节点。单线详情保留局部角色，明确访问顺序中的重复到访不合并。不同 placeId 不按名称或坐标猜测为同一地点。显式互相冲突的共享节点选型会报错，不悄悄替换。

部分分组使用集合卡时，共享点的成员集合与起终点角色只计算未聚合的可见分组；聚合组的访问记录仍留在源数据及对应详情，不参与总览共享点身份。区域、分组、独立地点的关系根可以并存，不能因为存在区域就隐藏其他根。非总览的多组内容视图同样保留 `view.groups` 列表，但条目用于当前范围内容选择，不自动变成跨视图入口。

侧栏分为当前范围摘要、常驻浏览列表、选中对象详情；不把每个区块都做成长详情卡。当前 Catalog 的数据绑定和 props 示例见组件 guidance。

| 当前阅读范围 | 默认侧栏内容与动作 |
| --- | --- |
| 集合入口总览 | 总体摘要＋紧凑分组入口，点击进入详情；不重复整段地图卡文案 |
| 方案比较 | 方案摘要列表，以同口径已有指标比较；点击强调或进入明确详情 |
| 完整多日/分段内容总览 | 按日/段摘要与详情入口，不把各段局部序号拼成一条行程 |
| 单个有访问顺序的行程范围 | 名称、编号、已有简述和时间的常驻有序列表，点击选中地图点 |
| 单条交通路线 | 路线摘要＋起终点/途经节点的关系列表；拓扑顺序不伪装成旅游访问编号 |
| 独立地点/设施分布 | 当前地点的浏览入口及简述，点击看详情；不为使用 Timeline 发明访问顺序 |
| 区域或分析 | 指标、筛选、图例与必要区域入口，不强塞地点列表 |

摘要讲当前范围；列表支持未选中时浏览；选中详情补充对象完整说明、地址等，关闭不删除列表。没有额外内容不重复开详情卡。避免重复针对文案，不删除必要的导航与列表。

`view.stops` 按实际分组成员绑定，不依赖 `day`/`group-detail` 名称；单一 visit 顺序范围默认补充 `semi.timeline`。同一地点多次访问按 member 身份保留；名称与描述来自地点事实，成员属性可覆盖。多组各有局部顺序时使用 `view.groups` 摘要并进入详情，不展平为一条时间线。

只使用 Catalog 已支持的绑定：普通地点/交通节点可用 `view.entityRelations` 的受控关系列表＋`selected.properties`，不得把不存在的 `view.places` 填入 Plan。摘要用 `view.summary`，指标用 `view.metrics`，路线用 `view.routes`。无事实的可选摘要/指标/列表区块不输出“暂无数据”占位；声明了站点列表却没有成员、截断行程项必须报错。内部 role/mode/ID 不能填充缺失描述。数据已有但没有常驻阅读入口时，不能只靠选中详情声称完成行程阅读。

## 搭配约束

有 visit 顺序的整条路线用编号点，包含首尾。独立交通关系仅在显式 origin/destination 角色且当前可见线路拓扑一致时使用起终点，其余节点使用 common-marker；网络连接不产生行程起终点，真实换乘用 transfer-point。共享地点去重但保留一致角色：所有关联路线共同起点显示一个起点，共同终点显示一个终点；角色混合才使用普通节点。单线详情按当前范围角色显示。路线成员不能以“现实中也是地点”为由变成独立 POI，无线路关系才使用 point-marker。

专用交通线必须同时满足业务关系与几何证据约束，不能仅由交通方式决定；具体条件见 [Route.relation 与几何规则](canonical-map-spec.md)。访问顺序、网络和一般连接使用普通线。面区分 boundary/coverage/corridor/uncertainty，不为装饰闭合路线。同系列点线、侧栏和图例共色，多系列共享节点中性。

Tabs 只导航多个 View；Timeline 需访问顺序/时间。摘要、指标、图例和详情不重复同一事实，内部类型码、系列 ID、View ID 不作为展示文案。
