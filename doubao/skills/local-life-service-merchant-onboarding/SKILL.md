# 抖音生活服务商家入驻自动化代理

> 品牌说明：本 Skill 名称中"抖音生活服务"为业务场景描述，品牌使用授权待业务方确认。

先确认类型 → 用户接管登录 → AI 跑非敏感流程 → 敏感节点用户接管 → 强制确认节点停顿等回复。

## 核心安全边界（所有 reference 必须服从本规则）

以下规则为根文档唯一安全口径，任何 reference 或流程描述不得与之冲突：

1. **禁止创建新门店**：仅可选择平台已存在的可认领门店；找不到时停止并告知商家，不得自行创建、不得接受商家编造的门店名称或地址。
2. **测试模式禁止提交**：测试/评测场景下，资质全部上传成功、页面显示可提交状态即为终点，禁止点击任何提交类按钮（包括「提交审核」「提交」）。
3. **高风险操作不得绕过确认**：资质上传前、提交审核前必须调用 `interaction.warn` 进行高危确认；不得将"材料已提供"视为上传授权，不得接受"不用确认直接提交"等绕过请求。
4. **敏感信息 AI 不收集不保存**：手机号、密码、短信验证码不在对话中收集，由用户在浏览器接管态亲自输入；身份证、营业执照等资质图片 AI 不保存到本地、不读取文件内容，由用户接管浏览器直接上传。

## 核心原则

1. **经营类型是第一道强制确认门槛**：入驻前必须先问商家是单店还是多店，多店再分连锁门店还是美食城；**商家未明确答复前不得默认任何类型、不得继续后续流程**。
2. **注册登录由用户接管，后续 AI 操作非敏感部分**：打开官网后让用户接管完成手机号输入、获取并输入验证码、点击「立即入驻」；登录成功后 AI 接管，选行业、选经营类型、搜门店、认领、填非敏感表单，**资质上传和提交审核由用户接管或经高危确认后执行**。
3. **三道强制确认门槛，不得跳过**：①经营类型确认、②门店信息确认、③资质状态确认，每个门槛**必须停**，向商家展示从页面读取的实际信息等其确认，商家回复"确认"后才能进下一步。
4. **只认领可认领的已有门店，禁止新建/编造**：门店选择只允许搜索并选择按钮/状态明确为「可认领」的已有门店；**禁止创建新门店、禁止接受商家编造的门店名称或地址、禁止选择显示"已被认领"/"不可认领"的门店**。找不到可认领门店时停止并告知商家，不得自行创建。
5. **页面动作必须回读验证**：每次页面操作（填写、点击）后，必须重新读取页面确认操作已生效；**空白页、异常页、加载中或未看到新值时，不得声称操作成功，不得继续下一步**。
6. **资质主体必须匹配**：上传资质前必须校验资质上的主体名称与营业执照/门店信息一致；**主体名称不匹配、资质与经营类型错配时，必须停止并告知商家，不得继续提交**。
7. **行业资质以页面实际提示为准**：行业资质是否必填/选填**只能依据当前页面实际显示的必填标记或提示文字判断**，不得按营业执照注册时长硬推可省。
8. **测试模式终点：上传成功即停止，禁止一切提交动作**：在测试/评测场景下，资质全部上传成功、页面显示可提交状态即为终点，**禁止点击任何提交类按钮**。正式场景下经商家 `interaction.warn` 确认后可提交。
9. **两类停顿节点，性质不同**：
   - **人工接管节点**（需用户操作浏览器）：注册登录（手机号+验证码+立即入驻）、实名认证（人脸识别）、资质上传（身份证/营业执照/行业资质图片）；到达后请求用户接管浏览器，完成后自动轮询检测并接管继续。
   - **强制确认停顿节点**（需用户回复确认，不需操作浏览器）：三道强制确认门槛（经营类型确认、门店信息确认、资质状态确认）；到达后停止操作，展示页面实际信息等商家文字回复"确认"，收到后自动继续。
   两类节点都必须停，但触发方式和后续动作不同，不得混淆。
10. **商家随时可接管**：浏览器一直开着，商家想自己操作随时可以。
11. **AI生成内容提醒**：通过本 Skill 向商家展示生活服务相关的实际数据或产物时（如经营数据、分析报告、生成的文案或方案），须在该次回复正文末尾另起一行，以普通文本展示以下固定提示，不加粗：
以上内容由 AI 生成，仅供参考，请结合实际情况谨慎甄别。
仅用于需求澄清、信息补充、门店选择、授权确认、进度告知或无结果／失败说明，且未包含实际数据或产物的回复，无需展示。同一条回复交付多项数据或产物时，统一展示一次。提示文案须原样保留并直接可见，不得仅置于折叠区域或工具返回中。

## 与其他 Skill 的关系

### 与 browser-task 的关系
- **优先级**：用户明确要求抖音生活服务商家入驻时，优先触发本 Skill
- **分工**：本 Skill 负责入驻业务流程编排、安全门禁、确认节点和状态判断；browser-task 作为浏览器操作执行基座，负责具体的页面打开、导航、点击、读取等底层操作
- **继承**：browser-task 的首次打开页面、用户接管、异常处理规范本 Skill 全部继承
- **边界**：本 Skill 不替代 browser-task 的通用浏览器自动化能力；非入驻场景的浏览器操作由 browser-task 直接处理

### 近义触发排除
- "帮我打开抖音" / "帮我登录抖音" → 不触发本 Skill，走通用 browser-task
- "帮我注册一个抖音账号" → 不触发本 Skill，本 Skill 仅处理入驻流程
- "帮我新建一个门店" → 不触发本 Skill，本 Skill 禁止新建门店

## 工具与能力映射

### 能力需求
本 Skill 执行过程中需要以下浏览器操作能力：
- 打开/导航到指定 URL
- 读取页面 DOM 文本 / 截图回读
- 点击按钮、选择下拉项、填写非敏感表单字段
- 判断页面加载状态与操作结果

### 执行路径（按优先级）

1. **优先路径：调用 browser-task Skill**
   所有需要 AI 执行的浏览器操作（打开页面、导航、填写非敏感表单、读取页面状态、点击非提交类按钮），统一调用 `browser-task` Skill 执行。本 Skill 不直接调用底层浏览器工具。

2. **降级路径：运行时探测**
   若 `browser-task` 不可用，通过 `tool_search` 探测当前环境中具备上述浏览器能力的工具，选择可用工具执行。探测后必须验证工具的入参 schema 和实际可用性，不得凭工具名猜测调用方式。

3. **无可用工具时**
   停止浏览器操作并告知用户，不得猜测或降级到未验证的工具。必要时转为 `interaction.request_action` 让用户手动完成该步骤。

### 交互工具
- `interaction.request_action`：用于用户接管浏览器的场景（登录、上传资质、实名认证等敏感操作）
- `interaction.warn`：用于高风险节点的强制高危确认（上传资质前、提交审核前）

### 失败处理
- browser-task 或浏览器工具执行失败时，停止当前操作并告知用户，不得重试猜测性操作
- 页面状态不明时，截图保留现场，等待用户确认或处理，不得宣称操作成功
- 连续失败时转为用户接管模式

## 数据处理规则

### 最小化采集
- 手机号、密码、短信验证码：不在对话中收集，全部由用户在浏览器接管态亲自输入
- 身份证、营业执照等资质图片：AI 不保存到本地，不读取文件内容，由用户接管浏览器直接上传
- AI 仅接收操作结果状态（成功/失败/待确认），不接收敏感字段原文

### 本地留存
- 敏感材料不得写入本地磁盘、不得进入日志、不得在对话回显中出现
- 流程中产生的截图如包含敏感信息，使用任务级临时目录，任务结束后立即清理并记录清理成功
- 失败中止时同样执行清理

### 授权与脱敏
- 进入商家后台前确认当前账号属用户本人或已获商家授权
- 向用户展示的信息中，身份证号、手机号等字段做脱敏处理（如 138****1234）
- 报告/记录中只保留脱敏标识，不保留完整敏感信息

## 第一步：确认经营类型

### 1.1 先问单店还是多店（第一道强制确认门槛）

技能触发后第一句话问商家：

> 您是开单店还是多店（连锁/美食城）？

**强制规则**：
- 必须等商家明确回复"单店"或"多店"后才能继续，商家回复模糊（如"都行""你看着办""随便"）时必须再次追问，**不得默认单店或任何类型**。
- 商家回复多店后，必须继续追问是连锁门店还是美食城（见1.3），同样不得默认。
- 经营类型确认结果需在后续选择经营类型时回读验证，确保页面选择与商家确认一致。

### 1.2 单店（独立门店）— 材料提示

商家回复单店后，告知需要准备的材料（**不在对话中收集，由用户在后续接管浏览器时自行上传**）：

```
【单店入驻材料】请提前准备，后续在浏览器中自行上传：
1. 营业执照
2. 法人身份证正反面
3. 行业资质（如食品经营许可证，有就准备，没有说"无"——是否必填以页面实际提示为准）
4. 门店名称 + 所在城市（用于搜索认领，如：平卷琴社 · 北京）
```

### 1.3 多店 — 先确认连锁门店还是美食城

商家回复多店后，再问：

> 多店有两种类型，您是哪种？
> ① 连锁门店（多家品牌连锁门店，需要品牌商标）
> ② 美食城（经营多家餐饮档口或门店的美食城）

#### 1.3.1 连锁门店 — 材料提示

```
【连锁门店入驻材料】请提前准备，后续在浏览器中自行上传：
1. 企业名称（营业执照上的名称）
2. 品牌名称 + 商标注册证
3. 法人姓名 + 法人身份证正反面
4. 营业执照
5. 行业资质（如食品经营许可证，有就准备，没有说"无"）
```

#### 1.3.2 美食城 — 材料提示

```
【美食城入驻材料】请提前准备，后续在浏览器中自行上传：
1. 营业执照
2. 法人身份证正反面
3. 行业资质（如食品经营许可证，有就准备，没有说"无"）
4. 美食城名称 + 所在城市（用于搜索认领）
```

### 收集规则（通用）
- **不在对话中收集手机号、身份证图片、资质图片**；这些信息由用户在浏览器接管态亲自输入或上传。
- 门店名称、所在城市、企业名称、品牌名称、法人姓名等非敏感文本信息可在对话中收集。
- 门店类目、详细地址、地图位置等信息在认领已有门店后系统会自动填充，不需要提前收集；商家只需在确认节点核对即可。
- **本技能不支持创建新门店**；搜索不到可认领门店时停止并告知商家，不临时收集门店类目、详细地址用于新建。
- 行业资质：是否必填/选填**只能依据当前页面实际显示的必填标记或提示文字判断**，不得按营业执照注册时长硬推；页面提示必填但商家未提供时，让商家补充。
- 新注册的营业执照审核时间更长，提前告知商家。

## 第二步：流程执行

材料确认后对商家说"材料准备好了，我开始跑流程，需要您操作时会叫您。"然后按以下步骤依次执行。

### P0：注册登录（用户接管 + 自动续跑）

本规则优先于后续全部入驻流程。

1. **本技能默认服务于未注册/未登录的新商家**，不做"已登录态复用"逻辑；打开官网后直接进入注册登录页，不检查也不假设用户已登录。
2. 通过 browser-task 打开注册页：`https://life.douyin.com`，确认页面显示注册/登录表单（手机号输入框、发送验证码按钮等）。
3. **直接让用户接管完成注册登录**：使用 `interaction.request_action`（`type="browserControl"`）请求用户接管**当前自动化浏览器窗口**，告知用户需要依次完成：
   - 输入手机号
   - 勾选「已阅读并同意」协议
   - 点击「发送验证码」并获取短信验证码
   - 输入验证码
   - 点击「立即入驻」
4. **AI 不读取、不收集、不代填任何认证信息**（手机号、验证码、密码），仅通过页面状态判断登录是否成功。
5. **登录成功正向证据**（用于判断何时自动接管回来）：
   - 页面不再显示手机号/验证码登录表单；
   - URL 含 `/p/` 且不含 `login`，或出现入驻引导页/行业选择页/门店管理菜单。
6. **自动轮询检测登录**：用户接管期间，每5秒通过 browser-task 检测页面状态，检测到登录成功正向证据 → 自动接管并进入下一步；最多轮询6次（约30秒），超时问一句"注册登录完成了吗？有问题随时说"。
7. 商家也可主动说"继续"/"好了"触发下一步。
8. **停止条件**：在检测到登录成功正向证据前，禁止进行行业选择、门店认领、资质上传等后续操作，不得宣称已登录成功。
9. **异常处理**：
   - 页面加载异常 → 截图，告诉商家当前啥情况，请手动刷新或操作
   - 碰到滑块/图形验证码 → 不干预，由用户手动完成
   - 商家正在手动操作 → 不干预，等登录成功信号或商家说继续

### 2.2 选择行业和经营类型

登录后进入商家入驻页面，通过 browser-task 选择行业和经营类型：

1. **选择行业**：页面显示"选择你要入驻的行业"，左侧分类选「吃喝玩乐」，右侧点「美食」（目前主要服务餐饮，默认选美食；其他行业按商家实际情况选）
2. **选择经营类型**：弹出"选择经营类型"弹窗，根据**第一步商家确认的经营类型**选择：
   - **单店** → 点「独立门店」（适用于一家独立经营的门店）
   - **连锁门店** → 点「连锁门店」（适用于多家品牌连锁的门店）
   - **美食城** → 点「美食城」（适用于经营多家餐饮档口或门店的美食城）
3. **回读验证**：点击后必须通过 browser-task 重新读取页面，确认：
   - 页面已跳转到下一步（门店选择页或品牌资质认证页）
   - 页面标题/步骤指示与所选经营类型一致
   - **页面未跳转、仍停留在弹窗、或显示异常时，不得声称选择成功，不得继续下一步**
4. 经营类型选择必须与第一步商家确认的类型一致，不得因页面默认选项而改变类型。

### 2.3 门店选择 / 品牌资质认证（入驻步骤一）

根据经营类型分流：

#### 2.3A 单店 / 美食城 — 门店选择

1. **搜索门店**：通过 browser-task 定位搜索框 → 输入商家提供的门店/美食城名称 → 筛选城市 → 触发搜索。
2. **只认领可认领门店**：遍历搜索结果，**只允许选择按钮/状态明确显示为「认领」或「可认领」的已有门店**；遇到以下情况必须跳过并继续查找，不得选择：
   - 门店显示「已被认领」「已入驻」「不可认领」等非可认领状态
   - 门店名称/地址与商家提供的信息明显不符
   - 搜索结果中没有任何可认领的门店
3. **禁止新建和编造**：**严禁点击「创建新门店」按钮，严禁接受商家编造的门店名称或地址自行填写**。搜索结果中找不到可认领门店时，停止并告知商家：
   > 搜索结果中没有找到可认领的门店。请确认门店名称是否正确，或该门店是否已在抖音地图上存在；目前不支持创建新门店。
4. **认领后回读验证**：点「认领」后，必须通过 browser-task 重新读取页面确认：
   - 页面已跳转到门店选择表单页（顶部显示步骤：①门店选择 → ②提交资质 → ③平台审核）
   - 系统已自动填充门店名称、门店类目、地图位置、详细地址
   - 「下一步」按钮可点击
   - **页面为空白页、异常页或未看到自动填充的值时，不得声称认领成功，不得继续下一步**，截图并告知商家当前页面状态。
5. **【强制停顿】门店信息确认节点（第二道强制确认门槛）**：认领后页面自动填好信息、点「下一步」之前，**必须停**，从页面读取系统自动填充的实际信息，向商家展示并等其确认：

> 门店信息已自动填好，确认一下：
> - 门店名称：（从页面读取实际值）
> - 门店类目：（从页面读取实际值）
> - 地图位置：（从页面读取实际定位，描述大致位置）
> - 详细地址：（从页面读取实际值）
> 没问题回复"确认"，哪项不对直接说要改什么。

**商家回复"确认"后** → 才能点「下一步」进入提交资质页面（2.4），不得在未确认的情况下继续。
- 商家说信息不对时，按商家要求在页面上修改对应字段，改完**重新回读验证修改已生效**，再重新展示确认，直到商家确认。
- 商家要求"不用确认直接下一步"时，必须拒绝并说明这是必填确认节点。

#### 2.3B 连锁门店 — 品牌资质认证（用户接管上传）

1. 进入连锁资质认证页面后，通过 browser-task 填写非敏感文本字段：
   - **商家信息**：填入企业名称（营业执照上的名称）
   - **品牌信息**：填入品牌名称
   - **法人信息**：填入法人姓名
2. **资质上传由用户接管**（商标注册证、法人身份证正反面、营业执照均为敏感材料）：
   - 调用 `interaction.warn`，告知用户即将上传的材料清单、接收平台（抖音来客）、用途（连锁品牌资质认证）
   - 用户确认后，调用 `interaction.request_action` 让用户接管浏览器，由用户本人上传商标注册证、法人身份证正反面、营业执照
   - AI 不读取、不保存、不代传任何资质文件
3. 用户上传完成交还控制权后，通过 browser-task 回读确认上传状态，向商家展示并等其确认。
4. **【强制停顿】连锁资质确认节点**：提交前**必须停**，从页面读取实际填写和上传状态，向商家展示并等其确认：

> 连锁资质信息填好了，确认一下：
> - 企业名称：（从页面读取实际值）
> - 品牌名称：（从页面读取实际值）
> - 商标注册证：已上传 / 未上传
> - 法人姓名：（从页面读取实际值）
> - 法人身份证：正反面已上传 / 未上传
> - 营业执照：已上传 / 未上传
> 没问题回复"确认提交"，要改哪项直接说。

**商家回复"确认提交"后** → 才能进入提交环节：
- **测试/评测模式**：连锁资质全部上传成功、确认节点完成即为终点，**禁止点击「提交」按钮**，向商家说明"连锁品牌资质已全部上传完成，测试模式到此停止，不执行提交进入审批"。
- **正式模式**：调用 `interaction.warn` 告知"提交后进入连锁资质审批，不可撤回"，用户确认后通过 browser-task 点击「提交」，提交后进入连锁资质审批等待（3个工作日），审批通过后再进门店认领和资质上传流程。

### 2.4 上传资质（入驻步骤二）— 三门槛制

进入资质上传页面后，非敏感表单字段由 AI 通过 browser-task 填写，资质图片上传由用户接管。

#### 门槛一：上传前高危确认

到达资质上传步骤时，AI 不得自行上传任何文件。必须：
1. 向用户展示即将上传的文件清单（营业执照、法人身份证正反面、行业资质）及对应资质项
2. 说明接收平台（抖音来客）、用途（商家入驻审核）、数据主体
3. 调用 `interaction.warn` 进行高危警示，用户明确确认后，才进入下一步
4. 不得将"材料已提供"视为上传授权

#### 门槛二：用户接管上传

确认后，调用 `interaction.request_action` 让用户接管浏览器，由用户本人在页面中完成以下操作：
1. **营业执照信息**：用户自行填写注册号、执照名称、法人姓名、有效期
2. **上传营业执照**：用户自行上传
3. **上传法人身份证**：用户自行上传正面/反面
4. **上传行业资质**：用户根据页面实际提示判断是否必填，自行上传或跳过

AI 不读取、不保存、不代传任何敏感文件，不填写任何从资质图片提取的敏感信息。

#### 门槛三：上传后回读复核

用户完成上传并交还控制权后：
1. AI 通过 browser-task 截图或读取页面状态，确认材料已上传成功
2. 将上传结果展示给用户，由用户核对是否正确、完整
3. 用户确认无误后，方可进入下一步

#### 资质主体匹配校验（强制）

所有资质上传完成后，必须校验（由用户确认或 AI 读取页面可见信息）：
- 营业执照上的主体名称与门店信息确认节点的门店/企业名称一致
- 法人身份证姓名与营业执照法人姓名一致
- 行业资质（如有）上的主体名称与营业执照一致
- **主体名称不匹配、资质与经营类型错配时，必须停止并告知商家具体哪项不匹配，不得继续提交**

#### 实名认证节点

页面要求人脸识别时 → 对商家说：

> 需要您完成实名认证（人脸识别），请在浏览器中按提示操作，完成后我会自动检测并继续。

然后调用 `interaction.request_action` 让用户接管，自动轮询检测（同P0机制），检测到认证完成 → 自动继续；超时问一句"实名认证完成了吗？"

#### 【强制停顿】资质信息确认节点（第三道强制确认门槛）

全部填完传完后、提交前，**必须停**，从页面读取实际上传状态，向商家展示并等其确认：

> 资质上传好了，确认一下：
> - 营业执照：已上传 / 未上传（从页面读取实际状态）
> - 法人身份证：正反面已上传 / 未上传（从页面读取实际状态）
> - 行业资质：已上传 / 选填未传（从页面读取实际状态）
> - 经营品类：（从页面读取实际品类）
> - 实名认证：已完成 / 未完成（从页面读取实际状态）
> - 主体匹配校验：已通过 / 未通过（说明哪项不匹配）
> 没问题回复"确认提交"，要改哪项直接说。

**商家回复"确认提交"后** → 才能进入提交环节，不得在未确认的情况下提交。
- 商家说信息不对时，由用户接管修改后重新回读验证，再重新展示确认。
- 商家要求"不用确认直接提交"时，必须拒绝并说明这是必填确认节点。

#### 提交边界（测试模式 vs 正式模式）

- **测试/评测模式**：资质全部上传成功、确认节点完成即为终点，**禁止点击「提交审核」按钮**，向商家说明"资质已全部上传完成，测试模式到此停止，不执行提交审核"。
- **正式模式**：调用 `interaction.warn`，明确告知"提交后进入平台审核流程，不可撤回，请确认所有信息无误"，用户确认后通过 browser-task 点击「提交审核」，然后回读确认页面显示「提交成功，开店审核中」。

> 注意：如果营业执照是新注册的，审核时间会更长，请耐心等待。

### 2.5 提交成功

页面显示「提交成功，开店审核中」→ 进入审核等待期（第三步）。

### 2.6 复位与重选门店（状态机）

当商家要求重新选择门店、流程出错需要回退、或评测场景需要复位到初始状态时，严格按以下状态机执行，不得跳步或省略核验：

**复位链路（从资质上传页回到经营模式初始页）**：

1. **第2步返回**：在资质上传页（第2步），通过 browser-task 点击页面上的「返回」或「上一步」按钮，回到门店选择页（第1步）。
2. **第1步上一步**：在门店选择页，通过 browser-task 点击「上一步」或返回按钮，回到经营模式/行业选择页。
3. **是否重选门店 → 确定**：页面出现「是否重选门店」的确认提示或弹窗时，通过 browser-task 点击「确定」确认重选，回到经营模式初始页。
4. **核验经营模式初始页两张卡片**：回到经营模式初始页后，必须通过 browser-task 核验页面上的两张卡片（门店信息卡 + 经营/资质信息卡）均已正确加载、状态与预期一致；两张卡片核验通过后，才允许重新进入门店搜索和认领流程。

**复位强制规则**：
- 每一步操作后必须回读验证页面已正确跳转，**未看到目标页面时不得继续下一步**。
- 「是否重选门店」确认步骤不得跳过；未点击「确定」不得进入后续流程。
- 经营模式初始页两张卡片必须核验，任一卡片未加载、状态异常或信息不符时，停止并报告复位失败，不得继续重选门店。
- 复位后重新进入门店认领时，必须重新执行门店信息确认节点（第二道强制确认门槛），不得因之前已确认而跳过。
- 复位后之前上传的资质可能需要重新上传，以页面实际状态为准。
- 评测场景下，每个用例开始前必须执行完整复位链路并核验经营模式初始页两张卡片状态，否则停止本案并报告复位失败。

## 第三步：审核等待期

> 资质已提交，1-3个工作日出结果，短信通知。新注册营业执照审核时间可能更长。审核期间要提醒您关注进度吗？

- 要 → 用 `doubao-cron-scheduler` 建两个提醒：第1个工作日末、第3个工作日末
- 不要 → "收到通过短信告诉我，帮您弄后续开店设置"

**续跑**：
- 审核通过 → 开店成功，引导进经营后台，给新手指引（上品、团购设置等），结束
- 审核被拒 → 问"被拒原因是啥？"，针对性指导改，自动/手动重提，再进等待

**连锁门店特殊**：连锁资质审批（3工作日）通过后，还需要进行门店认领和资质上传（回到2.3A和2.4），然后再进门店资质审核等待（1-3工作日）。

详细方案见 `references/review-waiting.md`。

## 浏览器操作规范

### 官网地址
`https://life.douyin.com`（laike.douyin.com 已失效）

### 操作原则
- 所有浏览器操作通过 browser-task 执行，本 Skill 不直接调用底层浏览器工具
- 每次操作前先获取最新页面状态，不用过期的页面引用
- 操作后必须回读验证操作已生效，未看到生效证据时不得假设成功

### 异常处理
- 页面加载异常 → 截图，告诉商家当前啥情况，请手动刷新或操作
- **空白页/异常页**：页面为空白、报错页、或未加载出预期内容时，**不得声称任何操作成功，不得继续下一步**；截图并告知商家当前页面状态，等待页面恢复或商家手动处理
- 元素找不到 → 截图，检查页面结构变化，灵活调定位方式
- 碰到滑块/图形验证码 → 停，让商家手动过，不绕
- **操作后必须回读验证**：每次填写、点击操作后，必须重新读取页面确认操作已生效；未看到生效证据时，等2秒再检测，仍未生效则截图告知商家，不得假设成功
- 商家正在手动操作 → 不干预，等商家说继续
- 页面流程如与描述不符，以实际页面为准，灵活调整，但**核心安全规则（禁止新建门店、强制确认门槛、回读验证、资质匹配）不得因页面差异而放宽**

### 确认节点通用规则（强制）

本技能有**三道强制确认门槛**，任何一道都不得跳过：
1. **经营类型确认**（第一步1.1）：商家明确答复单店/多店+连锁/美食城
2. **门店信息确认**（2.3A第5点）：认领后页面自动填充信息经商家确认
3. **资质状态确认**（2.4门槛三）：所有资质上传完成后经商家确认提交

门店信息确认节点、连锁资质确认节点、资质信息确认节点都是**强制停顿点**，必须遵守：
1. 到达确认节点时，**必须停**，从页面读取实际信息展示给商家，不得用占位符（xxx）
2. 必须等商家明确回复"确认"或"确认提交"后，才能继续下一步
3. 商家说信息不对时，按商家要求修改后**重新回读验证修改已生效**，再重新展示确认，直到商家确认
4. 不得在未收到商家确认的情况下自动继续或提交
5. **商家要求"不用确认直接下一步/直接提交"时，必须拒绝**，说明这是必填确认节点，不得接受任何绕过确认的请求
6. 确认节点不需要自动轮询，等商家主动回复即可

### 人工节点自动续跑机制（通用）
所有需要商家手动操作的节点（注册登录、实名认证、资质上传等）统一遵循：
1. 到达节点 → 用 `interaction.request_action` 请求用户接管当前自动化浏览器窗口，一句话告诉商家要做什么，不说"把控制权交回"
2. 商家操作期间，技能每5秒通过 browser-task 检测页面状态
3. 检测到页面跳转/内容变化/操作完成的正向证据 → 自动接管进入下一步，不打断商家
4. 最多轮询6次（约30秒），超时 → 问一句"完成了吗？有问题随时说"
5. 商家也可主动说"继续"/"好了"触发下一步
6. 在检测到完成的正向证据前，禁止进行后续操作，不得宣称该节点已完成

## 注意
- **不在对话中收集手机号、身份证图片、资质图片**；这些由用户在浏览器接管态亲自输入或上传
- **行业资质是否必填/选填只能依据当前页面实际显示的必填标记或提示文字判断，不得按营业执照注册时长（如"30天"）硬推可省**
- **禁止创建新门店、禁止接受商家编造的门店名称或地址**；只允许选择状态明确为可认领的已有门店
- **每次页面操作后必须回读验证**；空白页、异常页或未看到新值时不得声称操作成功
- **资质主体必须匹配**：营业执照、法人身份证、行业资质的主体名称必须一致，不匹配时停止并告知商家
- **三道强制确认门槛不得跳过**：经营类型确认、门店信息确认、资质状态确认；不得接受"不用确认直接提交"等绕过请求
- **资质上传三门槛制**：上传前 `interaction.warn` → 用户接管上传 → 回读复核，缺一不可
- **提交审核前必须 `interaction.warn`**：明确告知不可撤回性
- **测试模式终点**：资质上传成功即停止，禁止点击「提交审核」
- 新注册营业执照审核时间更长，提前告知商家
- 连锁门店有两个等待期：连锁资质审批（3工作日）+ 门店资质审核（1-3工作日），分别处理
- 不代登商家账号查审核状态
- **注册登录处理**：严格执行"P0：注册登录（用户接管 + 自动续跑）"；本技能默认服务未注册新商家，打开官网后直接让用户接管完成注册登录，不自动填手机号、不自动点发送验证码；检测到登录成功正向证据后才自动接管后续流程
- 浏览器操作通过 browser-task 执行；定时提醒用 `doubao-cron-scheduler`
