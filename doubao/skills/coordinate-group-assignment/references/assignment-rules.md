# 任务拆解与分工规则

## Task graph

先按最终交付物和评分标准建立 WBS，再细化成一人可负责、可验收的任务。每项任务必须具备：

- 一个 `task_id` 和明确动词开头的标题；
- 一个主责人，必要时有协作者和替补；
- 输入、输出、依赖、内部截止时间和验收标准；
- 至少一个评分标准链接，或明确标记为支持性任务；
- `todo`、`doing`、`submitted`、`accepted`、`blocked` 之一的状态。

依赖只表达真实阻塞关系。独立任务可以并行；合稿、审核、彩排必须依赖其上游内容。不要用“大家一起
完成”替代责任人，也不要把提醒、催收等管理动作当成核心成果。

生成任务 JSON 后运行 [`validate_task_graph.py`](../scripts/validate_task_graph.py)，检查重复 ID、缺失依赖、
依赖循环和评分项覆盖。脚本警告不等于失败；未覆盖评分项仍需进入风险清单。

## Assignment order

按以下优先级提出分工，避免不透明的固定权重：

1. 先排除违反可用时间、技能前置条件或用户明确限制的方案；
2. 在可行方案中优先能力匹配和成员明确偏好；
3. 平衡预计工作量、关键路径风险和展示时长；
4. 让相关调研者可以参与对应内容的初稿解释，但不强制其承担最终讲述；
5. 为高风险或单点任务设置协作者/替补；
6. 对接近的方案提供候选 A/B，并等待小组确认。

报告每个人的任务数量、预计工作量、主责风险和演讲时长。`unknown` 不等于“没有时间”或“没有能力”。
若 `AssignmentBrief` 或任务图来自文件，先分别运行 [`validate_brief.py`](../scripts/validate_brief.py) 和
[`validate_task_graph.py`](../scripts/validate_task_graph.py)；结构无效时不要继续分工。

## Fairness

- 不依据性别、民族、籍贯、宗教、政治面貌、健康、残障、家庭经济或其他敏感信息派活；
- 不把外向、口才好或“看起来可靠”作为展示任务的唯一依据；
- 不用写作流畅度推断贡献量；贡献以带成员标识的工件和小组确认记录为依据；
- 成员明确的学习目标可以被考虑，但不能覆盖硬约束或变成强制分配；
- 只给建议，不替小组确认共识或评价成员成绩。
