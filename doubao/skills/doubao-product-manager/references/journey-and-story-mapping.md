# 用户旅程、服务蓝图与故事地图

三者解决的问题不同，不要互相替代：用户旅程理解跨触点体验；服务蓝图解释前台体验如何由后台角色和系统支撑；故事地图用于按用户活动拆解产品范围和版本切片。

## 1. 先选正确地图

| 决策问题 | 产物 |
|---|---|
| 用户在完整经历中哪里受阻 | 用户旅程图 |
| 多角色服务如何协同、哪里会断点 | 服务蓝图 |
| 围绕一个任务如何组织需求和版本 | 用户故事地图 |

若没有真实研究或现有流程来源，只能做“待验证的假设地图”，不能把情绪、痛点或后台流程写成事实。

## 2. 用户旅程图

以用户目标而不是内部组织为主线。每个阶段记录：触发、用户任务、行为与触点、期待、事实证据、摩擦、关键时刻、机会和未知。

情绪曲线必须来自访谈、反馈或行为证据；没有证据时用“可能感受 + 验证问题”，不随手画高低曲线。

机会只保留会改变产品决定的部分，并能回到具体摩擦与证据。

## 3. 服务蓝图

按时间从左到右，至少区分：

- 用户行为；
- 用户可见的前台动作和反馈；
- 用户不可见的后台人工动作；
- 支撑系统、数据、政策和外部依赖；
- 失败点、交接、等待和恢复。

每个关键交接写明责任角色、必要输入、承载能力和失败动作。没有来源的后台能力保持未知，不能默认运营、客服或研发“可以处理”。

## 4. 用户故事地图

从左到右按用户活动和任务顺序排列，从上到下按必要性或成熟度切片：

1. 建立用户活动骨架；
2. 在活动下拆用户任务；
3. 再拆实现任务所需故事；
4. 横向检查从触发到结果是否闭环；
5. 切最小可用版本，标明首期不做及回补条件。

版本切片不是把高分功能堆在一起。每个切片都必须让目标用户完成一个有价值的端到端任务。

## 5. 输出判断

地图不是最终结论。图后必须写清：最大断点、为什么重要、证据强度、推荐改动、本次不做和下一次需要验证的关键假设。
