# PRD 与研发交付

PRD 的作用是让产品、设计、研发、测试和运营对同一个决定采取行动，不是展示产品经理知道多少框架。

## 1. 先判断是否需要 PRD

- 决定、用户和主方案尚未对齐：先写功能简报或评审方案；
- 核心方案已明确，需要跨职能评审：写一页 PRD；
- 已准备进入设计研发：补齐规则、状态、异常、依赖和验收，形成研发级 PRD。

文档名称应反映真实成熟度。信息不足不等于停止工作，但不要用长文制造“已经可以开发”的错觉。

## 2. 从决定展开，而不是从目录展开

先让读者看懂：推荐什么、为什么、解决谁的什么问题、关键取舍、本期做到哪里、哪些内容暂不进入。

根据任务选择需要的模块：现状与证据、目标与非目标、方案总览、范围、详细需求、流程或状态、异常恢复、数据与衡量、依赖风险、验收发布。没有决策价值的章节直接删除。

每项核心需求能够沿这条链解释即可：

`问题依据 → 目标结果 → 产品改动 → 用户或系统行为 → 可观察结果 → 验收`

链路中允许包含产品判断和暂定方案，但不要把它们写成已经存在的事实。

当研发级 PRD 同时包含外部事实、产品推断、已定结论、待验证事项或关键数字时，用一张简短的依据与待确认表或决策记录，显性呈现最容易混淆的内容；不必逐句贴标签，也不为低风险短方案强制建表。

## 3. 把范围写成真正的取舍

对存量产品说明保留、新增、修改、移除和暂不做。只有来源支持的页面、入口、流程、角色、规则或服务能力才能列为“保留”或“沿用”；未知现状先列为基线确认或条件方案，不能用行业常识补齐。用户明确说过已有、后置、不做或不要修改的内容，不能换个名字重新进入主流程、主图和验收。

每个关键页面或步骤围绕一个主要任务组织。说明、教育、推荐和运营内容不能反复打断主路径，也不为填满页面制造未经验证的卖点。用户选择稍后、跳过、取消或返回时，后续去向应尊重这次选择；没有新的明确触发，不能在下一步再次强制进入同一流程。

P0 或第一阶段要构成最小闭环，而不是功能名称清单。每项核心需求按实际需要说明：

- 谁在什么前提下触发；
- 系统和用户分别做什么；
- 用户看见什么结果；
- 关键规则、状态、权限和数据如何变化；
- 失败、超时、冲突或重复操作时如何恢复；
- 依赖什么能力，如何验收。

这些内容可以用表格、需求卡、流程旁注或正文表达，不要求固定字段全部逐字出现。关键非目标至少说明不做什么、为什么本期不做，以及什么条件下重新考虑。研发级 P0 优先用团队熟悉的用户故事或需求卡让角色、意图和价值显性化；不强制 `As a` 固定句式，但不能只给功能名称。复杂度应与风险和开发成本相称。

## 4. 状态、路由和权限

只有方案确实依赖对象状态、用户分群、权限或路由时，才建立决策矩阵或状态图。先识别受保护对象与不可突破的条件，再设计新路径。

至少明确：目标对象、需要保护的相邻对象、其他可能受影响的对象、关键信号及来源、优先级、动作或去向、信号缺失和依赖失败时怎么办。目标人群来自某个渠道、注册状态或历史行为时，不把同名但信号不同的人群自动合并。重点覆盖会改变产品决定的边界，不为追求“穷尽”机械罗列所有理论状态。

高风险或不可逆动作在关键信号未知时保持原路径或转人工；低风险可逆流程可以选择暂定默认值，但要有纠正和调整条件。若当前流程来自推断，应明确这是对现状的理解，不画成已确认事实。

## 5. 验收应证明行为，而不是证明写过文档

每项核心需求至少有一个成功场景，以及与主要风险对应的失败或边界场景。使用给定—当—则或其他团队熟悉的形式均可。

验收写清前置状态、触发动作、可观察结果，以及必要的状态、通知、记录或恢复。优先覆盖真实风险，例如混合意图、权限不足、依赖失败、重复操作、并发冲突、撤销和回滚；不为凑数量生成测试用例库。

业务指标衡量价值，不能替代功能行为验收。产品经理定义结果、规则和边界，不替研发编造架构、接口、模型准确率、性能或工期。

正式进入研发的每项核心改动至少提供一个成功场景和一个与主要风险对应的失败或边界场景；若外部依赖、权限、数据来源或异常去向仍无法说明，应明确这是待评审方案，而不是用篇幅制造可研发的错觉。

## 6. 数字、数据与发布

基线未知时先定义口径和采集方式。若提出阈值、灰度周期或目标，说明它是事实、估算还是产品初始参数，并给出设定逻辑、校准方法和调整条件。只有指标、实验或灰度确实用于选择方案、判断上线或控制风险时才展开，不因 PRD 形式完整而默认增加。

发布策略根据风险选择影子运行、人工复核、小流量灰度、分群放量或直接发布；不要自动套用固定周数。说明上线判断、监控、停止或回滚条件，以及上线后根据什么信号继续、调整或停止。

## 7. 可视化与交付

方案包含关键交互、路径、状态或取舍关系，且图能明显降低理解成本时，至少提供一种合适的可视化。图型由关系决定：页面任务优先用低保真原型，路径问题用流程或泳道，状态问题用状态图，取舍问题用矩阵或关系图；简单规则和短方案不强行画图。在飞书中需要自包含可视化时，优先通过原生 HTML5 Block 呈现。

图只需展示理解决定所需的关键关系，不复制需求表的所有字段。图与正文保持核心结论、范围、条件和去向一致；详细来源、依赖和验收可留在正文。

创建文档后回读并真实预览。发现图文冲突、内容溢出或相邻内容受损时，修正后再次确认。
