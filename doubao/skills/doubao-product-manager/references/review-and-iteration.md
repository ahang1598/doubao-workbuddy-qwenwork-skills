# 评审已有方案与存量迭代

面对已有产品、文档或附件，先还原真实现状，再做局部判断。默认保留未要求改变的内容，不借“优化”重写整套产品。

## 1. 最新口径覆盖旧方案

用户对已有方案作出纠正、否定、已有能力说明、阶段推迟或资源限制时，把它视为需求变更，不是可选反馈。先重建当前有效需求：保留什么、当前必须改什么、删除什么、推迟什么、哪些约束不能突破、哪些未知会阻断方案。

最新明确口径覆盖较早要求、旧产物和模型先前建议。被否定或推迟的内容必须从决策摘要、范围、详细需求、流程/状态图、页面原型、正式文案、指标、验收、Roadmap 和下一步中同步移除；不能只增加一条“暂不做”却保留其页面、提醒、指标或依赖。只保留不受本次变更影响且仍有事实依据的旧内容。

## 2. 建立基线

逐项读取用户给出的原文、链接、附件、截图、表格、批注、图和历史版本。需要建立基线时，围绕页面或入口、流程或状态、规则或权限、数据或指标、承诺或政策，记录当前事实、来源、与本次决定的关系，以及保留、修改或维持未知的动作。只记录与本次决定相关且已经填写的项目，不保留空行。

无法读取的部分明确列出，降低依赖它的结论强度。

## 3. 区分问题类型

不要把所有反馈都归为“缺功能”。依次检查：

- 能力确实不存在；
- 能力存在但入口、文案或认知有问题；
- 配置、权限、数据或使用方式错误；
- 流程或服务协同断裂；
- 用户目标与原方案假设不一致；
- 只是偏好差异或边缘场景。

## 4. 形成评审结论

按严重程度而非篇幅排序：

- **阻塞：**会造成错误决策、安全合规风险、核心闭环失败或虚假完成；
- **重要：**会显著降低价值、可执行性或可衡量性；
- **优化：**不改变主要决定的表达与体验问题。

每个问题写明证据、影响、建议改动、被保留的部分和验收方式。若问题只是推断，给出替代解释与验证动作。

用户给出评审维度、章节顺序、评分规则或输出格式时优先遵循。复杂方案可逐章给出结论、证据、影响和修改动作，最后汇总阻塞项与总判断；只有存在明确评分口径或用户要求评分时才给评分汇总，不为显得专业自创权重、总分或精确数值。

## 5. 局部修改协议

1. 回读最新版本并确认目标位置；
2. 合并用户最新纠正，列出保留、新增、修改、删除、推迟、资源限制和明确不做；
3. 只修改目标区域，同时同步受影响的决策摘要、范围、流程/状态、图、指标、验收和下一步，删除所有失效残留；
4. 不覆盖原始文件或历史版本，除非用户明确要求；
5. 修改后回读整篇，确认相邻内容、图、链接和格式未被破坏；
6. 提供简短变更摘要和仍待确认项。

## 6. 专家建议的使用

专家意见是判断输入，不是自动需求。先识别专家基于哪些事实、服务于什么目标、是否适用于当前版本，再决定采纳、部分采纳、转为验证项或不采纳。解释其对产品决定的实际影响。
