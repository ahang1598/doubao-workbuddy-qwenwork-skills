# 产品交付复核

本文件用于 P0、MVP、研发级 PRD 或高风险方案的最后复核。它帮助发现会改变决定的问题，不用于把产品文档改造成检查报告。

## 1. 判断是否成立

- 首屏能看懂要决定什么、建议什么、依据和关键取舍是什么；
- 事实、推断、产品决定和待验证假设没有互相冒充；
- 未知的现有页面、入口、流程、角色、规则、服务能力或申诉机制没有被写成“保留”或“沿用”；
- 用户最新纠正没有被旧材料、模板或模型建议覆盖；
- 方案不是材料复述，关键选择说明了为什么以及放弃了什么；
- 不相关的 Persona、竞品、页面、Roadmap、指标或实验没有因模板而出现。

## 2. 范围是否可控

- 本期范围构成核心闭环，并说明保留、新增、修改、移除和暂不做；
- 用户明确后置或不做的内容没有从默认路径、必经页面、P0、主图、验收或下一步重新进入本期；
- 核心需求覆盖与任务相关的前置、触发、行为、结果、失败恢复、依赖和验收；
- 用户选择稍后、跳过、取消或返回后，没有在缺少新触发的情况下再次被强制带回同一流程；
- 依赖未知时说明暂定方案或解锁条件，没有一边写待确认、一边当成既定能力；
- 工期、人力、技术能力和承载量没有被写成未经确认的承诺。
- 用户提出的日期仍是目标；没有技术、资源和依赖评估时，没有把缩小后的方案写成届时可以启动或完成。

若上述内容不足以支持研发行动，将产物明确定位为功能简报或评审方案，不用长文制造“已经可以开发”的错觉。

## 3. 数字与风险是否合理

- 精确数字是有口径的事实、可复算估算，或说明了依据和调整条件的产品参数；
- 生命健康、价格退款、服务履约、安全隐私和效果收益等对外主张有当前来源；没有来源时未写成正式卖点、具体数字或履约承诺；
- 指标能够帮助上线、迭代、停止或定位问题，不只是装饰文档；
- 高风险方案覆盖误判、漏判、人工接管、审计、申诉或回滚中真正适用的部分；
- 安全要求没有被扩写成未经确认的系统能力。

## 4. 交付前是否通过反向扫描

- 检索“现有、已有、仅支持、沿用、自动、默认、当前”等表述，确认每项现状能力、入口、渠道和自动流程都有当前来源；无来源时改成未知、条件方案或确认动作；
- 检索数字、比例、金额、周期、容量和性能值，确认它们分别有来源、可复算依据，或被写成可调整的初始参数并说明校准方法；关键数字在首次出现处就近标注，缺少依据时删除或改为定性门槛；
- 依赖尚未确认的数据、渠道、权限、接口、触达或优惠能力时，不把相关能力放进 P0 默认路径；先采用不依赖该能力的闭环或人工方案，并写清解锁条件；
- 对照全文检查自动执行与人工确认、待确认与既定方案、正文与验收之间是否冲突；高风险动作不得一边要求人工负责，一边默认自动生效；
- 删除“由 AI 生成”等内部过程话术、占位内容和无关工具说明；逐项核对最终回复承诺的文件、图、链接和章节是否真实存在且可读。

## 5. 成品是否好用

- 正式方案已按用户要求和当前可用能力创建到真实目标载体；
- 当交互、流程、状态、交接、依赖或阶段关系需要视觉表达时，已选择合适的可视化；简单方案没有为满足形式强行画图；
- 可视化帮助理解，没有为了覆盖字段塞满标签和长句，且与正文的关键对象、范围、条件、去向和数字一致；
- HTML 或其他需要视觉验证的内容已经真实预览，默认宽度下无溢出、遮挡和不可读文字；无法预览时已明确说明；
- 修改任务保留了未要求改变的内容，链接、附件和相邻区域未被破坏；
- 最终回复与实际产物一致，没有把接口成功或局部完成说成全部完成。

发现问题直接修正最小范围。机械格式问题可以重复修正，产品方向发生变化时重新做判断；不要为了显得完整或通过形式检查堆叠关键词。
