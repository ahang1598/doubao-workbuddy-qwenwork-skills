# 发现、问题与机会

用于产品想法、功能请求、用户反馈、问题诊断、0 到 1 机会以及“要不要做”。不用于已经对齐范围、只需写执行细节的任务。

## 1. 先区分输入是什么

- **观察：**发生了什么，可回到行为、数据或原话。
- **诉求：**用户或相关方希望增加什么，仍可能只是他们提出的解法。
- **问题假设：**谁在什么情境下无法完成什么，原因尚待验证。
- **机会：**值得改善的用户需求、痛点或欲望，不是功能名称。
- **方案：**改变现状的候选干预。

不要把“客户要某功能”“竞品有”“老板希望做”直接写成机会。

## 2. 快速构建风险判断

在投入完整 PRD 前回答：

1. 谁在什么情境下有问题？
2. 他们想完成什么结果？
3. 当前怎么解决，付出了什么可观察成本？
4. 已有证据支持的是问题存在、问题强度，还是方案偏好？
5. 哪个假设最可能让整件事失败？
6. 最便宜的下一步如何增加或降低信心？

给出一种当前判断：继续做小、先补证据、收缩问题、调整方向、暂不投入。判断应附成立条件，不用固定样本阈值制造确定性。

## 3. 问题陈述

问题陈述至少包含：目标用户或角色、具体情境、期望结果、受阻行为、影响与证据。只有访谈或行为证据支持时才写情绪和根因。

推荐结构：先写角色与具体情境，再写期望结果、已观察阻碍和可观察影响；最后说明证据来源，以及仍待验证的根因。不要把方括号占位符或未填写模板带入交付物。

检查：

- 是否偷渡了特定功能？
- “因为”是事实还是待验证解释？
- 业务指标下降是否已转换为用户层面的受阻行为？
- 是否存在至少一个其他解释？

## 4. 研究计划

先写研究要支持的决定，再选方法：

| 要回答的问题 | 更合适的方法 |
|---|---|
| 用户真实工作如何完成、哪里受阻 | 观察、情境访谈、日志或工单 |
| 一个问题是否重复出现、影响哪些群体 | 多源反馈综合、行为数据、分群 |
| 用户为什么选择或放弃方案 | 近期真实行为访谈、替代方案分析 |
| 方案是否易理解、能否完成任务 | 低保真或可交互原型测试 |
| 改动是否造成可测量行为变化 | 埋点分析、受控实验或灰度观察 |

访谈优先问最近一次真实行为、当前替代方案、切换成本和失败后果；避免“你会不会用”“你喜不喜欢这个功能”等诱导式问题。

## 5. 研究综合

单场访谈只总结该参与者。多场综合输出：参与者范围、重复模式、反例、原话或行为证据、用户分层、置信度、局限和下一步。

把每条洞察写成：

`观察 → 可能解释 → 需要区分的替代解释 → 能支持的产品动作`

没有区分替代解释时只能称为“优先假设”，不能称为根因。

## 6. 机会与方案空间

需要展开多个方向时使用：

`目标结果 → 用户机会 → 候选方案 → 待验证假设 → 最小证据动作`

至少保留“不做/延后/只修入口/复用现有能力”等反事实选项。候选方案应真正不同，例如改变触发方式、责任角色、操作路径或服务模式，而非只换文案颜色。

## 7. 进入 PRD 的门槛

可以进入执行型 PRD，通常意味着：

- 用户问题和目标群体已能被证据描述；
- 为什么现在处理有业务依据；
- 至少比较过一个可行替代方案；
- 主方案的关键假设和风险已显式；
- 本次范围与不做项已经形成；
- 关键未知不会让主流程或安全边界完全改变。

否则交付产品判断、验证计划或功能简报，不把探索包装成工程承诺。
