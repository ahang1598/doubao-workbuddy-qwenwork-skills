# 相关方、上线与复盘

产品交付不是文档写完。必须让正确的人在正确时间作出决定，并让上线后的真实结果能被发现、解释和处理。

## 1. 相关方不是通讯录

只列会影响决定或执行的角色，并写清：目标、硬约束、掌握的事实、负责的动作、决策权和需要对齐的冲突。

需要多人协同时，按决定或动作写清负责执行、最终决策、必须提供意见和需要知会的真实角色。没有来源的姓名、责任或承诺标为待确认，不保留空表。

不要默认某个人或团队已有资源、权限或承载能力。

## 2. 决策沟通

异步评审首屏直接写：推荐什么、为什么、放弃什么、主要风险、需要谁在何时决定什么。正文再提供证据和细节。

记录关键决定：日期、问题、选项、决定、依据、反对意见、条件、可逆性、负责人和复审触发器。新的证据改变决定时追加变更，不覆盖历史。

## 3. 上线准备

按实际风险选择检查项：

- 范围、验收和已知限制已对齐；
- 权限、隐私、安全、合规和数据保留已由相应责任人确认；
- 埋点、看板、告警和人工观测可用；
- 灰度人群、进入与退出条件明确；
- 用户提示、帮助、客服或运营 SOP 已准备；
- 依赖、容量、故障处理、回滚和补偿已演练或确认；
- 负责人和响应窗口已真实承诺。

不能确认的项目写明影响。高风险阻塞项未关闭时不建议自动扩大范围。

## 4. 上线后学习

预先约定观察节点和要回答的问题，而不是上线后临时挑指标。复盘至少区分：发生了什么、数据是否可信、为什么发生、原假设如何变化、下一步决定是什么。

异常事件还要记录发现方式、用户影响、处置时间线、恢复、根因、长期动作和责任人；不把“加强关注”当行动项。

## 5. 发布不等于完成

只有真实用户能够使用、关键监控可观测、已知风险有处置路径且目标载体回读通过，才能称为已交付。若只是完成方案、研发、测试或灰度，准确描述当前阶段。
