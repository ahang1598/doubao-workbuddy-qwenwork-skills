# 校园地点与办事导航

## 核心原则

- 只处理高校校内地点事实与办事流程，不扩展为校园百科、生活攻略或通用地图导航。
- 实时发现来源，不保存学校名单、建筑库、历年考场、社团地址或各校办事流程副本。
- 搜索结果只用于发现 URL；打开原始来源后再陈述事实。
- 将学校规定、事务第一方通知、用户当前凭证和第三方地图分开标注，不互相替代。
- 不确定时缩小结论或标记 `partial`、`unresolved`；不得以常识、其他学校经验或旧通知补齐事实。

## 任务模式

先选择一个主模式；混合请求按顺序处理。

| 模式 | 用户主目标 | 主要交付物 |
| --- | --- | --- |
| `service_guide` | 某事项怎么办、去哪办、带什么 | `ServiceRecord` 与可执行步骤 |
| `place_resolution` | 建筑作用、社团/活动/报名地点、考试教室在哪 | `PlaceRecord` 与地点层级 |
| `route_enrichment` | 从起点到已确认地点怎么走 | 可选路线补充，不单独作为主模式 |

以下情况不要触发：社团推荐、活动推荐、校园新闻、课程评价、选课、旅游攻略、城市交通，或要求实际提交、
缴费、预约、代登录。混合请求中只完成地点和流程部分，并把其他部分交给相应能力。

## 标准工作流

### 1. 读取现有上下文

从当前会话、用户粘贴内容和附件中提取已经给出的学校、校区、身份、事项、地点原文、活动名称、日期、
考试类型、批次和场次。不要重复追问。

只追问会改变答案的关键缺口：

- 学校无法唯一确定；
- 同一事项按校区或身份分办；
- 社团、活动、报名或考试地点依赖日期、批次或场次；
- 用户要求路线但未提供起点。

处理准考证、报名回执或截图时，只读取地点解析所需字段。不要搜索、复述或外传姓名、证件号、准考证号、
座位号等无关个人标识。

### 2. 建立请求记录

参考 [assets/campus-location-request.template.json](assets/campus-location-request.template.json) 整理请求；只有需要
跨步骤保存、校验或交接时才创建 JSON 文件。保留用户看到的建筑名、教室代码、房间号和通知地点原文；
不要过早改写。

根据任务加载资料：

- 任何任务：读取 [references/official-source-protocol.md](references/official-source-protocol.md)。
- 首次使用外部能力或部署验收：读取 [references/tool-bindings.md](references/tool-bindings.md)，核对 Action Hub
  中通用搜索、网页读取及可选浏览器的实际 Tool 绑定与状态。
- `service_guide`：再读取 [references/service-record-schema.md](references/service-record-schema.md)。
- `place_resolution`：再读取 [references/place-resolution-rules.md](references/place-resolution-rules.md)。
- 交付前或遇到失败、冲突：读取 [references/quality-and-failure.md](references/quality-and-failure.md)。

生成 `sources` 时必须按 [references/service-record-schema.md](references/service-record-schema.md) 填写发布主体、
发布日期或更新时间、查询日期、原始链接和支持字段；日期必须是能按公历解析的真实 `YYYY-MM-DD` 日期，
不得只检查字符串形状。缺任一必填字段就降级为未完成并修正记录，不得以搜索摘要代替来源。

### 3. 发现并读取来源

先按 [references/tool-bindings.md](references/tool-bindings.md) 检查必需能力。通用搜索或网页读取未绑定/未启用
时，不声称已完成外部核验，输出 `unresolved` 并指出缺失能力；浏览器未启用时只跳过需要交互的可选步骤。

在运行平台可用工具中按能力选择，不硬编码工具名：

1. 使用通用搜索或网页搜索发现学校官网、部门页面、活动原始通知、报名页面或考试安排。
2. 使用网页读取/抓取能力打开公开静态页面并提取正文。
3. 仅当页面依赖 JavaScript、站内交互或复杂导航时，使用浏览器能力。

登录墙出现时不要绕过认证。若用户没有明确授权或尚未登录，给出公开入口、责任部门和咨询方式，并将详情
标记为未确认。不要把搜索摘要当作最终证据。

### 4. 生成事实记录

`service_guide` 使用 `ServiceRecord`；`place_resolution` 使用 `PlaceRecord`。每个关键字段同时记录来源类型、
适用日期和证据状态；`sources[].supports` 必须指向记录中真实存在且非空的字段，嵌套字段使用点号。
`event`、`registration`、`exam_room` 与 `club_event` 必须绑定活动、报名或考试上下文；事件日期必须是有效
公历日期；`club_office` 表示常驻社团办公室，不强制要求 `event_scope`。

特别规则：

- 建筑作用：只总结官方建筑介绍、入驻单位或当前官方页面能确认的主要用途。
- 社团地址：`club_office` 表示有官方常驻依据的办公室、长期活动室或固定物资点，不要求 `event_scope`；`club_event` 用于招新摊位和一次性活动地点，必须记录事件名称及日期、批次或场次。仅当“活动室”确为长期固定地点时，按 `club_office` 处理。
- 活动/报名地点：绑定活动全名、主办方、日期、批次和截止时间。
- 考试教室：优先使用本次准考证、学校考场安排、教学楼代码或考场示意图。
- 教室代码：没有本校明确映射时不得按经验拆解，例如不能自行把 `A3105` 解释为 A 楼三层 105 室。

### 5. 执行真实性门禁

对结论设置以下整体状态：

- `verified`：核心字段由当前且适用的可靠来源支持。
- `verified_with_caveat`：来源可靠，但存在日期、身份、校区、事件或批次限制。
- `partial`：只确认到部分地点层级或部分办理字段。
- `unresolved`：没有足够证据，不能据此办理或前往。

`verified` 与 `verified_with_caveat` 禁止同时保留 `unresolved` 项；`partial` 与 `unresolved` 必须列出至少一个
未确认项。办事记录中的责任部门和步骤、地点记录中的标准名称必须由来源 `supports` 明确覆盖后，才允许使用
`verified` 或 `verified_with_caveat`。

两个来源冲突时，比较发布主体、日期、适用身份、校区和事件批次。不要仅因发布日期更晚就覆盖适用范围不同
的来源。保留无法解释的冲突，并提供责任部门的官方咨询路径。

### 6. 可选路线补充

只有用户明确要求路线、已经提供起点，或地点必须通过空间信息消歧时才处理路线。

采用三级降级：

1. **L0 默认**：提供已确认的校区、楼宇、楼层、房间、入口或地标，以及学校官方校园地图链接。
2. **L1 可选**：若平台允许且不要求绕过登录，通过浏览器访问在线地图服务，查询到已确认建筑的路线；明确
   标注第三方地图来源，并提示校内道路、入口和楼内房间可能不准确。
3. **L2 预留**：平台将来提供地图工具时再接入；当前 Skill 不声明地图 MCP 依赖。

地图网站或地图工具只能补充地址、坐标、入口、距离和路线，不得证明建筑功能、部门职责、活动安排或考试
教室，也不得证明办事入口、材料、步骤、时间、费用或联系方式。`service_guide` 至少需要一个非地图来源；
仅有地图来源时不得输出已核实的办理结论。若只能定位到楼宇，路线终点就停在楼宇或入口，楼内位置继续采用
学校或事务第一方来源。

### 7. 交付结果

参考 [assets/campus-location-answer.template.md](assets/campus-location-answer.template.md) 中与主模式匹配的模板，
直接在对话中回答；仅当用户要求文件或下游流程需要文件时再保存 Markdown。默认先给直接结论，再给材料/
用途、适用时间、地点层级、来源和未确认项。路线部分只在执行过路线补充后出现。

默认引用最少但足以支撑答案的原始来源。用户不需要查看内部 JSON、搜索过程或证据评分。

## 校验

已创建结构化 JSON 记录时，可运行：

```bash
python3 scripts/validate_location_record.py <record.json>
```

必填参数：`record.json`，一个 UTF-8 编码的 JSON 文件。无可选参数、默认值或互斥参数；脚本不接受标准输入，
也不写入输入文件或日志。使用 `python3 scripts/validate_location_record.py --help` 查看 CLI 帮助。
成功输出一行 `VALID` 并返回码 `0`；契约错误输出 `INVALID` 及逐项错误并返回码 `1`；文件不存在、不可读或 JSON
解析失败返回码 `2`。只对发布包中的 `scripts/validate_location_record.py` 执行编译和调用，不要把 ZIP 的
`__MACOSX` 或 `._*` 元数据当成脚本。

验证失败时先修正缺失字段、非法状态、动态地点上下文或来源；不要为了通过校验编造数据。

## 异常处理

- 若输入文件不存在、不可读或不是合法 JSON，则停止结构化交付，保留原始请求并报告读取/解析错误。
- 若任一必需来源字段、证据支持字段或动态事件上下文缺失，则禁止标记 `verified`，修正记录或降级状态。
- 若通用搜索或网页读取未绑定、登录墙无法公开访问、来源过期或冲突无法消解，则停止生成确定性办理步骤，
  输出 `partial` 或 `unresolved`，并列出官方入口与最小下一步。
- 若发现无关个人标识，则仅保留地点解析所需字段；禁止把原始凭证、Token、内部地址或私有路径写入回答或日志。
