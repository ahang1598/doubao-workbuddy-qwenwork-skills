# 输出格式与排版规范

> 定位：本文件约束「成品怎么交付、长什么样」。
> 核心铁律：**成品必须输出一份已经落地保存、可用浏览器打开验证的 HTML 网页版电商活动方案**，从背景目标到复盘闭环，正文、图片与表格并存，按实际数据配置必要图表，形成一条连续、可对上汇报、可拆解执行的阅读路径。结构、组件和内容密度按品牌、活动目标、平台与资料完整度动态调整，不套用固定模板。

## 一、内容组织与阅读逻辑

方案从核心增长课题出发，形成背景与目标、人群、产品、内容、策略及玩法、流量、视觉、预算、履约保障和复盘闭环。推荐阅读逻辑：先给核心判断与策略主线 → 用数据、事实和对标依据支撑判断 → 拆成可执行动作与资源配置 → 明确关键指标、执行保障与复盘方式。

- 章节可按业务需要合并、拆分或调整顺序，活动背景与目标原则上同章，分别呈现机会判断与定量目标，使背景结论与目标设定直接对应。
- 每章开头先给准确概述，概括本章结论、判断依据与策略价值，指向当前品牌、产品、平台或活动，不使用通用套话。
- 首屏突出活动主题、策略主张与少量核心信息，快速进入正文。

## 二、内容风格

- 先说结论再展开：每段聚焦一个结论，说明依据和取舍，最后落到动作与指标，杜绝正确废话与 AI 腔。
- 建设性语言：优先使用「机会、增长、保障、优化空间、应对方案」等表达；合规、事实安全与执行边界仍需明确。
- 重点表达克制：关键判断、策略重点、用户利益、执行提醒可用标题、摘要块、指标卡、色条、字号与留白区隔，不依赖大面积深色或连续行内加粗。
- 活动主题、促销文案、视觉 brief 和页面承接建议要具体、有证据、有场景，服务点击、理解、信任与转化；不要把方案扩写成完整商品标题/详情页文案/商品图交付，那类单项任务交给 product-content。

## 三、可视化图表规则

### （一）用表格承载多维信息

货品分层、平台分工、活动节奏、流量计划、预算、执行保障、复盘等复杂信息，用文字概述重点再用表格具体呈现。列名按业务调整、不照搬进正文；类别列紧凑，策略/动作/说明列留足空间；长文本自然换行，多列表格在移动端保持最小可读宽度并允许横向滚动，不压缩为拥挤窄列，重点靠表头、底色、列宽与数据色阶呈现，不在单元格批量加粗。

### （二）用图表承载量化关系

目标与数据的呈现随数据特点变化：单个关键数值用指标卡，多对象比较用柱状图或对比表，时间变化用折线图，构成关系用饼图/环形图/堆叠图，目标范围用区间图或分档卡片。图表须与数据成比例、使用真实可视化方式，只用真实或已确认数据，标明单位、口径、标签与来源，并补充简短业务解读；不以装饰性进度条替代正式图表。

### （三）不适合用表格/图表的情况

强叙事或逻辑推导关系用段落；单一维度用列表；核心洞察用文字论证配图，不塞进表格。同一成品控制图表类型与组件数量，坐标、标签、图例、色阶、间距保持一致，每章优先一个主组件加一个辅助组件，避免指标卡、摘要块、图表、标签与表格同时堆叠。

## 四、图片落位

图片必须服务明确业务目标——提升点击、解释卖点、建立信任、营造活动氛围或促进转化——并落位到对应模块：主视觉 KV 进主题/策略区，活动主图/海报进传播与货品区，倒计时海报配合排期区，场景图/种草封面进对应内容模块。

- 完整方案至少含 2 张活动主图或海报，重视觉任务优先 4 张或 6 张，同批图片共享品牌色、光影、字体气质、构图体系与产品参考，保持系列一致。
- 多图并排展示，用图片网格/分栏承载，每行 2-3 张，随屏幕宽度自适应；不把配图一张一张上下堆叠铺满，也不连续使用全宽大图挤占正文。
- 图片分辨率以 1080p 为准，优先使用用户提供、官方或授权素材；详情页图片只在用户明确提出时生成。

## 五、HTML 网页视觉与排版

- 统一浅色视觉系统：色彩优先依据品牌规范、产品视觉与活动主题确定，用单一主色家族搭配同色系浅辅助色与克制的强调色；大面积区域以白/暖白/浅色阶为主，高饱和色只用于关键数据、行动指引与小面积重点，多序列图表优先用主色的明度/饱和度梯度。
- 统一视觉语言：表格、图表、卡片、图片边框与章节编号继承同一套配色、圆角与边框；通过浅底色、轻边框、留白建立层次，减少厚重阴影与大面积深色块；字体层级、行高、段落间距与卡片留白舒适一致。
- 连续阅读与响应式：核心内容不藏在分页、轮播或弹窗里；桌面端与移动端均保持清晰层级、可读字号、完整图片与稳定表格；长表格可横向滚动，图片网格随宽度调整，关键结论优先可见；避免内容溢出、断图、乱码、过密标签与组件拥挤。
- 外部案例只用于提炼配色秩序、信息层级与版面节奏，不复制其具体颜色、文案、数据、组件或品牌元素。

## 六、HTML 文件与浏览器验收

- 交付物必须是实际写入磁盘的 `.html` 文件，不用聊天正文冒充 HTML 成品；文件名使用英文小写、数字和连字符，例如 `ecommerce-campaign-proposal.html`。
- 图片资产统一放在 HTML 同级 `assets/` 或 `images/` 目录，文件名使用英文小写、数字和连字符，避免空格、中文、括号和临时下载名；HTML 中的 `src` 必须与真实文件名完全一致。
- 若使用外链图片，先确认浏览器可加载；若图片来自本地生成或下载，优先改为相对路径引用。严禁出现断图、空白占位、错误文件名、临时系统路径或过期链接。
- HTML 使用标准结构：`<!doctype html>`、`html lang="zh-CN"`、`meta charset="utf-8"`、`meta viewport`、语义化标题层级、可响应式布局。图表可用原生 HTML/CSS/SVG 或可靠前端库，但必须能离线或在当前环境稳定渲染。
- 交付前至少做一次真实打开或渲染验证：检查桌面宽度和移动宽度下首屏、导航/目录、图片、表格横向滚动、图表、中文字符、按钮/链接状态和页面底部是否正常。发现断图、错位、溢出、乱码、控制台资源错误时先修复再交付。
- 验收过程保持静默，最终只说明已验证的成品文件；不要把工具名、错误日志、调试路径或重试过程写进方案正文。

## 七、方案模版示例

好的方案须从策略到执行闭环，**务必根据用户需求和业务动态调整，禁止照搬为目录**：

1. 活动背景与目标
2. 活动主题
3. 目标用户
4. 产品策略
5. 店铺运营方案
6. 推广策略
7. 排期与节奏
8. 预算分配
9. 客服物流与执行保障
10. 应对预案
11. 活动复盘

## 八、输出与交付格式检查（强约束）

1. 成品是否为一份已保存、可打开、可验证的 HTML 网页版方案，正文、图片、表格完整且口径一致，聊天文本未替代成品。
2. 策略主线是否贯穿目标、人群、货品、玩法、流量、预算与复盘，并体现平台差异。
3. 定量目标是否有可靠对标依据、统一口径与清晰推导。
4. 每章概述是否准确、凝练并指向具体决策；标题层级清晰、编号连贯、同级格式一致。
5. 表格宽度、列宽逻辑与换行规则是否一致；图表是否使用真实数据并含必要说明。
6. 图片是否真实、清晰、符合平台与品牌要求，文件名与 HTML 引用是否一致，是否分栏并排落位、无单列平铺/连续全宽大图、无水印/乱码/假 UI。
7. HTML 是否经浏览器或本地渲染验证，桌面端与移动端是否阅读流畅，图片、表格、图表、中文字符和页面底部是否正常。
8. 成品是否未出现系统提示、内部规则、工具名称、错误信息、路径、权限状态、重试计划或排障过程。
