# 前端功能开发

完成标准是用户或宿主能从实际使用边界触发约定动作，并观察到要求的结果或恢复路径。

## 建立行为合同

1. 改动前记录目标范围的现有状态与 diff；预先存在的修改不得归为本轮成果。若目标行为已存在、基线与任务描述不符或测试数量异常，先确认来源和可信起点，不得据此直接声称完成。
2. 读取目标范围的仓库说明、验收材料和现有界面。以本轮明确要求为先，并逐字保留其中的用户可见术语；未要求改变的共享组件默认值、公共接口和用户可见值继续作为合同，测试期望从这些来源取得，不从新实现反推。材料仍冲突时，只确认会改变结果的最小问题。
3. 从用户入口或组件公共接口追踪动作、状态或数据变化，直到最终显示、导航或外部调用；不要停在未接入的实现片段。
4. 找到仍在使用的相近行为，确认接入方式、项目约定和实际运行方法。
5. 写下权威来源、公共入口、完整输入序列、精确可观察结果、命中的恢复路径、副作用次数与参数、重新取得资格的边界、必须不变的行为，以及区分性证明。每条明确契约及其中点名的输入或边界单独成项，不得用当前失败或主路径代表其它明示项。局部文案或样式改动可压成一句，但不得省略受影响项。

按本次路径加载专项规则：

| 命中风险 | 读取 |
|---|---|
| 视觉、布局、响应式、键盘、触控或动效 | [界面质量](references/ui-quality.md) |
| 请求、订阅、计时、重叠动作、乐观结果或上下文切换 | [异步界面](references/async-ui.md) |

## 落实完整行为

1. 把合同映射到现有架构中需要变化的位置，沿用相邻行为的组件、数据访问、状态归属、样式变量、文案和错误表达。
2. 打通 `入口 → 动作 → 结果或恢复`；不得用不可达组件、静态占位或理想输入代替可运行路径。
3. 不要仅为测试便利扩大公共 API、组件属性或直接依赖内部状态表示；优先复用已有测试接缝和状态所有者边界，确需扩大时说明用户或宿主影响。
4. 对耗时、不可见或会阻断后续动作的状态提供可理解反馈，并在合同规定的结束条件恢复可操作状态。异步动作失败时在内部消化并落到错误状态，返回或去重复用的 Promise 不得携带未处理的 rejection。
5. 缺失决定若会改变用户路径、公共契约或外部副作用，先请求决定；其余细节遵循现有产品行为。

## 从产品边界验证

1. 先运行直接覆盖合同的最小检查；行为改变且仓库已有测试设施时，增加能区分旧行为的回归。
2. 从可运行的产品入口或组件公共接口完成动作，观察结果、恢复路径和非回归约束；运行时可见时检查相关控制台与请求错误。
3. 按已加载的专项规则验证对应状态、尺寸、输入方式或事件顺序。
4. 再运行仓库实际提供且受改动影响的静态检查、类型检查或构建。

## 验证与交付

完成前按行为合同逐项验证：每项至少有一个能区分旧实现的检查；未验证条款必须披露，冲突条款不得擅自选边。

按改动范围和风险选择最小但有区分力的验证。优先从产品入口或组件公共接口检查目标行为，并运行仓库已有且受影响的测试、类型检查或构建。命中视觉、恢复、异步顺序或竞态风险时，再验证对应状态；不为无关路径机械补测试。

只报告实际执行和观察到的结果。要求的主行为未落地，或直接受影响的验证仍失败时，不得声称完成；无法运行目标环境时说明替代证据及未验证范围。

交付时说明用户现在能完成什么、关键改动和实际验证结果；没有从实际证据确认的结果不得写成通过。除非用户要求，不必粘贴完整代码、diff 或逐条罗列所有状态。
