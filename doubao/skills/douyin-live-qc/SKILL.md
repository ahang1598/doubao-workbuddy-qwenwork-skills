# 抖音直播录屏抽查与话术质检

## 核心交互原则：两个确认节点
本流程**不是一路跑到底**，而是在两个节点必须暂停、向用户确认并等待回复后才继续：

1. **确认节点一（开播确认）**：找到直播间并确认在播后，让用户确认抽查哪个直播间、录制几分钟。
2. **确认节点二（质检范围确认）**：录屏和妙记生成后，先交付 MP4 和妙记链接，再问用户是否开始质检、关心哪些方面；用户未特别指定时按默认全面质检继续。

暂停期间不要自行推进下一步，也不要替用户做默认选择（节点二的"全面质检"是唯一兜底默认，且需在提问时明确告知）。

## 前置条件检查
执行前确认（缺任一项先解决再继续）：
1. **浏览器已开远程调试**：`curl -s http://127.0.0.1:9222/json/list` 应返回 JSON。
2. **抖音已登录**：未登录时直播间取流会失败。用 `interaction.request_action` 请求用户接管浏览器完成登录，不要跳过。
3. **依赖就绪**：`ffmpeg -version` 和 `python3 -c "import websocket, requests"` 均应成功。缺 websocket 时 `pip3 install websocket-client`。

## 标准流程

### 第一步：定位直播间（无需预置账号表，直接搜索）
用户可能给的是以下任一种，全部支持：
- **直播间链接**：`live.douyin.com/<数字>` → 数字即 room_id，直接进入第二步。
- **账号名/直播间名**（如"某品牌官方旗舰店"）→ 用浏览器在抖音搜索。
- **品牌名**（如"某服饰品牌"）→ 搜索后切"直播"标签，可能返回多个矩阵号。

**搜索方法（推荐用脚本自动提取）：**
```bash
python3 scripts/search_live.py "<账号名或品牌名>"
```
脚本会自动打开抖音搜索页、切到"直播"标签、滚动加载，并列出所有在播直播间（账号名、room_id、直播标题、是否蓝V）。
- **无结果** → 告知用户该关键词下没有在播直播间，建议换关键词或确认账号名。
- **脚本失败时兜底**：手动用浏览器打开 `https://www.douyin.com/search/<关键词>?type=live`，从直播间卡片链接中提取 `live.douyin.com/<room_id>` 中的数字。

**账号缓存（可选加速，非必须）：**
`assets/accounts.csv` 记录已查过的账号（格式：`room_id,名称,类目,类型`）。搜索到新账号后可追加一行沉淀，下次同账号可直接用 room_id 跳过搜索。但**不要依赖此表作为前置步骤**——它只是缓存，新客户、新账号一律直接搜索。

### 第二步：确认开播状态
```bash
python3 scripts/probe_live.py <room_id>
# 批量探测某品牌已知矩阵号：python3 scripts/probe_live.py --file assets/accounts.csv
```
输出 `LIVE` 才继续。返回 `OFF` 时告知用户该账号当前未开播；若用户给的是品牌名且有多个矩阵号，可批量探测并给出当前在播清单——不要对未开播账号强行录制。

### 第三步：【确认节点一】确认抽查目标与录制时长
定位并确认在播后，**不要直接开始录制**。汇总当前在播直播间清单（账号名、直播标题、类目、room_id、直播间链接），向用户确认两件事：

1. **抽查哪个直播间**：多个在播时列出候选让用户选；即使只有唯一结果，也请用户确认"就是这个吗"，不要自行假设。
2. **录制几分钟**，给出推荐选项：
   - **2分钟**：快速巡检，适合多账号扫一遍、抓明显问题；
   - **3分钟**：标准抽查，性价比最高（推荐首选）；
   - **5分钟**：深度质检，适合重点账号或问题复盘。
   - 用户也可自定时长（如1分钟、10分钟）。

**必须暂停并等待用户回复**，拿到明确的"直播间 + 时长"后再进入第四步。

### 第四步：录制
```bash
python3 scripts/record_live.py --room <room_id> --duration <秒> --output <name>_<n>min.mp4
```
- 时长按确认节点一的结果换算（2分钟=120、3分钟=180、5分钟=300）。
- 脚本自动完成：发现可用浏览器 tab → 导航到直播间 → 等待流加载 → 提取 FLV → 按 `_or4 > _hd > _sd > _ld` 选最高清晰度 → ffmpeg 直录。
- **必须在后台运行**（录制时长超出前台阻塞预算），之后轮询任务状态。
- 录制完成后核验时长：
  ```bash
  ffprobe -v error -show_entries format=duration -of default=noprint_wrappers=1:nokey=1 <file>
  ```

**多个直播间可并行录制**——同时启动多个后台任务，总耗时仍约等于单个（录制是 IO 等待，不抢CPU）。

### 第五步：转写逐字稿
调用 `doubao-video-extract` skill 的妙记上传脚本（本地视频可直传，无需先转音频）：
```bash
cd <doubao-video-extract skill 目录> && \
python3 scripts/minutes/social_video_to_minutes.py "<视频绝对路径>" --media-mode video --run-lark
```
记下返回的 `minute_token`。**等待约 60-90 秒**后拉取逐字稿（立即拉取会返回 "minute not ready, try later"）：
```bash
lark-cli vc +notes --minute-tokens <token> --output-dir ./minutes --format json
```
逐字稿落在 `./minutes/artifact-<视频名>-<token>/transcript.txt`。`--output-dir` 必须是相对路径且位于当前工作目录内。
妙记链接格式：`https://bytedance.larkoffice.com/minutes/<minute_token>`——必须写进报告。

### 第六步：【确认节点二】首轮交付 + 确认质检范围
录屏 MP4 和妙记都就绪后，按以下顺序操作：

1. **先做一轮交付**（用 `NotifyHuman`，每次单个附件）：
   - 先交付录屏 MP4；
   - 再给出妙记链接（`https://bytedance.larkoffice.com/minutes/<minute_token>`）。
   交付时附一句说明：账号名、录屏时长、妙记刚生成需1-2分钟后可查看完整逐字稿。

2. **暂停并询问用户**：
   - "录屏和逐字稿已交付，是否现在开始质检？"
   - "你关心哪些方面？可多选（不指定则按全面质检执行）："
     - **画面检查**：直播间贴片/横幅/角标/字幕文字、商品展示、价格标识、背景布置、违规导流元素（二维码/微信号/外部平台）、主播形象；
     - **话术合规**：绝对化用语、虚假/夸大宣传、医疗宣称、虚构价格库存等违法违规风险；
     - **SOP执行**：开场收尾、卖点讲解、逼单节奏、互动引导、话术结构与节奏；
     - **售后与价格**：退款/质保/运费险/价保说明、原价/活动价/使用条件是否完整；
     - **全面质检**：以上全部（默认）。

3. **根据用户回复决定**：
   - 用户说"开始/继续/质检吧"但未指定方面 → 按**全面质检**执行；
   - 用户只选某几项 → 只做选中的方面，报告聚焦这些维度，未选维度如无明显高危问题可简略带过或标注"本次未检查"；
   - 用户说"先不用/等等" → 停止流程，告知素材已保留、随时可继续质检；
   - 用户提出自定义关注点（如"只看有没有说最低价""帮我看看商品展示清不清楚"）→ 纳入质检范围并据此调整重点。

**不要在用户回复前自行开始质检。**

### 第七步：质检（按确认的范围执行）

#### 7a. 画面检查（用户选中时执行）
基于抽帧做视觉巡检。**抽帧不能替代逐帧审核**，需在报告中注明抽帧间隔和这一局限：
```bash
mkdir -p frames && ffmpeg -i <file>.mp4 -vf "fps=1/10,scale=1280:-1" -q:v 3 frames/frame_%03d.jpg
```
- 每10秒抽一帧（2分钟≈12帧、3分钟≈18帧、5分钟≈30帧）；帧数过多时可放宽到15秒。
- 用 `Read` 逐帧查看，重点检查：
  - 贴片/横幅/角标/字幕文字是否含违规词（最/第一/国家级等绝对化用语、医疗术语、未审核的功效宣称）；
  - 价格标识是否清晰、是否与口播一致、是否有虚构原价痕迹；
  - 商品展示是否充分，是否展示包装/成分表/资质；
  - 背景是否整洁专业、有无违规物料；
  - 是否有二维码、微信号、外部平台导流等平台违规元素；
  - 主播着装/形象是否得体。
- 发现问题记录对应帧号/时间点、问题描述、风险等级。

#### 7b. 话术合规与SOP质检（按选中范围执行）

**规则层**（毫秒级，先跑；只要用户选了"话术合规"或"全面质检"就必跑）：
```bash
# 通用电商违禁词扫描（所有类目必跑）
python3 scripts/scan_violations.py <transcript.txt>
# 指定类目可激活类目专属检查项和SOP维度
python3 scripts/scan_violations.py <transcript.txt> --category apparel   # 服装
python3 scripts/scan_violations.py <transcript.txt> --category software  # 软件/3C/会员
python3 scripts/scan_violations.py <transcript.txt> --category food      # 食品
python3 scripts/scan_violations.py <transcript.txt> --category beauty    # 美妆
python3 scripts/scan_violations.py <transcript.txt> --category general   # 通用（默认）
# 需要结构化结果时加 --json
```
输出按高/中/低分级的违禁词命中项，每项带原话、上下文、法条依据和改写建议，并附 SOP 覆盖情况自检。

**类目判断方法**：根据直播间售卖商品判断——卖衣服鞋帽用 `apparel`，卖软件会员/数码3C用 `software`，卖食品保健品用 `food`，卖化妆品用 `beauty`，不确定或跨类目用 `general`。

**语义层**（LLM 判断，规则层跑完后做；用户选了"话术合规/SOP执行/售后与价格/全面质检"中任一项时执行）：读取 `references/qc-criteria.md`，先按**通用九维度**评分，再根据类目替换类目专属维度（见该文件"类目适配表"）。根据用户选中的范围调整重点：
- 选了"话术合规"：重点查语义型夸大、虚假宣传、医疗宣称、规则层漏网的谐音/变体；
- 选了"SOP执行"：重点查话术结构、逼单节奏、互动质量、亮点识别；
- 选了"售后与价格"：重点查退款/质保/运费险/价保说明、价格优惠清晰度；
- 选了"全面质检"：全部维度都做。

重点补充规则层抓不到的问题：
- 语义型夸大（无固定关键词，如"用了就是效率天花板"）
- 话术结构问题（有无开场收尾、逻辑连贯性、重复度）
- 互动质量（是否真的回应了弹幕，而非只喊"扣公屏"）
- 运营导向问题（如"买完再取关没关系"——不违法但损害品牌资产）
- 售后/退款/试用说明是否充分（软件/会员类尤其重要）
- 亮点识别（做得好的动作要写进报告，可作为培训案例）

**规则层结果需人工复核**：命中不等于必然违规（如温度承诺若同时公示了检测报告可降级），未命中也不代表合规。判定要点见 `references/qc-criteria.md`。

### 第八步：生成飞书文档报告
以 `assets/report-template.xml` 为骨架填充内容。模板中 SOP 检查项是通用占位符，**必须根据实际类目替换为对应维度**（见 `references/qc-criteria.md` 类目适配表），不要把服装类的"尺码引导"写到软件直播报告里。然后：
```bash
lark-cli docs +create --content @report.xml --format json
```
`@file` 必须是当前工作目录下的相对路径。报告必须包含：
- 基本信息表（账号名、类目、直播间链接 + **飞书妙记链接** + 录屏时长 + **本次质检范围**）
- SOP 执行检查表（每项带评分和实际表现，引用逐字稿原话；用户未选的维度可省略或标注"本次未检查"）
- **画面检查结果（用户选中时）**：抽帧间隔、发现的问题、对应帧号/时间点，并注明"基于抽帧、非逐帧审核"
- 合规风险清单（分高/中风险两张表，每条给可直接替换的改写建议）
- 亮点与改进建议（P0/P1/P2 分级）
- 有历史抽查数据时，加横向对比表

### 第九步：最终交付
报告生成后，用 `NotifyHuman` 交付飞书文档报告，并给收口总结：综合评分 + 最关键的几项高风险 + 值得推广的做法。总结要给实质内容（具体违规原话、具体分数、具体建议），不要描述报告有多完善。

MP4 和妙记已在确认节点二交付，此处不重复交付，除非用户要求。

## 关键约束与已知坑
| 事项 | 说明 |
|------|------|
| **两个确认节点必须暂停** | 节点一（开播+时长）、节点二（首轮交付+质检范围）都要等用户回复，不要一路自动跑完 |
| **yt-dlp 不支持抖音直播** | 实测报 `Unsupported URL`，必须走 CDP 方案，不要浪费时间尝试 |
| **流地址每场都变** | 主播每次开新场 stream id 都不同，缓存只存 room_id，流地址必须实时取 |
| **签名有时效** | 流 URL 约 1 小时过期，取到后立即录制，不要缓存复用 |
| **tab id 会失效** | 浏览器重启后 tab id 变化，`record_live.py` 已内置自动发现，不要硬编码 |
| **`\u0026` 转义** | 从 performance entries 提取的 URL 中 `&` 被转义为 `\u0026`，脚本已处理 |
| **一个账号可能多个 room_id** | 同一账号可能有多个入口 room_id，可能指向同一场直播 |
| **搜索页虚拟滚动** | 抖音搜索结果非可见区域 DOM 会被移除，`search_live.py` 已自动滚动加载 |
| **ASR 会插标点** | 逐字稿常在句中插入「。」，写正则时分隔符类不要排除句号，否则漏检 |
| **画面检查是抽帧** | 只能发现抽帧时刻的画面问题，不能覆盖全程，报告中必须注明这一局限 |
| **飞书操作只走 lark-cli** | 文档用 `lark-cli docs`，妙记用 `lark-cli vc`，禁止用浏览器打开飞书链接 |
| **不要硬编码账号表** | 新客户新账号一律直接搜索，`accounts.csv` 只是缓存不是前置依赖 |

## 跨账号共性问题识别（价值最高的产出）
多个账号出现**完全相同**的违规表述时，说明问题在统一下发的话术模板或培训材料，而非个别主播临场发挥。这类发现必须在报告中单独标注，并建议从模板层面清理——比逐个培训主播效率高得多。

## 扩展：定时巡检
用户要求常态化/定期抽查时，匹配 `doubao-cron-scheduler` skill 创建定时任务。注意定时任务依赖浏览器登录态，登录过期会导致取流失败，需在任务中加登录态检查和失败通知。定时巡检场景下，确认节点一可按用户预设的账号清单和时长自动执行，但确认节点二的质检范围仍建议在首次配置时与用户约定好（默认全面质检）。

## 适配新客户/新类目
流程与品牌无关，新客户只需：
1. 给账号名或品牌名 → 直接搜索定位，无需预置任何数据。
2. 根据商品类目选择 `--category` 参数（apparel/software/food/beauty/general）。
3. 拿到客户自己的运营 SOP 后，可在 `references/qc-criteria.md` 的类目适配表中补充专属维度。
4. `scan_violations.py` 中的 `RULES` 是通用电商直播违禁词，跨类目可直接复用；类目专属规则（如服装的温度承诺）通过 `--category` 条件激活。
