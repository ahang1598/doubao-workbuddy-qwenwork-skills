# 共同处理型DPA协议操作指南

> **适用场景**：双方或多方就同一处理活动共同决定处理目的和关键方式
> **核心判断**：是否共同决定为什么处理数据、如何处理数据的关键方面

## 一、快速判断规则

### 1.1 三种数据处理关系区分

| 关系类型 | 判断核心 | 典型特征 |
|---------|---------|---------|
| **委托处理** | 一方决定目的，另一方仅按指示处理 | 乙方无独立处理目的，完全服从甲方指示 |
| **对外提供** | 接收方为自身独立目的处理 | 各自决定后续处理目的和方式 |
| **共同处理** | 双方共同决定处理目的和关键方式 | 联合设计、联合运营、联合控制 |

### 1.2 支持"共同处理"判断的迹象

- 双方共同设计数据收集逻辑和用户接触界面
- 双方共同决定处理目的，而非各自独立后续利用
- 双方共同决定关键使用方式、共享范围或对外展示规则
- 数据主体会合理认为双方共同提供相关服务
- 双方对同一处理活动具有持续、实质性的共同控制

### 1.3 削弱"共同处理"判断的迹象

- 一方仅提供技术支持、托管、客服、外包服务
- 一方仅在收到数据后为自身独立目的使用数据
- 双方只是合同相对方，但并未共同设计处理活动
- 一方仅按另一方规则接入系统，没有共同决定空间
- 双方各自处理各自数据，只在有限环节发生共享

### 1.4 判断流程

```
Step 1: 谁决定处理目的？
        → 仅一方决定 → 委托处理或对外提供
        → 双方共同决定 → 继续 Step 2

Step 2: 谁决定关键处理方式（收集逻辑、使用方式、共享范围、对外披露、保存期限）？
        → 仅一方决定 → 委托处理或对外提供
        → 双方共同决定 → 共同处理

Step 3: 确认共同处理范围
        → 仅限于特定处理活动，而非全部合作
```

## 二、必读法条清单

### 2.1 骨架法条（本类型必读）

| 法条 | 核心要求 | 条款体现 |
|------|---------|---------|
| **个保法第20条** | 共同处理者的权利义务约定、连带责任 | 共同处理范围、责任分配、连带责任条款 |
| **条例第12条第3款** | 共同处理的细化规则 | 统一窗口、透明安排、请求响应协作 |

### 2.2 血肉法条（根据场景增量读取）

| 场景要素 | 增量法条 | 读取指引 |
|---------|---------|---------|
| **敏感个人信息** | 个保法第28-32条、告知指南§6.3.2 | 敏感信息单独同意、必要性和影响说明 |
| **个人信息出境** | 个保法第38-40条、条例第35-40条、告知指南§6.3.3 | 跨境条款、跨境单独同意 |
| **未成年人信息** | 个保法第32条、告知指南§9.3 | 监护人单独同意 |
| **重要数据** | 条例第28-34条 | 重要数据处理规则 |
| **触发PIA** | 个保法第55-56条、条例第53条 | 共同处理触发PIA，见[PIA触发规则](个人信息保护影响评估触发规则.md) |

### 2.3 法条选取示例

```
场景：共同处理 + 敏感信息 + 无跨境

必读（骨架）：个保法第20条 → 条例第12条第3款
增量（血肉）：个保法第28-32条（敏感信息）、告知指南§6.3.2
无需：个保法第38-40条（跨境）
```

## 三、起草前必问问题

### 2.1 基础信息

| 问题项 | 说明 |
|-------|------|
| 各方身份 | 各方是谁，分别位于何处 |
| 业务目标 | 合作项目的业务目标是什么 |
| 处理活动 | 共同处理的具体活动是什么（不能笼统说"双方合作中涉及数据"） |

### 2.2 处理控制权

| 问题项 | 说明 |
|-------|------|
| 处理目的 | 谁决定处理目的，是否为共同决定 |
| 关键方式 | 谁决定收集方式、使用方式、共享范围、对外披露、保存期限 |
| 数据来源 | 数据主体是谁，数据从哪里收集 |

### 2.3 数据类型

| 问题项 | 说明 |
|-------|------|
| 信息类别 | 涉及哪些类别的个人信息 |
| 敏感信息 | 是否包含敏感个人信息、儿童信息、医疗健康信息、金融账户信息、位置数据等 |

### 2.4 对外安排

| 问题项 | 说明 |
|-------|------|
| 页面控制 | 面向数据主体的页面、界面、活动规则、通知文本由谁控制 |
| 透明告知 | 谁负责透明告知和必要同意，是共同负责还是由一方主导 |
| 联系窗口 | 数据主体请求由谁作为统一窗口接收 |

### 2.5 安全与协作

| 问题项 | 说明 |
|-------|------|
| 安全措施 | 谁负责安全措施，各方之间是否有最低基线 |
| 事件协作 | 一方发生安全事件时，另一方如何获知并协作 |
| 第三方披露 | 是否允许向第三方进一步提供 |
| 跨境安排 | 是否涉及跨境（触发PIA义务） |

### 2.6 责任与退出

| 问题项 | 说明 |
|-------|------|
| 协议范围 | 是否仅覆盖某一特定联合项目，还是覆盖更广泛合作 |
| 责任结构 | 双方希望的责任结构是对等、按过错分配，还是有特别赔偿安排 |
| 退出安排 | 合作结束或一方退出时数据如何处理 |

## 四、场景起草要点

### 3.1 联合营销和联名活动

#### 共同处理判断

- **构成共同处理**：双方共同设计活动页面、共同决定要收集哪些信息、共同决定如何触达用户、共同决定数据在活动结束前后的使用逻辑
- **不构成共同处理**：一方只是赞助商、渠道方或技术支持方

#### 协议重点

| 条款 | 要点 |
|-----|------|
| 范围条款 | 共同处理范围是否仅限于该次活动 |
| 透明告知 | 收集页面和隐私告知由谁制作和发布 |
| 同意获取 | 谁负责取得必要同意 |
| 后续使用 | 报名信息是否会被各方各自导出并继续独立使用 |
| 阶段区分 | 活动结束后数据是否转入各自独立处理阶段 |
| 联系窗口 | 谁作为用户权利请求的统一联系窗口 |

#### 常见误区

- 把一切联合活动都写成共同处理
- 不区分活动期间共同处理和活动结束后各自独立处理
- 没有限定联合品牌和数据使用边界

---

### 3.2 共同运营平台或联合会员体系

#### 共同处理判断

当两方或多方共同运营一个平台、会员体系、积分计划、联合账户或统一服务入口，并共同决定用户信息收集、使用、展示和运营规则时，较容易出现共同处理结构。

#### 协议重点

| 条款 | 要点 |
|-----|------|
| 范围条款 | 共同处理活动的边界，是仅限注册和账户管理，还是延伸至营销、画像、客服、数据分析 |
| 品牌入口 | 用户面对的是统一品牌入口还是多品牌并列入口 |
| 隐私告知 | 隐私告知是统一版还是分别版 |
| 请求分流 | 用户请求如何分流和转办 |
| 事件沟通 | 安全事件发生时由谁统一对外沟通 |
| 退出安排 | 若某一方退出合作，历史数据如何处理 |

#### 常见误区

- 只写"双方共同处理会员数据"，但完全不写具体分工
- 既想享受共同运营的灵活性，又想把所有责任压给其中一方

---

### 3.3 研究、画像与联合分析项目

#### 共同处理判断

- **构成共同处理**：双方共同决定数据来源、样本范围、处理目的、分析方法、输出方式和使用规则
- **不构成共同处理**：一方仅向另一方提供去标识化数据，另一方独立开展研究

#### 协议重点

| 条款 | 要点 |
|-----|------|
| 范围条款 | 共同处理的数据范围与项目范围 |
| 数据类型 | 是否涉及可识别个人信息还是去标识化/匿名化数据 |
| 合法性基础 | 谁负责原始收集合法性基础 |
| 成果归属 | 分析结果归属与再利用边界 |
| 独立使用 | 是否允许各方将项目成果转入自身独立使用阶段 |
| 数据处置 | 数据保留和删除规则 |

#### 常见误区

- 只因为双方都参与项目，就当然写成共同处理，而未分析处理控制权是否真的共同存在

## 五、核心条款清单与写法

### 4.1 必备条款清单

| 序号 | 条款 | 核心功能 |
|-----|------|---------|
| 1 | 共同处理范围条款 | 明确哪些具体处理活动构成共同处理，避免无限外扩 |
| 2 | 角色和分工条款 | 明确各方在透明告知、合法性基础、同意获取、接口管理等方面的职责 |
| 3 | 透明告知条款 | 明确谁提供隐私告知、告知如何体现共同处理事实 |
| 4 | 数据主体请求条款 | 明确统一联系窗口、内部转办机制、答复时限和配合义务 |
| 5 | 数据类别与目的条款 | 明确处理目的、数据类别、数据主体类别和使用边界 |
| 6 | 安全措施条款 | 明确各方最低安全义务、接口和共享链路保护要求 |
| 7 | 安全事件协作条款 | 明确一方发生事件时的通知、调查、缓释和对外协调机制 |
| 8 | 第三方披露条款 | 明确各方是否可向第三方继续披露以及边界 |
| 9 | 跨境条款 | 如涉及跨境，明确由谁履行何种前置义务（含PIA义务） |
| 10 | 保留删除退出条款 | 明确合作终止、项目结束、单方退出时的数据安排 |
| 11 | 责任分配条款 | 区分各方可控范围和责任归属 |
| 12 | 期限终止争议条款 | 补足法律文件基本结构 |

---

### 4.2 共同处理范围条款

#### 起草目标

回答：到底哪些具体处理活动属于共同处理，而不是笼统地把双方整个合作关系都包进去。

#### 推荐写法

应具体到处理活动层面，例如：

- 共同举办某次活动时对报名信息的收集和使用
- 共同运营某一会员体系时对注册、积分记录和活动触达信息的处理
- 共同管理联合平台账户时对账户信息和使用日志的处理

若合作中还存在各方后续独立使用数据的阶段，应明确区分。

#### 常见误区

- 只写"双方在合作中共同处理个人信息"，没有边界
- 不区分共同处理阶段与后续独立处理阶段
- 把本应属于委托处理或独立处理的活动也并入共同处理

---

### 4.3 透明告知与合法性基础条款

#### 分工方式

| 角色 | 职责 |
|-----|------|
| 主导窗口方 | 负责页面展示和基础告知（通常是更接近数据主体的一方） |
| 各方共同 | 确认隐私文本内容 |
| 前端操作方 | 负责取得同意或单独同意，另一方提供必要信息支持 |
| 统一页面 | 应体现共同处理事实和主要责任安排 |

#### 常见误区

- 双方都说自己负责，实际上没人真正落地
- 双方都不负责，以为对方会做
- 未在告知中体现共同处理关系，导致透明性不足
- 把所有前端义务扔给技术控制方，而忽略业务主导方的作用

---

### 4.4 数据主体请求条款

#### 条款要素

| 要素 | 内容 |
|-----|------|
| 统一窗口 | 谁作为统一联系窗口 |
| 转交机制 | 其他方收到请求后是否应转交 |
| 协助时限 | 各方需在多长时间内提供协助 |
| 答复主导 | 如请求仅涉及某一方控制的数据，由谁主导答复 |
| 拒绝协调 | 若一方拟拒绝请求，是否需与其他方协调 |
| 类型区分 | 对解释说明、访问、更正、删除、撤回同意、投诉等不同类型请求是否需要区分 |

#### 常见误区

- 完全不设统一窗口
- 只写"双方互相配合"，没有时限和流程
- 忽略不同数据分散在不同系统中的现实

---

### 4.5 安全措施条款

#### 条款要素

| 要素 | 内容 |
|-----|------|
| 各方责任 | 各方对自身系统和访问权限负责 |
| 接口安全 | 数据共享接口、传输链路和联合页面的安全要求 |
| 人员管理 | 员工和合作人员的保密与授权管理 |
| 高风险数据 | 对高风险敏感数据适用更高控制 |
| 统一标准 | 必要时采用统一加密、日志、留痕和权限审查标准 |
| 预警机制 | 一方发现风险时向另一方发出预警的机制 |

#### 常见误区

- 只写"双方应采取合理安全措施"，没有任何分工
- 以为共同处理就可以不区分谁管哪个系统
- 没有接口安全和协同流程

---

### 4.6 安全事件协作条款

#### 合理结构

| 阶段 | 安排 |
|-----|------|
| 发现 | 发现方尽快通知 |
| 信息共享 | 各方共享已知事实和影响范围 |
| 技术调查 | 如事件发生于某一方系统，由该方主导技术调查 |
| 对外沟通 | 如需面向数据主体或监管说明，由更接近数据主体或法律责任更直接的一方牵头，但需与其他方协调 |
| 紧急情形 | 对外发布前原则上应进行必要协调，但紧急情形除外 |

#### 常见误区

- 只写"及时通知"，不写协作和牵头安排
- 双方都保留单独对外发布权，导致口径冲突
- 没有考虑紧急情形

---

### 4.7 第三方披露与后续独立使用条款

#### 条款结构

| 要素 | 内容 |
|-----|------|
| 基本原则 | 原则上，各方不得超出共同处理目的向第三方提供数据 |
| 必要例外 | 法律法规、监管要求、争议处理或紧急情形所需的披露可作为必要例外 |
| 独立使用 | 若合作结束后各方拟继续独立使用某些数据，应明确独立处理的法律基础、使用目的、边界和透明安排 |
| 第三方角色 | 如需第三方支持共同项目，应明确其角色究竟是受托处理者、独立接收方还是其他身份 |

#### 常见误区

- 只处理共同阶段，不处理后续独立使用
- 默认任何一方都可自由导出并再利用全部数据
- 把共同处理和后续共享混在一起

---

### 4.8 责任分配条款

#### 设计方式

| 要素 | 内容 |
|-----|------|
| 各方责任 | 各方对其负责的透明告知、同意获取、页面管理、系统安全、后续披露、请求响应等事项承担责任 |
| 违约责任 | 因某一方违反其明确分工或适用法律而导致的损失，由该方承担 |
| 共同事项 | 对共同决定且无法完全切分的事项，可约定按过错程度、贡献程度或另行协商分担 |
| 责任上限 | 如商业上需要，可设置责任上限，但应注意与主协议衔接 |

#### 注意事项

- 不建议仅写"双方承担连带责任"而不作任何内部追偿和分工安排

#### 常见误区

- 认为共同处理就不需要细分责任
- 用过于抽象的"双方各自承担相应责任"代替实际分工
- 只写对外责任，不写内部责任分担

---

### 4.9 退出、终止与数据善后条款

#### 条款要素

| 要素 | 内容 |
|-----|------|
| 处理终止 | 合作项目结束后，是否立即终止共同处理 |
| 退出后续 | 若一方退出，其他方能否继续处理既有数据 |
| 通知更新 | 是否需要通知数据主体或更新对外说明 |
| 留存范围 | 留存数据是否仅限争议处理、审计、法定义务或历史记录 |
| 技术处理 | 数据迁移、备份和日志如何处理 |
| 书面确认 | 删除或隔离是否需要书面确认 |

#### 常见误区

- 完全不写合作结束后的安排
- 只写"各自依法处理"，没有操作性
- 没有处理联合页面、账户体系和用户预期问题

## 六、常见误区与禁用表述

### 5.1 十大起草误区

| 误区 | 问题 |
|-----|------|
| 1. 把普通合作误写成共同处理 | 仅因双方合作或共享收益，并不足以构成共同处理 |
| 2. 不限定共同处理范围 | 导致整份协议像雾气一样四处蔓延 |
| 3. 只写"共同负责"，不写分工 | 结果是人人都负责，等于人人不负责 |
| 4. 混用processor语言 | 一边写共同处理，一边又写某方"仅按另一方指示处理" |
| 5. 不处理对外透明安排 | 数据主体根本不知道双方是如何共同处理的 |
| 6. 不设统一联系窗口 | 数据主体请求无法高效响应 |
| 7. 不区分共同处理阶段和后续独立处理阶段 | 后续使用边界混乱 |
| 8. 安全事件条款没有牵头机制 | 一出事就像双驾驶座的车，谁都握着方向盘 |
| 9. 责任条款过度抽象 | 对内对外都不清楚 |
| 10. 不写退出和终止后的安排 | 合作一散，数据去向成了野生动物 |

### 5.2 不宜默认使用的表述

| 表述 | 问题 | 替代方案 |
|-----|------|---------|
| "双方对所有处理活动承担完全相同责任" | 共同处理并不意味着控制范围完全一致 | 在各自负责范围内承担责任 |
| "某一方仅按另一方指示处理" | 若已认定共同处理，此表述通常失真 | 按分工承担相应职责 |
| "双方对任何损失承担无限连带责任" | 商业上通常阻力很大，且未处理内部责任分担 | 按过错程度分配，必要时设置责任上限 |
| "任何第三方披露均绝对禁止" | 忽略监管要求、争议处理、法定义务和必要合作链条 | 法律要求或紧急情形除外 |
| "一方可自行对外答复所有数据主体请求" | 可能造成口径冲突和责任错配 | 经协调后对外沟通 |
| "合作结束后立即删除所有相关数据和备份" | 忽略审计、争议、法定义务和技术现实 | 留存数据仅限法定义务、争议处理等必要情形 |

### 5.3 更平衡的表述方式

- 在各自负责范围内
- 共同处理活动范围内
- 合理必要
- 在法律允许范围内
- 按过错程度分配
- 经协调后对外沟通
- 法律要求或紧急情形除外

## 七、起草风格选择

### 6.1 三种风格对比

| 风格 | 适用场景 | 特点 |
|-----|---------|------|
| **平衡版** | 中长期合作、双方均有一定议价能力、希望既合规又能落地 | 共同处理范围明确、分工细化、责任相对对等，对安全、请求响应、事件协作和退出安排写得较完整 |
| **强保护版** | 数据敏感度高、项目监管风险高、其中一方更关注品牌或监管暴露 | 更强调统一窗口、文本审定权、更严格的第三方披露限制、更清晰的事件牵头和更强的赔偿保护 |
| **成交优先版** | 时间紧、合作方议价能力强、联合项目市场压力大 | 保留最核心的范围、分工、透明、事件协作和责任条款，但避免过度复杂的内部流程和过强审计、审批要求 |

### 6.2 风格选择指引

根据用户描述的场景和立场偏好，自动选择相应风格：

1. **用户明确要求保护己方** → 强保护版
2. **用户强调快速签约、商业优先** → 成交优先版
3. **用户未明确偏好或希望平衡** → 平衡版（默认）

## 附录：短版判断规则卡

```
【判断规则】

仅在双方对同一处理活动共同决定处理目的和关键方式时，
优先考虑共同处理型DPA。

若一方仅按另一方指示处理数据，
应优先考虑委托处理型DPA。

若一方接收数据后为自身独立目的处理，
应优先考虑数据对外提供协议或独立处理者之间的数据共享结构。

【核心条款】

共同处理协议应重点围绕以下条款展开：
1. 共同处理范围
2. 透明告知
3. 同意与合法性基础分工
4. 统一联系窗口
5. 请求响应
6. 安全措施
7. 事件协作
8. 第三方披露
9. 后续独立使用边界
10. 责任分配
11. 退出安排

【禁止】

不得将"共同处理"写成没有边界、没有分工、
没有窗口的一团大棉被。
```
