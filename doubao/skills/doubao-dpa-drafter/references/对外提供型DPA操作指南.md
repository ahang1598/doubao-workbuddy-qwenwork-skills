# 数据对外提供协议（DPA）操作指南

> **适用场景**：一方向另一方提供个人信息，接收方基于自身独立业务目的处理数据（非委托处理关系）
> **核心判断**：接收方是否拥有独立处理目的、是否为自身业务/合规目的处理数据

## 一、概念与判断

### 1.1 什么是对外提供DPA

**核心特征**：
- 接收方**并非仅按提供方指示处理**数据
- 接收方基于**自身独立业务目的、法律义务或业务判断**处理数据
- 双方是**独立处理者**关系，非委托处理关系

**典型场景**：
| 场景 | 说明 |
|------|------|
| 再保险 | 保险公司向再保公司提供理赔和被保险人信息 |
| 集团共享 | 集团内公司为各自合规或运营目的共享数据 |
| 金融合作 | 向支付机构、征信机构、风控合作方提供数据 |
| 跨境业务 | 为境外理赔、救援、调查、争议解决提供信息 |

**常见错误**：
- 误把独立处理者关系写成委托处理
- 要求接收方"仅按提供方指示处理"
- 未写清第三方转传边界
- 未处理跨境安排
- 责任条款过硬或角色错位

---

### 1.2 如何判断场景类型

**判断核心**：谁决定处理目的 + 谁控制核心处理安排

| 场景类型 | 判断标准 |
|---------|---------|
| **委托处理** | 接收方仅按提供方指示处理，不得为自身独立目的使用 |
| **对外提供** | 接收方为自身业务目的处理（核保、再保险审核、理赔审查、审计、合规、风控建模等） |
| **共同处理** | 双方共同决定处理目的和关键方式（联合营销、共同运营平台、联合画像等） |

**支持"对外提供"判断的迹象**：
- ✅ 接收方有自身独立的处理目的
- ✅ 接收方并非仅按提供方指示行动
- ✅ 接收方对保存期限、再利用边界承担独立判断
- ✅ 接收方因自身法定义务需要保留和使用数据
- ✅ 接收方与数据提供方各自对数据主体承担部分独立义务

**削弱"对外提供"判断的迹象**：
- ❌ 接收方仅提供技术、托管、客服、IT等外包服务
- ❌ 接收方原则上不能将数据用于自身目的
- ❌ 服务终止后接收方需删除或返还全部数据
- ❌ 接收方严格服从提供方指示，缺乏独立决定空间

---

### 1.3 起草前必问问题

**必问清单**（按优先级排序）：

| 序号 | 问题 | 目的 |
|------|------|------|
| 1 | 提供方和接收方分别是谁，双方所在地 | 确定主体和跨境事实 |
| 2 | 接收方处理数据是为了自身独立目的，还是仅为提供服务 | 确定场景类型 |
| 3 | 数据提供的具体目的是什么 | 界定处理目的 |
| 4 | 涉及哪些类别的个人信息（是否含敏感/医疗/金融/未成年人/位置等高风险数据） | 确定风险等级 |
| 5 | 数据主体是谁，个人信息从何而来 | 确定前端合规责任 |
| 6 | 提供方是否负责前端告知、同意、单独同意 | 确定前端义务分配 |
| 7 | 是否涉及个人信息出境 | 确定跨境条款需求 |
| 8 | 接收方是否允许再向第三方提供，边界是什么 | 确定转传限制 |
| 9 | 数据保留期限由谁决定 | 确定删除/留存规则 |
| 10 | 数据主体请求由谁主导响应 | 确定协作机制 |
| 11 | 责任结构是对等、分类还是责任上限 | 确定责任条款风格 |
| 12 | 适用法和争议解决方式 | 完善基础条款 |

## 二、必读法条清单

### 2.1 骨架法条（本类型必读）

| 法条 | 核心要求 | 条款体现 |
|------|---------|---------|
| **个保法第23条** | 向他人提供个人信息的要求：告知+单独同意+接收方信息 | 合法性基础与前端义务、接收方使用边界 |
| **条例第21条** | 对外提供的细化规则 | 双方独立地位、使用边界 |
| **告知指南§6.3.1** | 向其他个人信息处理者提供的告知内容要求 | 告知内容清单、单独同意内容 |

### 2.2 血肉法条（根据场景增量读取）

| 场景要素 | 增量法条 | 读取指引 |
|---------|---------|---------|
| **敏感个人信息** | 个保法第28-32条、告知指南§6.3.2 | 敏感信息单独同意、必要性和影响说明 |
| **个人信息出境** | 个保法第38-40条、条例第35-40条、告知指南§6.3.3 | 跨境条款、跨境单独同意 |
| **第三方转传** | 个保法第23条（变更告知） | 第三方转传条款 |
| **未成年人信息** | 个保法第32条、告知指南§9.3 | 监护人单独同意 |
| **重要数据** | 条例第28-34条 | 重要数据处理规则 |
| **触发PIA** | 个保法第55-56条、条例第53条 | 对外提供必然触发PIA，见[PIA触发规则](个人信息保护影响评估触发规则.md) |

### 2.3 法条选取示例

```
场景：对外提供 + 敏感信息 + 跨境 + 无第三方转传

必读（骨架）：个保法第23条 → 条例第21条 → 告知指南§6.3.1
增量（血肉）：个保法第28-32条（敏感信息）、第38-40条（跨境）、告知指南§6.3.2/§6.3.3
无需：第三方转传相关条款
```

## 三、典型场景

### 2.1 再保险/理赔/救援

**场景特点**：
- 接收方为自身再保险审核、理赔评估、争议处理、合规留档、风险管理而独立处理
- 非委托处理关系

**起草重点**：
| 条款 | 注意事项 |
|------|---------|
| 数据范围 | 是否涉及医疗健康等敏感信息 |
| 跨境条款 | 是否出境，接收方/后续接收方位置 |
| 第三方转传 | 是否向调查机构、服务商、代理人、救援链条第三方转传 |
| 例外保留 | 是否需要紧急救援或法律要求的例外 |
| 删除与留档 | 如何平衡删除与理赔/争议/监管保留需要 |
| 责任条款 | 保持对等和可签署性 |

**常见误区**：
- 错写成受托处理
- 要求接收方"仅按提供方指示处理"
- 要求接收方承担全部前端告知义务
- 删除条款不考虑理赔、争议或监管保留需要

---

### 2.2 集团内部共享

**场景特点**：
- 接收方为自身人力资源管理、财务审计、合规管理、内部调查、客户服务、区域管理、IT安全监控而处理
- 非当然的委托处理

**起草重点**：
- 共享范围与目的限定
- 跨境事实确认
- 访问控制与共享边界
- 后续转传限制
- 数据主体请求协作
- 集团内责任分配

**常见误区**：
- 把所有集团内共享都写成委托处理
- 笼统写"集团内部可基于经营需要共享"但不限定范围和目的

---

### 2.3 支付/结算/风控/征信

**场景特点**：
- 接收方基于自身合规、风控、结算管理、反欺诈、征信评估等独立目的处理
- 非委托处理者

**起草重点**：
- 各自独立目的和义务边界
- 接收方可否用于模型训练或风险画像
- 后续共享边界
- 监管报送例外
- 争议处理留档
- 投诉和查询请求协作

**不宜照搬processor DPA**：
- 接收方通常不会接受"仅按指示处理"定位
- 通常不能承诺在所有方面服从提供方删除指令

---

## 四、核心条款设计

### 3.1 条款清单总览

**必须覆盖的核心条款**：

| 序号 | 条款 | 核心内容 |
|------|------|---------|
| 1 | 角色界定 | 明确双方为独立处理者，接收方非仅按指示处理 |
| 2 | 数据范围与目的 | 提供的数据类别、数据主体、提供目的、允许/禁止用途 |
| 3 | 合法性基础与前端义务 | 谁负责告知、同意、单独同意、影响评估 |
| 4 | 接收方使用边界 | 仅在约定目的和必要范围内处理，不得越权 |
| 5 | 第三方转传 | 限制进一步提供，规定例外和条件 |
| 6 | 跨境条款 | 跨境事实、责任分配和协助事项 |
| 7 | 安全保障 | 与风险相适应的技术和组织措施 |
| 8 | 数据主体权利协作 | 访问、更正、删除、解释说明、投诉的协作方式 |
| 9 | 事件响应 | 安全事件通知和协作机制 |
| 10 | 删除与留存 | 目的实现后、协议终止后或法律要求下的处理规则 |
| 11 | 审计或证明 | 合规证明或有限检查权（如需要） |
| 12 | 责任与赔偿 | 与独立角色和实际控制能力匹配的责任分配 |
| 13 | 期限与终止 | 协议期限、终止情形及终止后安排 |
| 14 | 通知、争议解决 | 基础法律文件结构 |

---

### 3.2 角色界定条款

**目标**：准确反映双方各自独立处理的地位和边界

**推荐要素**：
```
1. 双方各自独立承担其依法应承担的数据保护义务
2. 接收方并非仅按提供方指示处理数据
3. 接收方不得将数据用于约定目的之外的独立商业用途（除非另有明确约定）
4. 双方均不得当然将自身法定义务转嫁给对方
```

**常见误区**：
- ❌ 一边写接收方独立处理，一边又写"仅按提供方指示处理"
- ❌ 把所有义务都压给接收方，忽略提供方前端义务
- ❌ 把接收方写得毫无独立责任，只剩"代为处理"色彩

---

### 3.3 合法性基础与前端义务

**责任分配原则**：

| 义务类型 | 承担方 | 理由 |
|---------|--------|------|
| 确定合法性基础 | 提供方 | 更接近数据主体，更了解收集来源 |
| 向数据主体履行告知 | 提供方 | 控制原始处理场景 |
| 取得同意或单独同意 | 提供方 | 前端合规责任 |
| 告知接收方身份和目的 | 提供方 | 前端合规责任 |
| 完成内部评估程序 | 提供方 | 前端合规责任 |
| 约定目的范围内使用数据 | 接收方 | 后端义务 |
| 采取安全措施 | 接收方 | 后端义务 |
| 依法处理投诉和请求 | 接收方 | 后端义务 |

**条款设计避坑**：
- ❌ 把所有前端义务都写给接收方
- ❌ 只写"提供方已取得一切同意"，却未明确接收方的后端义务

---

### 3.4 接收方使用边界

**目标**：防止接收方在取得数据后无限扩张用途

**条款应回答的问题**：
```
1. 接收方可以为哪些目的处理数据？
2. 何种用途被禁止？
3. 是否允许内部风控、合规、审计、争议留档等附随处理？
4. 是否允许去标识化、匿名化、聚合后使用？
5. 是否需要额外授权后方可扩展用途？
```

**常见误区**：
- ❌ 只写"接收方应合法使用"，没有具体边界
- ❌ 禁止一切使用，不给合规留档和争议处理留空间
- ❌ 赋予接收方过宽的"改进业务、商业分析、模型开发"等用途

---

### 3.5 第三方转传条款

**基础逻辑**：原则上禁止 + 必要例外

**条款设计要点**：

| 要点 | 内容 |
|------|------|
| 基本原则 | 未经提供方事先同意，不得再向第三方提供 |
| 必要例外 | 法律法规要求、监管机关要求、争议处理必需、紧急救援、实现约定目的所必需的受限转传 |
| 例外条件下 | 接收方是否需确保第三方承担不低于本协议的保护义务 |
| 通知要求 | 是否需事先通知提供方 |
| 紧急情况 | 可否先转传后通知 |
| 关联方 | 关联方是否也属于第三方 |

**常见误区**：
- ❌ 绝对禁止任何第三方披露，忽略现实业务链条
- ❌ 对例外写得过宽，如"业务需要即可共享"
- ❌ 不要求接收方对子接收方建立约束

---

### 3.6 跨境条款

**重要提示**：向境外提供个人信息将触发个人信息保护影响评估（PIA）义务，且PIA是跨境合规路径的前置步骤。PIA触发情形详见 SKILL.md 路由的「个人信息保护影响评估触发规则」参考文档。

**责任分配**：

| 提供方责任 | 接收方责任 |
|-----------|-----------|
| 识别是否构成出境 | 配合提供必要信息 |
| 确认适用的前置程序 | 提供接收方身份、联系方式 |
| 完成必要的告知和同意 | 说明处理目的、处理方式、数据类别 |
| **开展个人信息保护影响评估** | **配合PIA提供必要资料** |
| 完成内部评估或其他前置安排 | 说明安全措施、后续接收方情况 |
| | 承担使用限制、安全保障、协助说明、后续转传控制 |

**不宜要求**：
- ❌ 要求接收方承诺其所在国家或地区整体保护水平
- ❌ 将跨境前置程序完全推给接收方

---

### 3.7 删除与留存条款

**核心原则**：目的实现后不再无限期保留 + 合法必要的例外留存

**合理结构**：
```
1. 当接收方完成约定目的，且无继续留存的合法必要性时，应删除或匿名化处理
2. 若法律法规、监管要求、争议处理、审计留档或建立、行使、抗辩权利所必需，可在必要范围内继续留存
3. 留存期间继续适用保密和安全义务
4. 可要求接收方在可行范围内确认已完成删除或隔离
```

**常见误区**：
- ❌ 要求接收方无条件按提供方要求立即删除
- ❌ 完全不限制留存期限
- ❌ 不区分普通数据与高风险敏感数据

---

### 3.8 数据主体请求协作

**分工原则**：与数据主体有直接关系的一方主导，另一方协助

**条款应写清**：
```
1. 数据主体联系接收方时，接收方是否可直接答复，还是应先转给提供方
2. 面对访问、更正、删除、解释说明、投诉时双方如何分工
3. 是否存在因各自独立身份而分别答复的场景
4. 协助范围是否限于合理、必要和可行的程度
```

**常见误区**：
- ❌ 完全把所有请求处理责任推给接收方
- ❌ 完全不写协作，导致实践中互相推诿
- ❌ 忽略独立处理者地位下各方可能分别承担义务的现实

---

### 3.9 安全事件通知

**条款应明确**：

| 要素 | 内容 |
|------|------|
| 触发标准 | 什么情况构成需通知的安全事件 |
| 通知时限 | 发现后多少小时内通知 |
| 首次通知内容 | 已知事实、影响范围 |
| 后续更新义务 | 是否需要持续更新 |
| 对外通报 | 由谁主导通知监管或数据主体 |
| 紧急处置 | 是否保留紧急处置优先权 |

**常见误区**：
- ❌ 要求接收方在极短时间内完成全部调查并出具完整报告
- ❌ 把对外监管报送全部推给一方
- ❌ 只写"及时通知"，没有任何协作要求

---

### 3.10 责任与赔偿条款

**合理设计原则**：

```
1. 提供方对其前端合法性基础、告知和必要同意负责
2. 接收方对其接收后的超范围使用、安全不足、非法转传、违反约定目的等负责
3. 双方各自对自身违反适用法律或协议约定的行为承担责任
4. 设置直接实际损失及合理维权费用为责任基础
5. 合理排除纯粹间接损失、惩罚性赔偿或不可预见损失
6. 如主合同已有责任上限，应考虑与本协议衔接
```

**不建议默认使用**：
- ❌ "接收方赔偿全部损失"
- ❌ "任何违反均承担无限责任"
- ❌ "接收方保证完全符合所有适用法律且承担一切后果"

## 五、常见误区

### 4.1 十大起草误区

| 序号 | 误区 | 说明 |
|------|------|------|
| 1 | 误把独立处理者关系写成委托处理 | 接收方明明有自身业务目的，却仍写成"仅按指示处理" |
| 2 | 角色条款与责任条款矛盾 | 前面承认双方独立处理，后面却把所有前端义务都压给接收方 |
| 3 | 只写原则，不写责任主体 | 仅写"双方应遵守适用法律"，没有说明谁负责什么 |
| 4 | 接收方用途边界过宽 | 允许"改进产品、商业分析、研究开发"等笼统用途 |
| 5 | 第三方转传条款过硬或过松 | 要么完全无例外，要么几乎不限 |
| 6 | 跨境条款堆规定，不落责任 | 只列概念，不明确前端义务和后端协助 |
| 7 | 删除条款机械照搬processor DPA | 忽略接收方独立合规和争议留档需求 |
| 8 | 数据主体请求协作缺失 | 实践中会导致互相推诿 |
| 9 | 责任条款不符合商业现实 | 无限责任、全部损失、绝对承诺，谈判阻力极大 |
| 10 | 没有为紧急情形保留例外 | 救援、反欺诈、监管要求、法院调查等 |

---

### 4.2 不宜默认使用的表述

| 不宜默认使用的表述 | 问题 | 更平衡的表达 |
|------------------|------|-------------|
| "接收方仅按提供方指示处理数据" | 若场景本质为独立处理者，造成角色错误 | "接收方在约定目的和必要范围内处理" |
| "接收方承诺其所在国家或地区的数据保护水平不低于中国法律规定" | 过硬且难以验证 | "接收方应采取与处理风险相适应的安全措施" |
| "接收方赔偿提供方全部损失" | 责任范围失衡 | "直接实际损失及合理维权费用" |
| "任何第三方披露均绝对禁止" | 未保留必要例外 | "法律要求或紧急情形除外" |
| "在任何情况下立即删除全部数据及备份" | 技术和法律上未必可行 | "在可行范围内删除或隔离" |
| "接收方应采取行业最高标准安全措施" | "最高标准"难以界定和证明 | "与处理风险相适应的技术和组织措施" |

## 六、起草风格选择

| 风格 | 适用场景 | 特点 |
|------|---------|------|
| **平衡版** | 双方均有一定议价能力，目标是合规稳妥且可签 | 角色准确、责任对等、条款完整，既限制接收方越权使用，也保留必要例外和合理责任边界 |
| **强保护版** | 数据敏感度高、提供方处于优势、项目监管风险较高 | 更强调用途限制、第三方转传控制、更具体的通知义务和更严格的责任条款，但仍避免不可执行的绝对表述 |
| **成交优先版** | 大型机构、境外合作方、行业惯例较强、时间紧或议价空间有限 | 保留关键条款，但在审计权、责任上限、通知时限和删除要求等方面更克制、更接近市场可接受版本 |

**选择建议**：默认采用平衡版，根据用户明确要求调整

## 七、判断规则速查卡

```
【核心判断规则】

若接收方并非仅按提供方指示处理个人信息，
而是为其自身独立业务目的、法定义务或合规需求处理数据，
→ 优先考虑采用数据对外提供协议或独立处理者之间的数据共享结构，
  而非委托处理型 DPA。

【起草要点】

重点围绕以下条款展开：
✓ 角色界定
✓ 数据范围
✓ 目的限制
✓ 前端合规义务
✓ 接收方使用边界
✓ 第三方转传
✓ 跨境安排
✓ 安全保障
✓ 数据主体请求协作
✓ 事件响应
✓ 删除留存
✓ 责任分配

【禁止事项】

✗ 不得同时使用"独立处理者"与"仅按指示处理"等相互冲突的表述
✗ 不得简单照搬 processor DPA 条款
```
