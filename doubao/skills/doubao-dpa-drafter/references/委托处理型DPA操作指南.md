## 一、概念与判断

### 1.1 什么是委托处理型DPA

**核心特征**：
- 委托方**决定处理目的和主要方式**
- 受托方**仅按委托方指示处理**个人信息
- 受托方**无独立处理目的**，不为自身商业目的使用数据

**典型委托处理场景**：

| 场景类型 | 具体示例 |
|---------|---------|
| 云服务 | 云托管、数据存储、文件存储 |
| SaaS服务 | 客户管理系统、CRM、ERP |
| 外包服务 | 客服外包、薪酬外包、IT运维 |
| 数据处理 | 数据标注、合规筛查、邮件发送服务 |
| 技术支持 | 技术支持、报销/差旅管理 |

**起草逻辑主线**：
```
1. 明确双方角色
2. 限制受托方只能按指示处理
3. 补足保密、安全、分包、协助、删除返还、审计、事件通知、跨境支持、责任分配等条款
```

**常见错误**：
| 错误类型 | 说明 |
|---------|------|
| 角色错配 | 把所有数据合作都写成委托处理 |
| 目的扩大 | 允许受托方为自身产品改进或商业分析自由使用数据 |
| 分包失控 | 未限制分包商 |
| 收口缺失 | 未约定删除返还 |
| 义务模糊 | 仅写"双方遵守适用法律"而没有分配具体义务 |
| 条款矛盾 | 同时出现"仅按指示处理"和"可自行决定处理目的" |

---

### 1.2 如何判断场景类型

**判断核心**：谁决定处理目的和核心方式

| 场景类型 | 判断标准 | 典型特征 |
|---------|---------|---------|
| **委托处理** | 接收方仅按委托方指示处理，无独立目的 | 仅为履行主服务合同、不能扩大处理目的、需服从委托方指示、服务终止后删除/返还 |
| **独立处理者** | 接收方为自身独立商业目的处理数据 | 用于核保/理赔/风控/营销/算法训练、自行决定保留期限/再利用/共享 |
| **共同处理** | 双方共同决定处理目的和关键方式 | 联合运营、联合营销、共同平台服务、共同画像 |

**支持"委托处理"判断的迹象**：
```
✓ 服务商处理数据仅为履行主服务合同
✓ 服务商不能自行扩大处理目的
✓ 服务商不能擅自决定保留期限、再利用用途和对外共享
✓ 服务商需服从客户的书面或系统化处理指示
✓ 服务终止后需删除或返还数据
✓ 服务商协助客户履行数据主体请求、审计、合规检查等义务
```

**削弱"委托处理"判断的迹象**：
```
❌ 服务商可为自身产品优化自由使用客户数据
❌ 服务商可自行决定二次利用、聚合分析或商业开发
❌ 服务商可将数据共享给关联方或第三方作自身用途
❌ 服务商作为受法律监管主体，为自身法定义务独立决定处理
❌ 服务商在合同中保留过宽的"运营、改进、研究、分析"用途
```

**判断不足时的补充问题**：
```
1. 接收方是否仅按指示处理？
2. 接收方是否有自身独立用途？
3. 是否涉及再共享？
4. 是否允许匿名化/聚合后使用？
5. 服务终止后如何处理数据？
6. 是否存在跨境？
```

---

### 1.3 起草前必问问题

**必问清单**（按优先级排序）：

| 序号 | 问题 | 目的 |
|------|------|------|
| 1 | 委托方和受托方分别是谁，双方所在地 | 确定主体和跨境事实 |
| 2 | 主服务关系是什么，DPA是主合同附件还是独立协议 | 确定协议定位 |
| 3 | 受托方是否仅按委托方指示处理个人信息 | 确认委托处理性质 |
| 4 | 受托方是否存在任何自身独立处理目的 | 排除独立处理者关系 |
| 5 | 涉及哪些类别的个人信息（是否含敏感/儿童/员工/财务/定位/医疗等） | 确定风险等级 |
| 6 | 处理目的是什么，处理活动有哪些 | 界定处理范围 |
| 7 | 受托方是否需要调用分包商或子处理者 | 确定分包条款需求 |
| 8 | 数据是否跨境，跨境到何处，由谁负责前置合规安排 | 确定跨境条款 |
| 9 | 是否需要保留审计权，审计强度和方式如何设计 | 确定审计条款 |
| 10 | 安全事件通知时限要求是什么 | 确定事件响应条款 |
| 11 | 服务终止时数据返还、删除还是继续保留 | 确定删除返还条款 |
| 12 | 是否允许去标识化、匿名化或聚合使用，边界是什么 | 确定使用限制 |
| 13 | 数据主体请求由谁主导响应，受托方如何协助 | 确定协助条款 |
| 14 | 责任结构是无限责任、分类责任还是capped liability | 确定责任条款 |
| 15 | 适用法和争议解决方式是什么 | 完善基础条款 |

## 二、核心条款设计

### 2.1 条款清单总览

**必须覆盖的核心条款**：

| 序号 | 条款 | 核心内容 |
|------|------|---------|
| 1 | 角色界定 | 委托方决定处理目的，受托方仅按指示处理 |
| 2 | 处理说明 | 处理目的、活动、数据类别、数据主体、持续期间、处理边界 |
| 3 | 指示限制 | 仅根据委托方合法指示处理，不得擅自扩大目的 |
| 4 | 保密条款 | 接触人员承担保密义务并接受培训 |
| 5 | 安全措施 | 与处理风险相适应的技术和组织措施 |
| 6 | 分包/子处理者 | 未经授权不得聘用，获准后仍需负责 |
| 7 | 协助条款 | 协助处理数据主体请求、合规评估、监管问询 |
| 8 | 安全事件通知 | 约定时限内通知委托方并配合处置 |
| 9 | 删除与返还 | 服务终止后删除或返还，法律另有要求的除外 |
| 10 | 审计与证明 | 问卷、报告、认证、现场审计等方式核查 |
| 11 | 跨境支持 | 前端合规安排责任，受托方协助义务 |
| 12 | 责任与赔偿 | 与角色匹配的责任分配 |
| 13 | 期限与终止 | DPA与主合同关系、终止触发条件和终止后安排 |
| 14 | 优先适用 | 数据处理相关事项以DPA为准 |

---

### 2.2 角色界定条款

**目标**：明确委托方决定处理目的，受托方不取得独立处理地位

**推荐写法要素**：
```
1. 委托方为处理目的决定者
2. 受托方不取得对数据的独立处理地位
3. 受托方不得为自身目的使用数据
4. 受托方仅在履行服务所必需范围内处理数据
```

**不推荐写法**：
| 问题写法 | 问题说明 |
|---------|---------|
| "受托方可为改进服务、研究分析、商业优化等广泛自身目的使用数据" | 前后矛盾，削弱委托处理定性 |
| "双方均有权根据业务需要处理数据" | 模糊表述，削弱委托处理定性 |
| 未明确主服务关系 | 导致DPA成为抽象文件 |

**平衡版设计**：
```
允许受托方在严格边界内为安全维护、故障排查、法律合规等必要目的处理数据
但应明确：
✓ 不得超出提供服务所合理必需的范围
✓ 不得演变为自身商业利用
```

---

### 2.3 处理指示条款

**核心原则**：受托方应仅根据委托方的书面、电子或其他可证明方式发出的合法指示处理个人信息

**条款应回答的问题**：
| 问题 | 建议设计 |
|------|---------|
| 指示以什么形式发出？ | 书面、电子或其他可证明方式 |
| 受托方可否拒绝明显违法的指示？ | 应通知委托方，合理设置法律判断和业务决定机制 |
| 受托方在法律强制要求处理时如何处理？ | 可在法律允许范围内告知委托方 |
| 指示变更时的流程如何？ | 应与主服务内容、附件、工单、系统配置等文件衔接 |

**建议加入的逻辑**：
```
1. 受托方应及时通知委托方其认为某项指示可能违反适用数据保护法律
2. 若适用法律要求受托方处理相关数据，受托方可在法律允许范围内告知委托方
3. 指示应尽可能与主服务内容、附件、工单、系统配置等文件衔接
```

**常见误区**：
| 误区 | 说明 |
|------|------|
| 没有规定指示形式 | 导致争议时难以证明 |
| 把所有法律责任都推给委托方 | 忽视受托方对明显违法指示的基本警觉义务 |
| 忽略适用法律强制要求这一必要例外 | 导致条款不可执行 |

---

### 2.4 分包/子处理者条款

**核心原则**：未经委托方授权，受托方不得自行引入子处理者；如获授权，受托方应确保子处理者承担不低于DPA的保护义务，并对其履约行为继续负责

**条款应明确**：
| 要点 | 内容 |
|------|------|
| 授权方式 | 采用逐一授权还是一般授权 |
| 名单披露 | 子处理者名单是否应提前披露 |
| 新增流程 | 新增子处理者时是否需提前通知及给予异议期 |
| 跨境披露 | 跨境子处理者是否需特别披露 |
| 协议要求 | 受托方是否需与子处理者签署书面协议 |
| 责任回传 | 子处理者违约后责任如何回传至受托方 |

**常见误区**：
```
❌ 完全不写子处理者条款
❌ 允许受托方自由使用"关联方/合作伙伴"而无边界
❌ 仅要求"确保第三方遵守法律"，但未建立合同传导机制
❌ 忽略云基础设施、多租户服务、工单系统、客服外包等实际存在的分包链条
```

---

### 2.5 安全措施条款

**核心原则**：结合处理风险和服务场景，要求受托方采取与处理活动性质、数据敏感程度、处理规模和潜在影响相适应的技术和组织措施

**可考虑的维度**：
| 维度 | 内容 |
|------|------|
| 访问控制 | 访问控制与最小权限 |
| 身份认证 | 身份认证机制 |
| 数据保护 | 加密或传输保护 |
| 日志记录 | 日志记录与留存 |
| 漏洞管理 | 漏洞修复与补丁管理 |
| 备份恢复 | 备份与恢复机制 |
| 人员管理 | 人员管理与培训 |
| 供应链安全 | 供应链安全控制 |
| 环境隔离 | 环境隔离措施 |
| 测试审查 | 测试与审查机制 |

**不同风格的写法**：
| 风格 | 写法特点 |
|------|---------|
| 强保护版 | 附安全措施附件，要求提供认证、审计报告、渗透测试摘要 |
| 平衡版 | 保留原则性表述，结合行业认证、SOC报告、ISO体系等证明材料 |
| 成交优先版 | 不宜要求过强现场审计或绝对安全标准 |

**常见误区**：
| 误区 | 说明 |
|------|------|
| 使用"最高标准""绝对安全"等无法验证的表述 | 难以证明和执行 |
| 没有区分敏感个人信息和普通数据 | 风险等级不匹配 |
| 只写技术措施，不写人员和组织措施 | 保护措施不完整 |
| 安全条款与安全事件条款脱节 | 缺乏联动机制 |

---

### 2.6 数据主体请求协助条款

**责任分配**：面对数据主体请求的主要责任通常在委托方（决定处理目的并与数据主体建立直接关系）

**条款应写清**：
| 要点 | 内容 |
|------|------|
| 转交机制 | 数据主体直接联系受托方时，受托方是否应转交委托方 |
| 直接答复 | 受托方是否可以直接答复 |
| 协助范围 | 是否限于技术和组织上合理可行的程度 |
| 费用分担 | 是否涉及费用分担 |
| 响应时限 | 如何与主法规时限衔接 |

**常见误区**：
```
❌ 完全把响应义务扔给受托方
❌ 完全不写协助义务
❌ 没有规定数据主体直接联系受托方时的处理路径
```

---

### 2.7 删除与返还条款

**基础逻辑**：受托方不应无限期持有委托方的数据；服务终止后，应按照委托方指示删除或返还个人信息

**条款设计应考虑**：
| 要点 | 内容 |
|------|------|
| 处理方式 | 删除、返还还是二选一 |
| 备份范围 | 删除是否包括备份副本 |
| 留存例外 | 是否限于法律强制要求、争议留档和安全审计 |
| 留存义务 | 留存期间是否继续适用保密和安全义务 |
| 确认机制 | 是否需要提供删除完成的书面确认 |

**常见误区**：
| 误区 | 说明 |
|------|------|
| 写成绝对删除，不保留任何法律例外 | 忽略法定留存和争议留档需求 |
| 只写"删除"，不考虑系统备份和日志现实 | 技术上不可执行 |
| 允许长期留存但不设边界 | 数据收口失效 |
| 不要求返还或删除证明 | 无法验证执行情况 |

---

### 2.8 安全事件通知条款

**核心要求**：受托方在知悉发生或合理怀疑发生个人信息安全事件后，在约定时限内通知委托方，并配合调查、缓释和后续响应

**条款应明确**：
| 要点 | 内容 |
|------|------|
| 触发点 | "实际知悉"还是"知悉或合理怀疑" |
| 通知时限 | 固定小时数还是"不无故迟延" |
| 首次通知内容 | 已知事实、影响范围等 |
| 后续更新 | 根因分析如何配合 |
| 对外通知 | 由谁主导通知监管和数据主体 |
| 直接披露权 | 受托方是否有权未经委托方同意直接对外披露 |

**不同风格的写法**：
| 风格 | 写法特点 |
|------|---------|
| 平衡版 | "无不合理迟延，且在可行范围内尽快通知" |
| 强保护版 | 写具体小时数（如24小时、48小时） |
| 成交优先版 | 避免过短硬时限 |

**常见误区**：
```
❌ 只写发生事件时"及时通知"，无任何标准
❌ 要求受托方承担对外监管报送主导责任，忽视角色分工
❌ 未要求后续更新和协作
```

---

### 2.9 审计权条款

**核心原则**：兼顾监督需求、商业秘密保护和服务商的运营承受能力

**常见可接受结构**：
| 层级 | 内容 |
|------|------|
| 优先路径 | 提供认证、审计报告、问卷和合规证明 |
| 触发条件 | 仅在存在重大事件、合理怀疑重大违规或法律要求时触发现场审计 |
| 审计程序 | 提前合理通知，遵守保密和最小影响原则 |
| 实施方式 | 可由独立第三方实施 |
| 配套机制 | 审计频次、范围、费用和整改机制应明确 |

**常见误区**：
| 误区 | 说明 |
|------|------|
| 给予委托方无限制、随时、无理由现场审计权 | 商业上难以接受 |
| 不考虑多租户环境和其他客户保密义务 | 实际执行困难 |
| 未规定由谁承担费用 | 引发争议 |
| 没有替代性合规证明路径 | 审计权过于刚性 |

---

### 2.10 跨境处理条款

**核心原则**：根据跨境安排的发起方区分责任，不简单把所有出境合规责任都写给一方

**责任分配（按发起方区分）**：

**场景A：甲方（委托方）主动选择境外受托方/存储**
| 责任方 | 义务内容 |
|--------|---------|
| **委托方（前端义务）** | 确定合法性基础、完成必要的告知和同意、选择出境合规路径、开展PIA、向数据主体提供必要信息 |
| **受托方（后端义务）** | 提供接收方信息、处理说明、安全措施说明、子处理者信息、配合签署相关附属安排 |

**场景B：乙方（受托方）为使用自身关联方/子处理者而发起跨境**
| 责任方 | 义务内容 |
|--------|---------|
| **委托方** | 审查受托方跨境方案的合理性、配合提供PIA所需的甲方侧信息（如数据规模、数据主体范围等） |
| **受托方（主要责任方）** | 提供境外接收方详细信息（名称、地址、联系方式、处理能力）、完成境外接收方尽调、落实访问控制措施、签署并履行跨境文件（如标准合同附件）、将DPA义务传导至境外关联方/子处理者、对关联方/子处理者行为承担责任 |

**关键规则**：
- 谁发起跨境安排，谁承担主动义务（尽调、方案设计、接收方管理、义务传导）
- 甲方的法定义务（告知、PIA）不因乙方主动出境而消失，但乙方应提供PIA所需全部资料
- 乙方使用自身关联方进行跨境时，乙方对其关联方行为向甲方承担责任

**条款应说明**：
```
✓ 跨境事实及发起方
✓ 接收地点及接收方信息
✓ 必要的分包情况
✓ 合规支持安排及责任分工
✓ 乙方对境外接收方的责任承担
```

**不宜要求**：
```
❌ 要求受托方承诺其所在法域整体保护水平
❌ 简单复制适用于独立处理者的数据共享条款
❌ 将全部跨境合规责任不加区分地集中分配给任一方
```

## 三、常见误区

### 3.1 十大起草误区

| 序号 | 误区 | 说明 |
|------|------|------|
| 1 | 误把独立处理者关系写成委托处理 | 服务商为自身业务目的处理数据，强行写成processor DPA导致角色错位 |
| 2 | 角色条款和用途条款互相打架 | 前面说仅按指示处理，后面又允许服务商自由改进产品、研究分析或商业复用数据 |
| 3 | 没有处理说明附件 | 未写明数据类别、数据主体、目的和期限，导致DPA过于抽象 |
| 4 | 对子处理者控制不足 | 完全不限制分包，或用"关联方/合作伙伴"一笔带过 |
| 5 | 安全条款空泛 | 堆"最高标准""所有适用措施"等口号，却没有任何执行逻辑 |
| 6 | 不写数据主体请求协助 | 忽略受托方在系统控制、数据检索和技术支援上的作用 |
| 7 | 安全事件条款过虚或过硬 | 要么只写"及时通知"，要么规定不现实的极短时限且无例外 |
| 8 | 删除返还条款不考虑技术现实 | 忽略备份、日志、争议留档和法定保存要求 |
| 9 | 审计权过于理想化 | 赋予无限制现场审计权，导致难以签署 |
| 10 | 责任条款不匹配角色 | 对受托方设置绝对无限责任，或反过来把受托方责任写得过轻 |

---

### 3.2 不宜默认使用的表述

| 不宜默认使用的表述 | 问题 | 更平衡的表达 |
|------------------|------|-------------|
| "受托方应采用行业最高标准" | 难以证明"最高标准"的具体含义 | "与处理风险相适应的技术和组织措施" |
| "受托方应赔偿全部损失" | 责任范围可能失衡，且与主合同责任限制冲突 | "直接实际损失及合理维权费用" |
| "受托方保证完全符合所有适用法律" | 表述过度绝对，范围难控 | "在法律允许范围内""在技术上可行范围内" |
| "受托方不得以任何形式使用数据" | 未保留必要的安全维护、法定留存、故障排查等合理例外 | "除提供服务所必需或法律另有要求外" |
| "委托方可随时进入受托方场所审计" | 商业上阻力很大，尤其对大型云服务商 | "经合理提前通知""在合理范围内" |
| "服务终止后立即彻底删除所有数据和备份" | 技术上未必可即时实现，且应保留法定留存例外 | "在可行范围内删除""法律另有要求的除外" |

## 四、起草风格选择

| 风格 | 适用场景 | 特点 |
|------|---------|------|
| **平衡版** | 长期合作、双方均有一定议价能力、以可签署性和实务执行为目标 | 角色清晰、责任明确、条款完整，不过度使用绝对措辞；审计、责任、安全事件通知等条款采用合理标准和例外 |
| **强保护版** | 委托方数据敏感度极高、受托方议价能力较弱、项目涉及高监管风险 | 对受托方设置更强的审计、分包限制、通知时限和赔偿责任，但仍避免明显不可签或不可执行的表达 |
| **成交优先版** | 标准化供应商、云服务、大型SaaS服务商等场景 | 保留关键角色界定、使用限制、安全与事件响应等核心条款，但在审计、责任、通知时限、分包控制等问题上更重视行业惯例和落地性 |

**选择建议**：默认采用平衡版，根据用户明确要求调整

## 五、判断规则速查卡

```
【核心判断规则】

若接收方仅为向委托方提供约定服务而处理个人信息，
并且原则上仅按委托方指示处理数据，
不为自身独立商业目的使用该等数据，
→ 优先采用委托处理型 DPA。

若接收方为自身独立业务目的处理数据，
或自行决定处理目的的重要内容，
→ 不应默认使用委托处理型 DPA。

【起草要点】

围绕以下条款搭建：
✓ 角色界定
✓ 处理说明
✓ 指示限制
✓ 保密
✓ 安全
✓ 子处理者
✓ 协助义务
✓ 事件通知
✓ 删除返还
✓ 审计
✓ 跨境支持
✓ 责任分配

【禁止事项】

✗ 不得同时写出"仅按指示处理"和"可自由用于产品优化/商业分析/研究开发"等相互矛盾的表述
✗ 不得把独立处理者关系强行写成委托处理
✗ 不得使用"最高标准""绝对安全"等无法验证的表述
```

## 附录：三种场景对比速查

| 对比维度 | 委托处理 | 对外提供 | 共同处理 |
|---------|---------|---------|---------|
| **处理目的决定权** | 委托方单独决定 | 各自独立决定 | 双方共同决定 |
| **受托方/接收方角色** | 仅按指示处理 | 为自身独立目的处理 | 共同处理者 |
| **数据使用边界** | 不得为自身目的使用 | 可在约定范围内独立使用 | 按约定共同使用 |
| **核心条款重点** | 指示限制、删除返还 | 使用边界、第三方转传 | 分工明确、责任分配 |
| **典型场景** | 云服务、外包、SaaS | 再保险、集团共享、风控合作 | 联合营销、共同运营平台 |
