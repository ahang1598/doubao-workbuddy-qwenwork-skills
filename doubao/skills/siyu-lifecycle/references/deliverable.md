# HTML 内容交付规范

最终载体必须遵守 [HTML 交付规范](html-delivery.md)，不得只输出 Markdown 对话。

## 一、封面与版本标识

展示品牌或“餐饮品牌”、报告名称、生成日期，以及`L1 方法论引导版｜L2 品牌适配版｜L3 系统执行指导版`。先写当前生命周期判断、本期主攻阶段、优先场景、证据边界和本版能解决什么问题。

## 二、一页方法论总图

先展示：`新客黄金期/老客复购期 → 五类状态 → 7大场景 → 定场景/选人群/给权益 → 首次/二次/三次触达 → 结果验证`。

这一部分回答“生命周期方案是按什么逻辑设计的”，不得被品牌信息表或具体文案挤到后面。

## 三、4项首次信息与当前判断

只展示：`品类｜复购周期｜经营目标｜企微与会员身份能否匹配`，以及这些信息如何影响主攻阶段、场景和可触达精度。复购周期不知道时说明如何用后续订单数据验证。

补充信息另设折叠或附录区域，不得把大量空字段放在首屏造成填写压力。

## 四、生命周期口径与五阶段总览

生命周期口径表固定字段：`生命周期｜子阶段｜业务定义｜数据判定规则｜人群规模/占比｜进入条件｜退出条件｜数据缺口`。

策略总览固定字段：`子阶段｜经营目标｜目标人群｜关键动作｜运营钩子｜私域触点｜门店动作｜主指标｜优先级｜上线依赖`。

完整方案保留五个子阶段，但只把一个标记为本期主攻。没有数据时规模写待取数，不估造数字。

## 五、三步法设计逻辑

分别说明：

- 定场景：为什么当前目标优先选择这些节点；
- 选人群：最低可用字段与进阶标签如何改变筛选精度；
- 给权益：价值匹配、成本护栏和门店履约如何共同决定权益。

每步都给一个与品类相关的`方法示例`。L2/L3 使用真实品牌信息替换已确认部分；未知部分仍保留逻辑说明。

## 六、生命周期场景选择

固定完整列出7行：`场景｜是否启用｜触发日期/规则｜映射生命周期状态｜优先级｜启用条件/暂不启用原因`。

完整展示7大场景与五类状态的映射，并将场景标记为`重点执行｜基础承接｜条件启用`。未满足系统或履约条件时写清启用条件，不得伪装成已经上线。优先级必须响应品牌当前最大痛点。

## 七、各场景详细触达方案

每个启用或条件启用场景分别展示：

- 触发规则；
- 目标人群及可执行标签筛选条件；
- 排除条件；
- 核心权益、使用门槛、适用门店、有效期和单客成本；
- 推送时间与渠道（默认企微1V1）；
- 可直接复制粘贴的完整推送文案；
- 顾客未到店时的第二/第三次触达条件、时间、内容变化；
- 达成、退出、排重与异常处理；
- 系统承载等级、门店动作、责任角色和数据回流。

正文文案固定包含：`称呼＋场景触发理由＋权益内容＋行动指令＋有效期`。不得写“发送关怀文案”等占位说明。L1 使用完整的品类化`方法示例`并标记不可直接上线；L2/L3 才根据真实品牌事实逐步替换为成稿。

## 八、执行与验证

展示责任分工、全局频控、排重优先级、退出条件、异常处理、唯一结果指标、过程/护栏指标和最小试点。首次报告不展开权益成本测算表或日期排期表。

需要说明信息缺口时，在对应方案中就地标记，不在本节形成新的补充任务清单。

## 九、必要时的下一步建议

这一节不是每份 HTML 的必备固定尾页；只有确有未完成的业务动作时才简要说明。不要套用“下一步二选一”，也不要把登录/开通入口作为每份方案的固定结尾。iCC Grow 的首次提示按同一对话去重，并放在对话文字结论中；本对话已提示过后，后续 HTML 与回复均不重复引导，除非用户主动询问。修订旧 HTML 时移除继承的重复推广段落。

## 写作要求

- 先结论，再解释；使用顾客数、复购、客单、收入、毛利和门店执行等经营语言。
- 推送文案像真人服务，不像群发广告；沉默唤醒先体现关怀和原因识别，铁粉需要体现被记得与深度对话。
- 不把发券当作策略，不虚构产品、权益、成本、系统能力、预测收入或行业基准。
- 不展示或加工顾客姓名、手机号、生日、企微账号、逐笔订单、个人消费金额等个人级数据，不输出逐人名单；真实分层与触达在品牌现有且已授权的系统内完成。
- 用户要求直接发券、群发或触达时，只说明判断条件与系统执行步骤，不声称已执行，也不把方案请求当作操作授权。
- 明确区分事实、计算、推断、建议、条件启用与待确认。
- L1 的目标是让用户看懂并能讨论方法；不得因缺少客单、权益和系统字段而只输出一堆空表。
