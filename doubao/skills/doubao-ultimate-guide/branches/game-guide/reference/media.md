# 游戏攻略视觉素材规则
本文件负责所有游戏攻略请求中的视觉素材检索、真实性验证、版本与场景核对、用途判断和最终插入要求。目标不是“给攻略配图”，而是使用经过验证的真实游戏画面帮助用户完成具体步骤。

所有进入本 Skill 的正式游戏攻略都必须读取本文件并执行视觉素材检索。最终攻略中的游戏画面类图片必须来自真实游戏实机画面。无法找到可靠素材时，宁可减少图片，也禁止使用生成图或无法验证来源的图片冒充攻略图。
## 一、核心硬规则
最终攻略中允许使用的游戏画面类图片仅包括：
- 真实游戏实机截图；
- 真实游戏内地图截图；
- 真实游戏UI截图；
- 真实玩家实机视频帧；
- 官方发布但明确属于真实游戏实机画面的截图。

禁止使用以下内容作为攻略实机图：
- AI生成游戏截图；
- AI模拟地图；
- 宣传CG；
- 概念设计图；
- 角色立绘；
- 同人图；
- 手绘伪地图；
- 非实机渲染图；
- 未经验证的二次创作图；
- MOD画面冒充原版；
- 私服画面冒充正式服；
- 不同版本、平台、地图状态或任务阶段的错误截图。

允许在真实游戏截图基础上增加：
- 箭头；
- 路线；
- 框选；
- 编号；
- 简短文字标注；
- 起点/终点标记。

任何标注都不能改变底图的真实游戏事实。

## 一点五、真实游戏图片检索工具优先规则
当任务需要游戏截图、游戏内地图、UI、角色/怪物/宠物/道具识别图、Boss关键帧、机制站位图或入口现场图时，若当前环境提供文搜图、图片搜索、视频搜索或专用搜图工具，应优先调用这些工具检索真实游戏画面。不要只凭模型记忆描述图片，也不要使用 AI 生成图模拟实机画面。

检索关键词必须同时包含：
- 游戏完整名或已验证别名；
- 目标对象、任务名、地点、Boss、道具、装备、机关或 UI 名称；
- 图片用途关键词，例如 实机截图、地图、位置、入口、UI、图鉴、打法、关键帧、当前版本；
- 必要时补充版本、赛季、平台、服务器、DLC、难度、英文名或社区常用名。

示例：

```text
{游戏名} {目标地点/道具/NPC} 位置 实机截图
{游戏名} {任务名} 入口 地图 当前版本
{游戏名} {Boss名} 二阶段 关键帧 打法
{英文游戏名} {target} location map screenshot
```

选图时按匹配度排序：
1. 目标游戏、目标对象和任务场景完全一致；
2. 来源可追溯，优先官方实机图、高质量 Wiki/数据库、公开攻略页、玩家实机视频帧和大型社区帖子；
3. 确认是真实游戏画面，不是 CG、立绘、同人、AI 图、MOD 或私服；
4. 当前版本、平台、地图状态、任务阶段和正文条件兼容；
5. 主体清晰，关键地标、UI、对象、站位或入口可见；
6. 图片能直接帮助当前步骤，而不是只做装饰。

如果官方或权威图片不够用，可使用公开攻略、社区帖子、实机视频截图中的真实游戏画面；必须重新组织正文和图注，不照搬原文长段落或完整排版。图片本身仍要按本文件逐张验真。

失败与降级：
- 先扩展关键词，补充英文名、别名、版本、平台、任务名、地区服、旧称或社区常用词；
- 再扩大到 B站、抖音、小红书、YouTube、贴吧、NGA、小黑盒、Steam 社区、Reddit、官方论坛、Wiki、攻略站和玩家实机视频；
- 可截取真实玩家视频中的清晰关键帧，但必须核对游戏、版本、场景、对象和 UI；
- 仍无可靠图片时记录 `visual_gap`，不得用 AI 图、宣传图、封面、立绘或无法追溯截图替代。
## 二、视觉素材的目标
每张图片都必须帮助用户完成一个具体攻略动作或判断。

优先回答：
- 这是什么地方？
- 从哪里进去？
- 从哪个方向走？
- 目标物品长什么样？
- NPC站在哪里？
- 机关应该看哪里？
- Boss出现什么动作时需要反应？
- 应该站在哪个位置？
- 菜单或UI里应该点哪里？
- Build中的关键装备或技能是什么？

只有“画面真实”但无法帮助当前步骤的图片，不应进入最终攻略。
## 三、内部视觉记录
建议维护：

```text
visual_assets:
  - atomic_need:
    visual_need:
    asset_type:
    source_type:
    source_url_or_reference:
    game_verified:
    gameplay_verified:
    version_scope:
    platform_scope:
    scene_verified:
    object_verified:
    mod_or_private_server_check:
    spoiler_risk:
    purpose:
    source_status:

visual_gaps:
rejected_visuals:
theme_color_basis:
  source_image_or_ui:
  target_or_scene_relation:
  extracted_palette:
  chosen_primary:
  chosen_accent:
  light_theme_ok:
```
其中：
- `game_verified`：确认是目标游戏；
- `gameplay_verified`：确认是真实游戏画面；
- `version_scope`：版本、赛季、资料片或地图版本；
- `scene_verified`：与当前任务阶段和场景一致；
- `object_verified`：目标NPC、Boss、物品、入口或UI识别正确；
- `mod_or_private_server_check`：确认不是MOD或私服画面冒充原版；
- `source_status`：`accepted` / `conditional` / `rejected`。
- `theme_color_basis`：用于HTML和飞书视觉主题，不是攻略事实证据；必须来自真实游戏截图、官方实机图、目标对象实机/UI图或当前版本游戏UI。
## 四、视觉需求等级
对每个 `atomic_need` 判断：
### `required`
没有视觉素材会明显降低可执行性或容易导致用户找错。

常见情况：
- 隐藏入口；
- 多层地图；
- 地下/地上切换；
- NPC具体位置；
- 隐蔽收集品；
- 复杂机关；
- Boss关键前摇；
- FPS/TPS投掷物点位；
- MMO团本复杂站位；
- 沙盒建造关键连接。
### `recommended`
文字可以说明，但真实截图能显著降低理解成本。
### `optional`
图片主要用于辅助识别，不影响执行。
### `none`
图片几乎不增加价值，例如简单资源优先级或纯数值决策。

所有请求仍需执行视觉素材检索，但最终只展示真正有帮助的素材。

正式飞书文档的视觉素材要求更高：必须至少插入 1 张经过验证且对执行有帮助的真实游戏图。图片不能作为装饰，必须绑定一个 `atomic_need`，并放在该关键信息或步骤旁边。除非用户明确要求纯文字，或请求被判定为 `visual_need=none` 且 `quality-check.md` 放行，否则不得交付无图飞书文档。

按问题类型确定最低配图：
- 地图、路线、去哪找、入口、NPC、隐藏点、收集品：至少 1 张地图定位图或入口/地标实机图；复杂路线应包含“地图定位 + 现场入口/地标”两类图，通常 2 张最有效。
- 精灵、怪物、宠物、道具、装备、技能：至少 1 张目标识别图或真实游戏 UI 图，帮助用户确认对象外观、图标、详情页或出现状态。
- Boss、机制、解谜、站位：至少 1 张关键帧、场地图、机关图、站位图或 UI 图，帮助判断动作时机或交互点；动态机制可使用 2-3 张阶段图，但不要为普通攻击逐个配图。
- Build、配队、资源规划：优先使用真实装备/技能/面板/UI 图；若图片不如表格清楚，可降级为表格，但必须记录为何不插图。

如果最低配图找不到可靠素材：
- 必须继续扩大视觉检索来源，而不是立即放弃；
- 优先补搜小红书、抖音、B站、YouTube、贴吧、NGA、官方论坛、Wiki、攻略站和玩家实机视频；
- 可从真实玩家视频中截取清晰关键帧，但必须核对游戏、版本、场景、对象和UI；
- 在 `visual_gaps` 记录缺口、搜索范围和无法采用的原因；
- 若该图对执行是 `required` 或 `recommended`，正式飞书文档不得放行无图交付；
- 不得用角色立绘、宣传图、封面图、AI图或无来源截图顶替。
## 五、图片候选验真流程
每张候选图片必须依次检查：

```text
确认目标游戏
→ 确认是真实游戏画面
→ 确认不是CG/立绘/概念图/生成图
→ 确认版本或地图状态
→ 确认平台/服务器差异
→ 确认任务阶段和场景
→ 确认目标对象
→ 检查MOD/私服风险
→ 与正文事实交叉验证
→ 判断是否真正帮助当前步骤
→ accepted / conditional / rejected
```
未完成以上验证的图片不能进入最终攻略。
## 六、如何判断是否为真实游戏画面
优先使用以下证据：
- 官方实机演示或游戏内截图；
- 连续实机视频中的明确帧；
- 高质量Wiki或攻略页中的游戏内截图；
- 玩家社区上传的明显真实游戏画面；
- 与游戏UI、模型、场景和其他独立实机来源一致的截图。

高风险信号包括：
- 画面过度电影化但无UI且无法对应实机；
- 构图明显是宣传海报；
- 角色姿势和镜头不可能出现在正常游戏内；
- 地图标注与真实地图结构不一致；
- 画面来自MOD、重制材质包或私服；
- 图片来源无法追溯且无其他实机可以印证。

无法确定时标记为 `rejected`，不进入最终攻略。
## 七、版本与场景一致性
图片必须与正文使用的攻略条件一致。

重点核对：
- 当前版本；
- 赛季；
- DLC/资料片；
- 正式服/经典服；
- 平台；
- 地图版本；
- 任务阶段；
- 昼夜/世界状态；
- Boss阶段；
- UI版本。

例如：
- 旧地图入口图不能解释新版本路线；
- 普通难度团本截图不能冒充高难机制图；
- NPC在任务前的位置不能用于任务后的阶段；
- 旧UI不能让用户按不存在的菜单操作。

若图片只在特定条件下适用，必须标记为 `conditional` 并在正文中说明条件。

## 十、地图与路线图片
路线类视觉必须尽量实现：

```text
地图定位
+
真实现场识别
```
推荐组合：
1. 真实游戏内地图：告诉用户目标区域和路线；
2. 真实现场截图：告诉用户入口或地标长什么样；
3. 必要时在真实图上增加箭头、编号或路线。

仅给终点截图通常不够。

若地图来自社区二次标注：
- 底图必须是真实游戏内地图；
- 标记不能改变真实地形；
- 必须核对标记位置；
- 不得使用手绘伪地图冒充官方或游戏内地图。
## 十一、Boss机制图片
Boss图必须用于具体识别：
- 前摇；
- 阶段；
- 地面提示；
- 安全区；
- 场地位置；
- 机制对象。

单纯Boss宣传图、立绘或CG不能作为机制攻略图。

若关键机制是动态过程，优先使用：
- 连续实机视频中的关键帧；
- 多张阶段截图；
- 一张真实截图加明确标注。
## 十二、解谜图片与剧透控制
视觉素材必须遵守 `spoiler_level`。

若用户只要提示：
- 只展示关键观察区域；
- 不直接展示完整答案；
- 不在图上标出全部操作顺序。

若用户明确要完整解法：
- 可以使用真实截图加编号说明。
## 十三、Build与UI图片
Build类图片必须确认：
- 装备名称和图标对应；
- 当前版本UI；
- 属性和技能页真实；
- 不用角色宣传立绘代替配置图；
- 不用旧版本装备图误导当前用户。

当文字或表格更适合说明优先级时，不强行为每件装备配图。
## 十四、图片来源与社区平台
可从不同来源生态发现真实游戏画面，包括：
- 官方；
- Wiki；
- 攻略站；
- B站；
- 抖音；
- 小红书；
- YouTube；
- Reddit；
- 贴吧；
- NGA；
- Steam社区；
- 官方论坛；
- 其他真实玩家社区。

来源热度不影响图片真实性判断。高赞图片也必须经过游戏、版本和场景验证。
## 十五、图片与正文一致性
最终使用前必须检查：
- 图片中的位置与正文位置一致；
- 图片中的NPC、Boss、道具或UI与正文对象一致；
- 图片版本与正文版本一致；
- 图片中的路线与文字路线一致；
- 图片中的编号与正文步骤一致；
- 图片没有展示用户当前阶段尚未出现的错误状态。

若图片与正文冲突，以重新验证事实为优先，不能硬改文字迁就图片。

## 十五点五、视觉主题与取色
最终HTML和飞书文档应使用与游戏主题或目标对象相关的浅色视觉主题，但不能为了好看牺牲事实和可读性。

取色来源优先级：
1. 当前版本真实游戏截图中的目标对象或目标区域；
2. 官方或玩家上传的真实实机/UI截图；
3. 当前攻略使用的地图、入口、Boss场地、精灵详情页或道具UI；
4. 无可靠视觉素材时，使用中性浅色主题。

取色规则：
- 只提取视觉主题，不提取或新增攻略事实；
- 主背景必须保持浅色，不能把目标对象深色直接铺成页面背景；
- 主强调色选择中低饱和版本，确保正文和按钮/标签可读；
- 飞书中将主题色映射为最接近的基础色或浅色 callout，例如绿色目标用 `light-green`，蓝色地图/UI用 `light-blue`，中性目标用 `light-gray`；
- 如果目标对象颜色非常艳、暗或杂，降低饱和度后只用于小面积强调。

必须记录：
```text
theme_color_basis:
  source_image_or_ui: 已验证素材或说明
  target_or_scene_relation: 与游戏/目标对象/场景的关系
  extracted_palette: 主色候选
  chosen_primary: 最终主强调色
  chosen_accent: 可选辅助色
  light_theme_ok: 是否保持浅色和可读
```

禁止：
- 大面积深色背景、黑底、深紫/深蓝渐变；
- 只因“看起来高级”使用与游戏无关的配色；
- 从宣传CG、立绘、同人图或AI图提取主题色；
- 因配色需要编造目标外观、稀有度或阵营信息。
## 十六、最终产物中的图片组织
在飞书文档或HTML中：
- 图片必须放在对应关键信息、步骤、路线节点、机制说明或对象识别说明旁边；
- 不将所有图片集中堆在文末；
- 每张关键图片应有一句简短说明；
- 图片说明只写用户需要关注的内容；
- 多图路线必须与正文步骤或编号一一对应；
- 视觉素材不能代替必要文字步骤。

飞书文档优先使用图文分栏组织关键图片：

```xml
<grid>
  <column width-ratio="0.42">
    <img href="VERIFIED_REAL_GAME_IMAGE_URL" width="360" caption="图：入口或目标对象实机截图" name="guide-image.png"/>
  </column>
  <column width-ratio="0.58">
    <callout emoji="📌" background-color="light-blue" border-color="blue" text-color="blue">
      <h3>看图做这一步</h3>
      <p><b>动作：</b>写清玩家要做什么。</p>
      <p><b>看哪里：</b>写清图中关键地标、UI 或目标对象。</p>
      <p><b>成功标志：</b>写清完成后会发生什么。</p>
    </callout>
  </column>
</grid>
```

组织规则：
- 路线题优先“左地图/入口图，右路线步骤”；必要时下一块再放“左现场地标图，右识别说明”。
- 精灵/道具题优先“左目标实机图或 UI，右外观/图标/出现条件/成功识别”。
- Boss/机制题优先“左关键帧或场地图，右前摇、站位、反应动作和失败排查”。
- 图文分栏内的图片说明不得新增事实；右侧文字必须能脱离图片继续执行。
- 不能只在文末用 `docs +media-insert` 堆图；若工具先把图片插到末尾，必须移动或重新插入到对应步骤附近。
- 路线/入口图片放在路线步骤开头或对应转折点旁；Boss关键帧放在该招式处理旁；道具/宠物/装备/UI识别图放在“确认目标对象”或获取步骤旁；历史资料图片不得混入当前步骤图文卡。

推荐：

```text
步骤3：从桥下入口进入
[真实游戏入口截图]
图：入口位于石桥正下方，右侧可看到两支火把。
```
禁止：

```text
正文10个步骤
→ 文末一次性堆20张无编号截图
```
## 十七、无法找到可靠视觉素材时
如果搜索不到可靠真实游戏画面：
- 不得调用图片生成工具模拟真实截图；
- 不得用宣传图代替；
- 不得用无法验证来源的截图；
- 加强文字、方向、地标和状态描述；
- 必要时明确“未找到可可靠核验的当前版本实机图”。

若任务高度依赖图片且无法可靠执行，应在 `visual_gaps` 中记录，并在 `quality-check.md` 判断是否需要继续检索。

对飞书文档，无法找到可靠图片不是常规降级路径。除非用户明确要求纯文字或 `visual_need=none`，否则应继续检索、从真实视频截帧、要求用户提供截图，或停止交付并说明缺口；不得交付无图飞书攻略。
## 十八、拒绝图片的条件
以下图片必须 `rejected`：
- AI生成或疑似AI生成；
- 纯宣传CG；
- 角色立绘；
- 概念图；
- 同人图；
- 手绘伪地图；
- 无法确认是目标游戏；
- 无法确认是真实游戏画面；
- 版本明显不一致；
- 场景或对象不一致；
- MOD/私服冒充原版；
- 路线或标记明显错误；
- 图片与正文事实冲突；
- 图片会造成严重额外剧透；
- 图片对当前步骤无实际帮助。
## 十九、视觉完成条件
完成视觉检索前确认：
- 每个重要 `atomic_need` 已判断 `visual_need`；
- 所有最终图片都确认来自真实游戏画面；
- 没有AI生成图、宣传CG、立绘或伪地图冒充攻略图；
- 游戏、版本、平台和场景均已核对；
- MOD和私服风险已排查；
- 图片与正文事实一致；
- 每张图片都有明确攻略用途；
- 地图和路线类图片包含足够的实际识别信息；
- 关键图片会被放在最终产物对应步骤附近；
- 无可靠图片时未伪造视觉素材；飞书文档未在缺少必需图片时强行交付；
- `rejected_visuals` 不会进入最终飞书文档或HTML。
