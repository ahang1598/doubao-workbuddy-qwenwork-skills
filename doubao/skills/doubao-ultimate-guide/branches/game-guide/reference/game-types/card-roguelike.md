# 卡牌 / Roguelike / 构筑处理规则
本文件适用于 `primary_game_type=card-roguelike` 的请求，负责根据卡牌、Roguelike、Roguelite与局内构筑游戏的核心机制修正具体任务攻略。它不决定攻略主体结构；主体结构始终由 `primary_task` 文件决定。本文件只补充该类游戏中特别影响正确性和可执行性的随机性、构筑方向、资源曲线、局内动态决策、协同组件与转型判断。
## 一、适用条件
当当前问题主要依赖以下机制时使用本文件：
- 卡组、牌序、费用曲线和卡牌协同；
- Roguelike/Roguelite局内随机获取与构筑；
- 遗物、祝福、装备、词条或随机组件组合；
- 随机地图、事件、商店和奖励选择；
- 局内资源有限，需要持续做取舍；
- 构筑方向需要根据已有组件动态调整；
- 不同局次无法复制完全相同的固定路线。

不要因为一款游戏存在卡牌、随机掉落或肉鸽模式就自动使用本文件。只有当前问题真正依赖随机构筑、卡组协同或局内动态选择时，才将 `card-roguelike` 作为主类型或辅助类型。
## 二、`mechanic_focus`
根据当前问题确定最主要的机制焦点：

- `card`：卡组结构、费用曲线、抽牌、牌序和卡牌协同是核心；
- `deckbuilding`：围绕核心轴构建、精简、补充和调整卡组是核心；
- `roguelike`：随机路线、随机奖励、局内成长和风险管理是核心；
- `run-based`：单局资源、路线、事件和临场决策决定结果。

只选择最贴近当前问题的焦点。若多个机制同时存在，以最能改变当前攻略决策方式的机制为准。
## 三、核心处理原则
### 1. 不把“最终成型Build”当作每局可复制方案
随机游戏中，攻略应区分：
- 理想成型状态；
- 当前已经拥有的组件；
- 接下来最值得寻找的组件；
- 未获得核心组件时的替代路线；
- 什么时候应该停止强行追某个流派。

不得默认用户一定能拿到指定卡牌、遗物、装备或随机事件。
### 2. 当前局面优先于固定Tier List
决策必须结合：
- 当前卡组/Build；
- 已有遗物或组件；
- 生命、资源和经济状态；
- 当前路线；
- 后续敌人或Boss；
- 已出现的选择。

单卡或单组件强度不能脱离当前构筑判断。
### 3. 给选择规则，不只给固定答案
动态局面应按需提供：

```text
已有核心A → 优先补B
缺少核心A → 不继续强追该路线
生存不足 → 优先补防御/恢复
卡组过厚 → 优先删牌而不是继续拿普通卡
```
让用户能够处理后续随机选择。
## 四、构筑核心与信号
判断构筑方向时，优先识别：
- 当前最稳定的伤害或胜利条件；
- 已经出现的关键协同；
- 能否形成可靠循环；
- 是否存在资源、费用、抽牌或生存瓶颈；
- 当前组件是否足以支持继续投入。

区分：
### `commit_signal`
已经拥有足够核心组件，继续围绕该方向投入收益高。
### `soft_signal`
存在潜力，但还不足以锁定路线，应保持灵活。
### `pivot_signal`
当前路线组件不足、环境不适合或出现更强协同，应考虑转型。

不得因为拿到一张强卡就立刻认定整局必须走对应流派。
## 五、卡组质量
卡组类问题重点检查：
- 卡组是否过厚；
- 核心牌能否稳定抽到；
- 费用曲线是否失衡；
- 抽牌和资源是否足够；
- 防御与输出比例是否符合当前敌人；
- 是否存在功能重复的低价值卡；
- 是否有会破坏循环的组件。

“拿强卡”不一定优于“跳过”。应根据卡组当前结构判断是否值得加入。
## 六、拿牌与组件选择
每次选择按以下顺序判断：
1. 是否直接补当前核心瓶颈；
2. 是否与已有核心组件协同；
3. 是否提高稳定性而不是只提高上限；
4. 是否符合当前资源和费用结构；
5. 是否对即将面对的敌人/Boss有效；
6. 是否会稀释卡组或破坏现有循环。

多个选择强度接近时，优先选择当前局面更稳定的方案，而不是抽象Tier更高的组件。
## 七、删牌、精简与放弃选择
卡牌构筑中必须考虑“不拿”和“删除”本身也是决策。

按需说明：
- 哪些基础牌或低价值牌应优先删除；
- 哪些功能牌虽弱但当前仍不能删；
- 什么时候应跳过奖励；
- 什么时候卡组厚度已经影响稳定性；
- 删除资源应优先用于什么。

不得默认每次奖励都应该拿一项。
## 八、路线选择
Roguelike路线规划应结合：
- 当前生命和恢复能力；
- Build成熟度；
- 精英/高风险节点收益；
- 商店和经济；
- 升级点；
- 事件收益；
- 即将面对的Boss；
- 用户目标是稳过还是高收益。

优先给当前状态下的路线决策逻辑，例如：
- 状态健康且Build成型 → 可以提高风险获取高价值奖励；
- 生存不足 → 优先恢复、升级或低风险路径；
- 经济充足 → 提高商店路线价值；
- 核心卡急需升级 → 优先经过升级节点。

不得给固定地图路线冒充通用最优路线。
## 九、资源与经济
局内资源包括但不限于：
- 金币；
- 生命；
- 能量；
- 消耗品；
- 刷新次数；
- 删除次数；
- 重投/重抽资源；
- 商店购买机会。

应把生命等“状态资源”视为可管理资源，但不能机械鼓励玩家用生命换收益。必须结合后续风险和Build稳定性判断。
## 十、风险与收益
高风险选择应考虑：
- 失败是否直接结束本局；
- 当前状态是否能承受；
- 奖励是否真正解决当前需求；
- 是否有更安全替代；
- 后续路线是否允许恢复。

用户目标是稳定通关时，优先降低方差；用户明确追求高分、速通或极限收益时，可以接受更高风险，但要说明条件。
## 十一、Boss与敌人针对性
构筑决策不能只看通用强度，还要考虑：
- 下一Boss的核心机制；
- 是否需要单体/群体输出；
- 是否需要爆发、持续伤害或控制；
- 是否存在特定抗性、免疫或阶段要求；
- 当前Build是否有明显被克制风险。

不要为了克制单个敌人破坏整个Build，除非该敌人是当前明确的核心阻塞。
## 十二、随机性与概率表达
无法保证的随机结果必须使用条件表达。禁止：
- “下一层一定能拿到某组件”；
- “这个事件肯定出现”；
- “只要这样选就必成型”。

若存在可靠概率数据，可以说明概率；无法可靠确认时，只提供相对判断，不编造具体概率。
## 十三、失败复盘
用户反复失败时，优先判断：
- 是否过早锁死流派；
- 是否卡组过厚；
- 是否缺乏稳定防御或资源循环；
- 是否路线风险过高；
- 是否经济使用失衡；
- 是否为追求理论上限牺牲了当前生存；
- 是否没有针对最终Boss修正构筑。

复盘应给出下一局可执行的调整原则，而不只是解释上一局哪里错了。
## 十四、长期解锁与局外成长
Roguelite存在局外成长时，应区分：
- 局内失败原因；
- 局外解锁不足；
- 永久升级；
- 新角色、卡牌、武器或系统解锁。

若当前失败主要是局内决策问题，不要简单建议继续刷永久升级；若确实存在硬性成长差距，再说明最有效的局外提升。
## 十五、与任务文件的结合
本文件只修正处理方式，不替代任务文件。
### `walkthrough`
强调单局阶段、路线节点和随机分支，不给固定唯一流程。
### `quest`
仅在模式存在事件链或任务目标时，补充随机触发条件。
### `navigation`
强调随机地图和节点路线，不假设所有局次地图相同。
### `combat-and-boss`
强调当前构筑如何应对敌人和Boss，而不是通用固定打法。
### `build`
强调核心轴、组件协同、转型信号和实际成型概率。
### `character-and-team`
强调角色/英雄之间的构筑适配和局内功能。
### `puzzle`
仅在存在独立谜题机制时使用。
### `collection-and-achievement`
强调随机事件、解锁条件和多局累计目标。
### `beginner`
强调先理解基础构筑逻辑，不要求新手记忆完整Tier List。
### `resource-and-efficiency`
强调局内经济、风险收益和局外成长资源。
## 十六、视觉辅助侧重
按 `reference/media.md` 执行，优先考虑：
- 核心卡牌或组件；
- 遗物、祝福或装备；
- 卡组结构；
- 路线节点；
- 关键Boss；
- 简洁的协同关系图或优先级表。

视觉素材用于帮助识别组件和理解协同，不得用大量卡图替代构筑逻辑。
## 十七、常见错误
生成卡牌/Roguelike/构筑攻略时禁止：
- 把最终理想Build当作每局都能复制；
- 脱离当前卡组和已有组件照搬Tier List；
- 默认每次奖励都应该选择一个；
- 因一张强卡过早锁死流派；
- 忽略删牌、跳过和转型价值；
- 给固定随机路线冒充通用解；
- 忽略生命、经济和路线风险；
- 编造随机事件、掉率或出现概率；
- 只追求理论上限而忽视稳定通关。
## 十八、完成条件
使用本文件修正攻略后确认：
- 已根据当前局面而不是理想成型状态给建议；
- 固定机制与随机结果已经区分；
- 构筑核心和当前瓶颈明确；
- 拿牌、删牌、路线和资源决策有实际判断逻辑；
- 已提供必要的转型或替代条件；
- 风险水平符合用户目标；
- Boss针对性没有破坏整体构筑逻辑；
- 随机概率没有被写成确定事实；
- 本文件只修正了主任务攻略，没有覆盖或重复主任务结构；
- 关键事实、版本和视觉素材已通过 `retrieval.md`、`media.md` 与 `quality-check.md` 校验。
