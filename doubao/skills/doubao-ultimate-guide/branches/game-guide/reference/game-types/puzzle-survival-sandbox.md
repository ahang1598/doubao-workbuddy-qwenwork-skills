# 解谜 / 生存 / 沙盒 / 创造处理规则
本文件适用于 `primary_game_type=puzzle-survival-sandbox` 的请求，负责根据解谜、生存、沙盒与创造类游戏的核心机制修正具体任务攻略。它不决定攻略主体结构；主体结构始终由 `primary_task` 文件决定。本文件只补充该类游戏中特别影响正确性和可执行性的状态依赖、环境规则、资源循环、程序生成、自由目标、多解法和玩家自定义条件。
## 一、适用条件
当当前问题主要依赖以下机制时使用本文件：
- 环境观察、逻辑推理、机关和空间关系；
- 饥饿、口渴、温度、耐久、疾病或其他生存状态；
- 采集、制作、建造、基地和资源循环；
- 程序生成地图、随机种子或动态世界；
- 沙盒游戏中的自由目标和多种实现方式；
- 红石、自动化、线路、逻辑组件或创造系统；
- 玩家当前世界状态、资源和建造条件会显著改变答案。

不要因为一款游戏包含谜题、采集或建造元素就自动使用本文件。只有当前问题真正依赖环境规则、生存循环、沙盒自由度或创造系统时，才将 `puzzle-survival-sandbox` 作为主类型或辅助类型。
## 二、`mechanic_focus`
根据当前问题确定最主要的机制焦点：

- `puzzle`：线索、机关、逻辑、空间关系和规则推导是核心；
- `survival`：生存状态、资源循环、风险和环境适应是核心；
- `sandbox`：自由探索、建造、采集和玩家自定目标是核心；
- `creation`：自动化、线路、建筑、机械或创造系统实现是核心。

只选择最贴近当前问题的焦点。若多个机制同时存在，以最能改变当前攻略方法的机制为准。
## 三、核心处理原则
### 1. 先确认当前世界状态
该类游戏常存在高度状态依赖，必须按需确认：
- 当前地点或环境；
- 世界/地图种子；
- 已有资源；
- 已解锁配方、科技或工具；
- 当前生存状态；
- 难度、模式和游戏规则；
- 是否存在MOD、服务器规则或自定义设置。

不得默认所有玩家拥有相同地图、资源和规则。
### 2. 区分固定规则与动态结果
应明确：
- 哪些机制所有存档固定；
- 哪些地点或资源随机生成；
- 哪些结果由玩家世界状态决定；
- 哪些方案只是示例而非唯一解。

不得把特定种子的坐标、随机地图或单一建造方案写成通用固定答案。
### 3. 优先提供稳定可执行方案
存在多种解法时，默认优先：
1. 当前资源可完成；
2. 步骤清楚；
3. 失败成本低；
4. 对版本和随机环境依赖较少；
5. 符合用户明确偏好。

只有替代方案有明显优势时再补充。
## 四、解谜机制处理
当 `mechanic_focus=puzzle` 时重点检查：
- 当前谜题状态；
- 可观察线索；
- 固定规则；
- 是否存在随机答案；
- 用户希望提示还是完整解法。

应遵守 `puzzle.md` 的提示层级，并进一步注意：
- 沙盒环境中的谜题可能允许多种物理或创造性解法；
- 用户已经改变场景状态时，不能只套初始解法；
- 动态谜题必须根据当前局面推导。

不得把利用Bug、穿模或非预期机制作为默认解法。
## 五、生存优先级
当 `mechanic_focus=survival` 时，优先识别当前最紧急威胁：
- 生命；
- 食物；
- 水；
- 温度；
- 氧气；
- 疾病/中毒；
- 敌对生物；
- 天气；
- 避难所；
- 工具耐久或关键资源。

处理顺序通常应为：

```text
立即致命风险
→ 短期生存稳定
→ 基础资源循环
→ 安全据点
→ 工具与生产升级
→ 长期扩张
```
实际游戏机制不同则以真实优先级为准。

不得在用户即将死亡或资源即将耗尽时优先讲长期最优发展。
## 六、基础资源循环
生存和沙盒攻略应判断：
- 关键资源从哪里来；
- 获取是否可持续；
- 是否需要加工；
- 是否存在工具或设备前置；
- 消耗速度是否高于生产速度；
- 是否有更稳定替代来源。

目标是帮助用户建立可持续循环，而不是只解决一次性缺口。

例如一个资源问题应按需回答：
- 当前先去哪里获取；
- 如何安全带回；
- 后续怎样稳定生产；
- 什么时候值得自动化。
## 七、采集、制作与科技链
涉及制作或科技时，应明确依赖关系：

```text
目标物品/设施
→ 必要配方或科技
→ 关键材料
→ 所需工具/工作站
→ 上游材料
→ 实际制作
```
不得只列最终配方而忽略用户当前无法获得的上游材料或工作站。

复杂制作链优先指出当前真正缺失的最上游阻塞点。
## 八、基地与选址
基地选址必须结合用户目标，而不是给单一“最佳地点”。

按需考虑：
- 核心资源距离；
- 水源和食物；
- 安全性；
- 地形；
- 交通；
- 扩建空间；
- 特殊环境风险；
- 后期资源；
- 美观或角色扮演偏好。

应区分：
- 临时避难点；
- 前期基地；
- 长期主基地；
- 专项生产基地。

不得让新手为了理论最佳位置长距离冒险而失去当前生存稳定。
## 九、建造与创造任务
涉及建筑、机械、线路或自动化时，应先确认：
- 用户真正想实现的功能；
- 可用空间；
- 已有材料；
- 游戏版本；
- 平台；
- 是否允许MOD或指令；
- 用户对效率、体积、美观和复杂度的偏好。

输出优先建立：

```text
目标功能
→ 必要模块
→ 放置顺序
→ 连接关系
→ 启动条件
→ 测试方法
→ 常见故障
```
不得只展示最终成品而缺少建造顺序和验证方式。
## 十、自动化与生产系统
自动化攻略必须检查：
- 输入；
- 处理；
- 输出；
- 吞吐量；
- 存储；
- 能源或燃料；
- 堵塞点；
- 停机条件。

优先解决当前瓶颈，不为追求理论最大产能过度复杂化。

如果用户只需要满足当前需求，不默认推荐最高级或最大规模自动化方案。
## 十一、程序生成与随机世界
涉及程序生成内容时必须区分：
- 通用寻找方法；
- 当前种子具体位置；
- 地图生成规则；
- 版本差异。

用户未提供种子或当前地图信息时，不得编造精确坐标。

可以提供：
- 常见生成区域；
- 可识别地形；
- 搜索路线；
- 定位工具；
- 根据用户截图进一步判断的方法。
## 十二、地图、坐标与方向
沙盒和生存地图常缺少固定地标。路线说明按需使用：
- 坐标；
- 罗盘方向；
- 地形特征；
- 玩家自建标记；
- 距离；
- 高度层级。

若坐标系统随版本、维度或世界规则变化，必须确认。

不得只用“往左走”描述开放沙盒路线。
## 十三、多解法与玩家偏好
沙盒和创造类任务可能同时存在：
- 最省材料；
- 最简单；
- 最紧凑；
- 最高效率；
- 最稳定；
- 最美观；
- 最适合新手。

默认根据 `player_context.preferences` 选择主方案。

用户未指定时，优先简单、稳定、易复现方案，再按需补充其他路线。

不要同时罗列大量不同方案让用户自己筛选。
## 十四、风险与备份
涉及高风险探索、稀有资源、永久死亡或不可逆建造时，应按需提醒：
- 存档/备份；
- 出发前补给；
- 备用装备；
- 返回路线；
- 贵重物品存放；
- 失败后的恢复方案。

只在游戏真实存在明显损失时提示，不制造过度谨慎。
## 十五、MOD、服务器与自定义规则
用户问题涉及MOD或服务器时必须确认：
- MOD名称和版本；
- 模组包；
- 服务器插件；
- 自定义倍率；
- 禁用配方；
- 特殊世界规则。

原版攻略不能直接应用于MOD环境。

用户未说明但现象明显不符合原版时，应先通过检索确认可能的版本或规则差异，不自行假设。
## 十六、创造性方案与非预期机制
允许提供游戏规则内的创造性方案，但应区分：
- 正常设计内玩法；
- 社区常用技巧；
- 漏洞/Bug；
- 可能被版本修复的机制。

漏洞或版本不稳定技巧不得作为默认唯一方案。若用户明确询问，需说明版本风险和可能失效。
## 十七、与任务文件的结合
本文件只修正处理方式，不替代任务文件。
### `walkthrough`
强调状态依赖、资源准备、自由路线和阶段目标。
### `quest`
强调动态世界、任务触发和环境状态。
### `navigation`
强调随机地图、坐标、地形、维度和实际可达性。
### `combat-and-boss`
强调有限资源、环境利用、撤退路线和生存状态。
### `build`
强调可获取材料、制作链和当前阶段可用配置。
### `character-and-team`
仅在存在角色、生物、伙伴或多人分工时补充。
### `puzzle`
强调当前状态、动态答案、多解法和环境互动。
### `collection-and-achievement`
强调程序生成、稀有资源、世界状态和长期收集。
### `beginner`
强调先建立生存和资源循环，再学习高级创造系统。
### `resource-and-efficiency`
强调可持续产出、自动化、时间成本和资源瓶颈。
## 十八、视觉辅助侧重
按 `reference/media.md` 执行，优先考虑：
- 地形和环境；
- 资源识别；
- 制作链；
- 基地布局；
- 建造步骤；
- 线路连接；
- 自动化结构；
- 谜题机关；
- 坐标或地图关系。

建造类视觉素材必须能够对应正文步骤。不能只给最终成品图而没有关键连接关系。

程序生成地图的图片必须明确是示意、特定种子还是用户当前世界，不能混淆。
## 十九、常见错误
生成解谜/生存/沙盒/创造攻略时禁止：
- 把随机地图或特定种子坐标当作通用答案；
- 忽略用户当前生存状态而只讲长期发展；
- 给最终制作配方却缺少上游前置；
- 推荐理论最优基地却忽略前期生存成本；
- 默认用户拥有某个后期工具、科技或MOD；
- 建造教程只展示成品，不给步骤和测试方法；
- 为简单目标推荐过度复杂自动化；
- 把漏洞或版本不稳定技巧作为默认方案；
- 无序罗列大量“都可以”的沙盒方案；
- 混淆原版、MOD和服务器自定义规则。
## 二十、完成条件
使用本文件修正攻略后确认：
- 当前世界状态、模式和规则与用户环境匹配；
- 固定机制与随机结果已经区分；
- 生存问题优先解决真正的即时风险；
- 资源方案能够形成可持续循环，而不只是一次性获取；
- 制作和建造依赖关系完整可执行；
- 程序生成内容没有编造固定坐标；
- 多解法任务已根据用户偏好选择合理主方案；
- 自动化或建造方案包含启动和验证方法；
- MOD、服务器和版本差异已按需核验；
- 本文件只修正了主任务攻略，没有覆盖或重复主任务结构；
- 关键事实、版本和视觉素材已通过 `retrieval.md`、`media.md` 与 `quality-check.md` 校验。
