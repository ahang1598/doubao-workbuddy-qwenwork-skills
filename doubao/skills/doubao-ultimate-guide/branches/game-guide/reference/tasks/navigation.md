# 地图与寻路攻略规则
本文件适用于 `primary_task=navigation` 的请求，负责地点、入口、NPC、道具、收集品、区域、楼层和具体移动路线的定位与寻路。目标是让用户从已知起点准确到达目标位置，并能通过地标、场景和状态判断确认自己没有走错。
## 一、适用条件
当用户核心需求属于以下情况时使用本文件：
- 不知道某个地点、入口、NPC、道具或目标在哪里；
- 知道目标位置，但不知道怎么过去；
- 在复杂地图、地下城、多层建筑或开放世界中迷路；
- 需要从当前位置到目标位置的具体路线；
- 需要确认隐藏入口、传送点、楼层切换或区域连接方式。

若核心问题是完成任务，使用 `quest.md`；连续推进多个区域或章节，使用 `walkthrough.md`；寻找多个收集品，使用 `collection-and-achievement.md`。只有当前定位问题构成独立复杂卡点时，才作为辅助任务加载。
## 二、处理目标
寻路攻略必须建立：

```text
已知起点
→ 初始方向
→ 关键路线节点
→ 中间确认点
→ 目标入口或位置
→ 到达确认
```
不得只给地图坐标、区域名称或终点截图而不告诉用户如何从可识别起点到达。
## 三、生成前必须确认
至少确认：
- `final_goal`；
- 目标对象准确名称；
- 用户当前已知起点或最接近的可识别起点；
- 目标所在区域、楼层或地图层级；
- 是否存在前置解锁、单向路线、隐藏入口、传送限制或地图状态变化；
- 是否存在版本、平台、DLC或模式差异。

用户已说明当前位置时必须优先从该位置开始；若当前位置未知，优先选择最近且普遍可识别的传送点、存档点、区域入口或固定地标作为起点。
## 四、起点选择
起点优先级：
1. 用户明确当前位置；
2. 用户截图可确认的位置；
3. 用户已解锁且距离目标最近的明确地标；
4. 常用传送点、存档点、区域入口；
5. 其他稳定可识别位置。

不得默认用户拥有尚未解锁的传送点、坐骑、快捷通道或特殊移动能力。若路线依赖这些条件，必须说明前置或给替代路线。
## 五、路线描述
路线按真实移动顺序描述，每个关键节点按需包含：
- 从哪个位置出发；
- 面向或前往哪个方向；
- 沿什么道路、墙体、河流、建筑或地形移动；
- 在哪个分岔口转向；
- 经过什么明显地标；
- 是否需要上楼、下楼、跳落、攀爬、游泳、传送或切换区域；
- 到达节点后如何确认位置正确。

优先使用游戏内稳定地标和场景特征，不依赖模糊的“往前走一点”“附近”“左边那里”等描述。
## 六、中间确认点
路线较长、地图复杂或容易走错时，必须设置中间确认点。

适合作为确认点的内容：
- 传送点或存档点；
- 明确命名区域；
- 独特建筑；
- 大型雕像、桥梁、门、塔、洞口；
- 明显敌人或机关；
- 楼层切换点；
- UI或地图状态变化。

每个确认点只说明用户真正需要确认的特征，不堆叠无关环境描述。
## 七、地图层级与空间关系
涉及多层、地下、垂直地图或重叠区域时必须明确：
- 目标在地上、地下、洞穴、建筑内部或其他层级；
- 正确入口是否与地图图标垂直重叠；
- 是否需要从其他区域绕行；
- 是否存在只能单向进入的路径；
- 上下层之间的切换方式。

不得只根据二维地图图标判断用户可以直线到达。
## 八、隐藏入口与特殊进入条件
隐藏地点或特殊入口应重点说明：
- 真正入口在哪里；
- 从哪个方向最容易发现；
- 入口的视觉特征；
- 是否需要攻击墙壁、触发机关、使用道具、完成任务或改变世界状态；
- 是否存在多个入口；
- 哪些看似接近的路线实际上无法进入。

如果用户当前条件尚不能进入，必须明确指出原因和解锁方式。
## 九、NPC、道具与动态目标定位
### NPC
确认：
- 当前任务阶段下NPC应出现的位置；
- NPC是否会移动；
- 时间、天气、任务状态或世界事件是否影响位置；
- 用户找不到时优先检查什么。
### 道具与收集品
确认：
- 目标是固定刷新、一次性获取还是随机掉落；
- 是否在容器、敌人、商店、任务奖励或场景交互中；
- 是否需要特定前置；
- 到达位置后具体如何取得。

动态位置必须根据用户 `stage` 和版本给出条件分支，不把多个可能位置无序堆叠。
## 十、替代路线
仅在以下情况提供替代路线：
- 用户可能未解锁推荐起点；
- 主路线存在高难战斗或高操作要求；
- 不同平台/版本路线不同；
- 存在明显更安全、更快或更低门槛的方案。

优先给最符合 `player_context` 的主路线，其余路线简要说明适用条件。
## 十一、路线中的战斗、任务与解谜
寻路攻略只解释到达目标所必需的内容。

- 途中高难战斗构成主要阻碍 → 调用 `combat-and-boss.md`；
- 入口依赖任务状态 → 调用 `quest.md`；
- 路线本身属于连续区域推进 → 调用 `walkthrough.md`；
- 入口需要复杂机关 → 调用 `puzzle.md`。

辅助规则嵌入对应路线节点，不拆成无关联模块。
## 十二、到达确认
必须给出明确的终点识别方式，例如：
- 地图区域名称变化；
- 出现目标NPC；
- 看到特定建筑、门、雕像、Boss雾门或机关；
- 获得位置提示；
- UI、任务目标或传送点发生变化；
- 可以与目标对象交互。

不得只写“到了以后就能看到”。
## 十三、视觉辅助
按 `reference/media.md` 执行。地图与寻路通常优先级最高的视觉素材包括：
- 区域地图；
- 起点和终点位置；
- 路线转折点；
- 隐藏入口；
- 中间确认地标；
- 多层地图或楼层切换位置。

复杂路线优先形成“地图定位 + 现场识别”的组合。图片必须与正文路线、版本和地图层级一致，不得只展示无法定位的单张终点截图。
## 十四、推荐输出结构
根据问题复杂度选择必要部分，不机械展开：

```text
目标位置
→ 最佳起点
→ 具体路线
→ 关键确认点
→ 入口/终点识别
→ 找不到时的条件分支
```
用户只问“在哪里”且位置关系简单时，可直接给区域、最近起点和关键地标；复杂地图再展开完整路线。
## 十五、完成条件
地图与寻路攻略输出前确认：
- 起点对用户可用且可识别；
- 路线顺序和方向正确；
- 复杂路线存在足够的中间确认点；
- 地图层级、楼层和入口关系没有混淆；
- 动态NPC或目标位置与用户阶段匹配；
- 必要前置和特殊进入条件已说明；
- 终点有明确到达判断；
- 视觉素材与实际路线一致，或已合理降级；
- 用户可以从给定起点实际到达 `final_goal`；
- 关键事实、版本和视觉素材已通过 `retrieval.md`、`media.md` 与 `quality-check.md` 校验。
