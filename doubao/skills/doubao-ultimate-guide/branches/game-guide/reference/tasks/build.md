# Build与配装攻略规则
本文件适用于 `primary_task=build` 的请求，负责装备、武器、属性、技能、天赋、符文、词条、卡组及其他构筑体系。目标是根据用户当前目标、版本环境、已有资源和玩法条件，给出可以实际组成、理解和使用的Build，而不是只复制理论最优配置或堆叠名称清单。
## 一、适用条件
当用户核心需求属于以下情况时使用本文件：
- 不知道装备、武器、技能、天赋、符文、属性或词条怎么搭配；
- 想围绕某个角色、职业、武器、流派或核心机制构筑；
- 想优化已有Build；
- 想知道某件装备、技能或属性是否值得使用；
- 需要开荒、低成本、毕业、速刷、PVP或特定场景Build；
- 需要卡组、遗物、组件或其他构筑体系的组合方案。

若核心问题是角色培养优先级、队伍组成或角色间协同，使用 `character-and-team.md`；核心问题是如何打某个BOSS，使用 `combat-and-boss.md`。只有这些内容是当前Build成立不可缺少的独立需求时，才作为辅助任务加载。
## 二、处理目标
Build攻略必须建立：

```text
使用目标
→ 核心机制
→ 必选核心组件
→ 属性/技能/装备优先级
→ 可替代组件
→ 实际使用方式
→ 后续升级方向
```
不得只给“毕业配置”而不解释为什么成立、用户缺少关键组件时如何替代，以及实际应该如何使用。
## 三、生成前必须确认
至少确认：
- `final_goal`；
- 构筑对象：角色、职业、武器、流派、卡组或其他核心；
- 使用场景：开荒、推图、Boss、速刷、PVP、多人副本等；
- 用户当前已拥有的装备、技能、角色、资源或卡牌；
- 用户明确的成本、操作、氪金、获取难度或玩法限制；
- 当前版本、赛季、模式和关键平衡环境；
- 用户希望优化的是伤害、生存、控制、循环、效率还是综合表现。

未知条件不得自行补造。用户没有要求极限最优时，优先提供当前条件下真正可组成和可使用的方案。
## 四、先确定构筑目标
所有Build必须先确定主要目标，不得同时追求互相冲突的所有指标。

常见目标包括：
- 稳定通关；
- 单体/BOSS输出；
- 群体清场；
- 生存与容错；
- 低成本开荒；
- 自动/低操作；
- 速刷效率；
- PVP对局；
- 特定机制或玩法体验。

存在多个目标时，明确主目标和次目标，并围绕主目标做取舍。
## 五、核心机制
先解释Build为什么成立，只保留真正决定构筑逻辑的机制，例如：
- 主要伤害来源；
- 关键技能或资源循环；
- 属性之间的联动；
- 装备、天赋、词条或卡牌的协同；
- 触发条件、叠层、冷却、能量或资源要求；
- 生存或控制机制。

核心机制应让用户理解“为什么这样配”，但不要展开与当前Build无关的完整游戏机制百科。
## 六、组件分级
将构筑组件按实际重要性区分：
### `core`
缺少后会改变Build核心玩法或使主要循环无法成立。
### `important`
显著提升强度、稳定性或效率，但存在可用替代。
### `flex`
根据副本、敌人、玩家资源和偏好调整。

不得把所有装备和技能都写成“必需”。真正不可替代的核心组件必须说明原因。
## 七、装备与武器
按需说明：
- 核心装备/武器；
- 主要作用；
- 获取或使用门槛；
- 替代选项；
- 何时应该更换；
- 是否存在版本或模式限制。

推荐装备时优先匹配用户已有资源。若毕业装备暂时无法获得，应先给当前可执行的过渡方案，再说明升级方向。

不得因为某装备理论上限最高就忽略获取成本、操作要求或用户当前进度。
## 八、属性与词条优先级
属性推荐应明确：
- 必要门槛；
- 第一优先级；
- 次优先级；
- 低收益或应避免的属性；
- 达到阈值后是否需要改变优先级。

存在攻速、暴击、命中、冷却、能量、抗性等阈值时，应说明阈值的实际作用。无法可靠确认精确数值时，不得编造具体断点。

不要只给一串属性排序而不说明关键门槛和取舍逻辑。
## 九、技能、天赋与能力配置
按构筑实际使用方式组织：
- 核心主动技能；
- 必要被动/天赋；
- 辅助能力；
- 可调整槽位；
- 升级优先级。

技能选择必须与核心循环对应。若不同场景需要更换技能，按场景给少量真正有差异的变体，不罗列所有可能组合。
## 十、卡组与构筑型系统
涉及卡牌、遗物、组件或随机Build时，重点说明：
- 核心构筑轴；
- 必拿或高优先级组件；
- 关键协同；
- 曲线、资源或稳定性；
- 哪些组件只是锦上添花；
- 未抽到核心组件时如何转型；
- 哪些信号说明应该放弃原路线。

不得只列“最终成型卡组”，必须考虑实际构筑过程和随机性。
## 十一、最低可用版本与毕业版本
根据用户条件按需区分：
### 最低可用Build
用当前阶段较容易获得的组件建立核心循环，目标是先能用、能过、能继续发展。
### 标准Build
兼顾强度、获取成本和稳定性，通常作为默认推荐。
### 毕业/高投入Build
只在用户明确需要或确实有条件时提供，说明额外投入带来的实际提升。

不需要机械同时输出三套。根据 `player_context` 选择最适合的一套作为主方案，其余只在有实际价值时补充。
## 十二、替代方案
当用户缺少核心外的组件时，应给明确替代逻辑：
- 替代哪一个位置；
- 保留什么核心功能；
- 会损失什么；
- 什么情况下值得换回推荐组件。

替代方案必须功能对应，不得只因为“同类型”就视为等价。

真正不可替代的 `core` 缺失时，应明确说明当前无法完整成立，并给可执行的过渡构筑或其他路线。
## 十三、实际使用方式
Build攻略不能停留在配置表。按需说明：
- 开场顺序；
- 核心循环；
- 资源如何保持；
- 什么时候爆发；
- 什么时候停手或转入防御；
- 不同敌人或场景需要调整什么。

复杂战斗执行问题调用 `combat-and-boss.md`，但本文件至少要让用户知道Build本身如何运转。
## 十四、升级与资源投入顺序
用户需要培养或优化时，应给出清晰优先级，例如：

```text
先补核心组件
→ 达到关键属性门槛
→ 提升主要伤害/循环来源
→ 补生存或稳定性
→ 最后追求高成本优化
```
优先告诉用户“下一份资源投在哪里收益最高”，避免平均投入或无顺序的毕业清单。

若核心问题转为长期资源分配，可调用 `resource-and-efficiency.md`。
## 十五、版本与Meta处理
Build属于高版本敏感内容时必须按 `reference/retrieval.md` 深度核验。

重点检查：
- 技能、装备、词条、卡牌是否被调整；
- 核心联动是否仍成立；
- 推荐数据是否来自当前版本；
- PVE/PVP是否使用不同数值或规则；
- 旧版本毕业Build是否已经失效。

“当前Meta最强”与“最适合用户”不是同一概念。Meta信息只能作为方案依据之一。
## 十六、视觉辅助
按 `reference/media.md` 执行。Build攻略优先使用：
- 装备或武器图标；
- 技能/天赋界面；
- 属性面板；
- 卡组或构筑界面；
- 能帮助识别核心组件的游戏内截图。

视觉素材用于识别和理解配置，不得用角色宣传图代替Build信息，也不得让图片替代必要的文字逻辑。
## 十七、推荐输出结构
根据实际需求选择必要部分，不机械输出全部栏目：

```text
最适合你的Build结论
→ 核心机制
→ 核心配置
→ 属性/技能优先级
→ 缺组件时怎么替代
→ 实际怎么打/怎么循环
→ 下一步升级顺序
```
用户只问某件装备或某个属性时，直接回答其在当前Build中的作用和取舍；用户要求完整构筑时，再展开完整结构。
## 十八、完成条件
Build攻略输出前确认：
- 构筑目标和使用场景明确；
- 核心机制真实且当前版本有效；
- 已区分核心、重要和可调整组件；
- 推荐配置符合用户当前资源和限制；
- 不存在“只有毕业装才能用”的无执行方案；
- 属性和技能优先级有明确逻辑；
- 关键组件缺失时有合理替代或过渡方案；
- 用户知道Build实际如何运行；
- 后续资源投入顺序清楚；
- 视觉素材能帮助识别或理解核心配置，或已合理降级；
- 关键事实、版本和视觉素材已通过 `retrieval.md`、`media.md` 与 `quality-check.md` 校验。
