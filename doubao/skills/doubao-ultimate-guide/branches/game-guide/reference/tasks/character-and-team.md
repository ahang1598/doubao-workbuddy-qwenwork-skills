# 角色培养与配队攻略规则
本文件适用于 `primary_task=character-and-team` 的请求，负责角色培养、职业培养、队伍构成、阵容搭配、角色协同、站位与功能分工。目标是根据用户当前拥有的角色、资源、玩法目标和版本环境，给出真正可执行的培养与配队方案，而不是只推荐理论最强阵容或罗列角色强度榜。
## 一、适用条件
当用户核心需求属于以下情况时使用本文件：
- 不知道优先培养谁；
- 不知道角色、职业或英雄应该如何培养；
- 不知道现有角色怎么组队；
- 想围绕某个主C、核心角色、职业或玩法搭配阵容；
- 想优化现有队伍；
- 想判断某个角色是否值得培养或加入队伍；
- 需要开荒、Boss、速刷、PVP、多队模式或特定副本阵容；
- 需要处理角色之间的功能分工、技能联动、元素/属性反应、资源循环或团队协同。

若核心问题是装备、技能、天赋、属性或具体Build，使用 `build.md`；核心问题是长期资源投入和养成优先级，使用 `resource-and-efficiency.md`；核心问题是某个具体战斗怎么打，使用 `combat-and-boss.md`。只有这些内容对当前配队或培养结论具有独立决定作用时，才作为辅助任务加载。
## 二、处理目标
角色培养与配队攻略必须建立：

```text
用户目标
→ 当前角色池与资源
→ 核心角色/核心功能
→ 队伍结构与分工
→ 角色之间的协同
→ 培养优先级
→ 缺角色时的替代方案
→ 后续调整方向
```
不得只给“推荐四人组”或角色排行榜，而不解释为什么这样搭配、每个角色负责什么，以及用户缺少角色时如何替代。
## 三、生成前必须确认
至少确认：
- `final_goal`；
- 用户当前拥有或明确可用的角色/职业/英雄；
- 当前队伍、主力角色或准备围绕的核心；
- 主要使用场景：开荒、推图、Boss、速刷、PVP、多人副本、多队模式等；
- 用户现有培养资源、账号阶段和关键限制；
- 当前版本、赛季、模式及角色平衡环境；
- 用户更重视强度、低成本、低操作、泛用性、角色喜好还是长期价值。

未知的角色池、资源或培养程度不得自行补造。若用户没有提供完整角色池，应优先基于已知角色给出可执行方案，并只在确实影响结论时使用条件分支。
## 四、先确定队伍目标
队伍必须围绕明确目标构建，常见目标包括：
- 稳定开荒；
- 单体/Boss输出；
- 群体清场；
- 生存与容错；
- 自动或低操作；
- 速刷效率；
- PVP对局；
- 多人副本职责；
- 多队模式中的账号资源分配；
- 围绕特定角色、职业或玩法体验。

存在多个目标时，明确主目标和次目标。不得为了“面面俱到”让队伍失去核心方向。
## 五、角色功能识别
根据当前游戏机制识别每个角色的实际功能，不机械套用固定“主C/副C/辅助/奶妈”标签。

可能包括：
- 持续输出；
- 爆发输出；
- 前台/后台输出；
- 坦克或承伤；
- 治疗；
- 护盾；
- 控制；
- 增伤；
- 减防/减抗；
- 能量或资源供给；
- 聚怪；
- 破盾/破韧；
- 触发反应或机制；
- 生存保护；
- 战术功能或特定副本职责。

同一角色可承担多个功能，但必须说明其在当前队伍中的主要职责。
## 六、队伍结构
先确定队伍需要哪些功能位，再填角色，不要先列角色再强行解释。

按需判断：
- 核心输出由谁承担；
- 谁提供关键增益或减益；
- 谁负责资源循环；
- 谁提供生存；
- 是否需要控制、破盾、驱散、净化、打断或其他特殊功能；
- 队伍是否满足当前副本或模式的硬性要求。

若某个功能缺失会导致队伍无法稳定运行，必须明确指出。
## 七、核心协同
解释真正决定队伍成立的角色联动，例如：
- 技能持续时间与爆发窗口匹配；
- 元素、属性或状态之间的触发关系；
- 能量、怒气、行动条或其他资源循环；
- 增益覆盖时间；
- 召唤物、连携、追击或协同攻击；
- 控制与输出窗口；
- 前后台切换关系；
- 坦度、治疗与承伤机制。

不要把所有技能都逐个介绍，只解释影响当前队伍协同的关键机制。
## 八、角色选择优先级
推荐角色时按以下顺序判断：
1. 是否满足队伍必需功能；
2. 是否与核心角色或核心机制协同；
3. 是否适合当前使用场景；
4. 是否符合用户现有资源和培养成本；
5. 是否满足用户操作和玩法偏好；
6. 最后再考虑理论强度和Meta排名。

理论强度更高但用户无法培养、无法获取或不符合队伍机制时，不应作为唯一推荐。
## 九、培养优先级
培养资源必须有明确顺序。按需区分：
### 核心优先
直接决定队伍主要输出、核心循环或关键生存能力的角色。
### 次优先
明显提升队伍强度、稳定性或功能完整度，但不影响基础运行。
### 后补
当前阶段收益较低、可暂缓或只需达到功能门槛的角色。

培养建议应具体到真正有价值的维度，例如：
- 等级；
- 突破；
- 技能等级；
- 关键天赋；
- 装备；
- 武器；
- 命座/星魂/突破阶段；
- 其他游戏特有养成系统。

不得机械要求所有角色平均培养，也不得把所有项目都列为“必须拉满”。
## 十、最低功能门槛与过度投资
对辅助、功能位或过渡角色按需说明：
- 达到什么程度就能正常发挥作用；
- 哪些培养暂时不值得投入；
- 哪些关键等级、技能或装备必须优先；
- 什么时候再继续投入。

若角色只需要满足功能门槛，不应建议用户为追求极小提升投入大量稀缺资源。
## 十一、替代角色与替代逻辑
用户缺少推荐角色时，替代方案必须按“功能”匹配，而不是只按角色类型或稀有度匹配。

说明：
- 替代哪个位置；
- 必须保留什么核心功能；
- 替代后会损失什么；
- 是否需要调整队伍其他位置；
- 哪些角色可以互换；
- 哪些角色看似相似但实际上无法替代。

若缺失的是真正不可替代的核心机制，应明确说明当前无法完全复刻该队伍，并提供可执行的替代体系。
## 十二、单队与多队场景
### 单队
优先构建完整、稳定、资源集中的主队。
### 多队
需要同时考虑：
- 核心角色不能重复使用；
- 稀缺辅助如何分配；
- 不同队伍是否争抢同一装备或资源；
- 每队最低功能完整度；
- 账号整体收益，而不是只优化其中一队。

多队方案应优先保证每队能运行，再追求单队极限强度。
## 十三、不同场景下的队伍变体
仅在场景差异会明显改变队伍时提供变体，例如：
- Boss单体；
- 群体清场；
- 生存压力高；
- 特定属性/元素要求；
- PVP；
- 多人副本职责；
- 特殊机制副本。

优先给一个主队伍，再给少量必要变体，不罗列大量阵容让用户自行筛选。
## 十四、角色是否值得培养
用户询问某个角色是否值得练时，必须结合：
- 用户当前角色池；
- 现有队伍缺口；
- 账号阶段；
- 培养成本；
- 当前版本环境；
- 该角色的不可替代功能；
- 与用户偏好是否匹配。

结论应尽量明确，例如：
- 现在优先培养；
- 可以培养但优先级不高；
- 只在某类队伍中值得；
- 当前账号暂时不建议投入；
- 喜欢角色可培养，但强度收益有限。

不得仅引用角色强度榜下结论。
## 十五、队伍实际使用方式
配队攻略不能停在阵容名单。按需说明：
- 谁先手；
- 核心技能顺序；
- 增益和爆发如何对齐；
- 什么时候切换角色；
- 如何维持资源循环；
- 生存技能何时使用；
- 哪些错误会破坏队伍循环。

复杂实战问题可调用 `combat-and-boss.md`，但本文件至少要让用户理解队伍为什么能正常运转。
## 十六、与Build和资源规划的关系
当角色是否可用主要取决于装备、属性或技能配置时，调用 `build.md`。

当用户需要在多个角色之间分配长期材料、抽卡资源、体力或时间时，调用 `resource-and-efficiency.md`。

主任务仍由当前 `final_goal` 决定，不得因为涉及培养资源就自动把所有问题转成资源规划。
## 十七、版本与Meta处理
角色强度和阵容属于高版本敏感内容时，必须按 `reference/retrieval.md` 深度核验。

重点检查：
- 角色技能或数值是否调整；
- 新角色是否改变队伍结构；
- 当前环境是否改变关键功能价值；
- PVE/PVP是否使用不同规则；
- 旧阵容是否因机制变化失效。

当前Meta可以作为参考，但不得覆盖 `player_context` 和用户真实角色池。
## 十八、视觉辅助
按 `reference/media.md` 执行。角色培养与配队攻略优先使用：
- 角色识别图；
- 队伍构成界面；
- 关键技能或机制图；
- 培养界面；
- 能帮助理解队伍关系的简洁结构图。

资源优先级和培养顺序优先使用结构化文本或表格，不为每个角色强行加入宣传图。
## 十九、推荐输出结构
根据实际需求选择必要部分，不机械输出全部栏目：

```text
最适合你的培养/配队结论
→ 队伍核心思路
→ 角色分工
→ 推荐阵容
→ 缺角色时怎么替代
→ 培养优先级
→ 实际怎么操作
→ 后续调整方向
```
用户只问“这几个角色怎么组”时，直接给最适合的队伍和关键分工；用户要求完整养成规划时，再展开培养顺序和长期调整。
## 二十、完成条件
角色培养与配队攻略输出前确认：
- 队伍目标明确；
- 推荐基于用户真实角色池和条件；
- 已说明关键角色分工；
- 核心协同真实且当前版本有效；
- 队伍功能完整，没有明显机制缺口；
- 培养资源有清晰优先级；
- 没有要求所有角色平均投入；
- 缺少推荐角色时有合理替代逻辑；
- 用户知道队伍实际如何运行；
- 多队场景考虑了账号整体资源冲突；
- 理论Meta没有覆盖用户实际条件；
- 视觉素材能帮助识别角色、队伍或关键机制，或已合理降级；
- 关键事实、版本和视觉素材已通过 `retrieval.md`、`media.md` 与 `quality-check.md` 校验。
