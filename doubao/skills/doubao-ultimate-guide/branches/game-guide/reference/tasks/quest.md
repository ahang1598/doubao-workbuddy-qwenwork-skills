# 任务攻略规则
本文件适用于 `primary_task=quest` 的请求，负责主线、支线、NPC任务、隐藏任务、事件链和连续任务阶段的触发、推进与完成。目标是根据用户当前任务状态，准确判断“为什么没触发、下一步做什么、去哪里、完成后如何确认”，避免任务阶段错位和遗漏关键前置。
## 一、适用条件
当用户核心需求属于以下情况时使用本文件：
- 不知道任务如何触发；
- 任务没有出现、NPC不在、对话不更新；
- 不知道任务下一步做什么；
- 卡在某个任务阶段；
- 想完成某条主线、支线、NPC任务或隐藏任务；
- 想确认任务分支、失败条件、奖励或完成状态。

若核心问题只是找一个地点，使用 `navigation.md`；只是打某个BOSS，使用 `combat-and-boss.md`；需要连续推进多个章节或区域，使用 `walkthrough.md`。这些内容只有在当前任务中构成独立复杂卡点时才作为辅助任务加载。
## 二、处理目标
任务攻略必须建立：

```text
当前任务状态
→ 缺失前置或触发条件
→ 当前阶段目标
→ 执行步骤
→ 阶段更新判断
→ 后续阶段
→ 任务完成确认
```
不得直接从任务第一步开始复述完整Wiki流程，必须先定位用户当前处于哪一个任务状态。
## 三、生成前必须确认
至少确认：
- `final_goal`；
- 任务准确名称或可唯一识别对象；
- 用户当前 `stage`；
- 当前任务日志、NPC状态或最近已完成步骤；
- 必要前置任务、事件、区域、等级或道具；
- 是否存在版本、DLC、平台或模式差异；
- 是否存在分支、失败条件、不可逆选择或时间窗口。

用户已明确说明当前阶段时不得重复从头解释；无法确认但不影响当前步骤的信息保持未知。
## 四、任务状态定位
优先使用以下证据判断任务阶段：
1. 用户明确描述的当前任务目标或任务日志；
2. 用户截图中的任务文本、NPC、地图标记或场景；
3. 已确认的前轮对话信息；
4. 联网核验后的任务阶段结构。

不要仅根据“用户提到某个NPC”推断其一定处于某一步。

必要时将任务状态内部整理为：

```text
quest_state:
  prerequisites_met:
  current_stage:
  completed_steps:
  next_required_action:
  branch_state:
```
该结构不要求展示给用户。
## 五、任务触发问题
用户问“为什么任务没有出现/触发”时，按以下顺序排查：
1. 前置任务是否完成；
2. 必须的主线/世界进度是否达到；
3. NPC、区域、时间、天气、难度或特殊状态是否满足；
4. 是否需要持有、使用或交付特定道具；
5. 是否需要先完成一次对话、休息、传送、重新加载区域或其他状态刷新；
6. 是否因分支、失败条件或不可逆选择导致任务无法继续；
7. 是否存在版本、平台或DLC差异。

只列与当前任务真实相关的条件，不使用通用排查清单填充答案。
## 六、任务推进步骤
每个关键阶段按需包含：
- 当前阶段目标；
- 从哪里开始；
- 找谁或去哪里；
- 需要交互、对话、收集、击败或选择什么；
- 完成后任务状态如何变化；
- 下一步从哪里继续。

任务步骤必须按真实任务状态顺序组织。不得省略会导致用户卡住的关键交互或状态刷新。

简单步骤可合并；出现以下情况时应单独拆出：
- NPC位置变化；
- 任务目标发生变化；
- 需要跨区域；
- 有关键道具或交互；
- 出现BOSS、解谜或复杂路线；
- 存在分支或不可逆选择；
- 任务容易因状态错位而中断。
## 七、NPC与任务状态变化
涉及NPC任务时重点确认：
- NPC当前可能出现的位置；
- NPC移动的触发条件；
- 对话是否需要重复至内容耗尽；
- 是否需要刷新世界状态；
- 是否有其他事件会覆盖或终止该NPC任务；
- NPC死亡、敌对、消失等状态是否影响任务。

存在多个可能位置时，应根据用户 `stage` 给出最可能位置，并按状态条件提供分支，不无序罗列所有位置。

复杂定位调用 `navigation.md`；视觉素材按 `media.md` 使用NPC位置、地图点位或关键场景图。
## 八、任务分支与不可逆选择
存在分支时：
- 只说明当前决策会影响什么；
- 标出不可逆选择、失败条件和重要锁定条件；
- 用户未要求完整剧透时，不提前展开所有后续剧情；
- 多个分支均可完成任务时，根据 `player_context.preferences` 推荐最合适方案；
- 奖励差异只有在会影响玩家当前决策时才重点展开。

不得为了“完整”把所有结局和后续任务链全部剧透。
## 九、隐藏任务与特殊触发
隐藏任务或无明确日志任务必须重点说明：
- 触发入口；
- 必要前置；
- 游戏内可观察到的确认信号；
- 后续推进依据；
- 容易漏掉或失效的条件。

若游戏本身不会给任务标记，应明确告诉用户应该依据NPC对话、道具描述、地图变化或世界事件判断，而不是假设存在任务日志。
## 十、任务中的战斗、寻路与解谜
任务文件只处理与任务状态直接相关的核心操作。

- 路线复杂 → 调用 `navigation.md`；
- BOSS或高难战斗构成主要卡点 → 调用 `combat-and-boss.md`；
- 复杂谜题 → 调用 `puzzle.md`；
- 连续跨区域主流程 → 调用 `walkthrough.md`。

辅助规则必须嵌入对应任务阶段，不得把答案拆成互不连接的多个模块。
## 十一、任务完成判断
必须给出至少一种明确的完成或阶段更新信号，例如：
- 任务日志更新或消失；
- 获得关键奖励或任务道具；
- NPC移动、出现新对话或状态变化；
- 地图标记更新；
- 新任务、区域或事件解锁；
- 游戏明确显示完成提示。

不得只写“然后任务就完成了”。
## 十二、常见卡点处理
只处理与当前任务真实相关的问题，例如：
- NPC不出现；
- 对话不更新；
- 任务目标没有刷新；
- 关键道具无法交付；
- 地图没有标记；
- 已完成步骤但下一阶段未触发；
- 任务因分支或世界状态变化中断。

排查必须按用户当前状态排序，优先给最可能原因和最快验证方式。
## 十三、视觉辅助
按 `reference/media.md` 执行。任务攻略优先使用：
- NPC当前位置；
- 任务触发点；
- 关键交互对象；
- 任务入口；
- 容易认错的场景；
- 必要的地图路线。

图片必须匹配正确任务阶段。不得使用后续阶段截图误导当前用户，也不得因配图泄露超出 `spoiler_level` 的剧情。
## 十四、推荐输出结构
根据实际复杂度选择必要部分，不机械输出全部栏目：

```text
当前任务状态判断
→ 下一步直接做什么
→ 必要前置/触发条件
→ 关键阶段步骤
→ 分支或易卡点
→ 任务完成确认
```
用户只问某一步时，直接回答该步骤和必要前置；用户要求完整任务攻略时，再按阶段展开完整流程。
## 十五、完成条件
任务攻略输出前确认：
- 已定位用户当前任务阶段；
- 没有从错误阶段开始；
- 所有必要前置和触发条件正确；
- NPC、任务目标和关键状态变化与当前阶段匹配；
- 分支与不可逆条件已按需提示；
- 复杂战斗、路线或解谜已按需调用辅助任务规则；
- 每个关键阶段都有可验证的推进或完成信号；
- 没有不必要剧透；
- 用户可以从当前状态执行到 `final_goal`；
- 关键事实、版本和视觉素材已通过 `retrieval.md`、`media.md` 与 `quality-check.md` 校验。
