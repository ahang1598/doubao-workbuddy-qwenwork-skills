# 解谜攻略规则
本文件适用于 `primary_task=puzzle` 的请求，负责机关、密码、环境谜题、逻辑谜题、符号组合、顺序操作、场景互动和其他需要推理或观察完成的游戏谜题。目标是在控制剧透的前提下，根据用户当前卡点提供可执行的提示或完整解法，而不是只直接甩出最终答案。
## 一、适用条件
当用户核心需求属于以下情况时使用本文件：
- 不知道某个机关怎么启动；
- 看不懂谜题规则或提示；
- 不知道密码、顺序、符号或操作方式；
- 卡在环境谜题、机关房、门锁、光线、平台、线路或逻辑谜题；
- 想要提示而不是完整答案；
- 已尝试解谜但不知道哪一步错了；
- 需要确认谜题完成后的状态或下一步。

若核心问题只是找到谜题位置，使用 `navigation.md`；谜题只是任务中的一个简单步骤，使用 `quest.md`；谜题嵌在连续流程中且不是主要卡点，使用 `walkthrough.md`。只有谜题本身需要独立规则时才加载本文件。
## 二、处理目标
解谜攻略必须围绕：

```text
当前谜题状态
→ 谜题目标
→ 可观察线索
→ 规则或逻辑
→ 提示层级
→ 具体操作
→ 完成判断
```
不得默认用户一定想看完整答案。默认遵守 `spoiler_level=minimal`，优先给完成当前卡点所需的最少信息。
## 三、生成前必须确认
至少确认：
- `final_goal`；
- 谜题准确对象或场景；
- 用户当前看到的机关、符号、提示或已完成步骤；
- 当前谜题状态是否会因任务阶段、版本、难度或随机生成而变化；
- 用户是否明确要求提示、完整答案或快速解法；
- 是否存在多种解法、随机答案或存档差异。

用户已提供截图时，应优先基于截图中的实际状态判断，不直接套用固定答案。
## 四、先识别谜题类型
根据当前谜题判断核心机制，例如：
- 顺序型：按正确顺序操作；
- 对应型：符号、颜色、图案或位置配对；
- 环境观察型：从场景中寻找线索；
- 逻辑推理型：根据条件排除或推导；
- 空间型：旋转、拼接、移动、路径或视角；
- 机关联动型：多个开关、平台、线路或设备相互影响；
- 资源约束型：有限次数、步数、能量或物件；
- 密码型：从文本、图案、音频或环境获取组合；
- 动态/随机型：答案随存档、局次或场景变化。

不得在未确认类型前直接给固定答案。
## 五、提示层级
默认按以下层级提供帮助：
### Level 1：方向提示
只指出应该观察什么、关注哪里或理解什么规则，不给具体答案。
### Level 2：关键提示
说明核心逻辑、关键关系或下一步思路，但保留最后操作。
### Level 3：分步解法
按顺序告诉用户如何完成，但尽量避免无关剧情剧透。
### Level 4：直接答案
直接给密码、顺序、位置或最终操作，仅在用户明确要求、已经反复卡住或问题本身只需快速答案时使用。

根据用户请求直接选择合适层级，不必机械从Level 1逐级输出。用户明确说“直接告诉我答案”时，不要强行只给提示。
## 六、基于当前状态解谜
解谜必须从用户当前状态出发，而不是从谜题初始状态重置说明。

优先判断：
- 哪些机关已触发；
- 哪些对象已移动；
- 哪些线索已发现；
- 用户当前具体卡在哪一步；
- 是否存在可以继续操作的下一动作；
- 是否需要重置谜题。

若用户已经完成前半部分，不重复讲完整流程；只补当前卡点和必要后续。
## 七、线索与逻辑说明
按需说明：
- 线索在哪里；
- 线索与机关之间是什么关系；
- 为什么某个顺序或答案成立；
- 哪些信息是干扰项；
- 哪个观察点最容易漏掉；
- 如何从游戏内信息自行验证。

解释应帮助用户理解当前谜题，但不要为了展示推理过程写成长篇逻辑分析。
## 八、随机谜题与动态答案
若答案会随局次、存档、玩家选择或随机生成变化：
- 不得给固定答案冒充通用答案；
- 应教用户如何读取当前局的线索；
- 必要时根据用户截图或当前状态现场推导；
- 明确哪些部分固定、哪些部分动态。

如果无法从现有信息确定当前答案，应按 `routing.md` 判断是否属于 `blocking`，优先通过截图、游戏内信息或联网确认解决。
## 九、多步骤机关
复杂机关按真正的状态变化拆分：
- 当前目标；
- 操作对象；
- 操作方式；
- 状态变化；
- 下一步。

只有机关状态或空间关系发生变化时才单独拆步，不把每次按键都机械编号。

存在可逆和不可逆操作时必须明确；需要重置时说明重置方式和重新开始的位置。
## 十、环境谜题
环境谜题优先利用稳定可识别元素：
- 建筑、雕像、壁画、灯光；
- 颜色、符号、数字；
- 音效或节奏；
- 地面、墙壁或天花板结构；
- NPC对话、日志、物品描述；
- 视角、影子、反射或空间关系。

不得引用用户当前场景中不存在的线索。
## 十一、密码与符号谜题
若密码或符号答案固定：
- 先确认版本和场景一致；
- 用户只要答案时可直接给；
- 用户想知道原理时再解释线索来源。

若答案动态：
- 明确读取规则；
- 根据用户当前线索推导；
- 不得复制其他玩家的固定答案。
## 十二、操作精度与时机
涉及平台、时序、光线、移动物体或动作操作时，按需说明：
- 起始位置；
- 操作顺序；
- 时机判断；
- 失败后如何恢复；
- 成功时会出现什么反馈。

不得只写“快速操作”“把握时机”等模糊表述。
## 十三、解谜中的路线、任务与战斗
- 找不到谜题位置 → 调用 `navigation.md`；
- 谜题依赖任务状态 → 调用 `quest.md`；
- 谜题是连续流程中的关键节点 → 按需调用 `walkthrough.md`；
- 解谜期间存在独立高难战斗 → 调用 `combat-and-boss.md`。

辅助规则嵌入当前解谜流程，不拆成无关联模块。
## 十四、完成判断
必须给出明确完成信号，例如：
- 门打开；
- 机关停止或变色；
- 出现音效或动画；
- 获得道具；
- 新路径解锁；
- 任务日志更新；
- 场景结构改变。

不得只写“这样就解开了”。
## 十五、视觉辅助
按 `reference/media.md` 执行。解谜优先使用：
- 谜题整体场景；
- 可交互机关；
- 关键符号或线索；
- 正确观察位置；
- 空间关系图；
- 必要操作节点。

默认避免用一张包含完整答案的图直接破坏提示层级。用户只要提示时，视觉素材也只展示对应层级的信息。
## 十六、推荐输出结构
根据用户需要选择必要部分，不机械输出全部栏目：

```text
你现在卡点是什么
→ 先看哪个线索
→ 核心规则
→ 下一步怎么做
→ 必要时给完整分步解法
→ 完成判断
```
用户明确只要答案时，直接给答案和最少必要操作；用户想自己解时，优先使用提示层级。
## 十七、完成条件
解谜攻略输出前确认：
- 谜题对象和当前状态识别正确；
- 没有把动态答案误写成固定答案；
- 提示深度符合用户需求和 `spoiler_level`；
- 关键操作具体可执行；
- 已从用户当前状态继续，而不是无意义地从头复述；
- 多步骤机关的状态变化清楚；
- 完成信号明确；
- 视觉素材没有提前泄露超出需求的答案；
- 用户可以据此继续或完成 `final_goal`；
- 关键事实、版本和视觉素材已通过 `retrieval.md`、`media.md` 与 `quality-check.md` 校验。
