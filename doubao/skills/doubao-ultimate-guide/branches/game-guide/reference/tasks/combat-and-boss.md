# BOSS与战斗攻略规则
本文件适用于 `primary_task=combat-and-boss` 的请求，负责BOSS、精英敌人、普通战斗卡点、战斗机制、阶段转换和实战应对。目标是根据用户当前角色、装备、队伍、资源和操作水平，提供真正可执行的打法，而不是只罗列敌人技能或推荐理论最强配置。
## 一、适用条件
当用户核心需求属于以下情况时使用本文件：
- 打不过某个BOSS、精英敌人或战斗关卡；
- 不理解敌人机制、阶段变化或特殊规则；
- 不知道如何躲避关键攻击、寻找输出窗口或处理机制；
- 需要根据当前角色、职业、装备或队伍制定打法；
- 需要稳定、低操作、低资源、速杀或其他特定战斗方案；
- 想确认战前准备、阶段策略或失败原因。

若核心问题是Build配置，使用 `build.md`；角色培养和队伍组合，使用 `character-and-team.md`；BOSS位置或路线，使用 `navigation.md`。只有这些内容构成当前战斗成功的独立关键需求时，才作为辅助任务加载。
## 二、处理目标
战斗攻略必须围绕：

```text
当前失败原因
→ 必要战前准备
→ 核心机制识别
→ 危险动作与应对
→ 可输出/安全窗口
→ 阶段变化
→ 稳定击败
```
不得只写“注意躲技能、提高装备、抓住机会输出”等无法执行的泛化建议。
## 三、生成前必须确认
至少确认：
- `final_goal`；
- 敌人或BOSS准确对象；
- 用户当前 `player_context` 中已知的角色/职业、装备/Build、队伍、等级、资源和限制；
- 战斗所在版本、难度、模式、DLC或副本环境；
- 战斗是否存在阶段转换、强制机制、特殊弱点或失败条件；
- 用户当前主要 `core_blocker`。

未知的玩家条件不得自行补造。若不影响基础打法，可先给通用可执行方案；只有缺失信息会导致方案明显错误时才按 `routing.md` 处理。
## 四、先判断失败原因
根据用户描述、截图和已确认事实优先判断当前卡点属于哪类：
- 不理解关键机制；
- 无法识别或躲避高威胁攻击；
- 输出窗口判断错误；
- 生存不足；
- 伤害不足；
- 装备、属性或队伍明显不匹配；
- 资源管理失败；
- 阶段转换处理错误；
- 团队职责或站位错误；
- 等级/进度明显低于合理门槛。

优先解决真正导致失败的1–3个核心问题，不把所有可能原因全部罗列给用户。
## 五、战前准备
只推荐会实质提高当前战斗成功率的准备，包括：
- 必要等级或属性门槛；
- 武器、装备、抗性或消耗品；
- 技能、法术、天赋或召唤；
- 队伍配置和职责；
- 战斗前可获取的关键增益；
- 必须关闭、开启或调整的游戏机制。

推荐必须满足 `player_context.constraints`。不得默认用户拥有稀有角色、顶级装备或高成本资源。

存在多个方案时优先给：
1. 用户当前条件下最容易执行的方案；
2. 必要时再给低成本替代或高效率进阶方案。
## 六、核心机制拆解
只解释真正影响胜负的机制。每个关键机制按需说明：
- 什么时候触发；
- 游戏内如何识别；
- 玩家应该做什么；
- 做错会发生什么；
- 成功处理后的机会是什么。

不要把完整技能数据库当成攻略。低威胁普通攻击可以合并说明，重点突出会导致死亡、团灭、状态异常或阶段失败的机制。
## 七、攻击识别与应对
关键攻击应尽量使用“视觉/声音信号 → 应对动作 → 时机”描述，例如：
- 看到什么前摇；
- 听到什么提示；
- 应向哪里移动、闪避、防御、跳跃或中断；
- 应提前还是延迟操作；
- 是否存在追踪、多段、延迟爆炸或二次攻击。

禁止只写“及时躲开”“注意闪避”。

不同角色、职业或移动方式会改变应对时，按用户条件给对应方案。
## 八、输出窗口与战斗节奏
说明真正安全或高收益的输出机会，例如：
- 某个大招结束后；
- 连招最后一击后；
- BOSS进入硬直、倒地或破防后；
- 机制成功处理后；
- 特定阶段或部位暴露时。

按需说明：
- 能安全打几次或持续多久；
- 什么时候必须停止贪刀；
- 近战、远程或不同职业窗口是否不同；
- 资源应在哪个阶段保留或爆发。

用户卡点是“总被反打”时，优先强调停止输出的信号，而不是单纯提高伤害。
## 九、阶段转换
存在多阶段战斗时必须明确：
- 阶段转换触发条件；
- 新增或变化的关键机制；
- 哪些旧机制仍然保留；
- 转阶段时应该保留什么资源；
- 新阶段的优先处理目标。

不得把多个阶段混在一起描述，导致用户无法判断当前应该执行哪套策略。
## 十、针对玩家条件调整打法
根据 `player_context` 调整：
- 新手/低操作：优先安全、稳定、容错高的打法；
- 资源不足：优先低成本替代；
- 装备不足：明确哪些提升最有效，避免泛泛建议刷装备；
- 特定角色/职业：围绕其真实机制调整；
- 单人/多人：分别处理仇恨、职责和站位；
- 速杀/挑战：可提高风险，但必须标明适用条件。

理论最优方案如果用户无法执行，不得作为唯一答案。
## 十一、Build与队伍辅助
若战斗失败主要由配置导致：
- 装备、属性、技能或构筑问题 → 调用 `build.md`；
- 角色培养、队伍协同或职责问题 → 调用 `character-and-team.md`。

战斗攻略主体仍应解释“如何打”，不能因为调用Build文件就只输出配置清单。
## 十二、多人战斗与团队机制
涉及多人副本、MMO或团队战斗时按需说明：
- 各职责需要处理什么；
- 关键站位；
- 集合、分散、换位、分摊或打断要求；
- 团队失败最常见原因；
- 用户当前职责应该重点观察什么。

只详细展开用户所属职责需要执行的内容；其他职责只解释与其配合直接相关的部分。
## 十三、失败诊断
用户已经多次失败时，优先提供可验证的诊断：
- 如果死于某招 → 如何识别和处理；
- 如果进入后期资源不足 → 哪个阶段过度消耗；
- 如果伤害不够 → 是输出窗口、Build还是等级问题；
- 如果机制后必死 → 是否漏掉前置动作；
- 如果队伍团灭 → 哪个团队机制未完成。

每个诊断应给出明确修正动作，不只解释原因。
## 十四、战斗中的替代方案
仅在以下情况提供替代方案：
- 用户缺少推荐角色、装备或资源；
- 某种打法操作要求过高；
- 不同职业/武器差异明显；
- 存在召唤、联机、环境利用或其他合法机制；
- 用户明确要求稳过、低成本或速杀方案。

优先给1个主方案，再给必要替代，不堆叠大量Build让用户自己选择。
## 十五、视觉辅助
按 `reference/media.md` 执行。战斗攻略优先使用：
- BOSS或敌人识别图；
- 战斗场地；
- 高威胁攻击前摇或机制状态；
- 阶段转换视觉信号；
- 关键站位或安全区域；
- 多人副本机制图。

视觉素材必须服务于“识别和执行”。普通攻击不需要逐个配图，也不得用无法对应当前版本的旧机制图。
## 十六、推荐输出结构
根据实际卡点选择必要部分，不机械输出全部栏目：

```text
你现在最可能卡在哪里
→ 战前只需要准备什么
→ 核心打法
→ 关键攻击：看到什么 + 怎么处理
→ 安全输出窗口
→ 阶段变化
→ 失败时优先调整什么
→ 击败确认
```
用户只问某个招式或机制时，直接解释该机制及应对；用户明确需要完整BOSS攻略时，再展开完整战斗结构。
## 十七、完成条件
BOSS与战斗攻略输出前确认：
- 已识别用户真正的 `core_blocker`；
- 没有用泛化建议替代具体动作；
- 关键机制都有识别信号和应对方式；
- 危险攻击和输出窗口清楚；
- 多阶段战斗没有混写；
- 推荐方案符合用户当前角色、装备、资源和限制；
- 配置问题已按需调用Build或配队规则；
- 视觉素材能帮助识别机制或站位，或已合理降级；
- 用户可以据此实际提高成功率并完成 `final_goal`；
- 关键事实、版本和视觉素材已通过 `retrieval.md`、`media.md` 与 `quality-check.md` 校验。
