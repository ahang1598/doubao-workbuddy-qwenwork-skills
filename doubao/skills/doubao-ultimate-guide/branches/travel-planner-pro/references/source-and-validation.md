当旅行计划依赖当前事实、预约、价格、规则、天气、交通或安全信息时，读取本文件。

## 信息源优先级

1. 政府和官方机构：签证、入境、海关、旅行提醒、公共卫生、道路关闭、国家公园、许可证。
2. 交通运营方：航空公司、机场、铁路、巴士/渡轮公司、地铁机构、收费道路、官方路线规划。
3. 景点和场馆运营方：开放时间、闭馆日、票价、年龄优惠、限时入场、行李规定。
4. 官方旅游局：城市通票、季节活动、街区概览、公共交通基础信息。
5. 地图和 LBS 服务：POI 位置、营业状态提示、驾车/公交/步行耗时、周边聚类和路线可视化。地图结果要和官方开放时间交叉核对。
6. 机酒门票平台：动态价格、库存、酒店区域、取消政策和用户近期反馈。价格只能写 `实查` 或 `参考`，并提醒锁价前会变。
7. 近期本地媒体和可靠旅行媒体：新开业、街区氛围、活动背景。
8. 评论和社交平台：小红书、大众点评、美团、携程、马蜂窝等只用于判断人流、服务稳定性、真实步行负担、常见骗局、餐厅稳定性、菜品形态、排队情况、点单搭配、近期差评点等定性体验。

不要把社区帖子当作法律规则、官方价格或开放时间的权威来源。

## 必须核验的项目

除非用户明确要求离线头脑风暴，否则需要核验：

- 签证、ETA/eTA、护照有效期、过境签、疫苗或健康表格。
- 预报范围内旅行的天气；较远期旅行至少核验季节气候。
- 核心景点的开放时间、闭馆日、停止入场时间、预约窗口和票价。
- 核心景点、博物馆、演出、跨城交通、签证/入境、酒店/热门餐厅的官方或可信预订入口；无法确认 exact URL 时至少给官方平台/小程序/地图搜索复查路径。
- 关键交通班次、末班车/末班船、机场到车站转场时间和缓冲。
- 出境游汇率和当地货币习惯。
- 安全问题：罢工、抗议、道路关闭、山火、洪水、台风、降雪、高海拔、高温、疾病提醒。
- 动态价格：机票、酒店、租车、高需求体验项目。
- POI 和路线耗时：景点/餐厅位置、跨区交通、公共交通末班、停车和步行距离。
- 酒店区域与取消政策：特别是节假日、演唱会、展会、樱花/雪季/暑期等高需求时段。

## 可靠度标注

在预算和推荐中使用这些标签：

| 标签 | 含义 | 示例 |
|---|---|---|
| `实查` | 来自官方/运营方/预订平台的当前具体数据 | 官方票价、当前火车票价 |
| `参考` | 近期但不保证实时的来源，或常见平台区间 | 酒店价格区间、餐厅人均 |
| `估算` | 没有直接来源时的合理推断 | 打车总价、小吃、杂费 |

## 信息冲突处理

- 官方来源优先于平台摘要。
- 运营方来源优先于博客攻略。
- 两个可靠来源矛盾时，说明冲突，并采用更稳妥的操作假设。
- 后果较高时，告诉用户出发前要复查的具体页面或动作。

## 引用和来源习惯

- 来源或引用放在对应事实附近，不要全部堆在文末。
- 对规则、价格、时间、预约限制、班次、警告和当前天气进行引用或标注来源。
- 天气信息不能只写“注意天气”。必须转成行程动作：晴天保留什么、雨天/高温/低温/大风删什么或替换什么、出发前多久复查。
- 预约/购票信息不能只写“提前预约”。必须写在哪里订、何时订、先确认什么、失败替代；能给真实 URL 时用 `<bookmark>` 放在对应模块附近。
- `<bookmark>` 只能放已确认真实可打开的 URL。禁止空链接、占位链接、example.com、猜测官网、凭印象编造的小程序网页链接。
- 如果只有小程序、公众号、App 或地图入口，且无法确认网页 URL，不要硬写 bookmark；写成执行路径，例如“打开微信搜索官方小程序：___”“打开大众点评/美团搜索：城市 + 店名/菜品/商圈”“打开地图搜索：___”。
- 美食模块可以使用美团、大众点评、地图或官方店铺入口，但具体餐厅 URL 必须真实可打开；不确定时只给平台搜索路径，不编店铺链接。
- 如果是基于来源做推断，要明确说“实际含义是...”或“我推断...”。
- 如果无法联网，说明“未能实时核验”，并给出最重要的出发前复查清单。

优先使用目的地当地语言，必要时加英文：

```text

[出发地] 到 [目的地] 火车 渡轮 巴士 时刻
[机场] 到 [车站] 转场时间 末班车
[国家] 签证要求 [护照国籍] 官方
[目的地] 天气预报 [日期]
[目的地] [月份] 台风 雨季 雪季 封路
[目的地] 常见骗局 安全 街区
[目的地] official tourism itinerary map
[景点名] access official transport parking
```

社区平台使用边界：

- 可以用来交叉验证哪些菜/店近期被频繁提到、实物长什么样、分量和排队情况。
- 不把单篇笔记当作权威结论；至少看多个近期结果，和点评/地图平台交叉判断。
- 不直接搬运无授权图片到飞书文档；可记录为参考来源，或据此生成风格化美食拼图/点单卡。

## 事实类型对应来源

| 事实 | 优先来源 | 不可替代来源 |
|---|---|---|
| 签证/入境 | 政府/使领馆/官方移民部门 | 社区攻略不可作为依据 |
| 开放时间/票价 | 景区/博物馆/官方票务 | 地图摘要和博客不可单独作为依据 |
| 预约/购票入口 | 官方网站/官方小程序/官方公众号/运营方票务 | 不可编造 URL；社区攻略不可作为唯一入口 |
| 交通班次 | 运营方/官方交通/票务平台 | 游记不可作为依据 |
| 路线耗时 | 地图/LBS + 官方交通说明 | 单篇游记不可作为依据 |
| 天气 | 气象服务/官方天气/可靠天气平台；远期用季节气候资料 | 旧游记不可作为天气依据 |
| 酒店价格 | 酒店官网/OTA 当前价格 | 旧攻略不可作为依据 |
| 餐厅体验 | 点评/地图/近期社区交叉判断 | 单篇种草不可作为唯一依据 |
| 安全提醒 | 政府/官方预警/当地权威媒体 | 社交平台只能辅助感知 |

## 引用密度

完整攻略不需要每句话都引用，但这些信息附近必须有来源或可靠度：

- 签证/入境、开放时间、门票、预约、交通班次、天气预警、安全提醒。
- 当前价格、热门酒店、租车、演出和一日游体验。
- 由于来源冲突而做出的保守判断。

美食、街区氛围、排队和避坑可用“近期平台反馈显示/多平台反馈”这样的表述，但不要伪装成官方事实。

## 周末与近期活动核验

用户提到本周末、下周末、未来一个月、近期活动、演出、展览、集市、球赛、夜游、优惠门票或 city walk 时，执行额外核验：

- 把相对时间转成绝对日期，并写入文档。
- 活动以举办日期为准，不以文章发布时间为准。
- 演出、球赛、展览、集市必须尽量核验时间、地点、票务/预约和交通。
- 过期活动删除；长期活动写清有效期或“覆盖出行窗口”。
- 如果活动信息单源、平台摘要不完整或票务不明，标注为 `参考`，并放入出发前复查。
- 不要为了丰富度编造活动。宁可写“未找到可靠近期活动”，再转为城市常规路线。

周末城市搜索模式：

```text
[城市] 本周末 活动 展览 演出 集市 2026年7月
[城市] 下周末 演唱会 球赛 场馆 票务
[城市] 博物馆 当前展览 预约 官方
[城市] 优惠门票 暑期 学生 夜游 官方
[城市] city walk 路线 老街 历史街区 地铁
[城市] 美食街 夜市 地铁 推荐 最近
[城市] 地铁 线路图 站点 出口 官方
```

## 多来源失败处理

任何关键事实不要因为一个来源失败就放弃：

| 失败项 | fallback |
|---|---|
| 官方页面打不开 | 查官方公众号/小程序/票务平台，并标注需复查 |
| 票价不一致 | 采用官方或售票页，其他写为参考 |
| 地图 POI 不确定 | 用官方地址或商场/场馆名交叉确认 |
| 酒店/机票价格查不到 | 给区间和复查路径，不写死 |
| 近期活动不足 | 补查本地媒体、文旅号、场馆排期；仍不足则改为常规路线 |

最终文档可写“来源状态”：已核验、部分核验、出发前复查。不要假装所有来源都成功。
