本文件合并了飞书旅行文档的内容/版式规范、CLI 创建工作流和表格 schema。它是旅行攻略的**唯一**飞书交付契约。SKILL.md 给 8 步流程和必填清单；这里给每一步的细则。

## 1. 执行原则（canonical，只说一次）

- 默认主交付物是**真实创建的飞书/Lark 旅行文档**，最终回复只给标题 + URL + 出发前复查项，**不粘贴正文**。
- 默认用 XML 富文本创建（XML 能稳定表达 callout/grid/checkbox/bookmark/语义色彩）；用户明确要 Markdown 或降级时才用 Markdown。
- **正文只写旅行攻略内容。** 工具版本、CLI 子命令、认证、权限、scope、token、fallback、替代方案、命令不可用等执行状态**只能出现在最终回复的失败说明里**，绝不写进正文。禁止在正文写“当前版本 lark-cli 无 auth 命令”“后续需考虑替代方案”“确认是否为预期情况”等内部状态。
- **正文禁止 HTML 表单标签。** 复选清单在 XML 里只能写 `<checkbox done="false">事项</checkbox>`；Markdown 降级稿才写 `- [ ] 事项`。不要写 `<input type="checkbox" />`、`<button>`、`<select>`、`<textarea>`、`<label>`、`<form>`，也不要把它们转义成 `&lt;input...&gt;` 放进正文。
- **XML 只用白名单组件。** 允许：`title/h1/h2/h3/p/b/i/br/callout/grid/column/table/thead/tbody/tr/th/td/checkbox/bookmark/blockquote/hr`。不要自造 `<card>`、`<section>`、`<timeline>`、`<badge>`、`<tag>`、`<panel>`、`<tabs>` 等标签；这些会原样露出。路线卡/美食卡/预算卡用 `callout + grid + table` 实现。
- 用 `--content @file.xml` 文件方式传内容，**不要**把 XML 内联进 `--content '<...>'`——引号/反引号/`$` 会被 shell 吃掉。
- 完整飞书攻略不搜图、不生图、不插图，必须同时满足**富文本结构底线**和**内容厚度下限**（见 §5），缺一不可。
- 动态事实（开放时间/票价/班次/天气/活动）必须核验或标注需复查；来源以 bookmark、blockquote 或复查动作就近呈现，**不要在文末加来源章节**。
- 文末不写“关于本攻略/由某 skill 生成/欢迎分享/祝你旅途愉快”等自我说明或营销尾巴。
- 不在正文暴露“部分内容由豆包生成/AI 生成”。即使平台自动加过这类提示，交付前也要删除。

## 2. 命令能力确认

执行飞书文档命令前，先读当前 CLI 帮助，确保参数与本机版本一致。**只检查实际要用的 `docs` 命令**；不要探测 `auth`、`skills` 等与正文无关的子命令：

```bash
lark-cli docs +create --api-version v2 --help
lark-cli docs +update --api-version v2 --help
lark-cli docs +fetch --api-version v2 --help
```

若某条帮助不可用，改用当前环境已暴露的飞书文档工具、`lark-cli docs +create --help` 或本文件 XML 写法继续创建。禁止把工具兼容性问题写进正文。

## 3. 创建流程（7 步，第 6 步是内容门控）

1. **解析需求**：目的地、天数、日期、同行人、预算、偏好。缺失但可合理假设时继续，不要频繁追问。
2. **核验时效信息**：开放时间、预约规则、交通班次、天气、节假日、签证/入境、动态价格。规则见 `source-and-validation.md`。
3. **生成正文草稿**：标题、核心结论、天气/季节策略、路线总览、分日行程、住宿交通、美食、预算、预订入口、风险备选、出发前复查。第一屏不重复标题；来源就近放。优先用 XML 表达富组件，组件必须围绕路线、天气、预订、认路、点单、预算和风险服务。
4. **设计富文本结构**：用 callout 承载结论/风险，用 grid 承载对比，用 table 承载行程/预算/预订，用 checkbox 承载复查清单，用 bookmark 承载官方/可信入口。不要创建图片清单，不要搜图、生图、下载图或写图片锚点。
5. **XML 草稿只写正文**：XML 正文只写正常旅行内容；不要写 `<img href="外部URL"/>`，也不要写 `<!-- 插图位置 -->`、`caption=`、`anchor=`、`source=`、`image-plan.tsv` 等内部字段。
6. **内容门控（硬门控）**：创建飞书文档前逐项确认：路线顺路；每天有主线/交通步行/用餐落点/预约排队/可删减项；天气策略能影响行程；预算和预订入口闭环；主要 H2 不薄；富文本底线达标；没有图片流程痕迹。雨天、疲劳、堵车、预约失败等只在确实会影响主线时轻量写 1-2 个应对，不展开成大模块。
7. **创建飞书文档**（XML 只带正常正文，不带图、不带图片注释）：
   ```bash
   lark-cli docs +create --api-version v2 --as user --doc-format xml --content @outputs/[目的地]-[yyyy-mm]/[目的地]-[天数]天飞书导入稿.xml
   ```
   拿到真实 URL。若失败：不要把错误写进文档；在聊天回复说“本次未能创建飞书文档，原因：___，可重试：___”，给本地 .xml 路径。
   创建后 `lark-cli docs +fetch --api-version v2 --doc "文档URL" --scope outline` 确认 outline 清晰、标题层级正确、主要模块完整；如能回读正文，检查没有 XML/HTML 标签、内部字段或图片流程痕迹泄漏。

## 4. 清晰路书骨架（先清晰，再好看）

飞书攻略可以多彩，但不能乱。创建前先确认正文已经形成一条清楚的“路书脊梁”，再用 grid、callout、table、checkbox、bookmark 做结构层次。

### 必须具备的清晰度

- **第一屏直接答怎么走**：推荐路线、住宿/落脚区域、适合谁、最大风险要在开头看得到；不要重复标题、默认假设或大段目的地介绍。
- **天气不是装饰**：有具体日期且在预报范围内，写温度、降雨/高温/低温/风和对应调整；无日期或远期，写季节气候区间、雨季/台风/雪季/高温/花期和 48 小时复查。
- **路线总览能扫读**：每天的主区域、住宿地、核心安排和预订风险必须清楚。用户应能看出为什么先去 A 再去 B。
- **每天是真正能执行**：每个 Day 必须包含时段顺序、交通/步行、用餐落点、预约/排队、可删减项。若当天存在明显天气、堵车、疲劳、预约失败风险，再补 1-2 条轻量替代；不要让兜底内容盖过主路线。
- **预订入口就近出现**：核心景点、演出、博物馆、酒店区域、跨城交通、签证入境、热门餐厅/排队平台等，能确认真实可打开 URL 时才用 `<bookmark>` 放在对应模块附近。不要只写“提前预约”；不要用 example.com、空链接、占位链接或猜测链接；不确定 exact URL 时写官方小程序/公众号/地图/票务平台的搜索路径，并放入复查动作。
- **模块有阅读节奏**：主要模块按“取舍解释 → 执行动作/表格 → 变化处理”组织。表格前后要有自然语言解释；callout 不连续堆超过 2 个；富文本组件不能替代路线细节。

### 视觉混乱的处理

- 连续多张表、多个 callout 或多个 grid 会让攻略像素材堆。每个大模块最多连续 2 个同类组件，中间用 1–3 句取舍或执行说明串起来。
- “天气策略”“预订入口”“风险替代”优先用黄色/灰色 callout、checkbox、bookmark、短表承载；“路线结论”“今日主线”用蓝/绿 callout；不要把所有颜色都用于装饰。
- 若某个 H2 下只有一句话或一张薄表，合并到相邻模块或补充具体执行，不留空壳章节。
- 不用图片时，更要用路线总览、Day 卡、天气策略、预订入口、预算矩阵、风险备选和 bookmark 把信息讲清楚。

## 5. 内容与版式平衡（无图片版两条硬底线）

### 富文本结构底线

完整文档至少包含：

- ≥3 个语义色彩 callout（蓝=结论/路线、绿=推荐/顺路、黄=风险/预约/复查、灰=来源/边界），不同含义不同色，不同色堆叠。
- ≥1 个 grid/分栏（住宿区域对比、保守/进取路线、天气影响方案、场景化 Q&A）。
- ≥1 组 `<checkbox done="false">...</checkbox>`（出发前复查/预订清单/证件打包）。不要使用 HTML `<input type="checkbox" />`。
- ≥1 个 bookmark（官方票务/交通/地图/酒店/签证入口，必须是真实可打开 URL，非 example.com/空链接/猜测链接）或 blockquote。
- 蓝/绿/黄/灰中 ≥3 类语义色彩。
- ≥2 个场景卡片（路线决策卡、Day 主线/撤退卡、住宿取舍卡、美食点单卡、预算预订卡、风险补救卡、Q&A 卡）。

不合格形态：正文主要由 `<p>`/`<table>`/`<hr/>`/`<checkbox>` 构成，几乎没有 callout/grid/bookmark/blockquote/语义色彩。横线和表格只能承载，不能替代结构层次。

### 内容厚度下限

- 每个核心章节先有 1–3 句解释或取舍，再放表格/清单/组件。
- 表格不能成为正文主体。多日行程可以有表格，但每个 Day 和关键模块必须有自然语言取舍、现场执行和调整方式。
- 每个 Day 至少包含：今日主线、时间段安排、交通/步行、用餐落点、预约/排队提醒、可删减项。撤退点、雨天/疲劳/预约失败备选只在当天确实相关时写成短提示，不要每一天机械铺满。
- 完整攻略必须有天气或季节策略；有具体日期时优先查天气预报，无具体日期时写月份/季节风险和 48 小时复查动作。
- 完整攻略必须有预订/预约入口或复查路径。核心景点、交通、酒店、演出、签证/入境等至少给 1 个真实 `<bookmark>`；若没有可靠 URL，写明从官方小程序/公众号、地图、票务平台或 App 内搜索什么关键词复查，不能编造链接。
- “怎么玩”必须落到动作层：先去哪、怎么过去、在哪里吃、什么时候预约、现场删什么；下雨/太热/人多/堵车等只在影响主线时补轻量调整。
- 全文项目符号列表连续最多 2 组；超 5 条优先改成表格/grid/checkbox/callout。
- 主要 H2 至少有一个可执行组件和一段取舍解释；只有表格没解释或只有解释没落地动作，都不合格。

## 5. 文档结构（按场景变，不固定目录）

稳定的是信息覆盖：首屏结论、路线总览、分日行程、住宿交通、美食、预算预订、风险备选、复查清单。**不要所有攻略套同一目录。** 不同场景不同开头和重心：

- 城市初访：先给“第一次去最省心路线”和住宿区域，再展开经典景点取舍。
- 美食主题：先给“吃什么和住哪里最顺路”，再按街区/时段/菜品组织。
- 亲子老人：先给“舒适节奏和风险边界”，再安排低步行、午休、室内备选。
- 自驾路书：先给环线/落脚点/驾驶强度，再展开里程、路况、停车、补给。
- 出境自由行：先给证件入境、支付通信、城市间交通，再展开每日路线。
- 中转短停：先给能否出站/进城和误机风险，再给保守版/进取版。

`<title>` 不要默认 `XX旅游攻略/XX旅行计划`；用路线/路书/地图/雷达/日历/清单/时间账/决策表/手册/玩法等形态。标题与 H2 规则见 `scenario-and-richness.md`。正文开头不复制标题、不写“默认假设/当前假设”；第一屏直接进结论卡、路线摘要、取舍说明或风险提醒。

## 6. 表格 schema（可直接用，替换内容）

| 用途 | 列 |
|---|---|
| 路线总览 | 天数/日期 \| 住宿地 \| 主区域 \| 核心安排 \| 预订风险 |
| Day 时段 | 时间 \| 安排 \| 交通/步行 \| 费用/预约 \| 为什么这样排 |
| 住宿区域 | 区域 \| 适合谁 \| 通勤逻辑 \| 优点 \| 缺点 \| 不建议情况 |
| 美食 | 区域 \| 代表食物 \| 适合时段 \| 人均 \| 注意 |
| 交通段 | 路段 \| 推荐方式 \| 时间 \| 费用 \| 注意 |
| 预算三档 | 类别 \| 节省型 \| 舒适型 \| 升级型 \| 可靠度（实查/参考/估算） |
| 预订时间线 | 时间（30–60 天前/7–14 天前/48 小时前/当天） \| 要做什么 \| 原因 |
| 天气策略 | 天气/季节信号 \| 影响 \| 原计划 \| 替代玩法 \| 复查动作 |
| 预订入口 | 项目 \| 官方/可信入口或平台搜索路径 \| 何时订 \| 需确认 \| 失败替代 |
| 风险备选 | 风险 \| 可能影响 \| 更稳妥做法 |
| 成本矩阵 | 方案 \| 总成本 \| 现金支出 \| 便利度 \| 风险 \| 适合谁 \| 下一步 |
| Day 卡 | 今日主线 \| 今日高光 \| 可删减项 \| 撤退点 \| 备选 |

可靠度标签：`实查`（官方/运营方/预订平台当前数据）、`参考`（近期但不保证实时）、`估算`（无直接来源的推断）。动态价格必须提醒锁价前会变。

## 7. 飞书组件建议

- `<callout>`：首屏结论、最大风险、天气/预约提醒。按语义用色。完整文档 ≥3 个。
- `<table>`：路线总览、分日计划、预算、预订时间线。
- `<grid>`：住宿区域对比、美食图鉴、保守/进取路线、雨天/晴天方案、Q&A。完整文档 ≥1 个。
- `<checkbox>`：出发前复查、预订清单、证件打包。
- 不使用图片：不要搜图、生图、下载图、写 `<img>`、创建 `image-plan.tsv` 或调用 `+media-insert`。
- `<bookmark>`：官方票务/交通/地图/酒店/签证入口（真实可打开 URL，非 example.com、空链接、猜测链接）。美食可用美团/大众点评/地图的真实入口；具体餐厅 URL 未确认时，不写 bookmark，改写“打开大众点评/美团搜索：城市 + 店名/菜品/商圈”。
- `<blockquote>`：动态价格提示、安全边界、适用前提。
- `<hr/>`：大主题切换时用，长文档 1–3 次。
- 标签式短句：Day/餐饮/风险旁加 `推荐保留`/`可删减`/`雨天替代`/`需预约`/`高排队风险` 等。

不要全篇有序列表，也不要全篇表格。

不要自造组件标签。以下会露出到正文：

```xml
<card title="主食小吃类">担担面、钟水饺、甜水面</card>
```

应改成真实飞书组件：

```xml
<grid>
  <column width-ratio="0.5"><callout emoji="🍜" background-color="light-green"><p><b>主食小吃类：</b>担担面、钟水饺、甜水面，适合午餐或高步行日。</p></callout></column>
  <column width-ratio="0.5"><callout emoji="🥬" background-color="light-blue"><p><b>正餐硬菜类：</b>老妈蹄花、开水白菜、清蒸江团，适合晚餐补足蛋白。</p></callout></column>
</grid>
```

### 多彩但克制的 XML 示例（只展示组件搭配，不是固定目录）

```xml
<callout emoji="🧭" background-color="light-blue" border-color="blue">
  <p><b>路线结论：</b>住在老城边缘，白天按片区吃逛，晚上只保留近距离夜宵，避免跨区找饭。</p>
</callout>
<grid>
  <column width-ratio="0.5">
    <callout emoji="✅" background-color="light-green" border-color="green"><p><b>优先保留</b><br/>最顺路的 2 个高光点。</p></callout>
  </column>
  <column width-ratio="0.5">
    <callout emoji="⚠️" background-color="light-yellow" border-color="yellow"><p><b>现场删减</b><br/>排队/天气变差/疲劳时删掉重复体验。</p></callout>
  </column>
</grid>
<hr/>
<checkbox done="false">出发前 48 小时复查门票/天气/交通。</checkbox>
<bookmark name="中国铁路 12306" href="https://www.12306.cn/"></bookmark>
```

无图片富文本骨架示例（保证颜色/分栏/信息卡足够清晰）：

```xml
<callout emoji="🧭" background-color="light-blue" border-color="blue">
  <p><b>最顺路线：</b>先把跨区移动压到 1 次以内，核心体验集中在两个相邻片区。</p>
</callout>
<grid>
  <column width-ratio="0.5"><callout background-color="light-green" border-color="green"><p><b>优先保留</b><br/>主体验、顺路餐饮、交通最稳一段。</p></callout></column>
  <column width-ratio="0.5"><callout background-color="light-yellow" border-color="yellow"><p><b>现场删减</b><br/>排队>40 分、天气变差、疲劳时删重复体验。</p></callout></column>
</grid>
<blockquote>动态信息以官方票务、交通平台和天气预报为准；出发前 48 小时复查。</blockquote>
<checkbox done="false">确认核心景点预约、营业时间和闭馆日。</checkbox>
<bookmark name="中国铁路 12306" href="https://www.12306.cn/"></bookmark>
```

## 8. 无图片版信息组件

没有图片时，必须把原本图片承担的识别、记忆和决策功能转成结构化信息：

- **路线识别**：用路线总览表、交通段表、住宿区域 grid、地图/官方入口 bookmark 承载。
- **美食点单**：用菜品表写清口味、分量、人均、适合时段、忌口、替代；美食是主线时用 grid 分成早餐/正餐/小吃/夜宵。
- **天气变化**：用天气策略表和黄色 callout 写清晴雨冷热如何影响主线；只保留最关键调整，不把兜底写成主内容。
- **预算判断**：用预算三档表和成本矩阵，不写空泛“丰俭由人”。
- **预订复查**：用 checkbox + bookmark + blockquote，就近放在景点、交通、酒店或签证模块。
- **现场取舍**：每个 Day 必须有可删减项；撤退点、雨天/疲劳/预约失败备选按当天风险轻量出现。

正文和本地输出里不得出现：`<img>`、图片说明、图片来源、图片锚点、`image-plan.tsv`、`media-insert`、`image_gen`、`生成图`、`搜图`、`插图位置`。

## 9. 降级交付

以下情况降级：`lark-cli` 不存在；未登录/权限不足/scope 缺失且无法在任务内修复；网络或平台错误导致创建失败；用户明确不要在线文档。

降级必须包含同结构 Markdown 正文和必要复查清单，不提供 `visuals/` 图片文件夹，不虚构图片文件。最终回复明确说明“未创建飞书在线文档”，给本地文件路径。

- [ ] 达到无图片版富文本底线（≥3 callout、≥1 grid、≥2 table、≥1 checkbox、≥1 bookmark/blockquote、≥3 类语义色、≥2 场景卡）？
- [ ] 正文没有图片承诺、图片说明、图片来源、图片锚点或媒体插入流程？
- [ ] 没有 example.com/placeholder 占位 URL？
- [ ] 文末没有“来源/信息来源/图片与信息来源/参考资料”等来源章节，只有复查/预订/仍需确认/补救？
