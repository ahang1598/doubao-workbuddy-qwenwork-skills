当用户需要图片、海报、长图、手绘地图、豆包可用视觉卡片、社交平台旅行图、插画行程、美食地图、避坑卡、预算卡，或要求参考图片风格生成旅行视觉资产时，读取本文件。

不要在基础行程事实稳定前生成图片。旅行规划的准确性优先，图片只是派生交付层。

图片不是装饰层，而是用户服务层。任何视觉资产都必须在内部对应一个明确价值：认路、识别、决策、点单、避坑、预算判断或记忆强化。最终成品不要暴露内部字段标签或图片选择逻辑。

## 执行条件

完整飞书旅行攻略必须进入图片任务设计。独立图片包仍然只在用户明确要求时交付，但文档内至少要有 1 个服务核心决策的图片或生成视觉图。图片不是封面配额，也不是每日配图配额；它应放在最能帮助用户执行的位置。

图片采用双轨策略：

- **真实对象优先搜图**：目的地风景、景区外观、古城街巷、博物馆入口、季节景观、海岛/草原/山景、代表菜品、夜市摊位、酒店区域和交通枢纽，优先搜索官方/开放授权/可标注来源的真实图片。用户需要知道“长什么样”“值不值得去/吃”“怎么识别入口”“菜品是不是适合自己”时，不要直接用抽象生成卡替代真实图。
- **抽象结构优先生图**：路线顺序、预算构成、现金/积分对比、交通衔接、避坑提醒、晴雨两案、中转时间账、亲子低步行、停车补给、预订清单，优先生成信息图、路线卡、预算卡、风险卡或时间轴卡。
- **搜不到再生成**：真实对象找不到可用图片或授权不稳时，生成风格化替代图/图鉴卡，并在图注写“生成图”；不要搬运版权不明平台图片，也不要用无关风景图凑版面。

独立图片交付的典型表达：

- 图片、海报、长图、视觉攻略、图文攻略、手账、插画、路线图、手绘地图。
- 豆包、小红书、朋友圈、公众号、封面、分享图、种草图。
- “像这张图一样”“参考这个风格”“做成图”“生成可分享图片”。
- 用户要求飞书文档、HTML、PDF 之外，还需要单独图片物料。

默认处理规则：

- 如果用户只说“给我写攻略 / 怎么玩”，不要自动生成固定图片集合；但必须选出 1 个最有用的图片任务。第一次去、风景目的地、美食主题通常优先搜真实景点/风景/美食图；自驾、短停、预算、亲子老人、交通复杂时通常优先生成功能图。
- 不存在默认最小图片集合。封面/代表图、路线图、每日图、美食图、避坑卡都按用户需求和旅行决策价值触发；完整攻略只要求至少 1 个有效视觉资产。
- 复杂多日路线、节假日预算路线、第一次去某地、或正文包含多个景点/美食/住宿区域时，最低不是“1 张任意图”，而是“视觉覆盖核心决策”。如果唯一图片只是预算饼图、价格图或泛信息图，必须再补一个路线/地图/区域、景点/街区/酒店区域或美食/点单视觉锚点。否则用户会觉得有图但没帮助。
- 如果当前无法搜到合适图片，必须生成一张功能型视觉图；如果生图工具不可用，生成程序化图卡、地图/官方页面 bookmark 配图说明，或给本地可插入图片文件路径，不能用无关图片凑数。
- 用户明确要求独立图片包时，再基于已确认行程数据生成图片文件或图片 prompt。
- 一旦图片需求清单中列出某张图，就必须生成/搜集/合成并插入正文对应位置；不要只在文末列需求或统一堆图。
- 如果无法生成或插入任何图片/视觉卡，完整飞书攻略不应交付为最终版本；先降级为“需补图”的本地稿或可插入视觉文件，不要假装图文已完成。禁止写“图片说明：图片来自公开旅游资料”，也不要新增文末来源章节。

## 视觉类型

| 类型 | 适用场景 | 默认比例 |
|---|---|---|
| 总览插画地图 | 整体路线、2-5 天城市漫游、美食地图、景区环线 | `2:3` 或 `3:4` |
| 单日行程时间轴 | 单日时间、景点、餐饮、提醒 | `2:3` 或 `3:4` |
| 美食拼图 / 图鉴 / 地图 | 多个重点菜、去哪吃、围绕美食街区的路线 | `2:3` |
| 预算与住宿卡 | 性价比对比、交通/住宿/预算摘要 | `3:4` |
| 避坑卡 | 宰客、闭馆、排队、低性价比景点、替代方案 | `3:4` |
| 封面 / 分享海报 | 行程标题、核心路线、情绪钩子 | `3:4` 或 `4:5` |
| 长图攻略 | 适合手机阅读的多区块纵向攻略 | `9:16` |
| 住宿区域对比卡 | 第一次去、亲子老人、预算敏感 | `3:4` |
| 交通衔接卡 | 机场/高铁站到市区、自驾环线、中转短停 | `3:4` |
| 晴雨两案卡 | 雨季、海岛、户外、亲子 | `3:4` |
| 彩色路线卡 | 无需真实图片但需要扫读路线、主线、撤退点 | 飞书 callout/grid |
| 标签式点单卡 | 美食主题、外地人不知道怎么点 | 飞书 table/grid |
| 出发前复查卡 | 动态信息较多、近期活动或门票预约 | checkbox/callout |

## 尺寸与版式规范

在同一份飞书攻略中，先确定图片系统，再生成或插入图片。图片不是随机素材集合，必须像同一套路书组件。

推荐像素：

| 角色 | 固定像素 | 用法 |
|---|---:|---|
| 封面图 | `1600x900` | 首屏大图，仅 1 张 |
| 横版路线/区域图 | `1200x900` | 路线总览、住宿区域、交通衔接 |
| 竖版 Day 卡 / 避坑卡 | `1080x1440` | 每日时间轴、预算卡、提醒卡 |
| 方形图鉴缩略图 | `1024x1024` | 景点图鉴、美食图鉴、同一 grid 内的小图 |
| 长图攻略 | `1080x1920` | 仅用户明确要手机长图时使用 |

约束：

- 同一文档最多选择 2-3 种图片比例：封面一种、正文卡片一种、图鉴缩略图一种。不要横图、竖图、方图随意混排。
- 同一组图必须完全同尺寸：多个 Day 卡都用 `1080x1440`；多个美食/景点格都用 `1024x1024` 或都用 `1200x900`。
- 先确定文档视觉系统：封面负责目的地印象，路线图负责认路，Day 卡负责当天主线和撤退点，美食图鉴负责点单，预算/避坑卡负责决策。不要每个章节机械配一张风景图。
- 真实照片比例不同，必须先中心裁切、留白裁切或合成为图鉴；不要把原图大小直接交给飞书。
- 横图适合城市印象、路线和住宿区域；竖图适合时间轴和信息卡；方图适合图鉴。不要让一个竖版信息卡夹在横版照片组中间。
- 多图同屏时使用 grid/拼图，不要连续插入大小不同的单图。
- 文字密集的信息卡要优先程序化生成或严格控制字数，避免小字缩放后不可读。

完整攻略优先生成最小有用集合：

1. 先生成最能解决用户核心问题的一张：路线图/美食图鉴/预算卡/中转时间账/亲子低步行卡。
2. 用户要求系列图、长图、手账或内容确实复杂时，再按天生成单日卡。
3. 封面只在目的地第一印象、分享传播或用户明确需要时生成；否则把唯一图片放到路线、美食、住宿、预算或风险模块。

不要按章节机械配图。美食、景点、住宿图片必须和具体判断绑定；如果只是让页面“看起来丰富”，改成更有信息量的路线图、点单卡、避坑卡或不生成。美食章节尤其不能用一张单菜大图代表多个推荐菜。

场景优先级：

- 城市初访：总览路线图、住宿区域对比卡、Day 时间轴。
- 美食主题：美食图鉴/地图、点单卡、排队避坑卡。
- 预算主题：预算卡可以出现，但若文档同时安排多日路线和美食景点，预算卡不能是唯一图片；还要补路线卡、地图 bookmark、景点/美食图鉴或官方入口链接卡。
- 亲子老人：低步行路线卡、厕所/午休/室内备选卡。
- 自驾路书：环线地图、驾驶日卡、补给/停车/风险卡。
- 出境自由行：证件支付通信卡、城市间交通卡、当地语言地点卡。
- 中转短停：时间账卡、保守/进取路线对比卡。

视觉丰富度要求：

- 有图片不等于视觉效果好。优先保证统一比例、统一图注、同类图同尺寸、图片和正文相邻。
- 如果图片数量少，用高信息量视觉卡补：路线方向卡、今日主线卡、点单卡、晴雨两案卡、预算决策卡。
- 图片很少时，唯一图片必须放在最能帮助执行的位置，而不是默认放预算章节。多日路书通常先考虑路线/区域图或地图入口；美食明显时考虑美食图鉴；景点识别重要时考虑景点/街区真实图或官方图片页 bookmark；预算是核心痛点时才把预算卡作为主图，但仍需用 bookmark/地图入口补足旅行识别。
- 如果无法稳定插入真实图，不要承诺“图文攻略”；改用地图/官方页面 bookmark、生成信息卡或出发前复查卡。
- 图片不能压缩正文。插图后仍必须有交通、用餐、预算、预订、备选和取舍说明。
- 如果真实图片不适合，也不要为了视觉效果硬塞无关照片；生成路线卡、点单卡、预算卡、晴雨两案卡或住宿区域卡，并继续用 callout、grid、table、checkbox、bookmark 做文档层次。
- 视觉要更丰富多彩时，优先增加“语义色彩 + 卡片 + 标签 + 分栏”，而不是增加无关图片。飞书里可用蓝/绿/黄/灰四类语义色，但同一文档不要超过 4 类。
- 每个视觉卡都必须承载信息：路线卡写顺序和撤退点，点单卡写菜品和忌口，预算卡写价格可靠度和预订动作，风险卡写触发条件和替代方案。

图片较大或数量较多时，优先合成图鉴/拼图/地图卡，或在飞书文档中使用 2 列/3 列分栏展示。不要因为图片大就删掉已规划图片，也不要把它们挪到文末。

## 兜底视觉

真实图片不稳定时，优先使用更可控的视觉替代：

- 路线图无法精确绘制时：生成“路线方向卡”或放可点击地图链接卡。
- 景点图找不到可用图时：放官方景区/旅游局页面 bookmark，并在正文说明查看入口。
- 美食图无法授权时：生成插画式点单卡或多菜品文字图鉴，不搬运平台图。
- 图片工具不可用时：不要声称有图片；用可点击官方/地图/图片页面 bookmark 和对应章节的“查看图片/地图入口”兜底，并在最终回复说明本次没有生成位图。
- 想提升视觉但真实图片不必要时：生成信息图卡，同时用彩色 callout、两列 grid、短标签、checkbox、bookmark 和 hr 形成图文节奏；不要把“无真实照片”理解成“无图片”或“只能纯文字”。

兜底视觉也必须放在对应章节附近，不能集中到文末。

## 数据要求

写图片 prompt 前，先整理精简的 `visual_data` 清单：

- 目的地和路线标题。
- 日期或 Day 标签。
- 内部视觉目标：这张图解决哪类阅读或决策问题。该字段只用于生成前判断，不写进成品文案。
- 需要出现在画面上的精确文字。
- 已核验或已标注为估算的点位、餐食、价格、门票和提醒。
- 目的地视觉地标和本地元素。
- 绝不能被改写的关键信息。

图片里的文字只能来自这份清单。不要为图片编造价格、地址、排名、开放时间或“必吃”结论。

## 文字渲染规则

图片模型容易把密集文字画歪。可见文字必须短而可控：

- 每张图优先控制在 6-10 个文字块。
- 需要渲染的中文使用 `“”` 明确包裹。
- 避免小段落、完整地址和过长餐厅说明。
- 详细事实放在 Markdown、HTML 或飞书文档里；图片只做视觉摘要。
- 必须精确的信息要放大、独立呈现。
- 不使用 `XX`、`某店`、`标题文案`、`若干文字` 等占位符。

如果视觉图需要大量准确文字，应优先用 HTML/SVG/幻灯片式模板程序化生成，而不是只依赖文生图。

## 旅行手绘风格

参考潮州示例图时，用通用风格语言描述，不要直接复制某张图：

- 暖色羊皮纸背景，旅行手账拼贴感。
- 手绘墨线和水彩插画。
- 本地建筑、河流、桥、街巷、食物水彩小图。
- 虚线步行路线、指南针、印章、纸标签、纸胶带、票签式标题。
- 柔和低饱和大地色，赤陶色点缀，鼠尾草绿和江河蓝。
- 信息密度高但可读，像编辑整理过的旅行笔记，不要现代 App 界面感。

不要提及或复制参考图里的水印。

## Prompt 模板

每张图片写一个完整 prompt。若图片工具支持独立传入比例，比例不要写进 prompt。

```text
生成一张旅行手账风中文信息图，主题是“{标题}”。画面为暖色羊皮纸背景上的手绘水彩拼贴，中间是{目的地/路线}的简化手绘地图，使用虚线步行路线串联“{点位1}”“{点位2}”“{点位3}”。四周放置{食物/景点/预算/避坑}小卡片，每张卡片有手绘图标和短文字。画面必须清晰呈现这些文字：“{文字1}”“{文字2}”“{文字3}”。整体像旅行手账、旧地图、城市漫游攻略，细腻水彩、墨线描边、纸胶带、印章、指南针装饰，信息密度高但留白均匀，中文字体像手写标题和清晰宋体注释，无水印，无乱码。
```

## 常见旅行视觉配方

### 总览地图

适用于“3 天 2 夜攻略”“古城美食地图”“步行路线图”。

应包含：

- 目的地和天数标题。
- 简化地图，不要求导航级精确。
- 4-8 个带标签的地标或美食点。
- 虚线路线和指南针。
- 底部 2 个精简信息卡：交通、住宿或预算。
- 地图不要求导航级精度，但不能误导方向；精确导航交给地图链接或正文。

### 单日时间轴卡

适用于 “Day 1 / Day 2 / Day 3”。

应包含：

- 票签式标题。
- 左侧竖向时间轴。
- 4-6 个时间块。
- 1 个避坑提醒。
- 1 个餐饮或预算提醒。
- 2-4 个和当天相关的小插画。
- 标出“可删减项”或“雨天替代”，让图片承担决策价值。

### 美食攻略图

适用于“美食地图”“美食清单”“菜市场扫货”“夜市吃什么”。

应包含：

- 围绕地图或网格摆放的 3-6 个菜品小图；若正文表格列了多个重点菜，视觉上要覆盖这些重点菜。
- 每个菜品：名称 + 区域 + 点单/口味/忌口/场景中的一条有用提醒。
- 只有在行程数据支持时，才使用“必吃”“避坑”等强标签。

不要只生成单个菜品大图来搭配整张美食清单。若要突出一道菜，必须做成点单卡，并且正文里不要让它代表其他菜。点单卡包含：

- 这道菜是什么口味或形态。
- 适合什么时段、什么路线、几个人吃。
- 推荐搭配或替代选择。
- 不适合谁：忌口、带刺、辛辣、油腻、排队久、价格波动等。
- 一条明确避坑提醒。

多菜品美食图优先使用这些结构：

- `美食图鉴`：每个重点菜一个小图 + 一句点单提醒。
- `美食地图`：按街区/路线标注去哪吃，适合城市漫游。
- `一餐组合卡`：例如“烧麦 + 咸奶茶”作为早餐组合，“手把肉 + 奶茶”作为正餐组合。
- `避坑对比卡`：适合解释价格、分量、排队和口味差异。

可用小红书、大众点评、美团等平台核对近期实拍形态、热门搭配和差评点；未授权平台图片不要直接嵌入，改为生成插画拼图或只记录来源参考。

### 避坑卡

适用于“避坑”“不要去哪里”“排队/宰客/闭馆”。

应包含：

- 清晰标题。
- 3-5 条提醒。
- 每条提醒配一个更稳妥的替代方案。
- 视觉可用便签、印章、红色感叹号、检查清单等形式。

### 住宿区域对比卡

适用于第一次去某城市、带娃/老人、预算敏感或夜间活动明显的目的地。

应包含：

- 2-4 个区域。
- 每个区域：适合谁、通勤逻辑、优点、主要缺点。
- 不写具体酒店价格，除非已经核验并标注为参考。

### 交通衔接卡

适用于机场/高铁站到市区、城市间转场、自驾环线和中转短停。

应包含：

- 起终点和推荐方式。
- 大致耗时、缓冲和风险。
- 保守替代方案。
- 精确班次放正文，不在图片里写密集小字。

## 质量检查

交付前检查：

- 每个可见文字是否都来自行程数据？
- 关键信息是否足够短，适合图片清晰渲染？
- 图片类型是否真正解决用户的旅行决策？
- 是否能在内部说清每张图的读者价值？不能说清就删除或改成信息卡。
- 美食视觉是否覆盖美食表中的多个重点菜，而不是只放一张单菜大图？
- 完整攻略是否至少有 1 个图片或生成视觉图？图片需求清单中的每项是否都已产出，并插到对应正文位置？
- 是否没有把所有图片集中放在文末？
- 如果图片一张都没有，是否已暂停最终交付或补做生成视觉图，而不是删除图片承诺并假装完成？
- 成品文案是否没有出现内部字段标签或图片选择逻辑？
- 视觉元素是否有目的地特征，而不是泛泛旅游元素？
- 不确定信息和动态价格是否避免进图，或已标注为估算？
- 图片是否无水印、无伪造 logo、无未经支持的平台宣传语？
- 是否避免了“欢迎分享”“祝旅途愉快”“本攻略由...生成”等宣传式或自我说明式尾巴？
