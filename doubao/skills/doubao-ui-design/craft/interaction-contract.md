# 移动端交互合同：九条

> **决定首屏长什么样之前不用读它；写第一个按钮之前必须读完。** 约 2 秒。
>
> 这一份的来源很具体：用户拿 `gold/h5-qq2026`（QQ 2026 年度盘点）当金标准，
> 逐条点名了它做得好的地方，然后问了一句——
>
> > **「上述交互优点能否在其他产品里也可以增加，让移动端 h5 的交互更加精美」**
>
> 答案是能。因为这九条讲的全是**「控件和内容怎么响应状态」**，与题材无关。
> 一份年度报告和一个咖啡点单首页，用的是同一套。
> 下面每条都给两种落法：**叙事 H5** 与 **产品界面原型**。

---

## 先说清楚一件事：**不要照抄 QQ 的机箱**

用户在这一条上说得很直接：

> **也不能抄 QQ 的，有些 app 没有 QQ 年终报告顶部和底部的这些按钮。
> 每个产品不一样，不能完全一模一样抄。**

他是对的，而且这正是最容易走歪的地方。下面九条是**机制**，不是**形式**：

| 机制 | ❌ 抄形式 | ✅ 落到你这个产品上 |
|---|---|---|
| 位置表达 | 每个产品都塞一条分段进度条 + `05 / 10` | 首页 → 底部 tab 的选中态；列表 → 分页器；表单 → 步骤条；轮播 → 圆点 |
| 主操作在拇指区 | 每个产品都放一条「上一页 / 继续 / 分享」 | 电商 → 底部「加入购物车」；工具 → 悬浮主按钮；信息流 → 主操作**就是内容本身**，底部 tab 就够了 |
| 控件响应状态 | 每个按钮都写「再看一遍 ↺」 | 提交按钮的加载/完成态；收藏的已收藏态；展开的收起态 |
| 把等待做成内容 | 每个产品都做一段插卡开机动画 | 产品界面用**骨架屏**；开场仪式只属于叙事型 |

**门也是这么写的。** `check.py` 的 `interaction-contract` 只查
「有没有位置表达」「主操作够不够得着」，**不查它长什么样**：
一组带选中态的同级元素算，一个 `N / M` 页码也算；
贴底的固定条里有可点元素算，最大的可点元素在下半屏也算。

骨架也分了两份，就是为了不给"套错形状"留机会：

| 形态 | 骨架 | 里面有什么 |
|---|---|---|
| 产品界面 | `skeletons/app.html` | 取景框 · 状态栏 · 顶部栏 · 连续内容流 · 底部 tab · toast · 骨架屏 |
| 叙事 H5 | `skeletons/h5.html` | 取景框 · 状态栏 · **分屏引擎 · 页码 · 分段进度 · 三键底栏** · toast · 开场壳 |

**`skeletons/app.html` 里的底部 tab 也是可以删的**——工具类 App 常常没有 tab，
只有一个悬浮主操作。删了不违反任何门。

---

## 为什么是九条而不是"参考 gold"

这九条里有六条骨架里已经有了，另外三条（末页状态 / Toast / 开场仪式）
只存在于参照案例的源码里 —— 只有翻源码的人才拿得到。那是运气，不是机制。
所以三条补进 `skeletons/h5.html`，九条写成这一份。

`check.py` 的 `interaction-contract` 门量其中五条（能被机器量的那五条），
**按几何与行为认，不按类名认** —— 按类名认会漏：
产物把 `.dock` 改名叫 `.tab-bar`，门就查不到了。

## 九条

### 1 · 进度要双重表达：一个精确值 + 一个可感知的量

**规则**：进度同时给一个精确值和一个可感知的量 —— 顶部固定位置放 `05 / 10` 的数字页码，
配一条分段进度条。位置在换页、换色时都不移动。

两件事各管一半：**数字回答"我在哪"，条形回答"还剩多少"**。
只给数字，他得自己算；只给条，他不知道还有几屏。

| | 叙事 H5 | 产品界面原型 |
|---|---|---|
| 落法 | `01 / 10` + N 段进度条，固定在顶部 | 列表位置指示 / 步骤条 / 已读态 / 分页器 |
| 反例 | 一个百分比数字 | 无限流不给任何位置线索，滑到第 40 条不知道自己在哪 |

**位置固定**是这条的一半：换页换色，骨架不动。

### 2 · 主操作占拇指区，次操作弱化到两侧

**规则**：主操作放在底部拇指区并做成最强的那一个；上一页与分享弱化到两侧。

判据是几何的：**底部 40% 视口内，最大的那个可点元素就是主操作**。
`.dock .next{flex:1}` + 两侧 `.ic` 是它在骨架里的样子。

| | 叙事 H5 | 产品界面原型 |
|---|---|---|
| 落法 | 三键底栏，「继续」`flex:1` | 主 CTA 固定底部；次操作收进「更多」或右上 |
| 反例 | 三个一样宽的按钮 —— 那等于没有主操作 | 主按钮在首屏顶部，拇指够不着 |

### 3 · 控件文案响应当前状态

**规则**：进入末页后，把主控件文案切换为「再看一遍」；再次触发时回到首屏并重置进度。
控件文案、可访问状态与实际行为必须同步更新。

这一条最便宜也最容易被漏。**按钮不该永远说同一句话。**

| | 叙事 H5 | 产品界面原型 |
|---|---|---|
| 落法 | 末屏 `继续 ↓` → `再看一遍 ↺`，点它回第一屏 | 按钮四态：默认 / 加载中 / 完成 / 禁用 |
| 骨架 | `setCur` 里已经写好，**别删** | 自己写；至少给"加载中"和"完成" |

### 4 · 把等待做成内容

**规则**：入场先给一个开场动作（插卡启动 / 扫描线 / 逐行日志），
把等待时间变成叙事的一部分，而不是一个转圈。

等待是一定会发生的。问题只是**这段时间里他在看什么**。

| | 叙事 H5 | 产品界面原型 |
|---|---|---|
| 落法 | 开场壳：扫描线 / 逐行日志 / 进度条 / 开机自检 | 骨架屏（灰块占位），**不是转圈** |
| 骨架 | `.intro` 空壳 + `.off` 退场 + 2.5s 自退 | — |

**骨架只给壳，不给内容。** 内容由「借来的那个世界」决定
（一台旧机器 / 一个电视台 / 一次开箱）。给满了，所有人的 H5 又会长一样。

### 5 · 一个意图多条通路，反馈同一套

**规则**：同一个意图给多条通路 —— 继续按钮、上下滑动、键盘方向键、点击空白处都能翻页，
且四条通路的反馈一致。

关键在后半句：**多条通路要走同一个函数**。
四条路各写一遍逻辑，迟早有一条的动效或页码对不上。

| | 叙事 H5 | 产品界面原型 |
|---|---|---|
| 落法 | 按钮 / 键盘 / 点空白 / 滑动 → 同一个 `go(i)` | 点击 / 滑动 / 长按 → 同一个状态函数 |
| 门 | `interaction-contract` 查 click 之外还有没有第二条 | 同左 |

### 6 · 落点确定，不停在半途

**规则**：滚动结束必须吸附到完整一屏，不允许停在半屏位置。

| | 叙事 H5 | 产品界面原型 |
|---|---|---|
| 落法 | `scroll-snap-type:y mandatory` + `scroll-snap-stop:always` | 列表吸顶、分页对齐，不停在半个卡片上 |

`scroll-snap-stop:always` 是重点：没有它，快速滑动会一次跳过好几屏。

### 7 · 动效在组织阅读，不在装饰

**规则**：入场按信息优先级排序 —— 章节名、标题、数字、解释依次进入，
让阅读者先看到结论、再理解细节。

**入场次序 = 阅读次序。** 这不是"让它动起来"，是"决定他先看到哪个"。

| | 叙事 H5 | 产品界面原型 |
|---|---|---|
| 落法 | `.an` + `nth-child` 错峰 delay，进屏才播 | 首屏内容分批入场：先骨架，再内容，最后次要信息 |
| 反例 | 一进页面全部动画一起播完 | 每个卡片都有 hover 缩放，眼睛不知道该看哪 |

### 8 · 换色不换规则

**规则**：每页换主题色制造章节感，而顶部、内容区、底部骨架保持不变，
学习成本很低。」

这一条同时是**人格与机箱的分界线**：
机箱（分屏、安全区、取景框、状态栏、底栏几何）可以复用；
人格（配色、字体、构图）必须按 `style.json` 的签名逐案重新长。

| | 叙事 H5 | 产品界面原型 |
|---|---|---|
| 落法 | 每屏 `data-t` 给一组 `--bg1/--bg2/--key`；底纹与质感层全局同一条 | 主题色可换，组件规格（圆角/间距/字阶）不换 |

### 9 · 每个副作用都要有一句解释

**规则**：每个副作用都要有一句解释 —— 收藏、提交、分享跳转之后用 Toast 说明刚刚发生了什么。
以及「体验有闭环：浏览、分享、重看都被覆盖，不会在最后突然"断掉"。」

**凡是点了之后世界变了的动作，都要有一句话告诉他变了什么。**
两份 gold 各有 6 处 toast。

| | 叙事 H5 | 产品界面原型 |
|---|---|---|
| 落法 | 分享 / 保存 / 复制后弹一条 1.6s 说明 | 提交 / 删除 / 收藏 / 加入购物车后给一句反馈 |
| 骨架 | `toast(msg)` 已经写好 | 自己写；一个函数就够 |

**动作可以换，那句解释不能省。**

## 门量哪五条

`python3 scripts/check.py --url <产物> --profile h5|app-screen`

| 门里的名字 | 对应上面第几条 | 怎么量 |
|---|---|---|
| 进度/位置表达 | 1 | 一组 >=2 个带激活态的同级小元素，或一个 `N / M` 页码；只有一屏时不要求 |
| 主操作在拇指区 | 2 | 最大的可点元素其底边在视口 60% 以下 |
| 控件响应状态 | 3 | 脚本里存在对控件文字的赋值 |
| 多通路 | 5 | click 之外还有键盘 / 滚动 / 触摸中的至少一条 |
| 副作用反馈 | 9 | 存在 toast / 提示条一类的机制 |

四、六、七、八量不了——它们是"好不好"，不是"有没有"。
那四条靠动作 5 的看图闭环和这一份自己。

**标定**：`gold/h5-qq2026` 与 `gold/h5-cycle` 五条全绿；
`tests/case79`（静态 App 关键屏）报 3 条。
