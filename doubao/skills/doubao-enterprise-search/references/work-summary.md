# 工作总结处理

本文件适用于查询或总结本人一段时间内整体工作，以及发现本人在该时间段负责、参与或跟进的项目和事项，包括“做了什么”“跟进了哪些项目”“参与了哪些事项”“总结工作进展”“写周报或述职”等。用户未明确具体项目或事项清单时，必须依次执行阶段一和阶段二；特定项目的进展总结或已明确事项清单的请求，直接按主 Skill 处理。

命中本文件适用范围时，必须先执行阶段一，使用 `lark-xxx` 发现候选项目和事项；不得因请求属于跨来源工作总结而跳过，也不得直接将“我的工作”“本周工作”等概括范围交给 `enterprise_agentic_search`。候选清单确定后，再进入阶段二拆分正式检索目标，并按 `SKILL.md` 第 1 章分别路由。仅路由到 `enterprise_agentic_search` 的目标按主 Skill 第 2 章构造 query；路由到 `lark-xxx` 的目标遵循对应 Skill 的调用方式和参数要求。

使用 `lark-xxx` 执行带有 `--format` 参数的命令时，必须使用 `--format json`，不得使用 `--format pretty`；只有 JSON 格式能够完整保留返回信息。

## 1. 明确总结范围

优先从用户原文和上下文确定：

- 主体：本人、团队、项目或其他已明确对象；
- 时间范围；
- 总结目的和用户明确要求的维度；
- 输出形式，如周报、月报、述职材料、项目复盘或汇报提纲。

只补全可由上下文唯一确定的信息。主体或时间范围无法确定且会实质影响检索结果时，先请求澄清；不得根据用户身份、常见模板或检索结果擅自推断。

## 2. 阶段一：发现项目和工作事项

### 适用条件与目标

命中本文件适用范围时，进入本阶段。阶段一只负责建立候选项目和工作事项清单，不总结项目进展，也不得假设存在一份材料可以直接回答或凭主题猜测项目名称。

### 发现流程

1. **选择发现来源**：优先考虑三类互补证据：
   - **会议与日程**：发现工作线索，通常作为起点。
   - **本人发送的消息**：补充实际跟进线索。
   - **本人新建的文档、周报或工作记录**：补充产出线索。

   根据用户问题和已有线索选择消息、文档或周报，并调整查询顺序与范围；不必机械遍历，也不能仅凭一种来源或几个会议名称认定已覆盖整体工作。

   用户明确指定了其他数据来源时，必须全部纳入发现范围，不得只取上述三类而遗漏用户指定的来源。
2. **整理并补充候选**：查询时优先用人员、时间、创建者等条件缩小范围；提取候选项目、事项及时间信息，合并能够确认的同名、别名和重复事项。

   已有结果有明显缺口、缺少关键时间段，或用户要求及线索指向任务、项目记录、审批等与本人工作相关且工具可查询的记录时，针对性补查；这些记录只作为候选事项线索，不直接视为已完成的工作成果。
3. **判断是否进入阶段二**：当不同来源的证据能够相互补充并支撑候选事项，且继续查询预计不会明显改善覆盖时，候选清单非空则进入阶段二。某类来源不可用或明显无关时可以跳过并记录原因。

   合理尝试后仍无候选则停止，不进入阶段二。如实说明已查询、失败或未覆盖的范围，不得推断该时间段没有工作事项；必要时请用户提供事项清单或可查询的资料范围。

### 发现约束

- 无法确认候选名称是否指向同一项目时，应保持分开，不得强行合并。
- 只有材料明确表明用户负责、主导、担任 owner 或承担核心交付时，才归为“负责”；仅参会、被提及、收件、抄送或偶尔发言只能作为参与线索。
- 无法确认责任关系时标记为“参与”或“待确认”，不得自动列为用户负责的项目。
- 探索时必须保留用户给定的主体、时间范围和其他约束，不得新增用户未表达的结论或限定条件，也不得在范围、来源和意图均未发生实质变化时机械重试。
- 无法确认完整性时，应如实记录已发现范围，不得虚构遗漏内容。

项目发现是前置探索，不适用阶段二的来源选择规则。

## 3. 阶段二：查询并总结已确定项目和事项

### 分解正式检索目标

阶段二必须以阶段一清单中的候选项目或事项为检索对象，并遵循以下规则：

- **默认分别检索**：不同候选项目或事项默认属于独立检索目标，应分别调用。
- **合并必须有依据**：只有已有材料明确表明候选名称是同一项目的别名、上下级事项或同一工作流的一部分，且同一批资料能够共同回答时，才能合并。
- **不得主观合并**：名称相近、属于同一业务方向、出现在同一时间段、用户只需简要总结或希望减少调用次数，都不能作为合并依据；不得先用综合 query 试查多个独立候选事项。
- **不得退回宽泛检索**：不得丢弃候选清单，重新使用“总结我的工作”“我做了哪些工作”等宽泛 query 让 `enterprise_agentic_search` 再次发现全部工作。
- **候选不等于确认**：仅由参会、被提及等线索发现的事项，不得直接表述为用户已经参与或负责的项目；应在正式检索中确认用户实际完成或推进的工作。


常见目标包括成果与交付、项目进展、关键决策、问题与风险、协作事项、待办和后续计划，但这些仅用于识别用户意图，不得自动全部加入 query。用户只要求笼统的“工作总结”时，应保留开放范围，不得擅自扩写成固定维度清单。

分解后的每个检索目标必须：

- 保留共同的主体、时间范围和用户限定；
- 只表达该检索目标，不包含写作、排版或文件操作要求；
- 可独立理解，且不添加用户未表达的来源、结论或限定条件。

### 按信息源选择路径

- 用户明确限定单一信息源或对象类型，如日程、消息、文档、邮件、任务等，且目标仅是筛选、枚举、计数或统计匹配记录，或提取指定字段并结构化整理，不需要综合多个对象的内容归纳背景、原因、风险、结论或演变时，按主 Skill 第 1.2 节使用对应 `lark-xxx`。
- 用户只给出项目、主题、人员或工作目标，未限定信息来源，且答案可能分布在文档、会议、消息、邮件等任意来源时，使用 `enterprise_agentic_search`。例如查询“XX 项目的进展”时，不应预设资料位于某一数据域。
- 同一请求中，信息源明确的子目标和来源不明确的跨来源子目标应分别处理，再统一整理；不得为了完成工作总结而将所有子问题强制走同一路径。

阶段二中，路由到 `enterprise_agentic_search` 的独立检索目标适用主 Skill 第 2 章的调用、query 构造与补查规则；路由到 `lark-xxx` 的目标遵循对应 Skill 的调用、参数和补查规则。不得为了绕过同一目标的重复调用限制而机械拆分近义 query。

## 4. 合并和输出

资料获取完成后：

- 按用户要求的结构组织；用户未指定时，优先按主题或项目组织，必要时在主题内按时间排序。
- 合并重复事项，区分已完成、进行中和后续计划，不得把计划写成已完成成果。
- 结论必须由已有材料支持；资料未覆盖的维度应省略或明确说明缺少信息，不得补写惯常工作内容。
- 所有资料的内容使用和引用统一遵守主 Skill 第 3.2、3.3 节。
- 保留关键数字、时间、责任关系和材料链接。
- 若用户要求写入文档、发送消息或生成其他交付物，先完成内容整理，再使用对应工具执行；对外写入或发送前遵循相应工具的确认要求。

## 5. 调用示例

用户请求：“总结我上周的工作。”用户未提供项目或事项清单，因此必须依次执行两个阶段。

**阶段一：发现候选事项**

根据“本人”和“上周”的范围，通常先通过对应 `lark-xxx` 查询日程与会议，再结合线索选择本人发送的工作消息，以及本人新建的文档、周报或工作记录；可按已有结果调整顺序，命令带有 `--format` 参数时使用 `--format json`。综合互补来源发现“项目 A”“项目 B”和“事项 C”等候选事项；参会、被提及等只能作为线索，不能据此认定用户实际参与或负责。若仍有明显缺口，或用户要求及线索指向其他来源，再按需查询任务、项目记录、审批等与本人工作相关且工具可查询的记录；已有证据足以支撑候选事项时，不必机械查询全部来源。

**阶段二：查询候选事项**

以阶段一得到的候选事项为正式检索对象，逐目标按主 Skill 路由。以下 query 仅示意已路由到 `enterprise_agentic_search` 的独立目标；项目 A、项目 B 和事项 C 默认分别检索：

- `上周我围绕项目 A 做了哪些工作？`
- `上周我围绕项目 B 做了哪些工作？`
- `上周我围绕事项 C 做了哪些工作？`

不得丢弃候选清单，重新查询 `上周我做了哪些工作？`。完成检索后，只合并有材料支持的实际工作，并按用户要求生成总结。
