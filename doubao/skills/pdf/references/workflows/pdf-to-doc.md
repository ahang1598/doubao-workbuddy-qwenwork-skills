## PDF 转飞书文档

PDF 转飞书文档工作流必须使用 `create_agent` 启动。各个agent只需阅读本文档中自己负责的部分，无需关注其他agent的工作。

### 命中信号

用户提供 PDF，且交付目标是**飞书云文档**（Docx 或 Wiki）时，使用本流程。命中关键词包括 `飞书文档`、`飞书云文档`、`lark doc`，以及包含 `feishu.cn/docx/...` 或 `larkoffice.com/docx/...` 的 URL。若目标是 `.docx` 格式的 Word 文件，则使用 `pdf-to-word.md`，不使用本流程。

### 三个层级的Agent
#### MainAgent
`MainAgent`的主要工作:
1. 如果用户未提供目标文档，先使用`docs +create`创建一个空的飞书云文档
2. 启动`OrganizerAgent`并传递相关上下文
3. `OrganizerAgent`工作完成后，`MainAgent`承担交付任务

用户提供目标文档时，先确认其正文是否为空；若非空，只有在用户明确要求覆盖时才能先按更新规则移除或替换原正文，否则应另建空文档。

#### OrganizerAgent
`OrganizerAgent`的主要工作:
1. 统计PDF的页数，每 4 页启动一个`SubAgent`重建PDF，实现并行处理
2. 每个`SubAgent`会输出其负责的4页PDF对应的 DocxXML 片段，`OrganizerAgent`维护一个当前待上传批次，当下一批次的 DocxXML 片段准备好后，检查当前批次片段是否与下一个批次的片段有粘连。如果有，将这两个批次的粘连处合并，确保内容连贯，随后将当前批次的片段写入待交付的飞书云文档中，同时将下一批次标记为当前待上传批次，直到最后一个批次完成后直接上传。

#### SubAgent
`SubAgent`的主要工作是按照下文中`SubAgent的转换核心要求`要求重建每4页的内容，完成后交付给`OrganizerAgent`

### 转换必读文件
1. `lark-doc/SKILL.md`
2. `lark-doc/references/lark-doc-xml.md`（飞书 XML 语法）
3. `lark-doc/references/lark-doc-update.md`（分批 append、str_replace、block_replace 等）
4. `lark-doc/references/lark-doc-fetch.md`（回读文档）
5. `lark-doc/references/lark-doc-media-preview.md`（预览）

### SubAgent的转换核心要求
#### 过程记录文件
在SubAgent重建PDF时，必须在工作目录创建独立的 `pdf-to-doc-process-{subagent_id}.md`，并在整个转换过程中持续更新。创建前可以读取 PDF 元数据以取得总页数，并按上文确定目标文档；暂时无法取得的字段先标记为 `pending`，取得后立即补齐。该文件只记录本次任务的处理过程，不得插入待上传 XML，也不得写入目标飞书文档。图片处理记录统一按“页码 → 裁剪 run → 裁剪文件”组织，所有目录和文件均记录实际路径，不得只写“已完成”。

至少记录以下内容：

- 当前批次ID、PDF路径、需要处理的页号、目标文档链接或 token
- 每页对应的页面渲染图路径，以及该渲染图是否已被 agent 作为图片实际读取
- 裁剪输出根目录、每轮 `run-id` 及其目录、每页当前有效的 `run-id`；重裁时还要保留旧 run，并记录 `superseded_by`
- 当前有效 run 中每张裁剪图的路径、实际图片读取状态、源页位置或内容摘要、`use`/`skip`/`native`/`recrop` 结论、理由和后续动作；另行记录源页有效图片到 `use` 裁剪图的覆盖映射及 XML 插入位置
- `unclear_source`、`source_anomaly`、源色到落地色映射、版式调整、失败与恢复操作
- 正文段落、公式、源语义表格、源有效图片和 `<grid>` 的预期数、已完成数及终版核对结果；另行记录落地后的 `<table>` 和 `<img>` 块数
- 本批次4页中，第一页和最后一页是否有截断（即可能和相应批次中的其他页有粘连）

#### 公式转换要求（`<latex>`）

凡可以可靠转录的公式必须使用飞书原生 `<latex>...</latex>`；禁止以纯文本近似（如 `x^2 + 1`）、Unicode 上下标（如 `x²`）或截图代替，也不得创建空 `<latex>`。

**识别**：先检查源页面。数学字体名（`CM*`、`MSAM`、`STIX`、`Cambria Math`、`Symbol`）、密集数学符号（`∑ ∫ ∏ √ ± ≤ ≥ ≠ → ∈ ∀ ∃`、希腊字母、上下标嵌套、根号）、分数线特征（水平细线夹在两行小字之间），以及整行居中且右侧带 `(数字)` 或 `(章节.序号)`的文本行。

**转录规则**：

- 同时参考源页面高清渲染图、文本层和字体信息；三者冲突时以可见渲染结果为最终依据，不直接采信可能错误解码的公式字符。
- 上下标、共轭 `\bar`、转置 `^{\top}`、极限 `\lim_{n\to\infty}`、大定界符 `\left(\right)`、分段函数 `\begin{cases}...\end{cases}`、对齐推导 `\begin{aligned}...\end{aligned}`，以及矩阵 `\begin{bmatrix}` 或 `\begin{pmatrix}` 均按源文转录。
- **希腊字母与形近字逐条核对**：`v/ν`、`o/O/0`、`l/1/I`、`ε/ϵ`、`φ/ϕ`。局部无法辨认时，在对应位置使用 `\text{[unclear]}`，并在交付说明中记录 `unclear_source` 的页码、位置和上下文；整条公式无法可靠辨认时，不创建空 `<latex>` 或猜测内容，改用相邻普通段落明确标注“源公式无法可靠转录”，并将其列入未完成项。
- **函数名直立**：`\sin \cos \log \exp \lim \min \max` 使用内置命令（自动直立）；单字母变量默认使用斜体。
- **多字符变量名**使用 `\mathrm{Var}` 或 `\text{if}`，不要写成 `Var`（否则会被当作 `V·a·r`）。
- **疑似原文笔误**（量纲不匹配、明显手误）应**忠实保留**，并在交付说明中单独列为 `source_anomaly`；不要擅自改成正确形式。

**写入 XML**：

- **行内公式**： 与正文写在同一段中：`<p>由 <latex>a=2</latex> 可得...</p>`。
- **独立公式**： 单独成段并居中：`<p align="center"><latex>a^2 = 4</latex></p>`。
- **带编号的独立公式**：单独成段并居中，使用 `\tag{编号}` 添加编号，并写在 `<latex>` 内部。例如：`<p align="center"><latex>a^2 = 4 \tag{公式1.4}</latex></p>`。

**LaTeX 中的 XML 转义**：LaTeX 源码中的 `<`、`>`、`&` **必须写成 XML 实体** `&lt;`、`&gt;`、`&amp;`；花括号 `{}` 无需转义。


```xml
<!-- 错 -->
<latex>a<b</latex>
<latex>P(A&B)</latex>

<!-- 对 -->
<latex>a&lt;b</latex>
<latex>P(text\_A \land text\_B) \tag{2-5}</latex>
<latex>\begin{aligned}a&amp;=b+c\\&amp;=d\end{aligned}</latex>
```

逻辑“与”优先使用 `\land`；`aligned`、矩阵等 LaTeX 语法中的对齐符 `&` 仍须保留，但在 XML 中写成 `&amp;`。

**LaTeX 元素内禁止嵌套任何 XML 标签**——强调或颜色样式应写在 `<latex>` 外部，或使用 LaTeX 内置命令（如 `\boldsymbol`、`\color{red}`）。

**自检**（交付前逐条检查）：`\begin{X}` 与 `\end{X}` 成对，且 `X` 一致；`\left` 与 `\right` 成对（需要单侧定界符时使用 `\left.` 或 `\right.`）；`\frac{}{}`、`\sqrt{}`、`^{}`、`_{}` 的花括号完整；命令拼写正确（例如 `\sum` 不是 `\Sum`，`\infty` 不是 `\infinity`）。

#### 表格转换要求（`<table>`）

表格必须使用飞书原生 `<table>`；禁止转为段落文本、用制表符拼接的 `<pre>` 或代码块、项目符号列表或整表截图。

**结构要求**：

- 源表存在语义表头时，在 `<thead>` 中使用 `<th>`；没有表头时不要凭空创建。数据行放在 `<tbody>` 中并使用 `<td>`。
- 合并单元格使用 `colspan` 或 `rowspan`，且**只在起始单元格中出现**；被合并的单元格不要重复写入。
- 使用 `<colgroup><col width="..."/></colgroup>` 显式指定列宽，`width` 数值按照源表格的列宽比例反推，不附加未在 `lark-doc-xml.md` 中声明的单位。禁止**无依据**均分；源表本身等宽时可以等分。
- 单元格内如果包含公式，必须仍用 `<latex>`。
- 底纹使用 `background-color` 命名色：基础 7 色、`light-{色相}` 或 `medium-gray`；表格单元格不得使用其他 `medium-*` 值。源文使用飞书不支持的十六进制颜色时，降级为最接近的命名色，并在交付说明中列出“源色 → 落地色”。无法通过飞书 XML 表达的边框颜色也应列入保真妥协。

**跨页表格**：语义连续且服务端可接受时使用一张 `<table>`，并删除续页中重复出现的表头。若单表写入失败、体量过大或超出批次限制，则按连续行拆表，每张表重复语义表头并注明“续表”；不得删除数据行。

**超宽表**：不要为了缩窄版面合并不同语义的列。确实无法在文档宽度内清晰呈现时，按列组拆成多张 `<table>`，每张重复主键或标识列，并在正文中明确说明“该表按列分段呈现”。服务端返回容量或结构错误时停止当前批次，根据错误缩小表格或拆分行；当前 `lark-doc-xml.md` 未声明固定列数或单元格数上限，不得编造具体上限。**禁止**降级为 `<pre>` 或代码块。

**目视可见但未被识别的表格**：PDF 中的表格有时没有边框，仅依靠空白对齐。先使用 PyMuPDF `page.find_tables()`，必要时用 pdfplumber 的表格策略复核；仍未识别时，再结合文本 x 起点、行基线、列间空白和语义一致性补建 `<table>`。仅凭 x 坐标聚类不足以判定表格。

#### 图片转换要求（`<img>`，必须真实上传）

本地图片必须在对应批次 XML 的原位置使用 `<img path="@./relative/path"/>` 上传；公开 HTTPS 图片可使用 `href`，仅复制文档中已有图片时使用 `src` token。禁止用占位文字代替图片、以 `src` 引用本地文件，以及使用 `file://` 或 `data-src`。

**硬性要求**：正文与图片必须同步处理。当前页图片未全部检查、当前有效 run 中仍有 `recrop`，或未与原始页对齐时，不得完成该页 XML。

**目录口径**：页面高清渲染图写入独立的 `<page-render-dir>`；裁剪候选图写入 `<figure-output-dir>/<run-id>/`。两类目录不得混用。执行命令后，立即把实际目录、文件名和当前有效 `run-id` 写入过程记录文件；只有最终判定为 `use` 的图片，才需要另外保证其路径可由批次 XML 相对引用。

##### 1. 使用脚本批量定位并裁剪

使用 `python scripts/locate_pdf_figures.py <source.pdf> --pages "5-8" --output <figure-output-dir> --run-id <run-id>`，将 PDF 中的图片裁剪下来。
每轮结果位于独立的 `<figure-output-dir>/<run-id>/` 目录，目录内只包含本轮裁剪图。裁剪图命名为 `page-<四位页码>-image-<两位序号>.png`，例如 `page-0030-image-01.png`。

**注意**
1. 同页裁剪图序号不代表其在原 PDF 中的位置或图号顺序。写入 XML 前，必须实际读取每张裁剪图并逐一对照原页，确认对应图号、裁剪完整性和插入位置。
2. 原 PDF 中一张图片可能包含多个子图（如图 2.1-a、2.1-b），也可能被裁成多张；必须确认各裁剪图的归属和组合关系，避免子图错位或顺序错乱。

##### 2. 随正文逐步检查

生成正文 XML 时，图片检查必须逐页、逐张完成。每页 XML 写入前，先完成该页正文整理草稿，再完成以下图片核查；图片核查全部通过后，才允许产出该页最终 XML

1. 如果当前批次尚未生成页面渲染图，使用 `scripts/pdf2png.py <source.pdf> --pages "1-4" --output <page-render-dir>` 渲染一次，每两页会被合并渲染成一张PNG图片；同一批次复用该渲染结果，不得重复渲染。检查其中当前页区域目视可见的图片及其版面位置，并在过程记录文件中写入该渲染图路径和读取状态。
2. 找到当前批次有效 `run-id` 目录下的全部裁剪图，然后将**每一个裁剪 PNG 作为图片实际读取**；只执行 `ls`、查看文件名、读取图片尺寸，或根据正文、图注和原页猜测裁剪内容，均不算完成检查。
3. **将每张裁剪图与当前页在页面渲染图中的区域逐一对照**，检查四边是否完整、是否包含全部子图，以及是否混入图注、页眉页脚或相邻正文；同时确认它在源页中的位置和正文中的插入位置。不得遗漏原PDF中的任意一个有效图片，否则整个转换任务将毫无意义。
4. 为每张裁剪图立即给出且仅给出一种结论，并写入过程记录文件：
   - `use`：裁剪完整且内容确为应保留的图片，记录对应图号或内容摘要及计划插入位置
   - `skip`：属于误检、装饰碎片、重复项，或已被另一张更完整的裁剪图覆盖；记录不写入的理由
   - `native`：内容实际为公式或语义表格；分别按 `<latex>` 或 `<table>` 处理，不写入图片
   - `recrop`：内容缺损、留白不当、子图缺失、文字不可辨或混入其他内容；暂停该页 XML，按“问题页重裁”处理
5. 对照原页复核：原页中的每张有效图片都必须被至少一个 `use` 结果完整覆盖；允许一对多或多对一，但必须记录映射

##### 3. 问题页重裁

1. 当有图片命中 `recrop` 结果时需要按照具体情况使用不同的方式重裁。
2. 当候选图被拆成多张时：使用 `--adaptive-merge-gap-pt` 增大候选组的二次合并距离。该参数作用于所选页面的候选分组，可能改变图片数量和编号；应从接近默认合并距离的较小值开始调整，并重新检查该页全部裁剪图。
```
python scripts/locate_pdf_figures.py <source.pdf> \
  --output <figure-output-dir> \
  --pages "30" \
  --run-id <new-run-id> \
  --adaptive-merge-gap-pt 12
```
3. 当需要对某张截图进行边界微调时，使用 `--adjust` 调整指定图片的最终裁剪框，四个数值依次对应左、上、右、下；正数向外扩，负数向内收。图片 ID 表示在`--adaptive-merge-gap-pt`参数下生成的候选编号。
```
python scripts/locate_pdf_figures.py <source.pdf> \
  --output <figure-output-dir> \
  --pages "30" \
  --run-id <new-run-id> \
  --adaptive-merge-gap-pt 12 \
  --adjust page-0030-image-01,8,0,0,0
```
4. 当`scripts/pdf2png.py`截图时有漏截，或反复调整截图边界仍无法实现正确的裁剪时，可以手动编写代码截图。
5. 重新截图完成后，必须检查新截图是否与预期一致，并将结论写回过程记录文件。重复以上步骤，直到该批次需要处理的PDF中的所有图片均被正确裁剪，即所有关联的最新截图被记作`use`。

##### 4. 图注转换要求

图注优先使用对应 `<img>` 的 `caption` 属性写入，如 `<img path="@./figure.png" caption="图 1 示例"/>`，并忠实保留图号、标题和子图标识，不得将图注裁入图片；仅当原生图注无法表达复杂内容时，才降级为紧随图片的独立文本段落。

#### 目录转换要求

对于整个文档的目录，使用两列表格进行转换，按照8：2的比例分配宽度，左列是文章内容中的标题，右列是标题的页码。

目录中标题的缩进、格式也按照原文中的格式进行转换。

如果整个批次以文档目录开始或结尾，要注意可能与相邻批次的目录有粘连。

#### 飞书 XML 的几个陷阱

**不要在待上传 XML 中使用注释**：XML 注释不是 `lark-doc-xml.md` 声明的文档结构，页码、批次和审计备注应保存在本次任务的过程记录文件中。若草稿已含注释，使用支持 XML fragment 的解析方式（先包裹临时根节点）删除注释，再序列化根节点的全部子节点；不要直接对包含多个顶层 block 的 DocxXML 调用 `etree.fromstring(xml_bytes)`，也不要用正则表达式处理 XML。

**多栏页面按语义选择 `<grid>`**：双语并排、逐项对照或阅读关系依赖横向位置时使用 `<grid>`，各栏 `width-ratio` 之和为 `1`，并按源页面比例设置。普通学术或报纸双栏若只是连续阅读流，可以按“左栏从上到下，再右栏从上到下”转成单栏；同页存在跨栏标题、表格或图片时，应拆成“满宽 block + grid + 满宽 block”，不要把整页机械包进一个 grid。

#### SubAgent 的交付

每个 `SubAgent` 完成批次后，需要先进行检查，尤其关注公式转换是否正确、标题内容和层级设置是否得当、图注是否正确等。
检查出问题后，必须立即修复，不得交付错误的内容。

`SubAgent`必须向 `OrganizerAgent` 交付以下产物：

1. **DocxXML 文件**：包含本批次最多 4 页、按源 PDF 阅读顺序排列且可直接用于 `append` 的 XML 片段。文件不得包含临时根节点、XML 注释、页码标记或审计备注。所有 `<img path>` 必须使用相对于该 XML 文件的有效路径。
2. **交接 README**：即本批次的 `pdf-to-doc-process-{subagent_id}.md` 过程记录文件，不另建内容重复的说明文件。除上文要求的过程记录外，交付时还必须集中列出：
   - 批次 ID、页码范围、DocxXML 文件路径、目标文档链接或 token，以及当前有效的页面渲染图、裁剪图和核验截图所在目录。
   - 批次开头和结尾是否存在跨批次粘连。分别记录结论（`none`、`possible` 或 `confirmed`）、对应首尾 block 的类型和原文、版面及语义证据，以及建议的合并方式；不得只写“有粘连”。
   - 正文段落、公式、源语义表格、源有效图片和 `<grid>` 的预期数与已完成数，实际 `<table>` 和 `<img>` 块数，以及 XML 解析、LaTeX 自检和逐图检查结果。
   - 所有 `unclear_source`、`source_anomaly`、保真妥协、失败与恢复操作和未完成项。存在未分类裁剪图、当前有效 run 中的 `recrop`、缺失图片资产或其他阻断项时，不得交付为可写入批次。
3. **图片资产目录（如有）**：随 DocxXML 一并保留所有被 `<img path>` 引用的最终裁剪图片。不得交付未被 XML 引用的临时候选图作为有效资产，也不得在交付后移动、重命名或删除图片，直至 `OrganizerAgent` 完成写入、回读和逐图预览。

`OrganizerAgent` 应以 README 中的页码范围排序批次，以其中的首尾粘连记录作为相邻批次复核线索，但仍须按下文要求自行对照相邻 XML 和源页面后再决定是否合并。

### OrganizerAgent的写入与回读

`OrganizerAgent` 负责汇总各 `SubAgent` 交付的 DocxXML 片段，处理相邻批次的内容衔接，并按 PDF 页码顺序分批写入目标文档。具体流程如下：

1. **排序并检查批次**：无论各 `SubAgent` 以何种顺序完成，都必须按 PDF 页码范围对批次排序。
2. **处理相邻批次衔接**：从第一个批次完成开始，维护一个“当前待写入批次”，每当下一批次处理完成，必须对照其末尾与下一批次开头，检查是否存在内容粘连。只有在版面位置、缩进、字体、行距和语义均表明内容连续，且前页末尾没有明确的段落终止信号，或明显可以判断出是表格跨页时，才能合并跨页内容。英文内容可将下一页是否以小写字母或续词开头作为辅助证据；中文及 OCR 文本不适用该条件。标题、列表项、图注和公式不得仅因物理位置相邻而合并。合并时必须使用 XML 解析器移动子节点，禁止通过字符串截断拼接。
3. **按序写入**：当“当前待写入批次”的前后内容粘连处理好后，立即按批次顺序升序执行 `docs +update --command append`，将内容写入目标文档。一次最多只上传5000个block，XML大小不超过200 kB，超过上传上限时需要将本批次进一步拆开，按顺序上传。随后更新当前待写入批次为下一批次。
4. **逐批回读**：每批写入后，立即使用 `docs +fetch --detail full` 回读，确保新上传的内容符合预期，包括文本顺序、`<latex>` 源码、`<img>` 的数量和顺序、`<table>` 的行列数及 `colspan`、`rowspan` 序列，以及 `<grid>` 的数量、栏数、内容顺序和 `width-ratio`。
5. **预览图片**：回读通过后，对本批新增的每个 `<img>` 逐张调用 `+media-preview`，确认图片上传完整、没有混入额外正文且可以正常访问。
6. **处理异常**：如果出现内容缺失或不匹配、`warning`、`partial` 或图片预览失败，应立即停止，且不得重试 `append`，以免重复写入。先使用 `docs +fetch --detail full` 确认远端实际写入进度，再通过 `str_replace`、`block_replace` 或 `block_delete` 修正；重新核验无误后方可继续。
7. **记录结果并继续**：每批完成写入、回读和图片预览后，将页码范围、写入结果、`revision_id`、核对结果及异常写入对应批次的过程记录文件，再处理下一批。

**终版全文回读**：全部批次写入并通过逐批核验后，`OrganizerAgent` 应在交由 `MainAgent` 交付前再次执行 `docs +fetch --detail full --as user`，并对照本地稿逐项检查，若缺失存在问题则需要进行局部调整。

1. 读取所有标题，检查层级和内容设置是否得当。防止标题层级错误、不应被设置为标题的内容被误设置为标题、同级标题格式不统一、标题遗漏标号等。标题设置会严重影响阅读，发现问题必须修复。
2. 检查所有表格是否有截断或缺失，防止表格内容缺失、一张表错误拆分、表格内格式不统一。
3. 检查所有公式是否与源文一致；带编号公式逐条核对源编号与 `\tag{...}`。

### MainAgent的交付说明

根据PDF的页数计算耗时，小于20页的PDF约20分钟，20页以上，每10页多7分钟，将计算后的耗时通知用户，并告知用户可以先处理其他任务，任务完成后交付。

交付内容必须包含：

1. **文档链接与当前 `revision_id`**（便于用户回滚）。
2. **计数**：按“已完成数 / 源侧预期数”列出正文段落、公式、源语义表格、源有效图片和多栏版式 `<grid>`；另列实际 `<table>` 和 `<img>` 块数。
3. **LaTeX 自检结果**：通过条数、修正条数，以及未解决的 `unclear_source`、`source_anomaly` 和整条公式无法可靠转录的未完成项清单（附页码与位置）。
4. **视觉检查范围**：列出抽样对照的页码，以及已逐张检查的裁剪图片；不要笼统写成“全部通过”。
5. **保真妥协**：源色 → 落地色映射、栏宽近似值、跨页或超宽表拆分说明、转为单栏的页面、无法完全排除的裁剪残留文本，以及无法映射的 PDF 内部锚点。
6. **未能验证的限制**：OCR 未接入等不阻断既定核对项的限制。受控浏览器不可用时，应说明采用的导出预览替代方式；若受控浏览器和导出预览均不可用，则终版视觉检查未通过，只能在用户明确接受后交付不完整结果。

**飞书不保留 PDF 的文档物理分页**——这是产品特性，应在交付说明中明确指出，避免用户误认为这是保真失败。
