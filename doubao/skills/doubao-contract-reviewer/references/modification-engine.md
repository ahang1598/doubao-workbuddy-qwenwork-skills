# 修改执行引擎

本文档是 Track Changes 和 Comments 写入的**唯一技术权威**。所有 JSON 格式规范、脚本使用、自检流程、降级路径、批注格式均以此为准。

---

## 一、技术方案

采用 `python-docx` 库 + 批注脚本实现修订和批注写入。

| 对比项 | 说明 |
|--------|------|
| 格式兼容性 | python-docx 处理各种格式差异 |
| 异常恢复 | 单条失败跳过，不影响其他 |
| 模型兼容 | JSON 输入，模型友好 |
| 安装要求 | 需要 python-docx + lxml |

---

## 二、脚本使用

```bash
pip install python-docx lxml -q

python3 <skill_dir>/scripts/apply_review.py \
  --input /path/to/contract.docx \
  --output /path/to/contract_AI审核版.docx \
  --json /path/to/modifications.json
```

### ⚠️ JSON 文件写入规则（ TOML 版）

**根因**:合同原文中包含中文引号 `""''`、全角括号 ``、反斜杠 `\`、换行符等特殊字符。过往路径的问题:
- JSON 用 `"` 作字符串定界 → 中文 `""` 必须转义,LLM 经常漏转
- Python 字符串也用 `"` → `"abc""def"` 被解析为字符串拼接,SyntaxError
- bash `echo`/`heredoc` 对反斜杠、引号的转义规则复杂,合同原文极易出错

**最可靠的方式**:TOML → JSON。TOML 的**单引号 `'...'`**和**三重单引号 `'''...'''`**是"字面串"(literal string),不解析任何转义,对中文引号/全角括号/反斜杠/换行零冲突。

**标准做法**:
```
1. 用 write_file 写一个 TOML 文件(review_all.toml),字符串一律用 '...' 或 '''...'''
2. bash: python3 scripts/build_json.py --from-toml review_all.toml --multi
   → 一次生成 modifications.json + 4 个 verify 输入 JSON
3. bash: python3 scripts/verify_all.py --from-toml review_all.toml --output verify_results.json
   → 一次执行全部 4 个 verify 子脚本
4. bash: python3 scripts/apply_review.py --input ... --json modifications.json
```

**禁止**:
- `write_file` 直接写 .json
- bash `echo` / `heredoc` / `printf` > *.json
- 写 Python 模块再 json.dump( 路径,遇中文 `""` 仍 SyntaxError)

完整的 TOML + JSON 示例见 [references/json_examples.md](json_examples.md)。

## 三、JSON 输入格式

### 最小完整示例（覆盖全部常用类型）

```json
{
  "author": "合同审查助手",
  "modifications": [
    {
      "type": "track_change",
      "search_text": "甲方应在合同签订后十个工作日内向乙方支付合同总额的80%作为预付款",
      "old_text": "合同总额的80%",
      "new_text": "合同总额的30%",
      "comment": "【风险等级】P0\n【风险分析】预付款80%远超30%惯例，乙方违约则大额资金难追回。\n【修改建议】将预付款比例降至30%，剩余按进度或验收节点支付。",
      "risk_level": "P0"
    },
    {
      "type": "comment_only",
      "search_text": "本合同一式两份，双方各执一份",
      "comment": "【风险等级】P1\n【风险分析】无保密约定，泄密时无合同救济途径。\n【修改建议】合同末尾增加保密条款，约定保密义务及期限不少于3年。",
      "risk_level": "P1"
    },
    {
      "type": "insert_after",
      "search_text": "第十条 争议解决",
      "new_text": "第十一条 保密条款\n\n双方对本合同内容及履约过程中知悉的对方商业秘密承担保密义务，保密期限自合同终止之日起三年。违反保密义务的一方应赔偿由此给对方造成的全部损失。",
      "comment": "【风险等级】P1\n【风险分析】缺保密条款，履约中知悉的商业秘密无合同保护。\n【修改建议】新增保密条款，约定保密范围、期限及违约责任。",
      "risk_level": "P1"
    }
  ]
}
```

### 字段说明

| 字段 | 必填 | 说明 |
|------|------|------|
| `type` | 是 | `track_change` / `comment_only` / `insert_after` / `delete` |
| `search_text` | 是 | 定位段落的文本片段（支持模糊匹配） |
| `old_text` | track_change/delete 时必填 | 要被替换/删除的原文 |
| `new_text` | track_change/insert_after 时必填 | 替换后/新插入的文本 |
| `comment` | 建议填写 | 批注文本，使用三段式格式（风险等级+风险分析+修改建议） |
| `risk_level` | 建议填写 | `P0` / `P1` / `P2` |

### 如何选 type（判据见 SKILL.md §七"修改类型决策"）

一句话原则:**能给出确定的替换/新增文本就走修订，给不出才 comment_only。**

| 我能给出的东西 | type |
|---|---|
| 能替换的确定文本（"80%"→"30%"） | `track_change` |
| 整条缺失且能给出可落地的补充条款 | `insert_after` |
| 某片段删除即解决（仲裁诉讼并存等） | `delete` |
| 只能指方向、给不出确定文本 | `comment_only` |

**字数上限豁免**：内容空置聚合那 1 条 P2 批注可超字数上限（见 SKILL.md §七），其余批注一律守 P0≤60/P1≤60/P2≤35。

## 四、搜索匹配策略

脚本使用以下策略匹配段落：

1. **精确匹配**：`search_text` 完整出现在段落文本中
2. **模糊匹配**：使用 `difflib.SequenceMatcher` 计算相似度，取相似度 > 0.5 的最佳匹配
3. **回退策略**：都匹配不到则记录错误并跳过（不影响其他修改）

对于 `old_text` 在段落内的定位：
1. 先在段落全文中找到 `old_text` 的位置
2. 遍历段落的 runs，找到包含 `old_text` 的 run 组合
3. 对涉及的 runs 执行修改操作

## 五、风险等级视觉编码（统一作者名 + 图标入批注正文）

Word 是**按 author 名字字符串**给批注底纹和修订痕迹分配颜色的。早期版本给不同风险等级的 author 加 `[P0🔴]/[P1🟡]/[P2🔵]` 前缀，结果同一份文档里作者名不一致，批注底纹被 Word 渲染成红蓝混杂，非常花。

因此现在**所有批注/修订统一使用同一个作者名 `合同审查助手`**，保证颜色一致；风险等级改为用**红黄蓝图标放进批注正文**来可视化，既保持批注底纹同色，又保留等级区分。

| risk_level | 批注正文呈现 | author（统一） |
|-----------|-------------|---------------|
| `P0` | `【风险等级】🔴 P0` | `合同审查助手` |
| `P1` | `【风险等级】🟡 P1` | `合同审查助手` |
| `P2` | `【风险等级】🔵 P2` | `合同审查助手` |

实现方式：

```python
def get_author(risk_level: str, base_author: str = "合同审查助手") -> str:
    # 统一作者名，Word 据此分配单一颜色，批注底纹不再混色
    return base_author

_RISK_ICON = {"P0": "🔴", "P1": "🟡", "P2": "🔵"}

def decorate_comment_with_risk(comment_text: str, risk_level: str) -> str:
    # 在批注正文的【风险等级】标签处插入对应图标 → "【风险等级】🟡 P1"
    # 图标只出现在批注文字里，不影响 Word 按 author 分配的底纹颜色
    ...
```

JSON 中无需手动设置 author，脚本自动统一；风险图标由脚本按 `risk_level` 注入批注正文，无需手写。

**批注精确锚定**：批注范围只包裹本次修订真正创建的 `w:del`/`w:ins` 片段，而非整段——Word 中只有被改动的文字带批注底纹，不会整段变色。

**逐词修订**：底层用 `difflib.SequenceMatcher` 做多块 diff，能识别句子中间夹着的公共子串（如「有管辖权的」），只对真正变化的片段做 `w:del`/`w:ins`，实现真正的逐字/逐词修订，而不是整句删掉再整句重插。

## 六、JSON 输出自检（调用脚本前必做）

脚本能否正确执行取决于 JSON 质量。调用前逐条自检：

| # | 检查项 | 说明 | 常见错误 |
|---|--------|------|----------|
| 1 | **search_text 可匹配性**| 从合同原文中复制粘贴，不要凭记忆编写 | 漏字、多字、标点不一致 |
| 2 | **old_text ⊆ search_text 所在段落**| `old_text` 必须是 `search_text` 定位到的段落内的子串 | 跨段落、或不在同一段 |
| 3 | **必填字段完整性**| track_change→search_text+old_text+new_text；comment_only→search_text+comment | 缺少字段 |
| 4 | **批注格式合规**| 含 `【风险等级】`、`【风险分析】`、`【修改建议】` 三段式，不引用规则编号 | 格式标记写错 |
| 5 | **risk_level 有效值**| 仅允许 P0/P1/P2 | 写成"高""中""低" |
| 6 | **JSON 语法 + write_file 写入**| 无多余逗号、换行用 `\n`、双引号正确转义，字段名和字符串值仅使用英文半角双引号 `"`，不使用中文全角引号 `“”‘’` 作为 JSON 定界符。**必须用 write_file 写入文件，禁止 bash echo/cat**| 末尾多逗号、shell 转义错误、JSON 中混入中文全角引号 |
| 7 | **批注条目数量 ≤ 15**| 与审查上限一致（Track Changes 不受此限制） | 超出未裁剪 |

## 七、批注格式规范

所有批注遵循三段式结构，不引用内部规则编号：

```
【风险等级】P{n}
【风险分析】{点明不改会引发的具体后果，稍带法言法语、金额比例写具体}（P0≤60字 / P1≤60字 / P2≤35字）
【修改建议】{具体的修改建议内容}（P0≤60字 / P1≤60字 / P2≤35字）
```

> **定位纪律（全批注通用）**：批注中引用位置一律用合同条款号（"第三条""第三条第一款""首部""附件三"）或性质词（主体控制/联系人控制/金额控制等），**严禁出现"第34段""第40段"这类 clean_text 段落序号**——法务对着 Word 无法数段落，段号与条款也不对应，极易误导。

**写批注的原则：**
- 风险分析要说清风险——不说"不够规范"，说"可能导致XX风险/XX后果"；字数上限旨在逼出要害、直击后果，不铺垫、不复述条款原文
- 修改建议要具体——不说"建议完善"，说"建议将XX改为YY"
- 不引用内部规则编号——用户看不懂，直接自然语言解释
- 若个案确需展开分析，不要撑破批注字数，改由对话摘要末尾统一提示"如需进一步分析，请告知"

**批注示例：**

```
【风险等级】P0
【风险分析】仲裁与诉讼并存将致争议解决条款无效，最终只能诉讼。
【修改建议】删除仲裁约定，仅保留"向甲方所在地有管辖权的人民法院提起诉讼"。
```

```
【风险等级】P1
【风险分析】第三条运费由乙方承担、第五条又称甲方承担，矛盾易引发争议。
【修改建议】将第五条"运输费用由甲方承担"改为"由乙方承担"，与第三条一致。
```

**合并规则：**
- 同类错别字合并为一条；同一条款多个子问题合并按子项列出
- 不同优先级分别标注；不同审查维度分别标注

## 八、显式降级路径（脚本执行失败时）

`apply_review.py` 可能因 `search_text` 找不到匹配、JSON 格式错误或文档结构异常而报错。

**第一步：读取错误信息，定位问题条目**

脚本报错时会输出具体错误信息（如 "search_text not found: ..."）。

**第二步：修正 JSON 中的问题条目**

| 错误类型 | 修正方法 |
|----------|---------|
| `search_text not found` | 回到合同原文重新定位，复制准确文本替换 |
| `old_text not in paragraph` | 确认是 search_text 所在段落的精确子串 |
| JSON 语法错误 | 检查多余逗号、未转义引号 |
| 编码错误 | 确认 UTF-8 编码 |

**第三步：重新执行脚本**（保存为 `modifications_fixed.json`）

**第四步：两次仍失败——降级输出**

1. 剥离失败条目，仅用剩余条目执行脚本
2. 输出交付物：
   - ✅ 部分修改后的 .docx 文件
   - 📋 完整的 modifications.json
   - 📝 审查摘要（标注哪些条目未能自动写入）
3. 告知用户哪些修改需手动添加

## 九、批量执行策略

- 每批 5-15 处修改（统一写入一个 JSON）
- 修改前自动备份原始文件
- 修改完成后验证：文件可正常打开、Track Changes 和 Comments 数量正确

## 十、异常恢复机制

脚本内置多层异常恢复：

| 异常类型 | 恢复策略 |
|----------|----------|
| 段落匹配失败 | 记录警告，跳过该修改 |
| old_text 找不到 | 尝试去除空白后重新匹配，失败则跳过 |
| XML 操作失败 | 回退该修改，记录错误 |
| 文件损坏 | 从备份恢复，输出部分结果 |

脚本输出包含：成功/失败/跳过数量、每条失败的具体原因、最终文件验证结果。
