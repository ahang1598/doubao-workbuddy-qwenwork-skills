# 合同审查手册 Playbook

本手册是合同审查的完整执行文档，SKILL.md 中每个 Step 的详细操作规程均在此。

## §0 准备工作

### 并行加载策略

审查开始时并行启动：
- 获取合同文件（下载/解析）
- 读取本地 `references/` 知识库文件
- 读取用户提供的外部知识库（如有）

**类型专属规则条件加载（多模块并行）**：按 §2.1 四问解构出交易本质后，可能识别出**多个并存的交易模块**。从 `references/contract-types/` 目录下加载**每个模块对应的类型文件**（不再"只加载一个"）。

| 交易模块（本质） | 文件 | 说明 |
|----------------|------|------|
| 物使用权让渡 | `contract-types/lease.md` | 9 条租赁专属规则（LS-01~LS-09） |
| 货物所有权转移 | `contract-types/sale.md` | 8 条买卖专属规则（SP-01~SP-08） |
| 行为/服务给付 | `contract-types/service.md` | 7 条服务专属规则（SV-01~SV-07） |
| 智力成果/IP 创作授权 | `contract-types/copyright.md` | 9 条版权专属规则（CR-01~CR-09） |
| 共同研发、成果共享 | `contract-types/joint-dev.md` | 7 条合作开发专属规则（JD-01~JD-07） |

- **按解构出的模块加载对应文件，可同时加载多个**（建议 ≤3 个，抓主要模块，避免过度拆分稀释重点）
- **跨文件去重**：多个类型文件 + risk-library + trap-detection 已整体去重；同一风险被多源命中时只批注一次
- 加载的全部类型规则与通用规则**合并为统一规则集，按 P0→P1→P2 统一排序后一起执行**（详见 §4.9）
- 若某模块不在列表中（如建设工程/融资租赁），该模块跳过类型文件加载，仅用通用规则 + §2.5 推理清单兜底

**文件获取方式：**

| 文件类型 | 处理方式 |
|----------|---------|
| `.docx` | 先调用 `scripts/convert_to_docx.py`(原样返回),然后用 `docx` skill 解析文本,同时保留原始文件作为后续修改载体 |
| `.doc` | **必须**先调用 `scripts/convert_to_docx.py` 转换为 .docx(libreoffice 无头模式,自动备份原文件),后续步骤使用转换后的 .docx。若含修订痕迹,在审查摘要顶部提示用户核对 |
| `.pdf` | 用 `pdf_builtin_extract` 提取。提取后用 `docx` skill 创建新 .docx 载体写入原文 |
| 多文件（正文+附件） | 并行读取所有文件 |

**异常处理：**文件获取失败时立即告知用户，建议替代方式。不要反复重试。

## §1 持方严格确认

**核心规则：持方身份必须由用户主动说明或确认，不得自行推断默认。**

### 1.1 持方确认规则

| 场景 | 处理方式 | 示例 |
|------|---------|------|
| 用户明确说明了持方 | 匹配确认后直接进入 §2 | "站在甲方立场审查" |
| 用户说明了但有歧义 | 列出甲乙方身份请用户确认 | "站在采购方立场"但双方都可能是采购方 |
| **用户未说明持方**| **暂停并要求补充**| "帮我审查这份合同"→列出甲乙方请选择 |

**禁止行为**：用户未说明持方时，不得自行推断、猜测或默认。

### 1.2 审查上下文摘要

持方确认后生成：

```
审查上下文：
- 合同名称：{name}
- 合同类型：{type}
- 甲方：{party_a}
- 乙方：{party_b}
- 我方持方：{our_side}（用户指定）
- 谈判地位：{position}（默认势均力敌）
- 特殊关注：{focus}
```

## §2 交易场景分析 + 风险推理

### 2.1 交易本质解构（⭐ 核心方法：穿透标题看本质，不做标题归类）

**不要先问"这是什么类型的合同"，而要先问"这笔交易实际在做什么"。**合同标题（如"采购协议""服务框架")常常掩盖真实交易结构——一份"采购协议"可能同时包含定制开发（技术合同）、货物买卖、长期服务三个并存的交易模块。审查前先用下面四问解构交易本质，再据此并行加载多个类型规则。

#### 四问解构（依次自答，形成推理链）

| # | 提问 | 解构目的 |
|---|------|---------|
| ① | **钱、标的、权利分别怎么流动？**| 画出资金流向（谁付谁）、标的交付流向（谁交付谁）、权利归属流向（成果/IP 归谁），三条流向勾勒交易骨架 |
| ② | **核心给付是什么？穿透标题看本质。**| 抛开合同名称，判断对方真正"卖"给我方的是货物、行为/服务、使用权、还是智力成果/IP——核心给付决定主交易模块 |
| ③ | **由哪几个交易模块叠加而成？**| 拆出并存的子交易（如"开发+授权+运维"）。每个模块对应一个 type；建议 ≤3 个，抓主要模块，避免过度拆分 |
| ④ | **各模块最常出什么纠纷？我方在哪最容易被动？**| 为每个模块预判高频争议点与我方易被动点，喂给 §2.5 清单二/三 |

#### 模块→类型→法律映射（解构后据此并行加载）

| 交易模块（本质） | 对应 type 文件 | 适用法律 |
|----------------|---------------|---------|
| 货物所有权转移 | sale | 《民法典》合同编买卖合同章 |
| 行为/服务给付 | service | 《民法典》合同编委托合同章 |
| 物的使用权让渡 | lease | 《民法典》合同编租赁合同章 |
| 智力成果/IP 创作授权 | copyright | 《民法典》合同编 + 技术合同章（著作权法） |
| 共同投入研发、成果共享 | joint-dev | 《民法典》合同编 + 技术合同章 |
| 建设工程 | （无专属文件，用通用规则） | 《民法典》+《建筑法》+《建设工程质量管理条例》 |
| 融资租赁 | （无专属文件，用通用规则） | 《民法典》融资租赁合同章 |

> **多模块判定示例**：一份《游戏定制开发与运营协议》→ ② 核心给付是"按甲方需求开发游戏并交付源代码"（智力成果）+ 后续"代运营"（服务）→ ③ 拆为 copyright（开发成果归属/不侵权）+ service（运营 SLA/响应时效）两个模块 → 并行加载 `copyright.md` + `service.md`，跨文件去重后统一排序执行。

**特别注意**：如合同引用了已废止的法律法规（如《合同法》），应标注修改为现行有效法律。

### 2.2 交易合法性

- 交易标的是否属于法律禁止或限制流通物品？
- 交易行为是否违反法律禁止性规定？

### 2.3 主体资质

检查是否涉及特殊行业（金融、医疗、建筑等），如是需核查相关资质、许可、批准。

### 2.4 审批要求

- **政府审批**：外资准入、土地审批、行业准入等
- **第三方同意**：是否涉及股东优先购买权等？

### 2.5 交易场景风险推理（核心，必做）

基于 §2.1 解构出的**各交易模块**，自主推理三张工作清单（多模块时按模块分别推理后合并去重）：

#### 清单一：核心必备要素

自问："要让这笔交易能实际履行，合同至少要写清哪些信息？"

参考维度（根据具体交易灵活补充）：交易标的描述要素、对价/费用结构、履行安排、完成/验收标准、风险转移节点。

→ Step 2 Layer 2 中逐项检查，缺失标记 P0。

#### 清单二：高频风险点

自问："这类交易实践中最常出现什么纠纷？合同怎么预防？"

→ Step 3 中逐项核查合同是否已覆盖。

#### 清单三：易遗漏保护条款

自问："站在我方立场，经常忘记约定但出事就被动的条款？"

**新增退出条件**：如合同已有该方向的保护条款且保护力度合理，标记为✓已覆盖，不生成批注。

→ Step 3 中逐项核查。

#### 推理质量自检（输出清单后立即执行）

- 清单一：逐项自问"缺少这项交易能正常履行吗？"能→降级或删除
- 清单二/三：逐项自问"这与**这笔具体交易**相关吗？"与具体交易无关的泛化条目→删除
- 如发现独特风险未覆盖→优先补充

#### 输出格式（强制锚定标记）

```
===== 交易场景推理清单 =====
【清单一：核心必备要素】
1. ...

【清单二：高频风险点】
1. ... — 建议等级：P{n}

【清单三：易遗漏保护条款】
1. ... — 建议等级：P{n}
===== 清单结束 =====
```

## §3 审查合同结构（存在性检查）

只回答"**有还是没有**"。条款写得好不好留给 §4。

执行顺序：Layer 1 → Layer 2 → Layer 3。

### 3.1 Layer 1：基础文本检查

1. **错别字**— 对照 appendices.md 附录C
2. **标点符号**— 中英文标点混用
3. **金额大小写**— 数字与大写是否一致
4. **日期期间**— 合同期限计算是否准确
5. **条款序号**— 正确、连续、不跳号
6. **法规/技术规范引用**— 是否有效、最新
7. **主体称谓一致性**— 全文统一
8. **附件完整性**— 正文列明的附件齐全
9. **留空检查**— `____`、`【】`、`[xxx]`、`{xxx}`、空白表格
10. **条款重复**— 是否存在表述重复

### 3.2 Layer 2：必备条款完整性

#### ⭐ 强制输出：必备条款存在性 Checklist

**必须逐行输出以下 11 项存在性检查表**，每项标注 ✓（存在）或 ✗（缺失）。**不输出本表视为 Layer 2 未完成。**

| # | 必备条款 | 缺失时等级 | 关键子项 |
|---|---------|-----------|---------|
| 1 | 主体信息 | P2 | 双方全称、法定代表人 |
| 2 | 标的条款 | P0 | 交易内容描述、范围界定 |
| 3 | 履行安排 | P1 | 期限、地点、方式 |
| 4 | 价款与支付 | P0 | 总金额(大小写)、币种、含税情况、付款节点 |
| 5 | 质量标准与验收 | P1 | 验收标准、流程、期限 |
| 6 | 权利义务 | P1 | 甲乙双方各至少1项权利和义务 |
| 7 | 违约责任 | P0 | 违约情形及责任、违约金计算 |
| 8 | 争议解决 | P1 | 仲裁或诉讼(二选一) |
| 9 | 保密条款 | P2 | 缺失时提示补充；涉敏感场景在批注中重点提示，等级固定 P2 |
| 10 | 合同效力 | P1 | 生效条件、有效期、终止条件 |
| 11 | 交易类型特有条款 | P1 | 由 Step 1 推理确定 |

**强制输出格式**：

```
===== 必备条款存在性检查 =====
| # | 条款类型 | 存在? | 条款位置 | 缺失等级 | 备注 |
|----|---------|-------|---------|---------|------|
| 1  | 主体信息 | ✓    | 首部    | -       |      |
| 2  | 标的条款 | ✓    | 第1条   | -       |      |
| 3  | 履行安排 | ✓    | 第X条   | -       |      |
| 4  | 价款与支付 | ✓  | 第X条   | -       |      |
| 5  | 质量标准与验收 | ✓ | 第X条 | -       |      |
| 6  | 权利义务 | ✓    | 第X条   | -       |      |
| 7  | 违约责任 | ✓    | 第X条   | -       |      |
| 8  | 争议解决 | ✓    | 第X条   | -       |      |
| 9  | 保密条款 | ✗    | 缺失    | P2      | 一般商务合同法定兜底；涉敏感场景重点提示 |
| 10 | 合同效力 | ✓    | 第X条   | -       |      |
| 11 | 交易类型特有 | ✓ | 第X条   | -       | {条款名称} |
===== 检查完成：✓=X项 / ✗=Y项 =====
```

> **设计目的**：将"应有但缺失"从隐式推理变为显式逐行判定，确保每一类条款都被明确检查。第 9 项保密条款必须明确判定存在与否；缺失时固定 P2（一般商务合同有法定默认兜底），涉技术秘密/源代码/用户个人信息/核心商业数据等敏感场景时在批注中重点提示业务方，等级不上浮。

### 3.3 Layer 2：核心商业要素完整性

逐项对照 **Step 1 清单一**，检查每项要素是否已填写具体内容。空白、占位符、"详见附件"但附件不存在→视为缺失→P0。

### 3.4 Layer 3：逻辑一致性检查

> **强制要求(必读)**:Layer 3 的 4 项脚本验证(§3.4.2 期限 / §3.4.3 金额 / §3.4.6 交叉引用 / §3.4.7 流向矛盾)采用**聚合 TOML + verify_all.py 一次调用**方式执行,不再分别 4 次调用子脚本。
>
> **标准流程**:
> 1. 从合同中按 4 项检查分别提取结构化数据
> 2. 合并到一份聚合 TOML(顶层 4 个表:`[amounts]` / `[dates]` / `[cross_refs]` / `[payment_flow]`),与 §3 的 `[modifications]` 共用同一个 `review_all.toml`
> 3. 一次调用:
>    ```bash
>    python3 scripts/build_json.py --from-toml review_all.toml --multi
>    python3 scripts/verify_all.py --from-toml review_all.toml --output verify_results.json
>    ```
> 4. LLM 读一次 `verify_results.json`,取出 4 个子字段分别解读
>
> 下面各小节(3.4.2/3/6/7)的 JSON schema 仍是脚本输入格式——TOML 只是书写层的语法,经 build_json.py 后就是一样的 JSON。

#### 3.4.1 主体一致性
合同各处名称是否一致（首部、正文、落款、附件）。

#### 3.4.2 期限一致性（⭐ 必须调用脚本，不得跳过）

> **强制要求**：期限计算**必须**通过脚本执行精确月数计算。禁止以"心算"或"目测"替代脚本。脚本执行失败时方可降级为手动计算，但必须在审查摘要中声明。

**执行方式**：LLM 提取 → **必须调用脚本**→ LLM 解读

**第一步：LLM 提取结构化数据**

从合同中提取以下信息，整理为 JSON 格式：
- `review_date`：当前审查日期
- `contract_term`：合同整体期限（起止日期 + 约定时长）
- `date_pairs`：所有需要校验的日期/期限对（保密期限、竞业限制期限等）
- `key_dates`：关键日期节点（付款日、交付日等）
- `renewal`：续约条款

JSON 格式详见 `scripts/verify_dates.py` 文件头注释。

> ⚠️ 提取的 JSON 必须通过 `write_file` 工具写入文件（如 `dates.json`），禁止通过 bash 输出。详见 modification-engine.md。

**第二步：调用脚本**

```bash
python3 scripts/verify_dates.py --json dates.json --output results.json
```

**第三步：LLM 解读结果**

读取脚本输出，对每项 `status: "fail"` 的检查：
- `term_duration_consistency`：约定时长与起止日期不一致 → P0
- `contract_expired`：合同已过期 → P0
- `contract_backdate`：倒签风险 → P1/P2
- `date_pair_duration`：子期限不一致 → P0
- `key_date_dependency`：关键日期超出约定 → P1
- `auto_renewal`：续约通知期过短 → P2

**脚本覆盖的检查项**：
- 约定时长 vs 起止日期精确月数计算（如"1年" vs 11个月）
- 合同是否已过期
- 倒签风险检测
- 各子期限（保密期、竞业限制期等）一致性
- 关键日期节点与依赖条件的一致性
- 续约条款合理性

> ⚠️ **含尾日整期不是风险**：合同/授权期限惯例采用"闭区间含尾日"写法——
> "X 年，自某年某月某日起"，终止日写作到期年同月**减一日**（含当日）即为完整 X 年。
> 例如"授权 3 年，自 2026/5/1 起，至 2029/4/30 止"是标准的完整 3 年，**完全一致**。
> 脚本已通过 `is_inclusive_term_match` 自动识别这种写法并判 PASS，
> 结果中会带 `"inclusive_end": true` 标记。LLM 解读时**不得**把含尾日整期当作期限不一致风险上报。

**降级方案**（仅当脚本执行报错时启用）：
- LLM 手动计算：从起始日期逐月推算到终止日期，得出精确月数，对比约定时长
- 示例：起始 2026-02-01，终止 2027-01-01 → 实际间隔 = 11 个月 ≠ "1年"（12个月）→ P0
- **必须在审查摘要中声明**："⚠️ 日期验证脚本未执行（原因：{error}），已降级为手动计算"

#### 3.4.3 金额一致性（⭐ 必须调用脚本，不得跳过）

**执行方式**：LLM 提取 → **必须调用脚本**→ LLM 解读

> **强制要求**：金额验证**必须**通过脚本执行确定性计算。禁止以"心算"或"目测"替代脚本。脚本执行失败时，方可降级为手动计算，但必须在审查摘要"验证工具执行状态"中声明降级原因。

**第一步：LLM 提取结构化数据**

从合同中提取以下信息，整理为 JSON 格式：
- `total_amount`：合同总金额（如为空白/未填写，标注为 null）
- `installments`：各期付款（金额 + 百分比 + 条款位置）
- `deposit`：定金/订金信息
- `penalty_rates`：违约金日利率
- `amounts_uppercase`：大小写金额对照

JSON 格式详见 `scripts/verify_amounts.py` 文件头注释。

> ⚠️ 提取的 JSON 必须通过 `write_file` 工具写入文件（如 `amounts.json`），禁止通过 bash 输出。详见 modification-engine.md。

**特别注意**：当总额为空白（null）但各期同时约定了百分比和金额时，脚本会从各期百分比和金额**反推总额是否自洽**（如 20%=3万→总额15万，40%=5万→总额12.5万→不一致→fail）。这是手动审查最容易遗漏的场景。

**第二步：调用脚本**

```bash
python3 scripts/verify_amounts.py --json amounts.json --output results.json
```

**第三步：LLM 解读结果**

读取脚本输出的 `results.json`，对每项 `status: "fail"` 的检查：
- 定位到具体条款（`clauses` 字段）
- 按 `risk_level` 生成对应等级的批注
- 在批注中引用脚本计算的具体数值（如"百分比合计 105% ≠ 100%"）

**降级方案**（仅当脚本执行报错时启用）：
- LLM 手动计算以下核心项：
  - 大写金额与小写金额是否一致
  - 分期付款各期金额/比例之和是否等于总金额/100%
  - **各期具体金额是否与总价×百分比一致**（当总额未知时，从各期数据反推交叉验证）
- **必须在审查摘要中声明**："⚠️ 金额验证脚本未执行（原因：{error}），已降级为手动计算"

#### 3.4.4 条款一致性
同一事项在不同条款中的表述是否一致。

#### 3.4.5 逻辑顺畅
权利义务的履行时间顺序应明确，不能存在逻辑混乱。

#### 3.4.6 条款交叉引用深度核验（⭐ 必须调用脚本 + 语义复核）

> **强制要求**：交叉引用核验**必须**调用脚本执行结构层验证，并完成语义层复核。脚本执行失败时方可降级，但必须在审查摘要中声明。

##### 第一步：构建条款编号-标题索引表

通读全文，提取所有层级的条款编号及标题，构建索引表。覆盖所有层级（第X条、第X.X条、第X.X.X条），确认编号连续性。

##### 第二步：提取并核验所有交叉引用

扫描全文，提取所有交叉引用表达式（"第X条""见第X条""依据第X条""定义见第X条"等），执行三层核验：

| 核验层次 | 检测内容 | 风险等级 |
|----------|----------|----------|
| ① 编号存在性 | 被引条款编号在索引表中是否存在 | P0 |
| ② 内容相关性 | 被引条款实际内容与引用语境是否匹配 | P0 |
| ③ 定义匹配性 | "定义见第X条"中被引条款是否包含该术语定义 | P1 |

> **重点**："定义见第X条"模式是最高风险的引用类型——必须验证被引条款**确实包含该术语的首次定义**，而非仅验证编号存在。

##### 第三步：调用脚本执行结构层验证（必须执行）

**LLM 提取**：从合同中提取条款索引和交叉引用，整理为 JSON。格式详见 `scripts/verify_cross_references.py` 文件头注释。

> ⚠️ 提取的 JSON 必须通过 `write_file` 工具写入文件（如 `cross_refs.json`），禁止通过 bash 输出。详见 modification-engine.md。

**调用脚本**：

```bash
python3 scripts/verify_cross_references.py --json cross_refs.json --output results.json
```

**LLM 语义复核**：

读取脚本输出的 `results.json`：
- `conclusion: "P0"` → 直接生成 P0 批注（引用目标不存在）
- `conclusion: "P0_suspect"` 或 `"needs_review"` → **必须**阅读 `llm_review_queue` 中的指令，逐条核查被引条款实际内容是否与引用语境匹配
- `conclusion: "pass"` → 跳过

**关键：不得跳过 `llm_review_queue` 中的复核任务。**脚本只做结构层（编号存在性+标题初筛），语义匹配必须由 LLM 完成。

##### 第四步：输出核验结果（强制，缺失视为未完成核验）

**表1：条款编号索引表**
| 编号 | 标题/主题 |
|------|----------|
| 第1条 | ... |
| ... | ... |

**表2：交叉引用核验结果表**
| 引用位置 | 引用表达式 | 被引编号 | ①存在性 | ②相关性 | ③定义匹配 | 结论 |
|----------|-----------|---------|---------|---------|----------|------|
| 第X条 | "依据第Y条" | 第Y条 | ✓/❌ | ✓/❌ | ✓/❌/— | P0/P1/通过 |

如合同无任何交叉引用，明确输出："本合同未包含条款间交叉引用，跳过核验。"

**降级方案**（仅当脚本执行报错时启用）：
- LLM 手动执行三层核验，逐一验证每处交叉引用
- **必须在审查摘要中声明**："⚠️ 交叉引用验证脚本未执行（原因：{error}），已降级为手动核验"

#### 3.4.7 条款间逻辑矛盾检测（⭐ 必须调用脚本 + LLM 补充）

> **强制要求**：流向/归属类矛盾检测**必须**通过脚本执行确定性比对。脚本执行失败时方可降级，但必须在审查摘要中声明。

**检测方法：LLM 提取 → 脚本确定性比对（4类） → LLM 补充（3类）**

##### 脚本覆盖（4类，必须调用）

| 索引维度 | 脚本检测内容 | 矛盾等级 |
|----------|-------------|---------|
| **付款流向**| 同一付款事项在不同条款中的付款方→收款方是否一致 | P0 |
| **费用承担主体**| 同一费用在不同条款中的承担方是否一致 | P0 |
| **义务执行方**| 同一义务在不同条款中的执行方是否一致 | P0 |
| **权利归属**| 同一权利（IP/成果/数据）在不同条款中的归属是否一致 | P0 |

##### LLM 补充（3类，手动比对）

| 索引维度 | LLM 检测内容 | 矛盾等级 |
|----------|-------------|---------|
| 时间节点 | 同一期限在不同条款中数值是否一致 | P0 |
| 金额/比例 | 同一金额/比例在不同条款中是否一致 | P0 |
| 条件/标准 | 同一标准在不同条款中描述是否一致 | P1 |

##### 第一步：LLM 提取结构化数据

从合同中提取以下信息，整理为 JSON：
- `parties`：合同各方信息（甲方、乙方全称）
- `payment_items`：所有涉及付款/收款的条款（付款方、收款方、金额、条款位置）
- `fee_items`：所有费用承担条款（承担方、条款位置）
- `obligation_items`：所有义务执行条款（执行方、条款位置）
- `right_items`：所有权利归属条款（归属方、条款位置）

**提取要点**：
- 付款流向是最容易被 LLM 全局语义框架"自动纠正"而忽略的矛盾类型，提取时必须忠实于条款原文
- 同一事项在多处出现时，每处都要独立提取，使用相同的 `label`

JSON 格式详见 `scripts/verify_payment_flow.py` 文件头注释。

> ⚠️ 提取的 JSON 必须通过 `write_file` 工具写入文件（如 `payment_flow.json`），禁止通过 bash 输出。详见 modification-engine.md。

##### 第二步：调用脚本

```bash
python3 scripts/verify_payment_flow.py --json payment_flow.json --output results.json
```

##### 第三步：LLM 解读脚本结果 + 补充检测

读取脚本输出，对每项 `status: "fail"` 的矛盾：
- 定位到具体条款（`details` 中的 `clause` 字段）
- 在较后出现的一处标记 Track Change，批注引用两处原文
- 所有矛盾均为 P0

然后 LLM 手动执行时间节点/金额/条件三类补充检测：
- 构建关键要素索引
- 同一要素在所有出现位置的表述逐一比对
- 发现矛盾时同样标记 Track Change

**降级方案**（仅当脚本执行报错时启用）：
- LLM 手动执行全部 7 类矛盾检测
- **必须在审查摘要中声明**："⚠️ 流向矛盾检测脚本未执行（原因：{error}），已降级为手动检测"

## §4 审查合同条款（质量审查）

逐条审查"写得怎么样"——四个维度评估：

| 维度 | 核心问题 |
|------|---------|
| 合规性 | 是否违反法律强制性规定？ |
| 可操作性 | 履行顺序明确？标准可量化？ |
| 公平性 | **仅检测不利于我方的不对等**。对我方有利的不对等属有利条款，不批注。同时覆盖"对我方明显不利的倾向"——凡条款整体导向损害我方利益的，均纳入本维度 |
| 周延性 | 条款完整，无遗漏关键情形？ |

### 4.1 标的条款

根据标的性质（物/行为/权利）逐项检查描述是否充分、可执行。

### 4.2 价格和支付条款

重点检查：
- 税前/税后是否明确
- 预付款比例（**仅当我方付款时**检查是否≤30%）
- "定金"与"订金"是否区分（定金≤20%）
- 逾期付款违约金/滞纳金标准
- **我方付款时**对方是否有开票义务

### 4.3 违约条款

重点检查：
- **对方**主要义务是否都有对应违约责任（我方义务无违约责任→有利→不报）
- 违约金日利率折年化是否≤24%（**仅审查我方**违约金；对方违约金高→有利→不报）
- 我方违约责任是否明显高于对方
- **对方**是否有随时解除权（有正当理由+通知期→合理→不报）
- 间接损失方向审查（见 risk-library 规则36）
- 我方赔偿总额是否有上限（对方无上限→有利→不报）

### 4.4 争议解决条款

- 仲裁和诉讼是否同时约定
- 仲裁机构名称是否完整准确
- 管辖是否对我方有利
- **约定"合同签订地"为管辖法院/仲裁地时，回查合同首部、落款、签署栏是否实际写明了具体签订地（城市/区县）**（见 rules.json C-26）——签订地缺失或留空会使"签订地管辖"无法落地，最终落回法定默认管辖（如被告住所地），我方可能被拖去异地应诉；P1
- 涉外合同是否明确适用法律

### 4.5 合同生效、解除、终止

- 生效条件（见 risk-library 规则25 触发前提）
- 合同起始日期是否早于审查日期（倒签风险→P1）
- 合同截止日期是否早于审查日期（已过期→P0）
- 自动续约（见 risk-library 规则28 触发前提）
- 终止后义务（已有概括性兜底条款→不报）

### 4.6 知识产权条款（⚠️ P0 高危区域）

- **IP 归属一致性**：检查 IP 归属条款中“定义名称”与“归属方向”是否自相矛盾（例：定义名为“甲方知识产权”但归属为乙方 → P0 矛盾）
- **定制开发穿透判定**：即使合同标题为“采购”，若合同内容包含定制开发/技术开发条款，仍按定制开发标准审查 IP 条款
- **不侵权承诺**：涉及定制开发/内容创作/技术合作时必查；纯标品采购不强求
- **合作 IP 归属**：合作项目中产出 IP 应约定归我方
- **衍生知识产权**：利用一方 IP 产生的衍生 IP 归属是否合理，是否与主 IP 归属一致

### 4.7 交易场景推理叠加

将 Step 1 清单二和清单三作为额外审查依据，逐项核查：
- 清单二中的风险点未在合同中预防→按建议等级标记
- 清单三中的保护条款在合同中缺失→按建议等级标记
- **清单三退出条件**：合同已有该方向保护条款且力度合理→标记✓已覆盖→不批注

### 4.8 陷阱检测

逐项扫描 [陷阱检测清单](trap-detection.md)，**执行规则**：
1. **跳过标注 `⚙RL-X` 的规则**——这些已在 Step 3 风险库匹配阶段执行，重复扫描会导致同一问题双重批注
2. **仅执行 16 条独有规则**：F-01、F-05、F-10、L-10、L-11、L-12、S-02、S-17~S-25（与 trap-detection.index.json 的 active_rules 一致）
3. 严格遵守每条规则的触发前提

### 4.9 类型专属规则（⭐ 条件加载，与通用规则统一排序执行）

当 Step 0 加载了类型专属规则文件（如 sale.md 的 SP-01~SP-08）时，**不单独作为最后一块补充执行**，而是把类型专属规则与通用规则（risk-library + trap-detection 独有规则）在加载阶段**合并成一个统一规则集**，按 **P0 → P1 → P2**统一排序后一起跑——重要风险（P0）自然前置，类型专属的 P0 不会被排在通用 P2 之后。

**执行方式**：
1. 加载类型文件后，把其每条规则（带编号、等级、触发前提）并入当前规则集
2. 统一按等级 P0→P1→P2 排序，逐条检查：触发前提满足？→ 合同存在该风险？→ 生成批注
3. **去重规则**：同一风险若已被 risk-library / trap-detection 规则命中并批注，则跳过类型规则的重复项，不双重批注
   - **重复问题单条批注**：同一性质问题在多个条款反复出现时，只在首次出现处批注一条，正文末尾追加"另在第X条、第Y条也存在同样问题，建议一并修改。"（列出全部重复条款序号），取真实等级不降级，只占 1 条批注配额
4. 类型规则的"我方为买方/卖方时触发"等方向前提，与通用规则的持方方向保持一致判定

> **设计原则**：类型专属规则不是"附加层"而是"同级规则"，与通用规则同池排序。这样类型特有的 P0（如买卖合同 SP-01 货物描述不完整）能与通用 P0 一起最先被处理，避免因执行顺序靠后而被 15 条批注上限截断。

### 修改记录格式

```
位置：第X条 X.X（一律用条款号/性质词定位，禁用 clean_text 段号）
原文：{原文摘录}
风险等级：P0/P1/P2
风险分析：{点明不改会引发的具体后果，稍带法言法语、金额比例写具体}（写入批注时上限 P0≤60/P1≤60/P2≤35 字）
修改建议：{具体修改内容}（写入批注时上限 P0≤60/P1≤60/P2≤35 字）
立场检验：✓（对我方有利/至少不损害）
```

## §5 审查质量门控（⭐ 强制执行 · 全 skill 唯一权威门控表）

**时机**：Step 2-3 全部审查完成后、生成最终 JSON/docx 之前。

**目的**：确保关键检查项未被遗漏，避免"设计了但没执行"的系统性风险。

> **单一信息源约定**：本表是整个 skill 唯一的权威门控自检表。SKILL.md §五仅作摘要指针，执行时以本表为准、按本表逐行回填。修改门控项只改本处。


### 门控规则

- **10/10 ✓**（+ 第 11 项 ✓ 或 N.A.）→ 直接进入输出阶段（build_json 写入 JSON → apply_review → upload_file 提供下载）
- **存在 ✗**→ **必须回溯补做对应检查**，补做完成后更新门控表状态，确认全部 ✓ 后才可进入输出阶段
- **第 1 项不允许降级**：格式统一与修订预处理是审查正确性的前提，pipeline prepare 失败时停止审查
- **第 4 项允许 "✗(降级)"**：verify_all.py 整体执行失败时，声明降级原因改用手动计算。子脚本粒度的失败由 verify_all.py 的 summary 汇总
- **第 8 项不允许降级**：JSON 生成必须走 TOML → build_json.py，不走其他路径
- **第 11 项条件执行**：Step 0 加载了类型专属规则文件时必须为 ✓；未加载任何类型文件时填 N.A.，不阻断输出

### 门控失败补做示例

```
门控检查发现 #3 状态为 ✗（保密条款未判定）
→ 回溯 Layer 2 checklist，补充第9行保密条款判定
→ 本合同涉及源代码/算法、合作开发等敏感场景
→ 保密条款缺失，固定 P2，并在批注中提示业务方重点关注敏感信息保护
→ 更新门控表 #3 为 ✓，继续输出
```

## 修改执行流程

1. **备份**：`cp original.docx original_backup.docx`
2. **收集修改**：将 §3-§4 的所有修改整理为 TOML，按 P0>P1>P2 排序
3. **数量控制**：批注最多 15 条（按优先级保留前 15 条；**P0 级全部保留**，仅在 P1 及以下级别中执行截断）
4. **批量执行**：调用 `scripts/apply_review.py`（技术细节见 modification-engine.md）
5. **最终验证**：对照 [补充验证清单](review-checklist.md) 核查
6. **输出文件**：通过宿主环境的文件上传工具提供下载链接，并生成审查摘要
