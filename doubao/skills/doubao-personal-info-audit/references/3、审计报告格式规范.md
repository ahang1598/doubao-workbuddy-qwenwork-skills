# 审计报告格式规范

## 一、适用原则

本规范同时控制报告的内容顺序、观点呈现和Word版式。用户提供的样例优先；未另行指定时，以“证据—事实—不确定性—数据分类—处理活动—法律角色—处理情形—适用规则—审计结论—风险—整改”为不可改变的分析顺序，并采用Claude式“先查明事实、再完成法律定性、最后形成结论和整改”的六任务正文。不得退化为只有“概况—依据—发现—结论”的空泛通用模板。

Markdown仅是中间格式。最终DOCX、PDF和打印稿不得出现Markdown控制符、工具引用令牌、代码围栏、未处理占位符或裸露的长URL。

## 二、成果形态

根据证据和程序选择名称，不得一律称为正式审计报告：

| 成果等级 | 建议名称 | 是否给出整体审计意见 |
|---|---|---|
| L0 | 个人信息保护法规研究/专题分析 | 否 |
| L1 | 个人信息保护合规差距分析 | 否 |
| L2 | 个人信息保护有限程序审计报告 | 仅可给出有限范围结论，不得外推 |
| L3 | 个人信息保护合规审计报告 | 是 |
| L4 | 个人信息保护合规审计报告（监管要求） | 是，并满足法定签署及报送要求 |

L0—L2使用精简封面和六任务正文；L3—L4使用完整封面、文档控制页、审计摘要、六任务正文、整体意见、签署页和附件。

## 三、报告结构

### （一）封面

至少列明报告名称、审计对象、成果等级、审计期间、审计基准日、报告编号、版本、密级、出具机构和出具日期。封面不显示正文页码。

### （二）文档控制页（L3—L4强制）

列明编制人、复核人、批准人、签发日期、分发对象、修订记录、使用限制和独立性声明。无法取得的信息不得编造，以“待委托方确认”标识并在交付前清零。

### （三）审计摘要

控制在一至三页，至少包括：

1. 审计对象、范围、期间、基准日和触发事由；
2. 管理层责任、审计方责任、独立性和报告用途；
3. 主要处理场景、数据规模、高风险场景和范围排除；
4. 审计程序、抽样和限制；
5. 关键发现、风险分布、整改优先级；
6. L3—L4的整体审计意见；L0—L2的成果边界声明。

### （四）正文六任务链

正文固定按下列顺序组织。章节名称可结合项目微调，但不得改变逻辑顺序。

#### 任务一：证据、事实与不确定性识别

先列证据目录和证明力，再使用一张“证据、事实与待补数据综合表”完成事实讨论。不得将证据、冲突、尚待核实和补充材料拆散到表外。统一使用“链条编号｜讨论项目｜内容”三列纵向表；同一F事实连续列示E证据及精确定位、材料三级识别、评价单元与原子事实、事实来源类型、样本与外推边界、证据状态与证明力、冲突/相反证据、U不确定性及竞争性假设、待补数据与核验程序、十类交叉核验结果。

“证据状态与证明力”必须明确区分“材料未提及”“证据不足”“已经证明不存在”和“已由直接证据确认”。事实列不得混入合规、违法、委托处理等法律评价；冲突和不确定性不得藏在脚注或报告末尾。

#### 任务二：数据与个人信息分类

逐项判断个人信息、敏感个人信息、匿名化/去标识化状态，必须结合具体业务环境、控制人及接收方的关联能力，不得只按字段名称判断。建议使用比较表；复杂项目可在表后逐项展开。

#### 任务三：处理活动、法律角色与处理情形

先列A处理活动，再判断RO法律角色，最后识别SC处理情形。角色包括自主处理、共同处理、委托处理、独立接收、对外提供、公开、转移和出境等；处理情形包括合法性基础、告知、敏感信息、未成年人、自动化决策、AI、人脸识别、跨境、保存删除等。企业合同标签或内部命名不得代替实质判断。对不能确定的关系和情形列出U编号及最小补证要求。另设“处理情形与模块适用性矩阵”，逐条展示A/RO和触发事实、情形状态、触发或排除要素、候选规则、关联模块及核验程序；“不涉及”必须有积极排除事实。

#### 任务四：适用规则与合规审计分析

先列关键问题摘要，再按重要性展开。不得机械抄录全部107项；完整点检进入底稿和附件。每项问题固定使用两张表，不得改为连续的标签段落：

```text
问题X：【能够表达争议核心的标题】

表X-A 参考法条与规范
列：法源编号及层级｜规范名称及条款｜具体规则内容｜本案对应要件及效力说明。层级与编号、要件与效力分别合并，以便为规则正文保留足够列宽。

表X-B 11环节审计分析链
采用三列纵向表“顺序及环节｜编号与直接上游｜分析内容”。行序固定为：①证据E、②事实F、③不确定性U、④数据分类D、⑤处理活动A、⑥法律角色RO、⑦处理情形SC、⑧适用规则NR、⑨审计结论C、⑩风险RK、⑪整改RM。
```

法条表的“具体规则内容”不得只重复规范名称或条号。逐字引用时使用引号并确认已核对官方文本；无法逐字核对或不宜全文复制时，写准确规则摘要并明确标记“规则摘要，非原文”。标准应展示本项目实际依赖的具体控制要求，并注明强制性、推荐性或合同转化依据。

事实、证据、证据缺口、相反证据和待补数据必须在同一张表X-B中闭环。每一行引用直接上游编号，不得从E直接跳到C。不得在表外另写“已确认事实：”“审计证据：”“待核实事项：”造成读者跨页查找。

#### 任务五：风险评价与整改建议

风险和整改必须与任务四的C、RK、RM编号一一对应，但可按根因合并措施。每项至少列明风险对象、期间和理由，以及整改目标、核验措施、具体措施、责任部门、配合部门、优先级、期限、验收标准、整改证据、管理层回应和风险接受批准。禁止只写“加强管理”“完善制度”。

#### 任务六：审计限制与补充材料

至少包括：待补数据汇总、可形成的结论、暂不能形成结论的事项、正式意见限制、材料真实性责任、抽样和程序限制、范围及期间限制、基准日后事项、法律版本边界、使用对象和未决事项影响。待补数据汇总只能交叉引用任务一和任务四的U记录，不得在本章首次提出或重新拆分事实证据讨论。

### （五）总体审计结论与意见

L3—L4在任务六后单设本节；L0—L2不得冒用正式整体意见。本节汇总26模块107子项结果、重大问题、根因和影响范围，并仅选择以下一种意见：

1. 在所有重大方面符合；
2. 除已列明事项外，在重大方面符合；
3. 不符合；
4. 无法形成整体意见。

意见必须同时说明评价基准、范围、期间、重要性、主要保留事项或无法取证事项。不得使用“基本合规”等非标准意见。

### （六）签署页

L4按监管规则设置专业机构主要负责人、合规审计负责人签字和公章；L3按委托约定设置。L0—L2可设置编制、复核栏，但不得伪造姓名、签名或机构信息。

### （七）附件

按以下顺序编排：

1. 附件一：审计发现与整改清单；
2. 附件二：法源与文献数据库；
3. 附件三：证据与材料目录；
4. 附件四：处理活动、角色和数据流摘要；
5. 附件五：11环节追溯矩阵；
6. 附件六：107项点检索引；
7. 附件七：管理层反馈及整改承诺；
8. 附件八：AI与高风险场景专项分析（适用时）；
9. 附件九：其他解释说明材料。

## 四、引文与观点

### （一）编号

| 类型 | 编号 | 用途 |
|---|---|---|
| 法律、行政法规 | L001… | 直接法源 |
| 部门规章、司法解释、规范性文件 | R001… | 直接或补充法源 |
| 标准、实践指南 | S001… | 强制或辅助实施依据 |
| 案例与决定 | J001… | 裁判、指导案例和行政处罚决定 |
| 政策材料 | P001… | 问答、公告、指南和草案 |
| 证据材料 | E001… | 审计证据 |
| 原子事实 | F001… | 事实索引 |
| 审计发现 | C001… | 结论与整改闭环 |
| 不确定性 | U001… | 缺口、冲突和核验程序 |
| 数据分类 | D001… | 信息属性和分类结论 |
| 处理活动 | A001… | 目的、动作、系统和流向 |
| 法律角色 | RO001… | 处理者、共同处理、受托等 |
| 处理情形 | SC001… | 专项处理场景及适用性 |
| 适用规则 | NR001… | 具体规则、要件、例外和效力 |
| 风险 | RK001… | 风险等级、对象、期间和理由 |
| 整改 | RM001… | 目标、措施、责任、期限和验收 |

### （二）正文引法

- 法律：`〔L001，《中华人民共和国个人信息保护法》，第十三条第一款第（二）项〕`
- 部门规章：`〔R003，《个人信息保护合规审计管理办法》，第十条〕`
- 标准：`〔S001，GB/T 46903—2025，第6.3.2条，推荐性实施参考〕`
- 证据：`〔E012，《SDK清单（V3.2）》，工作表“SDK”，第18行〕`
- 组合：`〔F021；E012；L001，第十三条第一款第（二）项〕`

连续引用不得只写“同上”。直接引语使用引号并精确定位；转述不得伪装成法规原文。正文不堆叠URL，官方链接和完整元数据进入附件二。

正文引用的每一项L/AR/R/S法源均须进入相应问题的“参考法条与规范”表，并展示具体规则内容。正文不得只写规范名称、条号或`〔L001，第X条〕`而没有规则内容。相同规则在同一问题中不得重复；跨问题使用时，可再次列示，或准确交叉引用已展示规则内容的表号和行号。细化规范适用时，上位法与下位法/配套规范分别成行并在第四列说明衔接与触发事实；不适用时正文仅保留上位法，排除过程留在底稿。

### （三）法源元数据

每项法源至少记录编号、层级、完整名称、制定机关、文号、公布日期、施行日期、失效日期、基准日状态、适用范围、引用条款、官方URL、核验日期和替代关系。未来施行规则标记“尚未施行”，征求意见稿标记“草案”，均不得作为基准日的确定性义务。

### （四）观点表达

采用“结论—法源—事实—证据—推理—相反证据—限制”结构。禁止使用没有主体、场景、数据和行为的“存在一定风险”“建议进一步加强”等空泛表达。证据不足时明确写“无法判断”，不得将“材料未提及”改写成“不存在”。

## 六、表格

1. 只在存在重复字段或比较关系时使用表格；不得用窄表格包裹长篇分析。
2. 表题置于表格上方，写为“表X  表名”，12 pt、加粗、左对齐。
3. 表头10.5 pt、加粗、水平和垂直居中；正文10.5 pt，叙述列左对齐，编号、日期、结论列居中。
4. 显式设置表宽、列宽、单元格边距和表格缩进；禁止固定行高导致裁切。
5. 跨页表格重复表头，禁止拆分单行；结论不得只靠颜色表达。
6. “法律依据”列必须列明条、款、项或标准章节，不得只写“相关规定”。
7. 法条表统一使用四列：法源编号及层级、规范名称及条款、具体规则内容、本案对应要件及效力说明；不得通过缩小到不可读字号解决长内容。
8. 任务一至任务三使用三列纵向表；单项问题的11环节分析链也使用三列纵向表，优先将最宽列分配给“分析内容”，不得使用十一列横向表。

## 七、页眉页脚、目录和分页

- 首页不同，不在封面显示页眉和页码。
- 正文页眉左侧为报告简称，右侧为密级或版本号；页脚居中连续编号。
- L3—L4在控制页后生成自动目录；L0—L2超过15页时生成目录。
- 一级标题原则上另页起；同一问题的标题与首段不得分离；避免孤行、异常空白页和跨页截断。

## 八、生成和视觉校验

1. 使用`assets/templates/审计报告正文模板.md`起草，不得重新发明章节顺序。
2. 生成DOCX后检查页面、字体、字号、行距、段距、缩进、标题、目录、页眉页脚和签署页。
3. 检查表格宽度、重复表头、跨页和文字截断。
4. 检查中英文混排字体、引用编号连续性和法源元数据。
5. 使用LibreOffice渲染PDF和逐页图像，以100%比例检查全部页面；修复后重新渲染。
6. 未完成视觉渲染不得宣称“格式校验通过”。

## 九、禁止事项

- 强制采用与任务逻辑脱节的七章通用模板；
- 省略或倒置证据、事实、不确定性、数据分类、处理活动、法律角色、处理情形、适用规则、审计结论、风险、整改中的任何环节；
- 把107项底稿全文复制进正文；
- 将法规摘要当作审计观点；
- 仅列法规名称、仅列URL或使用“相关法规”；
- 只列条号而不展示所依赖的具体规则内容；
- 将事实、证据、冲突、不确定性和待补数据分散到不同章节或表格；
- 把推荐性标准写成当然强制；
- 把未来规则或草案写成现行义务；
- 使用蓝色装饰标题、手工空格缩进或固定表格行高；
- 省略范围限制、责任、独立性、签署要求或管理层回应。
