# HTML 报告交付规范

本文件只规定股票研究的交付路由、信息结构和组件选择。正文准入、表达和删稿遵循 `writing-quality.md`。HTML 生成命令以本包 `scripts/render_html_report.py` 为准。

需要股价图、K 线、象限图、敏感性热力图、瀑布图等高级金融视觉时，同时读取 `advanced-html-visuals.md`。

## 1. 先设置 delivery_mode

在检索、分析或起草前锁定 `TEXT` 或 `HTML_REPORT` 并运行计划门禁。只有一至三句即可无损回答单一事实、口径或决策问题，且不需要结构化比较、图示或复杂证据链时，使用 `TEXT`；其他情况使用 `HTML_REPORT`。条件失效或生成高级组件时升级为 `HTML_REPORT`。

`HTML_REPORT` 的流程是：计划章节与图表 → 完成事实校验及读者版 Markdown → 用 `scripts/render_html_report.py` 生成自包含 HTML → 在浏览器复核结构、数据、来源、图表与移动端 → 运行最终门禁 → 交付 HTML 文件链接。无需在线文档认证。

## 2. HTML 生成前的校验

先完成事实校验、正文删稿和图表数据门禁。读者版 Markdown 中以 `{{embed:相对路径.html}}` 独立一行嵌入脚本生成的交互图；PNG/SVG 以 Markdown 图片语法引用。生成器将这些资源内嵌进单文件 HTML，报告离线打开时仍能阅读和使用图表。生成后打开最终 HTML，确认图表及引用正常。

## 3. 专业研究文档的信息顺序

默认按读者决策顺序组织，不套固定的“公司简介—行业—财务”模板：

1. **标题与研究元信息**：证券名称/代码、市场、信息截止日、币种、会计或价格口径；
2. **核心结论**：先直接回答用户问题，说明方向、最关键原因、判断边界与最大风险；
3. **核心金融与财务快照**：分析具体证券、公司、板块、股票池或组合时，按 `core-financial-snapshot.md` 用一张紧凑表格列 4–10 个最重要字段；确实不相关时才省略；
4. **决定结论的证据**：核心结论区通常 3–5 条，按影响判断的重要性排序；
5. **主体分析**：只展开用户问题需要的行业、商业模式、基本面、预期、估值或价格归因；
6. **最强反证与证伪条件**：不要把风险降格成页尾泛泛清单；
7. **验证点/催化剂**：写清指标、阈值、时间窗和数据来源；
8. **数据来源与方法**：读者可复核即可，冗长细节放附录；
9. **免责声明**：完整研究报告最后保留规定文本。

骨架阶段读取 `suggested-writing-templates.md`，按体裁选择一个主模板并裁剪栏目；跨体裁任务只嵌入必要模块。模板只帮助组织通过准入门槛的内容，不替代能力选择，不要求填满，也不得覆盖 `required_sections` 所代表的真实分析需要。

核心结论必须出现在正文最前部。若使用高亮块，全文通常只把这一处作为唯一重强调；若核心判断不确定，明确写出数据缺口或条件，不用颜色制造虚假的确定感。

### 信息密度门禁

大纲只列会改变用户判断的章节。检索笔记、覆盖矩阵结果和候选新闻属于工作材料，不自动进入文档。写正文前按 `writing-quality.md` 逐项筛选；证据弱、时点不明、没有传导机制、与前文重复或只提供背景的信息不得发布。

正文采用“结论 → 最少充分证据 → 含义/验证点”。一段只证明一个判断；一张表或图只回答一个问题。不要把同一结论同时写进高亮块、段落、表格和图注。信息不足时主动缩短报告，不使用更多栏目、背景或样式填充篇幅。

### 复杂结构的篇幅控制

在骨架阶段把用户问题与分析链所需章节写入 `required_sections`。复杂文档应通过节内压缩、紧凑表格、删除弱证据及把审计细节移到附录来控制篇幅；不得仅因为文档较长而删除或合并承担不同逻辑功能的章节。最终打开后，把实际一级/二级结构写入 `actual_sections`，逐项确认包含所有 `required_sections`。

## 4. 组件选择矩阵

由信息关系选择组件，不按“每篇都要有”的配额选择。

| 研究内容 | 首选表达 | 适用边界 |
|---|---|---|
| 核心结论、重大口径提醒、关键数据缺口 | 高亮块 | 仅强提醒；通常 0–1 个，避免每节一个 |
| 多空逻辑、结论与反证、公司 A 与 B 的短对照 | 对比分栏 | 两侧信息量接近且内容短；有多指标时改用表格 |
| 财务趋势、分部、同业、估值、情景、事件窗口 | 表格 | 真正行列数据；统一期间、币种、单位和口径 |
| 产业链、盈利驱动树、因果传导、风险链路 | 传导链 HTML 图表组件| 仅用于少量按阅读顺序排列的节点；图旁保留一句可独立理解的结论 |
| 双轴定位、同业分层、候选优先级、风险重要性 | 多象限 HTML 图表组件| 两个维度、刻度和分割阈值必须可解释；不代替原始数据表 |
| 单股价格路径、涨跌归因、量价和事件窗口 | 脚本生成的 K 线或股价 HTML 图表组件| 完整同口径 OHLC 使用 K 线；仅有可靠收盘价/分时价时使用股价图。注明复权、币种、时区、窗口和来源，仅按 `advanced-html-visuals.md` 明确例外退出 |
| KPI、盈利预期、估值或折溢价的可比趋势 | 趋势 HTML 图表组件| 1–5 组同期间、同单位、同口径序列；少量精确数字用表格 |
| 盈利、现金流、指引或估值桥接 | 瀑布 HTML 图表组件| 起终点和桥接项可复算；只保留重要驱动 |
| 两变量敏感性矩阵 | 热力图 HTML 图表组件| 基准格、单位和数值必须可见；小矩阵用表格 |
| 催化剂、监管与事件时序 | 时间线 HTML 图表组件| 只保留重要节点，区分发生/公布/可交易日 |
| 其他交互趋势和信息密集视图 | HTML 图表组件| 表格不足时使用；不要只为装饰创建 |
| 公式与关键假设 | 公式或简洁段落 | 展示可复算的关键公式，不把整篇写成方法论文 |
| 叙述、机制、判断与解释 | 连贯段落 | 默认表达；不要机械拆成 bullet 或卡片 |
| 来源、公告、监管文件 | 可点击引用/来源列表 | 来源紧随事实，并保留发布日期和截止日 |

### 高亮块

适合放“结论 + 关键条件 + 最大风险”的短摘要，不要把完整正文塞入。颜色保持语义一致：信息用中性/蓝色，风险用红色，待确认用黄色；不要用绿色或红色暗示无条件买卖建议。

### 对比分栏

适合以下短对照：

- 支持核心判断的证据 vs 最强反证；
- 牛方逻辑 vs 熊方逻辑；
- 现状 vs 触发重新评估的条件。

若每侧超过少量要点、需要跨行比较或含多期数值，改用表格。分栏不能替代三情景估值表。

### 表格

一张表只回答一个问题。表头写明期间，标题或注释写明币种、单位、是否复权、FY/CY/TTM、法定/调整后。重要变化优先展示绝对值与同比/环比，避免只用颜色表达涨跌。典型表格包括：

- 核心 KPI 与盈利桥；
- 同业经营和估值比较；
- Bull/Base/Bear 情景、关键假设、估值结果与触发条件；
- 催化剂/风险的时间、概率依据、影响路径与验证指标；
- 股价事件窗口与基准相对表现。

### 结构型 HTML 图表组件

结构关系只有在图示明显比段落更快回答问题时才使用 HTML：

- 少量节点的 `行业变量 → 业务量价 → 利润率/现金流 → 预期修正 → 估值` 传导链；
- 简洁价值链、盈利驱动、证据树或证伪路径；
- 风险传播或组合暴露链；
- 两个清晰维度上的同业、候选或风险项目定位。

传导链使用 `lark_charts.py flow`，象限使用 `lark_visuals.py quadrant`。精确数字回到正文表格；超过生成器节点上限、分支复杂或需要大量说明时，改用分节段落和表格。

### HTML 图表组件

仅当交互或高密度可视化有实质价值时使用，例如带悬停明细和事件标记的 K 线、可切换期间的 KPI 图、估值敏感性热力图、价格—盈利预期联动图或组合风险面板。遵守本包 `scripts/render_html_report.py` 对单文件、尺寸、资源和运行时的限制，并满足：

- 先由既有脚本生成单文件图表 HTML，再在读者版 Markdown 用 `{{embed:相对路径.html}}` 引用，由报告生成器嵌入完整 HTML；不得手写图表 HTML；
- HTML 图表组件前后各有一段文本，说明它回答的问题和读者应看到的结论；
- 关键结论不能只存在于交互组件内；
- 不内联大体积数据或图片，不把同一张表再做一遍 HTML；
- K 线只使用完整、严格升序、同一复权口径的 OHLC；只有收盘价时运行 `lark_visuals.py price`，不得手写图表 HTML 或补造 OHLC；
- 若静态表格足够，优先表格。

## 5. 体裁模板路由

按 `suggested-writing-templates.md` 的路由表选择一页纸、完整个股研究、财报前瞻、财报解读、模型更新、盈利预测修正、非共识、差异认知识别、估值、反向 DCF、股价归因、行业、同业比较、股票筛选、市场晨报、收盘复盘、市场周报、组合风险、论点跟踪或 A/H 相对价值模板。使用通用完整报告外壳确保元信息、核心结论、金融快照、反证、验证、来源和免责声明完整，再用主模板组织主体分析。跨体裁任务只嵌入必要模块，不拼接多份完整报告。

## 6. 生成与校验

1. 按 `core-financial-snapshot.md`、`writing-quality.md` 和适用模板形成完整读者版 Markdown，保留 `required_sections`；复杂引用按 `script-usage.md` 运行 `report_pipeline.py` 生成来源章节。
2. 运行 `python3 scripts/render_html_report.py <读者版正文.md> --output <报告.html>`。图表使用既有脚本生成，并嵌入最终 HTML。
3. 打开最终 HTML，复核核心结论位置、章节、引用、表格口径、图表交互与免责声明；检查移动端宽度、标签碰撞、配色和打印效果。
4. 按 `writing-quality.md` 删除低质量和重复内容；若正文或图表修改，重新生成 HTML 并再次复核。
5. 把实际章节写入 `actual_sections`，确认 `quality_checks`、`visual_checks` 和跨产物数据一致性后运行 `delivery_gate.py --phase final`。
6. 门禁通过后，在聊天中返回一至三句核心结论和 HTML 文件链接。

## 7. 最终交付门禁（必须执行）

发送最终回复前，盘点正文和图表中实际使用的高级组件，更新交付清单并运行 `scripts/delivery_gate.py --phase final <manifest.json>`。`HTML_REPORT` 必须有真实存在的完整 `.html` 文件，`html_created=true`、`html_path=<实际文件路径>`、`file_verified=true`。这些字段只能在最后一次生成后打开 HTML 并核对正文、表格、引用、图表和免责声明后填写。

若有交互图表，逐图记录独立问题、来源单位、无重复编码及实际渲染；`html_block_checks.embedded_in_html_report=true` 和 `html_block_checks.chart_source_embedded=true` 表示图表已嵌入完整报告。所有模式还必须完成跨产物数据对账并设置 `data_consistency_verified=true`。报告生成失败或渲染有误时保持未完成，修复并重新生成、复核后再交付。
