# 画布资产语义目录工作流

> 先按主 SKILL 判断交付环境。system 明示 `Device platfrom: Mobile` 时遵循 [Mobile 直接交付](mobile-app-direct-delivery.md)：Brief／素材记录留在本地，跳过本文全部 Workspace、Canvas CLI、Item 与卡片步骤，媒体逐项直接交付、HTML 预览走 CDN＋Markdown。其他环境执行本文默认 Canvas 分支。生产与编辑顺序不变。

本文件负责画布内部资产索引的判断、整理和维护。它不改变用户可见布局，也不替代 CLI 字段协议、HTML schema 或交付校验。

HTML 作品的专用预览截图仅走 CDN 上传与 Markdown 展示，不创建 IMAGE Item、不纳入本目录；正式导出媒体和生成素材仍按当前环境的媒体门禁执行。

**产后目录整理是默认 Canvas 的必经阶段。** `image_gen`／`image_edit` 的本轮结果完成直接交付，或 HTML 完成平台写入及首次 `+get` 后，必须读取画布中的真实对象，再通过更新顶层对象的 `path` 形成语义目录。Canvas 没有独立 `mkdir`：目录由 path 自动形成，禁止伪造建目录命令或创建空 Item 充当目录。

## 1. 目标与边界

画布目录属于 **Agent 内部资产索引（internal asset index）**。目录用于把图片、视频及其他资产组织成稳定、可理解、可检索的 Semantic Cluster，降低后续定位、复用和维护成本。

- `path` 只表达资产归档；视觉位置与层级只由 `transform` 和 `z_index` 表达。
- 所有顶层 Item／Frame 的 `path` 必须以 `/` 开头；Frame 成员不填 `path`。
- 顶层先区分 `/user-anchors`、`/core-assets`、`/generated-assets` 与 `/deliverables`，再按任务、身份、用途、角色、变体或版本建立必要的多级路径；不得固定为两层，也不得建立空层或无检索价值的深层目录。
- 目录、brief 和内部关系不得进入用户可见文字。
- 目录不是实体；某个 Cluster 没有对象后无需执行目录删除。
- 仅整理目录时，不得改变对象 ID、内容、资产 URL、transform、z-index、对象类型或 Frame 边界。

## 2. 触发条件

出现以下任一情况时评估并更新目录：

- 新增、批量生成或导入大量资产；
- 修改、替换、删除或发现缺失资产；
- 从原资产生成裁切、抠图、变体、延展或其他衍生资产；
- Generation Batch 或共同创作任务结束；
- 现有目录不能稳定定位资产；
- 用户要求重新整理资产。
- 继续创作、修改、衍生、做同系列或恢复历史任务。
- 本轮生图批次已经完成通过 `RichMediaCard` 直接交付，或 HTML 作品已经写入并完成首次 `+get` 回读。

手工 `+create`／`+create-batch` 的少量新资产仍应直接写入稳定 path 和准确 brief。图像工具自动关联的结果可能尚无稳定 path，统一进入下述产后整理；不得为提前写 path 重复创建 IMAGE Item 或第二个 HTML Item。

## 3. 产物完成后的强制目录整理

本阶段只在默认 Canvas 执行，且不得抢在媒体交付之前：

1. **等待产物闭环**：`image_gen`／`image_edit` 的每个成功结果先按媒体门禁使用 `RichMediaCard` 直接逐项交付；串行依赖与并行批次按原规则汇合。HTML 作品已经写入并完成首次 `+get` 回读。目录整理不替代这些交付和写入步骤。
2. **读取画布骨架**：调用 `+tree --path /`，必要时对 `/` 及候选分支调用 `+ls`，取得真实顶层对象 ID。优先使用本轮工具返回的真实 Item ID／结果句柄与任务记录缩小范围；无法映射时不得凭标题或时间猜测。
3. **读取实际内容**：对本轮新增对象和归类所需的少量候选分批调用 `design-cli design-workspace +get`，每批遵守最多 10 个 ID 的限制。至少核对对象 ID、type、title、brief、asset、现有 path，以及可用的来源关系。禁止用 `+get-workspace` 代替对象读取，也不把 `+get` 变成图片交付门禁。
4. **形成最小目录计划**：只整理本轮产物及与其关系明确的锚点，不顺手改动整个 Workspace。默认路径语义如下，可按任务增加必要层级：
   - 用户输入参考：`/user-anchors/<task>/source`
   - 核心品牌／商品／Logo 母版：`/core-assets/<identity>/master`
   - 生图素材与衍生图：`/generated-assets/<task>/<role>/<variant-or-version>`
   - HTML 与最终交付物：`/deliverables/<task>/<format>/<version>`
5. **以 path 创建目录**：使用 `+update`／`+update-batch` 只修改顶层对象的绝对 `path`；目录随 path 自动形成。brief 仍准确时不得顺手改写。图像工具结果不执行 `+create`，正式 HTML 历史版本不覆盖。
6. **回读验收**：执行 `+tree`／`+ls` 查看形成的目录，再对已移动对象按需 `+get`，确认 ID、内容、资产 URL、来源、transform、z-index 和类型未改变。失败时停止继续移动，保留已知真实状态并进入排障。

对于纯生图任务，产后目录整理发生在全部要求结果完成直接交付之后；对于含 HTML 的任务，在最终 HTML Item 卡片 `present_files("<workspace_id>?item_id=<item_id>")` 前完成，使最终卡片指向已经归档并回读的对象。目录整理失败不允许通过重复生成或重复创建对象来规避。

## 4. Semantic Cluster 判断

只能根据当前真实可得信息判断资产归属，不补造用户意图、生成关系或内容语义。证据优先级固定为：

```text
用户显式意图
>
用户上传的原始资产锚点（如有）
>
资产生成 / 编辑关系
>
共同创作任务
>
Generation Batch
>
资产内容语义
>
创建时间关系
>
资产类型及其他 Metadata
```

高优先级证据与低优先级证据冲突时采用高优先级证据。低优先级只在更高优先级缺失或无法区分时补充判断。

“用户上传的原始资产锚点”是可选证据，只在当前 Workspace 中存在由用户上传、已按第 5 节写入目录并成功回读的初始锚点时启用。它指向用户提供的原始来源 Item、锚点 ID、资产短链、brief 与受保护特征，不包括 Agent 生成后被临时选中的候选图。没有此类上传资产时跳过该层，继续使用资产生成／编辑关系判断；不得虚构原始锚点来提高某个生成资产的优先级。

`brief` 是语义入口，不是独立证据等级。brief 中的用户用途按“用户显式意图”判断，已核验的 `source_anchor_id`／`core_asset_id` 按“用户上传的原始资产锚点”判断，“由 A 抠图生成”按“资产生成／编辑关系”判断。brief 与当前用户意图、任务记录、真实资产关系或 `+get` 内容冲突时，将其视为过期摘要。

Semantic Cluster 使用稳定语义命名，优先表达用户目标、原始锚点、衍生关系和共同任务。用户上传的原始锚点与 Agent 生成资产必须可区分且可追溯；不得仅因文件类型相同、创建时间相近或 brief 文案相似就合并无关资产。

## 5. 用户上传的初始视觉锚点

用户上传视觉锚点、Logo、产品图或明确要求作为后续生成依据的图片时，不得只保留本地路径、会话附件引用或 Prompt 描述。开始生成、编辑或衍生前，必须执行以下动作：

先实际查看每张输入，区分产品／人物身份、风格、版式和事实证据。身份图决定“是谁／是什么”，风格图只决定视觉语言，版式图只决定结构；同一图承担多种职责时分别说明。参考图中的其他产品、文字、Logo 和界面不因其好看而成为可替换内容。用户已提供主体产品图时必须登记为身份源，不能以“没有核心资产”绕过；多款产品或多张图无法对应时先确认，不猜型号。

1. 取得可由 CLI 使用的已上传资产短链；只有本地路径时先完成上传，禁止把本地路径写入 `<asset><url>`。
2. 使用 `+create`／`+create-batch` 将原始文件写成可回读的顶层 Item，并写入稳定 path 与 brief。Logo、产品图及其他身份母版写入 `/core-assets/<语义名>/master`；不承担身份母版作用的构图、色彩或风格参考写入 `/user-anchors/<任务或语义名>/source`。
3. 保存服务端返回的锚点 Item ID：普通视觉锚点登记为 `source_anchor_id`，身份母版登记为 `core_asset_id`；并通过 `+get` 回读资产 URL、path、brief 与对象身份。回读成功前禁止开始下游生成。
4. `+create` 时 brief 记录“用户上传／初始视觉锚点”、当前作用、来源、受保护特征及允许变化，不得要求预先写入尚未返回的自身 Item ID，也不得在创建后为了补自身 ID 而 `+update` brief。返回的 `source_anchor_id`／`core_asset_id`、短链与确认状态保存到已有任务／资产记录；衍生物的 brief 才引用来源 ID。不得把推断出的品牌、型号、权属或用途写成事实。
5. 下游衍生物记录 `derived_from_core_asset_id` 或 `derived_from_visual_anchor_id`；工具未返回这些 ID 时记录等价母版句柄。每次调用前，将本次需要保留的身份源绑定到宿主工具实际接收图片的参数，核对图片输入与锚点对应；Prompt 写了产品名、文件名或 ID，以及“已参考”的自述，都不等于工具收到了图片。风格／版式参考不能替代身份输入。修改已有成品时以成品为 edit target、原始母版为身份参考；工具无法同时接收必要图片时停止该调用并说明限制，不降级为纯文本近似重绘。`image_edit` 结果通过透传 Workspace ID 关联画布，不再执行 `+create` 或填写新的 `<source_ids>`；手工创建的其他对象继续遵守来源 ID 规则。
6. 在已有资产记录中保留本次调用的图片输入、对应锚点与输出关系，不另建重复索引。仅需直接摆放的原素材可沿既有复用／抠图流程使用，不为建立关系强制重生。首张 KV 和每张正式衍生图均实际对照原图检查轮廓、比例、部件、包装配色、标签与 Logo；首张错误不得作为后续风格确认或身份母版。

**禁止偏移**是指未经用户明确要求，不得替换或覆盖原始锚点、把衍生图提升为新母版、把锚点迁出其稳定目录，或在衍生物中改变受保护的 Logo 轮廓与比例、品牌色、商品结构、包装识别、关键构图关系及用户指定视觉特征。用户明确要求修改某项受保护特征时，只解除该项约束，其他不变量继续保留，并在 brief 中记录变更范围与新版本关系。

初始视觉锚点用于锁定来源和视觉连续性，不等于强制创建 Frame，也不要求改变其视觉布局。除非锚点本身就是完整交付物，否则它保持为独立顶层 Item。

## 6. 核心资产锚点

创作或编辑开始前，判断是否存在决定其他物料身份的核心商品、品牌或 Logo。满足任一条件即需要核心锚点：

- 用户明确指定其为主体或母版；
- 多个交付物需要持续复用同一身份；
- 后续视觉围绕同一商品外观、品牌识别或 Logo 轮廓生产系列衍生物；
- 品类规范要求锁定真实商品或品牌身份。

只有主题、风格或普通装饰相似，不足以认定为核心资产。核心母版必须由用户提供、经过事实核验，或在 0→1 品牌／Logo 任务中已经确认并通过身份验收。母版缺失、冲突或未确认时，停止衍生生产。

确认后执行：

1. 用户上传或本地资产按 Item 规则登记到 `/core-assets/<品牌或商品语义名>/master`；由 `image_gen`／`image_edit` 产生的母版通过调用时透传的 Workspace ID 直接关联画布，不再另行 `+create`。结果先通过 `RichMediaCard` 直接交付，本轮生成完成后再按第 3 节通过 `+get` 读取平台已关联对象并归档。
2. 母版 brief 或素材记录保存核心身份、来源／确认状态、当前用途、版本和身份不变量；优先记录工具返回的 `core_asset_id`，若工具未返回该字段则记录 Workspace ID、工具调用标识与原始结果句柄，不猜测或补造 ID。
3. 所有包含该身份的新场景图、KV、详情图、包装或品牌应用必须以母版作为 `image_edit` 的 edit target／身份参考，并在实际工具调用中传入母版图片，不能只写 ID 或 Prompt。并行衍生 N 个同源变体时，先锁定互不依赖的 N 个任务，再分别调用 N 次 `image_edit`，单母版衍生时每次使用同一张已确认母版；编辑既有成品时同时保留必要的成品 edit target 与原始母版身份参考，各次使用同一组已确认输入，不一次请求多张输出、不把前一衍生结果作为下一次输入。每次记录同一母版的 ID、版本与短链；不得使用纯文本 `image_gen` 重绘相似对象。
4. `image_edit` 衍生资产由透传的 Workspace ID 直接关联画布；不得为结果另行创建 IMAGE Item。素材记录写入用途、`image_edit` 版本、身份核验结果，以及可用的 `derived_from_core_asset_id` 或等价母版句柄。手工创建的非图像工具对象仍按目录与 `<source_ids>` 规则管理。
5. 每个衍生物与母版逐张核验。身份漂移时重做；连续失败时沿用已选路线及原停止条件：AI + Coding 可在本路线内使用母版抠图或确定性合成；pure-image 仍按图像编辑路线处理，不自动转分层或合成。能力不足时说明限制，不无限重试。

核心锚点是身份与衍生关系索引，不是 Frame。除非母版本身是完整可交付物，否则不得因其重要而创建额外 Frame。

## 7. 读取、判断与写回

1. 对继续创作、修改、衍生、同系列或历史恢复任务，先按 [CLI 命令与执行策略](../cli/README.md) 使用 `+tree → +ls → +get` 恢复历史上传锚点、核心母版、可复用生成资产、既有交付物及版本／衍生关系；不得只依赖当前对话记忆。普通新建任务使用 `+tree` 获取必要目录骨架，再用 `+ls` 读取候选对象 brief。
2. brief 足够且不与高优先级证据冲突时直接归类；brief 含糊、过期、冲突或无法区分时，只对少量候选执行 `+get`，同时读取任务、批次和资产关系记录。
3. 新建非 `image_gen`／`image_edit` 的 Item／Frame 时，在 `+create`／`+create-batch` 载荷中直接写入 path 和 brief；目录由对象 path 自动形成。若新对象由画布现有对象派生，还必须按 CLI 创建协议写入 `<source_ids>`。图像工具结果禁止重复创建 Item；完成直接交付后按第 3 节读取平台已关联对象，并仅更新其 path。
4. 修改或衍生资产默认继承能够解释其来源和用途的 Cluster；出现更高优先级证据时迁移到其指向的 Cluster。
5. 重新整理已有资产时用 `+update`／`+update-batch` 修改 path。brief 仍准确时只改 path；资产语义、用途或关系变化时，先 `+get` 核实并在同次更新中修正 brief。
6. Frame 必须整体读取和整体更新；Frame 成员不写 path。
7. 写回后再次调用 `+tree`／`+ls`，并按需 `+get` 核对对象身份、brief、path 和未改变字段。

信息不足时按最高可用证据进行最小必要归类，保留准确的最小 brief；不得为了完美分类阻塞创作，也不得凭空推断。获得新证据后增量调整。

## 8. brief 写法

brief 优先回答“资产是什么”和“在当前任务中的用途”，已知时再补充来源／衍生关系、所属产物、必要批次或版本。

禁止：

- 把 path、类型名、坐标或风格形容词堆成摘要；
- 把未知信息写成事实；
- 仅因目录整理而无理由改写仍然准确的 brief；
- 将 brief 渲染到画布可见层。

## 9. 根目录未命名资产与 OrganizeAgent

当历史 Workspace 中存在与本轮无明确关系的大量根目录未命名资产、brief 为空或无法表达稳定语义时，按 [画布编辑执行策略](canvas-editing-strategy.md) 启动独立异步任务 **`OrganizeAgent`**。本轮新生成且用途已由 Brief、素材清单或生成记录明确的对象，由 Main Agent 按第 3 节直接完成产后整理，不触发 OrganizeAgent。

传入最小上下文：Workspace ID、根目录 `+tree`／`+ls` 结果、候选 ID、当前任务与 Generation Batch、已知生成／编辑关系，以及本文件的证据优先级。

`OrganizeAgent` 只能更新必要的 brief 与 path，并保持对象 ID、内容、URL、transform、z-index 和 Frame 边界不变。环境无法创建异步任务时，保持对象不变并报告尚未整理。

## 10. 验收与失败处理

完成后执行 [交付验证](validation.md)，至少确认：

- 每个顶层 Item／Frame 的 path 都能由最高可用证据解释；
- 每个顶层 path 都是绝对路径，四类顶层领域明确；延续任务在生成前已回读资产索引，没有重复生成可复用资产；
- brief 准确且来源／衍生关系未丢失；
- 用户上传的视觉锚点、Logo 和产品图已经写入稳定目录、成功回读，且所有衍生物保留来源锚点 ID 或可追溯的等价母版句柄；
- 核心资产母版唯一、已确认、可读取，衍生链可追溯；
- 手工创建的画布衍生对象的 `<source_ids>` 都来自本 Workspace 的真实 `+get` 回读，且与 `derived_from_*` 记录一致；批量创建没有混入需要分别贴近不同来源的对象；
- 原始锚点未被覆盖、替换、错误迁移或未经授权改变受保护视觉特征；
- 未因文案相似、类型或时间错误聚类；
- 目录操作没有改变可见布局、对象内容和 Frame 边界。
