# VI 内容与系统 Brief

在当前任务已有设计 Brief 中填写“VI 内容与系统结构”；没有时根据当前对话创建，同任务不另建副本。最终只保留一份品牌事实、系统内容、应用与视觉描述相互对应的 Brief。

本文件负责品牌事实、准确文案、获准母版、身份与授权边界、系统范围、应用对象、展示章节、来源和交付能力。Spec 不提前选择新视觉风格，不决定新配色、字体搭配或具体构图；用户已锁定的视觉规范作为既有约束记录。具体视觉语言由 [VI Visual](../systems/vi-visual-system.md) 在原章节、配图与应用条目中继续丰富，不另建视觉 Brief，也不另造内容来源。

## HTML 交付规范路由入口

命中 VI 后，必须在任务初始 Ref 路由阶段立即读取 [VI HTML 交付规范路由入口](../../../workflow/vi-html-delivery-route.md)，并一次性完整读取其中列出的公共 HTML Ref 及当前环境分支。禁止等到 HTML 组装、`shot.py` 或最终交付阶段才补读。该入口统一约束 Subagent 边界、禁止直接交付 HTML、CDN＋Markdown 预览、默认 Canvas 的 `FileBatchUpload`／唯一顶层 HTML Item／`+get`／画布卡片，以及 Mobile 仅预览分支。

## 最高优先级门禁：确认后的 Logo 唯一视觉锚点

Logo 本体完成并被用户确认后，它必须成为整个 VI 的唯一视觉参考。凡后续需要图像工具生成或编辑的 VI 衍生资产，包括背景、角色、插画、产品氛围图、应用场景和 Mockup，都必须调用 `image_edit`，并且只传入这一个已确认 Logo 母版作为视觉参考。禁止改用 `image_gen` 从零生成，禁止同时传入第二张风格图、材质图、角色图、产品图、场景图、历史候选或上一张衍生结果作为参考，也禁止仅凭 Prompt、文字描述或 Logo URL 文本声称已经继承视觉锚点。

该门禁不作用于 Logo 本体尚在设计和确认的阶段；一旦 Logo 被确认，后续衍生不得切换视觉锚点。用户上传的产品、人物、空间、包装或应用平稿可以作为真实内容直接复用并由 HTML 确定性放置，但不得作为图像工具的第二视觉参考。若某项衍生必须依赖另一张图片才能完成，而当前工具无法在“只传 Logo 母版”条件下执行，则停止该项生成并说明能力冲突，不得绕过本门禁。

Brief 必须记录唯一 Logo 母版的真实来源、版本、确认状态和可传入 `image_edit` 的实际资产标识。Logo 未确认、母版不可取得或出现多个冲突版本时，只能继续内容规划和原生 HTML 设计，不得调用图像工具生产 VI 衍生物。

## 最高优先级门禁：VI 首屏必须由 Logo 直接生成

Logo 已确认且完整设计规划已经告知用户后，正式 VI 的第一项图像生产必须是首屏效果：直接以该 Logo 母版为唯一参考调用 `image_edit`，生成与最终首屏画幅和视觉职责匹配的完整 Hero／品牌封面视觉。不得跳过该步骤直接用 HTML 把 Logo 贴在纯色背景上，不得改用 `image_gen`，不得先生成无 Logo 背景再拼贴，也不得把风格图、产品图、角色图、Mockup、历史候选或上一张衍生图加入参考输入。

首屏效果必须落实 [VI Visual](../systems/vi-visual-system.md) 已定义的沉浸裁切、标志／角色整合、封套陈列或身份系统预告中的一种主结构，并同时形成唯一最大视觉主体、明确品牌色场、符合 Logo 同源语言的光色／材质／空间关系，以及进入第二章的连续线索。生成结果不是随机品牌氛围图，也不是居中的小 Logo 加大量空白；它必须已经承担完整首屏的主视觉构图职责。

为保护准确品牌名、Logo 几何和可编辑文字，最终 HTML 可以在该首屏效果上叠加由同一原始 Logo 母版经 MediaKit 去底并验边通过的透明排版版本，以及 HTML/CSS 原生标题、短命题或职责说明；但这只用于准确覆盖和信息排版，不能替代首屏 `image_edit` 生产。若生成结果篡改 Logo 拼写、字形、比例、负形或核心身份，必须判为不合格，不得带入 HTML；先按公共媒体交付门禁交付并记录问题，用户要求修改后仍只使用同一确认母版重新调用 `image_edit`。

## 最高优先级门禁：VI 排版 Logo 必须抠成透明资产

确认 Logo 母版用于 `image_edit` 时保留其真实源文件和版本；但只要 Logo／字标将作为独立图片层进入 VI 的 HTML 排版、首屏准确覆盖、规范展示、应用平稿或展示板，就禁止保留白底、黑底、灰底、棋盘格或任何矩形图片背景，也禁止用 `mix-blend-mode: multiply`／`screen`、滤镜、蒙版或与页面同色的假底遮掩。带底位图必须先调用 MediaKit CLI 的 `image remove-image-background`，使用 `scene=general`、`output_format=png`，取得带真实 Alpha 的透明结果后才能排版；已有可靠 Alpha 的 PNG 或实际无底 SVG 核验通过后可直接使用，不重复抠图。

MediaKit 抠图结果必须记录原 Logo 来源、处理后短链、尺寸、Alpha、版本和采用状态，并在浅色、深色及最终品牌底色上检查外轮廓、字腔与内部孔洞、细笔画、负形、白边／色边、误删和残底。抠图只移除背景，不得重画、改字、裁掉 Logo、改变比例或把处理结果升级为新的身份母版。MediaKit 能力缺失、调用失败或透明边缘未通过时，停止该 Logo 的排版消费并报告阻断，不得回退到保留背景或混合模式。

## 最高优先级门禁：大图、大字、低空白

VI 首屏、系统章节、Identity Kit 与应用展示的整体排版，必须优先放大 Logo、主视觉、核心图片、应用物料和文字层级，使有效内容尽可能占据可用画布。每一章都从可读性、安全区、Logo 净空、裁切保护和真实载体边界允许的最大尺度开始，再缩到刚好满足约束；禁止把主体缩成小卡片、小 Logo、小图窗或窄栏后留下大面积无职责空白。

留白只保留阅读分组、品牌净空、呼吸节奏和制作安全所必需的部分。内容偏少时先放大主图、Logo、章节标题、关键数字和应用对象，允许有依据的出血、裁切和跨栏；内容偏多时先减少重复说明、横向重组或拆章，不得通过缩小字体和图片制造“精致感”。

## 最高优先级门禁：Logo 入口与确认

进入 VI 系统设计前，先判断用户是否已经提供可用 Logo：

- **用户已提供 Logo**：跳过“生成多个 Logo 风格并选择”的流程，直接核对准确品牌名、Logo 文件、版本、授权、可用背景状态和用户是否将其确认为本次母版。这里“跳过”只针对 Logo 候选生成，不会取消上文的 Logo 唯一视觉锚点规则；母版确认后，所有 VI 图像衍生仍只以该 Logo 为唯一参考。
- **用户未提供 Logo**：必须先完成 Logo 前置阶段，生成多个在核心概念、造型路线和风格语言上真正不同的 Logo 方向并逐一交付给用户选择。不能用同一标志换颜色、换字体、换 Mockup 或轻微改形冒充多个方向。用户没有明确选定并确认其中一个 Logo 前，禁止开始颜色、字体、IP、摄影、应用物料、Mockup 或整套 VI 展示设计。

无论用户是否提供 Logo，在开始正式 VI 生产前，都必须把完整设计规划作为用户可见内容告知用户，而不是只保存在内部 Brief。规划至少说明：品牌与受众理解、Logo 来源或候选阶段、推荐方向及依据、VI 范围级别、计划建立的颜色／字体／图像／IP 系统、应用触点、展示载体与章节、资产生产顺序、需要用户确认的节点、最终交付与验收边界。用户未提供 Logo 时，先告知包含 Logo 候选与选择门禁的整体规划；用户选定并确认 Logo 后，再以确认母版更新规划，然后才可开始正式 VI 设计。

## 最高优先级门禁：禁止交付 HTML 源文件；仅 HTML 生成允许调用 Subagent

VI 的完整 `.html` 是内部可编辑作品源、`FileBatchUpload` 载荷和 Canvas 顶层 HTML Item 的内容来源，**绝不是面向用户直接交付的文件**。禁止在最终答复中提供本地 `.html` 路径、Markdown 文件链接、下载附件、压缩包内 HTML、代码块、源码片段或任何让用户直接取得 HTML 源文件的出口；也禁止把 `.html` 直接传给 `present_files`。用户可见交付只有两类：同尺寸完整预览图的 CDN＋Markdown 展示，以及默认 Canvas 环境中唯一顶层 HTML Item 对应的画布卡片。

VI 设计中有且仅有进入完整 HTML 生成／修改与 `shot.py` 自检阶段时，Main Agent 才允许并且必须调用 Subagent。除此以外全部工作必须由 Main Agent 亲自完成，包括需求澄清、Ref 读取、Brief 建立与更新、设计规划输出、Logo 候选生成、Logo 确认、首屏 `image_edit`、其他 VI 图像与视频素材生产、MediaKit 抠图、素材检查、版本选择、返修调度、Workspace、CLI 写入／回读、CDN 上传、`FileBatchUpload` 和所有用户交付。禁止把这些任务拆给 Subagent，也禁止以“并行提效”“素材生产”或“质量复核”为由扩大 Subagent 范围。

Main Agent 亲自取得每个图像／视频／MediaKit 结果的原始短链和处理信息，并按照 [交付门禁](../../../workflow/image-generation-delivery-gate.md) 完成对应 CLI 写入／回读与 `present_files` 交付；双通道闭环后才能选稿、修改、衍生、进入 HTML 组装或开始下一批。Logo 候选、首屏效果、透明 Logo 和全部 VI 应用资产均遵循本规则。

### 完整 VI 手册 HTML 组装门禁

开始组装或修改完整 VI 手册 HTML 页面时，Main Agent 必须调用 Subagent 执行，不得由 Main Agent 绕过该交接直接编写 HTML。Subagent 的唯一职责是依据已确认 Logo、最终 VI 规划、已闭环素材和 [HTML 组装](../../../workflow/html-assembly.md) 完成整页 HTML，并按 [HTML 检查执行流程](../../../workflow/html-validation.md) 运行 `scripts/runtime/shot.py` 自检；为修复 HTML 或截图问题而继续修改同一 HTML 仍属于该阶段。Subagent 必须向 Main Agent 内部回传完整 HTML 文件、声明画布宽高、同尺寸本地预览结果、预览／校验状态、建议 `path`、完整 `brief` 与创建意图，然后停止；不得上传 CDN、调用 `FileBatchUpload`、操作 Workspace／CLI、调用 `present_files`、把 HTML 链接发给用户或直接完成任何用户交付。

整套 VI 无论采用连续长板、分页式章节、Brand Board 或多章手册，在 Canvas 中都视为一个完整作品：只生成并上传一个完整 HTML 文件，只创建一个顶层 HTML Item。分页仅能表现为该 HTML 内部的页面／章节容器，不得按页拆成多个 HTML 文件、多个 Item 或 Frame 成员。

Main Agent 必须按以下编号顺序完成 HTML 输出与交付，不得省略、调换或合并步骤：

1. **CDN＋Markdown 同尺寸预览**：Main Agent 接收 Subagent 使用 `shot.py` 自检后的完整预览图，确认其像素尺寸与 HTML 声明宽高一致；由 Main Agent 将预览图上传 CDN，亲自核验所得公网 HTTP(S) 链接可访问，再使用标准 Markdown 图片语法向用户展示。该预览是必需的用户可见输出，但不得调用 `present_files`、不得创建 IMAGE Item、不得写入 Workspace。
2. **使用 `FileBatchUpload` 上传完整 HTML（仅默认 Canvas）**：Main Agent 使用 `FileBatchUpload` 上传唯一完整 `.html` 文件并取得工具返回的原始短链。Subagent 禁止执行上传。该上传只为 Canvas 持久化提供输入，不是用户文件交付；禁止在聊天、Markdown、附件、`present_files` 或最终交付清单中暴露 `.html` 文件。
3. **`design-cli +create` 创建唯一顶层 HTML Item（仅默认 Canvas）**：Main Agent 使用第 2 步短链执行 `design-cli ... +create`，协议载荷中只能创建一个顶层 `<item type="HTML">`。`HTML` 是 Item 类型，`+HTML` 不是 CLI 命令；不得把 `design-cli create`、`+HTML` 或 `<frame type="HTML">` 当作替代语法。禁止 HTML Frame、Frame 成员 HTML、章节多 Item 或分页多 Item。
4. **`design-cli +get` 回读（仅默认 Canvas）**：取得 Item ID 后执行 `design-cli ... +get`，核对 HTML 短链、类型、`path`、`brief` 与对象 ID；回读失败不得进入画布卡片交付。
5. **交付画布卡片（仅默认 Canvas）**：回读成功后，将 `"<workspace_id>?item_id=<item_id>"` 作为单值传给 `present_files`。

`Device platfrom: Mobile` 环境只执行第 1 步，完成 CDN＋Markdown 预览后立即停止；禁止执行第 2–5 步，包括 HTML 上传、Workspace、CLI、Item 和画布卡片，也禁止以“用户仍需源文件”为由提供 `.html`。预览失败时按 HTML 预览策略保留“视觉未验证”状态；默认 Canvas 可继续执行第 2–5 步，但不得伪造预览成功。缺少第 1 步，或默认 Canvas 缺少第 2–5 步任一闭环时，不得把完整 VI 手册标记为完成。

使用自然语言，成品文案与规划说明分开；代码参数、模板 ID、工具字段、内部机器 Schema 和评分清单不进入 Brief。按用户范围组织内容，不强制凑齐全部系统、页数或物料品类。

本 VI 不建立、生成或交付独立辅助图形、Pattern、装饰性 Icon 或纹样系统。版面识别只使用确认后的 Logo／字标、品牌色、字体、获准 IP、产品、摄影、材料与真实内容；功能性界面图标仅在真实数字产品有操作需求时按通用可用性规则处理，不登记为品牌辅助图形。

## 背景系统结果约束

凡本品类进入 HTML/CSS 系统展示，整套作品必须建立与品牌和视觉系统相关的背景机制。背景机制可以由连续品牌色域、摄影场景、Logo／字标裁切、材料表面、纹理、肌理、渐变或空间光影承担。除 Logo 测试、色板、规范示意及具有明确品牌色／信息职责的功能纯色区外，普通展示背景必须由纹理、肌理或渐变等可观察机制承担变化，不得以无变化纯色铺满。获准的功能纯色区不因缺少装饰被判失败。

Spec 只记录背景机制的内容职责；具体色域、材质、Logo／字标使用、摄影、变化方向、生成方式与 Prompt 由 Visual 决定。不得为满足字段机械增加噪点、渐变或无品牌依据的装饰。底图效果不作为品牌事实、真实材料或生产工艺的证据。

## Brief 结构

按以下顺序组织同一 Brief；不适用项说明原因，不用空章节凑完整性。内容先确定，Visual 随后在相应位置补充可见关系。

```markdown
## VI 内容与系统结构

### 品牌事实与任务范围
- 品牌与受众：准确名称、简称、语言与大小写、业务、实际价值、服务对象、使用场景、定位与希望传达的认知
- 内容与语种：已确认描述语、口号、介绍及实际应用文案；成品文案与规划说明分开
- 品牌语言：核心命题、语气关键词、Tagline 使用范围，以及包装短句、社媒标题、说明文字之间的语气差异；未确认内容不擅自补成品牌事实
- 任务入口：沿用已有 Logo 扩展、Logo 确认后扩展，或整理已有 VI
- 范围级别：VI Lite、VI Core 或 VI Full；写明选择依据、实际包含项与不包含项
- 系统与应用范围：实际需要的识别系统，以及数字、实物、环境项目；不适用项与原因
- 展示载体与宽窄依据：记录用户指定载体、阅读方向、Brand Board／单板／分页／连续长板、目标宽高与内容分配；未指定时按下文“展示载体与宽窄判断”采用宽幅模块化长板，不把 VI 默认做成手机窄长图

### 母版、来源与身份边界
- 母版与授权：Logo、字标、产品、人物、IP 的来源、版本、确认状态与修改范围
- Logo 内容事实：品牌名准确字序、大小写、语种、发音提示、必要描述语／品类词及其是否进入组合标；未经用户提供或确认，不增加 `TM`、`®`、`©`、成立年份、城市、口号或其他事实性附文
- Logo 需求范围：需要字标、图形标、组合标、角色标、缩写标／副标中的哪些真实形式，各自承担什么场景；候选方向与正式家族分开记录
- 身份约束：已确认固定特征、仅可延展项、可重设计项与禁区；新视觉规则留待 Visual
- 参考意图：构图、风格、物料体系或局部效果参考；不继承参考中的品牌事实
- 配图计划：唯一 Logo 视觉锚点的真实 URL 短链，以及产品／人物／空间照片、主题素材与应用样机的数量、真实 URL 短链、直接复用／HTML 确定性放置方式及用途；后者不得作为图像工具的第二视觉参考
- 缺口与待核实：授权、母版、文案、字体资源、制作参数和未覆盖应用
```

## 展示载体与宽窄判断

先确定最终展示板的明确尺寸或不可变载体；没有此类约束时，默认采用 `1600px` 宽幅模块化长板。参考图形态、素材方向和内容组织只能影响板内构图，不能越过该优先级改变宽窄。

- **采用窄幅**：仅限用户明确指定最终交付为手机长图、竖向长卷、紧凑 Brand Board 或窄幅发布位；用户明确要求沿用主参考的竖向品牌总览板组织方式；本次直接续改的既有源设计已经锁定窄幅；或最终展示板对应的真实发布载体本身为不可变窄幅。记录目标宽高、观看场景和必须保持的纵向顺序。参考图只是竖版、图片素材偏竖、包装／海报／手机界面等应用物为竖向、内容较多或需要滚动阅读，均不单独构成窄幅依据；必须有用户对展示形式的明确意图。
- **采用宽幅**：VI 提案、品牌作品集展示、系统规则与应用总览、需要并列比较母版／变体／平稿／场景，或需要同时呈现不同尺度物料。用户未指定最终展示板尺寸／载体时默认本项，使用 `1600 × 900 px` 的 16:9 横向视域组织主要章节；用户指定其他宽幅尺寸时按该尺寸组织横向章节。模块化长板表示宽度稳定、章节纵向累加，不表示窄幅。
- **采用独立分页**：用户明确要求演示文稿、提案页、手册或逐页播放时，每页固定为用户尺寸；未指定时采用 16:9，不将多页合成一个超长页面。
- **采用真实应用尺寸**：包装平稿、海报、界面、导视等应用稿使用自己的真实载体尺寸；它们进入展示板时作为对象或图窗，不反向决定展示板窄宽。

宽幅模块化长板不是把所有内容塞进一张 16:9 页面，也不是把多张窄卡片放大。它以稳定宽画布承载多个横向章节，每章有独立结论、主焦点和结束点；章节高度可不同，但优先利用横向并列、尺度差和矩阵关系消化内容。内容增加时先横向重组、增加章节或增加总高度，整体仍过长再拆为多张宽幅长板，不缩窄板宽或持续堆成单列长条。

## Logo 母版内容与确认门禁

VI 需要新 Logo 时，Spec 只冻结 Logo 的准确内容、业务职责、必要形式、授权边界和验收任务，具体造型由 Visual 与主流程的 Logo 生产步骤决定。必须生成并交付多个核心概念、造型路线与风格语言真正不同的候选供用户选择；候选数量由能够形成有效选择的方向决定，不用同一方案的轻微变体凑数。Logo 母版尚未被用户明确确认时，只能规划并向用户告知 VI 章节、应用职责、生产顺序和交付边界，不得开始系统设计，不得冻结基于其轮廓、负形或字形派生的辅助系统，也不得把某张候选图直接登记为正式母版。

品牌名称已知时，每个候选和确认后的标准 Logo 母版都必须包含准确品牌名，并形成字标或图文组合标；禁止只输出独立图形、角色头像、物件符号、首字母图标或抽象符号。品牌名必须属于 Logo 本体的主要识别层，不能缩成角落说明。独立图形标只能在组合母版确认后作为家族附属版本派生。品牌名称未知时先澄清，不得用占位文字或纯图形绕过。

### Logo 内容 Brief

- **准确文字**：逐字记录品牌名、大小写、空格、连字符、重音符号、中文／拉丁文字关系、必要品类描述和唯一允许的断行。创意字形不得改变品牌拼写或让关键字符无法识别。
- **核心概念**：用一句话说明 Logo 需要压缩的品牌记忆点，以及它来自名称、产品、行为、受众或品牌态度中的哪项真实依据；同时记录不应出现的俗套隐喻和无关行业符号。
- **形式职责**：确定主标是字标、图形标、组合标、角色标或图文一体标；其他形式只在有真实应用需要时派生。副标、缩写标和图形标不是额外创意方向。
- **语气与识别**：记录需要呈现的力度、亲和度、秩序、幽默、手作感或实验程度，以及必须保留的可读性和业务可信度；不只写“高级、年轻、有趣”。
- **候选风格坐标**：用户未提供 Logo 时，分别记录候选在几何—有机、理性—亲和、极简—叙事、字标—符号—角色、静态—动势、标准—实验等维度的位置。候选必须占据不同坐标组合，不能只改颜色、字体名称或应用背景。
- **背景与透明状态**：记录 Logo 母版的真实源背景，以及排版消费版本是否具有可靠 Alpha。任何带底位图进入 VI 排版前都必须用 MediaKit `remove-image-background` 的 `general` 场景输出透明 PNG 并验边；禁止在 VI 排版中保留图片背景或用 `multiply`／`screen` 代替抠图。
- **使用环境**：记录最小使用场景、远近阅读、横／竖空间、深浅背景、单色印刷、数字头像、招牌或包装等真实约束，供 Visual 决定家族和简化级别。

### 候选、确认与家族边界

Logo 候选用于比较不同核心概念、造型路线和风格语言，不能把同一标志的轻微粗细、旋转、颜色或 Mockup 变化冒充多个方向。所有候选必须分别交付并说明概念、识别机制、适用气质、主要优势与风险，让用户能够完成明确选择。用户确认一个方向后，才围绕同一母版建立主标、横／竖组合、独立字标、独立图形标、紧凑副标、单色、反白和小尺寸简化；所有形式必须说明从母版保留了什么、为何适配对应场景。

候选确认至少核对准确文字、核心概念、黑白轮廓、主要负形、字符可读性、图文关系和目标场景。品牌名已知时，纯图形候选或只把名称作为角落注释的候选不得进入选择。场景效果图只用于验证，不能替代白底／黑底标准母版；生成图片、位图预览或样机也不能被描述为已经存在的矢量源。只有确认后的唯一母版可以成为 VI 核心视觉锚点。

## IP 与可编辑能力

### 角色内容与叙事职责

是否启用 IP 取决于品牌沟通、陪伴、导览、运营叙事或周边的真实需求；不用角色时，以产品、摄影序列或应用关系承接内容，不强行增加角色页。

IP 内容先确定名称、类别、品牌职责和母版，以可观察的行为描述性格，避免互相冲突的形容词。记录轮廓、头身比例、五官关系、标志部位、身体与服装配色、性格行为的已确认内容。表情、姿态、服装、道具、节庆或场景变化必须有实际用途并在授权范围内；2D 转 3D、毛绒或纸艺不等于换角色。

多个角色分别说明共同点、差异、家族关系和各自母版。保留能判断一致性的基准视图或真实源；单张正面图不足以证明所有角度一致。实体可行性需要专业制作或打样，不能由效果图保证。

### 真实编辑与交付能力

分别说明 HTML/CSS 原生可编辑文字和布局、可整体替换的位图素材、实际存在的外部专业母版、仅供预览的成图。场景图片中的文字不称为独立可编辑文字；需要修改图片内设计时，应回到对应平稿或专业源。

位图不冒充矢量或 3D 源，效果板不替代应用源稿，展示板中的包装不等于可印刷包装。交付声明以实际存在且可打开、可修改的内容为准。

## 应用条目的内容结构

- 数字应用按需求选择官网、界面、社交媒体、演示文稿、头像或数字广告；实物应用按需求选择包装、袋、杯、卡片、徽章、服装或文具；环境应用按需求选择门店、展台、导视、活动空间、陈列或装置。
- 每项写清谁在什么场合使用、需要传达或完成什么，并写入实际文案、引用资产、尺寸、载体及特殊条件，不只列物料名称。
- 说明各应用共用什么、内容职责有何差异，以及需要验证的阅读距离、材料、大小或状态。视觉上的固定与变化由 Visual 在这些条目中建立。
- 明确概念示意、正式平稿与真实业务材料的界限，不把提案内容称为已投入使用。
- 应用稿、包装平面、实际刀模、场景效果示意和展示板分别列明；只交付其中一部分时如实限定范围。

### 应用物料交付矩阵

应用物料从真实业务触点选择，不要求所有品牌机械生成同一套 Mockup；但只要品牌具有门店、线下服务、员工接触或周边传播场景，就必须在规划与交付范围中显式评估以下类别，选中的物料写入准确尺寸、使用人、阅读距离、材料、平稿、场景和交付状态：

| 类别 | 可选交付物料 | 需要证明什么 |
| --- | --- | --- |
| 店铺与空间场景 | 门头、橱窗、入口、收银台、吧台、菜单区、货架、墙面、桌面、等候区、快闪店、展台、活动空间 | 品牌在远景、中景和近景中的识别连续性，以及顾客进入、选择和停留时的真实体验 |
| 灯牌与导视 | 发光字、灯箱、侧招、吊牌、霓虹／轮廓灯、楼层牌、方向牌、营业信息牌、门牌、价格／菜单灯牌 | 昼夜状态、发光方式、阅读距离、安装位置、深浅背景与 Logo 反白／正色适配 |
| 员工服装与穿戴 | T 恤、Polo、卫衣、围裙、帽子、外套、袖章、工牌、胸牌、挂绳、员工证 | 正反面、胸口／背部／袖口位置、动作遮挡、织物折痕、姓名与岗位信息层级 |
| 品牌周边 | 帆布袋、贴纸、徽章／Pin、钥匙扣、杯具、笔记本、卡套、手机壳、伞、玩偶、礼盒与限定纪念物 | 品牌在可携带、收藏、赠送和社交传播场景中的识别与系列变化 |
| 交易与服务物料 | 包装袋、外带盒、杯／杯套、餐垫、托盘纸、价签、收据、优惠券、会员卡、感谢卡、配送包装 | 从购买到使用、携带、复购的连续触点，而不是只在随机物件上重复贴 Logo |
| 数字与传播物料 | 社交头像、帖子模板、短视频封面、数字广告、官网／小程序入口、电子菜单与活动页 | 小尺寸识别、内容变化、状态适配和数字端一致性 |

完整的门店型或消费型 VI，默认至少覆盖一项店铺关键场景、一项灯牌／导视、一项员工穿戴，以及一组周边或交易物料；确实不适用时必须在设计规划中说明业务依据。每类只选择能够补充不同品牌证据的代表物，不以同一 Logo 换载体名称凑数量。

### 消费者触点链

应用选择先映射真实消费者触点，再决定需要哪些数字、实物或环境项目：发现品牌 → 选择／购买 → 使用／消费 → 携带／传播 → 复购／社交分享。每个入选应用必须补充不同的品牌证据，例如远距离识别、菜单选择、包装携带、消费体验、门店确认或社媒传播；不得用同一种 Mockup 换载体名称充当完整触点系统。范围较小时选择最关键的连续触点，范围较大时再扩展，不要求机械覆盖五个阶段。

## 母版、平稿与场景关系

工作依赖按“母版 → 应用平稿 → 场景 → 展示板”建立，不把展示顺序误作资产生产顺序。

| 层级 | 内容职责 | 来源与修改关系 |
| --- | --- | --- |
| 品牌母版 | 确认 Logo、字标、角色等身份依据及允许用法 | 后续引用同一获准来源；母版变更说明受影响的应用 |
| 应用平稿 | 品牌文字、Logo／字标、图像与信息在海报、杯套、包装平面等载体上的实际设计 | 明确继承哪份母版；不能只靠场景图推测设计 |
| 应用场景 | 同一平稿进入杯身、袋面、灯箱或手持物件后的应用示意 | 明确对应哪份平稿；不在场景中另造字标或另一套设计 |
| 展示板 | 按章节组织规则、平稿、对象和场景，帮助读者理解系统 | 组织展示不替代前三层资产，也不自动构成生产源文件 |

三种位置必须分开描述：**物料在展示板上的位置、图文在应用平稿内的位置、设计在场景表面的落位**。Spec 明确各层对象、内容归属和来源关系，Visual 再补充构图、主次与具体落位，不能用一句“居中展示”代替三层说明。

母版、平稿或场景修改时，说明影响哪些应用，不重新发明无关部分。独立图与场景图分清：场景已有袋杯组合时，不额外叠入同一物件造成无职责的重复。

## 应用与展示结构

### 展示板章节与阅读链

- 开场印象：让读者迅速理解品牌主题与主要价值，准确标题直接写入，不用概念口号替代事实。
- 品牌解释：说明定位、受众和设计要解决的问题。
- 识别规则：介绍标志、字体、颜色、图像及其关系；IP 启用时增加身份基准和变体说明。
- 受控变化：说明同一系统怎样产生不同图案、角色状态或系列设计。
- 应用证据：展示规则怎样进入业务相关的数字、实物或环境载体。
- 扩展与交付：说明如何保持身份、生成后续应用，以及实际交付能力与限制。

章节顺序服务阅读，不固定为若干页模板。每章写出结论、必要说明、图注、准确名称和配图用途。宽幅长板先按横向章节分配内容，分页手册逐页说明职责；内容少时优先把主图、Logo、标题和应用对象放大到安全边界，减少无职责留白，内容多时先横向重组、合并重复说明或增加宽幅章节，仍过量再拆板。不缩成微小缩略图墙，不把宽幅展示退化为手机式单列长图。

### 范围、尺寸与制作条件

- 完整系统覆盖品牌认知、Logo、字体、颜色、图像、必要应用及扩展规则；局部任务只覆盖获准范围。
- 完整 VI 通常验证至少两类应用；未包含数字、实物或环境中的某类时说明原因，不为凑类别虚构业务。
- 用户尺寸优先。未指定的 VI 展示默认使用 1600px 宽画布，并以 `1600 × 900 px` 的 16:9 横向视域规划主要章节；整张宽幅长板的最终高度由已规划章节累加后固定。分页提案未指定尺寸时每页使用 1600 × 900 px。具体应用采用真实载体尺寸，不统一缩成展示页比例。
- 纸张、刀模、工艺、色彩模式、空间安装与生产精度采用供应商参数；未知项标待确认，不凭屏幕效果作生产承诺。

## 内容补写与核对

可创作品牌概念、标题与获准虚构场景，不伪造注册、历史、奖项、门店、销量、客户、授权或业务承诺。草稿中的经验内容就近注明“**注：**以下内容由模型根据经验生成，非真实事实，正式使用前请替换为已核实内容”；用户事实、参考信息和提案不得混写。

未核实法律与制作条件保留待确认，不宣称无侵权或可生产。保存前核对品牌名称与字序、母版唯一性、任务范围、应用文案、IP 是否需要、素材来源、平稿与场景对应关系以及交付能力。新色彩、字体搭配和变换规则由 Visual 完成，Spec 不输出内部机器 Schema。

## 写回 Brief 的内容结构规范

- **内容结构生产规范**：按本 Spec 把品牌事实、系统范围、Logo 准确文字／核心概念／形式职责／使用环境、唯一 Logo 视觉锚点及实际资产标识、各角色母版、身份约束、准确文案、应用清单、逐章职责、真实载体尺寸、母版—平稿—场景—展示关系、来源、授权和缺口写入同一 Brief。
- **内容结构验收规范**：核对名称与字序、Logo 候选和正式家族边界、母版唯一性、系统范围、应用职责、IP 需求、素材来源、载体条件和交付能力边界；用户未提供 Logo 时，确认已生成并逐一交付多个真正不同的候选、已由用户明确选定唯一母版，且完整设计规划已作为用户可见内容告知；用户已提供 Logo 时，确认没有误触发候选生成。确认规划告知后的第一项正式 VI 图像生产必须是以确认 Logo 为唯一输入直接调用 `image_edit` 生成的首屏效果，并符合既有首屏结构、尺度、色场和章节衔接定义；仅在 HTML 中贴 Logo、使用无 Logo 背景或跳过首屏生成均不得准出。凡作为独立层进入 VI 排版的 Logo 必须是经核验的透明 PNG／SVG；原图带底时必须存在 MediaKit `remove-image-background` 处理记录、透明结果短链与浅色／深色／最终底色验边，不得用混合模式替代。全板还须确认主图、Logo、标题、关键数字与物料已经在可读性和安全区允许范围内尽可能放大，没有小主体漂浮在大空场或用微小字号换取留白。除完整 HTML 生成／修改与 `shot.py` 自检外，所有 VI 生产、处理、写入、上传和交付都必须有 Main Agent 亲自执行记录，不得出现 Subagent 介入；完整 VI 手册 HTML 则必须有 Subagent 组装与 `shot.py` 自检记录。之后严格留下 Main Agent 编号交付链记录：第 1 步同尺寸预览上传 CDN、核验公网链接并用 Markdown 展示；默认 Canvas 再依次完成第 2 步 `FileBatchUpload` 完整 HTML、第 3 步 `design-cli ... +create` 唯一顶层 `<item type="HTML">`、第 4 步 `design-cli ... +get` 回读、第 5 步 `present_files("<workspace_id>?item_id=<item_id>")` 画布卡片。Mobile 只允许第 1 步。凡规划图像衍生，确认生产方式为 `image_edit` 且唯一输入是已确认 Logo 母版，没有第二参考或无参考生成；同时确认没有用效果板冒充应用源稿、用位图冒充专业母版、用场景文字冒充原生可编辑文字，或编造商标状态、品牌与生产事实。
