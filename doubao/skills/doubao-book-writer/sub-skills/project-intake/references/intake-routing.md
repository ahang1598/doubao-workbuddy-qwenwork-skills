# 入口判定与项目接纳

本文件解释如何把用户请求转换为写作意图与项目布局。它不定义额外阶段，也不创建机器状态；实际推进由 `make WORKDIR=<书稿目录>` 沿 prepare→write→deliver 依赖链强制。

## 0. 先排除不适用任务

本工作台只接非虚构长文档。以下请求不进入项目接纳，不创建`WORKDIR`，不写需求清单：

- 小说、网文、短篇故事、儿童故事；
- 剧本、分镜剧情、互动剧情、游戏世界观、角色设定；
- 诗歌、散文等纯文学创作；
- 以娱乐阅读为目标的虚构续写或仿写。

若用户素材中包含人物经历、品牌故事或家族叙事，只有在目标是事实可核验的口述稿、人物稿、家谱、报告或资料型书稿时才接纳。需要虚构化、剧情化或文学化创作时，应说明当前技能不适配。

## 一、先识别用户要改变什么

入口判断围绕书稿现状和预期结果展开，而不是让用户选择内部编号。

| 用户目的 | 意图 | 需要确认的事实 |
|---|---|---|
| 从空目录建立非虚构长文档 | 新建 | 主题、读者、体裁、规模、素材边界、交付要求 |
| 从现有进度继续写 | 续写 | 书稿根、当前断点、本轮推进范围 |
| 修改指定位置且保持其他内容不变 | 局部编辑 | 文件、精确范围、允许变化的内容 |
| 整体改变结构或表达 | 改写 | 重写范围、必须保留的信息、目标结构 |
| 在原稿基础上增加体量 | 扩写 | 目标字符、扩写范围、可用素材、禁止重复项 |
| 合并多份只读来源形成新稿 | 组装 | 来源清单、顺序、去重规则、新稿位置 |

"润色""去 AI 味""质检"等说法若没有写回要求，先做检查（按需运行 `make quality`）；收到明确修改指令后再按局部编辑或改写推进正文。

## 二、磁盘事实优先于措辞猜测

用户可能说"新建"，但目录中已经有书稿；也可能说"继续"，实际只有零散附件。判断布局与断点前先检查磁盘：

- 根目录是否有非空 `manuscript.md`；
- 是否存在 `manuscript/chNN-*.md`、`outline.md` 和 `chapter-ledger.md`；
- 用户声明的本地来源是否存在且位于允许范围内。

非空根 `manuscript.md` 优先决定短稿布局；否则存在 `manuscript/*.md` 或 `outline.md` 时按长稿处理。既有书稿续写或改写时从磁盘正文与 `.doubao-book-writer/reports/` 恢复现状，不重建项目。

## 三、需求清单是接纳凭证

动笔前把本轮可验证要求写入 `.doubao-book-writer/requirement-checklist.json`（格式见 [`references/checklist-schema.md`](../../../references/checklist-schema.md)）。至少一项要求标记为 `priority: main`。这是 `make prepare` 的强制门禁：缺失或字段非法会阻断整条依赖链。

清单要覆盖用户真正关心的结果：内容范围、保留边界、字数约束、来源输入、交付方式和验收条件。以下内容不能只写在聊天里：

- 用户给出目标字数时，写入结构化 `wordCountRules`；默认容差不超过 20%；
- 用户明确只要 Markdown 时，记录可核验的交付选择证据，并全程使用 `SKIP_LARK=1`；
- 本地附件作为只读来源时，声明路径和只读性质；
- 编辑、重写或扩写时，记录哪些区域不能改变。

附件是输入，不是默认写回目标。PDF、Word、文本、图片或链接中的可用内容应转入新的 Markdown 真源，除非用户明确要求修改原文件。

## 四、新项目接纳

新建书稿先完成需求冻结和素材判断。主题、目标读者或主要交付物仍不明确时，只问会改变项目结构的关键问题；可以从已有材料可靠推断的内容不重复追问。

正文开始前，外部事实需求至少从三个不同方向检索。第一轮结束后检查证据缺口，再决定是否补搜。有效来源写入 `sources.md` 或 `sources/`，包含标题或来源名、链接、日期、可用结论和目标章节。无法联网时明确说明降级，不编造来源。

需求清单与布局就绪后运行 `make prepare` 校验：短稿使用根 `manuscript.md`；长稿使用 `outline.md`、`chapter-ledger.md` 和 `manuscript/`。布局一经建立，不同时维护两套非空正文真源。

## 五、已有项目接纳

继续或修改已有书稿时，从磁盘恢复，不重建项目：

1. 读取当前正文布局与已有产物（`manuscript.md` 或 `manuscript/*.md`、`outline.md`、`chapter-ledger.md`）。
2. 核对正文与 `chapter-ledger.md`；冲突时以正文文件为准。
3. 为本轮请求更新 `requirement-checklist.json`。

继续写时，长稿断点取已完成章节后的第一个待写章节；短稿依据用户指定位置和现有正文结尾判断。恢复摘要只能加速定位，不能覆盖 Markdown 真源。

## 六、推进规则

推进顺序由 `make` 依赖链强制，保持线性：准备（需求清单 + 布局 +(长稿)大纲）→ 写作（形态 + 字数 +(长稿)台账）→ 交付。短稿跳过大纲；长稿必须先冻结并通过大纲结构检查。任何时候运行 `make WORKDIR=<书稿目录>`，它会停在最早未满足处并打印下一步。

素材是否足够由 [`material-intake-guard.md`](./material-intake-guard.md) 判断。达到充分线后应进入需求确认或大纲，不因用户一句"继续"无限追加近似材料。

## 七、用户沟通

用户看到的是当前状态、下一动作和真实阻塞，不是内部命令或状态文件。首轮说明尽量控制为一句状态加不超过三个可执行动作。需要用户决定时，给出差异明确的选项；已经能够安全推进时直接执行。

不得向用户暴露状态 JSON、报告路径或内部命令日志。最终只报告完成的检查、书稿 Markdown 路径、飞书链接或真实阻塞。
