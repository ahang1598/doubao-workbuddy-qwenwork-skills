# 多角色性能证据协议

> **何时读本文件**：非简单性能任务需要多角色独立反证，或需确认 `DEGRADED_SEQUENTIAL` 降级语义时加载。

本协议用于非简单性能任务，安排相互独立的角色从不同角度反证，最后由主 agent 裁决。

## 一、先探测真实能力

在编排前验证当前运行时是否真的支持：创建独立 agent 或上下文、并行执行、给每个角色传相同只读事实和权限、隔离各角色中间结论、取消并识别失败任务。不得仅根据工具名或说明就宣称这些能力存在。

能力不可靠时，执行「顺序封闭审查」：每个角色只读取冻结事实和原始 artifact，完成并封存结果后再开始下一角色；最终报告标记为「非独立上下文」。这是合法的降级路径，不是独立复核的替代说法。

## 二、冻结共享事实包

先冻结一份共享事实：主模式与完成边界、workload、环境和输入 artifact、correctness oracle、comparison axis、variant、计时边界、重置、指标和门槛。冻结纪律：

1. baseline 与 candidate 必须来自同一仓库的两个明确 revision，不得用两个伪仓库表达同仓库 revision。
2. revision、workload、环境、计时边界或冻结输入变化时重新冻结；不同版本的结论不能直接合并。
3. 冻结后角色产生的 profile、trace、capture、复核结论都是派生证据，另行记录并说明它依赖哪些冻结输入，不当成对冻结事实的 override。

## 三、按独立问题分配角色

角色数量由仍未解决的独立问题决定，不因耗时、tokens 或上下文成本裁剪。只并行读取、分析、测量设计与复核；不得并行修改同一实现、fixture 或测量状态。

| 角色 | 独立职责 |
| --- | --- |
| 基线与测量审计者 | 检查 workload、仪器、样本独立性、预热、重置、顺序、漂移和可重复性 |
| 路径与机制探索者 | 从真实入口追到成本，连接症状、等待/资源与端到端影响 |
| 替代假设探索者 | 独立寻找能解释同一症状的不同机制及互斥预测 |
| Correctness 审计者 | 在不了解候选收益的前提下建立双向 oracle 和故障场景 |
| Guard 审计者 | 检查候选可能转移到尾延迟、吞吐、内存、I/O、可靠性或副作用的成本 |
| 实验设计审计者 | 检查单变量 seam、随机化、对照、统计合同和恢复点 |
| Artifact 验证者 | 从原始输出重建规范化样本，核对来源、选择器和复核绑定 |
| 最终反证者 | 假定当前推荐错误，寻找能翻转决定的最强反例 |

先按主模式选择默认角色，再根据仍未解决的独立问题增补；不适用的角色只在记录中标 `not_applicable`，不为填满角色表执行无关审查：

| 模式 | 默认角色 |
| --- | --- |
| `explain` | 基线与测量审计者、Artifact 验证者、最终反证者 |
| `establish-baseline` | 基线与测量审计者、Correctness 审计者、实验设计审计者、Artifact 验证者、最终反证者 |
| `diagnose` | 基线与测量审计者、路径与机制探索者、替代假设探索者、Artifact 验证者、最终反证者 |
| `guard` | 基线与测量审计者、Correctness 审计者、Guard 审计者、实验设计审计者、Artifact 验证者、最终反证者 |
| `optimize` | 上述全部角色 |

增补与合并规则：

- 只有 profile 含义的 `explain` 不启动 candidate correctness、guard 或单变量实验审计；
- `diagnose` 只有在同时评价干预或 guard 时才增补对应角色；
- `guard` 只有在代理指标关系或阈值机制未闭合时才增补机制与替代假设角色；
- 简单、局部、证据单一的任务可以合并已选职责；一旦存在跨边界路径、多个合理机制、动态运行选择或高风险行为变化，就重新拆分相关独立角色。

## 四、角色输出

每个角色报告：所属角色、独立性说明、各条主张（区分 observation / inference / proposal，标注 `confirmed / inferred / unknown / conflicted / not_applicable`，并引用具体 `文件 path:symbol:line` 作为证据）、最强替代解释、会改变结论的未知项、已检查与未检查区域、停止原因、阻断性未知项、以及能裁决这些未知的下一步观测。

主张升级纪律：

1. 没有直接 artifact 的主张保持 `inferred` 或 `unknown`，不得用自信措辞升级。
2. confirmed / inferred / conflicted 主张必须有足以定位的证据。
3. proposal、unknown、not_applicable 可以没有证据，但不能因表达完整而升级认识状态。
4. 不返回没有证据根的长篇共识。

## 五、候选竞争

只有测量有效且限制机制具有运行证据后，才让相互隔离的候选角色提出干预。候选必须在作用机制或作用边界上真正不同，并各自说明：支持哪个假设、单一变化边界、作用机制、预测的可观测量、触碰的语义面、oracle 扩展、guard 预测、同合同实验设计、恢复方式和失效条件。

候选角色互不知道对方内容。汇总时先比较它们是否命中已观测机制、是否能保持行为、是否有可区分预测，再比较测量结果；不能按表达完整度或投票数选择。

## 六、主 agent 裁决

主 agent 必须重新打开所有会决定接受/恢复的原始 artifact，并逐项核对：

1. 各结论基于同一冻结事实版本；
2. workload 实际命中目标路径；
3. profile/trace 支持机制而非只有代码形状；
4. candidate 与 baseline 只有声明的单一变化；
5. oracle 覆盖 candidate 的全部语义表面；
6. 样本、环境和比较设计可比；
7. 复核针对精确输入，且给出 baseline、candidate 与两者对比三个方向；
8. 最强替代解释已被互斥观测削弱。

多数角色同意不提高证据等级；共识不能替代证据。发生冲突时，比较证据的 selector、来源、scope、时间窗、单位、revision；仍无法区分就设计一个会让两种解释得到不同结果的实验。

## 七、顺序降级（DEGRADED_SEQUENTIAL）

无可靠 agent 能力时的执行顺序：冻结同一事实包 → 按主模式路由依次执行已选角色（跳过 `not_applicable`）→ 每轮前隐藏其他角色结论，只保留冻结事实与原始 artifact → 封存该轮输出，最后统一综合。复核明确标 `DEGRADED_SEQUENTIAL`，并在交付中声明上下文并非真正独立，以及这会降低哪类结论的可信度。

> 坏例：「已由三个角色顺序审查并达成一致，独立复核通过。」
> 好例：「顺序封闭审查完成，标 `DEGRADED_SEQUENTIAL`；上下文非真正独立，ACCEPT 类结论可信度降低。」
> 点评：顺序执行不得填写为独立；「隐藏了上一轮文字」不等于创建了独立上下文。

`独立确认` 必须有真实的上下文隔离证据。不要因为降级而删除已选中的适用角色，也不要仅因角色存在于总表就给当前模式增加无关工作。

## 八、完成条件

所有模式都要求：关键主张定位到原始证据、主 agent 复核决定性 artifact、未知项被裁决或明确条件化、当前动作与证据边界一致。再叠加对应模式的完成条件：

| 模式 | 完成条件 |
| --- | --- |
| `explain` | 现有 artifact 的有效性、含义、scope 与不能推出的结论已复核，交付 `EXPLAINED` |
| `establish-baseline` | workload、环境、命令、状态重置、原始样本和漂移检查可重放，交付 `BASELINE_ESTABLISHED` |
| `diagnose` | 运行证据命中限制机制，首要机制与合理替代解释已被判别性观测裁决，交付 `BOTTLENECK_CONFIRMED` |
| `guard` | 守卫的 workload、oracle、指标、门槛来源和失败动作闭合，交付 `GUARD_ESTABLISHED` |
| `optimize` | candidate 经同合同单变量测量，严格正改善 target、correctness、guards、统计与独立复核全部通过，并有回归守卫和恢复路径，交付 `ACCEPT`（只能顺序封闭复核时标 `DEGRADED_SEQUENTIAL`；只登记零边界时只能称「未见退化」）；任一行为或 guard 门失败则以决定性失败证据和恢复路径交付 `RESTORE` |

收口纪律：

- 只有 `optimize` 或用户明确要求比较已有 candidate 时，才要求 candidate、A/B、接受或恢复；不得为满足完成门虚构 candidate。
- 权限缺失、artifact 不可得、测量污染或假设被证伪时，分别以 `EVIDENCE_REQUIRED`、`REMEASURE` 或 `REJECT_HYPOTHESIS` 有证据地收口，并给出能翻转状态的下一观测。
- 缺少任何适用角色时，保留该缺口并降低交付状态，不用共识补齐证据。
