# 证据图与状态机

证据图是本 skill 的工作底稿。它把代码事实组织成可检查的关系，而不是把搜索结果堆成文件清单。只在任务边界确定、分类完成后构图。

## 1. 图模型

按当前问题选择必要节点，不建立全仓知识图谱。

| 节点 | 表示 |
|---|---|
| 触发 | 外部输入、公共调用、任务、事件或宿主回调 |
| 执行单元 | 函数、方法、处理器、命令、任务或组件 |
| 数据 | 参数、返回值、消息、记录、文件或其他被传递的值 |
| 状态 | 会跨步骤保留并影响后续行为的内存、持久或外部状态 |
| 副作用 | 持久写入、外部调用、发布、文件或用户可观察变化 |
| 边界 | 仓库、进程、发布单元、存储所有者或外部系统 |
| 结果 | 返回、错误、确认、产物或最终可观察行为 |

使用具体动词连接节点：

- `调用 / 分派 / 回调 / 选择`：控制流；
- `产生 / 传递 / 转换 / 消费 / 返回`：数据流；
- `读取 / 写入 / 转换`：状态流；
- `提交 / 发布 / 请求 / 创建产物`：副作用。

`uses`、`handles`、`related to` 等模糊关系不能闭合图边。每条决定性边至少记录：起点、关系、终点、成立条件、证据定位（`path:symbol:line` + confirmed/inferred/unknown/conflicted）、激活阶段和最强反证。

同一代码表达式可支持多条不同关系，但不要把数据、状态和副作用合成一个箭头。“把值传给写入函数”不等于“持久写入已提交”，“发布请求返回”不等于“外部处理完成”。

## 2. 认识状态

调查从候选开始，先分清主张类型（observation 直接观察 / inference 可证伪解释 / proposal 待比较动作），再沿以下认识状态推进：

```text
候选
  ├─ 有直接证据且范围闭合 → confirmed
  ├─ 证据间接或动态选择未闭合 → inferred
  ├─ 缺少决定性证据 → unknown
  ├─ 同范围适用证据相互冲突 → conflicted
  └─ 不承担事实真值的 proposal → not_applicable
```

只有 `confirmed` 的 observation 能在其范围内作为事实进入最终解释。`inferred` 必须写出前提与证伪动作；`unknown` 必须写出缺失图边和影响；`conflicted` 必须先核对快照、环境、条件和证据来源。

保守矩阵：类型与状态受限组合，只有 `observation` 可以是 `confirmed`；`inference` 只能是 `inferred / unknown / conflicted`；`proposal` 必须是 `not_applicable`（其事实前提另建主张）。文档、注释、命名和框架惯例单独存在时，普通事实最高为 `inferred`。证据强度不按数量相加：多个 Agent、注释、文档或同源索引重复引用同一证据，不能通过投票把推断升级为事实。

## 3. 激活轴

认识状态与激活状态是两个正交维度。对每个可能影响答案的实现分别记录：

| 阶段 | 最小证据 | 不能推出 |
|---|---|---|
| `defined` 已定义 | 当前快照中的实现或声明 | 已接入系统 |
| `assembled` 已装配 | 构造、注册、注入、订阅、导出或宿主加载关系 | 本次条件会选中 |
| `selected` 已选择 | 当前配置、参数、条件、版本或调用路径指向该实现 | 已在某环境执行 |
| `runtime_activated` 运行时已激活 | 来源完整的运行观测：产生者、调用方式、采集时间、退出状态、目标环境与 workload 均可复核 | 其他版本、环境、workload 或目标也会执行 |

静态源码通常最多证明 `selected` 或“条件下可达”。`selected` 必须写出使选择成立的配置和条件；部署覆盖未知时只能写条件选择。没有运行观测时使用“当前源码选择”“静态可达”，不要写“线上正在运行”。

运行观测只有在能说清是谁、用什么调用、在什么时间、什么环境和 workload 下、以什么退出状态采集，且这些都可复核时，才能推进到 `runtime_activated`；缺项时相关主张最高为 `inferred`，激活轴保留在已有直接证据能证明的前一阶段（最多 `selected`）。日志文本自称来自某环境、文件名含版本号、多个 Agent 看到同一份产物，都不能补齐来源。

某阶段缺失时保留其前一阶段并记录缺口；不要因后续阶段看似合理而补齐中间箭头。测试装配、示例配置和 mock 与目标运行边界分别标记。

## 4. 按问题类型构图

所有问题先为用户点名对象建立精确锚点，搜索定义、引用、注册、同名实现和反向消费者。随后分支：

- **行为或流程**：从最可信入口正向追踪控制和数据，从结果、状态写入或副作用反向追踪调用者；在两侧相遇处核对参数、条件、错误和实际表达式。
- **存在性，尤其负向存在性**：冻结查询、路径范围、名称变体、排除项与快照；用主张记录找到的对象，或记录“在该边界内未找到”。搜索无结果不需要虚构入口、终点或因果链。
- **结构、边界或归属**：围绕模块、仓库、发布/运行单元、导出/装配、依赖、消费者和状态所有者建立边界图；关系闭合即可，除非问题还要求解释运行行为。跨仓边的两端分别用所属仓库的路径定位，不能把本地绝对路径或相同文件名当成身份。

对动态分派展开候选、装配、选择和运行观测四层。为每个未闭合关系记录竞争解释和最小验证动作。兄弟入口只有逐个核验后的相同图边才可合并；共享 helper 不证明调用者具有相同的前置条件、错误处理或副作用。

## 5. 反证

优先攻击会改变读者心智模型的强主张：

- 是否存在绕过主路径的入口或返回；
- 同名实现是否由不同装配或条件选择；
- 数据是否在中途转换、截断、复制或丢失；
- 状态写入是否提交，失败时是否部分完成；
- 副作用是否同步完成、仅发起、被吞错或停在外部边界；
- 机制是否只存在于测试、示例、废弃代码或未启用配置；
- 运行观测是否属于不同版本、环境或 workload，其来源是否缺失或冲突。

负向搜索记录查询、路径范围、排除项与快照。搜索无结果只说明在该范围内未发现，不能单独证明不存在。

## 6. 停止条件

正常完成时满足：

- 当前图或带搜索边界的主张已直接回答用户问题；
- 每条决定性边或关系主张都有可复核定位和范围；
- 定义、装配、选择和运行时激活没有混用；
- 最强竞争解释已被裁决或条件化；
- 剩余未知不会静默改变核心结论，或已有明确验证动作；
- 最近一轮调查没有新增独立且会改变答案的证据。

### 缺失特征收口门

上面是"允许停"的条件，容易被一句"我已满足"自我宣称。收口前再走一道**否定式**检查：不是勾选"我已深入"，而是逐条查你的**回答正文里是否出现**下列可观察缺失。出现任一项即判定未完成，回到指定步补齐，不得靠加"已确认/已闭合/已检查"这类形容词掩盖：

- **停在 helper**：行为/流程结论止于一个中间函数，未连到返回、状态提交或副作用 → 回到追踪，闭合关键跳链账本；
- **单向追踪**：只有正向 entry→result 或只有反向 result→caller，两侧没有在某一跳相遇核对 → 回到双向追踪；
- **关键跳塌缩**：多个关键跳被压成一句话，缺实际调用表达式或分派条件 → 回到链账本补该跳；
- **竞争解释未裁决**：对存在同名实现、动态分派或多候选风险的关键实现，正文必须留下**实际执行过的搜索产物**——同名/近似名、注册点、分派表的查询与其结果（找到的候选或"该范围内未见"）；不能只说"未发现其他实现"而不出示搜过什么。浮现出 ≥2 个机制时，只讲一个而不给区分它们的最小判别动作 → 回到反证。用"存在性问题不会漏"当默认、跳过搜索产物的，视为该门未过；
- **保证空推导**：一致性、幂等、唯一、可靠、"更快/更强"等结论仅由某个局部机制推出，没有端到端证据 → 降级措辞或补证据；
- **激活混用**：出现"线上运行/已生效"却没有运行 artifact 来源 → 降级为 selected 或"静态可达"。

这道门只作用于行为/流程类（需要因果闭合的）问题；纯存在性、结构/边界或归属问题按各自的闭合判据收口（带搜索边界的主张、边界图或关系主张），不套用链账本条目。

证据尚未闭合时，只因用户明确硬 deadline 到达、平台/环境硬限制、下一步需要新权限，或新增取证已不能产生独立答题证据而停止；将受影响图边标为 unknown 并输出 `PARTIAL` 或 `BLOCKED`，给出解阻动作。不要为“完整”扫描与问题无关的模块，也不得自设 token、耗时、上下文、Agent 数或输出篇幅上限来截断未闭合的决定性图边。
