# 责任闭合：跨组件效果的最小证明

仅在分析包含跨函数、跨模块、跨进程效果，或准备写“保证、自动、重试、补偿、最终一致、不影响”等词时读取。

## 一张卡只证明一个对象上的一个效果

填写：

| 格 | 必须回答 | 可接受证据 |
|---|---|---|
| 对象/范围 | 对哪些输入、实体、分支和副作用成立 | 参数、类型、过滤条件、分派条件 |
| 触发者 | 谁以及何时触发 | 入口、调用点、事件订阅、调度配置 |
| 当前选择 | 当前路径怎样选中实现 | DI、factory、router、flag、配置读取 |
| 执行者 | 哪段真实实现产生效果 | 实际 callee 与关键分支 |
| 成功效果 | 成功写了什么，在哪里可观察 | 返回值、提交点、持久化、发出事件 |
| 失败传播 | error 是否返回、被检查、被吞掉或转成成功 | return/continue/defer/callback 分支 |
| 再触发 | 谁保存失败状态并再次触发 | durable state、consumer、scheduler、契约 |
| 不覆盖范围 | 哪些对象或副作用不被该机制修复 | 反例分支与边界 |
| 状态 | confirmed/conditional/inferred/unknown | 以上证据的最弱等级 |

## 证明规则

- 卡的状态取所有格中最弱的等级。
- 只有实现定义而没有当前选择证据：至多 `conditional`。
- 只有发送/调用成功而没有接收与处理证据：不得声称下游效果成功。
- 只有重新读取或缓存重建：不得声称通知、广播或外部消费得到补偿。
- 没有 durable 失败状态或明确的重新触发点：不得声称会重试或最终收敛。
- 外部系统行为没有版本化契约或来源完整的观测：标 `unknown`。

## 反例扫描

签发前搜索并审阅与主张相关的：

- early return、ignored error、log-and-continue、best-effort；
- feature flag、runtime dispatch、DI/factory 和 no-op 实现；
- batch partial result、重复/空输入、顺序和幂等键；
- transaction commit 前后、跨存储/消息/RPC 边界；
- 失败记录的保存点、消费者、退避、上限和死信；
- 相邻但未被当前路径选择的实现。

找到反例不等于报告失败；它定义主张的准确范围。找不到证据也不等于成功，状态应为 `unknown`。
