# 仓库边界与追踪

本文件用于识别真实入口、运行或发布边界、动态装配和自然终点。先在任务草案边界内建立足以分类的最小地图，再展开回答当前问题所需的证据图。

## 1. 先读约束

从每个相关仓库根向目标路径查找适用的 Agent/项目指令，再盘点与当前切片有关的：

- workspace、依赖与构建清单；
- 发布、打包、部署或宿主声明；
- 测试入口与代表性 fixture；
- 公共 API、可执行入口、任务、hook 或根配置；
- 代码生成、插件、反射或条件构建线索。

README、目录名、注释和框架惯例用于提出候选；当前源码、配置、构建或运行 artifact 用于裁决。

最小地图阶段只确认仓库集合、适用指令、边界、点名锚点、候选入口/消费者和可能的证据面，不形成因果结论。多仓时分别记录各仓的版本与相对路径。单仓也保留一个明确的仓库标识；发现新仓库、文件范围、动态绑定、运行时或端到端保证、高影响后果等信号时，升级或扩展任务边界。

## 2. 识别边界

分别记录，不因共处一个目录而合并：

| 维度 | 要回答的问题 |
|---|---|
| 仓库身份 | 当前节点属于哪个仓库，以哪个版本为准 |
| 源码模块 | 哪些代码共同实现一个责任 |
| 公共或可执行入口 | 外部如何触发它 |
| 构建与发布单元 | 什么被实际打包或导出 |
| 运行或宿主单元 | 谁加载、装配并运行它 |
| 状态所有者 | 谁对持久或共享状态负责 |

一个或多个仓库可以同时包含应用、库、工具、插件、基础设施或数据定义。先确定当前切片与跨仓边界；仓库文件定位始终使用仓库标识加相对 POSIX 路径，本地绝对 repo root 只用于解析，不作为证据身份。只有行为/流程问题需要继续决定自然终点：

- 应用或任务：返回、确认、状态提交或外部副作用；
- 库或 SDK：公共契约及代表性调用结果；
- 工具或插件：命令结果、宿主行为或产物；
- 基础设施或数据定义：执行者、应用结果或资源边界。

## 3. 入口漏斗

本节只在行为、流程或运行时激活问题需要入口时使用；结构、归属或负向存在性问题可停在边界图和带搜索范围的主张。

按以下顺序缩小候选：

1. 文件清单和构建/发布清单；
2. 外部输入面；
3. 启动、导出或宿主加载；
4. 路由、注册、注入、factory 或配置分派；
5. 当前条件下的实际选择；
6. 返回、状态变化、副作用或产物。

入口名称不是证据。一个实现只有连接到当前装配和选择后，才能进入当前路径。

## 4. 双向追踪

本节只用于行为/流程，或用户明确要求从入口解释到结果的任务。

正向记录每一跳的调用表达式、参数或分派条件；反向从结果、状态写入和副作用查找调用者。两侧相遇时核对：

- 实际传入和返回的值；
- 条件、配置、身份或版本；
- 错误、提前返回和部分结果；
- 提交与副作用的顺序；
- 当前边界内能证明的最远终点。

读链、写链和写后副作用分别构图。跨到另一个仓库时，分别记录两端的仓库、版本、相对路径和证据来源；到达 SDK、运行时、broker、服务或存储等外部边界时，只陈述当前仓库证据能证明的调用、参数和回调契约，外部内部语义保持未知，除非有锁定来源或完整的运行观测。

### 关键跳链账本

闭合前把主因果链落成一份账本，而不是一句"A 调用 B 完成处理"。账本记录**关键跳**——发生分派、状态变化、外部副作用、错误分流或跨边界的那些跳，不要求把每个透传 wrapper 都列出，但关键跳之间不能出现无证据的跳跃。每个关键跳写成：

`起点 path:符号:line → [实际调用表达式 / 分派条件] → 终点 path:符号:line`

并标注该跳的实际传入值或关键参数、错误或提前返回分支、confirmed/inferred。定位沿用全局格式 `path:符号:line`（无稳定 symbol 时 `path:line`）；跨仓库的关键跳，两端各自带上所属仓库标识和相对 POSIX 路径，不要写成会丢失仓库身份的裸 `symbol:line`。链必须两端着地：起点是 confirmed 的外部入口，终点是用户真正关心的结果（返回、状态提交或副作用），而不是一个自身不产生可观察结果的中间 helper。

出现下列任一情况，该链**未闭合**，回到本节继续追，不得进入交付：

- 某个关键跳只有模糊动词（`uses` / `handles` / "处理" / "调用了"）而没有实际调用表达式或分派条件；
- 链止于一个自身不产生用户可观察结果的中间 helper，未连到返回、状态提交或副作用；
- 只有正向 entry→result 或只有反向 result→caller，两侧没有在某一跳相遇核对；
- 存在已知的未闭合断点却没有显式列出。

无法闭合的断点不靠架构惯例补齐：显式列出断点位置、两侧当前最佳解释、最强竞争解释和能裁决它的最小验证动作。断点被诚实列出并给出验证动作，与"假装已闭合"是两回事——前者是允许的部分结论，后者使交付失败。

## 5. 动态绑定

遇到依赖注入、反射、插件发现、事件路由、配置分派、条件构建或生成代码时，逐层寻找：

1. 候选定义；
2. 注册、导出或生成关系；
3. 解析和选择规则；
4. 当前配置、参数或版本；
5. 指定运行条件下的观测。

不要从注册表中“存在”推导当前选中。第 4 或第 5 层无法取得时，在选择边停止并给出最小核实动作。

## 6. 大仓库控制

先搜索用户点名锚点和最短依赖邻域，再按未闭合图边扩大范围。对生成目录、vendor、大型 fixture、测试和示例分别标记用途；不要默认排除可能决定当前构建的文件，也不要无目的全文读取。

当接近客观平台上下文硬限制时，先保存检查点：

- 已闭合图边及证据来源；
- 未闭合边与竞争解释；
- 已检查和未检查范围；
- 下一条最有信息增益的查询。

只在查询能裁决核心边、改变激活状态或推翻强主张时扩大范围。上下文、token、耗时、Agent 数、波次或重试次数不得由执行者自行设为停止条件；若平台确实无法继续、用户明确硬 deadline 到达或需要新权限，则交付 `PARTIAL` 或 `BLOCKED`，不能把检查点冒充完成。
