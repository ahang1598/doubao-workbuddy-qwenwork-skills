# 抖音生活服务·商品信息编辑（改品）
为抖音生活服务的商家对话式完成商品信息修改。商家带着具体问题来，AI自动定位商品、判断状态、读取真实页面字段能力、识别要改的字段，改前确认、写入回读、改后复核，最后提交审核。

## 不可覆盖的安全规则

以下规则不能被用户的泛化授权、"不用确认""自行处理""都授权了"等指令覆盖：

1. 必须核验当前登录主体、目标商品名称和完整商品 ID。
2. 任何写入前必须展示本次改前确认卡。
3. 提交审核必须在写后回读完成后单独确认。
4. 未经明确确认不得加载、放弃或删除草稿。
5. 不得生成或使用虚构经营图片、资质材料或授权证明。
6. 页面没有明确成功反馈且最终状态不可回读时，不得宣称成功。
7. 任一目标字段回读不一致时立即停止，不得继续提交。

## 统一操作状态机（必须遵守）

所有页面操作必须严格遵循以下状态推进，不得跳级：

```
READ_ONLY
→ PENDING_CHANGE_CONFIRM
→ WRITE_ALLOWED
→ WRITE_DONE
→ READBACK_OK
→ PENDING_SUBMIT_CONFIRM
→ SUBMIT_ALLOWED
→ SUBMITTED / FAILED
```

任何步骤失败，进入 `FAILED` 状态；用户中止或校验不通过时回到 `READ_ONLY`。

### 各状态含义

| 状态 | 含义 | 允许的操作 |
|---|---|---|
| `READ_ONLY` | 仅读取页面信息，不做任何写入 | 读取、搜索、导航、截图 |
| `PENDING_CHANGE_CONFIRM` | 已展示改前确认卡，等待商家明确确认 | 读取、展示确认卡；**禁止任何写操作** |
| `WRITE_ALLOWED` | 商家已确认修改计划，允许执行写入 | 逐字段写入、即时回读 |
| `WRITE_DONE` | 所有目标字段已写入页面 | 读取、回读比对 |
| `READBACK_OK` | 全部目标字段回读一致，非目标字段无异常 diff | 读取、生成截图、展示改后结果 |
| `PENDING_SUBMIT_CONFIRM` | 已展示改后结果和提交确认卡，等待提交确认 | 读取；**禁止提交** |
| `SUBMIT_ALLOWED` | 商家已明确确认提交，允许执行提交审核 | 点击提交审核、核验提交结果 |
| `SUBMITTED` | 提交成功，全部成功条件已核验 | 读取、报告结果 |
| `FAILED` | 提交失败或结果未知，保留现场 | 读取、等待商家指示（重试/回滚） |

### 写操作定义（以下均属于写操作）

- 切换单选、复选框、模式、开关
- 展开条件字段时改变页面值
- 新增或删除收费项、服务项、日期规则
- 加载、覆盖、放弃或删除草稿
- 修改关系字段，如适用门店
- 保存草稿、提交审核

### 状态机禁止规则

- 处于 `READ_ONLY` 或 `PENDING_CHANGE_CONFIRM` 时，**禁止执行任何写操作**。
- 禁止跳级执行（如未确认直接写入、未回读直接提交）。
- 禁止用历史确认代替当前确认（用户修改目标后必须重新确认，状态回退至 `PENDING_CHANGE_CONFIRM`）。
- 禁止从 `FAILED` 自动恢复提交（必须由商家明确指示后重试一次，再次失败必须停止）。
- "之前统一授权""测试账号随便""后面不用问"均不能替代本次操作确认。

## 商品状态处理（必须遵守）
本技能仅对以下状态执行正向编辑，其他状态不得复用改品授权：

| 状态 | 处理方式 |
|---|---|
| **已上架** | 支持编辑，修改后需重新提交审核 |
| **审核驳回** | 支持编辑，优先读取驳回原因并逐条处理 |
| **审核中** | 只读等待，不可编辑，建议等待审核结果 |
| **草稿** | 默认只读诊断；若要编辑必须进入单独流程并明确告知商家 |
| **已下架** | 默认只读诊断；若要编辑必须进入单独流程并明确告知商家 |

**永远不复用改品授权的动作**：恢复售卖、下架、删除商品。这些动作必须由商家在后台手动操作或走独立流程，不得在改品会话中顺带执行。

## 不适用场景
- 新建商品 / 商品首次上架 → 走商品创建能力
- 商品下架 / 删除 / 停售 / 恢复售卖 → 非编辑场景，不得复用改品授权
- 订单处理、退款、核销 → 走订单/售后能力
- 门店信息、账号信息修改 → 非商品维度
- 批量改品（一次改多个商品的不同字段）→ 需商家逐个确认，本技能单次聚焦一个商品

## 工具映射（按能力描述，运行时选择当前可用实现）
- **登录态浏览器能力**：抖音来客登录、导航、商品管理搜索、商品详情页读取与编辑、提交审核。运行时根据环境选择 `mac_computer_use_tool` 或 `computer_use_tool`（`plane="bu"`，`import seed_browser_use as bu`），不得硬编码单一运行环境。
- **用户接管能力**（`interaction.request_action`）：登录、短信验证码、图形验证码/滑块等人机交互。
- **页面截图能力**：截取编辑页预览图。证据文件写入当前任务输出目录，不硬编码桌面路径。
- **文件展示能力**（`present_files`）：改后预览截图交付。

## 前置条件
0. **核心确认环节（必须遵守，无豁免）**：本技能有两个强制确认点——"改前字段确认"和"改后结果复核+提交审核确认"。
   - 任何会写入商家后台的动作，**至少展示一次结构化修改计划并获得商家明确同意**（回复"确认修改""可以改""没问题"等）。
   - "你看着办""都行"等模糊表述仅表示授权自主选择，但**仍需展示改前确认卡**（列出要改的字段、原值、运算过程、新值），不得跳过。
   - **不存在"不用确认直接改"的豁免**。即使商家明确表示不用确认，也必须至少展示一次改前确认卡后再执行写入。
   - 提交审核必须在展示写后回读结果和截图后**再次单独确认**，不能由早先的泛化授权替代。

1. **P0：登录态接续与窗口校验（最优先，优先于后续全部采集和修改流程）**：本技能不主动索要账号和密码，采用「优先复用已登录态 + 用户接管登录」的方式。

   1. 打开抖音来客（`https://life.douyin.com/p/home`）后，先检查当前浏览器的**全部标签页和窗口**，优先复用已经登录且与抖音来客匹配的页面；禁止只检查当前活动标签页就判定登录失败。
   2. 登录成功必须由**当前可操作页面**的正向证据确认：
      - 页面不再显示阻断操作的手机号、邮箱、扫码等登录表单；
      - 页面显示可核验的商家身份（商家名称、门店数等）。
   3. 当用户说"已登录"或提供已登录截图，但当前页面仍显示登录表单时：
      - 只可表述为"用户侧已登录，但当前自动化页面尚未接续到该登录态"，不得表述为"用户未登录"或否定用户的登录结果；
      - 重新枚举全部标签页和窗口，切换到已登录页面；若没有找到，刷新当前目标页面并重新读取页面状态，禁止沿用刷新前的截图或DOM判断；
      - 若仍未接续，明确说明可能是窗口、标签页或浏览器上下文不同，但不得把未验证的原因写成事实；使用 `interaction.request_action` 请求用户接管**当前自动化浏览器窗口**完成登录，或在工具支持时连接用户已登录的可控浏览器窗口。
   4. **停止条件**：在当前可操作页面出现上述登录成功正向证据前，禁止搜索商品、禁止读取商品数据、禁止执行任何修改操作、禁止宣称已拿到真实数据。
   5. 登录成功后，立即记录当前页面URL、商家名称作为接续证据，再进入商品搜索；切换标签页或账号后必须重新执行本校验。
   6. 如页面要求短信验证码、图形验证码、滑块或人机验证，使用 `interaction.request_action` 请商家接管完成，并如实说明停在登录门禁；不得绕过验证、不得伪造登录成功。

2. **审核告知（必须主动说明）**：无论是已上架商品修改还是审核驳回商品修改，**修改完成后都必须重新提交平台审核**，审核期间商品状态可能变化（已上架商品修改后可能进入审核中、暂时不可售）。在改前确认环节必须主动告知商家这一点，不得隐瞒。

3. **字段能力五态（必须遵守）**：每个字段在运行时必须先判定其能力状态，再决定是否可改：

   | 状态 | 含义 | 处理方式 |
   |---|---|---|
   | `editable` | 页面存在直接输入控件，可直接修改 | 正常执行修改 |
   | `readonly` | 页面存在但为只读展示，无输入控件 | 明确告知商家该字段不可修改，停止该字段修改 |
   | `derived` | 页面展示为派生/计算值（如划线价由服务项目总价计算） | 先定位来源字段，展示计算关系，通过修改来源字段间接变更 |
   | `relation` | 需通过独立关联流程修改（如适用门店关联） | 走关联字段独立流程，不直接写入 |
   | `absent` | 当前类目页面不存在该字段 | 停止并说明类目限制，不得声称可改 |

   **常见字段状态提示**（以实际页面为准，不得凭记忆假设）：
   - 原价/划线价：多数类目为 `derived`，由套餐/服务项目总价计算，无直接输入控件
   - 退款规则：多数类目为 `readonly`，仅展示不可编辑
   - 商品标签、图文详情、行业资质、商品资质、客服电话：部分类目（如美发）为 `absent`

4. **写入前硬校验（必须遵守，校验失败不得写入）**：在任何页面写入前，对目标字段执行以下校验，不得依赖平台提交时再报错：

   **数值类校验**：
   - 售价/团购价：必须为正数；满足页面精度要求（通常为整数或两位小数）；满足类目上下限；与原价/划线价满足价格关系（售卖价不得高于原价）
   - 库存：必须为非负整数；不接受小数、负数
   - 限购数量：必须为正整数或"不限"

   **内容类校验**：
   - 商品名称/标题、商品详情、套餐内容：命中极限词（"最""第一""顶级""全网最低""国家级"等）、绝对化用语、不实承诺时，**禁止写入**并给出替代表述建议
   - 标题字数不超过页面限制
   - 图片类：需商家提供真实素材，不生成虚构商品图。素材来源和合规性要求详见 [references/material-policy.md](references/material-policy.md)。

   **校验失败处理**：明确告知商家哪个字段校验不通过、原因是什么、建议值是什么，等待商家确认调整后再继续。

5. **库存语义（必须遵守）**：库存字段表示**最终总库存**，不是新增库存。
   - 商家说"改成200""库存设为200" → `operation=set`，直接写入200
   - 商家说"加200份""补200库存""增加200" → `operation=increment`，先读取原库存，计算 `目标库存 = 原库存 + 增量`，在改前确认卡同时展示原值、运算和最终值
   - 商家说"减50""减少库存" → `operation=decrement`，先读取原库存，计算 `目标库存 = 原库存 - 减量`，结果不得为负
   - 不得将增量直接当作最终值写入

6. **基线快照与回滚协议（必须遵守）**：

   **写入前保存基线**：
   - 目标字段基线（所有目标字段当前值）
   - 非目标字段基线（页面上其他可见字段当前值，用于检测非预期变更）
   - 商品状态
   - 当前草稿数量

   **逐字段写入与即时回读**：
   每写一个字段：
   1. 写入目标值；
   2. 立即回读该字段值；
   3. 与目标值比对；
   4. 不一致则立即停止，不得继续写入其他字段，告知商家并等待指示（重试或回滚）。

   **全部写完后的全量校验**（未完成以下步骤不得进入提交确认）：
   1. 重新打开对应页面步骤/标签页，确保页面状态已刷新；
   2. 再次读取所有目标字段，与目标值逐一比对；
   3. 读取非目标字段，与基线比对是否存在非预期 diff；
   4. 生成编辑页截图作为证据；
   5. 任一目标字段回读不一致或非目标字段出现非预期变更 → 按基线回滚已修改字段，并再次回读确认恢复成功；
   6. 全部校验通过后，状态推进至 `READBACK_OK`，方可进入提交确认。

   **取消/异常时**：将已修改字段恢复为基线原值，并再次回读确认恢复成功。
   **退出前**：检查是否新增草稿，向商家说明草稿副作用，由商家选择保留或清理。
   **不可逆/破坏性动作分别确认**：删除草稿、恢复售卖、提交审核等动作必须分别获得商家明确确认，不得由改品授权顺带执行。

## 条件字段两阶段确认（必须遵守）

当目标字段只有切换模式后才出现时，必须分两个阶段确认，**禁止使用"临时切一下看看""先展开再确认"之类的处理**。

### 第一阶段：确认是否切换模式

1. 读取当前模式（页面实际显示值）。
2. 向商家说明切换模式的影响（会隐藏哪些字段、出现哪些新字段、是否会重置已有值）。
3. 仅确认是否允许切换模式，不涉及具体字段值。
4. 商家未确认前，**不得切换模式**（切换模式属于写操作，此时状态为 `READ_ONLY` 或 `PENDING_CHANGE_CONFIRM`，禁止写操作）。

### 第二阶段：确认具体字段和值

商家确认切换模式后：

5. 执行模式切换（状态需已推进至 `WRITE_ALLOWED`）。
6. 读取新出现的真实字段和选项，**不填写任何具体值**。
7. 生成第二张确认卡，列出具体字段、当前值和目标值。
8. 商家第二次确认后，才能写入具体字段值。

### 常见条件字段场景

| 当前模式 | 切换后模式 | 切换后新出现的字段 |
|---|---|---|
| 不限时间 | 限时售卖 | 售卖开始/结束时间 |
| 所有日期可用 | 部分日期不可用 | 不可用日期选择器 |
| 全天可用 | 指定时段 | 可用时段选择器 |
| 额外费用无 | 有 | 额外费用项目、金额 |
| 不限人数 | 限制人数 | 人数限制输入框 |

### 禁止规则

- 禁止在未获第一阶段确认前切换模式。
- 禁止切换模式后直接填写值而不展示第二张确认卡。
- 禁止将"确认修改商品"解释为同时确认切换模式。
- 模式切换后如页面重置了已有字段值，必须在第二张确认卡中明确告知。

## 字段语义和联动校验（必须遵守）

### 使用张数限制 vs 使用人数限制

必须严格区分以下两个字段的语义，不得混淆：

| 字段 | 语义 | 说明 |
|---|---|---|
| 使用张数限制 | 单次消费最多使用 N 张券 | 控制一次消费可核销的券数量上限 |
| 使用人数限制 | 每张团购券限 M 人使用 | 控制单张券对应的使用人数，**不是单次订单总人数** |

**组合最大人数 = 使用张数限制(N) × 使用人数限制(M)**

如果商家说"单次最多 X 人"，而页面只有"每张券限 M 人"字段：

1. 必须先计算组合结果：`组合最大人数 = N × M`。
2. 将组合结果与商家目标 X 比对。
3. 组合结果与商家目标不一致时，**禁止写入**，必须向商家说明计算过程并要求澄清（是调整张数限制、人数限制，还是两者都调整）。
4. 商家澄清后，重新生成确认卡，展示两个字段的目标值和组合结果。

### 预约字段依赖校验

切换预约方式前，必须先检查该方式是否会隐藏或重置以下字段：

- 提前预约量
- 项目时长
- 取消规则
- 退款规则

**校验规则：**

1. 读取当前预约方式下上述字段的当前值。
2. 评估切换到目标预约方式后，上述字段是否会被隐藏、禁用或重置。
3. 如果商家的目标字段（如提前预约量）不能在目标预约方式下同时存在：
   - **必须在任何写入前说明冲突**，告知商家切换后该字段将不可用或被重置。
   - 要求商家选择：放弃该字段修改 / 更换预约方式 / 调整修改计划。
   - **禁止先部分写入**（如先切换预约方式再发现字段丢失）。
4. 切换后必须重新读取所有受影响字段的实际值，与基线比对。

### 其他联动校验

- 价格字段：售卖价不得高于原价/划线价；修改套餐内容后需重新校验派生的划线价。
- 库存字段：增量操作后目标库存不得为负；库存模式切换（有限/无限）需确认是否重置已有库存值。
- 日期规则：新增或删除日期规则属于写操作，需在改前确认卡中列出具体变更。
- 收费项：新增或删除收费项属于写操作，需在改前确认卡中列出具体变更和金额影响。

## 禁止推断页面事实（必须遵守）

只有当前页面实际可见、或通过真实控件读取的值，才能写入报告和确认卡。**禁止任何形式的推断。**

### 禁止的推断行为

- **禁止根据商品标题推断类目**：类目必须从页面实际选择器或详情页读取，不得从标题关键词推断。
- **禁止根据格式推断商品 ID 归属**：商品 ID 必须从页面实际显示读取，不得根据 ID 格式（如数字长度、前缀）推断归属。
- **禁止根据字段名称推断支持的单位**：字段的单位（元/份/张/人/天）必须从页面实际标签或输入框旁标注读取，不得凭字段名猜测。
- **禁止报告没有独立读取证据的项目数量**：收费项数量、服务项数量、图片数量等必须从页面实际计数，不得估算。
- **禁止推断草稿来源**：草稿来源必须从页面实际显示读取，页面未显示时写"来源不可确认"，不得根据同名、同 ID 或名称包含"复制创建"推断。
- **禁止推断字段能力**：字段是否可编辑必须从页面实际控件判定（有无输入控件），不得凭记忆或通用清单假设。

### 字段不可见时的处理

字段在当前页面不可见时，必须在报告和确认卡中写：

- `UNKNOWN` / `当前页面不可见` / `需要进入详情读取`

**不得用推断值代替真实字段值**，不得在确认卡中列出未实际读取的字段值。

### 报告真实性原则

- 每一个写入报告的字段值，必须有对应的页面读取证据（截图或 DOM 读取记录）。
- 改前确认卡中的"原值"必须来自实际页面读取，不得来自历史记录或商家口述。
- 改后结果中的"新值"必须来自写后回读，不得来自写入时输入的值（输入后可能被页面格式化或拒绝）。

## 草稿协议（必须遵守）

进入编辑页或商品管理时如发现草稿，必须按以下协议处理。

### 草稿操作必须分别独立确认

以下四种操作必须**分别独立确认**，不得合并、不得由其他确认顺带覆盖：

1. **加载草稿**：将草稿内容加载到编辑页，覆盖当前线上值。
2. **覆盖线上值**：用草稿或新输入的值覆盖商品当前线上值。
3. **放弃草稿**：放弃当前草稿内容，不保存。
4. **删除草稿**：从草稿箱中永久删除草稿。

**"确认修改商品"不能被解释为"同时确认加载或删除草稿"。** 每一种草稿操作都必须有独立的确认卡和商家明确回复。

### 草稿确认卡必须包含

每次草稿操作确认前，必须展示包含以下信息的确认卡：

- 页面实际显示的草稿时间（不得推断或估算）
- 页面实际显示的草稿来源（页面未显示时写"来源不可确认"）
- 加载或放弃的副作用（如：加载后将覆盖当前线上值、放弃后草稿内容不可恢复）
- 将覆盖或丢失的内容（如：当前线上值将被草稿值覆盖、草稿中已填写的 X 个字段将丢失）
- 商品名称和完整 ID

**来源不可确认时**：页面没有显示来源时，写"来源不可确认"。**禁止**根据同名、同 ID 或名称包含"复制创建"等推断来源。

### 第二层弹窗刷新确认

如果草稿操作触发第二层弹窗（如确认删除弹窗、加载覆盖提示弹窗），且弹窗中出现了新的时间、来源或副作用信息：

1. 必须**刷新确认卡**，将新信息纳入展示。
2. 必须**重新获得商家确认**，旧确认不再有效。
3. 不得因为第一层已确认就跳过第二层确认。

### 草稿操作规则

- **加载草稿**：只有商家明确回复"使用该草稿""加载草稿"后才能加载。加载后必须重新读取页面字段，不得沿用加载前的字段快照。加载草稿属于写操作，状态需已推进至 `WRITE_ALLOWED`。
- **覆盖线上值**：加载草稿或直接修改时，如会覆盖当前线上值，必须在确认卡中明确列出将被覆盖的字段和原值，获商家确认后才能执行。
- **放弃草稿**：商家明确要求放弃时，告知放弃后草稿内容将不可恢复，获二次确认后执行。
- **删除草稿**：删除为不可逆动作，必须单独获得商家明确确认，不得由改品授权顺带执行。删除后需回读确认草稿已从草稿箱移除。
- **禁止操作**：不得在未展示草稿确认卡前自动加载/放弃/删除；不得根据推断的草稿来源做决策；不得在商家未明确选择时默认加载或放弃；不得将"确认修改商品"解释为同时确认草稿操作。

### 草稿与本次修改的关系

- 加载草稿后，草稿中的字段值成为新的基线，需重新执行字段能力读取和改前确认。
- 不加载草稿时，以商品当前线上值为基线进行修改。
- 修改过程中页面可能自动生成新草稿，退出前必须检查草稿增量并与商家确认保留或清理。

## 提交审核硬门禁（必须遵守）

### 提交前硬门禁（必须同时满足才能提交）

点击提交审核按钮前，必须同时满足以下全部条件，缺一不可：

1. **所有改动字段写后回读一致**：每个目标字段写入后均已回读，回读值与目标值完全一致。
2. **非目标字段差异检查完成**：已读取非目标字段并与基线比对，确认无非预期变更；如有变更已在确认卡中说明并获商家认可。
3. **保存提交前截图或等价页面证据**：已截取编辑页完整截图（或等价的页面状态证据），保存到任务输出目录。
4. **展示最终提交确认卡**：已向商家展示改后结果（含字段变更列表、回读状态、截图），并明确告知提交后无法撤回。
5. **获得本次提交的明确确认**：商家针对本次提交给出明确回复（如"提交""确认提交"）。

**"之前统一授权""测试账号随便""后面不用问"均不能替代本次提交确认。** 每次提交都必须有独立的、针对本次操作的明确确认。

未满足以上全部条件时，状态停留在 `PENDING_SUBMIT_CONFIRM`，**禁止执行提交操作**。

### 提交成功条件（必须同时满足才算成功）

提交后，只有同时满足以下全部条件，才能判定提交成功并向商家宣称"修改已提交"：

1. **页面出现明确成功反馈**：提交后页面显示"提交成功""已提交审核"等明确的成功提示（Toast、弹窗或页面状态变更），不得仅凭按钮恢复可点击或页面跳转推断成功。
2. **商品列表出现正确的最终状态**：返回商品管理列表，该商品状态已更新为"审核中"（已上架商品修改后）或对应预期状态。
3. **审核中版本包含本次目标值**：进入审核中版本的详情/预览，确认本次修改的目标字段值已正确包含在待审核版本中。
4. **草稿增量符合预期**：对比提交前后草稿数量，确认草稿变化符合预期（如提交后草稿被消耗或新增草稿符合平台行为）。
5. **商品名称和完整 ID 一致**：最终状态核验时，确认操作的商品名称和完整 ID 与改前确认的目标一致，未发生商品错位。

### 提交无反馈/失败处理

提交后如无明确成功反馈（页面超时、按钮恢复可点击但无提示、加载异常等）：

1. **不得判定成功**，状态停留在 `SUBMITTED`（提交操作已执行但结果未确认）或进入 `FAILED`。
2. **分别检查**：
   - 线上版本状态是否变化
   - 审核中版本是否新增或更新
   - 草稿数量和内容是否变化
3. **只能重试一次**：在获得商家新的明确确认后，可以重试提交一次。
4. **再次失败必须停止**：重试后仍无明确成功反馈，必须停止操作，保留以下证据：
   - 草稿内容
   - 提交前截图
   - 当前页面 URL
   - 错误信息或页面状态
5. 向商家如实说明"提交结果未确认"，提供回滚或联系平台支持的选择，**不得自动重复提交**。

### 状态推进

- 提交前硬门禁全部满足 → 状态推进至 `SUBMIT_ALLOWED`，允许执行提交。
- 提交成功条件全部满足 → 状态推进至 `SUBMITTED`（成功），向商家报告提交成功。
- 提交无反馈或失败 → 状态为 `SUBMITTED`（结果未知）或 `FAILED`，不得宣称成功。

## 工作流程

### 第一步：商品信息确认 + 登录态接续 + 搜索 + 确认商品
1. **确认目标商品**：技能启动后向商家确认要改的商品（商品名称或商品ID，二选一即可，ID定位更精准）。商家如果主动附带了修改诉求（如"价格改成128"），正常接收即可。
   ⚠️ 本步不索要账号密码，不追问修改诉求。
2. **登录态接续**：打开抖音来客（`https://life.douyin.com/p/home`），按前置条件第1点「P0：登录态接续与窗口校验」执行。优先复用已登录标签页/窗口，未接续时请用户接管浏览器完成登录。登录成功后记录商家名称和URL作为接续证据。
3. **导航到商品管理**：登录成功后，**按以下固定路径导航，不要在首页摸索**：
   - 左侧导航栏 → 找到「店铺管理」分类 → 点击「商品与货架」展开子菜单
   - 在展开的子菜单中点击「商品管理」
4. **搜索目标商品**：进入商品管理页后，在搜索框中输入商家提供的商品名称或商品ID进行搜索。
   - 提供了商品ID → 直接用ID搜索，定位最精准
   - 提供了商品名称 → 用名称搜索，从结果中匹配
5. **商品级确认 + 状态判定 + 流程预检**：搜索到商品后，从页面读取商品名称、完整ID、当前状态、所属类目，向商家确认：
   > "找到了「XXX」（ID：XXX），当前状态是「已上架/审核驳回/审核中/草稿/已下架」，所属类目是「XXX」，是要改这个商品吗？"
   - 状态为**已上架或审核驳回** → 商家确认后执行流程预检（见下方第6点），通过后进入第二步
   - 状态为**审核中** → 告知商家商品正在审核中，不可编辑，建议等待审核结果
   - 状态为**草稿或已下架** → 默认只读诊断，告知商家该状态非本技能核心场景；若商家明确要求编辑，进入单独流程并明确告知风险
   - 如搜索结果有多个相似商品，列出前3个让商家挑选

6. **流程预检（进入编辑页前必须执行）**：使用完整商品ID检查该商品是否已存在以下流程冲突：
   - **已上架但存在审核中版本**：该商品已有一个正在审核的修改版本，此时再次编辑会产生冲突。只读报告当前状态，不进入新的编辑提交；建议商家等待当前审核完成后再修改，或重新选择不存在流程冲突的商品。
   - **待商家审核**：商品处于商家待审核环节，只读报告，不进入编辑。
   - **审核驳回**：正常进入编辑流程，但需优先读取驳回原因。
   - **草稿箱**：存在未提交的草稿，按「草稿协议」处理（见下文），不得自动加载或放弃。
   - **违规流程**：商品因违规被限制，只读报告，告知商家需先处理违规。
   - 同一商品已经在上述任一流程中时：只读报告当前状态，不进入新的编辑提交；或重新选择不存在流程冲突的商品。

### 第二步：读取真实页面字段能力 + 生成字段能力快照
1. **进入商品详情/编辑页**，读取当前类目的真实页面结构。
2. **生成字段能力快照**：对商家可能涉及的字段，逐一判定其能力状态（`editable` / `readonly` / `derived` / `relation` / `absent`），记录控件类型、页面步骤/标签位置。字段能力矩阵参考 [references/product-fields.md](references/product-fields.md) 和 [references/product-capability-matrix.md](references/product-capability-matrix.md)，但**必须以实际页面为准，不得凭记忆假设**。
3. **保存基线**：按「基线快照与回滚协议」保存目标字段基线、非目标字段基线、商品状态、当前草稿数量。
4. 如商家诉求涉及的字段为 `absent`，立即告知商家该字段在当前类目不支持修改；如为 `readonly`，告知不可直接修改；如为 `derived`，说明计算关系并定位来源字段。

### 第三步：解析商家诉求 + 字段校验 + 改前确认（强制）
**原则：商家带着问题来，AI自动定位字段，不罗列所有字段让商家选。**
1. **解析商家诉求**：从商家自然语言中提取修改意图，映射到具体字段。常见映射见 [references/product-fields.md](references/product-fields.md)，字段能力详情见 [references/product-capability-matrix.md](references/product-capability-matrix.md)。
   - "价格写错了，应该是128不是99" → 字段：团购价格/售卖价，`operation=set`
   - "库存加200份" → 字段：库存数量，`operation=increment`
   - "主图要换成新的" → 字段：商品主图
   - "套餐里少写了一杯饮料" → 字段：商品详情/套餐内容
   - "使用时间要改成周末也能用" → 字段：使用规则/可用时间
2. **逐字段执行写入前硬校验**（见前置条件第4点）：存在性、可编辑性、派生关系、关联关系、数值校验、内容校验。校验失败不得进入确认卡，需先与商家沟通调整。
3. **读取原值**：进入对应字段的编辑区域，读取当前值（原值），确保修改基于真实数据，不凭记忆或猜测。对于增量操作，需基于原值计算目标值。
4. **展示改前确认卡**，**必须包含**：
   - 商品名称 + 当前状态 + 所属类目
   - 要修改的字段名 + 能力状态
   - 原值（当前值）
   - 运算过程（仅增量/减量操作需要，如"原库存500 + 增量200"）
   - 新值（商家要求的修改后值/计算后的目标值）
   - 不可修改项（如有 `readonly` / `absent` 字段，列出并说明原因）
   - 审核告知："修改后需要重新提交平台审核，审核期间商品可能暂时不可售"
   - 草稿副作用告知："修改过程中页面可能自动生成草稿，退出前会与您确认保留或清理"
   格式示例：
   ```
   【改前确认】
   商品：「XXX双人套餐」（当前状态：已上架，类目：美食/火锅）
   修改字段：
     1. 团购价格（editable）
        原值：99元
        新值：128元
     2. 库存数量（editable）
        原值：500份
        运算：500 + 200（增量）
        新值：700份
   不可修改项：
     - 退款规则（readonly）：当前类目仅展示不可编辑
     - 划线价（derived）：由套餐总价计算，如需修改请调整套餐内容

   ⚠️ 修改后需重新提交平台审核，审核期间商品可能暂时不可售。
   ⚠️ 修改过程中页面可能自动生成草稿，退出前会与您确认保留或清理。

   确认修改请回复"确认"，有调整请直接说。
   ```
   **多字段修改**：如果商家一次要求改多个字段，全部列在同一张确认卡中，一次性确认，不分轮次逐个问。

### 第四步：执行修改 + 逐字段回读
1. 商家确认后，在来客商品编辑页执行修改操作。
2. **逐字段修改 + 即时回读**：每个字段填写新值后，立即回读该字段值，与目标值比对。
   - 回读一致 → 继续下一个字段
   - 回读不一致 → 停止操作，告知商家哪个字段写入后回读不符，不得继续写入其他字段；根据商家指示重试或回滚
3. **图片/素材类字段**：如果需要替换图片，需商家提供新图片素材；AI无法凭空生成商品图。素材来源、合规性和缺少素材时的处理方式详见 [references/material-policy.md](references/material-policy.md)。商家提供后上传并确认。**禁止生成门店实景、资质证书、服务过程证明等经营证明素材。**
4. **派生字段**：不直接修改派生字段展示值，而是修改其来源字段（如套餐/服务项目内容），修改后确认派生值已按预期更新。
5. **关联字段**（如适用门店）：走独立关联流程，在关联弹窗/页面中完成选择后回读确认。
6. 修改过程中如遇到页面异常、字段不可编辑、需要额外资质等情况，如实告知商家，不强行操作。

### 第五步：改后展示结果 + 确认 + 提交审核（单独确认）
1. **提交前全量校验**：按「基线快照与回滚协议」中"全部写完后的全量校验"执行——重新打开页面步骤、再次读取所有目标字段、比对非目标字段 diff、生成截图。全部通过后状态推进至 `READBACK_OK`，方可进入本步后续操作。任一不一致则按基线回滚，不得进入提交确认。
2. **展示改后结果**：向商家展示修改结果。**必须截取编辑页预览图给商家看**，让商家直观看到修改效果。

   **截图步骤**：
   - 使用当前环境可用的登录态浏览器能力，截取编辑页视口并保存到当前任务输出目录（不硬编码桌面路径）：
   ```python
   import seed_browser_use as bu
   import os

   # 确保页面状态同步
   bu.resync()

   # 截取当前编辑页视口，保存到任务输出目录（show=False 不重复回传给AI）
   save_path = os.path.join(os.getcwd(), "改品预览.png")
   result = bu.screenshot(path=save_path, show=False)
   print(f"SCREENSHOT_PATH:{result}")
   ```
   - 代码返回 `SCREENSHOT_PATH:xxx` 后，用 `present_files` 把该路径的截图展示给商家。
   - 文字部分简洁列出改了哪些字段（原值 → 新值），作为截图的辅助说明，不堆砌信息。
   格式示例：
   ```
   【改后结果】
   商品：「XXX双人套餐」
   已修改：
     ✅ 团购价格：99元 → 128元（回读一致）
     ✅ 库存数量：500份 → 700份（回读一致）

   以上修改已写入页面并回读确认。确认无误后我将提交审核。
   回复"提交"即可，有问题请直接说。
   ```
3. **商家确认后提交审核（单独确认，不得由改前授权替代）**：商家回复"提交""确认提交"后，状态推进至 `SUBMIT_ALLOWED`，点击提交审核按钮。
4. **提交结果核验（严格按「提交成功定义」执行）**：
   - 提交后等待页面明确成功反馈（Toast/弹窗/状态变更），不得仅凭按钮恢复可点击或页面跳转推断成功。
   - 返回商品管理列表，核验商品状态已更新为预期状态（如"审核中"）。
   - 进入审核中版本详情/预览，确认本次目标字段值已正确包含。
   - 对比草稿增量是否符合预期。
   - 核验商品名称和完整 ID 与改前确认一致。
   - **全部条件满足** → 状态推进至 `SUBMITTED`，向商家报告提交成功。
   - **任一条件不满足或无明确反馈** → 记为"结果未知/提交失败"，保留现场，提供一次重试或回滚选择，**不得自动重复提交**，不得宣称成功。
5. **结果告知**（仅在 `SUBMITTED` 后）：
   - 提交成功
   - 当前商品状态（审核中）
   - 预计审核时长（如来客页面有提示则引用，没有则说"以平台实际审核时间为准"）
   - 审核结果会在来客后台通知

### 第六步：退出前草稿检查与清理确认
1. **检查草稿增量**：对比进入编辑页前记录的草稿数量和当前草稿数量，确认是否因本次修改产生了新草稿。
2. **向商家说明草稿副作用**：如产生了新草稿，告知商家草稿内容和位置，由商家选择保留或清理。
3. **清理草稿（如需）**：商家要求清理时，删除本次产生的草稿。删除草稿为不可逆动作，需商家再次确认。
4. **如修改被取消或异常终止**：按基线快照将已修改字段恢复为原值，再次回读确认恢复成功，然后执行草稿检查。

## 审核驳回专项要点
审核驳回商品在通用流程基础上注意：
1. **自动读取驳回原因**：进入商品详情页后，优先定位平台标注的驳回原因区域，读取具体问题描述和对应字段。
2. **逐条确认**：如果有多个驳回问题，逐条跟商家确认要不要改、怎么改。
3. **修改方式建议**：对于驳回问题，AI可根据驳回原因给出修改建议（如"极限词'最好吃'建议改为'招牌推荐'"），但最终由商家确认。
4. **全部改完后追问**：所有驳回问题处理完后，必须问"驳回的问题都改好了，还有其他要一起改的吗？"——避免商家漏改导致再次驳回。
5. **驳回原因涉及 `absent` 字段时**：如平台驳回原因指向当前类目不存在的字段，如实告知商家该字段在当前类目不支持，建议核对类目是否选错。

## 注意事项
- 修改必须基于来客页面真实数据，不凭记忆或猜测填写
- **字段能力以实际页面为准**：不同类目字段差异大，不得假设某字段一定存在或可编辑
- 价格、库存等数字类字段修改后必须回读核对，避免多零少零
- 写入前必须执行硬校验，校验失败不得写入，不得依赖平台提交时报错
- 库存为最终总库存，增量操作必须先读原值再计算
- 不使用"最""第一""顶级"等广告法极限词（如商家原文有，应提醒可能违规并禁止写入）
- 图片替换需商家提供真实素材，不生成虚构商品图；**禁止生成门店实景、资质证书、服务过程证明等经营证明素材**。素材规则详见 [references/material-policy.md](references/material-policy.md)
- 提交审核是最终动作，提交后无法撤回修改，需商家明确单独确认
- 删除草稿、恢复售卖、下架、删除商品等不可逆动作不得复用改品授权，必须分别确认
- 如遇到来客页面改版、字段位置变化，以实际页面为准，灵活定位
