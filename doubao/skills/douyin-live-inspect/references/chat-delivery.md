# Chat 状态与报告交付

Chat 是云电脑和本地电脑的一致交付面：两种模式都必须承载状态、风险通知和最终报告。豆包工作统一按 [豆包工作交付](doubao-delivery.md) 打开直播远端操作台，质检报告不上传，仅将复盘报告上传报告服务，不因本地电脑环境改回本地页面。

## 中间风险播报开关

- Agent 在本次任务上下文保存 `realtime_broadcast`，默认 `false`；这是 Agent 编排开关，不是服务端质检参数，也不是内置运行时参数。新任务独立初始化，续办沿用原任务设置；旧上下文没有该字段时按关闭处理。
- 仅用户明确要求“开启播报”“实时播报”“发现风险就告诉我”“继续播报”等时设为 `true`，无需再次确认。只说“质检”“实时质检”“继续”或打开工作台，不构成开启授权。
- 关闭时不启动 Chat 风险轮询、不发送新增命中或定时风险心跳；创建结果、工作台链接、用户主动询问的一次性结果、结束确认和最终报告正常交付。不要为了询问是否开启而打断默认流程，也不显示“监听已停止”等未实际发生的状态。
- 用户要求“关闭播报”“不要再播报”或在风险播报语境中要求“停止监听”时立即设为 `false`，停止后续风险查询和中间播报，保留任务及最后已播报游标；服务端检测继续运行。到达单轮风险监听时限只停止风险查询，不更改用户已开启的开关；之后用户回复“继续”才恢复新一轮监听。

## 独立的任务结束监听

创建成功或明确续接的直播任务按 [任务结束监听](task-completion-watch.md) 持续等待并接续复盘；本页仅维护风险播报和对话摘要。关闭风险播报不取消结束监听。完整交付条件统一见 [豆包工作交付](doubao-delivery.md)。

## 当前执行轮次内的有界风险监听（仅开关开启时）

- “对话窗口仍打开”不代表 Agent 仍在执行；不能自行断言用户已离开。Chat 监听由当前执行轮次驱动，本地工作台是否独立刷新不代表 Chat 正在监听。两种宿主遵循同一交付约定，实际能力分别验证。
- `realtime_broadcast=true` 时，创建成功或用户要求恢复原任务后开始有界监听：默认本轮 10 分钟，每 15–30 秒查询一次；用户指定时长时采用该时长，并受宿主实际执行上限约束。开始时告知本轮监听时长。用户仅问“现在有风险吗”时只查询一次，回复中明确这是本次查询结果，未启动持续监听。
- 从 Skill 根目录运行 `node scripts/chat-status.mjs`，通过 stdin 传入本次内部项目、任务编号、场景及上一轮 `cursor`。该脚本每次只查询一次，不会自行建立持续监听；Agent 必须在当前轮次内安排后续查询，不能查询一次后以最终回复结束却承诺继续监听。
- 首次 `cursor` 为空；在 Chat 成功播报 `new_findings` 后保存返回的 `cursor`。若查询已完成但尚未播报，不推进已播报游标。后续复用同一任务的游标，只播报新增事件。每条使用时间、规则、证据摘要和原因；只使用安全字段。证据时间是媒体时间点，不等于审核返回或通知送达时间。
- 监听期间发现 `new_findings` 后立即通过当前轮次的中间消息播报，不等用户追问、不积压到最终回复。没有新增风险时保持安静，只在状态变化或最长 2 分钟一次心跳时更新概况。心跳不是本轮最终回复。
- 以下“本轮监听”仅指风险监听。风险监听达到时限或被关闭时，停止风险查询；若任务结束监听仍在运行，仅用中间消息说明风险播报停止、仍等待任务结束，不结束执行轮次。所有监听已停止或宿主即将结束执行时，才在最终回复明确：“本轮监听已停止，质检任务仍在运行。当前不会在后台继续监听；稍后在本对话回复‘继续’可恢复查询并补报可查询到的新增风险。”任务状态以最后一次查询为准；无法查询则说明状态未确认。停止监听不调用结束任务接口，也不称为暂停任务。宿主突然中断而未能告知时，在下次恢复时如实说明中断，不能声称期间一直在监听。
- 宿主无法在当前轮次持续执行或发送中间消息时，直接说明本轮只能查询状态、不能主动持续播报；不得以“我会继续监听”“结束后自动发报告”收尾。缺少事件唤醒能力时，不承诺回复结束后的推送或自动交付。
- 用户在同一对话要求继续时，复用任务标识、播报开关和最后已播报 `cursor`。开关开启时先查询当前状态，补报停止监听期间仍可查询到的新风险，再开始新一轮有界监听；开关关闭时不恢复风险轮询；明确要求续接原任务时恢复一次结束监听，单次状态查询仍只查询一次，已完成任务直接继续报告交付。不得重建任务、重新结束任务或重复旧提醒。上下文或历史窗口缺失时明确恢复范围，不承诺补齐全部风险；上下文缺失也不得从零游标结果断言所有记录均为新增。
- 若本轮观察到任务结束/完成，停止实时风险轮询，转入同一任务的报告交付。报告等待与实时监听分别计时：报告等待最多 10 分钟，到期提示“报告仍未就绪，本轮监听已停止；任务仍由服务端处理。稍后在本对话回复继续即可重新查询”。恢复只读查询，不重建或重新结束任务。

## 开启播报或用户主动查询时的 Chat 信息

- 每次状态变化展示任务名称、中文场景、产品状态和已监控时长。
- 心跳或用户询问时展示自动质检命中数、涉及规则数、最新命中时点和主要命中规则；这些都是当前查询窗口的统计，不表述为最终违规数。
- 新风险卡片展示规则、时间、证据摘要和原因。多个同规则问题可以在一条消息中汇总数量，但必须保留各时间点。
- 当前返回存在状态或来源无法判定的记录时，提示“部分记录暂未纳入统计”，不展示底层状态码。
- 用户确认结束且请求成功后，Chat 只提示“已停止继续采集，预计约 3 分钟完成剩余处理并生成质检报告，实际时间可能因内容处理进度有所变化”。真实终态到达后再提示“检测已完成”；“约 3 分钟”只表示通常等待时间，超过预估时按真实进度更新，不得宣称必然完成。期间不展示底层仍为“检测中”、已受理时长、轮询间隔、工作台通知结果或内部同步机制。检测失败、质检报告生成中、质检报告就绪、复盘报告就绪等变化正常同步。
- 工作台的筛选控件、滚动位置、截图缩略图和结束按钮不复制到 Chat。截图只在用户明确要求查看某条证据且宿主支持安全附件时提供；不得输出图片或媒体 URL。

## Chat 中的最终报告

质检报告就绪后，按交付规则核验远端控制台报告可读，并在 Chat 中给出对应报告链接及：

1. 自动质检结论：发现风险或未发现规则命中；后者不等于事实核验通过。
2. 任务概况：中文场景、检测状态和有效内容时长。
3. 风险摘要：按规则列出数量、时间点/时间段和简短证据；无命中时明确“本次未发现规则命中”。
4. 建议：只根据真实质检证据生成，不补造事实。

内容复盘就绪后，在 Chat 中给出：

1. 一句话结论。
2. 2–3 条表现亮点。
3. 2–3 条主要问题。
4. 推荐话术链路和可执行建议。
5. 数据边界：没有评论、流量、停留、商品点击及成交数据时，不能判断反馈或转化。

### 风险证据时间格式（直播与视频共用）

- Chat 风险摘要与质检报告统一使用 `HH:mm:ss ~ HH:mm:ss`；小时至少两位，超过 24 小时不回绕。原始数值和接口单位不变，仅格式化展示。
- 数值时间先按当前接口合同转换为秒：秒值直接使用，毫秒值除以 1000，再向下取整。不得按数值大小猜测单位；单位无法确认时显示“时间未返回”。
- 已有 `HH:mm:ss` 时间保留；只返回开始时间时仅显示该时点，不补成起止相同的区间。时间缺失、无效或结束早于开始时，缺失部分明确说明，不生成虚构区间。
- 示例：秒值 `62–93` → `00:01:02 ~ 00:01:33`；毫秒值 `62000–93000` → 同一结果；秒值 `3599–3601` → `00:59:59 ~ 01:00:01`；仅开始秒值 `62` → `00:01:02`。

Chat 只展示结构化摘要，不复制完整 ASR 或整份 HTML。

## JSON 交付

复盘生成后默认继续完成上传，再交付真实“打开复盘报告”链接与摘要，不询问“是否上传到质检服务”或要求用户回复“同意上传”。用户明确要求不上传时遵从；真实上传失败或宿主审批拒绝时如实说明，按 [豆包工作交付](doubao-delivery.md) 保留报告续办。

质检 HTML 不上传；直播与视频均在 Chat 交付经核验的控制台报告链接、结论与证据；仅复盘 JSON 按交付规则上传报告服务，流程、成功判定与失败续办以 [豆包工作交付](doubao-delivery.md) 为准。控制台报告链接与 Chat 摘要一起交付；不以本地下载落地页或临时附件替代 数据库保存。

JSON 上传成功时，UploadReport 返回的 `url`（脚本规范化为 `report_url`）已是可直接观看的报告页面，直接作为“打开复盘报告”的 Markdown 链接交付，并保留完整地址。无需再换取预览链接，不标注为下载地址。
