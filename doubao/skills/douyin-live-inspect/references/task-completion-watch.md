# 直播任务结束监听与自动复盘

仅用于当前 Agent 创建成功或用户明确要求续接的远端直播任务；单次状态查询、历史列表和视频任务不启动本监听。监听使用宿主可管理的长运行进程，Agent 通过持续等待跟进结果；不是独立后台服务，也不会唤醒已经结束执行的 Agent。

## 启动与等待

1. 创建成功后先按 [豆包工作交付](doubao-delivery.md#直播任务打开远端操作台) 提供监控台链接，再启动本监听；页面打不开也保留已创建任务并继续监听。创建失败或结果未知不启动，不重建任务。保存创建结果中的 `environment`、`profile`、`account_id`、`project_name`、`task_id`、`scenario` 及监控台地址。
2. 以环境、profile、account_id、项目、任务作为会话内唯一键，保存监听工具的会话引用。同一任务已有运行中的监听时继续等待它，不再启动第二个；不使用 detached、nohup、cron 或宿主自动化。宿主无法持续执行时如实说明，保留任务供续办，不声称会自动交付。
3. **启动受管进程**：根据当前工具 Schema 使用会话或后台任务能力，从 Skill 根目录运行 `node scripts/task-completion-watch.mjs --output <落盘路径>`，用 stdin 传入一行 JSON：`{"environment":"<原任务环境>","profile":"<原任务profile>","account_id":"<原账号ID>","project_name":"<项目>","task_id":<任务编号>,"scenario":"<场景名称>"}`。身份缺失和恢复按 [原账号与任务绑定](auth-recovery.md#原账号与任务绑定) 处理。路径中的 profile 和 project_key 使用安全文件名或哈希；读取时核对结果中的环境、profile、account_id、项目和任务均与本次一致。落盘路径建议为会话工作目录下 `runtime-state/watch-<environment>-<profile>-<account_id>-<project_key>-<task_id>.json`，脚本完成（成功或失败）后会把完整结果原子写入该文件，供 Agent 轮次中断后续办读取。
4. 告知正在等待任务结束，最长 4 小时。脚本启动时立即核验，此后每 60 秒查询一次，每次请求最多 30 秒；不读取风险记录或截图。网络暂时异常按下一轮重试；任务状态查询首次遇到 `AUTH_REQUIRED` 时等待 30 秒后重试，整个本轮监听仅有一次认证重试额度，查询成功后也不重置，再次遇到认证错误则退出并恢复原账号授权。该重试不适用于启动时的账号绑定核验或终态后的报告准备；权限错误或任务不匹配仍立即退出。4 小时包含请求及重试等待时间；等待期间响应取消，剩余监听时间不足 30 秒时仅等待至截止，不再查询。
5. **持续等待**：保存宿主返回的会话或后台任务引用，按实际工具的等待／轮询接口跟进；单次等待不超过宿主上限。异步受理、工具等待超时不等于进程结束，仍运行则继续等待。用户插入消息时可获取一次非阻塞快照并回复，随后继续；不要提前用最终回复结束执行。不写死其他宿主的工具名。结束监听不受 `realtime_broadcast` 控制，风险播报到期不取消它。
6. **进程结束后读取结果**：优先从 `--output` 落盘文件读取完整结果；落盘文件不存在或不可读时再读取宿主保留的进程最终输出。读取后先保留落盘文件，复盘成功交付或状态已保存到后续续办记录后再删除（清理失败不阻塞续办）。
7. 用户只要求关闭风险播报时，保持本监听；明确取消自动复盘、停止全部监听，或明确要求结束当前等待时，取消对应进程并等待它退出。宿主结束执行前也应取消，避免遗留进程。取消监听不调用结束任务接口、不停止服务端检测。用户要求"结束质检"仍走既有结束确认流程；实际状态达到终态才完成本监听。

## 断点续办

Agent 轮次被宿主回收、对话窗口关闭或用户离开后重新回来时，按以下顺序恢复，不重建任务。优先使用续办记录保存的实际 `--output` 路径和会话引用；下方文件名仅是新监听的建议，不能据此重算路径而忽略旧版已经落盘的结果。旧结果身份字段不足时按 [原账号与任务绑定](auth-recovery.md#原账号与任务绑定) 从可信记录恢复，不能从当前登录补齐：

1. 检查落盘路径 `runtime-state/watch-<environment>-<profile>-<account_id>-<project_key>-<task_id>.json` 是否存在且包含完整结果：
   - 存在且 `ok:true`、`data.next_action:generate_review` → 直接复用 `data.review_preparation` 进入复盘分析，不重新监听。
   - 存在且 `ok:false` → 按错误码处理：`REPORT_NOT_READY` 说明任务已结束但报告未就绪，重新启动监听（脚本会立即核验终态并进入报告等待）；其他错误按实际阶段说明并续办。
2. 落盘文件不存在时，检查是否有仍在运行的后台监听进程（同任务唯一键）；有则复用并继续循环等待。
3. 既无落盘结果也无活动进程时，用原任务上下文重新启动一次后台监听。脚本启动时立即核验当前状态：已结束则直接进入报告等待，检测中则继续轮询。绝不重新创建质检任务。
4. 续办时保留原 `environment`、`profile`、`account_id`、项目、场景和任务编号，不使用当前默认账号替代。

## 返回结果与复盘接续

输出沿用 `{ok, command, data, error}`。`data.context` 是同任务接续参数，`task_status` 仅供内部判断；不要把内部字段、原始响应或命令复制给用户。

- `completed`：仅表示已观察到真实状态 3/4，不代表双报告交付完成。监听入口停止任务状态轮询后，自动调用共享准备逻辑等待 GetReport 并生成输入；准备成功才返回 `ok:true`、`review_phase:analyzing`、`next_action:generate_review` 和 `review_preparation`（沿用 prepare 的全部返回字段）。当前 Agent 停止同任务风险监听，立即接续下方分析、组装和上传。远端手动停止、自然完成和启动时已完成统一处理；不得以完成事件或输入文件作为最终交付。结束操作受理不代表达到终态。
- `task_failed`：状态 5，停止并说明检测失败，不生成复盘。
- `timed_out`：最长 4 小时已到，仅停止监听，说明最后已知状态，保留原任务，用户明确要求继续后再恢复一轮。
- `cancelled`：仅本轮监听取消，不生成复盘，不把任务说成已结束。
- `ok:false`：`error.stage:task_watch` 表示监听失败；`report_preparation` 表示终态后的准备失败，此时 `data` 保留任务完成状态、`context` 和 `review_phase`，但不返回 `generate_review`。`REPORT_NOT_READY` 保留 waiting 阶段，其他准备失败保留 preparing；`CANCELLED` 表示准备已取消，不抹去已确认的任务终态。缺 ASR 仍交付可用质检报告并说明复盘缺少依据；认证恢复或用户续办后从原任务对应阶段继续，不重新创建。

以同任务唯一键保存 `review_phase`（waiting/preparing/analyzing/rendered/uploading/saved）、本地 JSON 路径及已确认的上传结果。完成事件只接续一次：已有进行中的复盘继续该流程；已确认上传成功复用 `report_url`；上传结果未知先核验，不能重新生成并覆盖上传。

1. 正常监听返回后直接复用 `data.review_preparation`，不要重复 prepare。监听入口已传递原任务环境、profile、项目、编号及场景并完成准备。仅已确认终态但缺少有效准备结果时，将同任务上下文传给 `scripts/ecommerce-review-prepare.mjs`：`{"environment":"<原环境>","profile":"<原profile>","account_id":"<原账号ID>","project_name":"<项目>","task_id":<任务编号>,"scenario_name":"<场景>"}`。报告就绪等待另计最多 10 分钟、每 30 秒一次，每次请求最多 30 秒；请求和等待均响应取消。超时停止查询并保存 waiting 阶段，用户续办直接进入准备阶段，不再轮询任务状态。
2. 准备成功后，先按 [交互与进度](doubao-delivery.md#交互与进度) 在对话中告知用户质检报告已生成、内容复盘还需要一些时间；同一阶段已提示则不重复。随后由**当前 Agent**读取 [内容复盘规则](ecommerce-review.md) 及其输入合同、分析规则，读取临时输入并完成对应场景分析。监听入口已准备输入，但本身不生成模型分析；`generate_review` 必须由当前 Agent 连续执行，不能以最终回复结束本轮或要求用户再次发送指令。
3. 按 [默认收尾入口](ecommerce-review.md#默认收尾入口) 将准备上下文及分析交给 `scripts/ecommerce-review-finalize.mjs`，由运行时连续组装、上传、只读核验并清理输入。缺 ASR 时交付已有质检结果并说明复盘缺少依据，不臆造内容。显式仅本地时使用独立组装流程，不上传。
4. 保存 `finalization_id` 与结果状态；未知上传只续办核验，已保存复用链接，不重新生成或覆盖。质检控制台报告按既有交付规则单独提供，不因页面核验失败阻塞复盘上传。
5. Agent 完成页面核验并交付后，调用同一入口 `--ack-delivered` 清理最终文件。清理失败只重试该步骤，不能笼统声称所有收尾成功。

宿主中断后，不假定此前进程仍在执行或上传已经完成。续办先核对原任务、已保存的阶段及上传结果；存在活动监听则复用，否则启动一次新监听。确认已结束但尚未复盘时直接接续报告流程；绝不宣称中断期间一直在监听。

报告准备的 GetReport 只读请求遇到临时网络错误、请求超时、HTTP 429 或 5xx，沿原账号和任务自动追加最多两次重试，仍受原 10 分钟总预算和轮询间隔限制。权限、登录、身份不匹配与无有效内容不盲目重试；用户取消立即停止。耗尽后保留真实失败原因，交付已经可用的质检结果，不能把复盘准备失败变成质检报告不交付。报告生成与宿主页面/附件交付独立推进；已生成的报告复用，上传未知先核验，不自动重放写入。
