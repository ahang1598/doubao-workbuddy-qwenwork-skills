# Lite 判定调度与恢复

新实时直播由当前 Agent 串行处理，不做 Worker 能力探测。有内容立即判断，每批最多20段，不限制批内媒体时长。提交直接续领，空批次按下方运行时协议等待。处理策略见 [实时策略](../SKILL.md#实时策略)。

## 运行时协议

回执要求 `refresh-credentials` 时，在豆包工作的新一次宿主工具调用中执行原 CLI 的 `refresh-credentials --task-dir <原目录>`，继承当次宿主环境；不要从后台进程或持久 shell 反复调用，也不读取、打印或向用户索取凭证。随后按回执执行 `status` 继续原任务。`credential_changed=false` 不代表续期成功，继续本地处理并等待运行时再次提示；上传地址异常不能直接认定为凭证过期。宿主没有提供新凭证时不得声称云端已恢复。

直接调用随包 CLI，不编写替代调度脚本，不把完整回执裁剪为片段数、字幕或采集状态后再决定是否继续。完整读取 `result_file` 或分页后，按 `next_action`、`continuation_instruction` 和交付合同执行；后台命令完成只代表本次命令结束，不代表质检完成。

采集 `ended/stopped/failed`、空批次、轮询到期和 ASR 失败均不是退出本轮的条件。采集仍运行时继续领取或等待；采集结束时继续已有内容处理，再生成质检、复盘并实际交付确认。读取数据库或诊断音频后必须回到原任务 `status` 续办，不能以手工统计摘要代替报告。每次准备最终回复前核对最新回执：`workflow_complete=false` 时只发中间进度并执行下一动作；不得要求用户说“结束质检”才继续。宿主真实中断或工具不可用时明确未完成、原目录与最后动作，不承诺后台会唤醒 Agent。

同一任务使用同一 dispatcher_id，默认 main。新的领取或提交使用新的 request-id；结果未知时用原 ID 执行 review-state，读取保存状态与继续动作，不重复提交。旧回执只恢复原结果，不推进队列。用户明确要求恢复且工具可用时，可执行 review-state 返回的 review-recover --takeover，由运行时使旧合同失效后沿新合同续办；不会启动或恢复采集。

带 `--request-id` 的云电脑领取/提交新云电脑任务仅在开始快照缺失或采集结束时返回，旧任务仍在周期到期时返回 `snapshot_check`。没有该字段时直接处理原 next，不补查 status；返回该字段时，必须从当前 Lite 根目录用同一 Python 环境执行其中的 `command_argv`（原任务 status），处理该检查返回的工作台附件或导出错误，再继续原领取/提交响应的 `next` / `next_action`。旧回执缺少该字段时从 `argv` 的 `status` 起取参数。检查无快照时立即继续，不等待快照周期，不按 status 的继续动作重新领取。受控命令不渲染 HTML，快照检查不占短命令执行预算，主 Agent 原判定合同保持有效；大结果分页摘要同样保留此动作。Chat、本地任务与结果分页/回执查询不增加此检查。

提交原样执行合同命令。每轮先检查顶层 `snapshot_delivery`，ready 且附件能力可用时先尝试交付工作台，失败或不可用则按 [交付降级](delivery.md#阻塞恢复与跳过) 在对话更新进度并立即继续原 `next_action`，不等待附件修复；大结果分页摘要也保留此交付信息，不能只处理 `next` 而漏掉附件。大结果首响应含模板路径与提交命令；优先用宿主文件工具完整读取 result_file，不另行搜索模板。不能读文件时只沿 next_page_argv 读取到 next_offset=null；offset 是 Unicode 字符位置，不能按 total_bytes 推算。无论哪种方式，都须先读完证据及适用规则。命令输出丢失按上述 review-state 规则恢复，不扫描最新文件或重建请求、绑定，不重派未知任务，也不使用 `head` 截断命令 JSON。

新字幕合同省去重复 channels；模板已随结果提供时无需再读 input_path。串行 submit_command_argv 默认续领最多20段。成功提交后 next 含片段与合同时，完成 snapshot_check 要求的附件检查后直接处理该批，不通过 status 重新领取；next 为空批次时按其 next_action 继续，status 在云电脑执行 wait_command_argv（status --wait-seconds 30，有内容提前返回），本地最多等3秒后查询，不能套用“不再 status”的有片段分支。完整语义仍由模型逐条判定。

用户未回复、阶段性播报或空批次都不转入等待用户状态；后台媒体 worker 与工作台刷新不承担语义判定。云电脑仅在宿主实际提示额度不足时按[提前收尾](#云电脑提前收尾)执行，不按采集、判定或工具调用次数停止。

submit_command_argv 的 --next 返回下一批；repair_required=true 时只修复 retry_segment_ids，再执行 retry_command_argv。修复后的请求有新 ID，保留 --next。成功项不重判，身份与版本字段沿用返回值。

## ASR 恢复后判定未推进

ASR 恢复只表示语音处理有进展，不表示判定已完成。出现 `first_review_stalled`、`review_processing_stalled` 或 `review_not_dispatched` 时，沿原任务检查领取与提交：

- 当前没有结果未知的命令或在途合同，且返回 `next_action=review-next` 时，立即领取并处理；`await_host` 是等待当前 Agent 执行，不是等待用户回复，也不能仅轮询 ASR 或播报进度。
- 已有领取合同则读齐证据、完成判定并执行返回的提交命令；领取或提交结果未知时，先用原 request-id 查询 `review-state`，按保存状态续办，不另建请求抢领或重复提交。
- 以提交回执确认结果已保存，再处理返回的下一批或修复动作；ASR 成功、领取成功和媒体 worker 运行都不能代替判定保存确认。
- 停止后仅处理运行时允许的剩余合同；已冻结或已失效的合同不再提交，沿返回动作交付已有报告或失败说明。宿主工具确实不可用时保留原任务、请求标识和最后已确认阶段，说明续办阻塞，不承诺后台自动判定。

## 原在途 Worker

只有已有任务包含 child 批次时才处理下列恢复，不新建 Worker。调度者仍是唯一写库者；Worker 只返回它已领取批次的结果。

- 已知 host_task_id 的运行任务核对实际状态，返回结果立即按原合同提交。
- dispatching 或状态未知的任务先核对宿主，不重复创建任务；未占用的内容可以串行处理。
- returned 结果修复后按原 context_id 重交；旧代次、错误任务身份或过期证据的结果拒绝。
- cancelling 只取消本任务已知的 Worker，确认退出后登记 cancelled，携带 batch_id、generation、host_task_id 和 exit_confirmed=true。
- 宿主明确证明任务未启动时登记 failed、exit_confirmed=true、not_started_confirmed=true。不能把等待时间当作退出证明。

控制动作使用 `review-next --task-dir <原目录> --dispatcher-id <原ID> --dispatch-input-file <控制JSON文件>`，只确认动作，不领取新批次。报告固定后迟到结果不再写入；进程清理与报告交付独立。

## 采集与收尾

### 采集中

- 默认30秒切片，单段最多60秒。ASR 最多并行10段，本地最多按需启动10个独立模型进程；资源不足时使用已启动进程。
- 已采集片段保留排队，不因积压跳过。处理跟不上时说明延迟；达到采集资源上限时停止新增采集，继续已有内容。
- 主 Agent 的合同不因超过120秒无提交失效；异常子任务按取消与重新领取回执恢复，不跳过片段。
- 云端 ASR 持续无结果满10分钟进入备用或证据不足处理；本地单次识别以片长加90秒为故障超时。

### 停止后

用户停止、确认下播、达到任务时限或采集已终止后，执行同一收尾流程：

1. 停止新增采集，保留已落盘媒体与判定；待判定为0时仍按 `next_action` 检查媒体处理。
2. 在120秒无进展窗口内继续处理。识别状态或证据变化、判定提交、批次推进可续期；心跳与重复轮询不能续期。
3. 已提交且有远端任务 ID 的 ASR 保留原查询预算，并在本地15分钟、新云电脑3分钟总上限内预留判定窗口。worker 退出后保留媒体，在原预算内恢复。
4. 已领取的主 Agent 合同继续提交，未领取内容继续领取；不能只轮询 status。异常子任务允许有界取消重派，运行中或派发结果未知时必须先确认取消。
5. 排空则进入报告。单片段恢复耗尽或总时限到期时保留已完成结果，披露未完成范围与具体阻塞原因，拒绝迟到写入。用户明确要求立即舍弃时沿原立即停止语义收尾。

需要恢复状态更新时使用原 task_dir 执行 `resume`；已冻结任务只恢复收尾与报告，不重新采集。工作台“监控已结束／正在生成报告”不表示流程完成。

报告生成与交付按[复盘](recap.md)执行，不受上述收尾时限截断。复盘不追加识别或补判；历史已完成任务和报告不重开。终态失败须交付真实原因并确认 failed/chat，`workflow_outcome=failed` 不表示报告生成成功。

## 云电脑提前收尾

- 启动前说明有限采样、实际采集上限和双报告流程，报告不代表整场直播；不要求 Agent 统计工具调用次数。
- 仅宿主实际提示步骤、上下文或执行时间不足时，先提交本批已完成判断；执行结果未知先查 `review-state`。
- 再执行 `stop --task-dir <原目录> --reason execution_limit`，不使用 `--immediate`，不伪造 `--user-instruction`。
- 停止后最多处理已有内容180秒，随后生成、交付并确认两份报告。未完成范围按真实原因说明；不重建任务、不并行启动检测、不追加采样。
- 工作台仅在开始、必要恢复和采集结束时交付；运行中风险用 Chat 提示，不补导出或重复查快照。模板已在回执中时不重复读取，完整判定后直接按合同 `--next` 续领。
- 依赖准备失败只交付具体阻塞，不循环安装、诊断或启动。旧任务保存的调度计数不再触发停止，续办不重置采集时长。
- 已硬中断时保留原目录和请求；恢复后复用已有报告，已停止任务只收尾。无有效内容交付失败说明，不生成空成功报告。
- 宿主总步数无法由运行时直接获知；不承诺200步端到端保证，也不承诺后台自动生成复盘。

## 创建进展与中断续办

- `progress_health` 区分首媒体、首字幕和首判定卡点。
- 180秒无业务进展、心跳过期且 worker 独占锁释放时，运行时沿原任务最多自动恢复两次；Agent 不并行重启或另建任务。
- 锁仍占用或恢复耗尽时说明阻塞原因。
- 报告阶段按 `report_checkpoint` 与 `next_action` 继续复盘、导出或交付，保留已保存结果和回执；详见[复盘恢复](recap.md)。
