# 70 · 文档、图文与正式产物输出

> 输出层 reference。当交付涉及飞书文档、HTML、图文文档、流程图、卡片、表格或截图标注时读取。负责：正式产物格式选择、默认案例文档结构、图片优先级与禁令、无图替代方案、隐私脱敏、丰富不冗余原则。所有 template 的图文规范以本文件为准。

## 一、正式产物格式（强制）

所有正式电商客服产物默认只允许以下格式：
1. 飞书文档；
2. HTML。

客服回复类请求也属于正式产物。即使使用者只问“这句怎么回”，也要拓展为可交付文档；但文档第一屏必须先给可直接复制发送的话术，不能让建文档流程弱化当前回复。

选择规则：
- 使用者明确要求飞书文档 → 创建或更新飞书文档；
- 使用者明确要求HTML → 生成HTML；
- 使用者未指定 → 先检查是否有可用飞书创建能力；可用则创建飞书文档；
- 飞书能力不可用 → 生成HTML备用，并在最终回复中说明原因。

允许改用HTML备用的情况：
- 当前环境没有可用飞书创建能力；
- 飞书认证、权限或登录状态明确失败；
- 创建或更新飞书文档的命令/工具明确失败；
- 使用者明确要求不要使用飞书；
- 当前任务只适合交付本地可打开的HTML文件。

禁止仅以普通聊天文本、纯Markdown、提纲、摘要、链接集合或“见聊天记录”作为正式产物。最终聊天回复只负责交付飞书文档链接或HTML文件路径，并简要说明产物类型，不重复粘贴完整正文。

工具探测与降级：
1. 先判断当前环境是否有飞书文档创建/更新工具、认证状态和目标空间权限。
2. 有可用飞书能力时，按模板创建或更新飞书文档。
3. 飞书能力缺失、认证失败、权限失败或命令失败时，立即降级生成单文件 HTML。
4. 降级后不得中断任务；最终说明已使用 HTML 交付以及飞书不可用原因。

## 二、HTML备用要求

HTML必须是可独立打开的完整单文件，至少包含：
- `<!DOCTYPE html>`；
- `<html lang="zh-CN">`；
- UTF-8；
- viewport；
- 页面标题；
- 内嵌CSS；
- 完整客服产物正文。

HTML正文必须包含对应产物的完整内容，不能只放摘要或链接。版式应清晰、可打印、适合客服主管或一线客服直接使用。可使用浅色信息块、表格、流程卡、风险卡、话术卡和执行步骤；避免大面积深色背景或装饰性视觉。

## 三、丰富但不冗余（总原则）

> 同一信息只在一个位置完整表达，其他章节只引用结论，不再次完整复述。

信息分工：
- 截图 → 展示原始证据；
- 标注 → 指出关键位置；
- 问题分析 → 解释；
- 策略 → 决定怎么处理；
- 话术 → 对外表达。

**禁止**把客户投诉内容在"背景、问题判断、策略、总结"里重复四遍。

压缩规则：
- 具体案例正文默认控制在 6-8 个 H2 内；简单案例可合并为 4-5 个 H2。
- 不使用 H3，除非同一 H2 下确实存在两个以上独立方案；能用表格、分栏、清单表达时不用新标题。
- 首屏只放“可发话术 + 处理看板 + 流程图”的行动信息，不放材料背景、长分析和内部字段。
- 每个章节只回答一个问题：怎么说、怎么做、追问怎么接、什么不能承诺、依据是什么。
- “判断依据和材料核实”只保留会影响处理策略的事实，不把客户原话、情绪、诉求在多个章节重复展开。
- 占位符只放在真正缺失的信息处；不要为了模板完整而到处写【】。
- 不要让表格成为主要版面。连续两个大表会显得笨重；追问分支超过 4 行时，优先拆成小卡片、分栏或流程图。
- 不要滥用高亮块。具体案例文档默认最多 1-2 个 `<callout>`：话术卡 1 个，必要时风险/红线 1 个。其他内容优先用普通 `<grid>`、`<table>`、`<blockquote>`、`<ol>`、`<checkbox>` 和流程图承载。

## 四、具体案例开头顺序（强制）

具体客服案例文档开头必须先解决“客服现在怎么回、为什么这样回、接下来怎么做”。打开文档后，使用者应按顺序看到：

1. **可直接复制发送的首轮回复**：普通咨询用信息型；催促、投诉、售后异常、补偿争议、反复沟通用补救型。
2. **处理看板**：用三列卡片说明现在怎么做、先核实什么、边界与替代说法。
3. **客服处理流程图**：用飞书 Mermaid 画板展示判断路径。
4. **客户追问时怎么接**：客户要退/换/补偿/继续投诉时分别怎么接。
5. **核实材料和升级边界**：列出会影响处理的缺失材料和升级条件。

禁止把大段背景、材料说明、事实分类、情绪分析、规则依据或流程图放在话术前面。分析内容必须放在策略和流程之后，用来解释为什么这么处理。

飞书文档或HTML中，开头应使用明显的信息层级：
- 完整首轮回复用 1 个话术卡或引用块，便于复制；
- 处理策略、下一步、边界与替代说法用普通三列处理看板，不要三列都做高亮块；
- 客服处理流程用飞书流程图，不只用编号清单；
- 客户追问分支优先用卡片或小表格；
- 不能承诺事项只有高风险时才用风险高亮块。

不要让“可直接发送话术”只作为正文中间的一段普通段落出现。
不要使用明显的内部字段名当成面向使用者的标题，例如“首屏行动区”“事实分层”“响应需求标签”“权限判断”。这些内容可以在正文中自然表达，但不应出现在目录标题里。

## 五、飞书富排版建议

生成飞书文档时优先使用 XML 富 block，不要把 Markdown 骨架直接塞进正文。

具体案例推荐布局：
- 文档标题：`<title>`，用短标题概括客户问题，不写“方案/报告/分析”堆叠标题。
- 开头回复：用唯一的主要 `<callout emoji="💬" background-color="light-green" border-color="green">` 放完整可复制首轮回复；若文档另有高风险红线，可再加 1 个风险 callout。
- 处理看板：`<grid>` 三列普通内容。列为“现在怎么做 / 先核实什么 / 边界与替代说法”，每列 2-4 条，避免长段落；不要把三列分别包成 callout。
- 流程图：`<whiteboard type="mermaid">`，用 lark-cli 直接插入飞书流程图；售后投诉、履约异常、退换货、补偿争议、舆情询问必须有。
- 追问分支：优先用小表格或普通 `<grid>`，不把每个追问都做成 callout。
- 核实材料和升级边界：用 2 列普通 `<grid>`、紧凑表格或清单，避免再堆一个长表。
- 执行步骤：`<checkbox>`，只保留 4-6 项关键落地动作。

具体案例推荐首屏信息结构：
1. 首轮回复卡：直接复制发送；
2. 处理看板：一眼看到“现在怎么做、先查什么、边界怎么表达”；
3. 流程图：从客户反馈到退/换/补偿/升级的判断路径；
4. 追问接法：只放客户下一句最可能问的 3-4 类；
5. 核实和升级：把依据压缩到行动所需。

Mermaid 流程图要求：
- 使用 `flowchart TD` 或 `flowchart LR`，节点文案短，尽量不超过 14 个字；
- 路径必须体现关键分叉，如资格是否符合、客户是否要补偿、情绪是否升级；
- 不使用复杂配色，不写大段说明进节点；
- 中文节点统一写成 `A["节点文案"]`，判断节点写成 `D{"是否符合条件"}`，尽量避免问号、斜杠、括号和长句导致 lark-cli 解析失败；
- HTML 备用时用内嵌 SVG 或流程卡替代，但飞书产物必须优先用 `<whiteboard type="mermaid">`。

SOP、Bot、舆情文档也应使用同类富 block：
- SOP：流程用白板/流程图，权限用表格，红线用 callout，落地检查用 checkbox。
- Bot：自动回复项用表格或分栏，转人工规则用 callout，字段收集用 checkbox。
- 私聊舆情处置：统一回复用 callout，舆情判断看板用紧凑表格，客户分支用小表格，可答/不可答用 grid 或表格，高风险升级摘要用 callout 或代码块。

颜色语义保持清晰：
- 推荐/可执行：`light-green`；
- 待确认/注意：`light-yellow`；
- 风险/红线：`light-red`；
- 信息说明：`light-blue`；
- 表头：`light-gray`。

避免：
- 连续 4 段以上普通段落；
- 整页只有列表或大表，没有卡片/流程图/清单；
- 三列表格撑满页面、每格都是长话术；
- 连续出现多个 `<callout>`，或每个分栏都套高亮块；
- 为了“丰富”加入无信息价值的装饰图；
- 大面积深色背景或花哨配色；
- 在目录里堆“1.1/1.2/1.3”的内部字段。

## 六、默认案例文档结构

对具体客服案例，默认采用：
1. 可直接复制发送的首轮回复；
2. 处理看板；
3. 客服处理流程图；
4. 客户追问时怎么接；
5. 核实材料和升级边界；
6. 客服执行步骤。

具体案例默认必须包含客服处理流程图。售后投诉、履约异常、退换货、补偿争议、舆情询问必须有流程图；没有真实图片时，也要用流程图承载处理路径。

其中“核实材料和升级边界”应短而准，只保留支撑行动建议的内容；不要把“事实分层、感受、诉求、响应标签”拆成多个目录标题。

> 该结构**不机械套用到所有任务**。Bot 用 Bot 模板、SOP 用 SOP 模板、舆情用私聊舆情处置模板。

**所有任务共同的输出底线**：
> 核心结论 ＋ 策略或规则 ＋ 可直接使用的产物 ＋ 线上执行方式 ＋ 风险边界。

## 七、商家带图处理

使用者上传图片时，优先把图片作为真实材料和证据来源处理，而不是装饰素材。

处理顺序：
1. 读取图片内容，识别聊天原话、商品问题、详情页承诺、订单状态、物流节点、差评内容或售后记录；
2. 必要时下载或引用原图，保留与文档的材料关系；
3. 对真实截图进行脱敏、裁剪、编号、重点标注，裁掉无关区域和多余隐私；
4. 在文档中说明图片能支持什么、不能确认什么；
5. 用流程图、决策图、表格、策略卡或风险卡补充说明。

图片必须服务于理解或执行，不能只是装饰。

## 八、图片禁令

**禁止生成/使用**：
- 伪造的客户聊天截图；
- 伪造的订单或物流凭证；
- 看似真实的商品问题证据；
- 对真实聊天截图、订单/物流凭证、差评截图、商品问题图做图生图或改造成新证据；
- 与内容无关的客服人物、购物车、握手等装饰图。

只有非证据类视觉才可生成新图，例如流程图、决策图、说明卡、SOP示意图。凡是会被理解为真实客户材料、真实商品状态或真实平台凭证的图片，都只能引用、脱敏、裁剪和标注，不能图生图。

## 九、无真实图片时的替代

可用：流程图、决策树、对比表、风险卡、策略卡、时间轴。
**不能因为没有图片而中断文档生成。**

### 常用图文卡片类型（供各场景复用）
- 流程图 / 决策树：处理路径、判断分支；具体案例优先用 lark-cli `<whiteboard type="mermaid">` 插入飞书流程图；
- 对比表：商品差异、价格构成、订单-实收对照、宣传-真实能力对照；
- 策略卡 / 话术卡：策略要点、可直接发送话术；
- 风险卡 / 权限阶梯卡：风险边界、可给/需审批/无权限；
- 时间轴：物流状态、预售、沟通升级点；
- 标注图：对真实截图/详情页的重点圈注，不改变原始事实。

## 十、隐私脱敏（强制）

截图与文档需保护并脱敏：姓名、电话、地址、订单号、支付信息及其他个人信息。脱敏后再用于文档或标注。

默认脱敏规则：
- 姓名：保留姓或称呼，其余用 `*`；
- 手机号：保留前 3 位和后 4 位，中间用 `****`；
- 地址：保留省/市/区级定位，隐藏门牌号、楼栋、单元和详细地址；
- 订单号、支付单号、物流单号：只保留后 4 位或使用 `【已脱敏编号】`；
- 支付信息：隐藏账户、流水号、银行卡、支付截图中的金额外敏感字段；
- 聊天截图：裁掉无关头像、昵称、电话、地址、订单栏和旁支对话，只保留判断当前问题所需区域。

临时文件处理：
- 下载、裁剪、标注产生的原图和中间文件只用于生成交付物；
- 交付完成后清理非必要临时文件；
- 需要保留素材时，只保留脱敏后的版本，并在文档中标明材料用途。
