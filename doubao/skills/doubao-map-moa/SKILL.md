# 豆包地图Skill

## 概述

提供路线规划、导航指令、公交地铁线路查询、地点搜索与地图标记、当前位置定位。工具返回是地点、路线、距离、时长、线路信息、POI、实体 ID 和卡片引用的事实来源，不凭记忆替代查询，不编造结果。

本文件保留业务决策与关键约束；调用参数的类型、必填项和合法值以实际生效的工具定义为准。定义与本文不一致时，不猜测兼容映射或补造字段；只执行约定明确的部分，并说明无法满足的需求。

## 场景路由

| 用户意图 | 处理方式 |
| --- | --- |
| 从 A 到 B、怎么去、怎么走、多远、多久、哪个更近、交通换乘 | `route_plan_v2`，按“核心流程”检查地点与定位 |
| 导航去/到/回某地、带我去、帮我导航、从 A 导航到 B | 规划路线并出卡；是否启动导航按“导航执行”判断 |
| 发起/开始/启动/调起/立即/马上/现在导航 | 先规划路线，满足导航执行条件后启动导航 |
| 停止、结束、退出导航 | `navigate_command`，`command="stop_navi"` |
| 公交、地铁、市内或明确跨城公共交通路线 | `route_plan_v2`，出行方式与偏好按“路线参数”填写 |
| 某条公交/地铁线的首末班、票价、方向、途经站，或是否经过某站 | `transit_query` |
| 附近有什么、某地点在哪、哪里有、找地点 | 纯位置查询走 `local_search` → `map_mark(poi_ids)` |
| 我在哪、我在哪条街、当前位置、共享位置 | `locate`，按“纯定位交付”处理 |
| 餐厅、酒店、景区等消费推荐、比较及营业时间/价格/预约等消费事实咨询 | 交 `doubao-trade-locallife` 主导；仅附带地址不另开地图查询 |
| 中国大陆多日游、Citywalk、自驾游、景区游览的完整行程与整体地图 | 交 `doubao-trade-locallife` 的旅行地图流程 |
| 路线费用、打车多久到、打车费用、叫车或接驾 ETA | 不属于本 Skill，不调用地图工具回答 |

纯位置查询支持交易类和非交易类地点，不按行业过滤。“某餐厅在哪”由本 Skill 执行地点查询与地图交付，不因是商户再转生服重复出卡；“附近哪家餐厅适合聚餐”“推荐餐厅并附地址”由 `doubao-trade-locallife` 主导；“去某餐厅怎么走”由本 Skill 规划路线。混合请求按用户主要任务确定唯一主流程，消费事实/决策归生服，本 Skill 仅承接其中独立的位置或交通需求。

旅行混合需求由旅行 Skill 负责主流程，本 Skill 只提供其中明确路段的交通数据。不要把 POI 点位集合或一条交通路线当作完整旅行地图，也不要对同一业务结果重复出卡。目标 Skill 不可用时说明能力缺失。

## 核心流程

1. 按用户任务选择场景；与位置、交通无关的问题不调用地图工具。多个问题逐项处理。
2. 检查用户原话及上下文中的地点信息，按下述规则追问、复用或交工具消歧。
3. 需要用户当前位置且上下文没有可用定位时，先调用 `locate`；定位失败不继续编造路线或附近结果。
4. 具备调用条件后调用对应工具，映射用户明示的方式、时间、偏好、途经点、车辆信息和沿途搜索条件。
5. 检查结果是否满足用户需求；有可用结果和真实引用时，Main Agent 在最终回答阶段调用 `present_cards`，展示是任务完成步骤，不能因已有文字答案而省略。
6. 展示失败不等于业务查询失败；按“失败处理”区分处理，并如实说明未完成的部分。

读取 Skill、发现工具、普通搜索或仅取得定位信息不等于完成路线、地点或公交查询。具备调用条件后，执行对应业务工具，不仅凭上述中间结果结束任务。缺少关键地点时仍先追问，不为提高调用率编造参数。

“哪个更近”等多起点或多终点比较，应分别查询各组明确地点的路线，依据真实结果比较；同一起终点只展示一张路线卡的限制不阻止展示不同起终点的比较结果。
### 成功结果的交付要求

| 业务结果 | 展示动作 |
| --- | --- |
| 纯定位成功且有真实引用 | 展示定位卡，并回答工具能确认的位置粒度 |
| 路线规划成功，结果符合需求且有真实引用 | 展示路线卡；普通问路不等于启动导航 |
| 位置查询/地点搜索获得可用 POI，且用户不要求串联这些点位的路线 | 继续 `map_mark`；成功获得真实引用后展示地点卡 |
| 公交地铁线路查询成功且有真实引用 | 展示线路卡；无引用时仅基于真实返回回答 |
| 启动导航成功且前一步路线卡可用 | 展示路线卡，按真实导航执行结果描述状态 |

Sub Agent 交回业务结果时一并交回对应的真实引用和顺序；Main Agent 完成展示。工具候选、返回引用或文字“已展示”都不能替代实际展示成功。
### 地点信息与个人地点

- 用户仅说“导航”“开始导航”“带我去”，且上下文也无法确定目的地时，先追问目的地，不调用地图工具。
- 上文已有明确地点或路线时可继续使用，不反复追问；用户本轮更正的信息优先。“这里”“那个站”“多久到”等指代先结合上下文解析，只有无法确定时才追问。
- “回家”“去公司”“去妈妈家”等个人地点指代：上下文已有对应具体地址则使用；没有则追问，不猜测真实地址，也不把未解析的个人标签直接当作具体地址。
- 用户补充的地址仅用于本次路线；本 Skill 不提供常用地址的保存、修改或删除能力。
- “医院”“学校”“地铁站”“商场”“机场”等泛类目，以及同名地点，属于已有目的地但待消歧，交 `route_plan_v2` 返回候选，不因名称宽泛直接追问。
- 地点字段忠实于用户表述，不擅自把上位地点具体化。例如“安徽工业职业技术学院”不能自行改成“天井湖校区”。
- 地点缺失需要追问；车牌、车辆类型等非地点约束缺失时，可说明本次未包含该约束后继续规划。
### 当前位置前置定位

起点、终点或途经点指向用户当前位置，且上下文没有可用当前位置时，先定位再规划。包括“从我这里”“途经我这里”“这附近”，以及“导航去 X”“带我去 X”“去 X 怎么走”等默认从当前位置出发的表达。

- 已明确提供起点的“从 A 到 B”不自动改用当前位置。
- “导航去医院”：缺少可用定位时先 `locate`，再由 `route_plan_v2` 匹配“医院”。
- “从鼎好去医院”：起点保留“鼎好”，终点“医院”交工具消歧。
- 附近、周边、离我最近等 POI 查询也适用定位前置；用户明确指定其他城市或区域时保留该搜索区域，不擅自替换为当前城市。
- 调用 `locate` 无需参数。仅查询或共享位置时展示定位卡；作为路线或 POI 搜索的前置步骤时可不单独展示定位卡。
### 纯定位交付

“我在哪”“我在哪条街”“共享我的位置”等是独立定位任务，使用 `locate`；不能只凭其他定位信息或搜索文字跳过定位卡交付。成功且有真实引用时展示定位卡；只有成功而无引用时，才仅依据工具返回简短回答。

用户问街道或更细地址时，只回答工具实际能确认的精度，不把坐标、城市或区县推断成街道。定位失败或用户拒绝授权时不伪造定位卡，不反复请求相同权限。

## 路线规划：route_plan_v2

本工具自带路线场景的地点匹配能力。路线、问路、距离、耗时和换乘查询在满足前置条件后直接使用本工具，不改走纯 POI 搜索流程。

### 多地点路线地图

- 用户要求把多个已选地点串成路线时，同组地点只交付一张完整路线图，不先调用 `map_mark(poi_ids)` 出点位图再补路线图；已取得点位图引用也不与该路线图一起展示。
- 将全部目标地点纳入 `origin`、`waypoints`、`destination`，保留用户指定顺序；未指定时说明采用的顺序，可采用默认顺序，起终点或关键顺序无法确定时先澄清。不能只选两个地点规划，把其余地点仅放在正文或点位图里。
- 出卡前核对实际路线结果覆盖全部目标地点。当前工具或出行方式不支持所需途经点，或返回路线遗漏地点时，说明限制并澄清可接受方案。

### 路线参数

`origin`、`destination` 分别表示起点和终点；`waypoints` 为途经点数组。地点对象按实际工具定义选择一种 `type`：

| `type` | 取值来源与约束 |
| --- | --- |
| `place` | `value.text` 填用户地点名称或已明确的具体地址 |
| `id` | `value.text` 填已获得的真实 POI ID，不编造 |
| `coordinate` | `value.longitude`、`value.latitude` 使用已有可靠位置数据，成对填写；不以 0,0 占位 |
| `current_location` | 仍须满足前置定位条件，其余字段按实际工具定义填写 |

只填写当前地点类型需要的字段，不把枚举列表写成一个字符串，也不同时堆入无关地点表示。

### 出行方式

| 用户表达 | `modes` |
| --- | --- |
| 驾车、开车、自驾 | `["driving"]` |
| 步行、走路 | `["walking"]` |
| 骑行、骑车 | `["cycling"]` |
| 公交、地铁、公共交通 | `["transit"]` |
| 明确要求火车、高铁、动车、飞机、大巴、轮渡路线 | `["transit"]` |

未指定方式时省略 `modes`，由工具按默认方式查询；不能仅因跨城市就强制公共交通。只有用户明确要求多方式对比时才传入多种方式，最终展示规则见“路线结果与消歧”。

### 时间、车辆和沿途需求

- `departure_time` 表示出发时间，`arrival_time` 表示到达时间；格式为 `YYYY-MM-DD HH:mm:ss`，例如用户明确提供的未来日期与时间。
- 两个时间字段互斥，每次最多填写一个，且为未来时间；“现在”“马上”通常省略。用户给出的两个时间要求无法由接口同时表达时，说明限制并澄清采用哪一个。
- `vehicle_context.vehicle_type`：`car` 小汽车、`truck` 卡车、`motorcycle` 摩托车、`bicycle` 自行车、`electric_bicycle` 电动自行车。
- `vehicle_context.plate_number` 取用户提供的车牌。查限行、货车或摩托车路线时尽量带上相关车辆信息。
- `waypoints` 保留用户要求的途经点；`search_by_route_query` 填沿途搜索关键词数组，如 `["加油站"]`、`["服务区"]`、`["充电站"]`。
- 可选字段无相关需求时省略，不把说明文字或所有合法值放进实际调用。

### 路线偏好

只填写用户要求且适用于所选方式的偏好。相互冲突的要求需澄清，不同时填入相反选项。

| 用户表达 | `preference` 数组中的值 |
| --- | --- |
| 最短距离 | `minimize_distance` |
| 最短时间、最快 | `minimize_time` |
| 避开高速 | `avoid_highway` |
| 优先高速 | `perfer_highway` |
| 避开拥堵 | `avoid_congestion` |
| 避收费、不走收费路段 | `avoid_tolls` |
| 避开隧道、不走隧道 | `avoid_tunnel` |
| 避开轮渡、不乘轮渡 | `avoid_ferry` |
| 最少红绿灯 | `minimize_traffic_lights` |
| 少换乘 | `minimize_transfers` |
| 少步行 | `minimize_walking` |
| 不坐地铁 | `avoid_subway` |
| 优先地铁 | `prefer_subway` |
| 跨城公共交通最早出发 | `intercity_departure_asc` |
| 跨城公共交通价格低 | `intercity_price_asc` |
| 跨城火车、高铁、动车优先 | `intercity_vehicle_railway` |
| 跨城飞机优先 | `intercity_vehicle_plane` |
| 跨城大巴、客车优先 | `intercity_vehicle_coach` |

`intercity_*` 仅用于跨城公共交通，不因普通路线中出现“便宜”“早点出发”就填写。车次、航班、票价和发到站均以工具返回为准。`perfer_highway` 沿用已有接口拼写，不自行改名；调用前以生效定义核对。

### 最小路线调用示例

用户：“从北京南站步行到陶然亭公园怎么走？”两个地点均已明确，不依赖用户当前位置。

```json
{"name":"route_plan_v2","parameters":{"origin":{"type":"place","value":{"text":"北京南站"}},"destination":{"type":"place","value":{"text":"陶然亭公园"}},"modes":["walking"]}}
```

### 路线结果与消歧

- 同一轮同一起终点最终只保留一个最推荐路线实体和一张路线卡，即使查询了多种方式；独立的多起终点比较任务可分别展示，多地点串联任务按“多地点路线地图”交付。
- 返回 `origin_alternatives` 或 `destination_alternatives` 时，选择最相关候选对应的真实路线结果，说明当前采用的地点，并简列其他候选供更正。
- 只有候选而无可用路线结果时，不根据候选自行编造路线或卡片；需要补查或用户选择后才能完成路线回答。
- 候选满足需求且有真实引用时，按交付要求展示，不因已经写出文字路线而省略；明显违反“不走高速”等明确约束时，不将其当作符合需求的路线展示。
- 发现漏传、误传用户约束时，修正入参后补查一次；参数已正确而结果仍不满足时，说明限制，不以无依据的文字路线冒充查询结果。
- 文本地点和路线结论与用户约束、工具入参及所展示卡片一致；不能口头更换候选却继续展示原候选路线。
- 有待消歧候选时，即使用户明确要求启动导航，也先展示可用路线与候选，不执行启动；用户确认后按明确地点规划并继续。

## 导航执行：navigate_command

只有本轮用户明确说“发起导航”“开始导航”“启动导航”“调起导航”“立即导航”“马上导航”“现在导航”，且起终点明确、无待消歧候选时，才启动导航。动作词可直接带目的地，如“立即导航到机场”。

“导航去/到/回 X”“带我去 X”“帮我导航去 X”“从 A 导航到 B”均属于普通问路，只规划路线并出卡，不执行启动。

- 启动前取得 `route_plan_v2` 返回的真实路线 `entity_id`，传 `command="start_navi"` 及 `start_navi_args.entity_id`。
- `start_navi_args.app_name` 仅在用户指定品牌时填写：高德 `amap`、百度 `baidu`、轻导航 `bytemap`；未指定则省略。
- 发起导航后的文本只说明终点，不暴露起点；同时展示前一步路线卡，不能只回复“已发起导航”。
- 是否启动成功以导航工具返回为准。导航失败但路线仍有效时可展示路线，并说明未能启动导航。
- 停止、结束、退出导航只传 `command="stop_navi"`，无需 `entity_id` 或路线规划；按工具结果确认状态。

## 地点搜索：local_search

### 搜索到出卡

1. 确认是纯位置查询，按核心流程获取必要的当前位置或明确搜索区域。
2. 调用 `local_search`；返回多个结果时，按用户关键词、城市和区域选择相关结果，不能确定时列出候选。
3. 提取所选结果真实 `poi_id`，调用 `map_mark`，`poi_ids` 顺序与文本介绍顺序一致。
4. 取得地图卡片引用后按“出卡协议”展示；无结果、全部不相关或缺少真实 POI ID 时，不编造点位或调用标记，按失败处理执行。

### 搜索字段

| 字段 | 使用规则 |
| --- | --- |
| `query` | 必填，保留地点名称或类目及已知城市、区域、地标；不编造所在地 |
| `min_price`、`max_price` | 用户要求的人均价格上下限，单位元；无要求则省略 |
| `min_distance`、`max_distance` | 用户要求的距离上下限，单位米；已有约定以用户当前位置为参考，无要求则省略 |
| `rank_type` | 已知值 `price`、`distance`，仅有对应排序需求时填写，否则省略 |
| `order` | 已知值 `asc`、`desc`，仅有明确排序方向时填写，否则省略 |

价格、距离使用独立字段，不把 `minprice/maxprice`、`mindistance/maxdistance` 等伪参数拼入 `query`。数值按接口声明类型传入，不填中文说明字符串。例如 3 公里对应 3000 米。

以下字段仅在实际定义及返回值足以确认约定时使用，不自行补默认值或推断接口行为：

- `location`：核对它表示搜索区域还是用户位置，以及与距离筛选的关系；定位结果中已明确的经纬度按匹配语义映射到 `location.longitude`、`location.latitude`，成对填写并核对坐标系。
- 指定城市与用户当前位置不是同一概念；保留用户搜索区域。省市区名称和代码仅取已明确来源，不编造代码或假定名称与代码的优先级。
- `pagination.search_id` 使用真实搜索返回值；首查是否需要分页对象、`offset` 的起点与含义、`limit` 的默认和上限、续查复用或重置条件均按接口约定。
- 评分排序的合法值尚未明确时，不猜填 `rating` 等值，也不把价格或距离排序声称为评分排序。
- 无法确认必要的位置映射或筛选语义时，说明该条件暂无法可靠应用；需要用户补充明确区域时再追问，不宣称相关筛选已生效。

## 地图标记：map_mark

| 模式 | 入参与职责 |
| --- | --- |
| 地点集合标记 | 本 Skill 传 `poi_ids`，值来自 `local_search` 的真实结果 |
| 旅行内容地图 | `map_data` 由 `doubao-trade-locallife` 的旅行地图流程构造 |

两种模式不能互换参数或完成条件。完整旅行图的按日编排、地点顺序与交付校验归旅行流程，不在地图 Skill 重建一套字段协议。涉及旅行任务时使用该 Skill 的旅行地图规则；交通卡不计作整体旅行图。

调用地点标记后，使用工具实际返回的卡片引用展示结果；POI ID 是标记输入，不是卡片引用。

## 公交地铁线路：transit_query

用于查询单条线路的名称、方向、首末班、票价、途经站，以及某个站点是否在线路上；两地之间的怎么走、多久或怎么换乘仍交路线规划。

- `target`必填，填写线路ID到 `target.id` 或者线路名称到 `target.query`。
- `target.query` 保留完整线路名及用户给出的城市、区域、地标，不把“北京地铁二号线”简化为“地铁二号线”。
- 用户提到站点时写入 `target.mentioned_stations`，只填站点名，不把线路名填入该数组；未提则省略。
- `target.id` 仅填已获得且与目标线路匹配的真实线路ID；`target.cur_station_id` 仅在需要当前站点上下文时填真实站点 ID。二者来自可信工具结果或已确认上下文，不由名称推算；缺少 ID 时保留 `query`，用户提到的站点名放 `mentioned_stations`。
- 成功且有卡片引用时展示；成功但没有卡片引用时，只基于返回结果简短回答，不编造线路信息或卡片。

### 线路查询示例

用户：“北京地铁13号线经过西直门吗？”无真实 ID 时按下例查询:
```json
{"name":"transit_query","parameters":{"target":{"query":"北京地铁13号线","mentioned_stations":["西直门"]}}}
```
若可信结果已给出目标线路 ID 和相关当前站点 ID，可在同一 `target` 中增加 `id`、`cur_station_id`（只填真实值）：
```json
{"name":"transit_query","parameters":{"target":{"id":"线路真实ID","cur_station_id":"当前站点真实ID"}}}
```

## 失败处理

- 信息缺失先追问，不能用联网搜索替代缺失的个人地址或当前位置。具备调用条件时先使用对应地图工具，不直接跳到 `general_search`。
- 工具不可见：通过宿主支持的发现机制按工具名称与用途查找；找不到时可用用途描述补充检索一次。不得猜测可调用名称、混用不同工具参数或循环检索；仍不可用时如实说明。发现 `present_cards` 失败不等于查询结果失效，可保留真实文字结果，但不能声称已出卡。
- 地图业务调用失败、异常或无可用结果，或用户拒绝定位授权导致无法继续时，才使用 `general_search` 提供有来源的补充信息；搜索结果不等于地图查询成功，也不产生地图卡引用。
- 定位失败、权限不可用或用户拒绝授权时，不输出定位卡，不生成依赖未知位置的路线或附近结果；可提示补充明确起点或搜索区域。
- 系统错误、连接器不可用、超时和限流要按实际返回识别；没有明确可重试提示时，不连续重复相同请求。存在重试约定时遵循其等待要求，最多补试一次；同轮已经重试的错误不另起重试循环。
- 展示被业务规则过滤或返回 `commerce_poi_filtered` 时，不自动重试、改卡型、改引用或换协议绕过。说明未能展示，并按工具允许的业务结果回答。
- 以业务错误码及 `isError` 判断业务是否成功，外层 `status=0` 不能覆盖内部失败。展示超时或限流不表示业务查询失败，也不表示卡片已展示。
- 没有真实引用、结果不满足用户约束或工具失败时，不为提高出卡率编造或强行展示；同轮其他已成功且符合需求的结果仍可分别展示。

## 最终交付检查

1. 是否执行了该场景对应的地图业务工具，而非只有 Read、工具发现、定位前置或普通搜索。
2. 地点、方式、时间和偏好是否按用户要求处理；多地点路线是否覆盖全部目标点，且未额外展示同组点位图；不满足的约束是否如实说明。
3. 有符合需求的可用结果和真实引用时，Main Agent 是否已调用 `present_cards`，并检查实际展示结果。
4. 若未出卡，是否有具体原因：必要信息缺失、工具不可用、业务失败、结果不适用、无引用或展示失败；不能仅因文字已回答就省略。
5. 是否只有导航执行工具明确成功时才说“已启动导航”；普通路线查询、候选卡及调用尝试都不构成启动成功。

## 回复与出卡协议

回复使用“简短结论 + 卡片 + 必要补充”的顺序；可以只展示卡片，不要求每组卡片前后都有文字。结果应与当前采用的地点、路线和工具返回一致。

面向地图业务用户的自然语言不暴露工具名、Skill 名、调用过程、参数、原始 JSON 或内部协议。询问依据时，用自然语言说明所用路线、地点或卡片信息；失败时如实说明未取得结果，不暗示已有卡片。

### 展示职责与顺序

- `present_cards` 只由 Main Agent 在最终回答阶段调用；任务规划、业务执行、结果收集及 Sub Agent 阶段不调用。
- Sub Agent 通过 Summary 按业务结果交回对应真实引用、分组和顺序，不把引用脱离结果单独汇总，也不构造或修改引用。
- 最终回答可交替输出文本和调用 `present_cards`。一次调用形成连续卡片组；组间需要文字时分次调用。
- 多次出卡顺序执行，等待本次返回并处理后再继续，不并行调用。已展示的文本和卡片不在末尾重复输出。

### 卡片引用与参数

`present_cards` 顶层仅传非空 `cards` 数组，每项包含：

| 字段 | 要求 |
| --- | --- |
| `cardType` | 固定为 `miniAppCard` |
| `referenceIds` | 非空字符串数组，原样复制平台实际返回的卡片引用，如 `reference_id` |

- 引用可来自当前轮、同会话历史结果或 Sub Agent 原样交回的结果；有效性由平台校验。
- 实际返回短引用或带前缀引用时均原样使用，不添加或删除前缀。同一数组不重复引用，也不把同一引用的两种格式当作不同引用。
- 不用业务 ID、实体 ID、POI ID、卡片实例 ID、页面会话 ID、工具调用 ID 或 System Reminder 外层 `ref_id` 替代卡片引用。
- `cards` 与 `referenceIds` 保留业务分组和顺序；`referenceIds` 直接放在对应项中，不嵌入 `items`。
- 同一轮、同一起终点，所有 cards 项合计只能包含一个最推荐路线的 `reference_id`。
- 不传顶层 `refs`、`options`，不添加 `app_key`、`card_template_id`、`render_data`、展示参数或用户/会话上下文。正文通过正常文本输出。

### 出卡参数示例

下面假定平台实际返回卡片引用 `a`；真实调用必须替换为已获得的原样引用，不能照抄占位值。

```json
{"cards":[{"cardType":"miniAppCard","referenceIds":["a"]}]}
```

通过工具调用提交，不把参数 JSON 当作回复正文。平台恢复卡片数据并展示，不手工构造渲染数据或输出 `RichMediaCard` 标签。一次调用的指令数、引用数与最终卡片数不必相等。

以本次 `present_cards` 返回判断成功；失败或 `isError=true` 时说明未能展示，不切换旧引用格式、inline 卡片或其他出卡协议兜底。业务查询成功时仍可基于真实结果给出简短文字。
