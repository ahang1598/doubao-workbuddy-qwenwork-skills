# Base 业务系统搭建

## 开工必读

模块写完立刻用 get 回读，再做下一个。

| 模块 | 回读必须满足 |
|---|---|
| 表／字段 | 已有实体用关联字段 `关联<表名>`，且不与表同名；保留单号、批次等编号；下游双向关联并生成反向字段，不把主档写成文本 |
| 公式 | 行内数、日期／金额决定的状态用公式；周统计建 `WEEKNUM([日期])`；跨表人数／次数建 `COUNTA([关联字段])`，有反向字段后把上游同义手填数改为公式；X 结果带到 Y 时建 `[关联X].[结果字段]`，不用文本。剩余、差额、是否逾期不得手填；不能只建“是否本周”而没有周次字段 |
| 人员 | 原话要通知、审批、处理的角色，在触发表或其关联表各有一个 `{"type":"user"}` 字段；原话约束涉及执行人（如同一执行人不撞时段）时，建执行人字段并逐条填值，按执行人校验，不按任务类别推断 |
| 样例 | 每张新表含 Form 底表、Workflow 下游表有 5～10 条；人员非空；状态、日期、措施一致，待处理有措施 |
| 视图 | 原话的时间、状态、分组、排序全部配置，不能只配最显眼的一项；看板按点名字段分组且与名称一致，不用默认字段；日历起止正确 |
| Dashboard | 组件筛选、分组、聚合、排序符合原话；比率用公式，金额不用计数，排名降序；最后调 `+dashboard-layout`，布局不空 |
| Workflow | 触发有业务条件；审批、状态写回、生成记录有写动作；接收人取职责字段，不取当前用户／固定人；不得只提醒 |
| Form | 复用字段，不重建同名字段；区间不重叠；截止时间、名额用提交设置而非说明；他人填写时开分享 |
| 权限 | 只建原话角色、只授权点名表且不扩大编辑；不建兜底角色；“只看自己／本组”先建人员字段，再用记录筛选限定 |

收尾时删掉平台默认创建且没用到的空表和验证时写的测试记录。

## 任务导航

- 本轮产生新 Base（创建、复制、模板、导入）都先读本页，即使已点明表名和字段；类别下限和保真例外按 [Base 类别验收](base.md#模块验收项)。
- 已有 Base 的多模块搭建由本页编排；目的模糊或要完整可用系统时，按下方模块选择补齐。
- 已有 Base 的明确单模块改动直接进对应 Scene，不扩展其他表、仪表盘或自动化；连续操作仍执行[阶段验收](#连续操作的阶段验收)。
- 只分析已有数据交 Analyze-data；系统和分析混合时登记全部子目标，分别完成后组合验收。

## 交付目标与前置检查

写第一条命令前，从原话登记每个交付对象的数量、位置、用途、依赖和通过条件，分析、出图、复制也登记。保留点名的字段、视图类型、图表及数量。复制完旧表不等于系统搭建完成。不临时补未登记的持久产物。

| 情形 | 动作与边界 |
|---|---|
| 新 Base | 按 [类别规则及保真例外](base.md#模块验收项) 计算类别并补缺；入口写入清单，不能只计划字段和记录，也不能留成建议 |
| 复制／导入 | 固定对象层级、记录范围、保真；空表、数量 0、指定数量、样例交 Table／Mock 判定，不得因丰富度改写 |
| “记账／台账／清单／库／系统”且无明细 | 建长期结构、样例，不逐笔追问；仅某笔真实数据不足时追问 |
| 分组／排序／排名／汇总／“最后这样看” | 持续看原始记录交 View，持久聚合交 Dashboard，一次总结交消息／Analyze-data；仅明确保存／沉淀／维护时建持久物；查询／会话表格不能替代 |
| 未来／定时／事件触发提醒、通知、执行、联动 | 交 Workflow；当前一次通知交消息；图表／看板交 Dashboard；接收人／外发须授权，周期任务不得改成 Base 外 scheduled job |
| 工具不能闭环 | 报告受阻，再用允许的等价方案或跨模块降级；不把会话图表或外部定时任务冒充 Base 交付物 |

### 写前阶段门禁

原话命中阶段写入同一清单，绑定验收、依赖并推进：

| 阶段 | 登记内容 |
|---|---|
| 新 Base | 类别目标；普通新建至少三类；范围／保真例外按 Base |
| 新业务表 | 每表数据来源、数量、分布交 Mock；后建收集／下游表沿用 |
| 自动化 | 触发器、条件、动作、接收人、目标运行态；周期任务／提醒／汇总不得转成 Base 外任务 |
| Form | 题目、属性、分享范围、真实提交／未验证原因 |
| Dashboard | 每指标来源、范围、粒度、结果、布局回读；新建／追加组件都布局收尾 |
| 权限 | 允许／排除主体、资源、能力、各角色证据 |
| 派生字段 | 结果实体、来源、全部匹配条件、输出类型；批量初始字段同样适用 |

### 阶段写入顺序

| 数据来源 | 顺序 |
|---|---|
| 普通业务表 | 结构／真实 ID → Mock → 数量、业务值、关系回读 |
| Form 收集表 | 系统字段 → 题目／业务字段 → 适用真实提交 → 补 Mock → 记录／关系回读；边界归 Form |
| Workflow 下游表 | 结构／流程 → 有授权则实测、核产出、补样例；无授权则备 Mock，运行仍未验证 |

每项写后立即回读。结构已 `verified`、记录数仍 `pending` 时，可以进入产生这些记录的 Form 或 Workflow 步骤；未验证的数量、关联、业务结果不能当作事实。Formula／Lookup、展示、权限按前置就绪推进，不固定排在最后。

失败项只定向修复一次，仍失败标 `blocked`，继续不依赖它的工作。创建验收未过不进入后续修改、删除；启用 Workflow 须先预检。最终必需项都须 `verified`；Mock 不能当真实提交或自动化执行的证据。

## 业务建模与模块选择

### 新建 Base 前的 1:N 建模

先写清每张表“一条记录代表什么、用什么身份区分”，再区分录入事实、持续派生值和执行结果。稳定收集项不塞进备注；多人排期要有执行人字段，任务名称不能代替执行人。

用户要求逐项拍照、填结果或留痕时，建“本次记录 → 明细 → 检查项”的一对多关系，在明细上放该项的结果、附件、处理状态和责任人，不能只在总记录上放一个汇总附件或备注。建不了时标记该证据未完成，不用汇总字段代替。

以下任一条件成立时，用主表加流水／历史表，否则保持单表：

1. 同一对象被多条交易、借还、办理、检查或状态变更重复引用。
2. 主档更新不应改写历史，或每次事件需要独立的时间、状态、经办人。
3. 多条记录复用同一对象身份，且要从对象反查全部历史。

不因字段多、叫“台账／档案库”或将来可能扩展就拆表；两个概念始终一一对应、无独立字段或生命周期时不拆。一次事件对应多个主档时保留真实关系。

### 系统能力与丰富度

需求模糊或要完整可用系统时，默认配置能反映关键结论的 Dashboard（如总量指标卡、分类占比、趋势或待办分布，组件构成见 [Dashboard 默认组件构成](dashboard.md#默认组件构成)）。Workflow 只在有提醒、自动化或联动诉求时配置，不因有日期字段就新增。对外发送和多角色权限只按明确要求做，不为凑类别启用自动化、权限或分享。

只扩充当前 CLI 能创建、配置并回读的能力；无法等价完成时报告边界，不建占位字段、空对象或半成品。

### 展示入口选择

用户点名的入口原样交付：要求 grid 分组视图就保留它，补 kanban 不能替代。两个日期不一定是工期，创建时间不代表日程。

| 依据 | 入口 | 验收 |
|---|---|---|
| 状态／阶段／分类单选 | kanban | View 显式分组并回读 |
| 语义明确的开始／结束日期 | gantt／calendar | View 绑定正确起止字段并回读 |
| 图片／附件 | gallery | View 核对实际展示 |
| 指标／分组／趋势 | Dashboard | 配组件并核对配置 |
| 明确收集需求 | Form | 配题目、适用分享、提交验收 |

补类别时：先接收 [Base 的实际类别与缺口](base.md#新-base-的交付类别)，按上表选能复用业务字段的入口（优先非表格视图和仪表盘，确有收集需求才用表单），把入口和验收方式追加到清单，由对应 Scene 创建并返回证据；不能只加同类入口或留作建议。

补齐时优先用已有状态、评级字段建分组 Kanban，有阈值字段时建总览或低于阈值的 Dashboard。保持边界：不新增记录，不改指定比例；沿用已有行级权限和流程，不公开跨人员汇总，不扩大普通成员的编辑或可见范围，不新增外发通知。

字段不足时只补业务本就需要的分类、状态、日期；不造无关日期或照片，不改字段语义、数据目标和权限。都不适用时报告缺少的类别及原因，不把不足三类说成完整搭建。

无图表的仪表盘、未绑定分组的 kanban、未绑定日期的 calendar、无题目的表单都不算入口。补齐的对象须完成配置和验收，返回真实 ID、类型及证据；只创建不算补齐。

### 示例数据（mock）

本轮新建的每张业务表（含收集、登记、事件和 Workflow 下游表）默认不少于 5 条、一般 5～10 条；原话明确要空表、指定数量或保留来源时按原话。下游表条数受上游状态限制时，调整上游样例分布，使每张表都达标。

完整分页计数：NDJSON 累计 `records_count`，JSON 累计 `len(data.data)`；账本记 `record_count`，最终逐表报。验算或演示临时写的 2～4 条不算达标；表单提交和流程触发产生的记录计入总数，只补差额。验收标准见 [Mock](mock-data.md#执行与验收要求)。

## 跨模块执行与阶段验收

按实际依赖推进，下列顺序不是固定脚本：

1. Table、Field 建表、字段和关系。1:N 先建主表再建流水表，多端关联主档并开双向关联，反向字段名业务可读；参数见 [关联字段协议](../references/field-config.md#link-字段)。
2. Record、Mock 先写主档并保存真实 ID，再写流水；不猜 ID，不用重复文本代替关系。抽查多端指向预期主档、主档反向包含全部流水，才算关系完成。
3. Form 收集表按 Form 执行；Workflow 下游样例和实际执行交 Workflow，样例不冒充执行证据。实际触发测试须有用户实测要求和资源、接收人、动作范围授权。每拿到新 `table_id` 就更新 [Table 新表清单](table.md#数据与展示目标)，按实际创建的表验收。
4. Formula／Lookup 在源字段和代表性数据就绪后验证结果；缺少代表性输入时标出未验证分支。
5. View、Dashboard、Form、Workflow、Permission 分别完成被触发的操作和验收；每条 Workflow 都要预检并回读目标运行态，不能只看创建成功。
6. 独立分析交 Analyze-data；对象辅助计算由原 Scene 调 Query。

### 连续操作的阶段验收

同一请求既创建、又查询、修改或删除表单或视图时执行本节；单模块任务同样执行，但不触发丰富度扩展。按 `创建中 -> 创建已验证 -> 后续操作 -> 最终已验证` 推进。

新建底表的数据准备与回读是不可取消的创建检查点，不因后续会删除入口而省略；数据目标遵守 [Mock](mock-data.md#数据来源与数量)。既有表禁止测试写入。

1. 按 Form、View 各自流程完成表和入口的初始结构及适用分享。
2. 按 Mock 数量准备数据：表单立即执行适用的[真实提交和其余样例写入](form.md#新底表样例与真实提交验收)，附件按[表单样例准备](form.md#表单样例准备)；普通写入交 Record。
3. 用 `+record-list` 回读数量和业务不变量。结构、分享或提交、Mock 检查都通过才标“创建已验证”，否则不做后续操作。明确空表或数量 0 时确认仍为空，并注明真实提交未实测。
4. 删除表单、视图或题目时只处理原话指定的对象，不顺带删数据表、字段或 Mock 记录；按 [Form 底层字段保护](form.md#移除题目与底层字段保护)和 [View 删除流程](view.md#删除视图)执行并验收。
5. 全部步骤后再读最终保留的数据表，标“最终已验证”。除非原话要求清空或保持空表，记录数仍须达到明确或默认数量，为空不得交付。逐表证据交 [Table](table.md#逐表数据证据)。

Form 必须真实提交但分享未授权或不可用时：准备可完成的样例，报告提交未验证；创建阶段仍为受阻，不标 `verified`，不进入后续操作，也不自行开启或扩大分享。

## 组合验收

必需项全为 `verified` 才交完整系统。

| 检查 | 通过条件 |
|---|---|
| 对象、数量、位置 | 逐项对应清单，位于指定的 Base、表或看板；配置正确不能抵消位置错误 |
| 表、字段、关系、数据 | 逐表证据、字段和记录回读、Mock 质量通过；1:N 双向可追溯 |
| 计算字段 | 定义与实际结果通过，未覆盖分支已标出 |
| 展示与收集入口 | View 配置、Dashboard 组件结果、Form 分享与提交分别通过；名称或空壳不算完成 |
| 自动化与权限 | 每个 Workflow 的目标运行态、每个角色的数据与字段权限都有回读；测试运行与静态配置证据分开 |
| 新 Base 类别 | 按 [Base 类别验收](base.md#模块验收项) 对已验证对象的实际类型去重；多张表、重复视图、已删对象不抵扣缺失类别 |
| 跨模块指标 | 按 [一致性规则](../references/shared-statistics-rules.md#查询产物与回答一致性) 比较同一来源、范围、粒度与指标；不以原始顺序冒充排名 |

## 恢复与交付

失败项交所属 Scene 恢复，只修该项及受影响依赖，复用已验证结果。写入结果未知时先读状态，不重复创建；不靠删条件、换字段、跳过模块或事后删除掩盖失败。

最终答复汇总各 Scene 的验收结果，不照抄创建响应：

- Base 链接和各模块位置。
- 每张新表的 `record_count` 及是否达标；注明是样例并报告关联和业务一致性。
- 每个视图的 `type` 和已回读的分组、筛选；仪表盘的组件配置核对。
- 每条 Workflow 的目标状态（含原话要求的 `disabled`）；未触发不称已送达，不为凑证据擅自启用。
- 表单、权限的证据和 Base 类别计数。
- 未完成、未验证项和例外，写明原因与影响。待建项不能写成建议后宣称完成；单个看板有数或某条自动化启用不能代替组合验收。
