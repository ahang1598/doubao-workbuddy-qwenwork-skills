# Base SQL 分析 SOP

用户独立提出的分析问答统一走 `Context -> 固定分析口径 -> SQL -> 完整性与语义核验 -> 回答对账`，包括简单单表计数、求和、平均、分组、聚合 TopN，以及占比、趋势、多表关联和多阶段统计。不按数据量或复杂度切回 `+data-query` / 本地计算；下述数值精度复算是明确例外；第 3 节对已返回结果的确定性核验不属于原始取数或主分析回退。

普通表/字段读取、原始记录筛选和排序、已知记录定位继续用 `+table-*` / `+field-*` / `+record-*`，不额外加载本 SOP。图表搭建、Formula/Lookup、辅助汇总表及写后验收按原对象 reference 执行，所需 `+data-query` 或程序化计算不受本 SOP 的 SQL 回退门槛限制。解读已有图表仍使用 `+dashboard-block-get` / `+dashboard-block-get-data` 的实际配置和计算结果。

本 SOP 维护分析决策与验收；命令 reference 按下列阶段加载。同一任务中已读过且命令契约未变时复用，不要求每次调用重读，也不在入口一次性预加载全部参考。

## 1. 获取 Context，选择数据源

先按主 Skill 解析出可信 `base_token`，用 `+table-list` 列出表并选出本题相关的表（含关联表）。首次获取或解读 Context 前，读取 [Context 命令 reference](lark-base-schema-context-get.md)，按其中的参数、DDL 解读及结构截断规则，只传这些表的 `--table-id` 取得或复用有效 Context，再选择真实数据源和字段。

将每个需要交付的业务字段绑定到 Context 中的具体表和字段；多个字段的名称或取值相近时，依据字段定义选择来源，不能按样例值猜。Context 缺少必需字段或结构被截断时，按 Context reference 定向补查结构；不能用相邻或近义字段代替。

## 2. 固定口径，再生成 SQL

首次生成 SQL 前，读取 [SQL 命令 reference](lark-base-data-sql-query.md)，先确认支持的语法、函数、字段类型和返回契约，再据此写查询；不要等 SQL 写完才加载方言限制。

根据用户问题和 Context，在内部记下本题相关的分析口径：指标及来源字段、结果粒度、业务日期与时间范围、筛选条件、连接键，以及适用的分母/权重。注明各项来自用户要求、可信业务定义还是显式假设；简单问题只记相关项，已有明确依据不重复追问。主查询、后续核验与最终回答复用同一口径，再生成 SQL：

- 计数区分记录数、非空字段数和业务主体去重数；平均、比率明确分母与权重。同题不同指标分别按各自定义确定总体；组内发生率以该组符合定义的完整主体为分母，不因另一指标只覆盖部分主体就缩小，贡献占比等指标则按题定总体作分母。`sum(分子) / sum(分母)` 与逐项比率的等权平均不是同一口径；存在会改变结论的歧义时先澄清，合理且语义明确的敏感性对照可另列。
- 多表关联逐个指标确认原始事实粒度、唯一业务键及连接两侧的基数，不能只检查主指标。优先使用元数据明确的关联记录 ID 或已验证的业务键，确认两侧属于同一标识体系，不能仅凭字段名含 ID 或编号就连接。仅有名称可用时，核验相关范围内每个名称唯一对应一个目标实体，并检查未匹配记录和关联放大；事实侧同名的多条记录可以属于同一实体，不要求两侧名称列都唯一。复用已证实的键约束；证据不足时定向检查重复键及关联前后各指标的数量/金额对账。无法唯一定位时，补取字段元数据或关联键以消歧，仍无法确认则说明限制，不直接按名称合并不同实体。不同粒度的事实分别聚合到可连接的共同粒度，或按明确归属/分摊规则连接；不能把较粗粒度事实的金额随明细行重复求和，也不能用 `SUM(DISTINCT 金额)` 代替按事实键去重。最终展示真实业务值，必要时附业务编号消歧。
- 按业务实体统计时，用 Context 中已确认的实体键确定 `GROUP BY`、去重和窗口分区粒度，名称作为展示属性；只有问题明确按名称或类别统计时才按该维度合并。JOIN 未放大行数，不代表后续按名称分组不会合并不同实体；记录键与实体键不能混用。
- 实体排名先按已确认实体键聚合，再排序取 TopN，不能先合并同名实体再补编号；名称、编号及指标须对应同一实体。名称加评级、地区等属性也不能默认唯一，无可信实体键时先核实。
- 将业务目标映射为可证明的字段条件。对候选状态区分 `Include / Exclude / Unknown`；局部、阶段状态不能证明最终业务状态。无法判断的值先澄清或明确分组展示，不能静默排除。Context 样例不足以证明没有其他状态。
- 用户指定 View 时，先读取并确认其过滤和范围，再在 SQL 中等价表达；无法等价表达时说明限制，不能把全表结果当作该 View 的答案。
- 保持主口径：换指标字段、业务日期、时间/筛选范围、统计粒度或分母/权重，都属于口径变更。不因覆盖不齐、异常值或结果不符合预期就改主答案；补充对照单列并说明差异，例如周期总量与单位时间均量不能互相替代。可信业务定义可纠正模型自行推断的映射；若与用户明确的公式或范围冲突，说明冲突并请求确认，确认前不覆盖主口径。精度补查、语法修正与执行回退沿用同一统计总体。
- 以 Base 已记录数据作为事实依据：除用户明确要求估算或已确认的业务定义规定估算外，不自行插补、外推、年化或构造未记录的数据，再用它替代实际值计算总额、变化、排名、阈值等结论。遇到空缺、稀疏或异常分布，说明可核实的范围和限制；不能仅凭这些现象断言数据的生成方式、缺失原因或未观测值。
- 同一请求兼有事实分析和预测时，先按实际记录回答事实部分，只对用户指定的目标做预测；明确预测模型、假设及不确定性，估算值与实际值分列，不用估算结果改写已观测数据的比较结论。当前指标支持的相对风险排序，不等于未来事件的概率或必然性；缺少可核验的预测依据时不使用确定性语气。
- 每次调用只执行一条只读 `SELECT` 或 `WITH ... SELECT`。优先显式选择业务所需列，核对每个 SELECT 表达式是否来自已选定的源字段；别名只标记结果列，不能把另一源字段改名后冒充目标字段。`SELECT *` 仅用于确需全部可见字段的探索。过滤、聚合、去重、排序和派生数值尽量在 SQL 中完成；涉及下述精度限制时，改用原始记录本地复算相关数值。
- 一条主查询优先，必要时少量补查：口径、结构和关联关系明确后，优先用一条 SQL 完成主分析；同范围、兼容粒度的指标、派生计算和必要核验尽量合并或复用结果。仅在主分析所需结果或关键证据尚不完整、核验失败或执行受限时追加查询。不硬限查询次数，不为减少调用牺牲正确性，也不强行拼成难核验或低效的 SQL；优化目标是正确性前提下的端到端效率。

例如“销售额最高的 10 个客户”：先从 Context 确认客户、订单、关联键与销售额字段；明确销售额指应收还是实收、时间范围及退款口径；按客户粒度聚合全部符合条件的订单，再排序取 TopN。若问题只是“金额最大的 10 条订单”，直接走普通记录排序，无需 Context/SQL。

### 数值精度与本地复算

**原理**：二进制浮点无法精确表示许多十进制小数，数值在表示和运算时会产生近似误差；累加、除法等聚合运算会传播误差，计算顺序也可能影响末位。即使每条金额显示两位小数，均值仍可能恰好落在十进制舍入边界，例如精确均值 `43.135` 若被算成略小于该值，保留两位就可能由 `43.14` 变为 `43.13`。这不只是展示出多余小数，而可能改变最终金额或阈值判断。SQL 当前未提供精确十进制类型；从原始十进制值开始用 Decimal 或已确认单位的整数复算，才能避免引入同类二进制浮点误差。

- 普通求和、均值、比率和 TopN 继续按云端查询主路径执行；“金额展示两位小数”本身不触发原始记录全量读取，也不代表承诺精确十进制结果。仅在用户或已确认的业务规则要求精确十进制计算、指定十进制舍入规则或精确对账，或已有具体证据表明精度误差可能改变要求交付的数值、阈值判断或排名时，主动复算相关指标，无需等待查询报错。证据不足的疑点先用已有结果或必要的定向补查核实，不因指标是金额或涉及排名就假定需要全量复算。
- 当前 SQL 下游尚未实现精确十进制 `DECIMAL` / `NUMERIC` 类型，数值字段以 `DOUBLE PRECISION` 参与计算；`SUM` / `AVG`、派生运算及舍入边界可能出现浮点误差。`ok=true` 或 `truncated=false` 只证明执行/返回状态，不证明满足上述精度要求。
- `ROUND` 只对已有计算值舍入，不能恢复之前丢失的精度。当前不能依赖 `CAST(... AS NUMERIC/DECIMAL)` 获得精确十进制语义，也不要对已失真的聚合结果转 Decimal、加 epsilon 或调整容差来掩盖差异。
- 复算从原始数值输入开始：JSON 数字直接按十进制解析（例如 Python `json.loads(raw, parse_float=Decimal)`），或从原始十进制文本构造 Decimal，不能先解析成 float 再转换。也可在业务单位和小数位已确认时使用整数最小单位；字段显示两位小数不证明原值只有两位。Decimal 运算须设置足够的计算精度，最终按业务要求显式舍入；要求十进制四舍五入时用 `ROUND_HALF_UP`，不要依赖语言默认舍入。
- 只投影复算必需的业务键、分组/关联键和数值字段，分页覆盖原问题的完整范围，核验分页结束、唯一记录键和记录数，并复用已完整读取的数据。不能把去重后的维度行或 SQL 浮点聚合值当原始记录；若浮点计算参与候选筛选、排名或阈值判断，不能只复算已入选行，须覆盖可能改变入选结果的完整候选范围。
- 保持用户指定的指标、来源字段、空值规则、分母/权重和业务范围。用户要求统计已有公式字段时，读取该字段的原始值复算统计量，不擅自重算公式、替换业务指标。原始返回已丢失精度、完整数据无法取得或用户限定 SQL-only 时，说明精度限制，不声称本地计算能还原丢失的信息；权限拒绝仍按第 4 节停止，不能换工具绕过。
- 回答使用复算后的结果，必要时说明与云端值的差异；保留输入、公式、记录覆盖和舍入规则供复核。例如精确十进制均值 `43.135` 保留两位并四舍五入应为 `43.14`，浮点聚合后再 `ROUND` 不能保证得到该结果。

## 3. 执行、核验与回答

按已读 SQL 命令 reference 执行，依其返回、截断和错误契约检查结果完整性，再逐项核对数据源、范围、粒度、连接与指标是否符合主口径。接口成功或未截断不等于业务正确，失败或缺失不能当作 0；未确认完整性时不输出确定全局结论。执行错误进入第 4 节；数值精度问题按上节主动复算，不自行扩大重试。

补充查询与停止条件：

- 每次补查先明确它要验证的疑点，以及结果会改变哪个主结论或必要限制；优先复用已有结果、合并同范围的检查，不重复拉 Context 或扫描无关数据。覆盖率、最大日期、空值等结论必须带上查询的表和过滤条件；过滤后的局部结果不能推出全表缺失。
- 主结果和必要核验完成、没有新的可检验疑点时停止。覆盖缺口可以作为限制或补充对照的依据，不能直接推断停业、需求下降等业务成因；区分数据事实、模型假设与未知原因，不为解释异常无限扩展查询。

回答前检查（只核对准备交付的数字和结论，优先复用已有结果；仅在必答项证据缺失或存在具体矛盾时补查，不固定增加查询或完整重算）：

- 从答案列反查 SQL 结果列、SELECT 表达式及 Context 源字段，确认值与列名指向同一业务字段；只核对结果列名、列位置或数值合理性不足以证明来源正确。回退到 `+record-list` 时，按主 Skill 的字段 ID / 字段名映射读取行数组，不按位置推断含义；预算与实际、当前与基期、分子与分母等角色在计算、表格和文字中保持一致。每个计数、占比、排名附带数值和解释性数字都须有已核验依据；差额、比例、分布计数等派生数值优先复用 SQL 结果；已有结果完整覆盖所需范围和粒度时，允许对该结果用程序确定性计算、排序和核验，保留输入与公式，不在组织答案时重新心算。此核验不触发原始记录全量读取，也不能恢复已有聚合值丢失的精度。非用户要求的补充统计或解释，已有充分证据才输出，否则省略。

- 粒度核验与总额对账分开：确认每个分组对应预期实体键，未把不同键合并或把同一实体意外拆组。总额守恒、关联行数正确不能证明分组和 TopN 正确；合并同名实体仍可能保留总额却改变排名。优先检查现有查询的分组/分区键，证据不足时再定向补查，不为此固定增加全表扫描。
- 汇总前判断可加性：业务主体去重数、比率、加权均值需在目标粒度重新计算，不能直接相加或平均；预测须说明模型、计算顺序及不确定性。“先按组预测再求和”与“先汇总再预测”可能不同，不能将后者冒称前者的合计。
- 先验证断言，再据此组织结论：对准备交付的比较、排序、数量关系或趋势判断，明确同一口径下的数据范围、指标、左侧值、关系和右侧值；用已完整返回的结果确定性计算并判定，而非从相似指标的排名、局部样本或舍入后的展示值推断。只将成立的断言写入正文；证据不足的必答项定向补查或说明限制，非必答的延伸判断省略。按未舍入值判断排名与并列，精度证据不足时不强行判定。
- 总数、已完成数、未完成数等状态计数分别绑定结果，不能在文字中互换。仅在状态集合互斥且覆盖总体时用总数减已完成数得到未完成数，否则按明确状态条件计数，不能把未知状态自动归入未完成。
- 表格、图表和正文复用已验证的断言及其证据；交付前检查措辞没有扩大比较范围、改变方向或把推断写成事实。比较范围或补充口径在文字中明确标注；发现矛盾时按已验证结果修正，不能保留与表格相悖的总结。
- 核对单位、展示精度、总分关系和派生公式；仅对可加指标核对分项之和，舍入差异明确说明。展示值因舍入相同，不证明原值完全相等；“完全相同”等确定性结论须有对应精度的证据。
- 说明查询范围、关键口径与必要限制，保留实际 SQL 和结果供复核；如使用回退，明确结果来自回退而不是 SQL 成功。
- 分析结果不等于记录定位。需要完整记录、`record_id` 或后续写入时，按真实业务 key 用 `+record-list` / `+record-get` 精确回查；查询本身不授权写入。
- 混合任务中，另行要求的分析结论按本 SOP 执行；Dashboard、View、汇总表或 Formula 的配置、辅助计算与回读按原对象流程，不把 SQL 路由扩展到搭建步骤。共享指标的分析结果、持久产物与最终回答须使用相同范围和口径；纯分析不自行创建持久对象。

字段来源示例：Context 显示 `t."对象姓名"` 和 `t."联系人"`，用户要对象姓名时，查询应取 `t."对象姓名" AS "姓名"`；`t."联系人" AS "姓名"` 即使别名和返回值看起来都像姓名，来源仍然错。若改用 `+record-list`，同次响应的 `data.fields=["联系人","对象姓名"]`、`data.field_id_list=["f1","f2"]`、`data.data=[["甲","乙"]]`，且结构中已确认“对象姓名”的 ID 为 `f2`，则按 `f2 -> 第 2 列` 取“乙”；不能按外观取“甲”。

## 4. 有界修正与按需回退

SQL 能力以 [SQL 命令 reference](lark-base-data-sql-query.md) 的语法契约和服务端返回的 `error_msg` 为准，不判断底层版本。

1. 权限或身份被明确拒绝时，停止并说明授权问题，不换身份或改工具绕过；口径歧义先澄清，不靠换查询工具消除；用户要求 SQL-only 时遵守该限制，失败就报告，不回退。
2. 有明确字段、语法、算子或完整性错误时，依据 Context 和错误信息做一次定向修正；可识别的暂时性服务错误可重试一次。保持业务口径，不循环盲试，也不在没有证据时改写条件。
3. 确认 shortcut 不存在或接口不可用，或上述修正/重试后仍失败，且不属于第 1 项时，先向用户说明原因，再进入受控回退。执行失败回退时读取保留的 [旧查询与分析 SOP](lark-base-data-analysis-sop.md)，按需再读 data-query guide / DSL；正常 SQL 分析不预加载这些文档。回退期间只采用旧文档的旧工具执行、分页和核验规则，不再执行其中按复杂度返回 SQL 的选路；本节的权限、口径与 SQL-only 边界始终适用。
4. 回退可使用 `+data-query` 的云端过滤、计数和普通数值聚合；满足上节精度复算条件时，才以最小字段投影分页读取原始记录并复算。该精度例外不受第 2、3 项的报错/重试前置条件限制，无需先尝试 `+data-query` 数值聚合。必须证明原问题范围读取完整，保留同一身份、数据范围、分母和业务口径。范围无法确认、回退仍失败或被拒绝时报告限制，不给出确定全局答案。
