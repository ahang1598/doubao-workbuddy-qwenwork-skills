# 新建页面

**按原意实现用户的每一项要求，严格遵循所选设计规范。** 每个模块作用明确，展示的业务数据真实。

## 工作流程

按顺序完成三个阶段，不跳步。

### 阶段 1：整理并展示需求说明

按下面的结构整理用户需求，并向用户展示需求说明。展示后直接进入阶段 2 的准备工作，无需用户确认。后续设计、实现和审查都以这份说明为依据。

```text
页面概述：什么页面、给谁用、核心目的
约束与品味：用户对风格、调性、配色、文案的要求；没有就写“无特殊要求”
功能模块：
- 按页面从上到下的顺序列出，每个模块写清展示什么、用到哪些字段、支持哪些交互
数据说明（可选）：字段间的业务关系、用户对字段的特殊要求；不逐个复述字段名和类型
```

- **完整落实用户明确提出的内容、数量、文案、交互和数据要求。** 需求说明要逐项写清展示内容、所用数据、操作入口和结果。用户指定的模块和顺序保持不变。
- **需求简短时，结合页面用途、目标用户和真实数据补充必要的内容与功能。** 模块选择和信息重点服务于页面的核心目的，补充的内容只使用真实数据和平台支持的能力；单条新增仅在用户明确要求时提供。
- **仪表盘转换按来源保真。** 按 [仪表盘指引](webpage-dashboard.md) 整理来源已有的组件与口径，不用上述补充规则新增来源没有的组件。
- 不写 CSS、动画、布局等技术细节；文案有明确要求就写，没有则在实现时从数据中提炼。
- 用户已给出结构化需求时，直接沿用，只补缺失部分。

### 阶段 2：准备

1. **选择设计并准备工程。** 用 `+webpage-design-list` 获取设计系统列表，阅读各系统的 `description`，结合用户需求选择最匹配的一种；用户明确指定风格时，优先匹配该风格。
   - 空页面：按下方「初始化」准备工程。
   - 整页重做：沿用已 pull 的工程，按修改指引的 [切换设计](webpage-modify.md#切换设计) 安装所选设计，更新本地规范；不执行 init。
2. **核实字段（编码前必做）。** 代码里用到的选项、阶段、关联和格式等字段细节必须逐字来自已有上下文或 `+field-get`，不编造、不按字段名推测。以下信息缺失时先查询，多个字段并行查，**查齐前不进入下一步**：
   - 单选、多选、阶段：选项名称与选项 ID，不猜测选项值；
   - 单向 / 双向关联：目标表与目标字段；
   - 公式、查找引用：表达式与结果类型，不根据字段名推测计算内容；
   - 数字、货币、进度：显示格式（百分比、千分位等）。
   - 其他字段：本次实现需要的详细配置。
3. **主题落地（页面组件编码前完成）。** 先读取 `src/index.css`，按设计规范定制其中 `:root, .dark` 块的主题变量，包括颜色、圆角、间距等。`src/theme.css` 把它们注册为 Tailwind token（不可修改）。
   - 按语义把规范中的颜色、圆角、字体等写入对应变量。变量名与值格式以工程为准，不要求与规范写法一致；组件只引用工程中已定义的变量。
   - 只改已有变量的值。规范中面向其他工程结构的写法（如另建样式文件、注册主题 token）不照搬；没有对应变量的设计值在组件中统一实现。
4. **确定设计方向。** 按设计规范和需求说明决定配色与字体层级、布局结构、首屏内容和模块顺序。规范要求先作风格决策时照做，决策只在内部使用。再为每个列表、指标、筛选和控件定好数据来源、查询或聚合方式、是否分页，以及用户操作后的结果；有未决项就回到第 2 步补齐。
5. **重命名默认页面。** 用户先建好页面再来生成时，页面通常还是“页面”“页面 1”这类默认名称。此时用 `+base-block-rename` 改成概括页面内容的简短名称；用户指定过或已有意义的名称保持不变。改名失败（如重名）不阻塞生成。

### 阶段 3：实现与审查

1. **逐项实现模块和交互**：结构 → 内容与交互 → 接入数据 → 样式 → 动效。每个模块只承担一个任务、只有一个主视觉、只传达一个核心信息。
2. **按下方「交付前审查」对照实际代码逐项检查**，发现的问题一次修完。缺失的要求要补齐并接上真实数据，不通过删减需求来过审查。
3. 按入口的「提交与版本描述」提交并确认结果。

代码保持精简，不写重复逻辑和无用代码。

## 初始化

`+webpage-init` 先写入工程源码，再安装依赖。安装可能超过前台等待上限，**用 Bash 后台任务运行，并保留任务标识以确认退出结果：**

- 启动后并行推进其他准备：读表、取字段、拉记录、按需读数据规则。
- 源码写入后，可在依赖安装期间修改 `src/`；编码前的读取要求按入口的「工程与依赖边界」执行。

```bash
# <page> 来自已确认的空页或 create 返回；本地使用新的空目录
lark-cli base +webpage-init --base-token <base> --block-id <page> --design-id "<design_id>" --dir "<工程绝对路径>"
# 如需锁定版本，添加 --design-revision "<design_revision>"，值取自 design-get
```

新工程因指定版本与远端不一致而初始化失败时，重新 design-get，核对最新规范和版本后再试。

## 交付前审查

对照需求说明和实际代码逐项确认，不适用于本页面的项跳过。

### 字段可追溯（最先检查）
- [ ] 表、字段、选项 ID 原样来自已核实的来源，没有拼写或大小写错误？
- [ ] 代码中的选项、阶段、关联目标和格式配置，均可逐项对应到已有上下文或 `+field-get` 的返回？

### 需求覆盖
- [ ] 需求说明中的每个模块都出现在页面上，展示内容、字段和交互符合需求？
- [ ] 用户原始需求中的每一项都能在代码中找到具体实现？需求说明漏掉的要求也已补齐？

### 数据真实（违反即不合格）
- [ ] 展示的数据都来自 `useBaseData()`？没有示例数组、兜底假数据或模仿真实数据的默认值？
- [ ] 页面文案里没有写死的数字或结论（如“环比增长 34%”）？数字由查询结果计算，否则用“数据概览”等中性标题？
- [ ] 每个指标、筛选、排行和详情绑定的字段与它的名称含义一致，没有用 ID、编码或相近字段代替？
- [ ] 数值动画、图表和指标收到的是有限的原始数字（`.originValue` 或聚合结果），不是格式化后的字符串，也不会出现 `NaN`？
- [ ] 完整列表都能翻页看到全部记录？只有需求明确要 Top N 或单条时才只取一页？
- [ ] 其余查询写法已按 [数据规则](webpage-data.md)「构建前核对」逐项检查？

### 交互完整
- [ ] 每个按钮、标签页、筛选、分页和导航都有可用的处理逻辑、状态变化或有效目标？
- [ ] 受数据或接口限制而无法实现的要求，已向用户说明原因？没有生成无法使用的控件？

### 设计合规

严格对照 `DESIGN_PROMPT.md` 检查整个页面，确保设计与实现完全遵循其中的设计规范。发现遗漏或偏离时，修正后再提交。

- [ ] `src/index.css` 的主题值符合所选设计，组件的 `var(--...)` 引用均有实际定义？构建通过不能代替此项检查。
- [ ] 页面的设计风格、配色、字体层级、尺寸与间距、布局结构、组件样式和动效，均符合规范中的要求？
- [ ] 规范指定的具体数值、组件用法、使用条件和禁止项，都已按原文落实到实际代码中？
- [ ] 首屏一眼能看出页面主题或品牌？每屏只有一个主要视觉焦点，没有互相竞争的元素？

### 代码与运行
- [ ] Hook 都在组件顶层、条件返回之前调用，不在条件、循环或回调里？
- [ ] `SelectItem`、`TabsTrigger`、`RadioGroupItem`、`ToggleGroupItem` 没有使用空字符串 `value`？
