# Base Mock 数据严谨性指南

搭建 Base、表单、台账、管理系统或 Dashboard 时，只要需要生成示例、Mock 或测试数据，写入前必须阅读本指南。Mock 数据既要覆盖功能分支，也要满足真实业务中的跨字段、跨记录和时间一致性；“字段非空、格式合法、数量足够”不代表数据合理。

## 写入前：先定义业务不变量

根据本次表结构列出会影响业务结论的约束，再生成数据。至少检查：

- **实体一致性**：同一稳定实体的姓名、部门、岗位、客户等级等主档属性保持一致；确有调岗、转部门或等级变化时，用生效日期、历史表或备注显式表达，不能让随机 Mock 数据暗含冲突。
- **时间顺序**：开始不晚于结束，生产不晚于入库或交付，到期日必须来自明确起算日与周期；不得用录入日期、创建时间等语义相近字段替代业务日期。
- **状态与时间一致**：状态必须与当前日期、计划日期和实际日期一致。已完成/已归还应有实际完成时间；长期以前入职的员工不得仍处于普通试用期；预计日期已过且实际未完成时，应标记逾期、延期或给出明确例外说明。
- **金额与数量一致**：已付金额不超过应付金额，未付金额与付款状态一致，数量、单价、小计和总额守恒；取消或作废记录的后续状态不得冒充正常履约。
- **关联一致性**：流水记录引用的人员、部门、客户、产品等必须存在于对应主表；同一业务实体跨记录复用同一主档记录，不靠重复文本制造隐式关联。
- **分支覆盖**：覆盖本次 Formula、View、Dashboard、Workflow 和表单必填校验所需的正常、边界与异常分支，但不要为了覆盖分支制造互相矛盾的记录。

## 生成方法

1. 固定本轮使用的“当前日期”，所有相对日期与状态从同一基准推导。
2. 先生成稳定主档，再生成引用主档的流水；同一实体属性只在主档定义一次。
3. 先生成决定状态的源字段，再由业务规则推导状态、金额和日期，不要独立随机相关字段。
4. 用户指定数量时严格生成该数量；未指定且未要求空模板时生成 5~10 条。
5. 不使用真实身份证号、手机号、邮箱或其他敏感个人信息；格式需要演示时使用明显虚构且不可联系的值。

## 表单场景

- 创建表单后，先用 `+form-questions-list` 核对题目、类型和必填项，再生成与真实填写路径一致的 Mock 数据。
- 未要求空表单时，底表必须有 5~10 条可验证 Mock 数据；当前工具链可提交表单时，至少 1 条必须经真实分享入口执行 `+form-detail -> +form-submit`，其余记录可按需要批量写入。
- 表单暂时无法分享或提交时，仍需写入合理 Mock 数据并回读底表，但必须如实说明“表单提交链路未验证”，不得用直接写表冒充表单已可填写。
- Mock 值必须满足表单必填、选项、附件和显示条件；内部管理字段不得作为候选人、客户或外部填写者的题目。

## 多步骤生命周期

同一请求既要求创建，又要求查询、修改或删除表单/视图时，按 `创建中 -> 创建已验证 -> 后续操作 -> 最终已验证` 推进；Mock 是**不可取消的创建阶段检查点**，不能因为后续会删除入口而省略：

1. 完成表和表单的初始结构及分享配置。
2. 立即通过真实表单提交至少 1 条，并补齐总计 5~10 条 Mock；附件题仅在用户提供文件或已有可用 fixture 时提交附件，不能因缺附件跳过其余 Mock。
3. 用 `+record-list` 回读数量和业务不变量；结构、分享/提交和 Mock 均通过后才标记“创建已验证”，否则不得进入后续查询、修改或删除步骤。
4. 后续删除表单、视图或题目，只处理用户明确指定的对象；不得顺带删除最终保留的数据表、字段或 Mock 记录。
5. 全部步骤结束后再次读取最终保留的数据表并标记“最终已验证”；除非用户明确要求清空数据，否则记录数仍须满足创建阶段要求，为空时不得交付。

Few-shot：先创建学生信息表单，再查询和修改题目，最后删除表单。正确流程是先通过分享入口提交 1 条并补齐 5~10 条学生 Mock，再执行后续步骤；删除“体重题”时保留底层体重字段与已有值；删除整个表单后再次确认最终保留的数据表仍有 Mock。错误做法是因为最后会删除表单而不造数据，或删除题目时级联删除字段和历史值。

## 写入后验收

1. 用 `+record-list` 回读全部 Mock 记录及所有相互依赖的字段；默认 5~10 条数据不得只抽查一行。
2. 核对记录数、关键字段非空和本指南列出的每条业务不变量。
3. 对 Formula、View、Dashboard 和 Workflow 分别验证代表性正常、边界与异常记录确实进入正确分支。
4. 发现矛盾时修改源字段或业务规则后重新回读；不能只改最终展示状态掩盖上游错误。

## Few-shot：常见坏数据与正确方向

| 坏数据 | 为什么不合理 | 正确方向 |
|---|---|---|
| 入职日期距当前日期已数年，人员仍标记普通“试用期” | 入职时长与状态矛盾 | 改为在职，或把入职日期设为合理的近期日期；长期特殊试用需显式备注 |
| 预计交货日期已过、没有实际交付日期，订单仍是正常“已确认” | 时间已越界但状态未进入逾期/延期语义 | 标记逾期/延期/处理中，或补充已确认延期的新计划日期和原因 |
| 同一个人在普通报销记录中随机属于不同部门 | 稳定实体属性跨记录冲突 | 建人员主档并关联；调岗场景增加生效时间或组织历史 |
| 已填写实际归还时间，借用状态仍为“未归还” | 完成事实与状态冲突 | 状态由实际归还时间推导或同步更新 |
| 已付金额等于总额，付款状态仍为“未付款” | 金额守恒与枚举状态冲突 | 由总额、已付和未付金额统一推导付款状态 |
| 到期日用到货日期加保质期，但业务已有生产日期 | 使用了相邻但不等价的起算字段 | 优先使用生产日期加保质期；口径不明确时新增明确字段或询问用户 |
