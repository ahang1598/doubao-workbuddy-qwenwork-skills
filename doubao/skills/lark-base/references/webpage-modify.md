# 修改页面

目标页面已有源码时使用本文件，包括样式、布局、文案、功能、选区修改、错误修复与切换设计。

## 核心原则

1. **只修改用户要求的部分。** 本轮提出的要求都要完成，不附加无关改动。
2. **选区就是用户在页面上指定的元素。** 结合选区和用户指令确定要改的位置。
3. **未涉及的代码原样保留。** 不重排格式、不改名、不整理 import、不调整无关的间距和动效。
4. **先弄清改动范围。** 结合源码判断用户要改哪里；仍不能确定时，再向用户澄清。
5. **修复而不是删除。** 除非用户明确要求移除，否则不删现有功能和界面，也不顺手移除无关的元素。
6. **从代码诊断，不从任务描述推测。** 任务说明了现象和预期，根因要读实际代码确认。
7. **沿用现有设计。** 修改样式时保持与现有页面一致，不引入新的设计模式，除非用户明确要求。

只核实本次改动涉及的数据。已有代码中的表、字段和选项在读取确认后可复用；与本轮更新资料冲突时以更新资料为准。涉及选项、阶段、关联目标、公式 / Lookup 的表达式与结果类型、数字显示格式或其他字段配置时，缺失的信息先查询补齐，不按字段名猜测；独立查询并行执行。

## 工作流程

### 阶段 1：定位目标代码

1. 按入口的「开发流程」`pull` 当前编辑版本源码，不基于旧的本地副本修改。
2. 结合页面入口和选区定位目标代码，按需读取相关的主题变量、组件属性和数据结构。
3. 选区的行列只作位置提示，以元素开始标签在对应文件中定位；行列不符时在该文件内按开始标签搜索；仍无法唯一定位时按页面级修改处理。

进入阶段 2 前先确认：

- **改什么**：哪段代码产生了当前的表现？
- **怎么改**：要达到预期，样式、数据（查询与展示）、交互（状态、处理逻辑与界面）哪些层需要一起改？
- **数据不对？** 沿“查询 → 原始值 → 转换（截断、保留小数、乘 100、兜底默认值）→ 展示”追踪整条链路，问题通常出在转换环节，而不是数据源。
- **有多个相似元素？** 用选区内容确认是哪一个。
- **方案是否完整？** 按本轮要求逐项检查，明确每项要改的代码和修改后的效果，再按下方「交付前审查」补齐遗漏。

### 阶段 2：修改与验证

1. **一次完成全部修改。** 先确定所有改动，再统一修改。切换设计时，先按下方流程更新规范。
2. **确保改动完整。** 用户预期涉及的各层都要改到，例如新增筛选要同时有控件、状态和查询条件。
3. **先完成下方「交付前审查」**，发现的问题一次修完。
4. 按入口的「提交与版本描述」提交并确认结果。

## 错误修复

用户反馈页面打不开、报错、白屏或表现不符合预期时：

1. **定位问题。** 结合当前源码和真实报错，定位字段、空值、Hook、类型等问题。没有报错时，可运行 `pnpm run build` 获取构建证据。
2. **不把构建通过当作没有问题。** 运行时错误不一定导致构建失败，要结合实际代码和可获得的 Host 证据继续定位。证据不足时说明哪些行为未验证，不编造日志或根因。
3. **修复并复核。** 按阶段 2 修复、审查并提交，再对照原问题确认已解决；不以删除功能代替修复。

## 切换设计

用户要求更换设计或主题时，用 design-list 选择设计，再直接 design-install。

```bash
lark-cli base +webpage-design-install --base-token <base> --block-id <page> --design-id "<design_id>" --dir "<工程绝对路径>"
# 如需锁定版本，添加 --design-revision "<design_revision>"，值取自 design-get
```

- **核对安装结果。** 资源放在 `src/ui-kits/<designSystemId>`。`status=installed` 表示新安装，`reused` 表示复用已有目录。`prompt_only` 表示没有 UI Kit，或资源安装失败后仅更新规范；失败原因见 warning。此时按本地规范继续开发，不引用未安装成功的资源。
- **复用目录保留已有定制。** `kit_revision_status=matched` 只表示安装记录匹配，不表示源码未修改；`different` / `unknown` 表示资源版本不同或无法确认。不宣称资源已升级，也不自行清空目录重装。
- **按新规范修改页面。** 安装不会自动改变页面样式。按规范更新 `src/index.css` 中已有主题变量的值，并按需调整页面代码和组件引用；不修改 `src/theme.css`。
- 指定版本与远端不一致时，重新 design-get，核对规范和版本后再安装。

## 交付前审查

只检查本次改动涉及的层，其余跳过。

### 需求
- [ ] 用户要求的每项修改都有相应实现，没有遗漏或擅自简化？
- [ ] 本次要求的操作都有可用入口，操作后的展示内容和数据范围符合要求？无法完成的要求已说明原因？
- [ ] 没有改动用户未提及的内容？
- [ ] 切换设计时，适用于本次改动的设计细节已逐项落实？

### 数据（违反即不合格）
- [ ] 展示的数据都来自 `useBaseData()`？没有示例数组、兜底假数据或模仿真实数据的默认值？
- [ ] 表、字段、选项 ID 逐字来自已核实的来源，没有拼写或大小写错误？
- [ ] 改动用到的选项、阶段、关联目标和格式配置，可对应到本轮更新资料、已读取的代码或表 / 字段查询返回？
- [ ] 改动涉及的指标、筛选、排行和详情仍绑定字段的原本含义，没有用 ID、编码或相近字段代替？
- [ ] 数值动画、图表和指标收到的是有限的原始数字，不是格式化后的字符串，也不会出现 `NaN`？
- [ ] 完整列表没有被固定在第一页或截断？只有需求明确要 Top N 或单条时才只取一页？
- [ ] 改动涉及的查询已按 [数据规则](webpage-data.md)「构建前核对」检查？

### 代码与运行
- [ ] Hook 都在组件顶层、条件返回之前调用，不在条件、循环或回调里？
- [ ] DSL 引用稳定，动态时间等值用 `useMemo` 固定，没有直接写每次渲染都会变化的 `dayjs()`？
- [ ] `SelectItem`、`TabsTrigger`、`RadioGroupItem`、`ToggleGroupItem` 没有使用空字符串 `value`？
