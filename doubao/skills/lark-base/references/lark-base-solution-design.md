# Base 系统搭建指引

本文档服务于：把一句模糊目的翻译成一个结构合理、充分利用 Base 能力、足够丰富的方案，并在交付前逐项验收。下面依次讲丰富度（用满 Base 能力）、建模（表结构与字段）、复杂搭建的交付清单，以及若干跨功能纪律。先读本文档做方案判断，再回 SKILL 的具体命令执行。

何时用：用户只给目的、不确定要搭成什么样（“做点东西以后能一眼看出…”“记个账”“搭个系统管一下…”），或明确要一个“完整可用的系统”。此时按本文档主动扩展丰富度。

何时不用：用户已明确知道要什么形态、点名了具体组件或改动（“加一个 xx 字段”“把这个视图改成按状态分组”“建一张 xx 表”），就照做，不要按本文档额外扩展、追加用户没要的表/视图/仪表盘/自动化。

## 丰富度：让产物用满 Base 能力

模糊需求最常见的失败是“能跑但太单薄”——只有一堆文本字段、没有分类、不会计算、没有视图。把目的翻译成方案时，除了建好表与字段（见 [建模](#建模表结构与字段类型)），默认按下面的展示、协作与自动化能力逐层加厚。

分寸：字段类型、必要计算和关键视图属于“该有的骨架”，一律补齐。当需求模糊或用户想要一个完整可用的系统时，仪表盘也默认配上（哪怕没明说“要图”），让结论一眼可见；工作流按诉求里是否有提醒/自动化/联动语义来配。真正需要克制的只有对外发送和多角色权限——它们有外发或安全影响，用户点名才做。宁可让模糊需求得到一个丰富、开箱即用的系统，也不要交付单薄的纯文本空表。

丰富度只在 `lark-cli` 当前支持且能够完整闭环的能力范围内扩充。任何追加对象或功能都必须有可执行的创建/配置命令和回读验收路径；对于 `lark-cli` 不支持、只能完成一部分或无法验证的能力，不得先创建空对象、占位字段或半成品配置，也不得在最终答复中包装成已完成。优先采用 `lark-cli` 支持的等价方案，无法等价替代时明确说明能力边界。

### 视图

一张表可配多个视图，各自持久化筛选/排序/分组/展示且共享同一份数据。支持类型：`grid`（表格）、`kanban`（按状态分列看板）、`gallery`（画册，适合带图卡片）、`calendar`（按日期）、`gantt`（甘特，排期/工期）。默认给出对用户最有用的切面，例如逾期/待办单独一个筛选视图、按负责人或状态分组、按截止日排序。表单不是视图类型，用表单命令管理。

持续使用的筛选（“本月/今年/近 N 天/超过 N 月未…”）不能把当前的具体日期写死进 filter：用 Today/相对日期条件表达；平台视图无法表达动态区间时，新增承载判断的公式辅助字段（如“是否逾期”“距到期天数”），再基于它筛选。交付前读回 filter 确认不是固定值。

### 仪表盘

用户要“图/看板/占比/趋势/对比/一眼看出”时在 Base 内建 dashboard 组件（见 [lark-base-dashboard.md](lark-base-dashboard.md)）；即使没明说要图，只要需求模糊或想要一个完整系统，也默认配一个能反映关键结论的仪表盘（如总量、分类占比、趋势或待办分布）。外部图片只能补充，不能替代表内可持续图表。选型：比大小→柱状/条形图，看趋势→折线/面积图，看占比→饼/环形图，无分组维度的单值指标→指标卡，另有组合、散点、漏斗、雷达、词云和文本说明块。

- 宽表多指标横向对比（多个字段的平均值、各类占比等）不要用主键/姓名/编号等唯一值字段做 `group_by`；先生成“维度—指标”的 helper 汇总表再按维度出图，或使用支持无分类轴的多指标配置。
- dashboard 组件的 filter 作用在公式字段上时注意其返回类型（用等于筛公式返回值易报错）。
- 若仪表盘是本次新建的，布局也属于交付条件，必须同时满足**不重叠**与**紧凑**两组判据，并按“核心指标 → 分类对比 → 趋势与明细”的阅读顺序或当前业务对应的等价逻辑排列：
  - **不重叠**：任意两个组件不得相互覆盖（按 12 列栅格 `x/y/w/h` 判断，允许极小容差，避免把渲染取整误差误判为重叠）。
  - **紧凑**（下列任一条中招即不合格）：① 中间存在整行为空；② 同一行组件之间有空档；③ 除最后一行外，某行未铺满整幅宽度（右侧留白）；④ 最后一行未从左侧开始排（末行右侧可留白，但必须左对齐起排）。
  - 检查发现重叠、空行、行内空档、非末行右留白或末行未左起时，至少调用一次 `+dashboard-arrange` 尝试重排并再次检查；若重排后仍不满足，改用 `+dashboard-block-update --position` 按 12 列栅格 `{x,y,w,h}`（`x+w<=12`，逐行左起、行内铺满、组件间不重叠）逐组件指定坐标继续重试，写后回读 `+dashboard-block-get` 的 `position` 按上述判据自检；确实受平台限制无法满足时再如实报告限制。
- 组件交付前必须 get-data 成功、结果与需求一致，才向用户宣称看板可用。

### 表单

需要外部或多人填报时配 form：以字段为题、可设必填与条件显示，每次有效提交产生一条记录。报名/登记/信息收集类需求默认建表 + 表单；建好后补测试记录或用 +form-submit 提交测试数据，交付前确认主表非空。

### 工作流

`workflow` 适合到期提醒、库存预警、状态变更联动、按钮触发写回等（见 [lark-base-workflow-guide.md](lark-base-workflow-guide.md)）。用户明确要“提醒/预警/自动/一按就…”时才建，不要从“表里有日期/状态字段”自行推断创建。新建默认 disabled，必须先预检完整定义、再按题意 enable 并回查 enabled 状态，不能把“创建成功”当作“已生效”。

### 高级权限

数据敏感、要按职责限制可见/可改/可删时才开高级权限并配角色（见 [lark-base-role-guide.md](lark-base-role-guide.md)）。系统角色不可删除，关闭高级权限会影响自定义角色；开启或变更前确认目标与影响。

### 示例数据（mock）

要不要写、写到什么程度算过，见 SKILL.md 验收矩阵「本轮新建表的记录」行；条数、业务一致性和写后验收见 [Base Mock 数据严谨性指南](lark-base-mock-data-guide.md)。

## 建模：表结构与字段类型

### 新建 Base 前的 1:N 建模

在第一次 `+base-create` 前先区分稳定主档与重复事件。以下任一条件成立时，使用“主表 + 流水/历史表”，否则保持单表：

- 同一业务对象会被多条交易、借还、办理、检查或状态变更记录重复引用；
- 主档与事件有独立生命周期，例如主档属性更新不应改写历史，或每次事件需要独立时间、状态、经办人；
- 多条记录需要复用同一对象身份，并要求能从对象反查全部历史。

不要仅因字段很多、用户说“台账/档案库”，或可能未来扩展就拆表。一次登记只描述一个对象、没有独立重复事件时，单表更直接。

执行顺序：

1. 用 `+base-create --table-name --fields` 创建一端的主表，主字段使用稳定业务标识。
2. 用 `+table-create` 创建多端的流水/历史表；主字段标识一次独立事件。
3. 在多端创建 `link` 指向一端主表，设置 `bidirectional: true` 并给反向字段一个业务可读名称。link CellValue 必须传 record ID 对象数组，例如 `[{"id":"rec_xxx"}]`；常见 1:N 中每条多端记录只放一个对象。不要传裸字符串数组，也不要编造 `multiple` 属性。
4. 先写主档并保存返回的真实 record ID，再写流水/历史；不要猜 ID，也不要用重复文本代替 link。
5. 用 `+record-get` 从一条多端记录确认它只指向预期主档，再从主档记录确认反向字段包含对应的全部已写流水。两端都可追溯后，关联项才算完成。

| 关系类型 | 主表（一端） | 流水/历史表（多端） | link 放置与基数 |
|---|---|---|---|
| 可复用对象与发生记录 | 资产、设备、合同等稳定对象 | 借还、维保、收付等每次发生的记录 | 多端 link 指向主表；每条多端样例写一个主档 ID |
| 主体与资质/办理历史 | 人员、客户、供应商等主体 | 资质、证照、续期、审核等可重复记录 | 多端 link 指向主体；主表反向显示全部历史 |

若两个概念始终一一对应、没有独立字段或生命周期，不要为它们各建一张表；若一条事件确实可关联多个主档，按真实业务写多个 record ID，不要为了套用 1:N 丢失事实。

### 字段类型选择（含公式、关联）

不要什么都用文本。按数据语义选专用字段类型，产物立刻专业可用（字段 JSON 见 [lark-base-field-json.md](lark-base-field-json.md)）：

| 数据语义 | 推荐字段类型 | 说明 |
|-|-|-|
| 状态/类别/优先级/等级 | `select`（单选或 `multiple` 多选） | 可点选、可分组、可配色；别让用户手打自由文本 |
| 金额/价格/预算 | `number` + `style.type=currency` | 带币种与精度，而非裸数字或文本；用户说“钱/金额”默认货币而非普通数字 |
| 完成度/占比 | `number` + `style.type=progress` | 进度条展示 |
| 评分/星级/满意度 | `number` + `style.type=rating` | 满意度用评分而非文字，也别拿普通数字冒充评分档位 |
| 日期/时间 | `datetime` | 支持排序、相对时间筛选、日历/甘特视图 |
| 电话/链接/邮箱/条码 | `text` + `style.type=phone/url/email/barcode` | 语义化文本，不用裸文本 |
| 负责人/参与人 | `user`（`multiple` 可多人） | 关联真实成员，可用于分组、通知与权限 |
| 是/否、是否完成 | `checkbox` | |
| 文件/图片/扫描件/文档 | `attachment` | 用户说“放进去/传上去/附上”就建附件字段并上传原件，别用文本摘要替代 |
| 记录编号/单号 | `auto_number` | 自动生成稳定编号 |
| 创建/修改的时间与人 | `created_at` / `updated_at` / `created_by` / `updated_by` | 台账留痕天然需要 |
| 地理位置 | `location` | |

派生与关联字段：

- `formula`：小计（数量×单价）、总分/平均分、状态判断（“是否逾期”“是否达标”“距到期还剩几天”）、文本与日期处理。用户要求“自动算”“不用手动加”“一眼看出达标与否”时基本都要公式字段（见 [formula-field-guide.md](formula-field-guide.md)）。基于已有数据在表里做统计、汇总或派生时，用 `formula` / `lookup` 字段承载动态计算，不要先一次性静态算出结果再写回普通字段——静态值不会随源数据更新、随后即失真；只有本身是事实录入的存储值才按普通字段写入。
- `link` / `lookup`：多实体场景先用 `link` 关联主表与流水表（何时拆分见上方 [1:N 建模](#新建-base-前的-1n-建模)），再用 `lookup` 把主档信息跨表取到流水/历史表展示或聚合，避免每条记录重复抄主档（见 [lookup-field-guide.md](lookup-field-guide.md)）。

口径不默认假设：派生字段依赖用户没给出的源字段时，优先新增显式输入字段或向用户澄清，不要用相邻但语义不同的字段代替。例如到期日应由明确的起算日与周期推导，不默认借用录入日期；会随时间变化的状态口径优先用公式而非手填固定值。

## 复杂搭建先列交付清单

用户要求同时搭建多张表、计算字段、视图或仪表盘、自动化、角色权限时，第一次写操作前先从用户原话列出必交付项及数量，并按依赖顺序推进：表与真实字段/关联 → 示例数据与计算验证 → 视图/仪表盘 → workflow → 角色权限。不要因前面的表或图表已创建就提前结束，也不要增加用户未要求的自动化或外发动作。

一句话常包含多个意图（既要建系统，又要分析、出图，或顺带复制/找回一张旧表）。把每个意图都记进交付清单并全部完成，不要拆成互不相关的单步各自了事；尤其复制或找回一张旧表不等于新建系统已完成。

新建 Base 时，交付清单必须先做一次实体—事件—基数判断：若稳定主档会被多条交易、借还、办理、检查或状态历史重复引用，先按上方 [1:N 建模](#新建-base-前的-1n-建模) 拆成主表与流水/历史表；若只有一个实体且没有独立重复事件，保留单表，不为拆表而拆表。

每项只有在对应 read-back 证明配置与用户要求一致后才算完成：表/字段/关联用 get/list 与可读样例核对，公式用真实记录结果核对，视图用对应 get 核对配置，仪表盘用 block get/get-data 核对口径，workflow 用 disabled 预检后 enable 并回查 enabled 状态，角色用 role-get 核对数据与字段权限。若用户明确要求多条 workflow，逐条记录返回的 workflow_id，全部完成“预检 → 启用 → 回查”后才能交付；不要只验证其中一条，也不要把 create 成功或配置草稿计为已完成。

## 其他跨功能纪律

### 交互式“一键判断”

“一按/一眼就知道达标与否、谁未处理”这类诉求，核心是让结论在表/看板里可持续一眼查看，而不是在对话里口头汇报。优先建达标/状态判断公式字段，再配筛选视图或仪表盘组件呈现。筛选互斥状态时，基于原始结构字段（空值/布尔/枚举）判断，不要对自造展示文案做 contains；必须筛文案时枚举全部目标状态。真正需要点击触发写回时，先按 [字段 JSON SSOT](lark-base-field-json.md) 创建 `button` 字段；需要触发自动化时再用 `+button-rule-bind` 绑定 ButtonTrigger workflow。

### 分析类需求的口径纪律

分析对比、排名、归因这类需求属于查询分析，先读 [Base 数据表查询与分析 SOP](lark-base-data-analysis-sop.md) 选择查询路径。方案判断上额外注意：分组、计数、求和、TopN 用确定性聚合（+data-query 或脚本），不要在思考里手工数行累加；不要静默剔除样本或自行认定异常值后只报剔除口径，怀疑异常时同时给全量与剔除两种口径并说明差异，默认结论以全量数据为准。
