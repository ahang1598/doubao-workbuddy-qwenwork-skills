# Base permission authoring rules

> Entry guide: [lark-base-role-guide.md](lark-base-role-guide.md) | JSON schema: [role-config.md](role-config.md)

Use this guide when translating a natural-language Base role or advanced-permission request into role permission intent. After applying these authoring rules, construct the final `AdvPermBaseRoleConfig` JSON with [role-config.md](role-config.md).

## 权限等级偏序

可管理 > 可编辑 > 仅新增时可编辑 > 仅可阅读 > 无权限

字段级额外有「仅新增时可编辑」，位于「可编辑」和「仅可阅读」之间。「严于/低于/收窄」均按该偏序判断。

## 实体映射规则

本节解决「query 字面实体写成 Base 中哪个实体」。先映射，再判断是否授权。

### 1.1 就近择优替换

当 query 字面实体与 Base 快照没有完全同名实体时，在 Base 快照中选择语义最接近的实体写入 JSON。

例：

1. query 写「员工档案」，Base 中只有「员工花名册总表」→ JSON 使用「员工花名册总表」。
2. query 写「销售业绩看板」，Base 中是「销售业绩仪表盘」→ JSON 使用「销售业绩仪表盘」。
3. query 写「优先级=紧急」，字段选项只有「高/中/低」→ JSON 使用「高」。

语义阈值：近义、换名、长短形、同义梯度可以替换；名称完全无关时不要靠字面顺序兜底。

后缀容差触发条件：若 query 字面实体 A 在 Base 快照中无精确同名实体，但去掉通用后缀（表、明细表、记录表、情况表、登记表、统计表、汇总表、明细、清单、列表、信息表、数据表、台账）后，与某 Base 实体 B 完全一致或是 B 的去后缀形态，即视为同一实体，JSON 必须使用 B 的 Base 真实名。该规则同样适用于字段、视图、仪表盘：query 字面字段是 Base 中某字段去掉后缀（字段、信息、内容）后的形态时，JSON 使用 Base 中的全名。同一去后缀形态同时唯一命中多个 Base 实体时，按 §1.2 跳过。

### 1.2 无匹配则跳过

如果前序流程中有「本轮将新建」段（来自前序 domain 规划，尚未落库），该段列出的表/字段/视图由本轮前序负责创建，执行到权限配置时**已经存在**；实体存在性判断把该段与 Base 快照合起来当作 Base 全集。

只有当 Base 快照**和**「本轮将新建」段里都不存在任何可近似替代实体时，才跳过该项授权。不要为该实体写授权、字段子句、视图子句或行级条件，也不要虚构同名实体。

### 1.3 实体名字面形态

JSON 中实体名直接采用映射后的 Base 实体名。表、字段、视图、仪表盘、选项值都不简化、不翻译、不缩写、不加修饰。若 §1.1 把「员工档案」映射到「员工花名册总表」，JSON 后续始终写「员工花名册总表」。

实体名含空格时，空格是名称的组成部分，必须原样保留。

## 实体入选与范围收束

本节解决「哪些实体可以进入 JSON」。核心规则：显式点名 + 与当前角色直接相关 + 有授权或修改语义，才进入 JSON。

### 2.1 点名收束

未在当前角色 query 段落出现的对象整段不出现，包括兄弟表、字段、视图、仪表盘、关联字段指向的表、当前角色已有但 query 未点名的表。不要为「补全」「对齐」「默认放开」替下游补授权。

每条授权落笔前回扫 query 原文，确认当前角色对该实体存在显式语义路径。无法判断该实体是否属于当前角色授权范围时，默认不写该实体授权块。

### 2.2 关联字段不连带授权

数据表中的 SingleLink / DuplexLink 指向的关联表，只有被用户显式点名时才在 JSON 中写授权块。用户提及表 A，不自动连带授权 A 关联到的表 B。

### 2.3 字面清单边界刚性

当 query 用「管理/维护/处理/负责 + A、B、C」这类职责动词 + 字面对象清单给角色授权时，授权对象 = 字面清单 ∪ §1 近似映射结果。不要因主题接近、上下游关系、关联字段指向、命名互补、其他角色已授权而扩展清单。

注意：刚性边界不阻断 §1 的就近择优替换。必须先把清单中的字面项映射到 Base 最接近实体，再按映射结果判断授权。

### 2.3.1 主题词与字面清单边界

判定路径：query 给出字面表清单（顿号、逗号、「等」枚举的具体表名）→ 走 §2.3 刚性边界；query 只用「管理/维护/处理/负责/对所有 + 主题词 X」这类职责动词 + 主题名词概括 → 走本节按同根表谱系在表轴展开。

展开范围：Base 快照中所有以 X 为同根的强关联表。判定方式是对 Base 全部表名逐张做 `包含(X)` 子串/正则扫描，任何表名字面包含 X 的表，或经 §1 后缀容差/近义映射锚定到 X 的 Base 表，都是强关联同根表，必须纳入，含 X 表、X 登记表、X 分类、X 进度、X 参与情况、X 归档、X 子任务、X 验收、X 结项、X 明细、X 汇总等同根表谱系。关键词嵌在表名中段或尾部的复合名（如主题词为「合规」时的 `数据质量与合规审计表`）、形态像分析/统计/汇总/派生表的命中项（如主题词为「薪酬」时的 `薪酬公平性与性别平衡分析表`），同样是强关联同根表，不得因为复合名、不够「典型」或像派生表而漏选。精确匹配优先与关键词正则兜底的总纲见 §2.3.4。

本节只在表轴展开；每张同根表的字段、视图、行级条件仍按 §2.1、§3 各节按 query 字面点名收束。

### 2.3.2 字段范围名词

query 用「基本信息 / 反馈内容 / 评分 / 状态 / 明细 / 备注 / 说明 / 薪酬 / 福利 / 收入 / 绩效 / 考核 / 资金 / 财务 / 金额」等字段范围概括名词，而不直接给出字段清单时，按本节展开为 Base 字段集合；§1.1 后缀容差规则同样适用，字段范围名词可映射到 Base 同根的具体字段。

承载表确定：

1. 范围词字面绑定到具体单张表（例「{表}的反馈内容」）时，承载表 = 该表。
2. 范围词未绑定到具体单张表时，承载表集合 = 当前角色经字面表清单或经 §2.3.1 主题词展开获得表级访问权的全部数据表，排除按 §2.1 整段不出现的未点名表。

展开范围：对每张承载表，把范围词展开为该表内字段名字面或语义命中该范围的字段集合。仅使用 query 字面点名的范围词，不为对齐其他表扩展。Base 中某张承载表内无任何命中字段时，按 §1.2 跳过该表的范围子句，该表不写范围子句、不虚构字段。

语义边界：字段范围名词只覆盖与该范围词同语义层级的**原始信息字段**，即字段承载内容是该范围词直接描述的原始采集项。范围名词**不覆盖**基于这些原始信息进一步计算、统计、汇总、聚合得到的派生字段（公式、查找引用、汇总输出等）。承载表内同时存在原始字段与派生字段时，字段范围名词只展开为原始字段集合，派生字段归入「其余字段」轴，按 §4.2 / §4.4 偏序处理。关联（SingleLink / DuplexLink）字段是原始可录入字段，不归派生/系统自动生成。

### 2.3.3 指示代词解析

当角色段落中出现「这张表 / 这表 / 该表 / 此表 / 它 / 这」等指示代词作为表对象时，指代对象解析为同一角色段落内、指示代词之前最近一次字面出现的表名；指代对象不向同角色其他已点名表、字段范围词、关联表或主题词扩散。

### 2.3.4 精确匹配优先与关键词正则兜底

本节是 §2.3.1 表轴展开、§2.3.2 字段轴展开共同遵循的实体选择总纲。

1. 精确匹配优先且排他：query 中的实体词若与某 Base 表名或字段名完全同名，只绑定该精确实体，不再触发正则兜底展开。
2. 无精确同名才启用正则兜底：query 用主题词、范围名词等概括表达且无任一 Base 实体与之完全同名时，从该概括词中抽取关键 token，对 Base 全部表名 + 全部字段名逐个做 `包含(token)` 子串/正则匹配。
3. 命中即强制纳入：任何名称包含该 token 的表或字段都是强关联实体，必须进入 JSON。严禁以名称是复合名、主题不够「典型」、与已选实体语义重复为由漏选。
4. 轴归属与边界：本节只负责「该选的别漏」，不推翻各轴既有收束——表轴展开仍按 §2.3.1，字段轴展开仍按 §2.3.2（含派生字段排除等语义边界）。

### 2.4 全集语义

当 query 字面清单是全集语义时，按字面铺满对应轴：

1. 「所有数据表 / 全部数据表 / 每一张表」→ 逐张写表权限，仪表盘轴不动。铺满范围 = base 快照 `### 数据表` 节列出的全部表，逐张全列，不许按业务相关性过滤。
2. 「所有数据 / 全部数据 / 全量(的)数据」→ 无主题词限定的全量数据 READ 语义，同时铺满表权限 + 仪表盘可见；仪表盘轴指 Base 全部仪表盘，按权限词方向授权（查看/阅读 → 仅可阅读/可见）。
3. 「所有内容 / 所有信息」→ 有「看板/仪表盘」语境时按「所有数据」处理，否则按「所有数据表」处理。
4. 主题词限定的全集（「所有/全部 + 主题词X + (相关的)数据/内容」）是「所有数据」在主题词 X 上的收窄，数据 = 数据表 + 仪表盘双轴。表轴按 §2.3.1 在 X 同根表上铺满；仪表盘轴对 Base 全部仪表盘名逐个做 `包含(X)` 判定，命中纳入并按 READ 方向授权。
5. 「其他/其余 数据表 + 保持/保留/设为 + 仅可阅读/只读/可查看/可阅读」是对本轮未点名数据表的兜底 READ 授权：把 base 快照中本轮未被点名处理的全部数据表逐张枚举为仅可阅读。漏铺 = 下游按默认无权限处理 = 缩权；禁止省略、禁止把这些表配成无权限。

无表轴全集词时，JSON 禁止出现「所有表 / 全部数据表 / 每张表 / 逐表 / 所有已授权表 / 已有权限的表 / 已访问表」，也禁止枚举当前角色已有但 query 未点名的数据表。

### 2.5 视图全集只绑定最近点名表

原文只有「所有视图 / 全部视图」，但没有表轴全集词时，不要把视图全集扩展到全 Base 或角色所有已授权表。必须把视图全集子句写入对应表块内部。

反向的视图可见性是白名单——「只能看 / 只能查看 / 仅可见 默认视图」是**只放默认视图的白名单，绝不能写成「所有视图可见」**：先把「默认视图」按 Base 快照映射成该表真实视图名，写入对应表块 `仅可见视图 {真实名}, 其余视图隐藏`。视图管理限制（禁新增/修改/删除视图）与可见性独立，按 §3.6 写。

## 权限维度识别规则

完成实体映射与入选后，逐角色按以下维度扫描 query。字面没提到的维度整段不出现。

扫描每条权限描述时，先判断权限词方向，再落到具体维度：

- **正向授权**：可以 / 能 / 具有 / 拥有 / 保留 / 保持 / 维持 / 沿用 → 只影响点名实体（保留/保持 = 维持点名实体现状，不蕴含排他、不收窄未点名实体；「保留 X」≠「只保留 X」）
- **局部精确否定**：不能 / 不可 / 不允许 / 禁止 → 只影响点名实体且否定关键词要字面保留
- **局部排他重写**：只能 / 仅可 / 改为 → 是否补写其余同层实体必须服从新建/更新分支规则

正向授权对象的表/字段消歧：权限词方向判定为正向授权后，落入具体维度前先把对象字面在 Base 快照中做精确匹配——命中数据表名走 §3.3 表级，命中字段名走 §3.4 字段级。两端都精确匹配不上时，优先按数据表方向解析，不要默认下沉到字段级。仅在数据表方向所有路径都不命中、且字段方向能精确或经后缀容差命中时，才落字段级。

### 3.1 角色名

query 没有显式角色名时，优先从角色主体语义中提取，例如销售员、运营人员、产品经理、客服、财务、市场部。不要用权限用途或任务动作反推出「订单管理员」「报销审核员」这类动作 + 对象合成名。

### 3.2 基础操作

命中「允许/禁止 + 复制内容 / 创建副本 / 导出下载 / 打印」时，在角色 JSON 中写对应基础操作。只列 query 字面命中的操作。否定关键词必须字面落进 JSON，例如「禁止复制内容 / 禁止导出下载 / 禁止打印」。

### 3.3 表级权限

表级权限只由数据内容访问目标或表结构/配置目标决定：

1. 查看、阅读、浏览、访问、查阅、查询数据内容或记录 → 仅可阅读。「访问 / 进入 / 接触 / 能看到」这类只表达「能触达数据」的泛词，默认按最小的仅可阅读处理，不因词泛而升到可编辑/可管理。
2. 编辑、修改、维护数据内容或记录 → 可编辑。
3. 明确管理表结构、字段结构、表配置、权限配置、整张表结构 → 可管理。

视图管理、选项管理、记录新增删除、基础操作、仪表盘权限都不是表级可管理的充分条件。

两类动词的区分按功能判定，不按字面词表死记：

- **动作动词直接描述对内容的具体操作（查看、阅读、浏览、访问、查阅、录、录入、填写、登记、打分、评分、编辑、修改、上报、提交、更新等作用于内容/字段的动词），本身就锁定权限等级**
- **职责动词是「负责/统管某块」的笼统授权（管理、负责等），等级未定，需走兜底映射**；`维护`、`处理` 兼具两义：单独出现按职责动词兜底，同句另有更具体的动作动词时归该动作动词

职责动词单独出现且对象是数据表内容时，兜底映射为：

1. 「管理 X」→ 对 X 的可管理权限。
2. 「维护/处理/负责 X」→ 对 X 的可编辑权限。

同句中动作动词与职责动词共存时，以动作动词为准。

对象决定等级：字面读级动词作用于表结构、字段定义、视图配置、权限设置等表配置类元数据时，写可管理；字面管理级职责动词作用于表内记录且带行级条件时，写可编辑 + 行级条件，不要写可管理。

表级由数据访问的**正向目标**定级，编辑类操作否定词不单独抬级：某角色对一张表的数据操作目标全是读方向且整句对该表没有任何 EDIT 方向动作时，该表表级 = 仅可阅读。`仅可阅读` 本就不含增删改，所以同句出现的「不能删除/不能修改/不能编辑/不能更新/不能新增/不可更改 + 数据或记录」这类编辑类操作否定只是「看得到但改不了」的字面强化，按只读理解即可，不能反推成「持有编辑权、只单独禁掉某项」而升到可编辑。只读表上不写 `禁止删除记录 / 禁止修改` 子句。

### 3.4 字段权限

字段权限命中字段名 + 可编辑 / 仅新增时可编辑 / 仅可阅读 / 不可见 / 其余字段等字面语义时，写在对应表块内。

常用落笔：

1. 「X、Y 可编辑，其余只读」→ `仅可编辑字段 X、Y，其余字段仅可阅读`
2. 「所有字段只读」→ `所有字段仅可阅读`
3. 「仅 X 不可见，其余可编辑」→ `字段 X 不可见，其余字段可编辑`
4. 「仅 X、Y 可见，其余可编辑」→ `字段 X、Y 仅可阅读，其余字段可编辑`
5. 「X 可编辑，Y 仅可阅读，其余不可见」→ `字段 X 可编辑，字段 Y 仅可阅读，其余字段不可见`
6. 「仅可编辑 X」且无对应表级权限、未提其余字段 → `仅可编辑字段 X`
7. 「仅可阅读 X」且无对应表级权限、未提其余字段 → `仅可阅读字段 X`
8. 「所有字段可新增 / 所有字段仅新增时可填」→ `所有字段仅新增时可编辑`
9. 「字段 X 可新增，其余只读」→ `字段 X 仅新增时可编辑，其余字段仅可阅读`

字段「可新增 / 新增时会写 / 仅新建记录时可填 / 写入后不可修改」等语义 → 写「仅新增时可编辑」，不要落成「可编辑」。

纯字段级排他且无表级权限时，按字面保留「仅可」，不要替下游推断未提及字段。若同一句同时给了表级权限，按 §4.2 的创建分支字段轴收束处理。

### 3.5 记录权限与行级条件

#### 3.5.1 操作符与字段类型白名单

行级条件只支持以下操作符：为本人、等于、不等于、大于、大于等于、小于、小于等于、包含、不包含、为空、非空。

行级条件支持字段类型：数字、货币、评分、进度、单选、多选、阶段、人员、创建人、上述类型的公式、上述类型的查找引用。不支持文本、日期、复选框、电话、链接、邮箱、附件、关联字段。

字段类型不支持时的回退：若 query 锚定的字段类型不在支持列表中，优先找同表的人员/创建人字段替代；都没有就只配表级权限，跳过行级条件，不要硬写。

#### 3.5.2 筛选字段同名优先

行级条件锚定字段时，必须优先选用与 query 字面完全同名的 Base 字段；只有当同名字段不存在，或同名字段虽存在但类型不在白名单、无法承载该筛选条件时，才按 §1.1 就近择优替换为语义最接近的近似名字段。同名字段已存在且类型可用时，不得因近似字段更顺手或语义更贴而越过同名字段。

#### 3.5.3 主观锚点词识别

若 query 用「自己/本人/我」，必须落到能表达「操作主体 = 当前用户」的字段：

1. 默认使用平台隐式自带的「创建人」系统字段，写 `创建人 = 当前用户`；Base 快照中即使未显式列出也可用。
2. query 明确用动词锚定字段时，按锚定字段写，例如「自己提交的」→ 提交人 = 当前用户，「指派给自己的」→ 指派人 = 当前用户。
3. query 直接点名非黑名单的人员字段时，用该字段 = 当前用户，例如协作者、知会人。
4. 裸「自己/本人/我」不能 fallback 到负责人、指派人、提交人、经办人、跟进人、审批人、审核人、申请人、录入人、主理人、受让人、执行人、对接人、客户经理、owner、PIC 等暗含分配/审核/业务关系的字段；无动词锚定时仍用创建人。

主观锚点词不能丢。只写表级权限而漏掉「创建人 = 当前用户」等记录条件，等价于扩权。

#### 3.5.4 选项值字面忠实

`字段 = 选项A` 中的选项名必须来自该字段自己的 optionList，不能借用同表另一个 select 字段的选项；选项值仍按 §1.1 就近择优替换映射到 Base 真实选项，但不允许跨字段借选项。

#### 3.5.5 数值边界与百分比还原

数值边界：

1. 以下 / 不到 / 低于 / 不足 / 之前 / 以前 → 小于 N。
2. 不超过 / 不大于 / 不多于 / 最多 → 小于等于 N。
3. 以上 / 超过 / 高于 / 之后 / 以后 → 大于 N。
4. 不少于 / 至少 / 不低于 / 达到 N 及以上 → 大于等于 N。

`以下`/`以上` 取开区间，不含 N 本身。

百分比字段值还原：当 query 数值条件作用的字段在 Base 快照中类型为 Number 且配置 `percentage=true` 时，字面数值 N（无论是否带 `%`、是否口语化为「xx 成」）在 JSON 中按存储小数 N/100 落笔；Base 中 percentage 字段存储 0~1 区间小数。

例：字段「完成率」类型 Number percentage=true，query「完成率大于 60」→ JSON 写 `完成率大于 0.6`。

非 percentage 字段不做换算，字面数值保持原样。

#### 3.5.6 多条件连接

多条件连接：query 用「且/并且/同时/还要」连接时用「且」；query 用「或/或者/或是/任一/任何之一」连接时用「或」。

同一记录范围里「且」「或」混用时，保留分组优先级：先把记录范围拆成「或」并列的若干记录组，每个「或/或者/或是」分隔一个完整的「满足…的[记录/对象]」描述；同一描述内部修饰同一对象的多个条件用「且」绑定为同一组。落笔时给每个含两个及以上条件的组加上括号，写成 `(组1条件) 或 (组2条件A 且 组2条件B)` 的结构。只有一个条件的组、纯「且」串、纯「或」串本身无歧义，可不加括号。

### 3.6 视图权限与表内操作

视图新增、修改、删除限制必须带「视图」宾语，写成「禁止新增视图、修改视图、删除视图」或「禁止管理视图」。禁止写裸的「禁止新增、修改、删除」，避免被误解为记录新增/删除。

表内操作权限只在 query 字面命中时写入，例如：

1. 禁止新增记录 / 禁止删除记录
2. 禁止管理视图 / 禁止新增视图 / 禁止修改视图 / 禁止删除视图
3. 禁止管理选项 X
4. 禁止下载附件 Y

选项管理不是表级管理；视图管理不是表级管理；记录新增删除不是表级管理。

附件消歧：「附件」既可是下载操作也可是字段对象，按动词和宾语区分：(a)「不能/禁止 下载附件 X」是下载操作否定，写 `禁止下载附件 X`，只限制下载；(b)「不能/不允许 新增/编辑/修改 附件（内容/字段）」是对**字段「附件」**的字段级编辑否定，按 §4.4 走字段级黑名单。**严禁把 (b) 写成「禁止新增附件 / 禁止编辑附件」这类子句**。

正向选项授权（`允许管理选项`）：query 出现对单选/多选字段**选项**的正向维护语义时（动词类「加选项/新增选项/增删选项/管理选项/维护选项/编辑选项」、限定类「只许新增选项/只能加选项/仅可维护选项」），落规范子句：

1. **唯一规范写法**：在承载字段所在表块内写 `允许管理选项 {字段名}`，这是正向选项授权的**唯一规范写法。禁止**拆成 `仅允许新增选项 / 禁止修改选项 / 禁止删除选项` 这类按动作拆分的细粒度子句。
2. **不抬表级、逐表收束**：`允许管理选项` 是字段功能维度，不抬表级；按承载字段所在表绑定，只写进该表块，不跨表复述。

记录新增/删除能力与字段级、记录级限制相互独立：字段级编辑范围限制、记录级行条件限制都不蕴含对记录新增、删除能力的限制。某可编辑表只有在 query 字面出现「不能/不可/不允许/禁止 + 新增/删除 记录」时，才在该表块写入对应的禁止新增记录/禁止删除记录子句。

表内操作约束逐表收束：同一角色的多张表块之间，表内操作约束按 query 字面解析的承载表分别绑定，**必须写在该表的表块内部**。不要因为同角色另一张表存在该约束就把该约束类推到本表。

### 3.7 仪表盘权限

命中仪表盘名 + 仅可阅读 / 可见 / 隐藏 / 不可见时，写入仪表盘权限块。仪表盘名同样必须按 §1 映射到 Base 快照实体。

除字面点名仪表盘外，当某角色的需求是「查看/只能查看 + 所有/全部 + 主题词X + (相关的)数据/内容」这类主题词限定全集 READ（§2.4 rule 4）时，仪表盘轴不能留空：对 Base 全部仪表盘名逐个做 `包含(X)` 判定，命中的仪表盘必须写进本角色的仪表盘权限块，按 READ 方向给「仅可阅读/可见」。

无主题词限定的全量数据 READ（§2.4 rule 2）同理处理，唯一区别是不做 `包含(X)` 过滤、Base 全部仪表盘逐个纳入并按 READ 给「仅可阅读/可见」。

## 新建角色分支

仅当角色为「新建」时适用。新建角色的核心是「用户点名的实体可授权，实体内部未点名子项按最小权限收束」。不要把本节用于更新已有角色。

### 4.1 表轴仍按点名收束

新建角色不会自动获得未点名表。表轴只按 §2 入选。关联表不连带，兄弟表不补全，已有表不枚举。

### 4.2 字段轴正向授权：降一档

query 对某表内具体字段做正向授权，并出现「仅/只/仅能/只能/仅可/只可」等排他词，或字段级等级低于表级时，按以下规则：

1. 阅读类动作 → L = 仅可阅读。
2. 编辑类动作 → L = 可编辑。
3. 管理/维护/配置字段 → L = 可编辑，字段对象不支持可管理。
4. 目标字段权限 = L。
5. 承载表表级 = L。
6. 同表未点名字段 = L 降一档：可编辑降为仅可阅读；仅可阅读降为无权限。

JSON 必须在该表的表块内写出「表级 + 目标字段 + 其余字段」三层。例：

1. 「能编辑{表}的{字段}」→ 表级可编辑，字段{字段}可编辑，其余字段仅可阅读
2. 「只能看{表}的{字段}」→ 表级仅可阅读，字段{字段}仅可阅读，其余字段不可见

表级与字段同方向同级仍按字段轴处理：query 已给表级可编辑、又点名字段 A 可编辑时，不要因方向相同就删字段子句、放开整表。仍按三层落笔。

#### 4.2.1 字段轴动作触发

即使 query 没出现排他词，只要某表块的需求文本字面包含 [动作动词] + [具体字段名 或 字段范围名词（§2.3.2）]，也视为字段轴意图，按本节三层结构落笔，并按 §4.2 偏序对其余字段降一档。

例：

1. 「{角色}录{表}的反馈内容」→ 表级可编辑，命中反馈内容的字段集合可编辑，其余字段仅可阅读
2. 「{角色}查看{表}的基本信息」→ 表级仅可阅读，命中基本信息的字段集合仅可阅读，其余字段不可见
3. 「{角色}给{表}的字段 X 打分」→ 表级可编辑，字段 X 可编辑，其余字段仅可阅读
4. 「{角色}可以编辑{表}的字段 X、字段 Y，但不能修改字段 Z」→ 表级可编辑，字段 X、Y 可编辑，字段 Z 仅可阅读，其余字段仅可阅读

承载表内字段名/范围名词若无任何命中，退回到只写表级权限，字段层留空。

### 4.3 正向授权 + 字段级否定

当 query 同一句或紧邻子句中先给出某表的字段轴正向授权（按 §4.2 / §4.2.1），后续紧邻出现「其他…/其余…/别的…/剩下的… + 不能看/不可见/看不到/不能编辑」这类 deny 复述时，该 deny 子句视为正向授权三层落笔中「其余字段」轴的字面复述，直接被表块内既有的「其余字段」子句吸收，不另起字段级 deny，不触发 §4.4 黑名单分支。

判定要点：

1. deny 子句紧邻同一角色段落内的字段轴正向授权，且承载表已被正向句字面绑定到具体单张表。
2. deny 子句的对象是「其余字段」语义概括（其他/其余/别的/剩下的 等指代词 + 范围名词或类指），不是 query 字面新点名的独立字段名，也不是另一张表的字段范围词。
3. 同时满足上两点时，deny 子句的语义合并进正向句的三层落笔，不再额外写字段级 deny 子句，也不把 deny 扩散到同角色其他表块。

边界：若 deny 子句字面点名了承载表之外的另一张表或承载表外的独立字段，deny 不再构成正向句三层的字面复述，按 §4.4 各自分支处理。

### 4.4 字段级否定：黑名单

query 对某表内具体字段做 deny（例如「不能编辑字段 X」「字段 X 不可见」「对字段 X 隐藏」），deny 不传染表级。按动作反推表级并只下调目标字段：

1. 禁止阅读/可见 → L_deny = 仅可阅读；目标字段 = 无权限；其余字段 = 仅可阅读。
2. 禁止编辑/修改/更新 → L_deny = 可编辑；目标字段 = 仅可阅读；其余字段 = 可编辑。
3. 禁止管理/维护字段 → 按禁止编辑处理。
4. 承载表表级 = L_deny。

JSON 必须写出「表级 + 目标字段 + 其余字段」三层。禁止用整表只读或整表无权限替代字段级 deny。本节仅适用于 deny 子句无法被 §4.3 吸收的场景。

#### 4.4.1 字段范围词 deny 的多表展开

query 中 deny 子句的作用对象是字段范围名词（参见 §2.3.2），且该范围词没有绑定到具体单张承载表、也不满足 §4.3 紧邻吸收条件时，按以下顺序处理：

1. 确定承载表集合：按 §2.3.2 承载表确定规则，把 deny 子句的承载表集合定为当前角色经字面表清单或经 §2.3.1 主题词展开而获得表级访问权的全部数据表，排除按 §2.1 整段不出现的未点名表。
2. 范围词展开：对承载表集合中的每张表，按 §2.3.2 展开范围把范围词展开为该表内字面或语义命中该范围的字段集合；按 §2.3.2 语义边界仅取原始信息字段。
3. 逐表落字段级 deny：对每张承载表，在该表的表块内按 §4.4 偏序写「表级 + 目标字段 + 其余字段」三层，表级 = L_deny，命中范围词的原始字段 = 目标字段等级，其余字段（含派生计算字段）= L_deny。
4. 单张承载表内无任何命中字段时，按 §1.2 跳过该表的字段级 deny 子句，该表的表块仅保留承载表表级权限，字段层留空。

字段范围词 deny 不允许退化为对任意承载表的整表无权限替代，也不允许只在最显著的一张承载表上落字段级 deny 而在其他承载表上漏掉。

### 4.5 记录轴部分授权

当 query 给某表写了表级权限 + 部分记录条件，且未显式声明「其余记录可查看/不匹配记录可阅读」时，未命中记录默认隐藏。按以下模板（均落在该表的表块内）：

1. 部分可编辑 + 其余可查看，仅在 query 显式说其余可查看时写：`可编辑, 仅可编辑{条件}的记录, 其余记录仅可查看`。命中即落 `其余记录仅可查看`（只读），**不得把其余记录配成无权限**。
2. 部分可编辑 + 其余隐藏：`可编辑, 仅可编辑{条件}的记录`
3. 部分可编辑 + 部分可查看 + 其余隐藏：`可编辑, 仅可编辑{条件A}的记录, 可查看{条件B}的记录`
4. 部分可查看 + 其余隐藏：`仅可阅读, 仅可查看{条件}的记录`
5. 全部可编辑/可查看：`可编辑` 或 `仅可阅读`，末尾不写「仅可」记录子句。

`其余记录仅可查看 / 可查看{条件}的记录`（rule 1 / rule 3）的写出条件——**只由本角色本表 query 里下列两类显式短语之一触发**：

- **局部其余可读**：其他/其余/别的/剩下的 记录 + 只能查看/只能看/仅可查看/仅可阅读/保持可见/还能看
- **全表可读**：可见全表/全表可见/全部记录可见/能看到全部记录/能看所有记录。与同一表的部分可编辑（或部分可查看）记录条件同句出现时，等价于显式声明「未命中记录至少只读可见」，按 rule 1 落 `仅可编辑{条件}的记录, 其余记录仅可查看`

两类短语都受同一反扩权约束：只绑定**最近的一个角色 + 表 + 记录条件**、**只消耗一次**，不跨角色/跨表传播。query 没有任一短语时，按 rule 2 / rule 4 未命中记录默认隐藏。

只读记录范围（只能看到/只能查看满足某条件的记录）即便同句带任何编辑类操作否定，也按 §3.3「正向目标定级、编辑类操作否定不抬级」走模板 4，不写成可编辑 + `仅可编辑{条件}` + 否定子句。

## 更新角色分支

仅当角色为「更新」时适用。更新角色的核心是「只写 query 字面修改项，未提及 = 保持现状但不写出来」，不要把 §4 的默认收束用于更新场景。但「只写字面项」不等于「从不收束」：排他、黑名单推定、承载表跃迁会按 §5.2 规则**算出**其余字段的连带变化，这类连带是规则结果、不是补未提及对象。

### 5.1 输出骨架与承载封顶

表级以下的一切变更（字段权限、行级条件、视图、增删记录、视图管理、选项管理、附件下载）必须收在对应表块内，不裸写。不要为了表达「未点名对象保持现状」而枚举该角色已访问的其他表；除非 query 字面点名「其他表/其余表/所有表」并要求保持或修改，否则 JSON 中不出现未点名表的任何表块。

**承载封顶（写表块前先查快照）**：可管理表挂不住字段/记录/视图等子权限粒度。该角色对某表当前是**可管理**、且本块要写任何子权限子句时，该块必须以 `表权限改为可编辑` 开头（可管理表配子权限必须先降到可编辑）。表块逐 (角色, 表) 实例独立生成：query 字面对称（所有角色/两个岗位都/所有表）不构成套同一模板的理由，每个实例各查各的当前权限。

### 5.2 表内子维度的三层裁定

更新表内任一子维度（字段/记录/视图）都按同一三层骨架：① 点名目标的新档、② 同层其余的处置、③ 表级承载。仪表盘/基础操作是角色级、无承载表，不走三层，按 §3.7 / §3.2 平铺。

每个**字段子句逐 (角色, 表) 实例算这三层。输入是从快照读到的两个当前值：表当前级**、**目标对象 X 当前级**。读 X 当前级时区分来源：快照中 X 的权限值 < 该表表级 = **字段层显式覆盖**，X 当前级按快照标注值算；否则 X **跟随表级**，X 当前级 = 表级。不允许统一回读表级当字段值。

先按触发词分流（语气词，定操作类型）：正向（能/可以/可/具有/拥有/允许/保留/仍可/仍然/继续/维持/沿用/不变）、负向（不能/不可/不允许/禁止/看不到；「X 不可见/不可阅读」等等级形容词作谓语同负向）、排他（只能/仅可/仅能/只允许/只保留/仅保留/仅显示）、局部覆盖（改为/设为，目标等级由字面给定）、反向（撤销/去掉/解除/取消/放开 → 走 §5.4）。动作方向（动词定等级，词表统一按 §3.3）：查看/阅读/浏览/访问/查阅 → 阅读级；录入/填写/编辑/修改/维护/更新 等 → 编辑级；管理表结构 → 可管理（走 §5.3）。

「只能看不能改」复合消歧：句中同时含「能看/只能看/仅可查看」与「不能改/不能编辑/不能修改」、且**字段名在前作主题（如「X 只能看不能改」「X 字段只能查看不能编辑」）时，按字段编辑限制处理（等同负向「不能编辑 X」）——走①负向编辑（X 仅可阅读）+ ②局部（同表其余保持现状）、表级不变，不按排他**。反之，**动词在前、字段作宾语**的「只能查看 {字段}」「只能看 {字段}」不走本条，按 ②-3 排他：目标字段仅可阅读、其余字段无权限；表级看句尾——带「不能编辑/不能改/不能修改」（未绑定到另一具体字段）= 整表只读信号 → 表级降仅可阅读，无此尾巴的纯「只能查看 {字段}」→ 表级按 ③ 承载裁定。

**① 目标字段定档**（点名对象 X 的新等级；纯查表；X 的等级只由触发词 + 方向决定，正向与排他在此层相同，差异全在 ②）：

1. 正向看 / 排他看（只能看）→ 仅可阅读。
2. 正向编辑 / 排他编辑（只能编辑）→ 可编辑。
3. 负向不能看 → 无权限。
4. 负向不能编辑 → 仅可阅读。
5. 改为/设为{等级} → 字面等级。

正向冗余短路：正向「能看/能编辑/保留/保持 X」且 X 当前已 ≥ 目标等级时，该正向子句整条不写，不进②③；严禁把「保留 X」改写成「仅可 X / 其余字段降级 / 其余不可见」（保留是维持现状、不收窄其余，不是排他）。

**② 其余字段定档**（同层未点名字段；按触发词；负向看 X 当前级判 deny 是否冗余）：

1. 正向（非冗余）、局部覆盖、负向且 deny 不冗余（X 当前仍高于 deny 目标 = 还能看/还能编辑）→ 其余字段**各自钉原档**，只动 X。「钉原档」= 逐字段照快照里该字段**当前实际等级钉死，不是凭直觉给「合理默认」：表升到可编辑时不得因「其余总得能看」就填仅可阅读；源表无权限 → 其余字段当前即无权限 → 钉原档就是无权限**，query 没要求让其余可见就不放开。
2. 负向且 deny 冗余（X 当前已 ≤ deny 目标 = 本就看不到/本就不能编辑）→ **黑名单推定**：其余字段升到该 deny 的正向等级（不能看 → 其余升仅可阅读；不能编辑 → 其余升可编辑）。即便同句还有正向子句，deny 冗余的「放开其余」压过正向的「钉原档」。
3. 排他（只能/仅可）→ 其余字段降到**严格低于 X 新等级**，原本已低于的保持现状（只能看 X → 其余无权限；只能编辑 X → 其余仅可阅读或更低）。
4. **同表多类白名单合成**：同一张表同时出现阅读白名单与编辑白名单时，名单外业务字段取两类「其余」的交集 = 无权限，即便 query 未显式说其他不可见；不得只应用一类把名单外留在仅可阅读/可编辑。
5. **白名单 + 独立黑名单混合**（同表既正向/排他点名某些字段 = 白名单，又**独立**点名某些字段 deny = 黑名单；黑名单须是字面新点名字段、非「其余字段」复述）：三组互不传染——白名单按①落各自目标档；黑名单只把**被点名字段自己降到 deny 档，不传染名单外**；名单外按 ② 第 1/2 条既有结论取档，**绝不被黑名单一起降成无权限**。字段自定义权限因白/黑名单开启后，名单外必须显式写 `其余字段 {档}`，留空会被下游漏配成无权限（缩权）或随新表级带高（扩权）。

示例（deny 翻转）：源表无权限、字段 X 当前无权限，query「X 不能编辑」→ X 本就不能编辑（deny 冗余）→ 黑名单推定其余字段升可编辑、整表升可编辑、X 仅可阅读。

**③ 表级定档**（承载先行）：承载下限 = ①② 算出的所有字段新等级里最高档（可管理封顶到可编辑），再跟表当前级比：

1. 表当前 = 可管理 → 目标 = 可编辑（挂子权限必降，承载下限更低也不向下穿透）。
2. 表当前 = 可编辑 → 目标 = 可编辑（保留，不向下跃迁到只读/无权限）；例外：排他「只能查看 X」句带整表「不能编辑」只读信号时降仅可阅读。
3. 表当前 = 仅可阅读 / 无权限 → 目标 = 承载下限（允许向上跃迁）。

表当前 = 目标 → 不写表级；不等 → 块内显式写 `表权限改为{目标级}`。表升档且②为「钉原档」时，其余字段原档值必须显式写出，否则被新表级默认带高 = 扩权；表降档时未点名字段跟随表级自动降，无需显式写其余字段。

### 5.3 表级正向与查看落点

query 直接说整表方向（不碰字段/记录子集）时跳过 §5.2 三层直接落表级：

- 编辑/维护 → `表权限改为可编辑`
- 明确管理表结构且不涉及任何子权限 → `表权限改为可管理`
- 查看/阅读/访问**整张表** → `表权限改为仅可阅读`（正向「能查看」与排他「只能查看」同等，源可编辑/可管理也降，不因「本就能看」保留）
- 仅当 query 字面「保持不变/不修改/沿用原配置/保留原权限/其他不动」绑定到该表级时，才写 `保持原有表级权限不变`
- 表级降级词「改为只读/降为只读/表权限改为可阅读/调整为阅读」直接指向表级 → 一律降可阅读

**查看落点是更新场景最高频的误判点**，按「查看」宾语判，不按带不带记录条件判：

1. **查看落表**：有独立的「查看/阅读 整表/A 表」、且**无任何 EDIT 方向动作**（可再叠加字段隐藏/视图可见性/记录阅读条件等阅读方向收束）→ 按上面降为仅可阅读，字段/视图/记录子权限都在降级后的只读表上承载，记录条件作可阅读记录范围。
2. **查看落记录/字段**：宾语是记录或字段、句中无独立的「查看整表」（如「只能看满足某条件的记录」「只看本人记录」「可查看字段 X」；「在 X 表中可查看…的记录」里的「在 X 表」是定位状语、不是查看整表）→ **不降表级**：源可编辑/可管理保留原表级 + 记录过滤（命中可编辑，落笔 `仅可编辑{条件}的记录`），源仅可阅读/无权限建立仅可阅读 + 记录范围（落笔 `仅可查看{条件}的记录`）。
3. **查看整表 + 同句 EDIT 动作**（如「查看 A 表，但能编辑 X 字段/维护 X 选项/管理 X 字段」）：「查看」是冗余表达，表**不压只读**——源可编辑/可管理**保留原级别**，源无权限/仅可阅读跃迁可编辑承载 EDIT；字段 EDIT 按 §5.2 三层配。判别：同句**只要含**字段/记录/选项的 EDIT 方向动作，EDIT 承载优先于「查看落表」的降只读。

示例（同字一降一留）：表当前可编辑——「可以查看{表}，只能看自己负责的记录」（查看落表）→ `表权限改为仅可阅读, 仅可查看负责人字段为本人的记录`；「只能看自己负责的记录」（查看落记录）→ `仅可编辑负责人字段为本人的记录`（表保留可编辑、命中可编辑）。

记录轴默认范围：**表为可编辑、query 只给可编辑记录条件、未提其他记录权限**时，可阅读记录范围默认与可编辑条件一致（命中可编辑、未命中无权限），只写 `仅可编辑{条件}的记录`——**禁止补「其余记录仅可查看」，更不得放宽为全部记录可阅读**（下游据此把未命中记录也设为可见 = 扩权）。`其余记录仅可查看`**只由本角色本表 query 里显式的「其他记录可查看/其余记录只读/不匹配记录可阅读」短语触发**；该短语只绑定最近的一个角色 + 表 + 记录条件、只消耗一次，**不得跨角色/跨表传播**。

### 5.4 反向操作

「撤销/去掉/解除/取消/放开」按字面写目标变化，落在该表块内，仍按 §5.2 ③ 检查表级跃迁：

1. 「撤销{表}字段 X 的不可见限制」→ `字段 X 改为可编辑`（或按 query 指定目标态）
2. 「解除{表}禁止下载附件 Y」→ `允许下载附件 Y`
3. 「去掉{表}行级条件」→ `移除行级条件`

## 冲突裁决与落笔规则

### 6.1 表级 + 子维度必须拆开

同一句需求里出现表级数据访问、字段权限、记录范围、视图管理、选项管理、基础操作、仪表盘权限等多个维度时，必须逐维度拆开写。不要把一个维度的 deny 扩散到另一个维度。

### 6.2 正向表访问叠加收束时必须显式写表级等级

同一表块里只要同时存在查看/编辑/修改/维护表内容或记录，以及字段不可见、字段只读、仅部分字段可编辑、视图限制或选项维护等子维度约束，JSON 必须在该表块**第一个子句**就写出表级等级词：

1. 新建场景：`仅可阅读,...` 或 `可编辑,...`
2. 更新场景：`表权限改为仅可阅读,...` 或 `表权限改为可编辑,...`

禁止写 `保持原有表级权限不变,...` 或省略表级等级直接进入子维度。源 Base 里的既有高权限只能作为冲突判断依据，不能覆盖 query 给出的正向等级。

### 6.3 承载一致性：表级必须 ≥ 该块字段最高档

字段权限挂在表级之上，**字段档不可能高于所属表的表级档**。落笔后若同一表块里某字段子句的档高于表级档（典型：`仅可阅读, 字段 X 可编辑…`、`无权限, 字段 X…`），即自相矛盾，必须消除——但**不要默认抬表级**，先回查 query 与上下文判断该表到底是什么意图，再二选一：

1. 该表本意就是表级那个档（如 query 把它归入「只读/仅可阅读」清单）→ 越级字段是误生成，把它降到表级档（或删掉该字段子句），表级不动。
2. 该表本意确实要承载更高的字段权限（query 对该表有对应的 EDIT/管理目标）→ 把表级抬到块内字段最高档（可管理封顶到可编辑），字段子句不动；抬表级只承载字段权限，不连带放开记录增删/视图/选项。

拿不准时偏向 rule 1（收窄），避免越权；抬表级只在 query 对该表有明确正向 EDIT 意图时才做。
