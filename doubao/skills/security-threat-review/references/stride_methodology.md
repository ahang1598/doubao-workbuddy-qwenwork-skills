# STRIDE 方法论

## 什么是 STRIDE

STRIDE 是由微软开发的威胁建模方法论，是六个威胁类别的首字母缩写：

| 类别 | 英文 | 中文 | 核心问题 |
|------|------|------|----------|
| S | Spoofing | 仿冒 | 是否有人可以冒充他人或系统？ |
| T | Tampering | 篡改 | 数据是否可以被未授权修改？ |
| R | Repudiation | 抵赖 | 是否可以否认执行过的操作？ |
| I | Information Disclosure | 信息泄露 | 敏感信息是否可能被未授权访问？ |
| D | Denial of Service | 拒绝服务 | 服务是否可能被耗尽资源而不可用？ |
| E | Elevation of Privilege | 权限提升 | 是否有人可以获得超出授权的权限？ |

## DFD 元素类型

数据流图（Data Flow Diagram）是 STRIDE 威胁建模的基础。标准 DFD 包含四类元素：

### 1. External Entity（外部实体）
- 位于系统信任边界之外的参与者
- 包括：终端用户、第三方系统、合作方、浏览器、移动设备、外部 API
- 用矩形表示

### 2. Process（处理过程）
- 系统中执行计算或数据转换的组件
- 包括：微服务、Web 应用、后台任务、API 网关、函数、守护进程
- 用圆形表示

### 3. Data Store（数据存储）
- 持久化或临时存储数据的地方
- 包括：关系数据库、NoSQL、缓存（Redis）、消息队列、对象存储（S3）、文件系统、密钥管理服务（KMS/Vault）
- 用两条平行线表示

### 4. Data Flow（数据流）
- 元素之间的数据传递
- 必须标注方向（source → target）和传递的数据内容
- 包括：HTTP 请求、RPC 调用、消息发布/订阅、数据库查询、文件传输
- 用箭头表示

### 5. Trust Boundary（信任边界）
- 不同安全级别区域之间的分界线
- 包括：公网/内网边界、租户边界、网络分段边界、DMZ/内网边界
- 用虚线表示

## STRIDE 适用矩阵

并非每个元素都适用于所有六类威胁。以下矩阵定义了每种 DFD 元素类型适用的 STRIDE 类别：

| 元素类型 | S | T | R | I | D | E |
|----------|---|---|---|---|---|---|
| external_entity | ✅ | | ✅ | | | |
| process | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| data_store | | ✅ | ✅ | ✅ | | |
| data_flow | | ✅ | | ✅ | ✅ | |
| service | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| component | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |

> **未知类型回退规则**：如果出现不在上表中的元素类型，回退为 `process` 类型并应用全部六类 STRIDE 类别。这样确保覆盖面不会被静默收窄。元素类型匹配时，先做 `strip().lower().replace(" ", "_")` 归一化。

### 详细说明

**External Entity（外部实体）**
- **Spoofing**：外部实体可能被仿冒（如用户身份被盗用、第三方系统被伪装）
- **Repudiation**：外部实体的操作可能被否认（如用户否认发起过某笔交易）

**Process（处理过程）** — 全部六类都适用
- 作为系统的核心计算单元，面临最全面的威胁面
- 包括身份认证、数据完整性、操作审计、信息保护、服务可用性、权限控制

**Data Store（数据存储）**
- **Tampering**：存储的数据可能被未授权修改（如数据库被篡改、缓存被投毒）
- **Repudiation**：数据修改操作可能被否认（如谁改了数据无法追溯）
- **Information Disclosure**：存储的敏感数据可能泄露（如数据库被拖库、备份泄露）

**Data Flow（数据流）**
- **Tampering**：传输中的数据可能被篡改（如中间人攻击修改请求/响应）
- **Information Disclosure**：传输中的数据可能被窃听（如明文传输被嗅探）
- **Denial of Service**：数据流可能被洪泛攻击阻断（如大量请求耗尽带宽/连接）

## 每类别威胁说明

### Spoofing（仿冒）
- 用户/服务/组件身份冒充
- 弱认证或缺失认证
- 凭证窃取（日志泄露、Referer 泄露、不安全存储）
- JWT/Session Token 伪造、重放、算法混淆（alg=none）
- 证书伪造、服务间无 mTLS 导致上下游被冒充
- 密码重置/OTP 暴力破解、特权账户无 MFA

### Tampering（篡改）
- 传输中或静态数据的未授权修改
- 缺失完整性校验/MAC
- 不安全反序列化（pickle、yaml.load、对象映射器）
- SQL/命令/Prompt 注入
- 非 TLS 或 TLS 校验不当的中间人篡改
- 未签名的固件/容器镜像/部署产物、可变的构建流水线

### Repudiation（抵赖）
- 关键操作（认证、支付、配置变更）未写入不可篡改审计日志
- 审计日志可被同一主体修改/删除，或缺少用户+时间戳+操作信息
- 共享服务账户掩盖实际操作人
- 跨系统事务无签名/可追溯请求链

### Information Disclosure（信息泄露）
- 密钥/PII 写入日志、错误信息、指标或 URL（查询参数）
- 明文传输或 TLS 校验被禁用/弱化
- 静态数据未加密，或密钥与数据同存/存入代码仓库
- 过宽的 API 响应/GraphQL 字段/批量赋值泄露不应暴露的字段
- 错误响应暴露堆栈跟踪、内部主机名、版本信息

### Denial of Service（拒绝服务）
- 无限制的资源使用：无请求大小/超时限制、O(n²)/ReDoS
- 公网或多租户端点缺失限流/节流/背压
- 连接/线程池耗尽、无界队列增长、缓存击穿
- 未清理的日志/上传/备份导致存储耗尽、无配额
- 不可信输入触发昂贵的 LLM/Agent 调用而无成本/循环上限

### Elevation of Privilege（权限提升）
- IDOR/缺失对象级授权（用户 A 访问用户 B 的资源）
- 角色/权限检查缺失或仅在客户端、管理路径访问控制失效
- JWT 声明篡改/Scope 膨胀/跨租户 confused deputy
- 错误配置的 IAM、过权限的服务账户、SSRF 访问内部元数据（169.254.169.254）
- 不安全默认值（admin/admin、调试端点、actuator/env 暴露）

## 威胁建模最佳实践

1. **先画 DFD 再识别威胁**：不要跳过架构梳理直接想威胁，确保覆盖所有元素
2. **按元素逐类分析**：对每个 DFD 元素，只分析其适用的 STRIDE 类别
3. **威胁要具体**：每条威胁必须描述真实的攻击场景，而非泛泛而谈
4. **带证据**：每条威胁应引用设计文档中的具体内容作为依据
5. **标注置信度**：基于证据强度标注置信度，区分已确认和待确认
6. **去重合并**：相似威胁应合并，避免重复
7. **聚焦高危**：优先分析和报告 critical/high 威胁
