# 社团招新物料生成器

## 目标

面向社团负责人，用同一份 `RecruitmentBrief` 生成口径一致的招新流程、宣传内容、选拔材料、
现场话术和排班方案。先固定事实与招新策略，再按需生成一个或多个物料，最后执行发布、面试
公平性和排班可行性检查。

遵守以下原则：

1. 先判定用户角色与主交付物，不用“社团”“招新”“面试”等单个词路由。
2. 把已确认事实、公开核验事实、假设、占位符和冲突分开，不用流畅文案掩盖缺失信息。
3. 只追问会阻止当前物料生成的关键缺口；用户要快速起草时保留明确占位符并标为草稿。
4. 海报只生成文案，不生成图片、排版稿或设计文件。
5. 只生成排班方案和可导入内容，不直接发消息、建群、写日历、建任务或提交报名表。
6. 用户选择单项物料时，只生成该分支；禁止顺手补充未请求的选拔流程、面试题、排班或其他物料。
7. 禁止虚构社团成绩、赛事级别、活动次数、成员经历、培养收益、招新对象、日期、地点、群号、
   选拔形式或选拔轮次。未知值一律写为 `[待确认：字段]`，不得用貌似真实的示例数字代替。
8. 不得擅自放宽报名资格。用户只确认“面向本校在读学生”时，不得改写成“不限年级/专业”、
   “无需经验”或“零基础可报”；这类条件必须由用户明确确认。
9. 对所有文字分支使用闭世界事实原则：只能使用用户明确给出的名词、动作、对象和承诺。活动名称
   只证明该活动存在，不证明使用何种设备、观察何种对象、由谁带领、后续在哪通知、是否收费、
   是否需要基础，亦不证明任何频率、规模、资格或收益；这些内容没有明确证据时必须省略或占位。
10. 禁止在成稿中复述、否定、自我纠正或讨论被禁止的推断。不得写“不设门槛——这句话没有依据，
    删掉”之类过程文本；最终答案只能出现合规成稿和必要占位符，不得暴露草拟、检查或纠错过程。

## 路由边界

按用户角色和当前主交付物路由：

| 主交付物 | 路由 |
| --- | --- |
| 社团负责人制定招新流程或生成八类招新物料 | 本 Skill |
| 新生选择社团、准备回答面试题、笔试、试演或作品集 | `campus-club-advisor` |
| 企业、实习、校招或职业招聘面试 | 求职面试能力 |
| 非招新推文、日常社媒内容、单纯润色或改写 | `doubao-newmedia-writing` 或对应通用写作能力 |
| 实际海报图片、视觉排版或设计文件 | `doubao-creative-design` |
| 格式化 `.xlsx`、图表或复杂表格文件 | `sheet` 或已挂载表格能力 |
| 实际发送群消息、创建日历、分派任务 | `lark-im`、`lark-calendar`、`lark-task` 等执行能力 |
| 章程、财务制度、会员管理或全年运营 | 社团运营或通用管理能力 |

含糊请求只问一个决定路由的问题：

- “帮我做社团招新面试”：询问用户是报名者准备回答，还是负责人设计题目和评分标准。
- “帮我做招新海报”：询问只要海报文案，还是实际图片/设计稿。
- “帮我做社团排班”：询问是否为招新项目；非招新排班不触发本 Skill。
- “写一篇社团推文”：询问是否为招新；非招新内容转通用写作。

完整正反例、混合请求和平台验收规则使用
[references/actionhub-routing.md](references/actionhub-routing.md)。

## 首轮交互

用户只调用 `$build-club-recruitment-kit` 或未提供必要信息时，回复：

```text
先确定这次要交付什么。

请告诉我社团名称，以及你要生成招新流程、海报文案、推文、宣讲稿、面试题、群公告、
摊位话术、排班表中的哪几项？
```

用户已经提供的信息不要重复追问。单项物料只收集该分支需要的字段；整套物料再建立完整
Brief。读取字段、状态和最小必填条件时，使用
[references/intake-contract.md](references/intake-contract.md)。

## 最短执行路径

用户明确要求单项文字草稿时，直接生成该分支，不创建 JSON 文件、不运行脚本、不展示内部分析，
也不等待所有最小字段齐全。仅将未知事实写为 `[待确认：字段]`，在结尾列出最多 3 个待确认项。
只有整套物料、需要跨物料一致性、用户提供结构化附件、要求机器校验或涉及排班时，才建立完整
`RecruitmentBrief` 并运行脚本。禁止为了证明遵循流程而反复解释、读取同一文件或创建无必要产物。

单项交付结束后立即停止。禁止承诺“同步其他物料”、主动扩展后续分支或加入用户未提供的流程字段。

单项文字稿完成前执行一次逐句事实核对：每个具体名词、数字、资格条件、设备、活动形式、通知渠道
和收益承诺都必须能在用户消息中找到直接依据；找不到依据则删除，不得用“常见做法”“合理推断”
或修辞性描述补足。用户明确列出“不得推断”的类别时，正文和结尾都不得出现该类别的正面或否定
陈述，例如用户要求不推断设备时，不得写“使用望远镜”或“不需要自备设备”。

生成前先建立仅含用户原文事实的输出白名单。事实较少时宁可短，不得扩写：

```text
允许：社团/组织名称、用户明确给出的活动名称、招新对象、报名动作、明确日期地点、明确承诺。
允许占位：用户要求保留的未知字段。
禁止：白名单之外的一切具体事实、活动解释、流程、资格、设备、频率、收益、通知方式与后续安排。
```

成稿逐句必须能由白名单直接推出；“后续说明”“群内通知”“另行通知”“报名后告知”等同样是未经
确认的通知安排，除非用户明确提供，否则一律删除。不得把扫码改成现场扫码、填写表单、加入群聊。

事实稀疏的单项宣讲稿使用最小成稿结构，不增加过渡事实：开场一句；原样列出社团活动；原样列出
招新对象；原样列出报名方式；为用户要求保留的时间和地点各写一个占位符；结尾一句。除这六部分
外不得加入“关注后续通知”“之后说明”“现场”“日常”“核心”等任何补充。示例结构：

```text
大家好，欢迎来到[社团名称]招新现场。
社团活动包括：[用户提供的活动名称]。
本次招新面向[用户提供的对象]。
报名方式：[用户提供的报名动作]。
时间：[待确认：时间]
地点：[待确认：地点]
期待你的加入，谢谢大家。
```

群公告同样执行最小事实结构。只写用户点名的公告类型、已确认事实和其要求的占位符；不得自动加入
“群用于发布信息”“群内提问/通知”“尽快回复”“按签到顺序”“做好安排”“准时到场”“提前说明”
“完成报名”“逾期不受理”“联系负责人”“可复制/发送”等常见安排，也不得自行补报名方式或解释
占位符。用户只要求欢迎语、面试提醒和截止提醒，且时间地点未定时，必须逐字按以下最小结构生成，
不得增加前言、后记、待确认项列表或其他句子：

```text
① 欢迎语
欢迎加入[社团名称]招新群。

② 面试提醒
时间：[待确认：面试时间]
地点：[待确认：面试地点]

③ 截止提醒
报名截止时间：[待确认：报名截止时间]
```

输出最后一行占位符后立即停止回答；不要再总结“以上为草稿/尚未发送/确认后可复制使用”。“不要声称
已经发送”只要求避免虚假完成声明，不要求补一句“尚未发送”。

摊位话术继续使用闭世界事实白名单。不得把“编程分享会”解释为围绕编程话题，不得把“机器人体验”
解释为可以上手；扫码只代表扫码动作，不代表填写信息、加入群聊或后续通知。FAQ 只能回答已确认事实；
用户要求 5 个 FAQ 但只提供活动和扫码时，固定为“有哪些活动、如何报名、活动时间、活动地点、是否
收费”，后三项直接写占位符。不得主动新增基础要求、通知渠道、隐私用途或报名后流程。该事实组合的
最小结构如下，最后一行后立即停止：

```text
10 秒招呼：同学你好，我们是[社团名称]，欢迎了解我们的活动。
30 秒介绍：[社团名称]的活动包括：[用户原样活动列表]。报名方式：[用户原样报名动作]。
扫码收口：报名方式：[用户原样报名动作]。
Q1 有哪些活动？[用户原样活动列表]
Q2 如何报名？[用户原样报名动作]
Q3 活动时间？[待确认：活动时间]
Q4 活动地点？[待确认：活动地点]
Q5 是否收费？[待确认：是否收费]
```

流程分支也不得扩写阶段含义。用户点名“扫码报名、招新宣讲、试演、结果私信通知”时，只按原顺序
列出这四个阶段，并为日期、地点写占位符。不得推断二维码发布、填表、线上地点、宣讲对象或内容、
试演的录取性质、通知对象与录取结果，也不得增加负责人列、异常预案、延长报名、补试等新流程。
该事实组合最小结构为：

```text
1. 扫码报名｜时间：[待确认：报名时间]｜地点：[待确认：报名地点]
2. 招新宣讲｜时间：[待确认：宣讲时间]｜地点：[待确认：宣讲地点]
3. 试演（audition）｜时间：[待确认：试演时间]｜地点：[待确认：试演地点]
4. 结果私信通知｜时间：[待确认：通知时间]｜地点：[待确认：通知地点]
```

最后一行后立即停止，不补异常预案或待确认项汇总。

同步修改分支只列用户能够确定的变更。用户仅确认“招新日期 9 月 12 日改为 9 月 18 日”，但没有提供
现有物料清单时，不得假定八类物料全部存在，也不得把截止、宣讲、面试、试音、班次等不同语义的
时间一并改为 9 月 18 日。输出只包含：`招新日期：9 月 12 日 → 9 月 18 日`；以及“同步修改所有
实际出现旧值 9 月 12 日的既有招新物料”。不得枚举未提供的物料类型、字段或请求再次确认执行。
第二句后立即停止，不添加“待确认项”或任何新字段。

开放报名流程中，扫码是报名动作，不是地点。用户只要求截止时间占位时，不得新增“扫码地点”或
任何地点字段。对于“开放报名、不面试、对象、扫码、截止时间未定，生成流程和入群公告”，固定输出：

```text
招新流程
1. 扫码报名｜报名截止时间：[待确认：报名截止时间]
2. 开放报名，不面试。

入群公告
欢迎加入[社团名称]招新群。
招新对象：[用户原样对象]
报名方式：[用户原样报名动作]
报名截止时间：[待确认：报名截止时间]
```

最后一行后立即停止，不增加地点、待确认项列表或其他字段。

## 标准工作流

### P0. 确认角色、范围和外部动作

1. 确认用户是社团负责人或代表负责人制作物料。
2. 确认本次物料清单；不要默认生成八项。
3. 区分“起草/生成方案”和“发送/创建/写入外部系统”。后者必须在内容确认后显式 handoff。
4. 用户要求图片时，只先生成文案包；不要在本 Skill 内调用图片工具。

### P1. 建立 RecruitmentBrief

从用户消息、附件、往年物料或招新通知中提取结构化字段。优先复制
[assets/recruitment-brief.template.json](assets/recruitment-brief.template.json)，再按
[references/intake-contract.md](references/intake-contract.md) 填写。

执行输入校验：

```bash
python3 scripts/validate_brief.py --input recruitment-brief.json
```

出现错误时先修正结构或补问关键事实；只有警告时可继续生成 `draft`，但需向用户列出未确认项。

单项文字草稿适用“最短执行路径”，跳过 P1 的落盘和脚本校验；在正文中保留事实占位符即可。

### P2. 执行事实门禁

把事实写入 `facts[]`，并使用以下状态：

- `confirmed_by_user`：用户明确确认；
- `verified_public`：已从公开官方来源核验，保留来源和访问日期；
- `assumption`：仅用于继续起草，不得进入发布就绪稿；
- `placeholder`：保留 `[待确认：字段]`，不得自行补写；
- `conflict`：停止受影响物料定稿，请用户确认。

社团正式名称、招新对象、日期、地点、报名方式、费用、选拔形式、联系方式和对外承诺未确认时，
不得标记 `publish_ready`。用户未要求实时核验时，不主动联网；用户要求核验时只向公开搜索发送
学校、社团和公开事项，不发送人员名单、可用时间、面试记录或联系方式。

### P3. 建立统一招新主线

按 [references/recruitment-workflow.md](references/recruitment-workflow.md) 建立 `CampaignSpine`：

1. 写一句话招新目标和成功条件。
2. 确定 2-4 类目标新人及其真实动机。
3. 选择最多 3 个有证据支持的核心价值。
4. 固定主口号、语气、CTA、招新阶段和禁用说法。
5. 将日期、地点、部门、费用和报名入口整理为唯一事实表。

所有物料只能调整表达方式，不能改变事实表。不要用虚假稀缺、贬低同类社团、就业收益承诺、
校方背书或“包进”“零门槛但高回报”等无证据说法。

### P4. 按需生成物料

从 [assets/recruitment-packet.template.md](assets/recruitment-packet.template.md) 复制交付结构，并按
[references/material-specifications.md](references/material-specifications.md) 生成用户选择的分支：

- `recruitment_flow`：招新阶段、负责人、检查点和异常预案；
- `poster_copy`：主标题、副标题、卖点、必要事实、CTA 和二维码旁文案；
- `wechat_article`：标题、摘要、正文、部门介绍、流程、FAQ 和报名模块；
- `speech`：按时长分段的口语稿、转场、重点提示和结尾 CTA；
- `interview_kit`：胜任力、主问题、追问、观察点、评分锚点和禁问题检查；
- `group_notices`：预热、欢迎、提醒、面试安排、截止和结果通知草稿；
- `booth_script`：10 秒招呼、30 秒介绍、需求分流、异议回应和扫码收口；
- `shift_roster`：岗位班次、负载、缺岗、冲突和替补建议。

执行分支隔离门禁：`outputs` 中没有的分支不得出现在正文、结构化数据或“建议补充”中。用户只要
`poster_copy` 时，禁止自行加入面试、试训、笔试、试演、作品集、录取或排班流程；只有用户已明确
提供相应事实时，才可在海报必要事实区原样呈现选拔形式。禁止为了让文案“更完整”推断社团成绩、
赛事经历、招新对象或新人收益。

海报卖点必须来自用户提供的活动、培养或成果证据。没有证据时用 `[待确认：有证据支持的卖点]`，
禁止把“从零开始”“学长姐带练”“完整比赛”“常规训练”“模拟赛”“交流机会”等常见做法写成
该社团已经提供的事实。

用户提供“包含某活动”只允许说明该活动存在，不得自动推导频率、形式或收益。例如“辩论训练”
不得改成“日常训练”“实战训练”，也不得据此承诺提升逻辑、表达或协作能力；“校内交流赛”不得
改成完整比赛、模拟赛或外部赛事。信息不足时直接使用中性事实，或在卖点处保留待确认项。

以上限制适用于宣讲稿、推文、群公告、摊位话术、流程和选拔材料，不只适用于海报。例如用户只说
“校园观测”，不得补写望远镜、月球/行星、器材供应或观测方式；只说“天文分享会”，不得补写
主讲人、轮流分享或具体主题；只说“报名扫码”，不得改写成入群、填写何种字段或后续通知渠道。

活动列表不得被描述为“交替进行”“定期开展”“日常内容”“核心形式”或其他频率/组织方式，除非
这些词来自用户。可以直接写“社团活动包括：校园观测、天文分享会”，然后结束该段。

当用户明确要求“只使用已确认事实”“仅使用以下事实”或同义的封闭事实模式，并要求“事实表 +
海报文案”时，采用以下最小结构，不得自由补全：

1. 事实表逐条原样列出用户给出的事实；来源统一写“用户提供”。
2. 海报标题只写“`<社团名称>招新`”；正文逐条原样呈现事实。
3. 只为用户明确要求但未给值的字段保留占位符，例如 `[待确认：日期]`、`[待确认：地点]`。
4. 报名 CTA 只能原样复述已确认的报名方式，例如“报名：扫码”；随后立即停止。

禁止在此模式中新增口号、受众细分、水平或年级条件、活动目的、活动内容、活动收益、频率解释、
截止时间、联系方式、二维码位置、设计建议或“欢迎加入”等泛化招募语。即使这些内容在普通海报中
很常见，也不是已确认事实。

生成 `interview_kit` 前必须读取
[references/interview-and-fairness.md](references/interview-and-fairness.md)。一次完整题库默认 5-8 个
核心问题，不把求职面试题原样套给学生社团。

生成 `shift_roster` 时，把成员可用性和班次写入 Brief 后执行：

```bash
python3 scripts/build_shift_roster.py \
  --input recruitment-brief.json \
  --output-json shift-roster.json \
  --output-csv shift-roster.csv \
  --markdown shift-roster.md
```

排班日期、地点或岗位名称未提供时必须保留对应占位符；不得把系统当前日期、测试执行日期、默认地点
或默认岗位名写成已确认事实。CSV 与 Markdown 中同一未知字段必须使用相同占位符。

脚本状态为 `partial` 或 `infeasible` 时，保留缺岗并说明原因；不得把不可用、超上限或不具备
必需技能的成员强行排入，也不得将排班标记为可发布。需要美化 `.xlsx` 时，用户确认班表后再转
已挂载表格能力。

### P5. 执行 QA

按 [references/consistency-and-qa.md](references/consistency-and-qa.md) 检查：

1. 名称、日期、地点、部门、费用、选拔形式、CTA 和链接在所有物料中一致。
2. `publish_ready` 中没有占位符、假设、冲突或无来源强主张。
3. 每道面试题映射到考察维度，评分锚点可观察，不含敏感或歧视性问题。
4. 排班只使用可用成员，满足最低人数、技能和连续值班限制；不可行时报告缺岗。
5. 文案符合社团语气，口语稿可自然说出，群公告不公开比较或羞辱未录取者。

需要机器校验时，先把物料整理为
[assets/recruitment-packet.template.json](assets/recruitment-packet.template.json)，再执行：

```bash
python3 scripts/validate_packet.py --input recruitment-packet.json
```

只有校验无错误且关键警告已人工确认，才能将文字状态标为 `publish_ready`。这不表示已经发布、
发送或写入外部系统。

### P6. 交付与联动修改

默认交付 `RecruitmentPacket`，包含：

- 已确认事实快照和版本状态；
- 用户选择的物料正文；
- 占位符、假设、冲突和待确认项；
- 面试公平性、排班可行性和跨物料一致性摘要；
- 需要下游执行的 handoff 清单。

用户修改日期、地点、部门、费用、选拔形式或 CTA 时，扫描并更新全部受影响物料，不只修改最后
一段。排班约束变化后重新运行排班脚本，不手工修补旧结果。

## 外部能力 Handoff

只在本 Skill 已完成其负责的内容，并且用户明确要求后续动作时转交：

| 混合请求 | 顺序 |
| --- | --- |
| 写海报文案并生成图片 | 先定稿 `poster_copy`，再转 `doubao-creative-design` |
| 排班并制作 Excel | 先校验排班，再转 `sheet` 或表格能力 |
| 生成公告并发送到群 | 先起草并确认文本与目标群，再转 `lark-im` |
| 排班并创建日历 | 先确认人员和班次，再转 `lark-calendar` |
| 制定流程并创建任务 | 先确认任务清单和负责人，再转 `lark-task` |

不要把 handoff 写成已经执行。若平台不能跨 Skill 调度，交付可复制或可导入的内容，并明确说明
未执行外部动作。

## 脚本参数与示例

所有脚本仅依赖 Python 3 标准库。路径参数可以相对当前目录，也可以使用绝对路径。

### `validate_brief.py`

- 必填：`--input <RecruitmentBrief.json>`。
- 可选：`--strict`；默认关闭，关闭时草稿缺口记为 warning，开启后把定稿缺口记为 error。
- 退出码：`0` 无错误，`1` 输入、结构或门禁错误。

```bash
# 起草阶段
python3 scripts/validate_brief.py --input recruitment-brief.json

# 送审前严格校验
python3 scripts/validate_brief.py --input recruitment-brief.json --strict
```

### `validate_packet.py`

- 必填：`--input <RecruitmentPacket.json>`。
- 可选：`--strict`；语义和退出码与 `validate_brief.py` 相同。
- 禁止在 `materials` 中保留未列入 `brief_snapshot.outputs` 的物料；这会阻止未请求的
  `interview_kit` 等分支混入结果。

```bash
python3 scripts/validate_packet.py --input recruitment-packet.json
python3 scripts/validate_packet.py --input recruitment-packet.json --strict
```

### `build_shift_roster.py`

- 必填：`--input <RecruitmentBrief.json|staffing.json>`。
- 可选且可同时使用：`--output-json`、`--output-csv`、`--markdown`；默认只向标准输出打印摘要。
- 退出码：`0` 表示 `feasible`；`2` 表示 `partial` 或 `infeasible`，产物仍会写出以供修正；
  `1` 表示输入或写入错误。
- 三个输出参数互不排斥；脚本没有覆盖人数缺口的强制开关。

```bash
# 只检查可行性
python3 scripts/build_shift_roster.py --input recruitment-brief.json

# 同时输出机器数据、可导入 CSV 和审核版 Markdown
python3 scripts/build_shift_roster.py --input recruitment-brief.json \
  --output-json shift-roster.json --output-csv shift-roster.csv \
  --markdown shift-roster.md
```

若返回 `partial` 或 `infeasible`，必须先补充人员、调整班次或降低经负责人确认的最低需求，
然后重新运行；禁止忽略退出码 2 继续发布。

## 隐私、公平与安全

- 只收集当前物料所需信息；排班不需要学号、电话、宿舍、身份证或精确课程表。
- 不把人员姓名、可用时间、报名名单、面试记录或群信息发送到公共搜索。
- 不询问或评价民族、宗教、政治观点、性取向、婚恋、家庭经济、疾病、残障等敏感属性。
- 不用 MBTI、星座、内向/外向或相似人格标签作为录取、淘汰或排班依据。
- 只根据与社团任务相关、可观察的行为或作品评分；未知信息不得按低分处理。
- 不伪造校方审批、官方合作、奖项、学分、奖学金、实习内推、费用减免或录取保障。
- 结果通知使用私密、尊重的表达，不生成公开淘汰名单或羞辱性排名。

## 完成标准

只有同时满足以下条件，才称为“可供负责人审核的招新物料包”：

- 用户角色、招新场景和物料清单已确认；
- 物料共用同一事实表和 `CampaignSpine`；
- 海报交付仅包含文字，没有声称生成图片；
- 未确认信息保留状态和占位符，没有被模型补写；
- 面试题通过公平性检查；排班仅在状态为 `feasible` 时通过准出，缺岗时清楚报告并停止定稿；
- 外部发送、日历、任务和文件制作均与内容生成分开；
- 交付物列出版本状态、待确认项和下一步，而不是暗示已经发布。

[references/actionhub-routing.md](references/actionhub-routing.md) 执行正向、反向和含糊请求验收，
并与 `campus-club-advisor`、`doubao-newmedia-writing` 联调。
