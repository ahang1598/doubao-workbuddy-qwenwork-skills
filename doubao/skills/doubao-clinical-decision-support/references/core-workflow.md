# 核心流程

本文件只定义端到端执行顺序。证据来源、检索工具顺序、预算和评价标准见 `evidence-standards.md`；附件读取见 `patient-upload-analysis.md`；图表规则见 `clinical-diagrams.md`；文档结构、链接、校验和交付规则见 `output-and-qa.md`。

执行原则：快速完成分流，不反复讨论任务模式；除非用户明确要求简短、精简或限定字数，边界不清时直接使用 `full_report` 并开始工作。

## 1. 判定任务归属

先判断用户最终要获得什么：

| 用户目标 | 路由 |
|---|---|
| 围绕具体患者或明确临床问题，获得诊断鉴别、检查路径、用药/治疗比较、安全性、预后或风险分析 | 继续本 Skill |
| 普通用户主动选择本 Skill，或明确要求循证、查文献回答其具体医疗问题 | 继续本 Skill；按任务复杂度完成快速回答或完整报告 |
| 直接查找或获取指南、共识、研究本身，或调研相关文献清单、证据脉络、研究进展、热点、里程碑、课题方向、研究思路、综述或引用清单 | 改用 `doubao-medical-literature-search` |
| 未主动选择本 Skill、未要求循证检索，主要询问上传体检、检验、影像或病理报告的异常含义、复查和就医沟通 | 改用 `doubao-medical-report` |
| 医生把报告作为复杂病例证据，并询问诊疗决策 | 继续本 Skill |

分流只看最终产物。“需要具体临床问题答案”只决定继续本 Skill，不决定后续 `response_mode`。普通用户主动选择本 Skill，或明确要求根据指南、研究或其他文献证据回答一个医疗问题时继续本 Skill；用户想直接查找、获取或整理指南/研究本身时改用文献检索 Skill。病例仅用于限定文献检索人群、用户最终要的是文献资料或研究调研时，也改用文献检索 Skill。普通用户入口只放宽触发条件，不改变报告受众：完整报告仍从临床团队视角讨论“该患者”或“该病例”。

继续本 Skill 后，用一句话锁定决策问题：

`在 {{病例条件或目标人群}} 下，{{方案/检查/用药/随访/诊疗原则}} 是否适合；与 {{对照方案或常规做法}} 相比，其获益、风险和证据边界是什么。`

## 2. 确定输入模式和交付深度

`task_mode` 只决定如何整理输入：

| task_mode | 判定 | 结构化方式 |
|---|---|---|
| `patient_case` | 有具体患者、病例资料、检查结果、用药、附件，或明确询问“这个患者/病例” | 提取病例要素、附件状态和会改变判断的缺失信息 |
| `clinical_question` | 无具体患者，但属于诊疗原则、鉴别诊断、检查路径、药物安全、治疗比较或指南冲突问题 | 明确目标人群、适用/排除条件、关键风险和问题边界 |

`response_mode` 只决定工作深度与交付方式：

| response_mode | 使用条件 | 交付 |
|---|---|---|
| `quick_answer` | 患者围绕自身情况进行自我问诊且未明确要求循证、查文献或完整报告；用户明确要求简短、精简、一段话、只给要点或限定字数；或背景信息少、问题简单封闭且不需要详细分析，例如固定权威条目或 1-3 个药品的简单说明书查询 | 1-2 个高价值检索/核验批次；聊天中给结论、风险和可点击来源 |
| `full_report` | 病例或背景信息丰富/完整；Query 较长；需要详细分析、多因素个体化判断、鉴别诊断、检查路径、多方案比较；医学关系复杂、高风险、指南冲突、需要多篇证据或正式产物 | 完成检索、筛选、原文阅读、证据综合、图表和目标文档 |

判定规则：

- 患者围绕自身症状、疾病、检查、用药或治疗进行自我问诊，且未明确要求循证、查文献、详细分析或完整报告时，优先使用 `quick_answer`；明确提出上述需求后，再按通常复杂度规则判定。仅做报告异常解读且未要求循证时仍按前述 Skill 路由处理。
- 用户明确要求简短、精简或限定字数时，优先使用 `quick_answer`。
- 背景信息少、问题简单封闭且不需要详细分析时，可使用 `quick_answer`；固定权威条目和简单说明书查询只是这类任务的例子。
- 用户希望得到具体临床答案，只决定使用本 Skill，不参与 `response_mode` 判定。
- 问题聚焦、只提出一个核心问题或 Query 表述较短，本身不构成选择 `quick_answer` 的依据；病例信息丰富、问题复杂或需要详细分析时，仍使用 `full_report`。
- 若患者年龄、合并症、器官功能、既往治疗、检查结果或风险偏好会实质改变答案，使用 `full_report`。
- 除上述情况外，出现任一复杂条件就使用 `full_report`。
- 一时无法确定时直接使用 `full_report`，不要在模式判断上消耗检索和交付时间。
- `full_report` 一经判定即保持到目标产物完成；用户未指定其他格式时，目标产物固定为 `lark-doc` 飞书文档。除非用户明确改变格式或要求改为简短回答，不得在检索、写作或创建失败后切回 `quick_answer`。
- `task_mode` 与 `response_mode` 相互独立：无具体病例也可以做完整报告，具体病例在用户明确要求简短时也可以快速回答。
- 表格请求按交付格式单独处理：用户要求创建表格、对照表、清单或矩阵但未明确指定 `Excel/xlsx` 时，目标产物固定为飞书文档，表格嵌入正文并配套结论、解释、风险和来源链接；明确指定 `Excel/xlsx` 时才交付电子表格。

## 3. 执行附件状态闸门

病例或问题结构化前，必须先设置 `attachment_state`：

| 状态 | 判定标准 | 动作 |
|---|---|---|
| `present` | 当前环境实际存在可读取的图片、PDF、Word、截图、影像文件、报告文件、本地路径或连接器附件 | 读取 `patient-upload-analysis.md`，评估质量并提取可用信息 |
| `none` | 没有真实附件；用户只粘贴报告文字、化验值、超声结论、病历摘要或自然语言描述 | 只按“用户提供的病例文字信息”处理，跳过附件分析 |
| `ambiguous` | 用户说“见附件/已上传”，但当前环境没有可读取文件 | 提示“未检测到可读取附件”，基于现有文字给条件性分析或请补传 |

硬性边界：

- 报告样文字、检查描述、化验数值和病历摘要不等于上传附件。
- `attachment_state=none` 或 `ambiguous` 时，不得声称读取附件、OCR、提取影像/报告或评估附件质量，也不添加对应空章节。
- 仅 `attachment_state=present` 时，报告才可加入“上传资料质量与病例提取”，并说明资料类型、日期、质量、关键发现、决策影响和局限。

## 4. 结构化临床问题

### patient_case

只提取影响当前决策的内容，不把病例原文重写成长摘要：

| 维度 | 内容 |
|---|---|
| 基本信息 | 年龄、性别、体重/BSA、妊娠/哺乳、就诊场景 |
| 疾病状态 | 诊断、分期/分型、严重程度、病程、当前关键矛盾 |
| 病例证据 | 症状体征、实验室、影像/病理文字、基因或评分 |
| 治疗与用药 | 既往治疗、疗效/不良反应、当前用药、过敏史 |
| 安全因素 | 肝肾功能、感染、出血、血栓、心血管风险和合并症 |
| 现实约束 | 可及性、费用、院内路径和患者偏好 |
| 缺失信息 | 会改变方案排序、安全边界或下一步检查的资料 |

缺失信息只分为 `必须补充`、`建议补充`、`可后续补充`。存在必须补充项时，可以给条件性暂定结论，但不能给确定性治疗指令。

### clinical_question

不硬填病例表，只明确：

- 目标人群和临床场景。
- 需要回答的诊疗、检查、用药、安全、预后或指南冲突问题。
- 证据适用条件与排除条件。
- 最可能改变答案的风险因素和 3-6 个待限定信息。

随后形成 1-3 个可检索子问题：

- 治疗、管理、预后问题使用 PICOTS。
- 病因或危险因素问题使用 PECO。
- 诊断问题写清目标疾病、待评价检查、参考标准、诊断性能和误诊/漏诊后果。

## 5. 初始化检索与证据记录

读取 `evidence-standards.md`，按问题复杂度设置 `search_budget`、`fetch_budget` 和停止条件；具体工具顺序及说明书检索规则以该文件为准。

`full_report`：

1. 初始化内部 literature-log CSV。
2. 先用 `general_search` 查找高质量中国指南、本土共识、国家/学会规范和必要国际指南，核对发布机构、年份/版本、适用人群和原文链接。
3. 指南/共识检索后，必须再用 `scholar_search` 检索相关系统综述、RCT、大型队列、诊断研究或其他高质量关键论文，丰富证据类型并核对指南依据。
4. 完成指南/共识和关键研究两类检索后，再判断是否已直接覆盖问题、关键风险是否清楚、是否存在会改变结论的冲突；信息足够时停止扩展。
5. 每轮返回后先筛掉明显无关、重复和低质量结果，再把拟纳入正文、图表、参考文献或保留为辅助参考的证据及时写入内部记录；保留 `evidence_id`、原标题、类型、期刊/机构、年份、级别、纳入理由和可访问链接，摘要或原文片段仅在实际取得时填写。

`quick_answer`：

- 仅查询 1-3 个药品的适应症、用法用量、禁忌、不良反应或特殊人群等说明书内容，且不涉及复杂病例、疗效排序或方案比较时，先用 `medical_search`；只保留带 `url/link` 的说明书结果。没有带链接的可用结果或信息不足时，再用 `general_search` 补充。
- 其他快速问题进行 1-2 个高价值批次，选用足以回答问题的高质量来源，不预设可见来源篇数；回答中提到哪个来源，就必须给出该来源的可点击 URL。
- 来源标题与检索结果结构化返回的 `url/link` 字段成对保留，不从摘要或正文手抄链接。渲染前先将缺少协议的完整域名与路径补成 `https://...`，再使用 `[来源标题](规范化后的 URL)`；Markdown 链接目标只允许以 `https://` 或 `http://` 开头，不显示裸 URL，也不额外打开或解析短链。
- 不为了凑轮次扩展检索。

执行过程中只报告一句必要状态；候选列表、初步梳理、todo、证据综合草稿、工具名称和中间推理均作为内部工作内容。

## 6. 筛选、精读和引用映射

`full_report` 按以下顺序执行：

1. 完成筛选和病例适配评价后，将纳入或保留为辅助参考的证据写入内部记录；`inclusion_reason` 合并记录核心/辅助用途、纳入理由、病例适配和主要局限，不另设筛选状态或适配性列。
2. 仅当已有信息不足以核对关键推荐、入排标准、效应量、亚组、禁忌或安全边界时，才在 `fetch_budget` 内定向阅读相关章节或表格；现有权威信息已足够时，不再详细阅读整篇指南或论文。
3. 在 `abstract_or_excerpt` 中记录实际读取到的推荐条文、摘要或关键结果短片段；没有可用内容时可留空。证据的核心/辅助角色按质量、来源权威性、问题匹配度和时效性判定。
4. 为每条纳入或辅助证据补齐除可选 `abstract_or_excerpt` 外的全部字段；`evidence_id` 首次写入时分配并保持稳定，不要重新编号。
5. 正文具体来源从内部记录的 `original_title + url` 生成可点击原标题或稳定简称；不得只写纯文本题名、编号、DOI 或 PMID。

`quick_answer` 优先结合足以回答问题的高质量来源，够回答即停止，但不预设可见来源篇数；回答中凡提到具体外部证据，来源名称都必须直接做成 `[来源标题或稳定简称](URL)`，不得遗漏。禁止引用或展示自媒体、营销软文、健康博客、问答社区、聚合转载、搜索结果页及来源不明页面。URL 取自检索结果的 `url/link` 字段；无 URL 的候选不得作为具名依据写入回答。生成最终草稿后逐项做格式检查：每个 Markdown 链接目标必须以 `https://` 或 `http://` 开头；发现 `](shturl.cc/...)`、括号中的 `shturl.cc/...` 或其他无协议域名时，先补 `https://` 并重新渲染，再发送。此处只检查格式，不做短链访问性核验。

## 7. 综合证据并直接回答临床问题

先形成条件性结论，再组织文档。结论确定性统一使用：`相对确定`、`倾向支持`、`存在争议`、`证据不足`、`不支持/需避免`。不得使用“强推荐”“强烈支持”“强烈建议”等高程度措辞，也不得输出替代面诊的确诊、排除诊断、停药、换药或手术指令。

“临床问题分析和解答”必须位于指南/共识和关键研究之前：
1. 直接进入分析，结合病例或目标人群及调研到的证据，详细、清晰、有条理地回答用户提出的问题；可按需要拆分临床子问题，不限制数量。
2. 对主要方案分别说明临床获益、风险、证据依据和适用限制。
3. 在合适的位置引用后文可点击的指南名、论文题名或研究简称。
4. 仅 `attachment_state=present` 时引用真实附件发现。

随后生成置于证据关系与决策逻辑之前的风险、安全性或临床管理章节，标题按用户问题和病例重点确定。可结合实际需要讨论重要风险、禁忌或安全条件，监测复评、协作或升级处置，以及可能改变判断或管理方向的缺失信息；不预设固定小模块标题、顺序或数量。

涉及多篇证据、多方案、证据冲突或复杂安全判断时，读取 `clinical-diagrams.md`：

- 证据关系思维导图以当前临床问题为根，分层表达病例线索、指南、研究、安全来源和临床判断。
- 决策逻辑图结合当前病例条件、关键缺失项和安全门槛绘制。
- 图表节点只能来自病例结构或已纳入证据；无附件时不得出现上传报告或 OCR 节点。

## 8. 生成、校验和交付

`quick_answer`：

1. 简洁直接回答核心问题，条目数按问题需要决定。
2. 给出必要风险和适用边界；仅 `patient_case` 列出会改变判断的缺失信息，固定条目查询不得虚构病例缺失项。
3. 回答中提到的每个外部证据均提供对应的可点击 URL，不限制来源篇数，不得漏链；禁止引用或展示自媒体、营销软文、健康博客、问答社区、聚合转载、搜索结果页及来源不明页面。发送前确认所有 Markdown 链接目标均以 `https://` 或 `http://` 开头，无协议短链先补 `https://`，不得以裸地址或普通括号文本输出。
4. 在收尾追问前写明：“免责声明：本回答仅提供循证医学信息参考，具体诊疗应结合患者实际情况、检查结果及院内规范，由负责医生综合判断。本回答不可代替医生诊断，请不要在未经医生确认的前提下，进行自我处置、用药调整，或据此判断就医时机。如有异常症状请及时就医。”
5. 无论任务类型，最后一句固定追问：“是否需要我进一步生成完整循证分析报告？”

`full_report`：

1. 读取 `output-and-qa.md` 完成目标格式路由；用户未指定其他格式时固定创建 `lark-doc` 飞书文档，普通表格、对照表、清单或矩阵仍在飞书文档中交付。
2. 先生成完整本地报告，再按 3 个 section 组织：
   - `section-1`：标题、总结论、病例信息梳理与临床问题、临床问题分析和解答。
   - `section-2`：按用户问题生成标题的风险/安全性/临床管理章节、证据关系与决策逻辑、指南/共识证据、关键研究证据。
   - `section-3`：证据覆盖、完整参考文献、免责声明。
3. 运行 `scripts/validate-report-whiteboards.js --attachments none|present <report>`；`ambiguous` 按 `none`。修复内容后重新渲染并复跑。
4. 飞书创建/回读、其他格式路由、正文链接、参考文献和最终回复统一按 `output-and-qa.md`；Word/docx 另读 `word-docx-generation.md`。创建失败时保留 `full_report` 模式并走完整草稿/重试兜底，不得用 Quick Answer 作为完成结果。
