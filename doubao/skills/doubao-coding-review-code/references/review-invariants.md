# 行为分析方法

只执行与变化形状匹配的方法。目标是产生可验证的执行轨迹，不是逐项输出检查表。

## 状态转移与发布

当变化读取或写入状态时，建立最小状态表：

```text
入口状态 | 操作 | 成功写入 | 失败前已写入 | 重试/取消 | 最终可见状态
```

检查成功、失败、部分成功、取消和恢复是否形成未定义、陈旧或不可恢复组合。共享缓存、索引、发布结果和完成标记只能在完整成功后可见；失败返回的 nil、零值或半成品不能覆盖最后已知正确值。把“本次调用返回错误”和“错误前改变了其他调用可见的共享状态”分开判断，前者可重试不能保护后者。

## 并发与检查后执行

出现计数、存在性检查、read-modify-write、锁、事务、upsert、缓存填充或共享集合时，必须写出两个执行者的最短交错。把锁、事务、I/O、await、重试和队列等待视为 stale-decision boundary：边界前作出的决定在边界后需要由同一保护域内的状态重新证明。

```text
A 读/检查 → B 读/检查 → A 获得保护并成功写回 → B 等待后获得保护
→ B 是否重查 → B 失败/重试写回 → 首个消费者看到的状态
```

确认锁和事务实际覆盖哪一步，进入临界区后是否重查，数据库约束是否真的表达目标不变量。分别完成“双方成功”和“先成功、后失败”两条最短轨迹；后者用于发现有效状态被等待者的失败结果覆盖。锁、事务、upsert 或 race test 的存在本身不是反证。没有具体交错，不得报告或关闭并发候选。

关闭一个 changed synchronization/state 候选前，逐项给出代码位置：

1. 进入保护域后重新读取决定是否继续操作的共享状态；
2. 只有完整成功的本次结果才能发布，失败保持此前有效状态；
3. 解锁后的消费者读取受同一同步协议保护；
4. 底层唯一约束、CAS 或事务表达的是业务不变量，而不只是消除 data race。

任一项不适用时写明原因；用具体保护证明 `safe`，用具体交错证明 finding。

## 修复完整性

当 diff 直接修改一个已失效的条件、锁、缓存、事务、错误恢复或资源协议时，建立修复差分：

```text
base 失效轨迹 → diff 试图新增的保证 → head 仍可达的最短反例 → changed 根因行
```

head 仍保留目标协议的反例属于 incomplete fix，即使 base 也能触发；它的审查对象是本次修复是否建立保证。只有反例与 changed protocol 无关、根因和修复都落在未改旧代码时，才作为无关旧问题关闭。PR 标题和注释只提供意图线索；changed control/data flow 与可达反例提供证据。

## 重试与捕获状态

对 retry closure、循环和补偿写出两次尝试：

```text
attempt 1 前输入 → 失败后留下的可变状态 → attempt 2 实际输入
```

检查捕获的参数数组、builder、buffer、请求对象和游标是否恢复；失败处理本身再次失败时，是否逃出单条处理边界、掩盖原错误或中断独立项。

## 异步、错误与时序

对新增 `async/await`、goroutine、callback、future、队列或动态加载写出：

```text
启动者 → 返回的句柄/Promise → 等待者 → 错误处理者 → 后续可见动作
```

检查调用方是否等待正确对象，集合是否在异步回调写入前已被快照，外围 try/catch 是否真的覆盖异步 rejection，失败是否从 best-effort 变为阻断主流程，邮件/事件/提交等后续动作是否早于必要副作用。

## 生命周期与资源

对进程、线程、连接、文件、锁、订阅和外部客户端写出：

```text
create → start/acquire → use → wait/join → timeout/cancel → terminate/kill → close
```

逐个检查正常、提前返回、异常和 deadline 耗尽出口。运行时具体子类决定类型判断是否命中；抽象父类名称不能代替实际构造类型。

## 外部协议、库与命令

参数形状、编码、命令语法、provider 能力或框架行为决定结论时：

1. 找到仓库锁定版本、实际实现、类型声明或官方语法。
2. 写出 head 传入的确切值、单位、顺序和类型。
3. 对照具体消费分支，而不是用另一个后端或相邻实现类推。
4. 静态签名或语法已经矛盾时直接登记候选；仍有歧义才运行最小只读探针。

同一抽象操作可能路由到不同后端；一个后端接受百分比，不证明另一个要求几何尺寸的命令也接受。

## 信任边界

对 nonce、state、token、签名、claim、header、metadata 和主体绑定写出：

```text
生成者/控制者 → 新鲜性 → 绑定的会话/主体/操作 → 验证点 → 首次安全消费
```

读取实际生成实现，不能因变量名为 state/nonce/signature 就假定随机或请求唯一。分别检查成功、恢复、直接访问、缺失状态和异常路径；复杂攻击链必须逐步证明每个权限和数据来源，不能用安全领域措辞填补缺口。

## 测试控制流与构建

- 按执行顺序应用 monkeypatch、mock、fake clock、sleep/wait 替换和 fixture；写出测试实际调用的对象、具体运行时类型和断言时刻。
- 区分“测试未覆盖”与“测试因为错误原因通过”。前者只进验证缺口，后者在能证明生产缺陷被隐藏时登记候选。
- provider、构造函数、绑定或生成配置改变后，读取实际依赖图或生成输入。声称编译失败前，使用语言规则、锁定签名或最小构建证明。

## 性能与规模

性能候选必须同时具备：当前可达调用频率、每次新增成本、能影响延迟/吞吐/内存/I/O/资源上限的规模，以及不存在主导性缓存或批处理保护。单次对象创建、重复缓存键、理论高 QPS 和纯复杂度增长不成案；先确认正确性和身份，再考虑性能。
