# 代码审查

执行只读、defect-first 的完整变更审查。先覆盖完整 diff，再用最短证据链核验候选；最终只报告当前可触发、可直接修复的真实缺陷。

始终遵守：

1. 审查 `base → head` 的行为变化，不把偏好、维护建议、测试缺失或未来风险包装成 finding。
2. diff 改变旧代码的输入、顺序、同步性、错误传播、可达性或消费者，使旧语句首次产生当前错误结果时，仍属于本次变更；不能仅以“根因原本存在”驳回。
3. 每条 finding 必须闭合：本次变化、当前触发、语言/运行时语义、首个错误消费者和最强反证。
4. 工具或辅助脚本失败一次后立即改用仓库原生命令或直接读文件；不要反复修复审查工具，也不要让辅助步骤阻塞审查与最终输出。
5. 正确性、错误传播、资源清理和 changed tests 优先于性能、容量、维护性与未改旧代码；前四类未关闭前，不展开后一类支线。

未经用户授权，不修改代码、安装依赖、切换分支、评论 MR/PR 或改变远端状态。内部覆盖账本和候选账本不输出。

## 1. 固定范围并覆盖完整 diff

使用用户指定的 base/head；未指定时从仓库状态推导唯一范围。优先用仓库原生 VCS 命令取得 revision、文件列表、统计和完整 diff，例如 `git diff --name-status <base>..<head>`、`git diff --stat <base>..<head>` 和 `git diff --find-renames --find-copies <base>..<head>`。不得因为 diff 较大或工具失败缩小范围。

范围无法唯一建立时输出 `unable`；关键内容不可读时继续审查可读部分并输出 `partial`。只有完整 diff 过长、需要分批时才读取 [范围与覆盖](references/review-coverage.md)。辅助脚本是可选的范围核对手段，不提供缺陷答案，也不是开始审查的前提。

按相关 hunk 合并行为组，并为每组在内部记录：

```text
位置 | base 行为 → head 行为 | 当前入口/producer | 直接消费者
     | 可观察结果 | mechanical/safe/candidate/gap
```

每个 changed file、hunk 和大型 changed declaration 都要有终态。纯格式、稳定生成物或一致机械替换只有在存在可复核依据时才标为 `mechanical`。不能因找到一个强问题而停止覆盖。

## 2. 从变化生成候选

对每个新增或改变的表达式检查适用项，不逐项机械执行，也不先围绕第一个显眼候选深挖。生产行为和同一行为组内的 changed tests 连续审查；不要先跨模块探索推测，再回头看直接测试。

### 值、身份与消费者

- 谁产生、写入或控制该值；缺失、畸形、历史数据、窗口外状态和 zero rows 是否当前可达？
- 计数、存在性、更新和清理是否描述同一对象集合、时间域与身份？
- factory、provider、adapter、mock 或进程工厂实际返回哪个运行时对象；类型判断、等待和清理是否命中该具体对象？
- builder、encoder、append/update 的结果是否进入最终返回值，还是随后被重建或旧对象覆盖？
- nonce、OAuth state、token、claim、header 等信任值是否由当前 producer 产生、每次不可预测、绑定正确主体/会话并及时失效？

### 调用、错误与时序

- base/head 的返回值、错误、副作用、执行顺序或同步性有何变化；哪个外层消费者首先观察到？
- 后台变同步、忽略错误变传播、best-effort 变阻断后，原成功路径是否仍能成功？必要副作用是否仍早于通知、提交或返回？
- 新增可失败调用若再次失败，会否逃出单项边界、掩盖原错误或中断其他独立项？外围 try/catch 是否真的覆盖异步 rejection？
- 不要在“缺少检查”处停止；继续追到现有 validator、存储层或外层错误处理，确认坏值确实被接受或消费。

### 状态、并发与重试

- 对 check/count-then-write、read-modify-write、upsert、缓存和共享集合，写出两个执行者读取同一旧状态的最短交错；核对锁内重查、事务、CAS 和唯一约束是否表达业务不变量。
- 分开核验调用返回错误和错误前发布共享状态；失败、取消或部分成功不得用 nil、零值或半成品覆盖最后正确状态。
- 对 retry/reentrant closure 写出前两次尝试，确认捕获的数组、参数、builder、buffer、请求或游标不会在 prepend/append/mutation 后累积。

### 测试与生命周期

- changed test 与生产代码同等审查。按 fixture、monkeypatch、调用、等待、断言和 cleanup 的真实顺序执行；测试缺失不是 finding，测试因错误原因通过才是候选。
- 新增 `sleep/wait/join` 时确认是否被 fake clock 或 monkeypatch，等待对象是否正确，deadline 后是否继续遍历并清理所有已启动资源。
- 对进程、线程、任务、连接和文件检查 `create → start → wait/join → timeout/cancel → terminate/kill → close` 的正常、异常和提前返回出口。
- 构建、依赖注入或生成失败必须读取实际消费者/生成图，并实际运行最小只读构建、类型或生成探针；仅看到 provider、签名或生成文件变化不能宣称失败。探针未运行或未证明失败时，该候选只能是 `gap`，不得出现在最终 finding 中。
- 可观测性名称、label/tag 和查询是数据协议的生产者与消费者；本次变化造成现有查询收不到数据是功能缺陷，不要仅因“只是指标”驳回。

候选一旦形成，登记：

```text
ID | semantic delta | 当前触发 | 待证消费者结果 | 最强反证
   | confirmed / rejected / gap / duplicate
```

## 3. 用最短证据链收敛

按风险从高到低核验候选，每个候选只追完成结论所需的最短链：

```text
base→head semantic delta → 当前 producer/入口 → 运行时语义或具体轨迹
→ 首个错误消费者 → 现有保护为何无效
```

根据主张补足硬证据：并发写 A/B 交错；retry 写两次实际输入；历史/缺失状态找 schema、迁移或 producer；异步追启动者、等待者和错误处理者；安全问题证明攻击者控制、越过保护和取得结果；测试问题列出实际 patch 顺序、具体对象及断言/cleanup 时刻。

只有动态 receiver、provider、资源 alias/handle 或运行时类型仍无法确定时，读取 [语义身份方法](references/semantic-identity.md)；只有复杂状态、异步、缓存、retry 或生命周期轨迹无法闭合时，读取 [行为分析方法](references/review-invariants.md) 的相关章节。不要为了“更全面”预先加载所有参考文件。

严格收敛：

- 同一候选连续两次定向搜索都没有获得新的决定性事实时，立即标为 `gap` 或 `rejected`，转向下一候选。
- 同一候选被反证后若已两次改写成不同风险（例如从正确性改成吞吐、再改成资源开销），立即 `rejected`；不要继续寻找能保留它的新叙事。
- 性能、容量和调优候选必须先在一次定向读取中找到仓库内的明确上限/延迟契约和当前规模后果；否则立即关闭，不继续估算或搜索相邻实现。
- 已由明确代码、契约或最小探针推翻的候选不得换措辞重新调查。
- 所有行为组和候选有终态后立即输出；不要再开性能、重构、死代码、命名或未来扩展支线。
- 性能问题只有在当前调用频率、每次新增成本、规模后果和缺少主导保护均有证据时才报告。

## 4. Finding 准入与定级

Finding 必须同时满足：本次变化引入/激活/明显放大；head 中触发状态当前可达；关键语义已确认；直接消费者收到错误结果；最可能的保护不能阻止；根因位置和最小修复方向明确。缺一项就继续核验、标为 `gap` 或删除，不能用高优先级补偿不确定性。

不得报告纯策略偏好、代码质量/维护性、死代码、重复常量、只有测试缺失、只证明行为变化或只有理论性能风险的问题。

- `P0`：几乎必然阻断主要运行，并造成广泛、严重且难恢复的后果。
- `P1`：明确当前路径造成严重安全、数据、功能或资源后果。
- `P2`：可复现的普通缺陷、边界回归或受限风险。
- `P3`：影响较小但客观存在且值得修复。

优先级不得高于已证明的可达性、影响范围和恢复成本。缺少实际构建、类型或生成证据的框架推断不得定为 P0；正文仍承认关键语义未验证时不得定为 P0/P1。

## 5. 输出

最终答案直接以 `## 问题清单（Findings）` 开始，标题前不输出计划、工具过程或总结。按 P0→P3 排序，每项包含：

- `[P#] 标题 — path:line`
- 最小触发条件与直接消费者看到的实际影响
- 足以独立复核的最小证据
- 最小修复方向

随后简述实际 base/head、覆盖文件以及会改变 finding 或 verdict 的验证缺口。验证缺口不能收纳被驳回候选、未来风险或额外建议。最后只给一个 verdict：`unable`、`partial`、`blocked`（P0/P1）、`changes_required`（P2/P3）或 `pass`。没有合格问题时，在标题下写“未发现由本次变更新引入且需要报告的问题”。不要输出候选表、扫描 ID、优点、过程复述、P4 或第二份总结。

提交前只做一次终检：完整 diff 是否覆盖；changed tests 是否已按真实 patch/等待顺序审查；每个候选是否有终态；每条 finding 是否同时写得出本次变化、当前触发、首个错误消费者和最强反证；构建/并发/重试/动态类型等强结论是否有相称证据。验证缺口若承认某条 finding 的关键语义、触发或影响尚未验证，必须删除该 finding，不能一边报告一边免责。任一为否就补证据、降级、删除或标记 `partial`，然后立即交付最终答案。
