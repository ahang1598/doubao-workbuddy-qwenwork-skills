# 产出规范：Excel / 图表 / 报告 / 看板

## 一、Excel 工作簿工程规范

工作簿的标准：**另一个人不需要问作者就能看懂、追溯、修改**。

### 结构

- 多 sheet 分职责：`说明`（数据来源/口径/更新时间/caveat）→ `原始数据` → `计算`（中间表）→ `Dashboard/结论`。简单任务可合并，但结论和原始数据不混在一张表里。
- 结论/汇总放最显眼位置（Dashboard 顶部摘要卡），不埋在表尾。

### 数值与格式

- 数字、百分比、日期一律存**类型化数值**，禁止存成文本字符串。只有真正的 ID（用户 ID/订单号）才存文本。
- 数字格式代码：计数 `#,##0`，率 `0.0%`（差异敏感的用 `0.00%`），金额 `"¥"#,##0` 或按币种，日期 `yyyy-mm-dd`。
- 列按语义对齐：文本左对齐、数值右对齐、日期显式格式。重要数值列禁止裸 General 格式。

### 公式可审计

- 用户需要可编辑模型时，派生值优先使用公式并把假设放独立单元格。大规模计算或静态审计结果可写入值，但须保留计算脚本、口径或可追溯中间表。
- 复杂计算拆助手列，一格一步；同一列的公式模式保持一致，能整列填充。
- 跨 sheet 引用用 `='Sheet 名'!A1` 格式。
- 交付前扫一遍 `#REF!/#DIV/0!/#VALUE!/#N/A`，检查区间引用有无 off-by-one。

### 可读性

- 表头样式和数据区分开；冻结首行/首列（大表必须）；列宽足够不截断。
- 条件格式表达状态/阈值/异常（优于手工涂色，数据更新后依然生效）；颜色必须承载含义，不做装饰。
- 只对有内容的区域设格式，别把样式刷到几万个空行。

### 写入与导入完整性

- 生成工作簿后重新打开文件，按稳定业务键核对源数据、计算结果和每个明细 sheet 的实际非空记录；样式、预留范围或界面显示的末行不能证明明细完整。
- 若再导入在线表格，必须从导入后的在线表格导出最终版本，把该导出文件作为 `delivery_guard.py` 的检查对象，并核对：实际非空业务键数、首条、末条、空关键字段数、最小/最大值、关键合计以及真实图表/公式对象数量。生成前本地文件通过不代表在线版本通过；导入成功只表示文件被接收，不表示全部单元格或对象已落地。
- 说明页、正文和文件名中的“共 N 条/完整/无遗漏”只能引用最终交付物回读得到的 N。若在线导入截断、公式不兼容或回读失败，应修复后重导，或直接交付已验证的本地文件并披露限制。

### 唯一计算源与多产物对账

- 逐句扫描用户整段请求，把字面约束写入 `delivery_contract.json` 的 `acceptance_items`；背景、核心问题、正文说明和输出章节都要扫描。`仅/只/固定/恰好/N 个/N 条/N 份/N 张`按 exact 检查，`至少/至多`按边界检查；未明确要求的内容不要擅自登记成硬约束。文件生成后运行 `scripts/delivery_guard.py --contract delivery_contract.json`，失败项必须修复最终文件并重跑。
- `delivery_contract.json` 必须声明 `target_scope`；存在明确规格、属性或对象范围时设 `required=true`，填写 `decision_target_quote`、`source.path/type/key_field/display_field`、`predicates[{field,op,source_quote,...}]`、`target_subset{path,sheet,rows}`、`decision_output{path,sheet}` 与 `decisions[{id,basis_scope,evidence}]`。`source_quote` 必须逐字来自决策目标原句；价格/销量/分数等 shortlist 规则另存，不能冒充目标资格。`decision_output` 只能指向直接回答该决策问题的最终区域，不得指向通用 TopN 候选池；若工作簿恰有一个名称明确含“建议/决策/行动/策略”或对应英文的 sheet，必须指向该 sheet。逐项登记推荐对象的 `key_value` 与原始命中证据。门禁须按稳定键回查源记录执行资格谓词，并用源记录的完整 `display_field` 在 `decision_output` 找到同一对象；人工填写宽泛搜索词、`eligible=true`、截断名、省略号或只在全局 TopN 表出现都不算证明。目标定价、区间和避开建议的 `basis_scope` 必须是 `target_subset`；全市场统计仅作背景。最终决策区不得让“避开/停止/排除”的数值范围与“入门/品质/主推/进入”的数值范围重叠；脚本会机械扫描此类冲突。确需重叠时，先用额外资格条件拆成互斥对象再分别表述，不能只写“差异化”。每个源表已有的关键指标 claim 使用 `authority=source_field`，同时提供 `source_lookup.path/sheet/label/value_offset`，让脚本从原始工作簿直接取值；禁止把人工填写的 `source_value` 当作已读取源表。
- 先生成规范结果表、关键指标注册表和统一参数表，再生成工作簿、文档、图表和摘要；各产物不得重新读取原始列并独立重算。
- 写入器按 `business_key + field_id` 取值，不按行位置、当前排序或展示名称取值。字段映射同时记录来源、单位、期间、情景 ID、聚合和空值规则。
- 每个产物生成后必须重新打开，从实际文件回读业务键、字段值、公式和值缓存；“文件已保存”不算验证。公式缓存为空、公式错误或结果与规范值不一致均不得交付。
- 对账同时核对“源值 → 计算值 → 产物回读值 → 摘要值”的键集合、字段集合、值、单位、期间和情景 ID。可转换为 CSV 时使用 `scripts/evidence_audit.py record-reconcile` 核对逐键逐字段值，而不只核对总数和合计。
- 所有摘要数字只来自最终产物回读后建立的事实清单；禁止在报告模板或最终回复中手填数字。文件内摘要与对话摘要不一致时修复并重跑，不能只改单侧。
- 最终事实清单采用 `metric_registry.json`，每项至少含 `metric_id、label、authority、source_value、computed_value、artifact_value、value、unit、period、source、artifact_source`。源表已有同名指标时 `authority=source_field`，不得用另算比率替换；派生指标用 `authority=derived` 并填写公式。运行 `scripts/final_facts.py` 后，最终回复只能复制该输出中的关键数字，不得再做口头换算。
- 用户要求“保留公式”时，交付后必须回读公式文本和计算值；若在线导入丢失公式，在线版本不得作为主交付，应交付已验证公式仍存在的本地工作簿，或修复导入方式后再交付。
- 情景参数至少记录 `parameter_id、scenario_id、value、unit、scope、evidence_type、source、version`；公式只引用参数单元格或参数 ID，不得嵌入魔法数。没有依据的参数只能写成条件式敏感性情景。

## 二、图表选型与规范

| 要表达什么 | 用什么图 | 要点 |
|---|---|---|
| 趋势 | 折线 | 时间点足以呈现趋势且不夸大稀疏变化；点少用数字卡片/分组柱 |
| 分类对比 | 柱状 | 无天然顺序就按值排序；标签长用横向条形 |
| 构成随时间变化 | 堆叠面积 | 关注总量时用；关注各系列轨迹时改多条折线 |
| 部分-整体 | 堆叠柱 | 饼图只在 ≤5 块粗略示意时用 |
| 分布 | 直方图 | 组间对比用箱线图 |
| 两变量关系 | 散点 | 观测足以支撑关系判断；小样本仅作描述并标注 |
| cohort 矩阵 | 热力图 | 留存三角矩阵标配 |
| 逐级流失 | 漏斗/阶梯柱 | 步骤名+转化率+流失量都标 |
| 增量分解 | 瀑布 | 仅当各驱动因子干净加总到总变化时用 |

规范：
- 每张图配一段解读文字（图说明"是什么"，文字说明"意味着什么"）。
- 标题中性描述，副标题写口径（时间窗/人群/过滤条件/分母）。
- 配色克制：中性灰底+一到两个强调色；正负值别依赖红绿，加符号和标签。
- 坐标轴诚实：柱状图 y 轴从 0 开始；截断轴必须显式标注。
- 双轴图默认禁用（误导重灾区），确要用则两轴刻度和颜色严格对应。

## 三、分析报告结构

先按复杂度选择结构：

- **L1 定向任务**：严格口径 → 主结果/最终计数 → 无法判断项 → 延伸项 → 数据说明。不要强制生成 Dashboard、图表或行动收益。
- **L2/L3 分析任务**：先在内部逐项核对用户问题。只有多附件、多角色阅读、问题较多或用户要求正式报告时，才显式展示验收项覆盖表；普通分析在正文中自然逐项回答。

```
1. 结论（2-4 条要点，每条加粗开头，直接回答用户问题+建议）
2. 关键数字表（现值、环比/同比、和目标/基准的差距）
3. 分析主体（按发现组织，不按分析过程组织；每节开头一句 takeaway）
   - 每个发现 = 结论 + 必要图/表 + 解读；只有包含推断、估算或不确定性时才标注证据层级
4. 数据说明（来源、口径、时间窗、质量问题及其对结论的影响）
5. 建议与后续（做什么、如何验证、还缺什么数据）
```

- 写给"只看前三行的人"：任何一节砍掉后半，前半仍然自洽。
- 禁止过程叙事（"我先尝试了 X 然后发现不对又…"），只写最终结论和支撑证据。
- 形容词换成数字："增长强劲" → "周环比 +23%，为近 12 周最高"。
- 报告可以简洁，但不能少答用户的验收项。证据不足时写“无法判断”，不能直接省略。
- 执行摘要只能引用最终违规数。候选多行数仅在用户要求或解释口径差异确有必要时单列，并明确其不等于违规数。
- 行动建议写清对象、动作、验证 KPI 和复盘条件；只有用户提供负责人或职责归属明确时才写负责人。预期收益需要基数、改善依据和公式；多个行动相加时还要去重。

## 四、看板（Dashboard）结构

四层布局，从上到下：
1. **Hero 指标**：3-5 个核心 KPI 卡片（现值 + 环比变化 + 迷你趋势），回答"业务现在怎么样"
2. **趋势层**：核心指标时间序列，回答"往哪个方向走"
3. **拆解层**：按关键维度（渠道/平台/地区/新老）的分布和对比，回答"差异在哪"
4. **明细层**：可查数的明细表，回答"具体数字是多少"

- 每层都能独立回答一个问题；默认视图不需要任何交互就能看懂大盘。
- 加 guardrail 指标位（质量/投诉/性能），防止只看增长不看健康。
- 标注数据更新时间和已知 caveat。

## 五、交付前自检清单

1. 建立关键数字清单：主结论、摘要、合计、比率、排序、目标和影响金额须标注源字段、公式或情景假设；有产物时最终值必须来自产物回读，而不是生成前缓存。无法追溯的决策性数字删除。
2. 关键数字用独立路径重算一遍（透视表 vs 公式、代码 vs 手算），对得上才交付。
3. 分类加总 ≈ 总计；率在 0-100% 之间；同一数字在摘要/正文/图/表里一致。
4. 先判断多来源关系：互斥同粒度分区才机械加总，重叠来源按稳定键去重或版本化，不同粒度分别报覆盖数；确定性脚本结果须回查源记录。
5. 图表逐张检查：除标题、坐标轴和标签外，还须重新打开最终交付版本确认真实 chart 对象数量达到要求；若交付在线表格，则先从线上导出再检查，不得只检查导入前本地文件。图片、水印、预留区域和“已生成图表”的文字不算图表。
6. Excel：无公式错误、格式类型正确、打开即见结论；逐行数据交付核对源、计算、本地文件与在线回读四层并抽查首尾，叙事型产物核对必答内容、关键数字和末尾完整。
7. 结论逐条问：证据在哪？属于哪层（事实/推论/推测）？反例查过吗？
8. 逐项核对用户问题：每项都有结论或“无法判断+缺失字段”，不得漏答。
9. 若发生连接、排序、去重或跨表取数，抽查高影响记录的稳定主键、展示属性和指标是否仍来自同一源记录。
