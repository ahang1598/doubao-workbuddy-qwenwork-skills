# 投放与运营调优的证据边界

只在任务涉及广告投放、搜索词、竞价、匹配、预算、否定或类似运营控制参数时读取。

## 四条硬停止线

任一建议触发以下条件时，必须停止该建议并改成补证或可逆测试；不能用未定义代理指标、平台机制或重命名口径绕过：

1. **配置证据门**：实际控制参数或状态未知时，不得把平均结果、建议值或同类对象参数当成当前配置，也不得给绝对值或百分比调参建议；先列出需要取得的当前配置，再依据可追溯证据定幅。取得配置后，相对试探幅度可来自用户风险预算、平台有来源的最小步长、同一对象在不同已知配置下的历史响应或既有实验。历史平均表现、不同对象之间的参数差异、“效率尚有空间”和无来源的“常规步长”都不构成幅度依据。
2. **目标损失门**：删除或大幅削减重要贡献来源前，量化它对主目标的直接损失、对护栏的改善及替代来源经调整后数据验证的承接能力。净影响无法界定或可能突破用户容忍度时，不得全量执行；不得通过重命名主指标排除将被损失的贡献。
3. **归因隔离门**：为了验证原因或动作效果，每个实验单元和观察窗原则上只改变一类变量。业务必须联合调整时可以执行，但记录完整变更包，并明确结果不能归因于其中单一动作。
4. **预测证据门**：缺少响应曲线或实验时，不得预测曝光、点击、订单、转化、成本率等行为结果的方向、恢复量、区间或时间，也不要在结构化计划的 `predicted_result` 中填写未来结果。直接算术应写成历史分解；敏感性只能写“若外部输入 X，则按恒等式得到 Y”，不能把历史占比、效率差或跨对象比较包装成行为响应模型。

按以下顺序执行，后一步不能替代前一步：

1. **定义主目标与护栏**：写清当前优先恢复或改善的指标，以及成本、转化、利润、合规等不能恶化到何种方向。长期效率目标不能覆盖用户当前明确的恢复目标。
2. **枚举时间数据**：检查所有日期/时间字段的唯一值、覆盖范围、各期行数和周期完整性。存在至少两个可比期间时，按最细且样本充分的粒度聚合核心指标，定位首次明显变化；不得看到“7天数据”等标题就把含多日明细的表当成单个汇总期。
3. **建立动作证据表**：分别记录实际配置/状态、用户明确执行的动作、建议表输出和未知项。建议值、平均成本、标签或用户笼统描述均不能伪装成已执行配置。
4. **对齐动作与断点**：比较动作前基线、动作时间和动作后窗口，并检查同期其他变化。只有时间、对象、方向和机制均吻合时才列“首要候选原因”；有对照或反事实证据时再升级为已验证主因。信息不足时给后台核验项，不拼接成确定故事。
5. **先恢复，再提效**：调整方案按“恢复主目标 → 控制护栏 → 提升长期效率”排序。每项建议都要写当前状态是否已知、预期影响方向、证据、观察周期和回滚条件。

- 严格区分后台实际配置与状态、历史结果指标、建议表或规则输出。建议值不等于已执行值，平均成本不等于当前控制参数；建立“业务对象 → 实际投放目标/配置项”的映射后再给精确改值。
- 平台机制只写可验证的影响方向，不臆造内部权重、学习周期或跨活动传导。不同活动之间的预算或流量联动，需要共享预算、状态和消耗证据；历史占比不能机械解释为动作后的同等损失。
- 历史 CPC、消耗、曝光或不同对象间的表现差，只是结果指标。没有后台 bid、预算和状态记录时，不得据此断言“竞价偏低/偏高”“预算不足”或把它们列为已观察到的原因；只能列为待核验假设，并明确需要取得的配置证据。低 CTR、高成本等表现也不能自行证明平台质量分、内部权重、学习期或流量惩罚机制；无可追溯平台说明或实验时，只描述表现事实，不编写机制因果。
- 否定、删除、停投等动作先核对对象类型、身份和平台支持的匹配语法，并列出该对象对**全部主目标和护栏指标**的历史贡献占比，不能只挑支持动作的花费或订单。若它同时承担显著曝光、点击、收入或学习样本，不得仅因效率差就整体移除；优先降低强度、隔离低效变体或分阶段测试，并保留对照和回滚阈值。明确无关、违规、欺诈或安全风险对象可直接阻断。
- 当主目标已经受损时，削减动作必须在 `objective_contributions` 中逐个填写它对
  `primary_objectives` 的历史贡献；数值未知写 `unknown`。只要对任一恢复目标仍有
  非零贡献或贡献未知，就必须按重要来源处理，不能用“订单为零”推出“对曝光、点击
  或其他目标无影响”。只有法律、安全、欺诈或用户明确禁止项可填写
  `direct_block_exception`，并附可追溯的 `direct_block_evidence`。
- ASIN、ID、品牌词或类似标识在否定前必须确认它是自有对象、竞品对象、客户查询还是投放目标，并选择平台实际支持的对象类型和否定方式；身份未知时只列核验动作，不执行否定。
- 需要验证根因或动作效果时，每个测试单元一次只改变一类变量；若业务必须同时调整，拆分对象或时间形成对照并记录变更日志。不能在同一天全量修改否定、竞价和预算后仍声称识别了单一动作效果。
- 收益、盈利和精确恢复量需要成本边界或响应曲线。缺少毛利率时不把低成本率称为盈利；缺少调整后逐日数据时，不给貌似精确的曝光、点击或订单恢复承诺。删除或大幅削减重要贡献来源即使写成“条件式”，也必须先在不削减原来源的情况下测试替代来源并取得调整后数据；只有承接能力达到事先声明的门槛，才进入削减阶段。先削减再观察、仅确认原对象仍在运行、效率偏低或身份无误，都不算事前承接验证。

## 完成前的最小答案合同

当任务询问“调整后为何变化”或要求具体改值时，最终答案至少包含以下四项；缺一项时继续取数或明确说明无法构造，不能用全周期汇总替代：

1. **时序证据表**：按可比期间列核心指标，至少覆盖变化前与变化后；若不能构造，列出实际发现的时间字段、唯一值和缺口，并把原因降级为候选。
2. **动作证据表**：对象、实际投放目标/类型、后台实际 bid/预算/状态、用户已执行动作与时间、建议表值；未知项必须写“未知”。历史平均 CPC 不得命名为当前 bid，也不得直接作为精确改值基数。
3. **原因表**：每个原因标记为已验证、首要候选或一般候选，并给出动作前指标、动作证据、动作后指标及尚未排除的替代解释。
4. **建议表**：每个动作列对主目标和护栏的影响方向、试验对象、一次只改的一类变量、观察周期和回滚条件。后台实际配置未知时，只给取数项、非数值的条件式分支和定幅方法，不给绝对值或百分比调参。

没有响应曲线或实验结果时，不把具体恢复量、订单量、成本率和完成时间写成预期或承诺；只保留方向、验证 KPI 与计算方法，或给出明确假设、公式和适用范围的情景测算。

### 强制运行决策检查

L2/L3 投放优化在输出具体建议前，必须把所有拟议动作写入一个临时 JSON，并运行：

`python scripts/decision_guard.py <plan.json>`

顶层 `context` 必须如实填写：

- `change_analysis`：任务是否涉及调整后、上线后、最近变化或断点归因；
- `actual_config_known`：是否已从后台或明确配置记录取得当前控制参数；
- `post_change_data_available`：是否有相关动作后的观测数据；
- `objective_impaired`：当前主目标是否已经受损；
- `primary_objectives`：主目标受损时，列出用户明确要求恢复的全部指标；
- `response_evidence_type`：`none` / `before_after_same_object` /
  `controlled_test` / `response_curve`；
- `time_window_type`：`point_events` / `non_overlapping_periods` /
  `overlapping_periods` / `cumulative_snapshots` / `unknown`；
- `time_fields_present`：相关业务记录是否有开始/结束或时间字段；
- 若存在时间字段，不得手工抄写或改写区间。先直接对每个相关源表运行
  `python scripts/time_window_audit.py <source.xlsx> --sheet <sheet>
  --header-row <表头行号> --start-column <开始列名> --end-column <结束列名>
  --output <audit.json>`，检查脚本输出。然后在 `time_source_audits` 中逐表填写
  `source_path`、`sheet`、`header_row`、`start_column`、`end_column`，
  并把 `time_record_count` 填为脚本读取总数。`decision_guard.py` 会重新打开
  源文件并复算类型；模型手填的日期列表不作为证据。不得只审计单日行、
  某个方便归因的 sheet 或选择性子集；
- `response_evidence`：若不为 `none`，写明同一对象不同已知配置的前后数据、
  对照实验或响应曲线；历史均值和跨对象差异不能填写为响应证据；
- 使用 `before_after_same_object` 时还必须填写
  `action_change_verified=true` 和 `action_change_evidence`；对象名称、
  创建时间或分组标签不能替代明确的参数变更记录；
- 使用实际配置、用户风险预算或平台最小步长作为幅度依据时，分别填写
  `actual_config_evidence`、`user_risk_budget_evidence` 或
  `platform_step_evidence`。

每个 action 至少填写 `name`、`phase`、`change_family`、`action`、
`execution_status`（`verify` / `conditional` / `immediate`）和
`impact_direction`（`none` / `increase` / `decrease` / `remove`），并按实际情况填写：

- `object_identity_known`；
- `absolute_target`；
- `relative_change`、`relative_basis_type`、`relative_basis_evidence`；
- `important_source`、`net_effect_evidence`；
- 对削减动作填写 `objective_contributions`；如适用直接阻断例外，再填写
  `direct_block_exception` 和 `direct_block_evidence`；
- `replacement_status`、`replacement_evidence_type`、`replacement_evidence`；
- `replacement_gate_required`、`replacement_test_plan`、
  `replacement_test_timing`（重要来源只能为 `before_reduction`）、
  `trigger_condition`；
- `predicted_result`、`prediction_kind`（`direct_arithmetic` /
  `behavioral_response`）、`prediction_basis_type`、
  `prediction_basis_evidence`。

若同一阶段因紧急业务需要联合调整多类变量，顶层同时填写
`phase_bundle_reasons[phase]` 和 `phase_bundle_attribution_limits[phase]`；
后者必须明确联合调整后不能把结果归因于其中单一动作。

只有脚本返回 `PASS` 的动作才能进入最终建议和周计划；返回 `FAIL` 时按错误修改计划并重新运行。然后先把最终答案写入临时 Markdown，运行：

`python scripts/final_advice_guard.py <draft.md> <plan.json>`

正文检查也返回 `PASS` 后才能提交。**提交时必须逐字使用刚通过检查的
Markdown 草稿全文，不得在最后一步重新压缩、摘要、改标题或改写动作。**
如果需要更短的回答，应先修改草稿并重新运行正文检查。最终答案中的动作不得超出
通过检查的 JSON；条件式动作不得在最终答案中改写为“立即执行”；实际配置未知时，
不能把百分比、绝对调参或“竞价/预算偏高偏低”的断言藏进动作名、触发条件、表格、
周计划或正文。两个脚本检查保持内部执行，不展示 JSON 或校验日志。
