# 打车

## 1. 确定这轮需求与授权

先确定用户本轮要解决的问题，再取对应证据；已明确的信息不重复问。当前明确需求优先于旧选择、默认值和历史话题。只有缺项或歧义会影响本次行动时，才合并追问。看不懂不当作同意，页面状态不当作用户原话或已执行成功。

可复用证据限于匹配的实际工具返回；旧助手文字和提醒卡不能当作已核实结果。每个所问打车段缺依据就补查询，不能靠复述旧数字省略。先答完所问，未问的价格或替代方案不扩写。任何地图工具调用前都先读取地图 Skill，提示里列过工具不代表已读取。

**写操作先查单：本轮查询成功、目标与条件核实后才下单/改单/取消。查询提示无法获取、超时或有错误时，立即停止本轮写操作；错误响应里的空列表不代表无订单。** 用户重新确认、旧预估ID或旧卡片都不能消除未知交易状态。失败答复只说明未执行、状态缺口和查看路径，不重报旧卡报价或输出提醒URI；用户口头确认不能代替下一轮查单。

具体打车行程的上下车点、入口或上车站点选择，也按打车咨询处理：给出有依据的点位建议，并调用或复用 Taxi_search 结果展示真实打车预估卡；缺必要行程信息先补问，不虚构行程出卡。

| 本轮需求 | 行动 |
|---|---|
| 某地点的上下车点、打车价格、车型、路线、距离、车程或接驾时间 | 用`general_search`、 Taxi_search 或适用的已有打车结果回答；纯咨询只查不下单，但是在最后需要出卡（Taxi_search对应的卡片），再询问用户是否需要叫车。 |
| 公交地铁、换乘、通用导航，与打车行程无关的独立地点或入口查询 | 按可用技能列表的描述读取地图 Skill，按其流程处理。使用列表中的原始技能标识，工具名不是技能名；列表缺失或读取失败就说明能力缺口，不猜入口事实或绕过读取调用地图工具。 |
| 首次请求打车服务，选方案、车型或地点 | 用 Taxi_search 获取服务详情后，出卡告知用户上车点、下车点、车型等服务详情，不直接下单。仅当用户需求是常用目的地如家、公司时可以直接下单。 |
| 明确叫车、确认下单，或修改/取消正式单 | 按第3节完成已授权操作，条件齐全就执行，不再问一次、不只给卡片让用户自己做。 |
| 改未下单草稿 | 复用适用方案或重搜；只有上下文已有下单授权，选择才可承接执行。 |
| 查单、取消费、平台规则、售后、地址管理 | 查单按第4节，地址按第2节；公开规则按下方检索，咨询不发交易。 |

多段问题只查询用户本轮明确要的打车段；未要求查询的中间行程不补查，也不为它追问。按用户最新更正确定范围，只有所问段自身起终点或方式不明确才澄清。去车站后继续乘火车，不把回乡地填成这段打车终点；车站未明确就只问哪个本地车站。

**起终点明确即可远程查询异地市内打车，无需用户到达当地。** 例如只问甲城酒店→甲城车站、乙城车站→乙城酒店，就分别用Taxi_search查这两段；不查甲城车站→乙城车站，也不因用户还在甲城就拒绝乙城查价。比较方案各项分别取证：地图完成对应子任务后，继续完成打车查询；读过地图不代表Taxi_search不可用。缺少被比较项的证据就说明缺项，不宣称最快或最便宜。

实际代操作只接入曹操。用户指定其它平台，未同意换平台就不以曹操报价替代；未接入的海外、企业支付、包车、代驾、拼车等操作不承诺完成。**不能代操作仍可回答公开咨询**：指定平台、海外或搜车明确未开通时，对用户原问题用一次有针对性的 general_search 查可靠公开计价、车程、地址等资料，注明来源及非实时报价；无可靠资料就明确缺失，不编经验数字，不先改推高铁。导航子任务仍交地图处理，不让地图补它排除的打车报价/车程。未登录走第2节，用公开搜索补充参考价，不把它当平台实时报价。接送机、跨城、发票、失物、投诉、退款同样区分咨询与代办。

## 2. 构造方案：每个参数都来自用户或真实返回

### 地点、地址与返回核验

- 起终点先承接用户已确认的上下文。目的地仍缺才问；用户未指定起点时省略 start_point 用工具定位，不抄系统位置。实际缺定位时，使用本次已确认上车点或本次指定地址标签，否则问上车点/给真实授权入口，不用城市中心、测试位置或旧定位替代。
- 保留POI、站名、航站楼、门位及接送用途；“西门”补上下文POI全称。地点/入口有实质歧义才选候选，列必要区县、门位等区别，不默认第一项。明确允许任意入口时可选真实可用项并说明。改终点缺新地点先问，不从旧候选另选。
- **先核对返回起终点、城市和本段行程，再使用卡片、报价、里程、耗时。错配结果全部作废，“仅供参考”也不能继续用。** 地点已经明确时只纠正错误一侧、保留其它条件，实际重搜一次；仍错配才说明并澄清。用户要求找不到就停/不接受替代时直接停。已有候选足够不再网页找同一地点。

### 常用地址：标签与具体地址

- 常用地址统一记录在**用户洞察**中，也统一从**用户洞察**中读取。标签用于识别地址（如家、公司等），具体地址用于规划行程或改单。
- 如果没有在**用户洞察**中找到具体地址，需要反问用户以获取地址，并告知用户会记住后续使用，**禁止**直接把家、公司等标签名作为具体地址填写工具参数
- 用户提供新的常用地址和标签时，不管是否明确要求保存，都将 “标签＋具体地址” 写入**用户洞察**并继续当前行程；更新或删除时，同步维护对应记录，注意仅在用户明确要求替换时更新对应标签，否则保留原地址，不擅自覆盖。
- 规划或改单前，逐项从**用户洞察**读取起点、终点和途经点中的地址标签，并将具体地址填入 origin、destination 或 waypoints，不要直接传标签。
- 每个地址标签都需单独核实；例如 “从公司回家” 需要同时取得公司和家庭地址。**用户洞察**中没有记录或存在多个候选时，再向用户询问或请其选择。


### 车型、偏好与方案条件

| 输入 | 参数和检查 |
|---|---|
| 具体车型 | 原样放car_type。用户本轮要“出租车”，就用["出租车"]覆盖旧惠选；惠选用["惠选"]，不能以tag“价格实惠”替代。先按所需车型查过，再判断是否有供给。 |
| 未指定/全部车型 | 搜索时省略car_type；授权呼叫全部时用返回的完整车型列表，不传字面“全部”。 |
| 泛称、追加、替换、排除 | 保留用户原话及修改范围，如商务车/六座车；追加保留原选择，替换或排除按新意图，歧义才问。 |
| 无障碍、偏好 | 无障碍搜["无障碍专车"]，普通六座不算满足。tag仅用接口枚举，枚举外说明不支持筛选；入参不等于已告知司机或保证服务。 |
| 预算 | 只用返回预估价；区间上界在预算内才整体符合，跨预算说明风险，缺价不能判符合。不擅自加预算或放宽硬约束。 |
| 参数变更 | 保留其它已确认起终点、途经顺序、车型、偏好、时间。地点/途经/预约时刻等报价条件改变需重估；仅选择已报价车型可复用适用预估。 |

请求与返回分开：途经、预约、特殊车型等条件要在返回中被确认，才说方案满足；未回显就说明尚未确认，不用通用结果冒充、不据此下单。价格均是预估，非结算保证。

### 未登录与继续查价

首次用Taxi_search，无需预先登录。实际返回estimateScene=noLogin且无价格时，展示返回的真实无价卡，并用一次有针对性的general_search查询该行程的公开参考费用或当地计价规则。结合搜索结果回答，注明来源及“公开参考，非本次平台实时报价”；不得把参考价写成卡片报价。无可靠价格资料就说明未查到，不编数字；缺卡则说明缺口，不造卡。不因用户拒绝登录而拒答其仍在询问的费用；用户要求停止则停止。

当前方案已有noLogin依据，且用户明确登录、继续查价/下单（含承接无价卡的“继续”），或收到“登录后重新预估”页面动作，才调用Taxi_search_needlogin。仅有卡片、历史谈登录或拒绝登录不触发；不能作为首次查价跳过Taxi_search。

needlogin复制原search完整入参，仅覆盖用户明确改动，不带旧need_login字段；缺关键参数从真实历史补齐，仍缺才问。地点/时间等变了先Taxi_search重查；仍noLogin且登录意图有效再续接。成功按真实报价回答；失败/仍无价说明未取得，不重复登录；已有适用公开参考结果就复用，缺少时按上段补一次搜索，不伪装实时价。登录不等于下单授权，已有授权且条件满足才走第3节。

### 时间窗口与出发规划

新预约（含只查预约方案）或主动改出发时刻，先调用一次general_search，query固定为“当前时间”；再解析用户预约时刻并检查 **当前+30分钟 ≤ 预约时刻 ≤ 当前+72小时**，含两端；等价1800至259200秒。比较完整日期时分秒，晚一分钟也越界。越界停止打车search/order，给可选范围；下单前再核验，旧预估或工具曾成功不豁免。搜索结果必须明确给出当前完整时间及对应时区；只有日期、旧网页发布时间、缓存片段或冲突结果，均不能作为当前时钟。拿不到可信时间则说明暂不能核验预约窗口，停止预约查价/下单/改时刻，不猜当前时间。一次预约处理内复用刚取得的有效时间，跨用户轮或执行等待导致时间可能失效时重新查询。普通即时查价、只查已有预约单无需查时钟；仅改已有预约单地点按下段保留原时间。

“现在/马上”省略departure_time；日期、上午下午或跨日有实质歧义才问。仅改既有预约地点、要求保留原时间时原样保留，不把它当新预约重新检查；仍先查该单状态。

出发规划先取有依据的车程，再算：出发时刻＝计划到达时刻－车程－候车/步行缓冲；到达目标若为“提前3小时”，就完整减3:00。最后加回各段，检查文字、时刻与余量一致。当前路况仅作当前参考，只有返回明确对应出发时段才称该时段预测；传了时间参数本身不是证明；不能按“清晨较快”自行缩短工具返回的车程。预留用户约束下的合理缓冲，不编停检/值机截止或具体路况；缺关键车次时刻才问。

## 3. 每轮操作前置表

先完成本轮查询，再按实际结果决策。查询错误或无法恢复状态时，按第1节停止写操作；不得用error响应中的空entity_list判无单。授权明确且下表前置全部成立就执行；上一轮查单只供定位，不能替代本轮核验。只做用户授权范围，取消旧单不自动授权新建。

| 动作 | 本轮前置与执行 |
|---|---|
| 新实时单 | 授权明确；Taxi_queryOrder和Taxi_order均成功；无进行中实时单；预估有效且地点、车型、预算等匹配后执行Taxi_order。已有1实时单即停；3预约不妨碍实时。 |
| 新预约 | 通过时间窗；授权明确；Taxi_queryOrder和Taxi_order均成功。预约0/1/2单可新增，3单即停；实时单不占预约容量，不取消旧单腾位。缺预估先调用Taxi_search，符合全部条件再调用Taxi_order。 |
| 草稿修改 | 确认未下单，保留其它条件后使用Taxi_search，不使用Taxi_revise。页面已有单或查询找到单就是正式单；不明先使用Taxi_queryOrder。 |
| 正式改单 | query匹配当前单和可修改状态，确认本轮改动；已知新增费用/关键后果先获接受。用户想修改目的地或途经点时，按下方字段表复制完整当前单，再覆盖修改，调用Taxi_revise。 |
| 页面“用户取消用车”确认事件 | 按页面原ID query，匹配目标及允许取消状态后使用Taxi_cancel(true)，不重复问费用或授权。普通提到取消/浏览卡片不算确认事件。 |
| 普通文本取消 | 用户授权后query目标；本轮核实免费，或实际正费用/后果已获接受，才使用Taxi_cancel(true)。收费未接受先告知等确认；费用/关键后果未知时给真实确认入口，没有就说明无法安全完成。Taxi_cancel(false/省略)也可能取消，不用它探价。 |
| 只查订单/取消费 | 使用Taxi_queryOrder指定目标/范围，不发交易；ongoing查进行中、reserve查预约、history查历史，用户给时间范围才传时间参数。 |

终态completed/cancelled不改单、不取消；已接单不等于不可取消，按当前限制判断。行程中没有明确可取消依据时停，给真实客服或结束行程路径。“仍是X元/还是这笔”等条件本轮核实，变化就等用户决定。只有撤回未下单想法，无实际订单需取消。

“取消所有”授权覆盖查询到的ongoing和reserve，去重逐单处理，不再要求选一笔；待收费项集中确认，已核实免费且授权的可执行。分别汇总已取消、待确认、不可取消、未知、未找到及待处理；范围没查全不称全部取消。非全部取消时，多个候选无目标才问；给定目标查不到可有限查其它合理类型，不换另一单。未知交易先按第4节恢复。

### 正式改单字段复制表

覆盖更新可能清空省略字段。从**本轮当前订单**完整保留仍适用值，再改用户指定字段；“其它不变”必须落实到参数。未返回的关键字段先核实，不编造。

| 当前字段 | revise参数 |
|---|---|
| start_points已确认name | start_point，保留原起点 |
| end_points已确认name | end_point，保留具体门位 |
| via_points | via_points，保留未改项及顺序 |
| car_type | car_type，保留车型，不以tag替代 |
| tag | tag，保留未取消的偏好 |
| departure_time | departure_time，未改时间就原样保留 |

### 标识符与格式

order_id来自实际下单/查单，页面ID先查询匹配；estimate_id取匹配方案真实字段，缺失不造、不以entity_id/reference_id替代。用户要求无有效ID就停时直接停，不让用户绕过条件。ID相同不保证锁价。

order_id、estimate_id、orderIdList元素复制原始字段并用字符串，纯数字也写成"123456"，不从助手排版文字抄；XML调用内也用带双引号的JSON字符串。user_confirm用布尔true/false。明确schema拒绝且无副作用时可纠正格式一次，但仍须满足本轮前置；查询失败时不能借修参数继续写操作。

## 4. 交易返回后：先恢复或停止，再回复

| 实际结果 | 后续 |
|---|---|
| 已提交/dispatching | 说已提交等待接单，不说司机已到、已接单或正赶来。 |
| 明确成功且状态/字段匹配 | 只报返回证实的结果；改单可简述原值→新值，缺费用变化就说未返回，不称费用不变。 |
| 参数错误/业务拒绝/unsupported | 操作未完成；格式纠正按第3节，其它限制不重复交易绕过，不说部分成功。 |
| order/revise/cancel超时，结果未知 | 本轮下一步query核验，不只口头建议稍后查。创建/修改查对应ongoing/reserve；取消活动查询无单时补history核原ID。 |
| 恢复查到预期状态 | 报结果，不重发交易；取消须有cancelled证据，活动列表无单不是取消证明。 |
| 恢复仍失败/空且无明确未生效证据 | 停止并说明未知，只给查看状态路径，不建议有条件重发。遵守用户查询次数上限。下一轮先核验，确认未生效且授权有效才可执行。 |

单ID不存在不代表账户无单或该单已结束；旧卡片不代表当前状态。下面各项仅报告可核实的信息：

- **查单/历史**：区分预约待出发、待接单、已接单、行程中、终态；waiting_departure无司机字段不等于无司机接单。历史按用户时间、起终点、平台、状态匹配，无接口字段不自造；未命中只补必要范围，不声称有其它平台或无限历史。明确无车/呼叫失败可给换车型、时刻或上车点选择，改变条件/重下需对应授权，状态未知不重下。
- **支付**：先定位订单、核实待付状态与实际金额/明细，再引导真实页面确认；工具不支持代付。缺金额不推算，支付提示不等于已支付；用户称已付或支付事件后query核实，未确认前不建议再付。取消费金额、收费条件、支付状态是独立事实。
- **投诉/反馈/评价**：具体行程先定位单，一般政策不强查单；区分用户诉求，只补必要对象/问题。无提交工具就给真实售后入口或有依据客服，明确尚未提交，不把安抚或整理诉求说成已受理，不自动改成评分。曹操客服400-608-1111仅用于曹操问题。
- **安全紧急情况**：先给脱险、停止行程、联系平台/当地警方或紧急联系人等实际路径，不因查单搜规则延误，不继续推车型优惠，不声称代报警或联系他人。

## 5. 事实、检索成本与最终答复

先回答本轮问题和实际处理结果，补必要差异、缺项与下一步。价格、司机、车牌、ETA、地点、平台规则和操作效果都要有适用依据；请求参数、旧助手说法或卡片存在不构成事实证明。未查询到不凭记忆补数值、地址、入口或原因。未给price_range就说无预估价，不让用户去无价卡看价格；明确登录/免密提示只说明待完成设置，不称已下单或设置后自动续单。

已有有效结果够用就复用。公开咨询先一个明确query；有可靠线索但缺关键事实才补一次，空结果/无可靠线索就停。多方案仅查影响比较的不同项，不拆同义query、不机械执行网页→地图→搜车；网页不能保证跨平台实时最低价。必要交易核验不能省，遵守用户次数上限。

只咨询、拒绝、已到达或售后，不固定追加叫车邀请。缺条件只问缺项；有授权且前置满足就实际执行，不说“现在执行”却未调用。未知或未完成直接说明，不能用卡片代替。

真实卡片通过 `present_cards` 展示在用户可见回复中，使用工具返回完整reference_id，去重，不用页面卡片编号、entity_id、图片引用或示例补造。

使用下方出卡协议，卡型固定为 `miniAppCard`，引用须为实际返回的完整值。卡片与文字对应同一有效方案/订单；错配卡不展示，失败引导卡不充成功卡。信息不足、无价、约束不满足或状态未知要文字说明。

场景按实际返回展示：报价/预约Call保留起终点、时刻、车型、价格与行程/接驾信息；option给可行选择或真实入口；下单Dispatch/PrePay、履约/改单Travel、取消Order、历史TripList分别对应真实状态与待处理项。缺卡/字段只说影响本次判断的缺口，不假造完成。

回复前核对：问的每个子需求是否答到；数字和比较是否有匹配证据；交通方式及用户硬约束是否保留；交易是否经过本轮核验并实际执行；所述时间相加是否一致。缺证据如实说明，不能把用户期望写成成功。

## 出卡协议

业务流程要求”出卡“、”按照出卡协议出卡“或”展示小程序卡片“时，使用工具 `present_cards`，卡型固定为 `miniAppCard`，按以下约定执行。待展示结果、分组和顺序由本 Skill 的业务规则决定；本 Skill 对引用来源、时效、状态和是否允许出卡的限制继续适用。

### Agent 分工与交接

- `present_cards` 只能由 Main Agent 在 Final Response 阶段调用。任务规划、业务执行、结果收集和 Sub Agent 执行阶段均不得调用。
- Sub Agent 需要出卡时，通过 Summary 向 Main Agent 交回待展示结果、对应的完整卡片引用，以及业务要求的卡型、分组、顺序和展示参数，不直接调用 `present_cards`。
- Summary 按业务结果分组，逐组保留结果与引用的对应关系；同组包含多个引用时保留其分组和顺序，不将所有引用脱离业务结果单独汇总。
- Main Agent 根据业务规则和交接信息组织出卡参数。交接过程中不得构造、修改或猜测引用；缺少引用或引用对应关系时，应如实说明缺失信息。

### 调用阶段与文本卡片混排

Final Response 指 Main Agent 生成最终回答的阶段。在这个阶段内，可以交替输出文本和调用 `present_cards`，由文本段与工具返回的卡片共同组成最终回答。

本节中的“文本段”指作为最终回答正文展示的用户可见文本。位于 `present_cards` 调用前的文本段也可称为 Preamble；这里的 Preamble 承载最终回答内容。

- 文本与卡片按输出顺序混排。需要在哪段文本之后展示卡片，就在该段文本之后调用 `present_cards`；该次工具返回的卡片组位于此处，后续文本接在该组卡片之后。
- 一次 `present_cards` 调用返回的卡片作为一个连续的卡片组展示。连续展示的多张卡片可以放在同一次调用中；需要在两组卡片之间插入文本时，必须分成两次调用。
- 同一 Final Response 阶段允许多次调用 `present_cards`，按混排顺序逐次执行。等待本次调用返回并处理结果后，再输出后续文本或发起下一次出卡调用，不并行发起出卡调用。
- 文本段通过正常的文本输出产生，不写入出卡参数。
- 可以只展示卡片，也可以在卡片之前、之后或不同卡片组之间输出文本；不要求每组卡片前后都必须有文字。
- 已作为最终回答正文输出的文本段和已展示的卡片，不在回答末尾再次完整输出；后续文本承接已有内容继续展开。

以下为混排执行顺序示例，引用仅为占位，实际执行时须替换为已经获得的完整引用。示例描述输出与调用的顺序，不作为普通回复原样输出：

```text
进入 Main Agent 的 Final Response 阶段
  输出文本段：A 方案的说明
  调用 present_cards({"cards":[{"cardType":"miniAppCard","referenceIds":["a"]}]})
  等待并处理工具结果：成功时在此处展示 A 方案的卡片组
  输出文本段：B 方案的说明
  调用 present_cards({"cards":[{"cardType":"miniAppCard","referenceIds":["b"]}]})
  等待并处理工具结果：成功时在此处展示 B 方案的卡片组
  输出补充正文（如有）
结束 Final Response
```

### 卡片引用

- `referenceIds` 使用平台生成并实际返回的卡片引用，例如模型可见结果中的 `reference_id`。原样复制完整值，不根据业务字段、示例或编号规律生成引用。
- 引用可以来自同一会话的当前轮或历史轮业务结果，也可以来自 Sub Agent 原样交回的结果；引用是否仍有效由平台校验。
- 短引用（如 `a`）和带前缀的完整引用（如 `<|card|>:a`）均受支持。使用实际获得的格式，不自行添加或删除前缀。
- 不使用业务 ID、实体 ID、卡片实例 ID、页面会话 ID、工具调用 ID 或 System Reminder 外层 `ref_id` 代替卡片引用。
- 每个 `referenceIds` 必须是非空字符串数组。同一数组内不得重复填写同一个引用，也不得将同一引用的短格式和带前缀格式作为两个引用填写。

### 工具参数

`present_cards` 的顶层参数为 `cards`，值为非空数组。每个元素是一条小程序卡片展示指令：

| 字段 | 类型 | 约定 |
| --- | --- | --- |
| `cardType` | 字符串 | 必填，固定为 `miniAppCard` |
| `referenceIds` | 非空字符串数组 | 必填，使用实际返回的完整卡片引用 |

- `cards` 和 `referenceIds` 均按业务要求的顺序填写，保留业务要求的分组。
- 将 `referenceIds` 直接放在对应的 `cards` 元素内，不使用 `items`。
- 小程序卡片没有可选展示参数。正文通过正常文本输出，不写入出卡参数。
- 只填写上述字段。不传入顶层 `refs`、`options`，也不自行添加 `app_key`、`card_template_id`、`render_data` 或用户、会话等平台上下文字段。

### 调用与结果处理

- 通过实际工具调用提交 `present_cards` 参数，不将参数 JSON 或上述代码示例作为普通回复输出。
- 一次调用可以返回一张或多张卡片，`cards` 元素数量、引用数量与最终卡片数量不必相等。
- 平台根据引用恢复数据并生成卡片，工具返回的卡片交由平台展示。不手工构造渲染数据，也不输出 `RichMediaCard` 标签。
- 以 `present_cards` 本次工具结果判断出卡是否成功。提交参数不等于出卡成功；调用失败或返回 `isError=true` 时，不能宣称卡片已成功展示。
- 工具出卡失败时，不切换为旧引用格式、inline 卡片或其他出卡协议兜底；后续业务处理遵循本 Skill 的业务规则。
