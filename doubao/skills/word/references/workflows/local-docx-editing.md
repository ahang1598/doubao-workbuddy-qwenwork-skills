## 编辑 Word（本地打开）

`<system-reminder>` 命中「打开的本地 Word 文件路径」场景时走本流程：回写目标是 runtime 提供的绝对路径本身，既有 DOCX 同时是内容、语言和版式 baseline，也是本次写作必须继承的模板。新增或改写内容应服从用户明确要求和可靠材料，并沿用原稿应保留的术语、事实、语气、标点、样式和编号规则。

> ⚠️ **先读完再动手**：本文档共 169 行，单次 Read 可能读不完；没见到末行「全文完」标记＝没读完，必须调整 offset 续读直到该标记。

### 命中信号

`<system-reminder>` 中同时出现 `<information>` 声明该路径 + `<type>lark_doc</type>` + `<file_path>` 为本地 `.docx` 绝对路径时命中，缺一即不适用（不适用时走 [`docx-editing.md`](docx-editing.md)）。

### 执行顺序
核心顺序：理解现状和用户需求 → 定位并规划修改  → 执行编辑操作 → 验收 → 交付。

### 第 1 步 · 理解现状和用户需求

**理解用户任务**：这一步要同时弄清三件事：用户要求改什么、用户提供了哪些依据、原稿当前实际是什么状态。

**先处理用户提供的编辑文件**：

- **目标锁定**：回写目标就是 `<file_path>` 本身。不得 glob、扫父目录、按文件名近似匹配，也不得使用/推断在线 URL 或 token（即便同时提供了 URL）。
- **读取重试**：首次不可读时按 `0.5s、1s、2s、4s` 退避，之后每 4 秒重试，直至总耗时 20 秒；期间不得改换目标路径。
- **超时仍不可读**：停止流程，告知用户编辑失败、请稍后重试；不得替用户挑候选，也不得静默降级到「仅在线 URL」分支。占用或权限异常属宿主状态，交回用户处理，agent 不改。
- **本地依赖失败不循环**：外部命令或 Python 库首次失败时最多重试一次。仍失败则降级并披露受限项，不得循环安装、探测或重试。
- **渲染器探测预算**：先判定本任务是否涉及"版面敏感项"（分页、跨页、图表增删、页眉页脚、纸张或方向变化）——判据 ① 用户 prompt 与命中信号中的版面词；② `SOURCE_DOCX` 结构初判；③ 第 2 步生成的 `edit_plan`（若 ①② 已判"涉及"则跳过）。未涉及时全流程不做 `which`、不做渲染；涉及时全任务合计至多一次 `which`（`soffice` 或 `libreoffice`，二者是同一二进制的别名），命中即用、未命中即"渲染不可用"走结构回读，不再重试或探测其他渲染器/转换器（Word / Pages / `pandoc` / `docx2pdf` / `textutil` / `unoconv` 等对 OOXML 版面不忠实，不构成版面依据）。若 ①② 判"未涉及"、③ 才发现涉及，此时补一次 `which` 即可，不回补 baseline 渲染，验收改用结构 diff。
- **任务临时目录约定**：指 `$(pwd)` 下新建的**任务专属子目录**（如 `./<task-slug>_work/`）——`$(pwd)` 是本 session 项目根，可能被多任务共享，**不要假设 runtime 已按任务隔离**。`SOURCE_DOCX`、`attachment_purpose.md`、渲染产物、edit_plan 全部落此；脚本用 `WORKDIR="$(pwd)/<task-slug>_work"` 并先 `mkdir -p`，**禁止**硬编码到 `/tmp/xxx` 等工作目录以外的路径。

**baseline 与结构检查**：

- **回写目标与只读 baseline**：将 `<file_path>` 作为 `TARGET_DOCX` 原地写回（不复制副本、不换路径），并在任务临时目录保存只读 `SOURCE_DOCX`。`SOURCE_DOCX` 仅供回读比对，不参与写路径——即便写不满意需要回退，也应在 `TARGET_DOCX` 上继续增量编辑，而不是把 baseline（或任何备份）覆盖回目标"整份重来"，那样会打断宿主状态并反复触发授权弹窗。
- **生成 `SOURCE_DOCX` 走 Python 二进制复制**：如 `python -c "import shutil; shutil.copy(src, dst)"` 或读 bytes 后 `open('wb').write` 落盘，避免入口就触发一次授权弹窗。此处只是二进制复制、不解析 OOXML，与下文"DOCX 本体必须通过 `python-docx`/`lxml` 操作"并不冲突。
- **结构检查（必做）**：制定修改计划前，用 `python-docx`/`lxml` 从 `SOURCE_DOCX` 读取正文、表格、图片、页眉页脚、批注、脚注尾注、修订或版式证据。
- **baseline 页面渲染（条件执行）**：遵循上文"渲染器探测预算"门槛——只在涉及版面敏感项且探测命中渲染器时才做全页渲染并作为 baseline；否则跳过，并在工作笔记中记录"未做 baseline 渲染（简单任务）"或"未做 baseline 渲染（渲染器不可用）"作为限制。跳过 baseline 渲染不影响结构检查的通过判定。

**再确定编辑类型**：

- 判断用户的任务是一个指令明确的简单编辑任务，还是一个包含写作质量要求的复杂任务。
- 本场景**不重新选择体裁**，也不套用 `writing-taxonomy.md` 的默认格式。仅在为新建表格、图片或示意图选择版式且原稿无同类基准时，允许回读该文件对应小节。规则优先级为：用户明确要求与可靠材料 > 原稿中必须保留的内容和结构 > 相邻同类基准 > taxonomy 表格/图片/示意图 小节。
- **判断任务是否为强附件和信息遵循类型**：判断用户的指令是否为根据用户给定信息或附件写作，且体裁类型为公文、论文、法律、科研等严谨、严格要求信息准确的场景。
- **默认不打断，能推测就直接做**：需求不完全明确时，优先按合理默认推进，不要为小问题反复发问。只有确实无法推进的硬阻塞才停下来，直接回复向用户说明并提问即可。

先把请求整理成轻量编辑 brief：明确修改目的、目标读者或使用场景、交付物、目标区域、期望结果、是否需要修订/批注及作者、必须包含和禁止改动的内容，以及事实时点或篇幅要求。小的歧义可根据原稿和上下文采用保守默认值继续；姓名、日期、文号、数据、审阅作者或会改变修改范围的关键条件不明确时，不要猜测，使用占位符或在确实无法推进时向用户提问。

### 第 2 步 · 定位并规划修改

**认真理解附件**：除了编辑原稿外，如果用户提供了附件，则需要认真阅读所有附件的格式和内容，理解它们之间的关系和在任务中的作用。若 `attachment_purpose.md` 不存在，必须重新写入到临时目录里。

- 若第 1 步中判定任务类型为强附件和信息遵循类型，说明附件原文非常重要，即使在你前序的步骤中，模型可能已经协助压缩附件、理解附件主题、补齐缺失信息，你依然需要非常认真地阅读附件。
- 若之前获取的附件内容（如有）存在必要信息缺失，请重新阅读。用户附件里有很多关键信息藏在图/表/公式里，只跑 `paragraphs` / `pdftotext` 会丢掉它们。
- 附件中的图片/表格插入 Word 时，须保留原图表的所有信息，**绝对不允许裁剪，但可以缩放大小来适配 Word 的排版布局**。
- pdf 必须先通过脚本 `pymupdf.open() 打开` 再跑 `page.get_images` + `page.find_tables` 来获得附件中的图片/表格信息，或使用 `page.get_pixmap` 获得 PDF 页面截图。
- 其他附件优先通过查找相关 skills 或者工具来获取完整的信息，若没有相关 skill 、工具可以使用代码能力来获取相关信息。
- 你写的附件作用清单中，应包含每个附件的内容概要、在任务中的作用、在任务哪个环节应该回读，以及附件之间的关系。

**回读原稿**：不要只凭用户描述的"第 N 页""某一段"或历史会话中的旧摘录直接修改；页码和展示位置只能帮助找线索，实际定位必须来自文档结构。

- 大文档先把结果落盘，再按关键词、元素类型、样式、story、part 或包级对象筛选，只把目标及必要上下文读入模型。
- 对每个候选目标确认当前文字或对象、story/part、样式、run 边界、命中数、所在表格或分节、相邻内容和必须保留的结构。
- 检查可能被修改牵连的编号、标题层级、目录与字段、书签与交叉引用、脚注尾注、页眉页脚继承、批注与修订、图片关系以及分页。
- **字段 pre-audit**：改动可能影响目录、分页、编号、书签或交叉引用时，扫描相关 story 的动态域，记录定位、域代码、缓存、依赖目标及 `updateFields` 状态。能证明改动不影响动态域时，无需生成全量字段清单。
- **结构枚举**：增删移动 body 级对象或锚点有多个候选时，枚举 `w:body` 直接子节点。简单文字或格式修改只记录目标和必要上下文。

**规划内容**：根据用户要求（如有）、材料（如有）写出一份编辑计划 `edit_plan`，使用 TodoWrite tool 写在上下文中，明确修改目标。

- 若发现缺少必要的素材，可以使用必要的工具获取（如联网搜索、搜图、生图），禁止编造内容。
- 附件的重要性远高于自行获取的信息，是用户提供的最核心信息组成部分，在形成计划时必须明确指出这些附件中的信息应该处于计划的哪些部分。若第 1 步中判定任务类型为强附件和信息遵循类型，那么**附件原文**非常重要，你应该忠实于原文而非压缩物或自己的解释，不要出于润色、完整等写作风格的考虑，自行扩写、增加用户给定以外的信息，你写的每一条重要信息应能溯源到原文或原附件。
- `edit_plan` 要按以下格式明确内容：

| 目标区域 | 当前证据与稳定定位 | 目标内容或状态 | 内容依据 | 拟用操作 | 必要关联项 | 必须保留 | 验收条件 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `<region>` | `<story + unique text/style/identifier>` | `<requested result>` | `<user/material/source>` | `<operation family>` | `<field/reference/layout>` | `<style/structure>` | `<content/count/visual check>` |

规划时遵守以下规则：

1. **用语义证据定位**：使用唯一文字、样式、story、SDT 归属、书签、图片 alt text、页眉文本等稳定条件；不要使用"第 N 个段落/单元格"或凭位置猜测。
2. **按字面锚点定位**：有歧义或涉及 body 级对象增删移时，枚举 `w:body` 直接子节点并区分目录、正文、附件、段落和表格；无法唯一定位时再澄清。
3. **分析必要关联项**：修改标题、编号、图表、表格数据、书签或分页时，检查目录、交叉引用、图表编号、字段缓存、合计值、页眉页脚和邻页是否需要同步变化。只加入为保持一致性确有必要的关联修改。
4. **限定编辑范围**：所有计划外节点默认不变。不要顺手润色、重排或"清理"用户未要求的区域；baseline 已有问题除非妨碍本次修改，否则记录但不擅自修复。
5. **沿用原稿风格**：不要为编辑任务重新选择写作风格或设计系统。新增文字对齐相邻内容的字体（对于标题字体样式也应该对齐同级标题）、术语、语气、句式、标点、标题层级和段落样式；新增结构复制最近的同类结构。用户明确要求某处改变语气或格式时，只在计划范围内执行。对每个新增或改写目标，在计划中记录一个可定位的"最近同类基准"；第 4 步按该基准验收语言和生效格式，不得在写完后临时挑选看起来相近的对象。
6. **使用占位符**：对于占位性质的内容，请用占位符来表示，而不要自行编造，例如不要写"发文【18】号字"而应该写"发文【XX】号字"；在改写用户的内容时，尤其是公文、论文等正式文件，不要自行发挥增加和改动内容，只有用户明确要求，或者为完成任务确有必要、能够通过可靠材料验证且不改变用户原意时，才可以补充；推断性内容必须明确标识。

#### 域影响面速查

本次改动可能影响动态域时，按下表核对必要关联项；无影响时跳过。计划外字段变化均视为超范围改动。

| 本次改动 | 波及域缓存 | 处理 |
| --- | --- | --- |
| 只改正文文字，分页与标题层级不变 | 无 | pre-audit diff 确认字段未误改 |
| 改动影响分页 | `PAGE` / `NUMPAGES` / `PAGEREF` / `TOC` 页码 | 核对结构和缓存；无法原生刷新时披露 `deferred_word_refresh` |
| 新增、删除、改名或移动 Heading | `TOC`、相关 `REF/PAGEREF`、可能的分页 | 保留有效书签；先修复 orphan；沿用同级样式和编号 |
| 新增图/表 | 可能影响后续编号和引用 | 沿用原稿的自动或手工编号方式，不得在同一序列中混用；必要时披露 |
| 删除图/表 | `SEQ` 后续顺延 + 可能 orphan `REF` | orphan 必须先修复 |
| 编辑含 `PAGE` / `NUMPAGES` 的页眉页脚 | 相应域缓存 | 保留完整域结构；仅按计划修改静态文本或目标域 |
| baseline 无域，本次新增目录/页码/自动编号 | 视为编辑期新建域对象 | 写完整域并提供可识别的缓存结果；未完成原生刷新时按下项处理 |
| 本次新增或改动动态域，但未完成原生刷新 | 相关域缓存 | 可标记相关域为 dirty；仅在已审计全篇动态域且允许整体更新时补 `updateFields`，并披露其全局影响 |
| baseline 复杂域结构缺失或损坏（历史脏数据） | 该域本身 | 不擅自修复；本次修改牵连到该域时才先修复，交付披露 |

### 第 3 步 · 执行编辑操作

按第 2 步中生成的 `edit_plan`，逐一执行操作。

- **始终编辑同一个目标文档**：所有写入直接落到 `TARGET_DOCX`（即 `<file_path>` 本身）；不得中途切到副本路径或再复制一份新文件。
- **增量编辑，禁止"重置+整份重生成"循环**：按 `edit_plan` 在 `TARGET_DOCX` 上就地增量修改，不得采用"`cp` 备份覆盖 `TARGET_DOCX` → 从零重跑整份生成脚本 → 再重渲"的重来式循环。即使原稿接近空白需要大量填充，也应一次性规划后落盘，而不是反复推倒重来。
- **减少触发授权弹窗的 shell 操作**（按对象分工，正面表述）：
  - **辅助文本文件**（脚本、`edit_plan`、`attachment_purpose.md` 等）：读、写、改优先走原生 `Read`/`Write`/`Edit` 工具，这些工具不经过 Bash 复核。
  - **DOCX 本体**：一律通过 `python-docx`/`lxml` 操作；不要用 `Read`/`Write` 直接处理 `.docx`（对二进制 OOXML 包不适用，读到的是乱码或截断）。
  - **Bash 保留给必要的外部工具**：如 `python-docx`/`lxml` 脚本、LibreOffice/`soffice` 渲染、`pdftoppm` 等，本地打开场景下每条 Bash 都会经过安全复核，覆盖/删除/移动类命令会反复触发授权弹窗。
  - **产物版本化，靠唯一命名区分**（如带轮次或时间戳的文件名）而非删除旧文件；任务临时目录由 runtime 回收。
- **只修改计划范围**：只编辑 `edit_plan` 允许变化的内容及其必要关联项。未计划修改的页面设置、样式、编号、关系文件、媒体、页眉页脚、分节、书签、内容控件、脚注尾注、嵌入对象和自定义 XML 应保持不变。
- **继承完整结构**：新增段落、表格行、单元格、图注或图片时，复制最近的同类结构，并继承字体、样式、编号、边框、列宽、合并关系和段落属性，不使用与原文件无关的默认格式。
- **分区域填写并及时回读**：每完成一组相关修改，就回读对应区域，确认内容写入正确位置、格式得到继承、示例内容已清理。写入结果不明确时，先检查目标文档，再继续操作。
- 新增段落复用真实 `styleId` 和必要段落属性，但不复制 `sectPr/pageBreakBefore`。普通段落不复制 `numPr`；加入编号序列时保留或重建正确的 `numId/ilvl`，并回读可见序号。
- 分裂 run 时完整复制原 `rPr`，包括 `rFonts`、`sz/szCs`、语言、上下标、底纹与字符间距；不得挑选属性重建。
- 用户要求修订时，整段增删必须同时标记正文与段落标记，并保留书签、字段等非文本边界对象。使用唯一修订 id，验证接受和拒绝修订后的内容、段落与编号。
- 新增分节默认继承相邻节的纸张、方向、页边距和页眉页脚；只有用户要求或修改计划确实需要时才改变页面方向或纸张。
- 批注、回复或修订操作需要作者时，显式提供作者；没有可靠作者信息时不要自行猜测身份。

### 第 4 步 · 验收

写作型编辑验收前，重新读取用户指令、`SOURCE_DOCX`、`edit_plan`、`attachment_purpose.md`（如有），按规则优先级提取本次实际生效的明确要求，在上下文中形成轻量验收证据表：

| 规则来源与定位 | 验收对象与范围                   | 预期值或行为 | 终稿实际证据                         | 结果                    |
| -------------- | -------------------------------- | ------------ | ------------------------------------ | ----------------------- |
| `<file:line>`  | `<Title/Normal/表格/正文结构等>` | `<明确要求>` | `<实际值、检查范围、异常数量与位置>` | `<通过/失败/N/A及理由>` |

后续第 1–5 项必须逐条核销该表，不能仅凭视觉印象或笼统判断通过：

- 字体、字号、颜色、段落、Heading、页面和表格等格式要求，必须从终稿 DOCX 的样式定义、继承链和直接格式中读取实际生效值，并记录检查范围及全部异常位置；只抽查一个段落或只查看渲染页面不算通过。
