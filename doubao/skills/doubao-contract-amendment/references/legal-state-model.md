# 整体法律状态重建

在拆分用户要求、选择条款方案或起草正文前，先尽可能识别材料中的整体法律关系、主要关联及未决边界。原子化的是后续授权单元，不是事实世界。

## 一、确认材料栈与当前版本

单份合同默认作为本次拟修改的原协议；存在多份材料时，再识别其角色和效力顺序，包括原协议、已生效补充协议、当前底稿、承载本次需求的修订稿、事实证明材料或参考模板。结合签署状态、日期、修订和批注判断当前有效文本；不要把所有文件当作并列事实，也不要在首次搜索命中后停止。

## 二、识别整体关系，可用“交易故事”辅助

可在内部用连贯叙述辅助回答，而不是先做 R1、R2 清单：

1. 这份原协议本质上安排了什么交易或持续关系？
2. 谁以什么身份向谁交付何种权利、资产、服务、文件或款项？
3. 标的从哪里来，履行前后分别由谁持有、控制或承担？
4. 哪些条件启动哪些义务，义务何时完成，未完成产生什么后果？
5. 截至拟起草时，哪些已经发生，哪些仍待履行，哪些日期已经届满？

进入逐项修改前，至少识别现有主体、标的、资金、条件、时间和文件之间的主要关联。材料不足以形成完整叙述时不必停止任务；识别哪些关联已经确定、哪些环节可能缺失或无法闭合，并将缺失事项及其影响记录到后续起草交接本中。

## 三、重建六类相互连接的关系

### 1. 主体与角色

记录每个主体的名称、协议编号、交易角色、权利身份、义务身份和签署关系。同一主体可以兼具股东、转让方、创始人、保证人或服务提供方等角色；不得因补充协议重新编号而改变其原角色。

### 2. 标的与权属

识别标的的名称、范围、数量或比例、来源、变更方式和变更前后状态。对新增标的，必须识别材料是否已经说明其来源或取得路径；材料没有说明时，将来源保持为未知，不补造实现方式。

### 3. 资金与对价

沿每笔款项记录付款人、收款人、金额、性质、对应标的、付款条件、期限及退款路径。分别核算百分比、金额分项和总额；“用户列出了各期”不等于“各期已经覆盖全部价款”。

### 4. 条件、义务与后果

沿以下链条追踪每项核心安排：

`条件或触发事件 → 有权确认或豁免的主体 → 义务人 → 履行内容与期限 → 完成标准 → 未完成时的后果`

检查链条是否循环、倒置或断裂。只能在交割后完成的事项不能同时作为交割发生前必须满足的条件，除非用户明确设计了其他时间关系。

### 5. 时间与状态

区分签署日、生效日、条件满足日、交割日、付款日、履行期间、终止日和责任存续期。把每项事实标记为已发生、当前持续、拟发生或待确认；相对期限必须有明确起算点。过去日期不能无说明地承担未来截止日功能。

### 6. 文件与证明

识别文件名称、性质、出具主体、接收主体、证明对象、证明强度和提交时间。确认函、法律意见书、审计报告、主管机关文件和当事人声明不是可以互换的近似表达。

## 四、识别边界，不急于解决缺口

将发现的问题区分为：

- **变化**：用户明确要求改变原安排；
- **未知**：材料没有确定答案；
- **歧义**：存在两种有材料依据的解释；
- **冲突**：两个有依据的要求不能同时成立；
- **联动**：不处理将导致已确定变化无法执行或与原协议直接矛盾。

未知不等于冲突，也不授权采用行业惯例填空。先考虑保留原安排、限定修改范围或原子化待补；不要用新增责任机制掩盖事实缺口。

## 五、叠加全部变化后检查最终状态

将用户全部明确要求同时加入原状态，回答：

- 最终每一项权利、资产或股权由谁取得，来自哪里？
- 最终每一笔钱由谁向谁支付，总额与分项是否一致？
- 最终每个条件发生在相应义务之前还是之后？
- 最终每份文件由谁出具，证明什么？
- 最终每个主体的角色和权利义务是否未经授权发生变化？
- 所有要求组合后，是否出现单项正确但整体不可能的结果？

例如，分项与总量不闭合、权利或资产来源未明确、证明文件的主体或性质不确定、条件与履行期限前后冲突时，应将相应关系保持为未决并记录其影响；不得自行补造来源、金额、文件或履行路径以使文本看似完整。

完成以上整体理解后，将确定状态、用户变化、必要保留、异常空白及安全处理方式交给主流程的“起草交接本”；再将用户要求原子化用于覆盖检查和授权控制。不得在进入成文阶段后重新推定或填补交接本中的未决事项。
