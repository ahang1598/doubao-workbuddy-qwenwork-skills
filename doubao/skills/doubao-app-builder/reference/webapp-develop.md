# Web 应用本地开发链路

本文档是**本地 webapp 链路**的完整开发规则：用官方脚手架建一个前端工程，写成**多页面、有路由、能构建**的应用。什么时候走这条链路见 [`../SKILL.md`](../SKILL.md) 的三链路分流，动手前完整读本文档。

跟另外两条链路的分工：**html 链路**做单文件展示物（一个 `index.html`，原生 JS，无构建）；**本链路**做工程化应用（多页面、有构建、dev server 预览）；**需要运行时 AI 能力或服务端能力的不在本地做**，走 `app_builder_agent`。三条链路互斥，一个任务只走一条。

本文是**栈无关**的链路规则：工作流、通用约束、交付与发布。**读完它就能开工**——用默认栈的话再加一份模板说明。下面按需读：

## 硬性技术栈约束

1. **默认栈就是 React + Vite + TypeScript + Tailwind + shadcn/ui + react-router**。用户没点名框架时**一律用它，不问也不换**——不因需求简单退回原生 JS，也不因复杂改用 Next.js。
2. **一律用官方脚手架初始化，不要手搓**。🔴 **`--dir` 只接受相对路径**，先 `cd` 到父目录，`--dir` 只给工程名；目标目录**必须不存在或为空**——不要先 `mkdir`、不要先写文件、不要先复制素材，让命令自己创建：

   ```bash
   cd /Users/xxx/Doubao/chats/2026-08-28/new-chat-34 && lark-cli apps +init-template --type frontend --dir team-project-manager
   ```

   `--type` 只用 `frontend`。这一步纯本地拉模板包渲染，不打平台 API。**不用 `npm create vite`**：官方模板自带 55 个 shadcn 组件、`ui/image.tsx`、合规的 `spark.json` 与 base path / CDN 前缀处理，手搓的全没有，发布前还得按[产物托管协议](publish.md)改造一遍。
3. **依赖该装就装**：PDF 预览、地图、表格解析、日历排期、拖拽排序一律装成熟库，**不要为"少装依赖"手搓残废版本**；同时模板已带的不重复引，UI 库只用一套。
4. **产物必须能跑**：交付前跑项目自己配的静态检查（含类型检查），全绿才算完成。**不用专门跑一遍构建**——构建慢，而且起 dev server 时编译有问题终端会直接报出来，等于顺带验了；真正需要构建产物是发布那一步的事。
5. **全栈不在本链路**：没有服务端和托管数据库，用户要真实后端时如实告知。

## 工作流

**开头这几步的目标是：3 分钟内第一个业务文件落盘。** 准备阶段做的是判断，不是产出——判断做得再细，用户看到的产物也不会更好，只会更晚。

1. 理解需求。默认基于已有信息和合理假设直接开始，**不为收集偏好打断**（判据见「提问」）。
2. **先把建工程命令发出去**（命令见上）——它要跑十几秒，别等。发完立刻读 [`webapp/stack/react-standard-webapp.md`](webapp/stack/react-standard-webapp.md)（用默认栈时），命令跑完时你也读完了。换了别的栈就跳过那份。
3. 解析附件、文档链接、URL——有附件才做。数据文件先看结构与样本行、指标用脚本算不目测，并复制进会被一起构建进产物的静态资源目录。
4. 列 todo 清单。

5. 🔴 **一轮想完再动手：结构 + 视觉一次定死。** 这是准备阶段唯一该花时间的地方，**但它只值一轮思考，不要拆成好几轮来回改主意**——先读 [`steering/frontend-design.md`](steering/frontend-design.md) 定视觉方向，然后在**同一轮**里把下面几件事一起想完：

   - **视觉方向**：按 frontend-design 的四槽位定，落到主色 + 中性基底 + 一两处强调色。
   - **页面清单**：名称 + 路由 + 每页放什么。**页面收敛**——能合并的视图用 Tab / 抽屉，不为每个细分视图开一条路由。
   - 🔴 **功能范围：用户说什么就做什么，没说的不要主动加。** 目标是尽快给他一个能打开、能用的版本，不是一次做到完善。用户提「客户管理」，就做客户的增删改查和列表——**不要顺手加上销售漏斗、数据导出、操作日志、批量导入这些他没提的东西**。少做两个功能能早两分钟交付，而他看到实物之后提的需求，比你现在猜的准得多。
   - **导航结构**：几个一级入口、放侧栏还是顶栏。
   - **每页的功能**和**数据从哪来**。

   用户给了参考图 / 品牌规范时以用户的为准，不用自己推导。

   **不写文档、不落盘**，结论留在思考里直接用于写代码。

   ⚠️ **别把这一步拆成「先定视觉，再定结构」两轮**——它们互相牵制（导航形态影响配色应用范围，页面密度影响留白策略），分两轮想必然要回头改第一轮的结论，白花一轮的时间。

6. **改主题变量落配色**，然后**立刻开始写业务代码**。

   建完工程后**最多只读两个文件**：路由注册文件、主题变量文件——因为这两个你要改。其余模板文件的内容以 stack 说明里的清单为准，**不要逐个打开确认**。

7. **写代码**。**一个页面文件别写太大**——超过两百多行就把独立的块拆成子组件（表单弹窗、确认对话框、列表项、图表卡片各自一个文件）。一口气吐五千 token 的巨型文件，中间任何一处 import 或类型写错，回头改的代价都是整块重来。
8. 🔴 **自检：只跑静态检查这一项，把「跑检查 → 改 → 再跑」压到两轮以内。**

   **所有文件写完之后**再跑第一次静态检查，不要边写边跑——写到一半的工程必然报错，那些报错你还得再看一遍。

   写之前先把所用技术栈的已知类型摩擦点过一遍（默认栈的见 [`webapp/stack/react-standard-webapp.md`](webapp/stack/react-standard-webapp.md) 的「类型摩擦」一节）——**这类错误第一次写对的成本，远低于等报错再回来改**。

   🔴 **看到 `0 errors` 就立刻停手，进交付。**

   **不要再读 warning 列表，不要清理任何 warning**——未使用的 import、未使用的变量、`any` 这些统统不管，它们不影响运行也不影响门禁。**「顺手清理一下」不成立**：每改一处都要重跑一次检查，那是十几秒，而产物不会因此好一点点。

   唯一要动的 warning 是 `react-hooks/exhaustive-deps`——它是真 bug（拿到旧值），不是洁癖问题。除它之外一律不动。

   拿到报错后：**一次把所有 error 读完、一次改完，再跑第二次验证**。

   - ❌ 改一处 → 重跑 → 再改一处 → 再重跑。一次完整检查要十几秒，跑八九次就是一分半纯等待，这段时间你什么也做不了。
   - ✅ 报错列表通读一遍 → 按文件归类 → 连续改完 → 跑一次确认。
   - 第二轮还有错就再改一批，但**第三次之后还在反复，说明你在逐个试错**——停下来把剩下的报错一起看完再动手。

   lint 过了，再搜一遍**裸根路径**（`fetch('/...')`、`src="/..."`、`url('/...')`）或拿资源基址变量拼的路径——这条 lint 查不出、dev 下也正常，**但发布后整片 404**。搜到就按所用框架的正确写法改掉（默认栈见 [`webapp/stack/react-standard-webapp.md`](webapp/stack/react-standard-webapp.md) §9）。

   🔴 **质检总共就三项：静态检查、裸根路径、下一步的白屏检查。做完直接交付，不做任何其他质检。** 不逐条扫代码、不逐页点验、不挑样式细节、不查响应式、不跑 steering 文档里的清单、不再截图确认——**这些都不做**。质检的目的是拦住"跑不起来"，不是把产物打磨完美；剩下的问题让用户看到实际页面之后自己提。

9. 🔴 **白屏检查：浏览器打开首页看一眼，只看这一次。**

   **lint 过了不等于页面能渲染出来**——组件运行时抛异常、import 路径写错、Provider 没包住、顶层 hook 报错，这些 lint 一条都查不出，但页面会整片白。**先按下面「交付与发布」的方式起本地服务**（服务起完就一直留着，下一步交付要用同一个地址），然后**直接照抄下面这段调用**，把端口换成实际的就行：

   ```python
   mac_computer_use_tool(plane="bu", code="""
   import seed_browser_use as bu
   bu.navigate("http://localhost:<实际端口>/")
   bu.wait_for_load()
   print(bu.get_page_text())      # 先读文本：空或只有零星字符就是白屏
   print(bu.console_messages())   # 再读控制台：白屏时用它定位原因
   """, title="白屏检查")
   ```

   🔴 **就用这段，不要为它去读任何其他 skill**（browser-use 之类的都不用读），也不用先了解工具用法——参数已经写全了，直接调。两行 `print` 的顺序不能换：`console_messages()` 读的是缓冲区且**读完即清空**，反了会拿到空列表、误判成「控制台干净」。

   🔴 **这个工具调不通时，在交付说明里如实写一句「页面未经浏览器验证」就结束，不要用 `curl` 代替、也不要另找别的办法**——SPA 的 `index.html` 首屏就是个空 `<div id="root">`，`curl` 无论页面好坏都返回同一份空壳，用它得出「检查通过」是**假验证**，比不检查更糟。

   - **渲染出内容 → 立刻交付。**
   - **白屏 → 看控制台定位原因，改完再看一次确认，然后交付。**

   ⚠️ **只做白屏这一件事，只做一次。** 不看样式、不看布局、不看响应式、不逐页点、不截图比对——页面能渲染出内容就算过。它是兜底不是验收，剩下的让用户看到实际页面自己提。

10. **交付**：把上一步已经起好的服务地址用 Link Block 给用户；用户要求发布时才发布。

## 路由与导航（通用）

跟框架无关，换任何栈都要守。默认栈下的具体写法见 [`webapp/stack/react-standard-webapp.md`](webapp/stack/react-standard-webapp.md)。

- **每个页面只有一个可访问 URL**，禁止同一个页面组件既挂首页又挂具名路径。首页内容与某个具名页一致时用重定向，不要复制一份组件。
- **全局导航只写在布局层**（Header / Footer / Sidebar），页面组件内**禁止重复实现**。单页无导航时布局保持透传，不要套一层带高度的空壳。
- 写导航前在思考里过一遍**路由对账表**（页面 / 注册路径 / 是否导航入口 / label / 布局里写的路径）：**不能有指向未注册路由的导航项，也不能有无法通过导航抵达的页面。**
- **站内跳转不要用原生 `<a href>`**——会触发整页刷新、丢掉应用状态，用框架的路由组件。
- **导航要有激活态**，桌面端和移动端都要有；激活判断从导航配置读路径，不要硬编码路径字符串。
- **页内锚点跳转和页面跳转是两件事**，同一个导航栏里不要混用。锚点滚动要单独处理——多数路由库的导航组件在 history 模式下不会滚动到锚点，这是高频 bug。

## 代码规范（通用）

**mock 数据克制**：只给真正的业务数据实体建 mock，不给 UI 组件状态、表单字段、筛选条件建。每个 mock 数组 **≤ 6 条**，多数场景 3 条即够（覆盖不同状态即可）；字符串字段写短，id 用简单序号不用长 UUID。**页面的丰富感靠布局和组件质量，不靠数据量**——堆 10 条 mock 撑场面只会让 token 和调试成本都变高。

🔴 **写同时引用多个实体类型的代码前（store / provider / 跨实体 hook），先把那几个类型的定义读一遍。** 一次并行写十几个文件时，写到这一层手边已经没有类型原文，只能靠记忆——于是必然出两类错：脑补一个不存在的类型名、构造对象时漏字段。**刚造出来的类型比读到的更容易记错，不是更不容易。**

**不抑制静态检查**：严禁 `@ts-ignore` / `@ts-expect-error` / `eslint-disable`。遇类型错误就修真类型，或用 `unknown` + 类型收窄，不用 `any`。**项目的 lint 配置宽松不等于可以乱写**——很多硬规则不靠 lint 拦，靠你一次写对。

## 配色落地

视觉方向定下后**必须真的落进项目的主题变量 / 设计 token**——脚手架一般都带一套语义色（背景 / 前景 / 卡片 / 主色 / 次色 / 强调 / 边框 / 图表系列色），**改它们的值，不要另起一套并行的变量**。

业务代码**只用语义化的颜色引用**，**禁止硬编码 hex 或任意值颜色**——改主题时必然漏改。需要边框就连颜色一起写，别只写个边框宽度。图表系列色同样走 token，不要在组件里写死。

**只在思考里定了方向、代码里仍是脚手架默认色，等于没做。**

## 跨栈 badcase 约束

1. **功能真实性**：列出的交互都要有真实 handler，严禁空函数。做不了的功能不要放按钮。
2. **不凑数、不加戏**：结构里没有的页面 / 功能一律不生成，不新增指向不存在功能的按钮 / 菜单项（防孤儿入口与死链）。**但已经做了的必须真能用**——宁可只做三个功能且个个完整，也不要铺开八个功能、其中五个点了没反应。范围可以窄，做进去的不能是半截。
3. **数据保真**：用户给了源数据时，每个数字和结论都从源数据实际计算，不目测、不凑整、不编造。
4. **深层页面有出路**：详情页、二级页必须能回上级，不能进去出不来。
5. **视觉一致**：同类元素跨页面保持同一套间距、圆角、阴影、密度。
6. **避免 AI slop**：滥用渐变、圆角＋左边框强调容器、被用滥的字体（Inter、Roboto、Arial）。**代码里不要用 emoji**——不作图标、不作装饰、不进数据，图标用 `lucide-react`。
7. **版本保留**：重大重构前把当前版本复制进 `_backup/`，它不属于交付产物。
8. **数据文件真读**：走到本链路说明产物要在运行时碰文件（要么渲染原件、要么用户会换数据），所以把用户的数据文件放进会被一起构建进产物的静态资源目录，运行时真去读它，**不要固化成代码里的常量数组**——那样用户换一份文件页面就不变了。（⚠️ 若只是「拿这批数据做一份分析」，本地算好写进代码就够，那种需求根本不该走到本链路，判据见 [`../SKILL.md`](../SKILL.md)。）
9. 🔴 **凡是指向自己应用的路径，都要带 base 前缀，一个都不能漏。** 线上应用不挂在域名根目录，而是挂在一个子路径下（形如 `/app/app_xxx`），这个前缀由构建时注入的环境变量决定——**不要自己拼、不要写死、不要从当前 URL 推导**。需要带前缀的地方比想象中多：

   - 静态资源：`<img src>` / `<iframe src>` / `<embed>` / `<video>` / CSS 的 `url()`
   - 数据文件与文档的 `fetch`
   - **同源接口请求**（有后端接口时）
   - 路由的 basename、站内跳转

   **这类错误在 dev 下一个都不会暴露**（dev server 挂在根路径），一发布就整片 404——本地怎么点都对，所以别指望自测发现，写的时候就得对。

   ⚠️ 框架可能注入不止一个前缀变量，**它们指向的地方不一样**：有的是资源基址（声明了 CDN 时会指向 CDN 域名），有的是应用根路径。**你手写的路径要用「应用根路径」那个**——因为 `public/` 下的文件和同源接口都在应用自己的域名下，不在 CDN 上。默认栈用哪个见 [`webapp/stack/react-standard-webapp.md`](webapp/stack/react-standard-webapp.md) §9。

## 数据持久化

本链路没有服务端：业务数据存浏览器本地存储（带项目命名空间，避免多个应用互相覆盖），导入走 File API 或读静态资源目录里的文件，导出走 Blob 下载。单机完整可用。**交付时必须讲清边界**：数据在当前浏览器，换设备不共享；要集中式存储得用户自备后端接口，接口位置在代码里留好。

## 提问

默认基于已有信息和合理假设直接开始。只有当一个决策**同时**满足两条才提问：① 用户没说、且从 prompt / 附件 / 截图推不出；② 猜错要推倒重来。有一条不成立就直接做。

⚠️ **常见应用形态不算「推不出」**：用户说"做一个 CRM / 客户管理系统 / 项目管理工具 / OA / 工单系统"时，用途和用户已写在需求里，**直接按这个形态做，不要为此发问**；数据要不要持久化**在路由阶段就判过了**（见 [`../SKILL.md`](../SKILL.md)），走到本链路说明已经定成前端版本，默认 `localStorage` 存着、交付时讲清边界，不用再问一遍。**技术栈不在提问范围**，没点名就用默认栈。

## 静态资源：图片与文档

图片能显著提升美观度，不要默认只用纯 CSS/SVG 撑视觉。

- **符号 / 信息型**（图标、状态标记、简单示意、数据图表）→ 内联 SVG 或图标库。
- **具象 / 氛围型**（人物、角色、产品情境、hero 主视觉、章节插画）→ 按 **用户素材 → 图片生成能力 → 外部检索** 的顺序取，**禁止用手写 SVG 或 CSS 几何图形代替依赖形象可信度的具象画面**。
- 🔴 **文件已经在本地，就直接用本地的**：用户给的图片、数据文件、字体，**直接复制进工程的静态资源目录**，用相对路径引用——本链路有构建，dev server 能挂载它们，发布时也会随产物一起上传。**不要绕一圈上传 CDN 再引远程 URL**，那是白花一轮工具调用。
- 🔴 **生图能力返回的 CDN URL 也要先下载下来**（`curl` 到静态资源目录），不要直接把那个 URL 写进代码——平台 CDN 会失效、会防盗链。唯一例外是**用户明确要求**用某个远程资源。
- ⚠️ 引用本地资源时注意**路径前缀在构建后会变**，按所用框架的方式拼，别写死根路径。
- 需要生图的位置**在写页面前批量生成**，再围绕实际图片的构图和色彩设计页面。

🔴 **要在页面里预览的文档，下载到静态资源目录用相对路径嵌，别绕路**：

- 需求里的文档给的是远程链接时，**先把文件下载进工程的静态资源目录**，页面里用相对路径嵌（PDF 直接 `<iframe>` / `<embed>`，浏览器原生就能滚动预览）。dev server 直接伺服它，发布后随产物一起上传，线上链接照样能打开——**这条链路本来就支持带文件走，不需要任何中转**。
- ❌ **不要上传 CDN 再引远程 URL**：白花一轮工具调用，还多一个可能失效的外部依赖。
- ❌ **不要把文档转成图片再嵌**：有损、慢、丢掉了选中和搜索，而原文件本来就能直接看。转格式是最后手段，不是默认做法。
- ⚠️ PPTX / DOCX 这类 Office 格式浏览器不能原生预览：原链接本身可访问就直接给链接或做下载入口；确实要页面内预览，**转成 PDF**（不是图片）再嵌。
- 文件较多时按用途分子目录放，别全堆在一层。

## 交付与发布

**一、起本地服务交出地址（每次开发完成后都做）**

🔴 **端口在 20000–39999 之间随机挑一个，不要用模板默认的 5173。** 用户经常同时开着好几个任务，都挤在 5173 会互相顶掉，还会让发布时的身份校验打到别人的工程上。

做法是在 `spark.json` 声明的 `dev.command` 后面加 `--port` 传参，**同时**把 `spark.json` 的 `dev.port` 改成同一个值：

```bash
npm run dev -- --port <你挑的端口>      # 注意 -- ，把参数透给 vite
```

⚠️ **上面那个尖括号是要你自己填一个数的**，别原样敲进去，也别从别处抄一个现成的——**每个新任务都重新挑**。

**两边必须是同一个数**（命令里的 `--port` 与 `spark.json` 的 `dev.port`）——发布时要靠 `GET localhost:<dev.port>/spark.json` 验证身份，对不上直接失败。

**地址仍以终端实际输出为准**：万一挑中的端口也被占，vite 会自动顺延，那就把 `dev.port` 改成顺延后的实际端口。服务保持运行，不要启动完就关掉。

🔴 **端口一变就立刻同步 `spark.json`**——起服务那一刻就改，别等到发布才回头补。**把 localhost 地址用 Link Block 交给用户——强制规范**：调 `present_files`，`source` 填终端实际输出的地址、`name` 给短标题（发布后的线上地址同样调它交付，见下文「交付与发布」），正文再用一两句说这是什么。❌ 不要只在正文丢裸 URL 或把地址混在句子里。

启动服务不等于开始质检——它只是给用户一个能点开的地址。

**二、交付说明**

**不写 `README.md`**——功能说明直接在回复里讲，写文件是多余的一轮。回复里讲清：任务目录路径、做了哪些页面和功能、未实现项、数据是真实来源还是示例数据（存浏览器本地时说明换设备不共享）。

🔴 **必须点明产物归属**：交付说明里要有一句话说清**这是妙搭平台的工程，需要线上地址时由你用平台链路发布**。这句不是客套——**用户往往隔很多轮才说「发布」，那时你手边只剩这段对话**，没有这句锚点就容易跑去给通用部署方案（Vercel / Netlify 之类），而那些在本平台一条都不适用。

**三、发布**

**默认不发布。** 用户明确要求（「帮我发布上线」「部署一下」「给个能分享的链接」）时读 [`publish.md`](publish.md) **自己执行**——这句话即授权，不用再问，也不要推回去让用户点按钮。

发布成功后**调 `present_files` 交付线上地址**，`source` 填地址、`name` 给短标题；正文只用一两句说这是什么，**不要再重复贴一遍链接**。地址取命令返回的 `online_url`，**不要凭 app_id 拼**。⚠️ 这一轮要发布时别先按「不发布」的路子交付一遍再发布，那会推两个卡片。
