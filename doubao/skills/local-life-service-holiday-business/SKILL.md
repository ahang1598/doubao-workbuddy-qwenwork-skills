# 节日经营

在豆包办公中回答：**中秋、国庆快到了，这个商家应当具体调整什么？**

服务餐饮、酒旅、休闲娱乐及其他到店行业，支持单店和多店。抖音生意经提供主要经营分析，抖音来客补充商品、履约和账号信息；双节历史资料只提供定性认知。

## 硬规则

- 数据读取只使用豆包工作浏览器提供的 DOM／可访问性树和页面可见控件。禁止调用 `mcp-http`、页面内部接口、抓包接口、`fetch`、`curl` 或自行拼接后台请求；DOM 不可用时记录暂无数据，不改用接口兜底。
- 账号一致性校验由本 Skill 直接执行：先确认来客登录态和当前商家，再从来客页面可见的“生意经”入口进入数据平台，对比两端页面展示的商家名称。只有名称一致才继续；任一端名称不可见或不一致时立即停止取数，请用户切换到同一商家后重新校验。
- 不单独核对或比较两端门店数量，不用门店数量相同或不同判定账号一致性。来客未通过资质验证的门店可能造成数量差异；门店数只可作为经营规模信息，不作为放行、终止或异常结论。
- 全程只读。不保存商品、不改价或建议改价、不改变关联门店、不投放或改预算、不报名发布活动、不生成视频。
- 数据使用 `observed`、`zero`、`unavailable`、`not_applicable` 四种状态；`--`、加载失败和没有权限不能记为 0。
- 实时热点、同行、搜索和投流结论必须来自当次可验证页面；没有数据时不补编。
- HTML 只展示有数据且能形成结论的模块。无数据模块直接省略，在页面给出一条简短“暂无数据”提示，不展示空卡片、空表格或占位图。
- 面向商家的文字和 HTML 不展示数据平台、采集路径、来源编号、P0/P1 完成度或“已获取哪些数据”等说明；这些信息只留在任务内审计记录。
- 只问会改变方案的预算、成本、人员或容量缺口，并一次合并询问。
- 建议给出一套科学合理的方案，不提供让商家调参或选择经营档位的界面。

## 数据获取优先级

“必采”表示必须检查并记录状态，不表示必须取得非空值。账号一致性校验通过后，优先复用当前已登录页面和当前分析范围；仅在对象、周期或口径变化时重新确认。

固定数据入口：

- 抖音来客：先枚举现有浏览器标签页，复用已登录的 `life.douyin.com` 页面；找不到时才打开来客首页。
- 抖音生意经：优先复用已打开且 DOM 中商家名称可见的生意经标签页；否则只从抖音来客当前页面可见的“生意经”入口进入。不得自行拼接、猜测或修改内部 URL，也不得复用无法确认商家的旧标签页。

登录、导航与账号校验按以下规则执行：

1. 先枚举当前标签页。找到已登录来客或生意经页面时直接复用，避免重复登录；每次导航后重新读取 DOM，不沿用旧节点索引。
2. 以 DOM 中可见的登录状态为准。来客未登录、登录过期或显示 SSO 登录页时，停在登录页并请用户完成登录；同一轮只提示一次，不重复打开登录页。
3. 用户登录后重新读取来客 DOM，确认已进入商家后台，并记录当前展示的商家名称。
4. 复用已打开的生意经页，或点击来客 DOM 中可见的“生意经”入口进入；不输入内部路径，不改 URL 中的商家参数。
5. 从生意经 DOM 读取当前商家名称。比较时只忽略首尾空格与不可见空白，不做别名、简称或模糊匹配。
6. 两端名称一致时记录 `account_consistency.status=matched`、`checked_by=local-life-service-holiday-business`、`method=dom` 与两端原始名称。名称不一致、任一端不可见或页面中途切换商家时，立即停止取数，请用户切换后从第 3 步重新校验。
7. 页面若明确展示 groupid，可作为辅助证据；不得只根据 URL 中的 groupid 判定账号一致。不比较两端门店数量，不以数量差异停止。

具体 DOM 读取、重试与登录接续规则见 [DOM 取数与登录接续](references/dom-collection.md)。

执行时以 [机器指标清单](references/data-manifest.json)（[中文说明](references/data-manifest.md)）的 `check_id` 和 `metric_key` 为内部口径。每条记录保存 `source_id`、`actual_scope`、`window`、`status` 和证据位置；P0 完成数由逐指标记录派生，不手填。内部审计信息不得渲染给商家。

### P0 · 数据平台核心指标（必采）

- [ ] 商家名称、groupid、门店数、区域数
- [ ] 成交金额、环比
- [ ] 核销金额、环比
- [ ] 退款金额、环比

- [ ] 商品榜单 Top5
- [ ] 商品概览：全部商品、动销商品、滞销商品
- [ ] 搜索分析：搜索词、搜索曝光、搜索点击、搜索成交

### P1 · 数据平台扩展指标（关注重点命中时采）

- [ ] 成交来源分布：渠道、体裁
- [ ] 退款原因分布
- [ ] 评价数据：评分、评价数
- [ ] 流量数据：曝光、访问、渠道分布
- [ ] 门店榜单
- [ ] 行业竞争排名：概览层级

### P0 · 商家后台必采指标

- [ ] 商家名称：用于本 Skill 的跨平台账号一致性校验
- [ ] 成交金额、核销金额、退款金额
- [ ] 曝光次数
- [ ] 经营分、门店等级分布
- [ ] 门店数、抖音号数
- [ ] 违规状态、收款状态

同一指标在两端均存在时，以生意经作为经营分析口径，来客用于商品、履约和异常补充；不为了追求数值一致而覆盖原值。两端门店数差异不触发中止。

## 快速执行流程

### 1. 校验账号一致性并确认周期

按本文“登录、导航与账号校验”七条规则直接完成校验。两端原始名称只留在任务内证据中；`collection_result.account_consistency` 保存 `status`、`checked_by`、`method`、`entry`、两端原始名称、校验后的 `merchant_name` 和 `checked_at`。只有 `checked_by=local-life-service-holiday-business`、`method=dom` 且 `status=matched` 才开始经营取数。

不要打开门店管理页核对门店总数，不枚举未通过资质验证的门店，不写两端门店数量差异结论。单店或多店只依据用户当前分析范围组织报告，门店数不参与账号一致性判断。

默认窗口为截至昨日的近 30 个完整自然日；同页直接读取环比及其实际对比周期。两端金额不同则保留各自定义，不按门店数量均摊或强行对齐。

### 2. 一次 DOM 快速预检

账号一致后，在当前页面 DOM 中一次读取并缓存：当前分析范围、近 30 日访问／成交／核销、全部商品数及在售商品数。读取 [快速分流与采集](references/fast-routing.md)，根据预检结果选择 F0—F3；用户特别关注的方向进入 FX。

快速分流只控制深挖范围。P0 指标仍需完成一次状态检查；明确无数据即可记为 `unavailable` 并停止该模块。

### 3. 按分支采集

只深入会改变建议的模块：

- 在售商品为 0：判断全部商品是否也为 0；存在草稿、下架或过期商品时，检查最多 3 个最可能恢复的商品及不可售原因。
- 有商品无成交：深入目标商品、搜索和流量；投流先做存在性检查。
- 有成交且观察窗口内无投流：深入 Top5、搜索和同城同类机会；只描述本窗口无消耗。
- 有成交且有投流：补采主要投放商品、素材与人群，形成完整诊断。

同一页面先批量读取全部目标字段。普通指标页加载失败只通过同一可见入口重试一次，仍失败记录 `unavailable` 并结束该模块；不把页面异常写成经营事实，不改用 `mcp-http`。热点先验证“城市＋品类＋节日”是否有结果，有结果才精读；同行未配置时不新增绑定。

### 4. 形成判断和建议

读取 [双节经营方法](references/holiday-playbook.md)，按行业检查消费人数、食材、节日含义、抖音短视频运营、消费场景、价格带、餐型、商品品类、名字、消费趋势和运营活动，只呈现真正适用的维度。

价格带只用于理解客群和商品结构，不输出改价、调价、降价、涨价、折扣加深或价格数字建议。可以建议补充权益、份量、预约、适用日期、服务说明和商品表达，但不改变价格。

不同业态只使用真实适用模型；不由公司注册地猜门店城市，不因一个 POI 推断全部门店业态。滞销不等于下架或不可售。近 30 日消耗 0 仅说明该窗口未见消耗。没有成功事实不硬凑“延续亮点”。

每条建议至少包含：

1. 具体动作名、适用范围与真实品类；
2. 双节变化与本店依据；
3. 具体怎么做；
4. 时间、执行角色与落实条件；
5. 观察指标。

证据足够时给出 5—8 条互不重复的个性化建议。证据不足时只保留能成立的动作；对应模块不生成，在页面统一说明“暂无数据”，不输出待补版、空模块或来源说明。

### 5. 结构化输出并渲染

按 [报告数据契约](references/report-data-contract.md) 先形成任务内 `collection_result.json`，再生成脱敏、展示就绪的 `report_data.json`。`groupid`、门店 ID、来源编号和后台参数不进入可分享报告。报告判断在 Skill 内完成，渲染层只展示数据。

优先把数据交给妙搭固定前端模板；搭建和绑定方式见 [妙搭渲染规范](references/miaoda-rendering.md)。无法调用妙搭时运行：

```bash
python3 scripts/render_report.py report_data.json output.html --collection collection_result.json
```

模板保持“中秋国庆经营方案”“双节经营调整”“双节消费趋势”以及暖白、松绿、月金、朱红的节日视觉。页首不显示工具栏、样例或版本说明；不提供节日筛选。无数据指标卡、洞察 Tab、空表格和空图表全部隐藏，只在总览下方显示一条简短暂无数据提示。页面不展示数据来源、采集状态或来源弹窗。

### 6. 交付

由脚本统一命名 `{范围名}-{年份}中秋国庆经营方案.html`。后续商品编辑或视频制作仅提供可复制任务说明；需要时读取 [已有能力复用](references/capability-reuse.md)。商品编辑任务也不得包含改价要求。

交付前实测桌面与 390px 窄屏、动作详情和可用洞察切换。核对：登录页只在需要时出现且登录后可直接接续；本 Skill 已通过 DOM 完成两端商家名称校验；全程没有 `mcp-http` 或内部接口兜底；门店数量未参与账号判断；P0 内部记录完整；零值与缺失分开；无数据模块已隐藏；页面没有来源说明；建议不含改价；桌面和窄屏可读。

通过本 Skill 向商家展示生活服务相关的实际数据或产物时（如经营数据、分析报告、生成的文案或方案），须在该次回复正文末尾另起一行，以普通文本展示以下固定提示，不加粗：

以上内容由 AI 生成，仅供参考，请结合实际情况谨慎甄别。

仅用于需求澄清、信息补充、门店选择、授权确认、进度告知或无结果／失败说明，且未包含实际数据或产物的回复，无需展示。同一条回复交付多项数据或产物时，统一展示一次。提示文案须原样保留并直接可见，不得仅置于折叠区域或工具返回中。
## 不触发与维护

纯日常改价、独立视频生成、入驻和一般经营日报不触发完整双节流程。数据只在已授权任务内使用；不保存登录凭据，不把后台身份和内部证据放入分享 HTML。交付后按组织留存政策清理任务内原始数据，未明确政策时不扩大分享或持久化到其他系统。依赖、版本和维护说明见 [发布维护说明](references/release-notes.md)。
