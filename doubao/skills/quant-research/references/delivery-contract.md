# 交付契约

最终正文依次包含：冻结假设（含唯一数据源、标的数、时间范围）；审计问题与具体位置/影响/修复；数据 manifest 和缺口；样本漏斗；方法与代码；逐笔或逐日工件；IS/OOS 指标；稳健性/容量；独立复算；结论与下一步。

请求代码时必须实际提供可运行函数及断言。请求 manifest 时必须列字段和示例骨架。请求文件时只有真实 artifact 存在才声称交付。

交付形态按题设执行：题设说只交一个包就只交一个，不自行拆成多份。

## 正文要自己站得住

主结论涉及的关键统计量必须出现在正文，不能只写"详见某工作表"。读者不打开附件也应当拿到主结论的数。反过来，正文不重复交付文件的明细内容——正文的职责是冻结口径、关键数值、结论，以及每份交付文件回答哪个问题。

关键研究纪律（可知时点怎么定的、股票池怎么取的、成交约束怎么落的）要能从正文看出具体做法。交付物再丰富，正文看不出纪律怎么落实的，判为透明度不足。

## 降级要全文一致

结论强度一旦因数据缺口降级，正文、摘要与交付文件里的**全部**表述都要落在同一级。不允许出现摘要写"仅作方法论演示"、结论写"该因子无效"这种前后不一致的降级尺度。

数据不足时明确停在哪一步，已完成代码审计和待运行工件，不输出未经计算的收益、显著性或 hash。

## 可重跑

交付包解压到任意目录都要能按 README 跑通：

- 不得硬编码作者的临时目录或绝对路径；
- 依赖要固定版本；
- 原始输入要么放进包里，要么在 README 写清从哪里取、放到哪个相对路径。
