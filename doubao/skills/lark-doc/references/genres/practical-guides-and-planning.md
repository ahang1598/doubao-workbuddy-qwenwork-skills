# 实用攻略、计划与规划

**使用方法**：1. 确认用户要完成的现实任务与使用现场 → 2. 明确行动路径、约束和有效性边界 → 3. 按用户行动顺序组织内容并规划可视化 → 4. 回读检查后交付。

## 适用范围与路由自检

**命中：帮助个人理解、选择并完成一项现实生活任务。**

- 旅行攻略、行程与规划；健身训练、饮食与恢复计划；菜谱、烹饪教学、食材利用、失败补救与保存复热；
- 用户需要的不是泛泛建议，而是一条可开始、可判断、可调整的行动路径。

## 第一部分 必须遵循的总原则

本体裁服务于用户在真实生活场景中完成一项具体任务。成稿不是知识介绍、泛泛建议，而应让用户能够据此开始行动、在过程中判断是否正确，并在条件变化时调整。用户明确给出的目标、对象、时间、预算、设备、身体条件、格式与素材等要求优先。

### 总要求

1. **逻辑清晰：开头解决用户最关心的核心问题，并给出roadmap** 开头先给出用户当前应采用的主路径、第一步或关键判断，并给出全文内容的roadmap，呈现**总分结构**，让读者直接获得清晰的“行动路线图”。后续内容按用户实际行动的顺序组织。

2. **信息来源真实、准确、时效性强**：用户需要的是一个可以真实执行的攻略和规划，所有信息务必基于最科学的事实、最真实的实际情况、最及时的更新。所有来源信息或计算数据都必须经过验证。如果使用了外部信息，务必使用参考来源标注。
  - **正文引用**：在正文中使用手动数字编号"[1]"、"[2]"方式标注，必须直接在正文中插入超链接（仅支持跳转，不能将url显示在正文），完整写作后需回读编号顺序检查是否对应
  - **对应尾注标注方式**：对应正文编号，在尾注中标注“作者或机构：《资料标题》（加超链接），发布方，发布日期，页码或章节（如有）”。

2. **内容完整且详略得当：提供足以完成任务的行动闭环** 用户应知道如何开始、如何推进、如何确认结果，以及条件变化时如何处理。但需要详略得当，不要所有内容都详细描述，而应当根据完成任务的主路径展开，边界信息只在必要时简短提供。

3. **规划类内容需要充分利用用户的时间和条件，不过于宽松，也不把计划写得超出正常可执行范围，避免用户因为计划过长而感到压力。**

3. **可执行：让用户知道现在做什么、如何做、做到什么算完成** 关键步骤应转化为用户能够直接采取的动作、能够观察到的状态和能够判断的完成标准。抽象目标、专业术语或泛化结论必须落实为具体行动；对会影响下一步的条件，应说明用户据此如何继续、减量、替换或返回上一步。

4. **边界清楚：明确何时不该继续、何处需要复查、哪些条件会改变方案。** 在需要时精简准确地补充必要的边界信息。对安全、时效、资源、身体状况、天气、设备、食材、预约或其他会影响结果的条件，明确适用范围、停止条件、复查节点或替代路径。不能把不确定信息写成既定事实，也不能为迎合目标给出明显不可行、有风险或超出专业边界的方案。

5. **图文并茂**：
- 视觉元素非常有利于用户直接执行，应尽可能搜索到有助于用户执行当前规划和攻略任务的图片信息，图片信息可以嵌入`table`并进行合理排版。
- 搜索插入图片必须有高质量来源，不能使用低质量的图片或生成式图片。

6. **不模板化：结构跟随用户任务，而不是固定目录**：根据用户的目标、限制、使用现场和交付范围决定哪些内容展开、哪些合并或省略。完整路线、周期训练和多步骤制作可以形成较完整的行动链；单项选择、单个动作、失败补救或替代方案只保留解决当前问题所需的部分。


### 篇幅要求

1. 先识别用户的目标，再确定最小可完成路径：确定用户的核心行动任务后，搜索资料并规划核心路径，以此为主线补充必要的边界条件，确保用户能够按照主路径执行，同时在必要的边界上进行复查，又不能被边界信息占据过多主要空间。
2. **篇幅以完整、简洁的行动闭环为限。** 先覆盖影响行动成败的必要信息，再删除不改变选择、步骤或判断的背景、重复解释和可有可无的例子。信息已经由 `table`、图片或其他元素完整呈现时，正文相应缩减；不得为显得全面写成长篇说明文。
3. **默认文字量。** 以下字数指正文、列表和 `table` 单元格中的文字总量，不含图片、视频、附件、链接预览和空白占位；用户指定字数、格式或交付范围时，以用户要求为准。

| 场景与交付范围 | 默认文字量 | 超出范围的条件 |
| --- | --- | --- |
| 单一主题或短周期交付，如 1—3 天旅行、1—2 周训练、单菜完整教学、小型备菜计划、单个动作或失败补救 | 500—1,500 字 | 优先用表格、图片和清单承载需要反复查阅的信息 |
| 多阶段或多对象交付，如 4 天以上旅行、4—12 周周期训练、多菜套餐或复杂烹饪教学 | 1,500—3,000 字 | 内容必须由多个独立阶段、菜品、地点或高风险限制支撑，并拆成可独立阅读的模块。 |

单篇通常不超过 3,000 字；超过时应由用户明确要求或任务复杂度支撑，并优先拆分总览与分阶段内容，而不是持续堆叠正文。

## 第二部分 可视化与排版参考

**使用说明：** 先判断读者在当前位置需要理解、比较、识别、打开还是核对什么，再插入元素。以下是信息任务与元素的对应关系，不规定每篇都使用相同组件或章节。

| 写到什么内容时 | 首选元素 | 插入方式与边界 |
| --- | --- | --- |
| 需要先看清主路径、关键限制或第一步 | 短段或 `callout` | 放在相关模块开头；`callout` 只突出会改变行动的结论，不连续堆叠。 |
| 需要比较方案、时段、剂量、用量、预算或字段 | `table` | 表前说明比较问题，表后写选择或下一步；不在窄单元格塞长段解释。 |
| 需要并列理解同层级的替代方案、正确/错误状态或准备内容 | `grid` | 各列信息结构一致、宽度平衡（插入两张水平方向不一致的图片时，允许调整宽度）；不放长正文或复杂宽表。 |
| 需要按顺序完成准备、操作或复查 | `checkbox` 或短列表 | 每项应可判断完成；需要正式分配的协作任务不进入本体裁。 |
| 用户必须打开预约、导航、视频教学、官方规则或资源入口 | `bookmark` | 紧贴对应事实或步骤；链接必须真实可用，不以裸 URL 填充正文。 |
| 用户需要查看或现场出示票据、签证、订单、PDF、表单或材料 | `figure view-type="Card"` | 放在对应交通、预约或操作项旁，不集中堆在文末。 |
| 文字难以准确传达对象、入口、动作、状态、路线或结果 | `img` / `figure` | 紧贴对应动作或判断；图片前后说明其帮助用户确认什么，不用氛围图替代信息。**图片的`caption`和文字说明禁止重复** |
| 需要理解路线、流程、条件分支或时间关系 | 路线图 `img` / `figure` 或 `whiteboard` | 地图回答“在哪里、怎么移动”；`whiteboard` 回答“满足什么条件时选哪条路径”，两者不重复。 |

**必须项**：
- **同组图片分栏。** 同一 `grid` 内图片方向一致时，所有 `column` 必须等宽，图片以统一展示比例呈现；同组同时包含竖图与横图时，不强制等宽，应根据原始宽高比调整 `column width-ratio`：竖图列适当收窄，横图列相应加宽，使各图在不被明显裁切、不出现大面积空白的前提下保持接近的视觉高度。无法在一行内兼顾比例与可读性时，拆分为两组 `grid`，不要用等宽列强行并排。
- **在`table`中插入图片**：在`table`中插入图片时，一般情况下禁止添加缩进（或需要选择“减少缩进”的参数）

### A-旅游攻略与规划

#### 内容要求

- **以下仅为必备项的内容建议，需要根据真实的用户需求，根据用户需求合理增加注意事项、出行前代办、交通方式等等旅行攻略常见部分。**
- **总览与路线** 多城市、环线、自驾、跨区域或转场较多时，在详细路线或每日行程之前，先给路线总览，再紧跟路线图或路线选择说明。必须用`html5-block`展示。
- **行前准备** 将签证、支付、预约、天气、交通、证件和特殊限制放在它们首次影响决策或行动的位置。需要在出发前统一完成的事项可放在总览后；仅影响某天或某段交通的事项放在对应 Day 或交通项旁。
- **每日行程必须用`table`** 
    - Day 标题写日期和当日区域或主线。如果行程较短，可以在一个大的表格内分开若干日写完所有行程，不强制要求每一天都需要单独起一个小标题，但需要保证每天行程信息的结构是一致的。
    - 表格中的行程说明需要根据内容要点和结构用有序列表和无序列表展示（例如门票、开放时间等可以单独列为无序列表内容，而不是用括号说明）。不要直接放一大段话。
- **旅游攻略必须包含丰富的图片**:

#### 元素插入要求
- **成稿必须包含总览`html5-block`、具体行程中国呢的`img`，否则不算完成任务，不能交付。**
- **旅行roadmap：提供路线总览图**：
    - **路线总览**：需要在文章开头“行程总览”需用可交互`html5-block`给出一个简单的路线总览，给用户提供总体的roadmap。路线图需要以核心地区、该地区的核心游玩点及主要节点为轴的路线总览，**每个关键地点需要插入一张当地最经典景点的图片，禁止在此插入美食图片**。使用`html5-block`时，务必遵循一套配色参考。`html5-block`的高度不要超过宽度的1.5倍。
    - `html5-block`图片插入已知问题**必须避免**：如果使用了相对路径（`src="img2_corniche.jpg"`），嵌入飞书文档后，iframe 运行环境里没有这些本地文件，导致图片全部加载失败，只显示空白或裂图。需要将 4 张图片压缩后转为 base64 直接内联到 HTML 中，不再依赖外部文件。
- **`img`是必须添加的元素**：
    - 整体规则：
      - 整体图片风格色系尽量跟所选择的一套配色参考保持一致。
      - 如需要插入`table`，同一个单元格内可放置1-3张图片
    - 行程`img`：
      - 要求每天的行程、每个景点都需要最少有一个高质量的经典找或当地的路线图，让用户能够知道该段行程是否值得去或者如何执行。必须在每日行程后用分栏形式展示每个自然人文点的高质量图片，并且在图片下方增加灰色、居中文字简要说明景点名称。每个分栏规定只能使用2列，该日行程超过2列时，需要在下方增加新的分栏。
      - 要求同一级标题下图片需要前后或并列放，中间不可放入`table`等其他元素，否则排版不流畅。一般图片统一插入`table`或统一放在`table`后。
      - 禁止某个当地自然人文点完全不提供任何图片。
      - 地点入口、住宿差异、交通现场、菜单/商品、路线位置或会影响现场判断的体验处，放在对应 Day 的说明后或该 `table` 行内。
    - 美食`img`：
      - **推荐美食时必须配图，否则不算完成任务**，可插入美食推荐的`table`内或者统一在美食推荐`table`后用分栏（一般2列）插入，多于4张图片时需要使用2*2及以上的分栏。
- **`table`**：每日行程必须用`table`呈现，方便读者把握整体路线信息。
    - 需要按时间推进、对照地点或反复查询信息时，在路线总览、行前准备或对应 Day 标题之后插入。如果行程较短，不强制要求每天都分别用一个表格，推荐合并为一个表格；如果一天内有多段段行程，推荐合并为一个表格，并且同一段行程可以用合并单元格形式整理，方便读者整体把握信息。
- **标题模块**：不要强制使用不必要的小标题，如果一级标题下只有一个二级标题，直接写在一级标题下，不单独起一个小标题。
- **长文导航。** 多城市或多个独立模块时，在标题和简短开场之后增加快速导航：等宽 `grid` 内放简短 `callout` 和 `<a>` 深链接。链接跳到模块标题或稳定引导块；通过飞书“复制链接”取得真实 `#share-...` 链接，不手写猜测锚点。自动目录仍由标题层级承担。

### B-健身训练与生活方式计划

#### 内容要求与对应排版

**说明**：本文档涉及的内容要求为需要覆盖的最小内容，实际使用时需要按照用户的具体需求进行调整。

- **成稿必须包含总览`html5-block`以及每个动作对应的专业动作`img`，否则不算完成任务，不能交付。**
- **全文开头给出训练总览及对目标总览**：必须用 `html5-block` 给出简洁的训练总览，包括训练目标、训练动作、训练时间等。
- **训练安排放在训练日或周计划开头。** 开头直接给出今天第一练、本周节奏或当前安全边界。在训练日或周计划开始处用 `table` 汇总动作、频率、组数/次数/时长、强度、休息、进阶与停止条件；在对应训练日下补充需要现场判断的提示。
- **动作与状态与动作卡同位呈现。** 核心动作、易错姿势、餐盘或停止信号在文字不足以准确判断时，将真实可靠 `img` / `figure` 紧贴动作卡或饮食说明。没有可靠图片时，在同一位置提供动作卡和自检说明，禁止用生成图冒充动作教学。
- **每个专业动作需要找到一个专业说明图放在对应训练节点`table`的对应行** 每个动作都需要有专业的动作要点说明以及对应的专业且高质量来源的讲解图，**必须插入到对应的动作行“动作示范”列**，无需在同一列搭配图片说明，直接插入图片即可。可以按热身、主训练、拉伸恢复等不同阶段分别动作，但同一阶段的视频必须置于同一层级结构内，不跨阶段混放。
- **每个专业动作务必找到最少一个专业说明图，否则不算完成任务**
- **调整与复盘放在触发调整的位置。** 时间不足、器械被占、疲劳或疼痛等情况出现时，在相应训练节点用 `grid` 展示标准与替代路径；用 `checkbox` 放本周任务，用 `table` 放完成率、重量/次数、疲劳或恢复指标。高风险、疼痛或不适用 `callout` 紧贴相应动作或计划，不放在文末泛泛提示。

### C-菜谱与烹饪教学

#### 内容与对应排版

- **准备信息放在步骤之前。** 在第一步前用 `table` 列出食材、工具、份量和预处理。套餐或多菜任务在分菜步骤前另用 `table` 列出备菜与出餐顺序。不要把关键火候、状态或风险统一塞进文末“注意事项”。
- **每个操作步骤对应一个判断节点。** 按真实制作顺序写步骤。每一步都要在同一处写清动作、时间或火候、应达到的可观察状态，以及偏离该状态时的即时处理。火候、油温、水温、打发、发酵、凝固、熟度、乳化、收汁等会改变成败的状态必须单独成步。

| 步骤行动表的列 | 每格写什么 | 元素与放置方式 |
| --- | --- | --- |
| 步骤 | 一个可独立执行且可独立判断的动作节点。 | 每行只处理一个关键状态。 |
| 动作与参数 | 下锅顺序、用量、时间、火力、温度或搅拌方式。 | 数值放在文字层。不要依赖图中文字。 |
| 达标状态 | 颜色、气味、形态、声音、质地、体积或挂勺等可观察标准。 | 将过程 `img`放在本行或紧随本行。 |
| 注意信号与即时处理 | 何种现象表示过火、未熟、过稀、分离或有安全风险。写当前应减火、离火、补液、继续加热、停止食用或改用替代路径。 | 高风险操作用短 `callout` 紧贴本行。不能只在全部步骤后给补救。 |
| 下一步条件 | 达标后进入哪一步。需要等待、冷却、静置或复查时写清触发条件。 | 需要计时或复查时可加入 `checkbox`。 |

- **过程图与动画。** 每个操作步骤都配对应的过程 `img`，并紧贴该步骤或嵌入其“达标状态”单元格；成品图、摆盘参考或信息图不能替代过程图。动画只展示一个动作或短状态变化，不能替代完整步骤、关键参数和状态判断。生成动画可用于手法示意或检索无果的补充，不可冒充真实火候、熟度或食品安全状态。
- **关键状态与纠偏。** 食材变化、火候、质地、熟度、正确/错误对比优先使用真实 `img`。多轮检索仍无真实图时，可用统一风格生成图或动画兜底，并标注“示意图，仅供参考，实际以文字描述的状态判断为准”；文字状态判断仍是用户执行的主依据。失败诊断只在用户已失败、或需要汇总多个症状时单独使用 `table` / `grid`，并区分当前补救与下次避免。
- **安全与外部教学。** 刀具、明火、生食、保存复热和特殊人群限制，用短 `callout` 紧贴相关步骤。视频不是默认开场素材，只有连续过程、手法或设备操作确实难以由步骤图说明时才插入。需要购买、预约或进一步学习的资源才插入 `bookmark`。

### Presentation Decision

选择本 Profile 时，默认使用 `presentation_mode: "rich"`。`rich` 用于主动组合原生组件与必要媒体，不代表固定 block 数量或装饰性页面。`visual_plan.reason` 应说明：`实用攻略、计划与规划｜用户行动主线；关键判断节点；可视化如何降低理解或执行成本`。图片、视频、地图和附件只记录确有实际使用需求的元素。

## 第三部分 交付前检查

### 内容检查

- [ ] 已按用户要完成的现实任务路由；
- [ ] 开头已回答用户当前最重要的行动问题；全文存在清楚主路径，而非背景、知识或链接的堆砌。
- [ ] 每个关键行动都写清可执行动作、完成判断和必要的下一步；局部问题未被自动扩写为无关的完整方案。
- [ ] 旅行路线地理顺序可行；训练剂量与安全边界匹配用户条件；烹饪步骤、状态判断和保存复热符合实际操作。

### 格式检查

- [ ] 篇幅与用户的目标、复杂度和使用方式匹配，并符合本指南的默认文字量或已说明超出原因；信息已通过组件呈现时，正文没有重复解释。
- [ ] 分场景规则的具体内容要素都必须包含在内，旅游攻略、健身计划必须包含总览的`html5-block`以及相应内容的`img`，否则不算完成任务。
- [ ] `table`、`grid`、`checkbox`、`bookmark`、`figure` 和 `whiteboard` 均放在其服务的内容旁；链接和附件可直接支持下一步行动。
- [ ] 最终成稿没有 XML/HTML 代码、工具命令、内部路由、检索过程、失败记录或占位字段。

### 视觉检查

- [ ] 每个可视化元素回答不同的行动问题，并紧贴对应步骤、判断或选择；没有用无关图片、空白卡片或重复组件制造“丰富感”。
- [ ] 地图、图片、视频和附件均与最终推荐路径或操作完全一致；地图使用真实路线/坐标，健身动作不以生成图替代，烹饪关键状态的生成图已明确标示意并由文字状态判断兜底。
- [ ] 图文、表格和 `callout` 分工清楚；读者只看标题、行动表、关键提示和必要媒体，也能找到主路径、当前状态和下一步。
