# 组织协作与执行文档

**使用方法**：1. 确认适用范围 → 2. 明确核心问题，读取和分析材料并按指南规划组织呈现内容 → 3. 选择合适的可视化元素及排版方式 → 4. 生成并检查后交付

**使用说明：**

1. **内容灵活适配**：先理解具体写作的目的、读者、使用场景和通行写法，再结合用户材料、组织习惯及本指南的核心指导，独立确定内容重点、结构和表达。不得机械照搬本指南的内容要求或加入无关内容。

2. **篇幅必须判断**：每项任务都必须根据任务复杂度、读者使用方式和整体信息量判断合适篇幅。参考范围应优先遵循。

3. **排版必须落实**：每项任务都必须以可读性为第一原则设计排版，遵循本指南的排版指导，并根据内容灵活使用。


## 适用范围与路由自检

**命中**
- 适用于服务组织内部信息记录、传递、执行或工作方法沉淀的文档，包括工作总结、工作计划、周报月报、会议纪要、提案与执行计划、流程、SOP、操作指引及培训操作手册等。
- 经营材料仅在核心目标是同步现状、明确责任或推动执行时命中；若核心目标是基于经营数据形成独立判断或决策建议，应路由至策略与分析体裁。

**不命中**
- 核心任务是通过数据或调研形成独立的经营、市场、行业、竞品或战略分析结论，即使文末包含建议或行动计划；
- 核心内容依赖法律、工程、医学、财务等专业规范和专业判断，即使成果名称是方案、流程、SOP或操作手册；
- 核心目标是岗位招聘、个人求职、面试准备、职称申报或人员评价，而不是推进具体工作与组织协作。


## 第一部分 必须遵循的总原则

### 核心内容指导

1. **以实际用途决定内容**：明确文档需要在组织运作中解决什么问题或产生什么结果，并据此确定内容重点和组织方式，不要记录与实际用途无关的冗杂信息。

2. **逻辑是第一原则**：呈现逻辑必须清晰，全文共同完成一个核心读者任务或回答一个核心问题。段与段之间逻辑连贯，每个小标题都承担清晰的逻辑角色，使读者仅阅读小标题就能够清晰把握全文内容。需要避免啰嗦重复的写作内容。

3. **充分利用用户提供的上下文**：用户提供的附件、企业资料链接（如飞书云文档）及其他链接是理解业务背景和形成内容的首要依据。写作前应完整读取其中与任务相关的文字、数据、表格、图表、图片及结构，准确继承已有事实、决定和术语口径；不得只依据用户的简短描述写作，也不得只列出链接而不使用其中的信息。无法读取时应明确说明，不得推测其内容。

4. **建立共享的工作上下文**：将分散在个人、会议和工作过程中的关键信息与已有共识沉淀下来，使相关人员能够形成一致理解，减少信息差、反复确认和沟通歧义。

5. **适配实际使用方式**：根据读者使用文档的场景组织和呈现信息，使内容便于理解、查找和必要时更新。例如，说明性文档应准确传达信息；协作或执行性文档还应提供完成相应工作所需的安排、规则或方法；其他未在说明文档中覆盖的内容，也应根据模型能力调整重点内容组织方式。

### 常见的内容闭环（按需参考）

下表用于检查文档是否足以支持读者任务，不规定固定章节、顺序或篇幅；内容简单时可合并，用户已有模板时优先沿用模板。

| 场景 | 通常需要让读者获得的信息 |
| --- | --- |
| 工作总结、周报、月报 | 本期结果或变化、重要原因或问题、需要支持的事项、下一步。 |
| 项目计划、推进方案 | 目标与边界、交付物、责任与协作、时间安排、关键依赖或风险。 |
| 会议纪要 | 已确认的决策、待确认事项、行动项及其负责人和时限。 |
| SOP、操作指引 | 适用范围、前置条件、操作方法、异常处理或升级方式。 |
| 跨团队协作说明 | 各方输入与输出、交接条件、协作关系、资料入口和当前阻塞。 |
| 培训材料、知识沉淀 | 学习或使用目标、正确做法、典型示例、练习或补充资源。 |



### 篇幅与排版

1. **可读性最重要**：根据内容关系灵活使用标题、表格、分栏、画板、任务及其他云文档元素；具体能力与嵌套边界以 [`lark-doc-xml.md`](../lark-doc-xml.md) 为准。排版元素用于承载和组织信息，使核心信息易于发现、理解和使用。

2. **篇幅服从实际需要**：优先遵循用户要求；未指定时，快速同步或说明类文档一般为300—1000字，一般协作或方案文档为1000—3000字，复杂流程、方案或操作手册为2000—4000字。内容较复杂时应优先分层、分模块或拆分子文档，而不是持续增加单篇长度；内容简单时不必为了达到参考范围而扩写。

3. **按照整体信息量控制文字**：表格、分栏、画板、任务等元素中的文字同样属于文档内容。信息已经通过这些元素完整呈现时，正文应相应缩减，只补充必要的解释和联系，不再用段落重复相同内容。


## 第二部分 可视化元素与排版

### 一、基本原则

本体裁服务于组织内部的信息同步、协作推进和执行交接。排版应帮助读者快速看清：当前状态、自己要做什么、与谁协作、下一步如何推进。

1. 正文、标题和列表能够清楚表达时，不强制使用视觉元素。
2. 优先选择可编辑、可持续维护的原生元素；需要频繁更新的状态、责任、日期和计划，不得做成不可编辑的 HTML5 block 或静态图片。
3. 用户附件、链接和已有文档中的原始图片、截图、图表优先于网络搜图；图片必须保留关键信息，不得为适配版式裁掉内容。
4. 每个表格、图片、画板或 HTML5 block 都必须服务一个明确的信息任务，且不与正文重复。

### 二、元素选择与组合排版

下表“承载内容”均为示例，应按读者任务调整。组合规则以 `lark-doc-xml.md` 已定义的嵌套能力为准：段落可使用加粗、斜体、删除线、下划线、颜色、链接、@人和@文档等行内元素；列表只承载短的同类要点；需要使用 `task`、`time`、`sheet` 等扩展标签时，另行读取 `lark-doc-xml-extended-blocks.md`。

| 元素 | 适用场景 | 可组合的内容与排版 | 使用边界 |
| --- | --- | --- | --- |
| `callout` | 核心结论、风险、待确认事项、操作提醒 | 内部仅组合段落、短列表、待办及行内强调；用“结论 + 必要条件/动作”组织。 | 只放短信息，不连续堆叠，不代替正文；不得嵌入表格、图片、分栏、画板、附件或其他资源块。 |
| `table` | 分工、状态、计划、问题、会议结论、规则对照 | 单元格内容可由文字、列表、引用、提醒、图片、附件、分栏、画板及链接等元素组成；多条并列事实、动作、条件或风险优先使用无序列表，而非分段或用分号串联。用表头统一字段，颜色仅标记状态或风险。 | 用于需要查阅或更新的结构化信息；根据单元格宽度选择内容，避免在窄单元格堆叠复杂资源。具体组合方式见下表。 |
| `checkbox` / `task` / `time` | 明确的行动项、负责人和截止时间 | `checkbox` 用于文档内轻量待办；`time` 用于提醒；`task` 仅挂载已创建的任务实体。 | 仅用于可判断是否完成的具体任务；需要分配、协同跟踪的正式任务，先通过任务能力创建，再以 `task-id` 挂载。 |
| `img` / `figure` / `source` | 截图、原图、界面、样张、原始图表、模板、录屏和补充材料 | 结合上下文，在图片前或后用一两句话提示看点或结论；图片已能独立说明时，不重复解释。附件可置于 `figure view-type="Preview"` 中直接预览，并在附近交代用途。 | 优先使用用户材料；不裁掉关键信息。附件不能代替正文必须说明的内容，且预览不应占据过多页面空间。 |
| `grid` / `column` | 两至三项同层级内容并排比较 | 每列以段落为基本单元，采用同一顺序与信息密度；需要其他嵌套内容时，先以 XML 规范和解析结果确认。 | 内容结构应一致、等宽且顶部对齐；避免放长正文、复杂表格、Sheet、Base 或关系图。 |
| `whiteboard` | 流程、依赖、角色关系、时间线 | 画板前用标题或短句说明读图问题，画板后用段落或短列表总结关键关系、责任或风险；相关行动仍使用表格或待办承载。 | 用于表格难以表达的关系；一张图只表达一个主要关系，不把详细任务或密集文字画进图中。 |
| `sheet` / `bitable` | 可筛选、计算或长期维护的台账 | 在正文说明台账用途、字段口径与读者应查看的结果，并提供对应文档入口。 | 正文写核心判断和使用口径，不复制全部明细；仅在确有筛选、计算或多人维护需求时使用。 |
| `blockquote` / `cite` / 文档引用 | 原话、正式口径、相关人员与材料入口 | 引用前说明为何需要保留，引用后写出其对当前判断或行动的影响；@人、@文档和命名链接作为段落内的上下文。 | 保留必要上下文，不能代替结论或行动安排；不连续堆砌长引用。 |
| `html5-block` | 低频更新的真实数据趋势、构成、阶段进度或多指标状态 | Block 前提出要回答的问题，后文给出结论、来源及可编辑数据入口；HTML 内应自带标题、口径、时间范围、单位和来源。 | 仅在表格、图片、Sheet 或可编辑画板无法以更低维护成本表达，且读者只需查看或探索时使用。 |

- **注意**：HTML5 block 不可在文档中直接编辑，因此不是本体裁的默认元素。仅在信息更新频率低或已有明确更新机制、且 Block 自身包含标题、口径、时间范围、单位和来源时使用；不得承载会议纪要、任务分工、SOP 步骤、项目计划、文字摘要或频繁变化的信息。使用后应保留可编辑的数据来源或原始材料入口。

#### 表格单元格嵌套与排版

`table` 是可组合的内容容器，不只是文字表。根据单元格承担的信息任务选择其内部元素；复杂元素宜放在 `colspan` 合并出的宽单元格或独占一行，避免压缩到窄列中。

| 单元格内元素 | 适合承载的内容 | 在表格中的排版方式与边界 |
| --- | --- | --- |
| `p` + 行内样式 | 一句话结论、字段值、状态、简短说明 | 同一信息单元用一段；用 `<b>` 标出短标签，用 `<span>` 标记状态或风险，避免整段着色。 |
| `ul` / `ol` | 多条并列事实、动作、条件、风险或步骤 | 并列内容优先使用 `ul`；只有顺序不可替换时使用 `ol`。每项保持短而同构，不用分号把多项塞进一个段落。 |
| `blockquote` | 必须保留的原话、约束、口径或例外说明 | 放在对应结论或字段之后，前后用短段落标明引用作用；不用于普通说明。 |
| `checkbox` / `time` | 单元格内需要跟进的少量明确动作与时限 | 适用于行动清单列；每项必须可完成、可判断。多个执行人或长期跟踪事项应转到独立任务或台账。 |
| `callout` | 单元格内需要突出显示的风险、阻塞或操作提醒 | 只用于信息密度较低、宽度足够的单元格；内部仍遵守 `callout` 仅可包含文本、列表、待办、引用等规则。 |
| `img` | 界面截图、原始图表、现场照片、视觉证据 | 放入“证据”“示例”或合并宽单元格；设置合适宽高和 caption，保留关键区域，不将多张大图堆入普通文字列。 |
| `source` / `figure view-type="Preview"` | 模板、PDF、录屏、原始文件等需读者直接查看的材料 | 在宽单元格中以预览视图展示，并用相邻短段落说明用途；若只需下载或引用，用命名链接或普通附件，避免过大的预览。 |
| `<a>` / `a type="url-preview"` / `bookmark` / `cite` | 外部网页、相关文档、负责人、资料入口 | 普通资料入口使用命名链接、@文档或 @人；只有读者需要直接预览网页内容且单元格足够宽时才使用链接预览。 |
| `grid` / `column` | 宽单元格内的 A/B 对照、两张同尺度截图或两个简短方案 | 放在合并宽单元格或独占行；各列保持相同结构与大致等宽，不在分栏内继续嵌套复杂表格。 |
| `whiteboard` | 流程、依赖、角色关系、时间线等难以用文字或列表表达的关系 | 放在合并宽单元格或独占行；画板只负责展示关系，责任、时间和状态仍由同表的文字列或待办维护。 |

### 三、常见文档的排版组合

以下“Block 与承载内容”仅展示常见组合，不规定文档必须包含该内容或采用固定章节结构；应按实际读者任务、材料和信息关系取用。

#### 工作总结、周报、月报

| 文档位置 | Block 与承载内容 | 使用要求 |
| --- | --- | --- |
| 标题后 | `callout`：本周期最重要的进展、风险或需支持事项。 | 只写 1—3 条结论；不重复后文的完整数据。 |
| 呈现状态与结果处 | `table`：目标、计划值/完成情况、状态、偏差原因、下一步。 | 适合需要横向核对的信息；状态字段用统一口径。 |
| 说明成果或问题依据处 | `img`：用户提供的成果截图、业务数据图、现场照片或原始图表。 | 图片前说明读者应关注什么，图片后说明其证明的结论。 |
| 收束行动处 | `checkbox` / `task`：下周期行动、负责人、截止时间。 | 仅把明确、可完成的事项写成待办。 |

#### 项目计划、推进方案

| 文档位置 | Block 与承载内容 | 使用要求 |
| --- | --- | --- |
| 开头概览 | `callout`：项目目标、边界或当前最关键的决策点。 | 不写完整方案，只帮助读者先建立共识。 |
| 呈现计划与分工处 | `table`：阶段、交付物、负责人、协作方、截止时间、验收标准。 | 计划会更新时，表格是主表达，不用静态图片替代。 |
| 说明依赖与风险处 | `table`：依赖事项、阻塞条件、影响、责任方、应对动作。 | 风险较少时可用短列表；需要跨团队关系时再使用画板。 |
| 需要展示关系处 | `whiteboard`：阶段关系、跨团队依赖、关键决策门或时间线。 | 只展示关系，不填写详细任务；详细责任仍保留在表格。 |
| 收束行动处 | `checkbox` / `task`：已确认的启动动作。 | 按“动作—负责人—截止时间”填写。 |

#### 会议纪要

| 文档位置 | Block 与承载内容 | 使用要求 |
| --- | --- | --- |
| 标题后 | `callout`：本次会议已达成的关键决策，或仍待确认的核心问题。 | 不超过 3 条；不得把所有讨论点塞入。 |
| 沉淀结论处 | `table`：议题、结论、影响范围、关联材料。 | 结论与讨论过程分开；结论优先写在表格中。 |
| 明确后续动作处 | `checkbox` / `task`：行动内容、负责人、截止时间。 | 一个待办只对应一个明确动作；无负责人或时限时写为待确认事项。 |
| 保留关键依据处 | `blockquote`：必须保留的原话、口径、约束或分歧。 | 原话之后必须写清其对决策或行动的影响。 |

#### SOP、操作指引

| 文档位置 | Block 与承载内容 | 使用要求 |
| --- | --- | --- |
| 标题后 | `callout`：适用范围、前置条件、风险提示或完成标准。 | 不用于介绍全部背景。 |
| 每个操作说明后 | `img`：对应步骤的界面截图、附件原图或从文件页面/内容中提取的截图。 | 一张图只解释一个关键操作；用户提供的原图不得裁剪。提取文件内容截图时应保留完成该操作所需的完整区域，并用图注指出操作结果。 |
| 给出全流程概览处 | `ol`：简短步骤名称和顺序。 | 详细操作说明与例外情况放在各步骤正文，不写入长列表。 |
| 处理异常或分支处 | `table`：问题现象、可能原因、处理方式、升级条件。 | 适合读者按现象快速查找处理方法。 |
| 提供补充材料处 | `source` / 附件预览：模板、原始文件、录屏或补充材料。 | 附件前说明用途；正文不得依赖读者打开附件才能完成基本操作。 |

#### 跨团队协作说明

| 文档位置 | Block 与承载内容 | 使用要求 |
| --- | --- | --- |
| 明确角色与交付处 | `table`：角色、职责、输入、输出、交接条件、协作对象。 | 以交付物而非泛泛职责划分责任。 |
| 解释协作关系处 | `whiteboard`：团队间的流转路径、依赖关系、升级路径。 | 流程图用于看关系；表格用于查责任与时限。 |
| 引用相关资料处 | `cite type="doc"` / `bookmark` / 链接预览：相关规范、项目主页、台账入口。 | 每个入口注明用途，避免只堆链接。 |
| 提示阻塞并安排跟进处 | `callout` + `checkbox` / `task`：当前阻塞、待决事项及跟进动作。 | `callout` 说明为什么重要；待办记录具体动作。 |

#### 培训材料、知识沉淀

| 文档位置 | Block 与承载内容 | 使用要求 |
| --- | --- | --- |
| 开头概览 | `callout`：学习目标、关键原则或常见误区。 | 只突出最关键的一两点。 |
| 展示具体做法处 | `img` + 短段落：真实界面、案例截图或用户材料中的原图。 | 图前交代场景，图后解释正确做法。 |
| 对比或归纳知识处 | `table`：概念、适用场景、正确做法、常见错误。 | 用于横向比较，不用表格承载长篇讲解。 |
| 提供练习或延伸材料处 | `checkbox`：学习者自查项；`source` / 链接预览：模板、录屏和延伸资料。 | 自查项必须可判断完成；资源链接需说明用途。 |

### Presentation Decision

选择本 Profile 时，默认使用 `presentation_mode: "rich"`。`rich` 表示按内容需要主动使用本 Profile 允许的原生组件、图片、附件预览与画板，不表示每个章节必须使用视觉元素，也不得放宽本文件对 HTML5 block、素材和可维护性的限制。

`visual_plan.reason` 应说明读者任务、信息更新方式、附件图片使用计划，以及表格、待办、画板和 HTML5 block 的分工。使用 HTML5 block 时，必须说明其不可编辑性为何可接受。`visual_plan.blocks` 仅记录确有最低数量要求的 `img`、`whiteboard`、`html5-block`；没有硬性数量要求时，写 `"blocks": []`。

## 第四部分 交付前检查

### 一、内容检查

- [ ] 文档服务的读者任务明确；读者只看标题、关键结论和结构化信息，即可了解当前状态、责任边界与下一步。
- [ ] 已按适用场景检查必要信息是否闭环；已确认的决策、待确认事项、行动项、负责人、时限和升级条件没有相互矛盾或遗漏。
- [ ] 事实、原话、推断、待确认事项与建议已清楚区分；内部信息可通过相关文档、会议纪要、台账、附件或负责人追溯，外部事实按通用规则标注来源。
- [ ] 长期维护的计划、SOP、台账或协作说明已标明维护责任、更新时间或更新入口；失效信息和过期链接已处理。

### 二、格式与结构检查

- [ ] 标题层级连续，编号模式统一；对象、状态、责任人称谓与日期格式全文一致。
- [ ] 段落、列表与表格各自承担恰当的信息任务；并列事项使用短列表或独立行，避免分号堆叠、长段文字和重复表达。
- [ ] 待办、提醒、附件、链接、@人和@文档的 XML 语法与引用信息完整；需要持续维护的责任、状态、日期或计划未被图片或 HTML5 block 替代。
- [ ] 禁止过度使用`callout`

### 三、视觉与资源检查

- [ ] 表格、待办、画板、图片和附件各自承担不同任务，不为装饰而重复呈现同一信息。
- [ ] 图片、截图与附件完整可读、用途明确；用户提供的原始图片未被裁剪，附件预览不会遮挡正文或占据不必要的空间。
- [ ] 使用画板时，流程、依赖和责任关系清晰；详细任务、时限和状态仍可在表格、待办或台账中维护。
- [ ] 使用 HTML5 block 时，已确认其不可编辑性可接受、数据和口径真实、存在可编辑数据入口，并已检查标题、文字和图例在文档中可读。
