# 产品 PRD 与技术协作文档

**使用方法**：确认文档类型与读者任务 → 补齐决策上下文 → 先解决核心不确定性 → 按场景组织方案、证据与验证 → 回读检查后交付。

**阅读路线**

1. 先在“适用范围与路由自检”确认文档是否属于产品 PRD 与技术协作。
2. 再按“总原则”确定读者、上下文、核心不确定性和主文边界。
3. 根据文档的信息任务，在“可视化元素与排版”中选择可维护的表达方式。
4. “分场景排版组合”只提供高频文档的专项参考；未列出的文档仍按总原则和元素边界组织，不视为不适用。
5. 交付前按内容、格式、视觉三组检查回读。

## 适用范围与路由自检

**命中**

- PRD、需求说明、功能设计、规则说明、接口或迁移说明；
- 技术方案、设计文档、RFC、架构设计、技术决策记录；
- 测试计划、测试记录、验收、上线验证；
- 故障复盘、问题分析、变更风险与技术风险记录。

**不命中**

- 核心任务是项目推进、会议结论、职责分工、流程或 SOP，进入“组织协作与执行文档”；
- 核心任务是经营、市场、行业、战略或消费选择分析，进入对应分析类文档；
- 面向外部用户的产品介绍、操作教程、营销传播内容，进入相应体裁。

### 规则优先级

1. 用户明确的内容、格式和交付要求优先。
2. 本指南中适用于当前文档的内容、证据和排版要求，按本指南执行。
3. 示例、推荐结构和组件组合按实际需要取舍，不为套模板新增内容或省略必要信息。

## 第一部分 必须遵循的总原则

### 1.1 核心内容指导

1. **先明确文档要让谁产生什么结果。** 动笔前明确文档类型、主要读者、读者读完后应作出的判断或行动、既有模板，以及篇幅、时间、技术或组织约束。

2. **在写方案前补齐读者需要的上下文。** 收集并梳理与当前问题有关的背景，包括已有讨论、关联文档、替代方案为何未采用、时间压力、技术架构、上下游依赖、历史事故和相关方顾虑。对理解当前决策不可缺少的信息，应在文档中说明，或提供读者可访问的明确材料入口；不要默认读者已掌握此前讨论。

3. **优先写清不确定性最大的核心问题。** 不从背景、术语或容易写的字段开始堆内容。先识别最需要确认的决策、提案、技术路径、风险判断或责任边界，围绕它写清可选路径、取舍依据、尚未解决的问题和需要谁确认的事项；摘要、背景和附录在核心判断明确后再补齐。

4. **让每一节都有明确的读者任务。** 每一节都应帮助读者回答一个具体问题，例如“为什么现在要做”“本次不做什么”“为何选择此方案”“依赖什么条件”“如何证明已经完成”。不按作者收集材料、会议发言或字段清单的原始顺序平铺内容；章节之间应连续推进读者的理解和决策。

5. **把关键取舍和未决事项写出来。** 文档不只呈现最终结论，也应让读者看见影响结论的前提：采用了哪些假设、排除了哪些方案、仍有哪些风险或未知、哪些内容需要后续验证。不要用看似确定的语言掩盖尚未确认的事实，也不要把待讨论事项写成既定决策。

6. **把篇幅留给会改变当前判断的信息。** 主文的大部分篇幅必须用于回答核心问题、说明取舍依据和交代下一步。背景、替代方案、风险或未决事项，只有在会改变当前决策、实施方式或验证结果时才展开；否则压缩为必要的一两句，或下沉到链接、附件、附录和可维护台账。不能让次要背景挤占核心结论、方案和验证的篇幅。

7. **先搭骨架，再逐节收敛。** 先建立覆盖全文的标题骨架和各节任务，再补正文。每个部分先确定应保留什么、删除什么、还缺什么，再写成可读段落；完成后回看全文，删除重复、矛盾、泛泛表述和只增加长度却不帮助读者判断的信息。

8. **用 Reader Testing 测试文档。** 假设读者没有参与此前讨论，仅凭文档检查：能否说明问题、核心提案或结论，以及下一步由谁如何验证或执行。若读者需要回到作者处补关键背景、定义或决策依据，文档仍未完成。

### 1.2 篇幅与信息层级

- 读者只看标题、必要摘要、关键要点与图表，应能理解全文的问题、主张、限制与下一步。
- 用户指定篇幅、模板或平台限制时优先遵守。未指定时，以帮助读者完成当前决策或协作任务为限，不把一份 PRD、技术方案或复盘自动写成项目百科。
- 单一问题的需求说明、局部技术方案、测试记录或故障复盘，正文通常控制在 `1,500—3,000` 字；标准 PRD、技术方案或复杂复盘通常为 `2,000—4,000` 字。
- 多系统架构、复杂迁移或多方案技术决策，正文可扩展到 `3,000—5,000` 字；接口、日志、完整用例、配置和长期台账建议用子文档另行承载。
- 超过 `5,000` 字必须由多个独立系统、复杂方案比较、重大故障或用户明确要求支撑；优先拆分主文、附录和可维护明细，而不是继续堆砌。


## 第二部分 排版与强制可视化要求

### 2.1 强制可视化要求
- 只要文档内容涉及流程与顺序、比较、构成或分布、机制、架构、空间结构、趋势、预测，或者定量分析与多因素分析，就应默认采用可视化表达，并将其视为强制要求，优先使用 HTML block。
- 这也适用于对材料、文档、报告、表格和附件进行解读、分析或总结：应主动提取其中的关键关系、模式、差异与结论并进行可视化，无需用户另行提出画图要求。后续内容调整时同步更新。
- 命中触发条件时，最终文档必须实际呈现承载核心关系、证据、步骤或结论的可视化。 文字、表格和列表可以补充，但不能替代已触发的可视化交付。
- 本体裁完整执行[创建工作流](../lark-doc-create-workflow.md)  Step 3.1—3.4，统筹选择文本排版组件与可视化组件；适合通过图示理解的信息，优先使用可视化。具体例外、选型、图文分工、制作要求、视觉样式与大纲记录均按创建工作流执行。

### 2.2 补充要求

- 视觉元素用于降低判断、查阅、验证或维护成本，不用于装饰；不为装饰重复用文本和可视化组件呈现同一信息。
- 一个元素只回答一个明确问题，并与相邻正文分工，不重复展示同一信息。
- 正文默认不使用 callout，否则容易打乱读者注意力
- 标题应反映读者的判断路径，不按材料来源或字段清单平铺。
- 开头摘要按创建流程选择原生段落、要点、两列表或必要的浅灰 callout，直接回应核心问题与当前主张，不强制组件数量。
- 摘要只保留主要回答和必要限制；背景、完整风险清单、日志、行动明细与长论证放在对应正文位置。
- 表格用于查阅字段、比较方案、描述状态、验收和行动；不在单元格塞长段解释。
- **表格单元格内按信息关系分层**：并列条件、行为或例外用无序列表；具有执行先后的步骤用有序列表；一个完整判断或必要补充可保持短段，不能用分号堆叠多项信息。
- 架构、流程、依赖和因果关系按通用选型选择可视化组件载体：确实需编辑节点与连接时用画板，需定制组合表达或局部交互时可用 HTML；精确字段、状态和责任仍由原生表或台账承载。
- 高频更新的接口、用例、配置、缺陷和行动项优先使用原生table、Sheet，不做静态图片或 HTML5 block。

### 2.3 PRD 常见场景与表达分工

| 内容场景 | 优先可视化表达 | 保留的文字或表格明细 |
| --- | --- | --- |
| 系统组成、模块边界与依赖 | HTML 架构图、分层图、依赖图 | 模块职责、接口定义、约束与取舍依据 |
| 用户任务、业务流程与异常分支 | HTML 流程图、分支图 | 业务规则、边界条件、异常处理和验收标准 |
| 跨系统调用、多角色交接 | HTML 时序图、泳道图 | 请求参数、返回值、错误码和交接标准 |
| 对象生命周期与状态变化 | HTML 状态迁移图 | 状态定义、触发条件、权限规则和测试用例 |
| 故障事件与影响传播 | HTML 时间轴、依赖图、有证据支持的因果图 | 日志、监控证据、待验证假设与修复行动 |
| 性能、容量、实验与方案指标比较 | HTML 趋势图、对比图、分布图 | 精确指标、测试环境、测量口径与限制 |
| 迁移、灰度、上线与回滚 | HTML 时间轴、甘特图、流程图 | 操作清单、负责人、验证标准和回滚条件 | |
| 页面结构、信息架构与交互行为 | HTML 页面结构图、页面跳转图、交互示意；已有真实界面或设计稿时优先保留原图 | 页面元素、交互规则、文案、空态及异常态说明 |
| 多条件判断、规则分支与优先级 | HTML 决策树、条件分支图；逐项核对条件组合时使用规则表 | 判断条件、阈值、优先级、冲突处理和边界案例 |
| 数据实体、关联关系与数据流转 | HTML 实体关系图、数据流图 | 字段定义、关联键、数据来源、更新规则与一致性要求 |

以上用于识别常见可视化机会，不要求每篇覆盖全部场景，但是出现这些机会的时候必须使用html；未列出的内容仍按创建工作流 Step 3.2 判断。

### 2.4 提交presentation decision

- 默认 `presentation_mode: "rich"`。
- 仅当用户明确要求简洁或纯文本，或内容本身不适合丰富排版时使用 `normal`。
- `visual_plan.blocks` 仅记录有最低数量要求的 `img`、`whiteboard`、`html5-block`

## 第三部分 交付前检查

### 3.1 内容检查

- [ ] 已明确读者、文档用途和读者读完后应作出的判断或行动。
- [ ] 已补齐理解当前决策所需的背景、依赖、替代方案、约束和未决事项。
- [ ] 最核心的不确定性、提案或技术路径已被优先说明。
- [ ] 每一节都承担明确的读者任务，未按材料来源或会议顺序平铺。
- [ ] 关键取舍、假设、风险、待确认项和验证方式没有被隐藏或混写。
- [ ] 不参加此前讨论的读者，仍能理解问题、主张、依据、限制和下一步。

### 3.2 格式与结构检查

- [ ] 篇幅符合用户要求或默认交付尺度；长内容已按主文、附录和维护台账拆分。
- [ ] 标题、必要摘要、关键要点与图表共同构成清楚的阅读主干。
- [ ] 标题层级体现判断路径，未按字段名或材料来源机械平铺。
- [ ] 主文、表格、附件、链接和台账职责清楚。
- [ ] 表格字段口径一致，单元格未承载长段解释。
- [ ] 同一单元格中的并列条件、行为或例外已使用无序列表，有执行先后的动作已使用有序列表，未以分号堆叠。
- [ ] 行动项写清动作、负责人、完成条件或待确认状态。

### 3.3 视觉与资源检查

- [ ] 已对照 `outline.md`，确认应当可视化的核心关系与数据模式均已在对应正文位置实际呈现。
- [ ] 每个表格、截图、图表、画板和附件均承担明确的信息任务。
- [ ] 架构、流程、依赖和因果关系未被误写为密集表格；精确字段未被塞入关系图。
- [ ] 高频更新的接口、用例、配置、缺陷和行动明细保留了可维护的承载方式。
- [ ] 截图、日志和原始图表保留支持结论的版本、时间、来源和关键上下文。
- [ ] 不存在装饰性图片、重复结论卡、连续色块或无信息价值的复杂 block。
