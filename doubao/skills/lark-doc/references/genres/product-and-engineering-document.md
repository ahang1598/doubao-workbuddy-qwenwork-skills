# 产品 PRD 与技术协作文档

**使用方法**：确认文档类型与读者任务 → 补齐决策上下文 → 先解决核心不确定性 → 按场景组织方案、证据与验证 → 回读检查后交付。

**阅读路线**

1. 先在“适用范围与路由自检”确认文档是否属于产品 PRD 与技术协作。
2. 再按“总原则”确定读者、上下文、核心不确定性和主文边界。
3. 根据文档的信息任务，在“可视化元素与排版”中选择可维护的表达方式。
4. “分场景排版组合”只提供高频文档的专项参考；未列出的文档仍按总原则和元素边界组织，不视为不适用。
5. 交付前按内容、格式、视觉三组检查回读。

## 适用范围与路由自检

**命中**

- PRD、需求说明、功能设计、规则说明、接口或迁移说明；
- 技术方案、设计文档、RFC、架构设计、技术决策记录；
- 测试计划、测试记录、验收、上线验证；
- 故障复盘、问题分析、变更风险与技术风险记录。

**不命中**

- 核心任务是项目推进、会议结论、职责分工、流程或 SOP，进入“组织协作与执行文档”；
- 核心任务是经营、市场、行业、战略或消费选择分析，进入对应分析类文档；
- 面向外部用户的产品介绍、操作教程、营销传播内容，进入相应体裁。

### 规则优先级

1. 用户明确的模板、读者、技术范围、篇幅、格式和交付要求优先；如需偏离本指南的“必须 / 不得”规则，用户必须明确提出。
2. 未被用户明确覆盖时，本指南的适用范围、事实边界及“必须 / 不得”规则为硬约束。
3. 命中某一分场景后，只有该场景中明确标注“必须 / 不得”的规则生效；其余组合仅供参考。
4. “建议”“可”“按需参考”的内容只用于辅助判断，不构成固定目录、元素数量或模板。

## 第一部分 必须遵循的总原则

### 核心内容指导

1. **先明确文档要让谁产生什么结果。** 动笔前明确文档类型、主要读者、读者读完后应作出的判断或行动、既有模板，以及篇幅、时间、技术或组织约束。

2. **在写方案前补齐读者需要的上下文。** 收集并梳理与当前问题有关的背景，包括已有讨论、关联文档、替代方案为何未采用、时间压力、技术架构、上下游依赖、历史事故和相关方顾虑。对理解当前决策不可缺少的信息，应在文档中说明，或提供读者可访问的明确材料入口；不要默认读者已掌握此前讨论。

3. **优先写清不确定性最大的核心问题。** 不从背景、术语或容易写的字段开始堆内容。先识别最需要确认的决策、提案、技术路径、风险判断或责任边界，围绕它写清可选路径、取舍依据、尚未解决的问题和需要谁确认的事项；摘要、背景和附录在核心判断明确后再补齐。

4. **让每一节都有明确的读者任务。** 每一节都应帮助读者回答一个具体问题，例如“为什么现在要做”“本次不做什么”“为何选择此方案”“依赖什么条件”“如何证明已经完成”。不按作者收集材料、会议发言或字段清单的原始顺序平铺内容；章节之间应连续推进读者的理解和决策。

5. **把关键取舍和未决事项写出来。** 文档不只呈现最终结论，也应让读者看见影响结论的前提：采用了哪些假设、排除了哪些方案、仍有哪些风险或未知、哪些内容需要后续验证。不要用看似确定的语言掩盖尚未确认的事实，也不要把待讨论事项写成既定决策。

6. **把篇幅留给会改变当前判断的信息。** 主文的大部分篇幅必须用于回答核心问题、说明取舍依据和交代下一步。背景、替代方案、风险或未决事项，只有在会改变当前决策、实施方式或验证结果时才展开；否则压缩为必要的一两句，或下沉到链接、附件、附录和可维护台账。不能让次要背景挤占核心结论、方案和验证的篇幅。

7. **先搭骨架，再逐节收敛。** 先建立覆盖全文的标题骨架和各节任务，再补正文。每个部分先确定应保留什么、删除什么、还缺什么，再写成可读段落；完成后回看全文，删除重复、矛盾、泛泛表述和只增加长度却不帮助读者判断的信息。

8. **用 Reader Testing 测试文档。** 假设读者没有参与此前讨论，仅凭文档检查：能否说明问题、核心提案或结论，以及下一步由谁如何验证或执行。若读者需要回到作者处补关键背景、定义或决策依据，文档仍未完成。

### 篇幅与信息层级

- 用户指定篇幅、模板或平台限制时优先遵守。未指定时，以帮助读者完成当前决策或协作任务为限，不把一份 PRD、技术方案或复盘自动写成项目百科。
- 单一问题的需求说明、局部技术方案、测试记录或故障复盘，正文通常控制在 `1,500—3,000` 字；标准 PRD、技术方案或复杂复盘通常为 `2,000—4,000` 字。
- 多系统架构、复杂迁移或多方案技术决策，正文可扩展到 `3,000—5,000` 字；接口、日志、完整用例、配置和长期台账另行承载。
- 超过 `5,000` 字必须由多个独立系统、复杂方案比较、重大故障或用户明确要求支撑；优先拆分主文、附录和可维护明细，而不是继续堆砌。
- 只阅读标题、开头唯一的 `callout`、一级标题和各节首段，读者应能理解全文的问题、主张、关键限制与下一步。

### 排版与可维护性

- 默认单栏、标题层级清楚、正文优先；标题应反映读者的判断路径，不按材料来源或字段清单平铺。
- **最终交付文档必须且仅可使用一个 `callout`。** 放在标题和必要元信息之后、正文之前，直接说明核心结论、当前主张或关键决策，以及最重要的限制或下一步。
- `callout` 控制在 3—5 条短句或一个简短段落内；不放背景、完整风险清单、日志、行动明细或长论证。普通风险、待确认项和证据说明使用标题、正文、表格或行内强调表达。
- 表格用于查阅字段、比较方案、描述状态、验收和行动；不在单元格塞长段解释。
- **表格单元格中的并列事项必须列表化。** 同一单元格内有两个及以上可由分号分隔、各自独立成立的条件、行为、例外或动作时，使用无序列表逐项表达；前后发生的步骤、因果关系或一个完整句子的补充说明仍使用连续文字，不为拆分而打断逻辑。
- 架构、流程、依赖和因果关系使用画板；精确字段、状态和责任使用表格或台账。
- 高频更新的接口、用例、配置、缺陷和行动项优先使用原生表格、Sheet/Base，不做静态图片或 HTML5 block。
- 页面、日志、监控和原始图表只用于证据与理解，不作装饰；必须保留版本、时间、关键区域和必要来源。

## 第二部分 可视化元素与排版

### 一、基本原则

- 视觉元素用于降低判断、查阅、验证或维护成本，不用于装饰。
- 默认以 `rich` 主动组合正文、列表、表格和其他原生 block；不强制每篇使用图片、画板或 HTML5 block，也不为装饰重复同一信息。
- 一个元素只回答一个明确问题，并与相邻正文分工，不重复展示同一信息。
- 明确区分主文、原生表格、Sheet/Base、附件和链接的职责。
- 除开头唯一的结论 `callout` 外，全文禁止其他 `callout`。

### 二、元素选择与使用边界

| 元素 | 适合的信息任务 | 使用边界 |
|---|---|---|
| `callout` | 核心结论、当前决策、关键限制、下一步 | 全文仅一个，置于开头，不代替正文 |
| `ul` / `ol` | 短、并列的要点、选项或操作步骤 | 不承载长解释、多重限定或复杂判断；需要比较、状态或责任时改用表格 |
| `table` | 可按共同维度核对、比较、追踪或维护的结构化信息 | 先遵循“表格组织规则”；表前说明核对对象与口径，表后给出判断或动作 |
| `whiteboard` | 架构、数据流、依赖、流程、故障传播和因果 | 一张图只表达一种主要关系，不填密集字段 |
| `img` / `figure` | 页面、日志、监控、原始图表、测试证据 | 保留版本、时间、关键上下文与来源 |
| `sheet` / `bitable` | 用例、接口台账、缺陷、配置、行动追踪 | 正文不复制全部明细，只说明口径和结论 |
| 代码块 | 关键代码、命令、配置或接口示例 | 先说明其解决的问题；只保留理解或执行所需的最小片段，完整实现或配置进入代码库或台账 |
| `blockquote` | 原始需求、关键错误信息、约束或决策原话 | 引用后说明其对当前判断的影响 |
| `html5-block` | 真实性能、容量、成本、稳定性趋势或交互数据 | 图形明显优于表格时才使用，不做静态仪表盘 |

#### 表格组织规则

- **可按共同维度核对的信息优先合并为一张表。** 同一判断对象下，若多项内容可用一致字段表达，应合并为同一张表，而不拆成多个短标题、短段落或零散列表；列由当前读者需要核对的维度决定。
- **用合并单元格表达归属关系。** 当多条记录共享同一归属、阶段、对象或其他上位信息时，可在承载该信息的任意单元格合并，避免重复填写相同内容；合并后的其余单元格逐行呈现差异信息。
- **标题只保留独立读者任务。** 只有内容需要独立进入目录、服务不同判断，或不能共享同一组字段时，才拆为新标题；连续的局部规则先判断能否收束为同一张表。
- **无序列表替代分号堆叠。** 单元格内有多个并列的信息点时，使用无序列表逐项表达，不用分号将其连续串联；前后发生的步骤、因果关系或完整补充说明仍使用连续文字。
- **表格不替代无法结构化的信息。** 无法按共同维度组织、需要展开论证，或重点在复杂关系而非逐项核对时，使用段落、画板或独立章节。

### 三、分场景排版组合

以下组合为高频参考，不构成固定目录或最低 block 数量；未列场景按读者任务选择最接近的组合：

| 读者需要完成的任务 | 参考场景 |
| --- | --- |
| 定义目标、规则和验收 | 产品需求与 PRD |
| 比较技术路径，说明依赖和取舍 | 技术方案与架构设计 |
| 证明结果、覆盖范围或上线条件 | 测试记录与上线验证 |
| 解释异常、影响和纠正措施 | 故障复盘与问题分析 |

组合可按需要并用，不必照搬对应场景的标题、顺序或元素。除明确标注“必须 / 不得”的内容外均为参考；用户模板和实际材料关系优先。并用时，全文仍只使用标题后的同一个 `callout`。

默认使用 `rich`。未覆盖场景按信息关系从第二节选择原生 block，并按 [`创建工作流`](../lark-doc-create-workflow.md) 提交 Presentation Decision，说明各元素与正文的分工；仅当用户明确要求简洁或纯文本，或内容不适合丰富排版时使用 `normal`。

#### 产品需求与 PRD

| 文档位置 | Block 与承载内容 | 使用要求 |
| --- | --- | --- |
| 标题后 | 唯一 `callout`：要解决的问题、当前关键决策或待决事项、范围边界、验收方向。 | 不复述需求背景或功能明细；与并用场景共用标题后的唯一 `callout`。 |
| 说明版本与共同语言处 | `table`：版本、状态、变更摘要；必要时补充术语或对象说明。 | 仅保留会影响当前理解和实施的变更；历史讨论和完整版本记录链接到来源。 |
| 解释问题依据处 | 短段落 + `table` / 同步引用：现状、用户或数据证据、竞品结论、关键限制。 | 主文只提炼结论及其对需求的影响；调研报告、截图和原始数据作为可追溯材料，不把背景写成独立长篇。 |
| 定义范围、规则与验收处 | `table`：模块或场景、规则、例外、验收条件、相关交互证据。 | 让同一行能看清“做什么、在何种条件下做、如何判定完成”；长规则、埋点、字段和状态台账进入 `sheet` / `bitable`。 |
| 需要理解路径或界面处 | `whiteboard`：多角色、多状态的产品流程；`img` / 设计稿嵌入：关键界面、原型或现有行为。 | 流程图只讲流转和状态，原型只证明交互；二者均不能替代规则、边界与验收的文字说明。 |
| 收束实施与维护入口处 | 链接或 `sheet` / `bitable`：埋点、项目计划、配置、附录和关联文档。 | 每个入口说明用途和维护位置；会持续变化的信息不复制到静态正文。 |

#### 技术方案与架构设计

| 文档位置 | Block 与承载内容 | 使用要求 |
| --- | --- | --- |
| 标题后 | 唯一 `callout`：推荐或已选方案、关键取舍、最重要的前置条件、风险或下一步。 | 与并用场景共用标题后的唯一 `callout`；结论必须能在后文找到约束、方案比较和验证依据，不把完整论证塞入其中。 |
| 定义问题和边界处 | 短段落 + `table`：技术目标、现状、约束、依赖、非目标和成功标准。 | 只说明影响方案选择的背景；术语、历史细节和完整依赖清单按需链接。 |
| 作出决策处 | `table`：候选路径、适用条件、收益、代价、未采用原因和结论。 | 比较维度由决策决定，避免为凑完整而罗列无关方案；已确定的前提与待验证假设需区分。 |
| 解释系统关系处 | `whiteboard`：系统边界、组件关系、数据流、调用链或迁移阶段。 | 图只负责关系和流向；接口字段、责任边界、容量数值和时序细节仍在相邻正文、表格或台账中。 |
| 说明实现契约处 | 分级步骤 + 代码块：关键实现或操作；`table`：接口、参数、兼容性、配置和迁移条件。 | 先说明代码或步骤解决什么问题，再给出最小必要片段；可执行的完整配置和接口明细进入可维护台账。 |
| 证明可落地处 | `table`：验证项、迁移或回滚条件、风险与应对；按需用 `img` / `figure` 或 `html5-block` 展示真实性能、容量、成本或稳定性证据。 | 数据图必须标明时间、口径和来源；没有真实数据或图形优势时使用表格。 |

#### 测试记录与上线验证

| 文档位置 | Block 与承载内容 | 使用要求 |
| --- | --- | --- |
| 标题后 | 唯一 `callout`：版本与环境、通过结论、上线限制、阻塞问题或必须跟进的验证。 | 与并用场景共用标题后的唯一 `callout`；先给出能否发布或验收的判断，不放环境细节、全部结果和缺陷列表。 |
| 建立结果口径处 | 两列表或短 `table`：测试对象、版本、环境、时间、数据口径、执行人和关联变更。 | 基本信息保持紧凑，足以让读者复现或判断结果适用范围。 |
| 汇总覆盖与结论处 | `table`：覆盖范围、关键场景、结果、缺陷状态、上线门槛和责任动作。 | 表格服务于“是否满足条件”的判断；按模块或风险维度组织，不逐条复制所有用例。 |
| 保留证据与明细处 | `img` / `figure` / 日志片段：关键页面、监控或错误证据；`sheet` / `bitable`：完整用例、缺陷和执行记录。 | 每份证据紧邻其证明的结论并说明上下文；正文说明明细入口、统计口径和更新时间。 |
| 说明限制与后续验证处 | 短段落或短 `table`：未覆盖范围、残余风险、降级或回滚条件、上线后观察项。 | 未覆盖项必须说明为什么未覆盖、影响何在及如何补证，不能只列“待跟进”。 |

#### 故障复盘与问题分析

| 文档位置 | Block 与承载内容 | 使用要求 |
| --- | --- | --- |
| 标题后 | 唯一 `callout`：影响与恢复状态、当前根因判断、已完成修复及最关键的后续动作。 | 与并用场景共用标题后的唯一 `callout`；先让读者知道事故是否已受控，根因尚未确认时明确其状态。 |
| 界定影响与过程处 | `table`：影响范围、用户或业务影响、关键时间点、处置动作和恢复节点。 | 时间线只还原事实与决策，不承担原因解释；时间、时区和数据口径保持一致。 |
| 解释传播与原因处 | `whiteboard`：故障传播链、依赖关系或因果路径；短段落：直接原因、系统性原因、触发条件。 | 图展示关系，正文说明证据如何支持因果判断；不要用单一异常或时间先后替代根因分析。 |
| 固定证据处 | `img` / `figure`、日志片段、告警、工单或命名链接：关键监控变化、错误信息和原始材料。 | 每项证据标明时间、来源和它支持的判断；大段日志、完整工单和原始数据放在链接或附件。 |
| 收束纠正与复查处 | `table`：修复项、防复发措施、负责人、完成条件、复查时间和验证证据。 | 行动项必须能对应一个原因或风险，并具有可验证的完成和复查条件；行动清单不能代替原因分析。 |

### Presentation Decision

- 默认 `presentation_mode: "rich"`。
- 仅当用户明确要求简洁或纯文本，或内容本身不适合丰富排版时使用 `normal`。
- `visual_plan.reason` 说明读者任务、信息更新方式，以及计划使用的正文、列表、唯一 `callout`、表格、画板、截图、Sheet/Base 等元素的分工。
- `visual_plan.blocks` 仅记录有最低数量要求的 `img`、`whiteboard`、`html5-block`；三者均无最低数量要求时使用空数组，不代表其他原生 block 不应使用。

## 第三部分 交付前检查

### 一、内容检查

- [ ] 已明确读者、文档用途和读者读完后应作出的判断或行动。
- [ ] 已补齐理解当前决策所需的背景、依赖、替代方案、约束和未决事项。
- [ ] 最核心的不确定性、提案或技术路径已被优先说明。
- [ ] 每一节都承担明确的读者任务，未按材料来源或会议顺序平铺。
- [ ] 关键取舍、假设、风险、待确认项和验证方式没有被隐藏或混写。
- [ ] 不参加此前讨论的读者，仍能理解问题、主张、依据、限制和下一步。

### 二、格式与结构检查

- [ ] 篇幅符合用户要求或默认交付尺度；长内容已按主文、附录和维护台账拆分。
- [ ] 标题、唯一 `callout`、一级标题和各节首段已构成完整阅读地图。
- [ ] 全文恰好一个 `callout`，其内容是核心结论、主张或关键决策，而不是背景摘要。
- [ ] 标题层级体现判断路径，未按字段名或材料来源机械平铺。
- [ ] 主文、表格、附件、链接和台账职责清楚。
- [ ] 表格字段口径一致，单元格未承载长段解释。
- [ ] 同一单元格中的并列条件、行为、例外或动作已使用无序列表，未以分号堆叠。
- [ ] 行动项写清动作、负责人、完成条件或待确认状态。

### 三、视觉与资源检查

- [ ] 每个表格、截图、图表、画板和附件均承担明确的信息任务。
- [ ] 架构、流程、依赖和因果关系未被误写为密集表格；精确字段未被塞入关系图。
- [ ] 高频变化的信息未制作成静态图片或不可编辑 block。
- [ ] 截图、日志和原始图表保留支持结论的版本、时间、来源和关键上下文。
- [ ] 不存在装饰性图片、重复结论卡、连续色块或无信息价值的复杂 block。
