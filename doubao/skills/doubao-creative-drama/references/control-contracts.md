# 全流程生产控制合同

本文件只定义跨阶段控制规则：来源优先级、阶段状态、确认事务、版本失效、证据边界和回炉原则。它不重复规划 schema、资产验收表、镜头阈值、视频生成参数确认 schema、接缝算法、字幕参数或成片命令。

## 本 Ref 关键要求

- 用户明确锁定的主体、动作、场景、风格、时长、比例、镜头方式、台词和禁止项不得被默认规则或创意优化覆盖；扩充只能发生在未锁定空间。
- 阶段必须按顺序推进；完整模式默认每阶段展示正式产物、等待用户明确确认后才能进入下一阶段。轻量模式按已确认视频模型分总时长上限：`seedance 2.0` 系列模型总时长 `15` 秒以内，`seedance 2.5` 模型总时长 `30` 秒以内；只保留规划页视频生成确认和最终成片确认，内部只生成用于编译 Prompt 的十五列详细分镜，不生成完整模式的其他创作配套文件。
- 凡实际调用视频生成/编辑工具或成片媒体变更工具，必须读取 `delegation.md` 并委派执行；主 Agent 保留参数确认、执行包、收口、交付、Canvas 写入/回读和用户确认责任。
- 资产、关键帧和视频片段阶段的任何图片或视频生成产物必须生成一个交付一个；非 Mobile 还必须由主 Agent 写入 Canvas 并 CLI 回读成功后，才允许继续下一个生成任务。成片阶段的裁剪片、拼接中间件、字幕测试样片和内部母版不逐项交付；每集只交付字幕策略对应的一个最终视频版本。
- 用户确认只记录真实确认事实、revision、确认原文、确认模式、影响范围和带时区时间；缺少确认记录时阻断。
- 上游修改只使实际受影响的下游失效；已确认文件不覆盖，改动创建新版本。
- 自动检查只处理阶段推进、关键产物文件、JSON 类型与枚举、计划集数与分集目录、各阶段 episode_id、时长闭合、核心 ID 去重、路径、资产引用与版本闭环、关键帧/视频覆盖关系、明确数字上限、五段式段数、manifest 映射、Prompt 与真实媒体标记、确认记录和多媒体输入清单。代码不得按字数、关键词、同义词、语速估算、文案具体程度或自然语言语义评价创意、剧情、镜头必要性、节奏、运镜、表演、口型、连续性或审美；这些只由导演规则与人工判断负责。

主观导演判断统一按对应权威 Ref 的教学算法执行：先识别触发条件和读取依据，再完成判断、分步推导、结果记录、人工检查与失败回退。不得只抄最终枚举或数量；同一算法不在本文件重复维护。

### 非视频生成的阶段迁移确认

本节只定义两个不执行视频生成的流程确认。它们不得复用或覆盖 `interaction-ask-video-clarification-ref.md` 的视频生成确认，也不得把 `proceed_project|proceed_assembly` 解释为 `generate`。

**项目执行确认**

- 仅用于完整模式且目标包含视频或成片，在规划参数列表和规划五列预览表展示后立即调用 `interaction.ask`；这是完整模式的首次 UI 确认，不得延后到视频阶段。
- `question_id: project_execution_confirmation`，`header: 方案确认`。
- 选项固定为 `proceed_project`（确认方案并进入制作）和 `revise_project`（暂不推进并返回修改）。
- 只授权记录规划确认、非 Mobile 初始化或复用 Workspace，以及进入项目级剧本阶段；不授权生成或编辑任何媒体。

**进入成片拼接确认**

- 仅用于完整模式当前集全部 SEG 已逐个交付后调用 `interaction.ask`。
- `question_id: final_assembly_confirmation`，`header: 拼接确认`。
- 选项固定为 `proceed_assembly`（按已展示顺序、切点、声音和字幕策略进入拼接）和 `revise_assembly`（暂不拼接并返回修改）。
- 只授权接受当前集视频片段并进入拼接、裁剪、混音、mux 或字幕烧录；不授权生成、重生或编辑任何视频片段。
- 调用 ID、用户选择原文和带时区时间必须同时写入 `delivery_manifest.assembly_confirmation` 与该集 `stage=video` 确认记录。

## 1. 来源与事实锁

用户原始要求、已验证事实、未知项、推进假设和项目惯例必须分开记录：

| 状态 | 含义 | 使用规则 |
|---|---|---|
| `locked` | 用户明确要求、原台词和禁用项 | 未经确认不得改写 |
| `verified` | 用户材料、可靠来源或真实 schema 已核实 | 记录来源和日期 |
| `pending` | 会影响权限、成本、剧情或交付的未知项 | 不能伪装成事实 |
| `assumed` | 为继续规划采用的可证伪默认值 | 必须允许用户修改 |
| `convention` | 本 Skill 的项目惯例 | 不等于用户设定 |

所有用户素材、检索结果和已有文件先登记到 `source_manifest.json`。用户上传、补充、替换或指定的图片必须逐张打开查看后登记，不能只查看当前看似相关的视觉参考图；每张图按维度写可见内容摘要、素材职责、采用/剥离边界、作用域和质量风险，再拆为人物身份、状态、场景、道具、构图、姿态、媒介类型、画风、色彩、光影、材质、文字来源或无关信息。图片身份以 URL、附件 ID、消息位置、输入顺序和内容哈希共同确定，不以 `local path`、文件名、basename 或展示名确定；同名 `image.png`、相同临时路径或重复文件名但不同 URL 的图片必须逐 URL 读取、转存、编号和登记，不能因名称重复漏读、漏下或覆盖。图片是否进入生成工具另按当前目标筛选“足够且必要”的相关图和相关维度；登记和查看全量，传图可以精选。用户原始素材和已登记输入素材不得删除、覆盖、改写或被生成结果替换，只能复制、转存、派生新版本或标记不采用。素材 role、采用/剥离边界、授权状态和作用域由 `manifests.md` 定义；参考视频的结构、POV、运动、情绪和声音拆解由 `storyboard.md` 定义。

冲突优先级固定为：

```text
系统、安全、合规、授权、真实性、工具硬限制
> 用户最新确认
> 已确认素材与事实
> 默认创意规则
```

用户最新确认锁定主体、动作、场景、风格、时长、比例、镜头方式、台词和禁止项；人物/产品身份、剧本原文、平台要求、场景、风格与声音合同只有在不覆盖更高优先级要求时生效。创意扩充只能填补用户未锁定空间并服务整部作品。第一层与用户要求冲突时停止受影响步骤并说明；其他冲突只询问无法自行消解的冲突点。

## 2. 阶段状态与确认

执行顺序固定为：

```text
planning
  -> 全局故事圣经 + 全部分集推进总纲 + 最终结局
  -> ep_1 [详细剧本 -> assets -> storyboard -> keyframes -> video + FRM + seam review -> final + subtitle + delivery + 用户确认]
  -> ep_2 [详细剧本 -> assets -> storyboard -> keyframes -> video + FRM + seam review -> final + subtitle + delivery + 用户确认]
  -> ...
```

完整模式先完成项目规划，再完成并确认项目级全局故事圣经、全部分集推进总纲、人物弧、伏笔账本和最终结局。分集详细剧本采用按集即时生成：当前集开始制作时先生成并确认该集详细剧本，再依次完成资产、分镜、关键帧、视频和成片确认；当前集未达到用户目标前不得启动下一集详细剧本。关键帧阶段是完整模式硬门，必须按当前集默认 `3-4` 张剧情高光 KF 逐张生成、逐张交付；非 Mobile 每张交付后立即写入 Canvas 并回读，全部完成后再做阶段确认。用户已有上游产物时可以登记复用，但必须完成当前 Skill 的完整性检查和当前集阶段确认。

轻量模式仅适用于 `drama_plan.objective.workflow_mode=lightweight` 的单条极短项目，并且 `scale_plan.total_duration_s` 不得超过当前已确认视频模型的轻量上限：默认或 `seedance 2.0` 系列模型为 `15` 秒以内；用户明确指定并确认 `seedance 2.5` 时为 `30` 秒以内。允许流程为：规划参数列表与最多 `8` 行五列预览 -> `interaction.ask` 视频生成确认 -> 内部十五列完整分镜 -> 生成并交付单条成片 -> 成片普通确认。规划页确认只有返回 `generate` 才成立，并同时授权这一次视频生成；不再调用项目执行确认，也不再设置独立剧本、资产、分镜、关键帧、视频片段或拼接确认门。确认后只把已确认预览扩充为与完整模式同列定义、同填写标准的十五列详细分镜；只能补足镜头、表演、声音、连续性和素材细节，不得修改已确认方案或另写一套故事，也不得用五列预览代替。Prompt 必须逐镜基于该十五列分镜编译。轻量模式不创建 `project_data_card.json`、`storyboard_ep_1.json`、导演总控卡、SEG 执行表、连续性账本、参考输入计划或关键帧计划；除完整分镜和 Prompt 外，只保留实际生成与追溯不可缺少的视频 manifest、请求快照、工具记录、状态与确认记录。视频生成结果按 `SKILL.md` 交付；若成片阶段产生字幕或其他内部中间媒体，只交付字幕策略对应的唯一最终版本。超过当前模型轻量上限、分集项目、用户要求完整剧本/资产/KF/片段审查，或任一阶段出现身份/连续性风险时，必须使用完整模式。

轻量状态迁移固定为：规划页取得 `generate` 后，把项目级 `script|assets|storyboard|keyframes|video` 和 `episodes.ep_1.stage_status` 中对应阶段全部写为 `merged`，设置 `current_episode: ep_1`，将 `current_stage` 与本集 `final` 写为 `in_progress`。十五列详细分镜、Prompt 编译和视频执行均在 final 流程中完成；`merged` 表示这些阶段不建立独立产物包、展示或确认门，但十五列分镜本身不得减少列或降低填写标准，也不把中间阶段改回活动状态。

阶段状态只允许 `pending|in_progress|awaiting_confirmation|confirmed|merged|invalidated|blocked`，完整结构读取 `manifests.md`。`merged` 只允许轻量模式中的 `script|assets|storyboard|keyframes|video`。`制作状态.json` 是唯一状态权威；完整模式项目级剧本确认后必须使用 `current_episode` 指向唯一允许推进的分集，并以 `current_stage: script` 开始该集详细剧本。

每一阶段按同一事务提交：

1. 读取当前状态、输入 revision 和实际文件。
2. 生成或修改正式产物，不覆盖已确认版本。
3. 完成人工内容整理，并确认产物具备进入结构检查或基础可交付检查的条件；视频和成片内容问题只内部记录，不阻断交付。
4. 将当前阶段及适用的 `current_episode` 分集状态写为 `awaiting_confirmation`，运行本阶段结构检查；项目级剧本只检查全局故事包，分集详细剧本及资产之后只检查当前集。失败时回退为 `in_progress|blocked`，不得展示为可确认产物。
5. 检查通过后只展示用户需要审查确认的正式产物。完整模式 `video|final` 目标的规划调用本文件项目执行确认，其他完整模式目标使用普通规划确认；轻量模式规划完整参数与预览后直接按 `interaction-ask-video-clarification-ref.md` 调用标准视频生成确认。若后续会生成图片或视频，有效确认写入后非 Mobile 必须立即初始化或复用 Workspace。完整模式资产、关键帧和视频片段必须逐项交付并上画布；轻量模式及成片阶段只交付并上画布字幕策略对应的唯一最终视频，内部媒体不展示。
6. 收到用户明确确认后，将确认事实追加到 `用户确认记录.jsonl`。普通阶段结合完整回复判断，不使用封闭关键词白名单；实际视频生成、重生或编辑始终必须按 `interaction-ask-video-clarification-ref.md` 取得当前 `generate`。完整模式 planning 记录使用 `project_execution/proceed_project`；轻量模式 planning 记录使用 `video_generation/generate`，同一次标准视频确认还登记到 `video_manifest.generation_confirmations`。进入拼接确认只适用于完整模式。
7. 确认记录写入成功后才推进状态，并原子同步 `current_stage`、`current_episode`、项目级 `phases` 和当前集 `stage_status`。项目级故事包确认后把 `current_episode` 设为 `ep_1`、`current_stage` 设为 `script`，并将 `episodes.ep_1.stage_status.script` 写为 `in_progress`。当前集详细剧本确认后进入本集 `assets`。当前集确认到目标阶段后，如仍有下一集，下一集始终从 `script` 开始；完整成片任务也只有当前集成片确认后才能切换。只有全部计划分集都达到 `objective.target_stage` 后才结束任务。

视频生成前的最终执行链固定为：

```text
规划前置
-> 完整分镜
-> 五段式 Prompt 编译
-> 一次集中客观预检
-> 必要时一次集中修订
-> 一次最终客观校验
-> 除硬阻塞外直接生成
```

不得把预检拆散到多份文件反复执行，也不得在最终客观校验后继续循环润色。客观预检只验证五段顺序、每镜恰好一次、时间覆盖、输入标记、台词原文、转场字段、尾态与禁区；创意力度、节奏感、审美、表演和观看效果由上游导演规则及人工判断负责，不写成代码评分。

用户修改已确认内容时，当前阶段及依赖它的下游状态变为 `invalidated`；未受影响的上游事实、资产和版本继续有效。不要手动逐个 JSON 猜改状态。规划或全剧剧本变化使用 `scripts/drama_rollback.py --project-root <项目目录> --to-stage <阶段> --reason <原因>` 做项目级回退；逐集循环中的资产及后续变化必须追加 `--episode ep_N`。若后续集仍为 `pending|invalidated`，工具只回退目标集；若后续集已启动或完成，默认拒绝以避免越权失效，只有确认跨集依赖确实受影响时才显式追加 `--cascade-later-episodes`。该工具只更新 `制作状态.json` 并追加操作日志，不删除旧产物。

用户在任一阶段追加或替换含人物、场景、道具、构图或风格等有效视觉参考维度的图片时，按采用维度、资产类别和稳定 ID 计算影响范围。若新图用于替代已确认资产或改写项目视觉类型，必须创建对应 CHR/SCN/PROP/STYLE 新版本，并使所有依赖旧版本或旧 `project_visual_mode` 的状态图、细节图、关键帧、视频输入图、分集资产引用和已生成视频片段失效；未依赖该资产或视觉类型的产物继续有效。不得只替换当前单张图片后继续使用旧关联图。

返修定位不等于执行授权。视频工具返回后发现的问题只做内部记录，不触发自动重生。凡再次调用视频生成或编辑工具，都必须由用户明确提出，并重新按 `interaction-ask-video-clarification-ref.md` 展示完整参数、取得当前 `generate`。

### 全量与增量确认

首次阶段交付始终使用全量确认。已有有效全量确认后，返修按实际影响分为：

| 类型 | 判定 | 用户可见交付 | 确认记录 |
|---|---|---|---|
| 重大修改 | 改变核心因果、人物动机或弧线、结局、集间边界、身份、风格、模型、时长、画幅或大范围下游 | 重新提供当前阶段完整文件和整体摘要 | `confirmation_mode: full` |
| 局部微调 | 错别字、单句润色、局部动作澄清、未改变含义的格式修正，且影响范围可以精确列出 | 只展示修改文件、变更摘要、修改前后和影响范围 | `confirmation_mode: incremental` |

增量确认仍必须等待用户明确回复，不能把“修改完成”自动当成同意继续。内部确认记录只登记本次实际变化文件 `changed_artifacts` 和影响范围 `impact_scope`，不要求保存全量指纹或重算哈希。无法可靠判断影响范围、推翻方案或重做产物时，一律按重大修改处理并使用 `confirmation_mode: full`。

规划完成后必须展示参数列表和最多 `8` 行的五列预览。完整模式视频目标使用本文件的项目执行确认；轻量模式参数列表必须满足 `interaction-ask-video-clarification-ref.md` 的完整生成参数要求，并直接调用该 Ref 的标准视频生成确认。轻量模式的 `generate` 同时确认规划并授权当前唯一视频，确认后只允许扩充分镜细节，不得改写已展示内容。

每次只允许推进一个用户确认门。完整模式下，规划、项目级故事包、当前集详细剧本、当前集资产、当前集分镜、当前集关键帧、当前集视频片段和当前集完整视频都必须分别展示和确认；当前集达到目标前不得进入下一集详细剧本。完整模式视频生成前按 `video-batch-confirmation.md` 展示一张本批次合并参数表和一张本批次五列分镜表，并调用视频批次 `interaction.ask`；每批连续 `1-2` 个 SEG。每个视频必须生成一个、交付一个、非 Mobile 上画布并回读一个，完成后才可生成下一个。全部片段交付后，只有 `target_stage=final` 才调用拼接确认；`target_stage=video` 使用普通阶段确认并结束。轻量模式只在规划页调用一次视频生成 `interaction.ask`，内部完整分镜不展示、不确认；字幕关闭时生成后直接交付唯一视频，字幕开启时先内部完成字幕链再只交付字幕版，随后等待成片普通确认。返修或重生才重新展示单视频批次参数并再次取得 `generate`。

面向用户的交付与内部执行记录严格分离，具体沟通边界以 `SKILL.md` 的“Prompt 文件与可见交付”为准。规划参数确认表是对话输出，不属于内部 Markdown 产物。中途进度只允许概括当前创作阶段，不播报正在读取、创建、计算、校验或写入的内部文件。

### 委派边界

主 Agent 负责阶段顺序、确认事务、版本失效和用户交付责任；实际工具执行是否必须委派、允许委派的阶段、数量限制、交接包内容、上游产物、禁止行为和收口检查统一读取 `delegation.md`，本文件不重复定义。

委派执行者只能写入交接包逐文件指定的产物和必要记录，不能确认阶段、改变上游合同、扩大目标阶段或替主 Agent 解释例外；白名单外新增或修改文件按越权阻断。

## 3. 版本、引用与失效

- `project_data_card.json` 是角色、场景、道具和音色身份及状态时间线的事实权威。
- `asset_registry.json` 是共享媒体资产版本权威；`asset_usage_ep_N.json` 记录本集采用的共享资产快照、本集新建的专属/状态资产，以及从其他分集复用的 approved 资产索引。
- 全局剧本包是全剧故事权威；单集剧本包只能细化，不得另建核心因果或结局。
- 所有下游 manifest 和视频单次请求快照记录 `project_data_card_revision`、上游路径与采用版本；哈希字段如保留，仅作为恢复辅助，不作为轻量 lint 硬门。
- 上游正文、数据卡或共享资产 revision 改变时，只使实际依赖旧版本的下游产物失效。
- 下游只能使用 `approved` 资产；`draft|reviewed|rejected|superseded` 不得进入正式生成。
- 已确认文件不得覆盖。修改建立 `_vNN` 新版本，保留旧版、变更原因和回滚关系。
- 稳定 ID、`ep_N` 目录及文件后缀必须一致；完整命名规则读取 `manifests.md`。

## 5. 运行完整性、证据与基础检查

跨阶段的“能生成”不等于“可交付”。所有阶段必须闭合以下证据链：

- 每个已确认阶段绑定当前 revision、正式产物路径和用户确认记录；下游只能消费匹配该 revision 的上游产物。
- 规划的 `OPEN001` 在第 1 集直接落到剧本开场合同，并由分镜首镜证据证明。后续集可以变体，但必须保留 `OPEN001` 引用和具体变体理由。
- 表演谱、情绪曲线和色彩脚本要么声明覆盖对象并逐项落地，要么写 `not_applicable` 与具体原因；空数组且无解释不能视为完成。
- planned SEAM 是生成前目标，FRM、observed seam 和 verified cut 是生成后事实；实际帧、核验结论和最终切点不得提前写入分镜或关键帧产物。

接缝完整性遵循：

- `continuous` 只允许规定的不变量连续推进；`elliptical` 允许计划内时间、空间、构图或状态变化，但仍必须保持 `required_invariants`。
- 任何未登记在 `permitted_deltas` 的变化都不是允许变化；先返回分镜修订衔接卡。若责任在已生成视频，只内部记录可选重生责任片段，用户主动要求修改前不调用视频工具。
- 跨集 `EPSEAM` 使用相同原则。`ep_2` 及以后首个 SEG 必须消费上一集结果、声音状态、未决钩子和 `required_invariants`；`continuous` 必须再消费上一集真实尾帧，`elliptical` 按已确认的新起点和允许变化执行，不能只写“保持一致”。

工具调用成功、文件存在或结构校验通过都不等于内容合格：

- `drama_lint.py` 只检查结构化且可确定的事实：文件、类型、枚举、ID、路径、版本、引用、状态、数量、顺序、时长、输入与输出对应关系。Prompt 只检查五段数量、媒体标记、锁定台词和文件哈希等精确合同，不判断自然语言写得是否具体、精彩或合理。
- 额外人工复核只关注会破坏阶段推进、版本追溯、用户确认、真实媒体交付、字幕对齐、片段顺序或相邻接缝的关键问题。
- 图片必须实际查看，音频必须可试听，视频必须具备可渲染/可播放资源。视频和成片生成后优先交付；完整播放、抽帧或接缝观察只作为内部记录。
- 自动检查不能冒充镜头质量、运镜质量、是否拆断完整动作、状态变化、审美、表演、口型、动作物理或剧情判断；这类判断只写自然语言备注或返修建议，不设置固定机器阻断。
- 只有客观交付错误，例如文件缺失、损坏、无法解码、无视频流、画布写入/回读失败，才可写为 `blocked` 并阻断。主观或内容问题不阻断交付，用户主动要求修改前不得调用视频生成/编辑工具。
- 当前未实际执行的黑帧、冻结帧、响度、OCR 越界或遮脸检测，不得在报告中标记为已通过。

结构校验默认静默执行。除非用户明确询问，不向用户输出内部检查统计、机器可读结构名称、机器字段、检查期望、内部文件名称、内部机制或运行配置。存在阻断问题时只说明需要用户处理的具体问题；可自主修复的结构缺口不对用户复述字段名或文件名，只说已补齐制作所需信息或追溯记录。凡是用户不能直接行动的内部原因，都不得作为对外解释。

## 失败、重试与回炉

重试预算、`V/A/F/S/N` 缺陷编号和返回层级只读取 `troubleshooting.md`。本文件保留三条跨阶段原则：

1. 只修改与证据直接相关的变量，不用多项同时变化掩盖根因。
2. 只重做失败产物及其必要上游，已确认且未受影响的产物继续复用。
3. 返回最早出错层级，不用下游裁切、转场、调色、混音或重复生成掩盖上游错误。

## 6. 文件操作与恢复

- 修改前先读正式文件、状态和输入 revision。
- 大范围本地重写先写同目录临时文件，校验通过后原子替换；失败时保留诊断。
- 外部生成无法与本地状态形成原子事务。先保存不可变的新版本并验证真实产物，再提交状态引用。
- 部分成功时盘点返回 ID 和文件，只补失败项。
- 每次调用和阶段变更追加 `操作日志.jsonl`；字段和恢复规则读取 `manifests.md`。
- 恢复任务时先读取最后一次成功操作、当前确认记录、正式文件和实际媒体证据，再从 `last_successful_operation` 后继续；聊天摘要不是完成依据。

## 7. 自动检查与交付

正式交付前必须同时满足：

- 当前阶段结构检查通过；视频和成片已完成基础可交付检查。
- 所有引用路径、版本和状态与实际文件一致；哈希字段不作为轻量流程硬门。
- 受影响下游不存在未处理的 `invalidated|blocked`。
- 最终成片按 `delivery.md` 完成规定的基础可交付检查。
- 当前阶段状态已写为 `awaiting_confirmation` 且结构检查通过；随后图片和视频统一按 `SKILL.md` 的交付前置路由和 `cli/README.md` 完成当前环境交付，音频和文档用当前宿主可用的文件展示工具交付，Prompt 文件仅在用户明确要求查看 Prompt、排查或交接时展示。图片交付必须可渲染直显；视频交付必须传入可渲染视频资源本体；该能力不可用时停止并说明能力缺口。不得只返回文字路径、链接、裸 URL、HTML 标签、工具自带预览、旧人工通知/展示工具、硬编码不存在的工具名或伪造工具调用。
