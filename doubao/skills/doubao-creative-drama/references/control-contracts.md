# 全流程生产控制合同

本文件只定义来源优先级、阶段状态、确认事务、版本失效和跨阶段交接。制作模式、视频方案选择和生成授权只读 `interaction-ask-video-clarification-ref.md`。

## 1. 来源与事实锁

用户明确要求、已核实事实、未知项、推进假设和项目惯例分开记录：

| 状态 | 含义 | 使用规则 |
|---|---|---|
| `locked` | 用户明确要求、原台词和禁用项 | 未经许可不得改写 |
| `verified` | 用户材料、可靠来源或真实 schema 已核实 | 保留来源和日期 |
| `pending` | 影响权限、成本、剧情或交付的未知项 | 不冒充事实 |
| `assumed` | 为继续规划采用的可证伪默认值 | 允许用户修改 |
| `convention` | 项目惯例 | 不等于用户设定 |

优先级为：系统、安全、授权、真实性和工具硬限制 > 用户最新确认 > 已确认素材与事实 > 默认创意规则。创意扩充只填补未锁定空间；发生真实硬冲突只暂停受影响操作并说明。

集数/组织方式缺口按视频交互 Ref 第 10 节先澄清，不以默认单条代替用户答复。用户明确答复属于真实要求；用户交由模型建议的规模属于 `assumed`，不写成用户锁定要求或真实批准。模式与规模结论按实际作用域继承，同一已回答问题不因进入新阶段、换执行主体或更换记录载体而再问；必要建议随已有方案确认，真实回复按本节原规则记录。局部任务不依赖的全剧未知项可保留未知，不能虚构集数、未来条目或确认记录来填满模板。

用户素材与检索依据登记到 `source_manifest.json`。首次收到及新增、替换的图片逐张查看、按维度登记；后续复用已有拆解，只重读新增、变化、当前相关或存在疑点的素材，不为每次生成重新打开全库。图片按真实 URL、附件 ID、消息位置/输入实例及哈希区分，不按同名文件去重；采用维度、剥离边界、职责与范围见 `assets.md` 和 `manifests.md`。查看来源是理解输入，不另设资产质检轮次。

原始图片、视频、音频、文本及用户原句不删除、不覆盖、不被生成结果替换。只复制、转存、派生新版本或标记不采用。未知的未来媒体不登记成已存在输入。

## 2. 阶段状态与确认

### 完整模式

单部微电影/电影：规划 -> 唯一完整剧本（含必要故事与设定）。连续多集：规划 -> 全局故事与全部分集总纲、结局 -> 当前集详细剧本。两者再按本次交付目标衔接：所需资产 -> 分镜 -> 批次生成确认 -> 视频 -> 必要合成 -> 交付；到目标即停止。

上述是内容依赖顺序。已有合格正文、分镜或有效批准资产时，继承其真实版本、适用范围和批准来源，只补当前目标的缺口；不重新写相同内容、重生媒体或重复确认。单部微电影/电影按单集唯一正文组织，不写分集总纲及空跨集文件。只做某集、某段或局部修改时保持原项目模式，准备该范围实际依赖，不重走全部阶段；未来集详细内容、无用途的类别和目标之后的制作均不补造。缺失的必要依据仍须补齐，不能将未批准素材或过期版本冒充合格上游。

多集按 `ep_1 -> ep_2 -> ...` 逐集完成目标阶段后再开始下一集详细剧本，不预写全部分集详细对白或未来资产。完整模式保留规划、故事方向、当前集剧本、资产和分镜等创作方案确认；生成结果和最终视频直接交付，不增加视频验收、最终验收或交付后检查。当前集目标已交付即能推进下一集，不把用户未回复当成确认，也不为推进伪造确认记录。若目标只是剧本或分镜，最终交付后不等待额外认可；其中必要的上游创作确认仍保留。资产全为同一适用范围内的已批准复用、没有新造型/用途/版本选择时，在现有使用记录写明真实批准来源并将 assets 记 merged，直接进入分镜；有新增采用决定时仍展示并确认。

单集只展示并确认同一完整剧本一次；该回复明确覆盖项目故事与本集正文时，按同一原文、时间、revision 分别记录两个作用域，直接进入资产，不再次展示或询问相同正文。多集全局总纲与各集详细剧本内容不同，保留各自确认。

### 轻量模式

先确定 `objective.target_stage`，只做到该终点；轻量合并的是配套文件和常规阶段门，不是把所有任务改为成片制作。

轻量适用范围由视频交互 Ref 第 10 节确定；难度不降低创作标准，也不新增阶段门。共用决定和状态约束按 `planning.md` 保存在已有规划，具体剧情、全部人声及逐镜变化保存到唯一正文/主表，内容按需展开，不受用户概览行数限制。

| 交付终点 | 准备、确认与停止位置 |
|---|---|
| `planning` | 交付采用方向和适用参数后停止；不为收尾等待认可 |
| `script` | 一次写全正文，必要规划与正文一起交付即结束；用户要改再改，不询问视频生成或补确认 |
| `assets` | 只完成必要资产设计、复用或已授权生图并展示采用；不编分镜或视频 Prompt |
| `storyboard` | 完成唯一十五列主表，连同必要规划交付后停止；不准备生成授权或最终 Prompt |
| `video` | 准备故事、主表和当前 Prompt，展示全片概览及本批完整人声/参数，取得 `generate` 后调用；本次目标片段逐项交付后停止，不做成片 |
| `final` | 视频授权与上行相同；每个源片返回即交付，完成已要求拼接/字幕等制作，直接交付唯一最终版本 |

落实视频交互 Ref 第 10 节要求的组织方式/集数后，内部内容可以在展示前准备；用户明确要求先审某一步时先展示，不升级模式。非视频目标不使用 `generate`。纯创作目标正常完成并交付即可收尾，不要求用户再回复认可；若用户明确要先选择方案或暂缓下一步，才按其要求等待。实际认可和交付完成分开记录，不能把交付写成 confirmed。实际生图前仍先明确方案和消耗，不把文字审阅或视频授权当作生图已完成。

视频任务首次 `generate` 同时确认规划并只授权列明批次；后续批次按视频交互 Ref 展示和确认，不反复展示整份规划。没有视频调用不安排该核对。

只保存目标所需正文/主表、真实来源、实际请求和交付记录。剧本目标正文是唯一正文；分镜/视频目标的故事与全部人声直接落实在主表，不再复制独立剧本。纯分镜的分段、计划边界、衔接不变量和参考职责写在同一主表的分段说明，不为此创建视频 manifest。实际进入视频制作时，从主表提取段序、镜号范围、计划边界和依赖到视频 manifest，再登记实际素材及待绑定尾帧，不补造完整模式的数据卡、分镜 JSON、导演卡、独立 SEG 表或账本。

状态只在此定义：取得适用确认后 `planning=confirmed`；`planning` 目标留在本阶段。其他目标设置 `current_episode=ep_1`、`current_stage=target_stage`，只将目标之前已包含在采用内容中的阶段写为 `merged`，目标之后一律保留 `pending`。目标阶段不写 `merged`：创作目标实际交付后写 `completed`，只有收到真实认可才写 `confirmed`；轻量纯创作目标的规划准备记 `completed`，视频任务仍须真实 generate 后 planning=confirmed。`video|final` 在执行中写 `in_progress`、实际目标交付后写 `completed`。项目 `phases` 与本集同阶段同步；不为合并上游虚构确认记录。中间 `merged` 不代表创作内容可以省略。

### 状态事务

- `制作状态.json` 是唯一状态源；状态枚举和字段只读 `manifests.md`。
- 完整模式进入后续制作所需的创作确认：读取当前版本 -> 完成产物 -> 展示并写 `awaiting_confirmation` -> 收到真实回复后追加确认记录并写 `confirmed` -> 推进。不逐阶段运行 lint 或质检。
- 视频与成片：按实际工具状态、保存和交付事实更新；交付目标完成写 `completed`，不写虚假的 `confirmed`。`completed` 表示目标执行和交付完成，不表示批准、质量审定或用户验收；纯创作终点同样可用，但不得据此越过终点制作视频。
- 项目级 `phases` 聚合全部分集进度；仅当前集允许活动。以前集可用 `confirmed|merged|completed` 中对应阶段合法的完成态，未来集保持 `pending|invalidated`。

### 非视频生成的阶段迁移确认

完整模式且目标含视频/成片时，规划参数与预览展示后调用项目执行 `interaction.ask`：确认按方案进入制作或返回修改。它只授权规划和进入创作，不代替各批视频 `generate`。

已确认项目/分镜方案包含的普通拼接、裁剪、混音或字幕制作，完成生成后直接执行，不另设常规“进入拼接确认”。实际剪辑方向或用户锁定方案发生重大变化时，主 Agent 展示变化并确认相应方案；若产生新增视频模型调用，仍必须另外取得本次视频生成授权。`assembly_confirmation` 只保存确实发生的独立方案变更确认，常规制作留空。

`proceed_project`、`generate`、`proceed_assembly` 只是内部授权语义，不是宿主工具必须返回的字段或调用参数。不得用枚举、旧记录、模板原文或无回复冒充授权。

### 全量与增量确认

首次创作方向或重大修改展示完整受影响内容并记录 `confirmation_mode=full`；已有有效全量确认后的局部修改只展示变更、前后文和影响范围，记录 `incremental` 与基线 revision。不能确定影响范围时按重大修改处理。只对确实需要确认的方案执行此规则，不把内部格式修正、媒体绑定、已授权执行细化或正常交付重新变成确认门。

视频方案选择、全部生成确认、批次范围与失效规则只读视频交互 Ref；同一回复可覆盖其明确展示的相同内容，不能覆盖未展示的未来生成或新增额度。

## 3. 版本、引用与失效

- 完整模式正文是剧情权威；数据卡是身份与状态权威；共享资产注册表是媒体版本权威。轻量模式从采用故事、逐镜主表和真实素材取得相同事实，不补建文件。
- 十五列完整分镜表是逐镜执行内容的唯一来源；需要阅读稿时从主表即时组织展示，不另存第二份逐镜正文。完整模式的分镜 JSON 统一组织分组、边界、首尾状态和依赖，不另写一套动作/台词。
- 下游记录实际上游路径、revision 与采用版本；Prompt 哈希绑定真正保存且提交的原文，其余恢复哈希可选。已确认版本不原地覆盖。
- 上游变化只使实际依赖旧版本的下游失效，保留未受影响的上游、资产及成功结果。失败执行包只修失败项，不要求整轮重来。
- 完整模式正式资产采用 `approved` 版本；该值表示已采用的创作依据，不证明视频生成效果。
### 用户修改后的状态更新

以下操作由 mainagent 在落实用户修改或已知执行问题时完成，不是生成后的检查步骤；不增加审片、试听、质量验收或自动返修。字段、状态枚举和日志结构沿用 `manifests.md`，推进和确认仍按本文件第 2 节执行。

1. 先读取 `制作状态.json`、当前内容版本及实际引用，确定最早需要修改的阶段，以及范围是项目级还是指定集。只定位本次修改涉及的依赖，不重新检查整部作品。指代或锁定要求有真实冲突时，按视频交互 Ref 进行必要澄清。
2. 规划变更：依 `planning.md` 更新规划内容和 revision，只将实际依赖旧规划的下游写为 `invalidated`。按现有模式和目标处理规划状态：
   - 完整模式：只有第 2 节原有路径要求独立规划确认时，才转到 `current_stage=planning`、`current_episode=null`，展示本次规划后将 `phases.planning` 写为 `awaiting_confirmation`，收到适用的真实确认后写为 `confirmed`；其余情况按原有目标规则更新，不新增或取消完整模式的确认步骤。
   - 轻量模式的 `planning|script|storyboard` 目标：保持 `current_stage=objective.target_stage`；除 `planning` 目标外，`current_episode=ep_1`。受影响规划准备期间写 `in_progress`，准备完成后写 `completed`；目标内容修改并交付后，目标阶段写 `completed`，只有收到真实认可才写 `confirmed`。不另问规划、故事或阶段通过确认，用户明确要求先选择或先审阅的情况仍按其要求处理。
   - 轻量模式的 `assets` 目标：保持资产目标及实际单集索引，规划准备完成写 `completed`，资产采用与实际生图沿用原有确认和授权规则，不新增规划确认。
   - 轻量模式的 `video|final` 目标：保持目标阶段和 `current_episode=ep_1`，受影响规划准备期间写 `in_progress`；将修改内容并入本批视频方案和参数，按视频交互 Ref 实际取得本批 `generate` 后，才将 `phases.planning` 写为 `confirmed`。不在本批生成确认之前另设规划、全局故事或剧本确认，不沿用修改前的生成授权。
3. 故事或结局变更：按现有模式和唯一内容来源落实，不因“结局”一词统一转入项目级剧本阶段。完整模式多集任务修改全局设定、分集总纲或全剧结局时，才将项目级 `phases.script` 写为 `in_progress`、`current_stage` 写为 `script`、`current_episode` 写为 `null`；只使依赖旧全局内容的已有单集详细剧本及下游失效，不同时启动各集详细剧本，完成原有路径要求的全局确认后逐集继续。完整模式单部作品仍修改 `ep_1` 的唯一完整剧本，不另建全局总纲或增加一轮故事确认；单集同一正文沿用第 2 节的一次确认规则。轻量剧本目标直接修改唯一正文，轻量分镜、视频或成片目标直接修改唯一主表中的故事、人声和逐镜内容；保持实际目标阶段及 `ep_1` 索引，不补独立全局剧本、总纲文件或全局确认。轻量规划或资产目标只修改本次目标实际需要的规划或设计，不扩展到后续阶段。涉及规划内容的变更按上一条，交付和授权按第 2 节原有目标规则执行。
4. 仅指定集正文、资产、分镜、视频或成片变更：先按下一条确定实际影响范围，保留有效全局基线。完整模式需要重新进入该集制作阶段时，按既有逐集顺序将 `current_episode` 指向该集、`current_stage` 指向最早需要修改的阶段，实际开始后才将该集对应 `stage_status` 写为 `in_progress`；轻量模式保持第 2 节规定的实际目标与单集索引。已完成集仅修改错别字、格式或不改变已采用剧情与媒体方案的文字，且不影响后续集时，保留当前推进指针，只保存目标集新版本并按第 2 节的交付事实和真实确认更新其记录，不重新开启其他制作阶段。只将实际依赖旧版本的下游写为 `invalidated`，项目级 `phases` 按第 2 节的作用域与聚合规则同步；其他集不因本次局部修改而被重置或写为 `in_progress`，尚未启动且未受影响的未来集保持 `pending`。
5. 局部变更默认不扩大到其他集。后续集已经启动或完成时，依据已有采用版本和跨集引用确定本次修改的影响，不为判断依赖而检查生成视频的质量。后续集不受影响时，只修改目标集及该集实际依赖旧版本的下游；保留后续集原有内容、状态、批准依据和成功结果，不因其已经启动而阻塞目标集修改，也不要求跨集确认。确有跨集影响时，只对实际受影响的集及阶段记录失效，展示对应修改范围，并仅完成原有路径确需的确认后按既有逐集顺序继续，不使全部后续集一律失效。影响范围因必要信息缺失或锁定项冲突而无法确定时，只暂停受影响范围，由 mainagent 按视频交互 Ref 澄清，不擅自扩大修改范围或增加独立的跨集批准步骤。历史调用结果仍如实记录，不能将过去成功改写为工具失败；上述状态处理不授权自动重生成或重试。
6. 一次变更完成时，将 `制作状态.json.revision` 递增一次，更新实际变更内容的 revision，并在现有操作日志记录原因、原版本、新版本、作用范围、失效项和保留项。不得删除或覆盖原始素材、历史确认和已确认内容版本；新内容按原命名规则保存。状态与日志写入失败时按已有恢复规则处理，不声称更新完成。状态更新不授权新增媒体调用，生成、编辑和重试仍须取得相应本次授权。


## 4. 跨阶段交接

| 阶段 | 输入与输出 | 权威 |
|---|---|---|
| 规划 | 用户目标与来源 -> 采用故事方向、参数和预览 | `planning.md` |
| 剧本 | 采用方向 -> 按规模合并正文、必要数据与当前集合同 | `scriptwriter.md` |
| 资产 | 已定故事与当前需求 -> 实际采用的复用/新增媒体与文字视觉合同 | `assets.md` |
| 分镜 | 正文、必要素材 -> 唯一逐镜主表及完整模式必要统筹信息 | `storyboard.md` |
| 视频 | 主表、人声、实际输入 -> 真实视频结果与请求记录；仅按需提取续段尾帧 | `video.md` |
| 成片 | 已生成片段、既定顺序/边界/声音 -> 唯一最终视频与实际制作记录 | `delivery.md` |

开场承诺、主要亮点、人物办法、必要反馈、声音及视觉策略沿同一 ID/镜号链落实。跨集延期后果先指向已确认总纲的承诺；不为当前集校验提前创建未来集详细合同。到目标集开始制作时才把承诺绑定到实际镜头。规则见 `storyboard.md`。

## 5. 执行、交付与恢复

- 视频与成片媒体变更的强制委派及权限边界按 `delegation.md`，不以简化为由改成主 Agent 直调。执行者只读本次模式和任务真正需要的上下文，只写白名单文件。
- 原始调用、真实任务 ID、结果、输出与状态更新保留在已有记录中，不为同一事实另建 Markdown/JSON 质检报告或证明。结构字段齐全、工具成功或完成交付不等于艺术质量保证。
- 原生人声、转场和连续性在创作与生成前落实；生成后不审片、不验收、不自动返修。必要尾帧提取、字幕 ASR、实际下载/交付工具状态按对应 Ref 执行，不扩为检查流程。
- 工具明确失败、输入缺失或交付失败时只恢复受影响操作，保留已生成结果与有效记录，不把未完成下载、未返回结果或未渲染卡片说成成功。产后归档与媒体交付分别记录，归档失败不倒退交付状态、不阻断下一项已授权生成，也不重生或补建媒体对象。
- 正式图片／视频交付格式及成功判据只按 `media-delivery.md`。能力缺失仅说明真实缺口，不用裸路径或虚构工具冒充交付，不增加阶段检查或用户验收。
- 修改和恢复先读当前状态、实际文件及最后成功操作。外部调用部分成功只补失败项；每次真实调用与重要阶段变化追加操作日志。
