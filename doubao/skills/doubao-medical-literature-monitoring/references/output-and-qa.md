# 飞书进展报告

报告面向医生阅读，不展示检索过程或监控系统。

## 文档结构

1. 报告开头直接显示日期范围和浅色**总结 callout**，不添加独立的“进展总结”标题。callout 内用无序列表覆盖正文中大多数值得提及的进展；主动扩大时间范围时先显示原始窗口和实际纳入跨度。
2. 用户原话有明确 `focus_question` 时，在顶部总结 callout 后增加独立的**你关注的问题进展章节**。章节 H1 固定写成“你关注的问题进展：{section_title}”，使用全角冒号且冒号后不加空格；该章节不用 callout、高亮块或彩色背景。忠实呈现问题与必要背景，回答正文紧接背景直接开始，不添加固定的“基于本期证据的阶段性回答”小标题。正文可按内容自由使用短段、要点或按需小标题，不强制无序列表，但不要堆成大段文字。证据日期、来源主体/研究简称、直接支持的内容与简洁编号必须就近融入同一句或相邻句；可适度加粗关键结论、重要数字或证据边界，不整段加粗。不在段末堆编号，不再另列“对应时间”。证据边界另起一段。没有明确问题时省略整个章节，不生成空占位。
3. **本期进展总览画板**：用 `scripts/render_overview_whiteboard.py` 生成 SVG，只包含具体核心观察与三类彩色分类卡，不再重复生成全部条目的原题/来源矩阵。
4. **最新医学资讯**：可包含临床实践、访谈、会议、机构动态与合格二次报道。
5. **共识、指南与监管进展**。
6. **研究进展**：按本期内容自然分组，不固定套模板。
7. **临床试验进展**：仅在用户关注试验注册、招募、状态变化或结果发布且本期有合格增量时出现。
8. **灵感启发**：结合用户重点与本期证据，每条使用独立的浅黄、浅蓝或浅绿色 callout，只提出待研究、待验证的问题。
9. **订阅设置**：仅首期或非定时触发时放在文档最后，展示关注主题领域、重点标注话题、更新频率、来源范围偏好；存在明确问题时另展示持续关注的问题与背景，注明它由用户原话预填而非新增必答项。来源偏好用于检索加权和排序，不是白名单。`action=scheduled_run` 时省略整个章节。

没有内容的章节可以省略。搜索成功但没有合格增量时写“本期未检出可核验的新研究或进展”；用户只要关键/重大研究而没有合格论文时写“当前核心期刊未检索到符合条件的有效更新”，不以低质量论文补位；主检索和必要兜底均不可用时写“本期检索未完整，暂不能判断是否无更新”。通常不要展示检索过程、问题范围、覆盖情况、基线、当前结论、task_id、checkpoint、内部台账或运行日志。唯一例外是主动扩大日期：报告开头必须显示原始窗口、实际纳入时间跨度和扩展原因，并区分原始窗口新增与扩大窗口补充。

## 唯一运行文件与交付真源

检索、筛选和同批明显重复项整理完成后写入一次 `report-data.json`，再由期刊分区脚本原地富化一次。正文、总览 SVG、顶部总结内容和灵感都从最终文件生成。定时运行不单独生成或维护跨期去重清单；只整理同批明显重复项，并在写作时避免重复显而易见的历史旧内容。不另建人工清单、证据台账、第二份报告 JSON 或逐批快照。使用原生 JSON/UTF-8 写入，保留可读中文；不要用 shell 拼接转义 JSON，也不要把整份 JSON 再包进字符串字段。

顶层必须写 `requested_date_range` 与 `included_date_range`。主动扩展时再写 `window_expanded=true` 和 `window_note`；报告开头与聊天摘要必须展示两个时间范围，避免用“本周/近一周”概括实际包含数月前论文的内容。

用户原话有明确关注问题时，顶层另写：

```json
{
  "focus_question": "希望通过持续文献关注回答的问题",
  "question_context": "与问题判断直接有关的人群、场景、技术路线、比较或争议背景",
  "focus_question_answer": {
    "section_title": "瑞米布替尼疗效、安全性与适用人群",
    "points": [
      {
        "text": "一个独立的阶段性判断",
        "supporting_display_ids": ["研究-01", "指南-02"],
        "evidence_dates": [
          {"display_id": "研究-01", "date": "2026-07-20", "date_type": "发表日期"},
          {"display_id": "指南-02", "date": "2026-08-01", "date_type": "发布日期"}
        ]
      }
    ],
    "evidence_boundary": "当前证据不能回答或仍不确定的部分"
  }
}
```

`focus_question_answer` 是证据综合，不是搜索前预设。`section_title` 只存用于固定标题“你关注的问题进展：{section_title}”中的简洁关注主题，例如“瑞米布替尼疗效、安全性与适用人群”。不得在字段内重复“你关注的问题进展：”，不要使用空泛的“问题回应”、直接复制整段问题，或附加“近期进展”“阶段性判断”等套话。`points` 按疗效、安全性、适用人群或其他实际证据维度自然拆分，每项只写一个清楚判断并保留 `supporting_display_ids`；这是数据层的证据映射，不要在正文末尾把所有编号一次性堆出。不要为了凑数量重复同一结论。

每个 point 必须用 `evidence_dates` 保留该点支持条目的对应时间，并与 `supporting_display_ids` 一一对应。`date_type` 按来源语义写“发表日期”“指南发布日期”“监管动作日期”“结果首次发布日期”“试验记录更新日期”或“资讯发布日期”；日期只使用已核对到的精度，来源只有月份或年份时保留原精度，不补造日。渲染时不另起一行写“对应时间”，而是写成“6 月 26 日，VICTORION-Mono China 研究显示……（研究-01）”这样的自然叙述；如同一判断有多项证据，将各日期和编号放在各自支持的句子旁，不用一个模糊时间覆盖全部，不产生“【研究-01】研究-01（发表日期……）”的重复。这里不写检索日期、访问日期、报告生成日期，也不把研究随访时长、入组时间或会议报道日期冒充论文发表日期。没有足够直接证据时，简洁写“本期证据尚不足以回答”并说明缺口，不用间接材料硬拼结论。

每个 `report_item` 必须有：

- 建议提供 `category` 并使用 `news`、`guideline`、`research`：资讯对应 `news`，共识/指南/监管对应 `guideline`，论文/预印本/临床研究对应 `research`；漏填时渲染器从编号或类型字段推断；
- 简短、易区分的 `display_id`，通常写作 `研究-01`、`预印本-02`、`资讯-03`、`共识-04`、`监管-05`；它用于画板索引；
- 易读中文概括 `short_label`，写清“谁/什么 + 哪项变化或发现 + 关键方向”，不能只是论文题名截断；
- 逐字保留的 `original_title` 与可点击 HTTP(S) `source_url`；
- 日期、来源身份和真实 `journal_name`、`record_source`、`preprint_platform` 或 `source_name`；ClinicalTrials.gov 条目另写 `trial_id`、`trial_delta_type`、`trial_status`、`trial_phase`；
- 可选的 `journal_rank_2025`、`journal_impact_factor`、`journal_quartile`、`journal_metric_year`、`journal_metric_source`；其中 `journal_rank_2025` 只由本地匹配脚本写入，其他指标只有检索结果或可信期刊信息源明确返回时才写；
- `support_level=snippet|abstract|official_full`、非空 `support_excerpt` 与非空 `body_blocks`。
- 存在 `focus_question` 时，增加 `question_thread={relation,relevant_evidence,bounded_inference}`。`relation` 说明该条与问题直接、间接或背景性的关系；`relevant_evidence` 只写来源片段/摘要/官方内容明确支持的信息；`bounded_inference` 说明这些信息对问题回答增加了什么，以及仍不能推出什么。与问题没有可解释关系的条目不应为凑数纳入。

`metadata_only` 只留在内部候选池，不能进入正文、画板、总结或灵感。`summary_points`、`inspiration_items` 建议引用入围条目的 `supporting_display_ids`。`key_observations` 支持以下两种等价写法，优先使用更简洁的字符串数组：

```json
{
  "key_observations": [
    "本期研究开始关注真实世界实施条件。",
    "多中心验证结果仍需结合目标人群判断。"
  ]
}
```

需要保留证据映射时，也可写成 `{"text":"…","supporting_display_ids":["研究-01"]}`。渲染器兼容两种形式，不要为确认字段格式读取脚本源码。

二次报道如显示具体 `underlying_action_date`，需同时有 `underlying_source_url` 或 `underlying_source_key`；否则写“底层动作原日期：未核验”。媒体门户、自媒体、社交平台和企业转述页默认按二次报道处理。PubMed、PubMed Central/PMC、Europe PMC、Crossref 是收录或检索平台，不是期刊。PMC 命中的最终候选先用一次批量 PubMed ESummary、Europe PMC core 或 Crossref 元数据取得真实 `journal_name`；有刊名时必须显示期刊而不是 PMC。仍无真实刊名时显示“收录平台：PubMed Central”或实际来源，不得猜测刊名。

## 画板与正文

先运行本地期刊分区富化，再生成画板：

```bash
node scripts/match-journal-rank.js \
  --report-json report-data.json \
  --in-place

 python3 scripts/render_overview_whiteboard.py \
  --input report-data.json \
  --output overview.svg
```

直接调用 Skill 包内脚本，不需要先查看 `--help` 或读取脚本源码；不复制脚本或索引到报告目录，不创建 `assets`、推导 `__dirname`、检查软链接或搬运文件。期刊脚本自动发现内置索引；仅在环境已经给出替代索引时可选传 `--index <path>`。返回 `journal_rank_index_unavailable` 时直接省略分区并继续渲染，期刊富化不能成为报告完成门。写 JSON 时正文引号优先使用中文全角引号 `“”`；渲染器会保守兼容正文中误写的未转义 ASCII 双引号、字符串形式的 `key_observations`，并根据 `display_id`/类型字段推断一次漏填的类别。`report-data.json` 仍须是合法 JSON；如有语法错误，只修复这一份交付真源，不另建转义副本。不要因可容错的轻微格式问题检查行号、阅读源码或逐条返工。

生成 XML 时，在“本期进展总览”标题下直接写：

```xml
<whiteboard type="svg" path="@overview.svg"></whiteboard>
```

`overview.svg` 与 XML 放在同一工作目录，由文档工具直接读取。不要上传 SVG、不要生成公网图片 URL、不要改用 `<img>`，也不要重新阅读 XML 语法来选择另一种插入方式。

画板分类卡显示全部入选条目的 `display_id + short_label`，不显示逐条 `original_title`、期刊/来源、日期或链接矩阵；这些可追溯信息完整保留在正文。条目多时分类卡纵向扩展，四周保留明显留白。核心观察和概括标题必须具体、自洽、可独立阅读；只看画板能理解本期发生了什么，但不要求画板承担完整题录索引。

正文逐条呈现资讯、共识/指南/监管和研究时，标题前尽量沿用画板中的同一 `display_id`，例如 `【资讯-01】`、`【研究-02】`，便于图文互相定位。标号用于图文相互定位。

正文表达保持灵活：

- 不规定每条进展的二级标题，可用连续段落、短列表、小表、callout 或补充图表；
- `snippet` 通常写 1–2 个紧凑段落，`abstract/official_full` 可写 2–4 个段落或等量信息，逐字复用 `body_blocks`；
- 每个条目的**标题本身**都用 `<a href="{source_url}">` 创建超链接，包括资讯、研究/预印本、共识/指南和监管；仅在段末放来源不合格；
- 标题下一行用 `<span text-color="gray">` 显示日期和真实来源。研究有真实 `journal_name` 才写“期刊”；否则写“来源”；预印本写“平台”。PMID/DOI 有则显示、无则省略。`journal_rank_2025` 非空时追加“期刊级别：…（2025）”；其他影响因子或分区可得时也必须带指标口径和年份。没有则整段省略，不显示“未知/待核验”；
- ClinicalTrials.gov 条目标题链接 `https://clinicaltrials.gov/study/{NCTId}`，灰字显示与 `trial_delta_type` 对应的“首次发布/结果首次发布/记录更新日期”、NCT、状态和可得分期；注册平台不写成期刊。普通 `record_update` 没有跨期差异支持时只写“试验记录更新”，不得升级为状态改变、结果发布或疗效结论；
- 经研究报道反查到论文时，研究标题链接论文/数据库/DOI 落地页，不能链接二次报道；如报道本身也有独立资讯价值，可作为单独资讯条目并链接报道页；
- 存在 `focus_question` 时，每个条目正文后用一段简洁的“问题线索”呈现 `question_thread` 的关系、相关证据和有限推导；不强制拆成三个固定小标题，但必须让读者分清来源直接事实与模型推导。直接回答问题的条目优先写，间接或背景性条目明确标注；
- 关键变化和数字可适度加粗；浅色 callout、高亮块、表头底色和图表适度使用，避免整页高亮；
- 顶部总结内容、画板和灵感不得比正文证据更具体或更确定。

## 忠实于来源写作

按已经取得的搜索结果、摘要或官方内容组织正文：

- `snippet` 只改写 `support_excerpt` 可见事实；有摘要或官方全文后才写其明确给出的对象、设计、结果和限制；
- 保留主体、样本/检测对象、研究类型、未来时态、关键阴性/无差异结果和证据成熟度；
- 不得因订阅主题把脑脊液改写成血液，也不得补造数字、阈值、成本效益、实施流程或会议议题；
- 新闻不能单独证明疗效、安全性、诊断性能或推荐强度；
- 不得把“与关注问题相关”本身当作支持答案的证据；推导应从来源可见事实出发，跨越人群、干预、结局或研究设计时明确降级，并写出不能外推的边界；
- 没有指南/监管依据时，灵感只提出待验证问题，不写成临床行动建议。

## 文档创建与交付

用同一 `report-data.json` 生成 `monitor-report.xml` 与 `overview.svg`，并放在同一工作目录。连接器激活提示属于文档生成后的聊天内容，生成报告数据和 XML 时保持医学报告独立；首期飞书报告在“确认创建”段后结束。正常路径从该目录使用相对 `@monitor-report.xml` 一次创建一份新文档，不追加旧文档。已有飞书创建能力及参数说明时直接执行；只有首次创建明确返回参数或 XML 语法错误时，才读取与错误直接相关的 create/XML 参考。若完整 create 明确因载荷或长度限制失败且没有留下可用文档，将已完成 XML 拆成最多 3 个连续 section 写入同一 document ID。文档生成后交付实际 URL，可通过 `present_files` 提供文档入口。

## 聊天正文引用

聊天正文、首期报告交付摘要、多轮追问和定时推送摘要中，积极在关键进展或判断所在句段使用引用角标。`general_search` 和 `seed_medical_search` 实际返回的内容均可使用 `<RichMediaReference>["真实来源URL"]</RichMediaReference>`；URL 取工具真实返回的 `url/link`，与来源题名成对保留，所引内容须支持相邻主张。组件放在所支持句段的标点之后，尤其是句号之后；同处多个来源使用纯 URL JSON 数组。其他来源可在相关句段用可点击的完整题名或可读研究简称引用。已用角标或就地链接引用的来源，不在聊天文末重复列“参考来源”。飞书文档 XML 继续使用可读文字超链接，不写入聊天富引用组件；文档原有来源和参考文献要求保留。

首期聊天给出本期摘要和 `[查看完整飞书进展报告]({本次实际 URL})` 后，再在聊天 response 的末尾区域完整展示订阅邀请与配置。若 `action=scheduled_run`，只回复订阅频率对应窗口（近 1 周、近 2 周或近 1 个月）的进展摘要和本期新报告链接，不附上一期报告链接，不再次邀请订阅，也不展示“确认创建”或订阅配置表：

> 🔔 我可以定期帮你跟踪「{关注主题领域}」的最新研究、指南监管与医学资讯，并推送新的进展报告。需要订阅推送吗？我已经根据该领域特点和本次检索结果生成以下默认配置；如无调整，回复 **确认创建** 即可。你也可以进一步告诉我最想重点关注的子领域、技术路线、人群或进展类型。

紧接着以 Markdown 配置表展示“关注主题领域、重点标注话题、更新频率、来源范围偏好”；存在明确关注问题时再加“持续关注的问题与背景”。聊天 response 不能以“详见飞书文档”代替该表；配置表及“确认创建”提示必须完整位于回复末尾区域。

使用检索前的 PubMed 路由检查结果控制一条可选连接器提示：只有本轮开始时没有可调用的 `pubmed-medical-literature` PubMed MCP、并实际使用了 PubMed URL fallback 时，才在飞书文档生成后，把下面一句拼接到最终聊天，作为整条聊天回复的最后一行；首期放在订阅配置表之后，定时推送放在本期摘要和新报告链接之后。MCP 可用时不显示；已明确可用但仅本次调用临时失败时也不显示，避免把临时故障误报为未激活。

> 如需提高 PubMed 检索质量，可以在「连接器」中激活添加「PubMed/医学文献 MCP」。

这句只属于聊天交付，不写入飞书医学报告、`report-data.json`、用户可见定时任务 Prompt、订阅配置或内部状态，也不算再次邀请订阅。除这句条件提示外，订阅配置表之后不再追加其他内容。

如果用户原话已包含明确关注问题，邀请订阅时自然补一句“我会继续围绕「{focus_question}」及上述背景更新阶段性回答”，并在配置表中展示该问题与背景；不要要求用户再次复述。

未收到更新频率时，根据领域变化速度和完整首期检索的有效进展密度，在“每周一次、每两周一次、每月一次”中选择一个默认建议。首期检索不完整、样本太少或快慢信号矛盾，导致无法可靠判断医学进展快慢时，默认建议每两周一次；未知不等于更新慢，不得因此默认月更。若首期必须从近 7 天扩大到近 30 天才找到足够有价值的内容，优先建议每两周一次；若完整检索需要扩大到近 90 天或有效增量仍稀疏，优先建议每月一次。不要仅因用户最初询问“一周”就默认周更；用户明确选择的频率仍优先。未收到具体推送日/时间时在建议频率后写“推送时间待确认”，不得擅自变成“每周一”。聊天摘要和订阅邀请可适度使用 1–3 个 emoji，正式医学事实与风险表述仍使用文字。

创建订阅后，首次定时推送等待一个完整已确认周期：每周一次满 1 周、每两周一次满 2 周、每月一次满 1 个日历月。用户可见任务说明只写“近 1 周”“近 2 周”或“近 1 个月”，不展示具体首次运行日期；报告内仍显示运行时计算出的实际纳入日期范围。
