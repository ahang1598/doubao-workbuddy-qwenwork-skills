# 飞书进展报告

报告面向医生阅读，不展示检索过程或监控系统。

## 文档结构

1. 标题下放浅色 **本周总结 callout**，用无序列表覆盖正文中大多数值得提及的进展。
2. **本期进展总览画板**：用 `scripts/render_overview_whiteboard.py` 生成 SVG，包含具体核心观察、三类彩色分类卡与全部条目的原题/来源矩阵。
3. **最新医学资讯**：可包含临床实践、访谈、会议、机构动态与合格二次报道。
4. **共识、指南与监管进展**。
5. **研究进展**：按本期内容自然分组，不固定套模板。
6. **灵感启发**：结合用户重点与本期证据，每条使用独立的浅黄、浅蓝或浅绿色 callout，只提出待研究、待验证的问题。
7. **订阅设置**：放在文档最后，展示关注主题领域、重点标注话题、更新频率、来源范围偏好；注明来源偏好用于检索加权和排序，不是白名单。

没有内容的章节可以省略。搜索成功但没有合格增量时写“本期未检出可核验的新研究或进展”；主检索和必要兜底均不可用时写“本期检索未完整，暂不能判断是否无更新”。通常不要展示检索窗口、问题范围、检索覆盖、基线、当前结论、task_id、checkpoint、内部台账或运行日志。唯一例外是：用户主动要求近 7 天、严格窗口内权威增量不足而主动扩大日期时，在报告开头简洁说明扩展原因和实际补充区间，并区分严格窗口新增与扩大窗口补充。

## 唯一运行文件与交付真源

检索、筛选和同批明显重复项整理完成后，只写一次最终 `report-data.json`。正文、总览 SVG、本周总结和灵感都从它生成；`seen_source_keys` 如需维护也从入选条目顺手生成，不作为交付必备字段。不另建人工清单、证据台账或逐批快照。使用原生 JSON/UTF-8 写入，保留可读中文；不要用 shell 拼接转义 JSON，也不要把整份 JSON 再包进字符串字段。

每个 `report_item` 必须有：

- 建议提供 `category` 并使用 `news`、`guideline`、`research`：资讯对应 `news`，共识/指南/监管对应 `guideline`，论文/预印本/临床研究对应 `research`；漏填时渲染器从编号或类型字段推断；
- 简短、易区分的 `display_id`，通常写作 `研究-01`、`预印本-02`、`资讯-03`、`共识-04`、`监管-05`；它用于画板索引，不是飞书回读格式门；
- 易读中文概括 `short_label`，写清“谁/什么 + 哪项变化或发现 + 关键方向”，不能只是论文题名截断；
- 逐字保留的 `original_title` 与可点击 HTTP(S) `source_url`；
- 日期、来源身份和真实 `journal_name`、`record_source`、`preprint_platform` 或 `source_name`；
- 可选的 `journal_impact_factor`、`journal_quartile`、`journal_metric_year`、`journal_metric_source`；只有检索结果或可信期刊信息源明确返回时才写；
- `support_level=snippet|abstract|official_full`、非空 `support_excerpt` 与非空 `body_blocks`。

`metadata_only` 只留在内部候选池，不能进入正文、画板、总结、灵感或去重键。`summary_points`、`inspiration_items` 建议引用入围条目的 `supporting_display_ids`。`key_observations` 支持以下两种等价写法，优先使用更简洁的字符串数组：

```json
{
  "key_observations": [
    "本期研究开始关注真实世界实施条件。",
    "多中心验证结果仍需结合目标人群判断。"
  ]
}
```

需要保留证据映射时，也可写成 `{"text":"…","supporting_display_ids":["研究-01"]}`。渲染器兼容两种形式，不要为确认字段格式读取脚本源码。

二次报道如显示具体 `underlying_action_date`，需同时有 `underlying_source_url` 或 `underlying_source_key`；否则写“底层动作原日期：未核验”。媒体门户、自媒体、社交平台和企业转述页默认按二次报道处理。PubMed、Europe PMC、Crossref 是来源，不是期刊；没有真实期刊字段时显示“来源：PubMed/Europe PMC/Crossref/其他数据库”，不得猜测刊名。

## 画板与正文

运行：

```bash
python3 scripts/render_overview_whiteboard.py \
  --input report-data.json \
  --output overview.svg
```

直接使用上述命令，不需要先查看 `--help` 或读取脚本源码。写 JSON 时正文引号优先使用中文全角引号 `“”`；渲染器会保守兼容正文中误写的未转义 ASCII 双引号、字符串形式的 `key_observations`，并根据 `display_id`/类型字段推断一次漏填的类别。不要因这些轻微格式问题检查行号、阅读源码或逐条返工。

生成 XML 时，在“本期进展总览”标题下直接写：

```xml
<whiteboard type="svg" path="@overview.svg"></whiteboard>
```

`overview.svg` 与 XML 放在同一工作目录，由文档工具直接读取。不要上传 SVG、不要生成公网图片 URL、不要改用 `<img>`，也不要重新阅读 XML 语法来选择另一种插入方式。

画板上层分类卡显示 `display_id + short_label`，下层矩阵显示同一编号的 `original_title + 真实来源`。全部 `report_items` 都要出现；条目多时纵向扩展，四周保留明显留白。核心观察和概括标题必须具体、自洽、可独立阅读；只看画板能理解本期发生了什么。

正文逐条呈现资讯、共识/指南/监管和研究时，标题前尽量沿用画板中的同一 `display_id`，例如 `【资讯-01】`、`【研究-02】`，便于图文互相定位。标号是可读性设计，不是交付门：不检查是否连续，不精确比较方括号、连字符和空格，也不因偶发标号差异修改或重建文档。

正文表达保持灵活：

- 不规定每条进展的二级标题，可用连续段落、短列表、小表、callout 或补充图表；
- `snippet` 通常写 1–2 个紧凑段落，`abstract/official_full` 可写 2–4 个段落或等量信息，逐字复用 `body_blocks`；
- 每个条目的**标题本身**都用 `<a href="{source_url}">` 创建超链接，包括资讯、研究/预印本、共识/指南和监管；仅在段末放来源不合格；
- 标题下一行用 `<span text-color="gray">` 显示日期和真实来源。研究有真实 `journal_name` 才写“期刊”；否则写“来源”；预印本写“平台”。PMID/DOI 有则显示、无则省略。影响因子或分区可得时追加一个即可，必须带指标口径和年份；没有则整段省略，不显示“未知/待核验”；
- 经研究报道反查到论文时，研究标题链接论文/数据库/DOI 落地页，不能链接二次报道；如报道本身也有独立资讯价值，可作为单独资讯条目并链接报道页；
- 关键变化和数字可适度加粗；浅色 callout、高亮块、表头底色和图表适度使用，避免整页高亮；
- 本周总结、画板和灵感不得比正文证据更具体或更确定。

## 来源内写作门

只核对已经取得的搜索结果、摘要或官方内容，不新增逐篇回读：

- `snippet` 只改写 `support_excerpt` 可见事实；有摘要或官方全文后才写其明确给出的对象、设计、结果和限制；
- 保留主体、样本/检测对象、研究类型、未来时态、关键阴性/无差异结果和证据成熟度；
- 不得因订阅主题把脑脊液改写成血液，也不得补造数字、阈值、成本效益、实施流程或会议议题；
- 新闻不能单独证明疗效、安全性、诊断性能或推荐强度；
- 没有指南/监管依据时，灵感只提出待验证问题，不写成临床行动建议。

## 一次创建、一次轻量回读

用同一 `report-data.json` 生成 XML 与 SVG，创建一份新文档，不追加旧文档。创建成功后用 `scope=full` 回读同一文档一次；`scope=outline` 不算正文确认。

回读只确认三件事：文档正文非空；报告标题和主要章节存在；入选条目的标题可见且没有明显整章丢失。不要运行 `verify-artifact`，不要逐字比对 `display_id`、正文段落或列表顺序，也不要把方括号、空格、加粗等呈现差异判为失败。`【监管 - 01】`、`【监管-01】` 与 `监管 - 01` 均可接受；内容完整时直接交付 URL，不为修饰性格式差异重建文档。

报告回读用于验证飞书写入完整性，不等同于来源回源。不要因为需要回读报告，就在搜索结束后逐篇 `web.fetch` 论文原页。

首期聊天首行写 `[查看完整飞书进展报告]({本次实际 URL})`，再给本期摘要并邀请：

> 🔔 我可以定期帮你跟踪「{关注主题领域}」的最新研究、指南监管与医学资讯，并推送新的进展报告。需要订阅推送吗？我已经根据该领域特点和本次检索结果生成以下默认配置；如无调整，回复 **确认创建** 即可。你也可以进一步告诉我最想重点关注的子领域、技术路线、人群或进展类型。

未收到更新频率时，根据领域变化速度和首期有效进展密度，在“每周一次、每两周一次、每月一次”中选择一个默认建议。若首期必须从近 7 天扩大到近 30 天才找到足够有价值的内容，优先建议每两周一次；若需要扩大到近 90 天或有效增量仍稀疏，优先建议每月一次。不要仅因用户最初询问“一周”就默认周更；用户明确选择的频率仍优先。未收到具体推送日/时间时在建议频率后写“推送时间待确认”，不得擅自变成“每周一”。聊天摘要和订阅邀请可适度使用 1–3 个 emoji，正式医学事实与风险表述仍使用文字。
